## 本节重点

### 动静态库的制作

写程序时，你实现了一套数学函数，同事也想用。如果每次发源码，对方要重新编译，费时费力还容易泄露细节。于是人们把编译好的二进制目标文件打包成"库"——像一个密封的工具箱，别人拿走去用，既看不到内部实现，也不用再编译。

库分两种：静态库像复印机，把工具说明印到你的程序书里，出门自带工具；动态库像公共图书馆，你的书里只写一张借书卡，运行时再去借。

#### 静态库的制作

静态库本质是把多个 `.o` 文件用归档器打包，命名必须遵守 `lib名字.a` 的规矩。假设你实现了加法和减法，分别编译成目标文件后，用 `ar` 打包：

```bash
gcc -c add.c -o add.o      # 只编译不链接，生成目标文件
gcc -c sub.c -o sub.o      # 同上
ar -rc libmymath.a add.o sub.o   # r=插入或替换，c=创建库；把.o打包成静态库
```

> **静态库就是 .o 文件的压缩包，链接时编译器会把需要的代码直接拷贝进可执行文件。**

#### 动态库的制作

动态库需要在内存中被多个进程共享，因此编译时要加 `-fPIC` 生成"位置无关码"——大白话说就是这段机器码无论被操作系统放到内存哪个地址都能正确执行，因为里面不涉及硬编码的绝对地址。再用 `-shared` 告诉链接器生成共享对象：

```bash
gcc -fPIC -c add.c -o add.o      # 生成位置无关的目标文件
gcc -fPIC -c sub.c -o sub.o
gcc -shared -o libmymath.so add.o sub.o   # 生成动态库，名字必须是 lib名字.so
```

> **动态库制作的核心是 `-fPIC` + `-shared`，缺一个都会出问题。**

---

### 动静态库的使用

编译器默认只在系统目录找库，你自己的库需要显式告诉它位置。

#### 静态库的使用

假设 `main.c` 里调用了库中的函数，通过 `-L` 指定库所在的目录，通过 `-l` 指定库名（去掉前缀 `lib` 和后缀 `.a`）：

```bash
gcc main.c -L. -lmymath -o myapp   # -L. 表示在当前目录找库，-lmymath 链接 libmymath.a
```

如果库之间有依赖，比如 `liba.a` 依赖 `libb.a`，要把被依赖的库放在后面：`gcc ... -la -lb`。

#### 动态库的使用

编译命令和静态库看起来一样：

```bash
gcc main.c -L. -lmymath -o myapp   # 编译时链接动态库 libmymath.so
```

但直接运行 `./myapp` 常会报错 `cannot open shared object file`。原因在于：编译阶段的链接器通过 `-L` 找到了库，但运行阶段的动态加载器（ld.so）不知道去哪找这个文件。静态库没有这个问题，因为它的代码已经被拷贝进了可执行文件。

---

### 动态库的查找

运行时加载器按固定顺序搜索动态库，最常用的三种告诉方式如下。

第一种，把库路径加进 `LD_LIBRARY_PATH` 环境变量，适合临时测试。第二种，在 `/etc/ld.so.conf.d/` 下新建 `.conf` 文件写入路径，再执行 `ldconfig` 刷新缓存，适合系统级永久配置。第三种，也是最自包含的做法，是在编译时直接把运行时搜索路径写进可执行文件：

```bash
gcc main.c -L. -lmymath -Wl,-rpath,/home/you/lib -o myapp   # -Wl, 把后面的参数传给链接器
```

> **动态库出错 90% 是路径问题：编译时找得到，运行时找不到，一定要区分链接期和运行期。**

---

### 可执行程序 ELF 格式

Linux 下的可执行文件、目标文件、动态库都遵循 ELF 格式（Executable and Linkable Format，可执行可链接格式）。你可以把它理解成一份详细的"装箱单"，告诉操作系统：我有哪些部件、每个部件在文件里什么位置、加载到内存时该怎么摆放。

ELF 在磁盘上主要由四部分组成：ELF 头（说明文件类型、入口地址等基本信息）、程序头表（描述加载到内存的"段"）、节头表（描述链接用的"节"）以及实际内容。其中 `.text` 装代码，`.data` 装已初始化的全局变量，`.rodata` 装只读常量，`.bss` 为未初始化的全局变量占位（不占磁盘空间但占内存）。

```bash
readelf -h myapp     # 查看 ELF 头信息
readelf -S myapp     # 查看节头表：链接器看这里，知道有哪些 .text .data 等节
readelf -l myapp     # 查看程序头表：加载器看这里，知道怎么把文件映射到内存
```

> **链接器看节（Section），加载器看段（Segment）；段是节的集合。**

---

### 可执行程序的加载过程

输入 `./myapp` 后，操作系统并不会把整个文件无脑塞进内存，因为程序有代码、有数据，有些部分暂时用不到，全部载入会浪费物理内存。

加载流程如下：bash 先 `fork` 出子进程，子进程调用 `execve` 陷入内核；内核读取 ELF Header 确认文件合法，再读取 Program Header Table，按照每个段的描述以页为单位将文件内容映射到虚拟地址空间；如果程序是动态链接的，内核不会直接跳转到 `main`，而是先把动态链接器（`ld-linux.so`）加载进来，由它负责加载依赖的动态库并完成重定位，最后才移交控制权给用户程序的入口。

```text
shell fork 子进程
    → execve 启动加载
    → 内核读 ELF Header / Program Header
    → 按段描述映射到虚拟地址空间
    → 若动态链接：加载 ld-linux.so
    → 动态链接器加载 libxxx.so 并重定位
    → 跳转到程序入口 → main
```

---

### 虚拟地址空间和动态库加载的过程

每个进程都有独立的虚拟地址空间，通过页表映射到物理内存。动态库加载时，操作系统利用这一点实现"一份物理代码，多份虚拟共享"：同一份动态库在物理内存中只存在一份，但不同进程的页表把它映射到各自虚拟地址空间的共享区，既省了物理内存，又互不干扰。

具体过程是：动态链接器根据 ELF 的 `.dynamic` 节找到需要的库名，按查找规则找到文件后，将其映射到共享区。由于编译时用了 `-fPIC`，库代码在任意虚拟地址都能运行；但程序里调用库的地址还是空的，动态链接器会填写两张表——GOT（全局偏移表）和 PLT（过程链接表）——把跳转地址修正为库在内存中的实际位置，这个过程叫重定位。如果某个进程修改了动态库中的全局数据，会触发写时拷贝，给该进程单独复制一份数据页，代码页继续保持共享。

> **动态库的核心优势在于：物理内存只存一份代码，靠页表映射到各进程虚拟空间；修改数据时写时拷贝保证独立。**

## 1. 什么是库

### 代码复用的烦恼

你写好了一套字符串处理和文件 IO 的工具函数，隔壁同事想用，你直接把 `.c` 源码发过去。很快你会发现三个麻烦：源码暴露了实现细节；每个人都要重新编译一遍，浪费时间；一旦你想更新，得通知所有人替换文件。库就是为了解决这个麻烦诞生的：它把代码提前编译成机器能直接读懂的 0 和 1 指令（即二进制），打包成一个独立文件。别人只需要知道"有哪些功能、怎么调用"，不需要拿到源码，也不需要自己重新编译那部分代码。

> **库的本质是屏蔽实现细节：对使用者暴露接口声明，对操作系统暴露二进制指令。**

### 库的本质是 .o 的集合

你之前用 `gcc -c` 把 `.c` 编译成 `.o`，这个 `.o` 已经是机器能读懂的二进制指令了，只是还不能单独运行。库文件本质上就是这些 `.o` 的"组织形式"：静态库是把多个 `.o` 打包成一个压缩包（Linux 下后缀 `.a`）；动态库也是由 `.o` 组成的二进制文件（Linux 下后缀 `.so`），链接时直接交给 `gcc`/`g++` 使用即可，不需要编译器再次翻译。

| 类型 | Linux 后缀 | Windows 后缀 | 类比 |
|------|-----------|-------------|------|
| 静态库 | `.a` | `.lib` | 把代码复印件钉进你的程序 |
| 动态库 | `.so` | `.dll` | 运行时大家共享同一份代码 |

### 在系统里找到库

你的系统能跑起来，正是因为底层依赖了大量现成的库。用 `ls` 查看系统预装的 C 库：

```bash
ls /lib/x86_64-linux-gnu/libc-2.31.so   # Ubuntu 的 C 动态库本体
ls /lib/x86_64-linux-gnu/libc.a         # Ubuntu 的 C 静态库
ls /lib/x86_64-linux-gnu/libstdc++.so.6 # Ubuntu 的 C++ 动态库（软链接指向 libstdc++.so.6.0.19）

ls /lib64/libc-2.17.so                  # CentOS 的 C 动态库
ls /lib64/libc.a                        # CentOS 的 C 静态库
```

这些文件就是系统级"代码罐头"，你的 `printf`、`malloc` 最终都是调用这里面的指令。

### 库里需要写 main 函数吗

不需要。`main` 函数是程序的"大门"，操作系统通过它来启动一个可执行程序；而库是"工具箱"，里面的函数等着被别人调用。比如 `libc.so` 里有 `strlen`，但它自己从不运行，只有你的程序调用了 `strlen`，库里的对应代码才会被加载进内存执行，因此程序的入口始终掌握在写 `main` 的人手里。

### 本节要用的素材

我们会把上一节封装好的 `my_stdio.h / my_stdio.c`（自定义文件 IO）和 `my_string.h / my_string.c`（自定义字符串处理）编译成真正的库文件，供其他程序调用。

## 2. 静态库

你写好了 `my_stdio.c` 和 `my_string.c`，里面封装了 `my_strlen`、`mfopen` 等好用函数。如果想给同事复用，直接发源码会暴露实现细节，而且对方每次都要重新编译；直接发几十个 `.o` 文件又难以管理。我们需要一种"成品"交付方式：把编译好的二进制代码打包，再配上说明书。静态库就是解决这个问题的——它把你写好的代码在编译时直接复印一份，贴进最终的可执行文件里，程序一旦生成，出门就不再依赖原来的库。gcc 默认优先找动态库，找不到同名 `.so` 才会用 `.a`；如果你要求全部静态链接，需加 `-static`（已学选项）。

---

### 2-1 静态库生成

#### 用 ar 把 .o 文件捆成库

`ar` 是 GNU 归档工具，可以理解成专门把多个 `.o` 文件捆成一包的"打包机"。`rc` 是两个选项的组合：`r` 表示如果包里已有同名文件就替换，`c` 表示如果包不存在就创建。假设你已经用 `gcc -c` 得到了 `my_stdio.o` 和 `my_string.o`，现在把它们打包成 `libmystdio.a`：

```bash
ar -rc libmystdio.a my_stdio.o my_string.o  # 将两个.o文件捆成静态库，libmystdio.a是库文件名
```

库文件名惯例以 `lib` 开头、以 `.a` 结尾，中间是库的名字。`ar` 做的事很简单：把 `.o` 文件原封不动地收进包里。你可以用 `-tv` 查看里面收了什么：

```bash
ar -tv libmystdio.a  # t=list列出内容，v=verbose显示详细信息，能看到里面包含my_stdio.o等
```

#### Makefile 自动化

用 Makefile 把编译和打包串起来，避免手敲冗长命令：

```makefile
libmystdio.a: my_stdio.o my_string.o       # 目标：生成静态库；依赖：两个.o文件
	ar -rc $@ $^                           # $@代表目标(libmystdio.a)，$^代表所有依赖(.o文件)

%.o: %.c                                   # 推导规则：每个.c生成同名的.o
	gcc -c $<                              # $<代表第一个依赖(当前.c文件)，-c只编译不链接

clean:                                     # 清理编译产物
	rm -f *.o libmystdio.a

output:                                    # 打包发布目录
	mkdir -p stdc/include stdc/lib         # 创建存放头文件和库文件的目录
	cp *.h stdc/include/                   # 把函数声明的头文件拷贝到include目录
	cp *.a stdc/lib/                       # 把静态库拷贝到lib目录
	tar -czf stdc.tgz stdc                 # 把整个stdc目录压缩成.tgz发布包
```

执行 `make` 生成库，执行 `make output` 就得到一个标准格式的发布包。

> **库发布 = 头文件 + 库文件一起打包，使用者拿到的是两样东西。** 头文件是"说明书"，告诉编译器有哪些函数、参数是什么；`.a` 文件是"工具箱"，里面是真正的二进制代码。缺了任何一样，别人都使唤不动你的库。

---

### 2-2 静态库使用

别人拿到你的库后，在 `main.c` 里像平常一样包含头文件并调用函数：

```cpp
#include "my_stdio.h"
#include "my_string.h"

int main() {
    char s[] = "hello";
    int len = my_strlen(s);   // 调用静态库里的函数
    // ...
    return 0;
}
```

一个可执行程序可能同时用到多个库，有的静态、有的动态，这是完全允许的。下面三个场景覆盖了实际开发中最常见的编译方式。

#### 场景一：库和头文件在系统路径

如果你把 `my_stdio.h` 拷贝到 `/usr/include/`，把 `libmystdio.a` 拷贝到 `/usr/lib/` 或 `/usr/local/lib/`，就相当于"安装"到了系统里。gcc 默认会搜索这些标准位置，所以编译时只需要告诉它链接哪个库：

```bash
gcc main.c -lmystdio   # -l后接库名，gcc自动去系统路径搜索头文件和库文件
```

> **库也要被"安装"到系统中的思想**：别人的库最终要么像本场景这样"安装"进系统路径，以后编译直接 `-l` 即可；要么像下面场景那样，每次编译都手动指路径。所谓"安装"本质上就是把头文件和库文件拷贝到 gcc 默认会搜索的标准目录里。

#### 场景二：库和头文件与源码同目录

开发阶段通常不往系统目录塞文件。如果 `main.c`、`my_stdio.h`、`libmystdio.a` 都在当前目录，gcc 不会自动在这里找库，必须显式声明库路径：

```bash
gcc main.c -L. -lmystdio   # -L. 表示库在当前目录(.); -lmystdio指定要链接的库名
```

#### 场景三：库和头文件有独立路径

工程变大后，头文件和库往往放在专门的目录里，比如头文件在 `lib/include/`，库在 `lib/mylib/`。这时三个选项要同时上场：

```bash
gcc usercode.c -I lib/include/ -L lib/mylib/ -lmyc   # -I=头文件路径; -L
gcc usercode.c -I lib/include/ -L lib/mylib/ -lmyc   # -I=头文件路径; -L=库文件路径; -l=库名(去掉lib前缀和.a后缀)

如果你要链接任何第三方库或自己写的库，只要它没放在系统默认路径里，就必须把这三个选项用熟。`-I`（大写i）是给编译器指"去哪找 `.h` 头文件"；`-L` 是给链接器指"去哪找 `.a` 库文件"；`-l`（小写L）是告诉链接器"具体拉哪个库进来"。

> **库名规则：去掉前缀 `lib`、去掉后缀 `.a`/`.so`。** 比如文件名叫 `libmystdio.a`，编译器只认 `mystdio` 这个名字，写成 `-lmystdio`；系统里的 `libc.so` 写成 `-lc`。这个约定一定要记准，少一个字母都找不着。

---

#### 验证静态库的本质特性

静态库最关键的特征是"一次性拷贝"。链接阶段，链接器把库中你实际用到的代码片段复制一份，贴进最终的可执行文件里。这意味着：

```bash
gcc main.c -L. -lmystdio -o myapp   # 编译链接阶段：必须有 libmystdio.a 才能通过
./myapp                             # 运行：正常执行
rm libmystdio.a                     # 运行后故意删掉静态库
./myapp                             # 程序照样跑，因为代码已经住在可执行文件里了
```

> **静态库拷贝到可执行文件里，所以运行时删掉库照样跑。** 你交付给用户的只是一个可执行文件，不需要附带任何库。

## 3. 动态库

### 动态库要解决什么问题
如果你用静态库，编译时会把库的机器码完完整整复制进每个可执行文件。想象十个程序都用到同一个打印函数，结果硬盘上存了十份一模一样的打印代码，内存里运行时也加载十份，磁盘和内存都被重复占满。动态库的出现就是为了共享：库的代码在磁盘上只留一份，程序本身不包含库的完整代码，运行时才由操作系统把库加载进内存；多个进程通过虚拟地址空间映射到同一份物理内存中的库代码，磁盘和内存都大幅节省。

### 动态库的核心机制
动态库（shared library）是程序运行时才去链接的代码仓库。可执行文件内部并不存放外部函数的完整机器码，只记录一张“入口地址表”——也就是用到哪些函数、去哪里找它们。程序启动前，操作系统负责把动态库从硬盘搬进内存，这个过程叫动态链接。得益于虚拟内存机制，物理内存中只需存在一份动态库的代码，所有需要它的进程各自在自己的虚拟地址空间里“映射”到这一份物理代码上，既省内存又省磁盘。

---

### 3-1 动态库生成

#### Makefile 规则与关键选项
动态库的文件名必须以 `lib` 开头、`.so` 结尾，例如 `libmystdio.so`。生成时需要两条编译规则：先把 `.c` 编译成位置无关的目标文件，再把目标文件链接成共享库。

```makefile
libmystdio.so: my_stdio.o my_string.o
	gcc -o $@ $^ -shared          # -shared：告诉gcc生成共享库（动态库）格式，而不是普通可执行文件

%.o: %.c
	gcc -fPIC -c $<               # -fPIC：生成位置无关码，让库的代码加载到内存任意地址都能执行
```

#### 位置无关码 fPIC
`fPIC`（Position Independent Code）大白话就是“不挑地址的代码”。动态库被加载到内存的哪个位置是不确定的，如果代码里写死了“我必须在 0x400000 这个位置”，一旦系统把它放到别处就会崩溃。`-fPIC` 让编译器生成一种灵活的寻址方式，无论搬到内存哪个小区，都能正常工作。

最终打包方式与静态库相同：头文件放进 `include` 目录，`.so` 文件放进 `lib` 目录，再用 `tar` 压缩交付。

---

### 3-2 动态库使用

#### 编译与依赖查看
编译命令与静态库完全相同：用 `-I` 指定头文件路径、`-L` 指定库路径、`-l` 指定库名。`ldd` 是一个查看依赖的工具，它会列出可执行文件运行时需要哪些动态库，以及系统能否找到它们。

```bash
gcc -o usercode main.c -I./include -L./lib -lmystdio   # 编译链接，与静态库用法一样
ldd usercode                                           # 查看usercode依赖哪些动态库，以及它们当前被找到的位置
```

此时如果执行 `./usercode`，大概率会报错，这就是下一节要解决的问题。

---

### 3-3 库运行搜索路径

#### 3-3-1 问题

##### 运行报错的典型现象
编译明明通过了，运行 `./usercode` 时却看到以下错误：

```text
error while loading shared libraries: libmyc.so: cannot open shared object file: No such file or directory
```

此时用 `ldd usercode` 查看，会发现 `libmyc.so => not found`。

##### 静态库为何能直接运行
静态库在编译时就已经把代码拷贝进了可执行文件，运行时是一个自给自足的完整程序，操作系统不需要再去找那个库文件。动态库则像“租房”，程序只带了份租赁合同（入口地址表），入住当天（运行时）必须真的找到房东（库文件），找不到就崩溃。

##### 运行时到底谁去找库
编译阶段的 `gcc` 和你指定的 `-L` 路径只在链接时有效，告诉链接器去哪里找库来拼凑入口地址表。但一旦开始运行，接管程序的是操作系统，操作系统加载动态库时按照自己的规则去硬盘搜索，根本不会理会你当初编译时写了什么 `-L`。系统默认会去一些标准路径（如 `/lib`、`/usr/lib`）以及环境变量 `LD_LIBRARY_PATH` 里记录的位置查找。系统自带的 `libc.so.6` 能被发现，是因为它本来就躺在系统路径里；而你自己写的 `libmyc.so` 放在当前目录或自定义目录，不在系统的搜索名单上，所以“失联”。

---

#### 3-3-2 解决方案

##### 方案一：拷贝到系统共享库路径
把 `.so` 文件复制到系统认可的目录之一，例如 `/usr/lib`、`/usr/local/lib` 或 `/lib64`。这是最直接的方法，但会污染系统目录，且可能需要管理员权限。

##### 方案二：建立软链接
在系统共享库路径下创建一个指向你库文件的软链接，不搬文件本身就能让系统找到。

##### 方案三：修改 LD_LIBRARY_PATH
这是一个环境变量，系统加载动态库时会查看它里面记录的路径。在终端里执行：

```bash
export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/your/path   # 把自定义库目录追加到搜索路径里
```

**注意**：这种修改只在当前终端进程及其子进程中有效，关闭终端后失效。

##### 方案四：ldconfig 配置
如果想让配置永久生效且对所有用户有效，可以向 `/etc/ld.so.conf.d/` 目录添加一个配置文件，里面写一行你的库路径，然后执行 `ldconfig` 刷新系统的库搜索缓存。

```bash
echo "/home/yourname/mylib" > /etc/ld.so.conf.d/mylib.conf   # 新建配置文件，写入库所在目录
ldconfig                                                     # 重新加载库搜索路径，让系统认识新库
ls /etc/ld.so.conf.d/                                        # 查看已有的配置片段
```

`ldconfig` 是系统的动态链接器缓存管理工具，它会扫描配置文件里记录的所有目录，把可用的动态库位置建一张缓存表，后续程序启动时直接查表，加载速度更快。

---

##### 核心结论

> **结论 1：gcc/g++ 默认优先使用动态链接**，除非显式加上 `-static`。
>
> **结论 2：Linux 系统默认安装的大部分库都以动态库形式存在**，这也是为了全系统共享。
>
> **结论 3：一份动态库可以被任意多个程序共用，库与应用程序的关系是 1 : n。**
>
> **结论 4：gcc 既能编译普通可执行程序，也能通过 `-shared` 生成动态库、通过 `-static` 强制静态链接。**
>
> **补充**：一旦使用 `-static`，如果系统里某个库只有动态版本没有静态版本，链接会失败；可执行程序可以选择静态链接库，但库本身如果要被静态链接进其他程序，它自己必须是以静态方式存在的。

## 4. 使用外部库-课后尝试

### 4.1 外部库是什么
编译器自带的 C/C++ 标准库就像手机出厂预装的计算器，写 `printf` 直接能用。但世界上还有很多别人写好的现成工具，比如专门操控屏幕的、画图的、处理网络的，这些编译器不自带，这就叫**外部库**。想用它，先得把它装到系统里，编译时还要额外告诉编译器"把这个库连上"。

### 4.2 ncurses 能做什么
终端默认只能一行一行往下打印文字，像老式打字机，光标永远在最底下。如果你希望在黑框框里弹出带边框的小窗口、把光标移到屏幕中央打印彩色文字、或者做一条动态增长的进度条，就需要借助外部库。**ncurses** 就是专门干这件事的：它把终端当成画布，让你自由开窗、着色、定位输出。

### 4.3 安装 ncurses 开发包
包名带 `-devel`（CentOS）或 `-dev`（Ubuntu）的是开发包，里面放着写代码时要包含的函数声明和编译后需要的库文件。用你已学过的包管理器直接安装：

```bash
sudo yum install -y ncurses-devel      # CentOS
sudo apt install -y libncurses-dev     # Ubuntu
```

### 4.4 课后尝试：多彩进度条
下面这段代码在终端中央创建一个带边框的窗口，窗口内显示黄字蓝底的百分比，并用 `=` 拼接出一条实时增长的进度条。

```cpp
#include <ncurses.h>  // ncurses 的头文件，里面有 initscr 等函数的声明
#include <unistd.h>   // 提供 usleep（按微秒数暂停）

int main()
{
    initscr();            // 初始化 ncurses，接管整个终端屏幕；此后普通 printf 不再生效
    start_color();        // 开启颜色支持，否则屏幕只能黑白显示

    // 注册一套颜色搭配，编号设为 1：文字黄色，背景蓝色
    init_pair(1, COLOR_YELLOW, COLOR_BLUE);

    int h = 10, w = 50;   // 窗口高 10 行，宽 50 列
    int y = (LINES - h) / 2;  // LINES 是 ncurses 提供的当前屏幕总行数，用来计算垂直居中
    int x = (COLS  - w) / 2;  // COLS  是屏幕总列数，用来计算水平居中

    WINDOW *win = newwin(h, w, y, x);  // 在屏幕中间新开一个窗口，拿到一个代表它的变量

    for (int i = 0; i <= 100; i++)
    {
        werase(win);      // 擦掉窗口里的旧内容，防止上一帧残影留在屏幕上

        box(win, 0, 0);   // 给窗口画边框；两个 0 表示使用默认横竖线字符

        wattron(win, COLOR_PAIR(1));          // "开灯"：接下来打印的内容使用编号 1 的颜色对（黄字蓝底）

        // 在窗口内部第 4 行、第 5 列的位置，打印当前百分比；%3d 让数字占 3 位保持对齐
        mvwprintw(win, 4, 5, "Progress: %3d %%", i);

        // 画进度条本体：第 6 行第 5 列起，用 '=' 填充
        int bar = (w - 12) * i / 100;         // 根据窗口宽度算出当前应填充多少个字符
        for (int j = 0; j < bar; j++)
            mvwaddch(win, 6, 5 + j, '=');     // 在指定坐标逐个画字符

        wattroff(win, COLOR_PAIR(1));         // "关灯"：颜色效果结束

        wrefresh(win);    // 把窗口内容真正刷新到屏幕上；没有这句，画面不会更新

        usleep(50000);    // 暂停 50000 微秒（50 毫秒），让进度条以肉眼可见的速度增长
    }

    wgetch(win);          // 等待用户按一个键，防止程序瞬间退出而看不到 100% 效果
    endwin();             // 退出 ncurses，把终端恢复成普通模式

    return 0;
}
```

编译与运行：

```bash
g++ -o bar bar.cpp -lncurses   # -lncurses 表示链接 ncurses 库，把库里的机器码拼进可执行文件
./bar
```

> **关键结论：ncurses 接管屏幕后，普通 `printf` 不再正常显示；所有画面更新都必须通过 `wrefresh` 才能真正刷到屏幕上；编译时必须带 `-lncurses`，否则链接阶段会报错找不到函数实现。**

参考使用指南：https://blog.csdn.net/bdn_nbd/article/details/134019142

## 5. 目标文件

### 为什么 Linux 下能"拆开看"
Windows 下的 IDE（集成开发环境，就是带图形界面的代码编辑器）把编译、链接、生成可执行文件的全过程封装在一个"运行"按钮里，中间步骤完全看不见。程序报错提示"链接错误"时，新手根本不知道问题出在哪一步。Linux 下用 gcc 可以一步一步手动执行，每个中间文件都能看得见、查得到，这正是排查这类问题的前提。

### 编译与 .o 文件的诞生
一个项目通常由很多 .c 文件组成。如果每次都把所有文件从头重编一遍，非常浪费时间。gcc 支持"只翻译、不组装"：把每个 .c 单独编译成二进制半成品，后缀是 .o，这就是目标文件。

语法 → 功能 → 示例：
```bash
gcc -c hello.c   # 只编译不链接，生成 hello.o
gcc -c code.c    # 只编译不链接，生成 code.o
```

示例代码：
```c
// hello.c
#include <stdio.h>

void run();      // 声明外部函数，告诉编译器 run 存在别处

int main()
{
    printf("hello\n");
    run();       // 调用定义在 code.c 中的函数
    return 0;
}
```

```c
// code.c
#include <stdio.h>

void run()       // 定义 run 函数
{
    printf("run called\n");
}
```

执行后得到 `hello.o` 和 `code.o`。它们已经是二进制，但还不能直接运行，因为 `hello.o` 里调用的 `run` 和 `code.o` 里的实现还没正式"对上号"，这个对接工作留给了链接阶段。

### .o 文件的本质：ELF 格式的可重定位文件
目标文件是二进制，不是文本。用已学过的 `file` 指令查看：
```bash
file hello.o   # 查看文件类型
```

典型输出：
```text
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

这里有两个新术语：
- **ELF**：一种"二进制集装箱"标准，它规定了文件里哪块放代码、哪块放数据、哪块记录符号信息，让操作系统和工具链都能统一识别。
- **可重定位（relocatable）**：代码已翻译成机器码，但函数和变量的最终内存地址还没确定。就像零件已经造好，但还没告诉它最终要装在机器的哪个位置，链接阶段才会给它"排座位"。

正因为 .o 是半成品，修改一个 .c 文件时，只需重新编译它得到新的 .o，再把所有 .o 重新链接即可，无需重编整个工程。这也是 Makefile 增量编译的基础。

> **核心结论：.o（或 Windows 下的 .obj）叫做可重定位目标文件。编译器负责把各个 .c 翻译成对应的 .o；链接器负责把这些 .o 以及库文件组装成最终的可执行程序。编译和链接是两个独立的阶段。**

> **核心结论：可执行程序、.o 目标文件、库文件，本质上都是 ELF 这种统一格式。它们以相同的标准"集装箱"规格存在，只是内容角色不同，最终都以结构化方式融入二进制文件中。**

## 6. ELF 文件

### 6.1 为什么需要一种通用的文件格式
编译软件时，硬盘上会出现各种二进制文件：编译后的半成品、链接好的可执行程序、以及动态库（你在 gcc 和 make 中已见过）。这些文件内容都是 0 和 1，操作系统怎么知道哪个能直接运行、哪个是零件、哪个是崩溃现场？如果各写各的格式，每次加载都要猜谜。于是 Linux 规定了一种统一的“二进制档案模板”，所有程序文件都按同一套封面和目录来写，这种模板就叫 ELF。

---

### 6.2 ELF 的四种身份
ELF（Executable and Linkable Format）大白话就是“可执行与可链接的档案格式”，相当于二进制文件的统一身份证。只要按这个模板填写，系统扫一眼开头就知道该怎么处理。使用这套模板的文件共有四种身份：

- **可重定位文件（Relocatable）**：后缀通常是 `.o`，是编译后生成的半成品。它里面的内存地址还没最终敲定，等着链接器把它拼进最终程序。大白话：还没拼好的积木零件。
- **可执行文件（Executable）**：链接完成的成品，加载进内存就能运行。大白话：拼好的完整模型。
- **共享目标文件（Shared Object）**：后缀 `.so`，也就是动态库。大白话：公共零件箱，谁需要谁借用，运行时共享（你在动态链接部分已见过）。
- **内核转储（core dumps）**：程序崩溃时，操作系统把当时的内存、寄存器等现场拍照存成的文件。大白话：事故黑匣子，供事后分析程序是怎么死的。

---

### 6.3 ELF 文件的身体结构
一个 ELF 文件由外到内分成四大块。可以把它想象成一个快递包裹：

- **ELF 头（ELF header）**：贴在包裹最外面的快递单。它描述文件主要特性，位于文件最开始，目的是告诉系统“我是什么文件、要在哪种机器上跑、以及去哪里找包裹里的其他部分”。没有这张单子，系统拿到二进制文件根本不知道从何看起。
- **程序头表（Program header table）**：模块清单。它列举所有有效的**段（segments）**和属性（每段在文件中的位置 offset、长度）。段是把性质相近的节打包后的运行单位，紧密挨在二进制文件里，靠段表描述才能分割开。大白话：操作系统加载程序到内存时，按这张表把需要的块搬进内存。
- **节头表（Section header table）**：零件明细表。包含对**节（sections）**的描述。节是编译器和链接器视角下的逻辑小块。
- **节（Section）**：ELF 的基本组成单位。各种信息和数据存在不同节中。大白话：包裹里的一个个小格子，代码放一格、数据放一格。

#### 6.3.1 ELF 头
ELF 头是整份文件的导航页。它记录了文件类型（是 `.o` 还是可执行文件）、目标机器架构、程序入口地址、以及程序头表和节头表在文件中的偏移量。系统内核和链接器第一步只读这一小块，就能定位到后续所有内容。

#### 6.3.2 程序头表与节头表
程序头表面向“运行时”：系统加载器靠它知道要把哪些段映射到内存的哪些位置。节头表面向“链接时”：链接器和调试器靠它知道 `.text`、`.data` 等各节的具体位置和大小。一张给操作系统看，一张给开发工具看。

#### 6.3.3 节（Section）
节是真正装东西的小格子。编译器把代码、数据、符号名等分类塞进不同格子，链接器再按格子名去拼装。

#### 6.3.4 文件布局框图（板书强调）
ELF 文件在磁盘上的真实布局从上到下如下：

```text
ELF Header
        ↓
Program Header Table
        ↓
Section 1 / Section 2 / ... / Section n
        ↓
Section Header Table
```

大白话：先贴快递单，再写加载清单，然后堆放货物，最后贴零件明细。

> **关键结论：ELF 头位于文件最开头，是找到其他一切的起点；程序头和节头两张表分别是“运行时加载视图”和“链接时细节视图”的说明书。**

---

### 6.4 最常见的节
节是 ELF 里真正装东西的格子。最常见的有两个：

- **`.text` 节**：装的是机器指令，也就是 CPU 真正执行的操作步骤。程序的主要执行部分都在这里。
- **`.data` 节**：装的是已经初始化过的全局变量和局部静态变量。大白话：程序里一开始就赋了值的数据。

想看一个可执行文件里这些格子的体积，直接用 `size` 命令：

```bash
size /usr/bin/ls      # 查看 ls 程序的 text/data/bss 各区大小
```

---

### 6.5 符号表与字符串的存储方式
程序源码里充满了函数名和变量名，但编译成二进制后只剩地址。链接器在拼装多个 `.o` 文件时，需要一张字典来查“`printf` 在哪里”“`add` 函数在哪段地址”，这张字典就藏在 ELF 里。

#### 6.5.1 符号表 `.symtab`（板书强调）
`.symtab` 节就是 Symbol Table（符号表）。大白话：源码里面函数名、变量名和代码地址的对应关系表。链接时靠它定位外部函数，调试时靠它把冰冷的地址翻译回人类能看懂的名字。

#### 6.5.2 字符串表（板书强调）
符号名在文件里并不是各自存成独立字符串，而是像串糖葫芦一样连续挤在一起，中间用 `\0` 隔开：

```cpp
char label[] = "helloworld\0func\0lib\0a\0ob\0o";  # 所有名字连成一个字符数组，\0 分隔
```

符号表本身不记录完整名字，只记录“我的名字从第几个字节开始”这个偏移量。这样同一个字符串表可以被多处引用，避免重复存储，大幅节省空间。

> **关键结论：符号表记录“名字→地址”的映射，但名字本身不直接存在符号表里，而是存在字符串表中，符号表里只存偏移量。**

---

### 6.6 查看 ELF 头信息：`readelf`（板书强调）
`readelf` 是 Linux 自带的 ELF 文件阅读器，不需要运行程序，直接读它的简历模板。

查看文件头：

```bash
readelf -h /usr/bin/ls    # 读取 ls 程序的 ELF 头部信息
```

输出中会有一行 `Entry point address`（例如 `0x4042d4`）。这就是**入口地址**。大白话：程序被加载进内存后，CPU 第一步从哪里开始执行，就记录在这里。操作系统创建完进程、完成加载后，把程序计数器指向这个地址，程序就开始跑了。

> **关键结论：ELF 头中的 Entry point address 是程序执行的起跑线，操作系统靠它知道该把 CPU 的第一脚油门踩在哪里。**

---

## 7. ELF 从形成到加载轮廓

### 7-1 ELF 形成可执行

你写了一个 `main.c`，又引用了别人写好的 `math.c`，这两份源代码怎么最终变成一个能双击运行的文件？Linux 规定了一种标准“容器格式”叫 **ELF**（Executable and Linkable Format），你可以把它理解为快递包裹的统一填写规范：不管是没加工完的零件（`.o`）、半成品库（`.a` / `.so`），还是最终成品（可执行文件），外表都按这套规范打包。

形成过程分两步走：

- **第一步：翻译**。每份 `.c` 源代码经过编译，变成目标文件 `.o`。此时每个 `.o` 内部已经按 ELF 格式划分好了小隔间，但还不能直接运行。
- **第二步：合并**。链接器把多个 `.o` 中用途相同的小隔间拼在一起，再拉上需要的库，最终生成可执行文件。这些小隔间的专业名称叫 **section（节）**，你可以把它理解为“代码放一间、变量放一间”的文件内部分区。

> **一句话：ELF 是 Linux 可执行文件的统一包装格式；链接的本质是把多个 `.o` 里同类的 section 拼成大块。**

---

### 7-2 ELF 可执行文件加载

#### 从 section 到 segment：为什么要二次合并

可执行文件里有很多 section，比如 `.text`（代码节）、`.data`（数据节）。如果 OS 加载程序时把这些小隔间原封不动搬进内存，会产生严重浪费。因为操作系统向内存“批发”空间时，最小单位是 **页（Page）**，一页固定 4KB。假设 `.text` 有 4097 字节（刚超一页），`.init` 有 512 字节，如果不合并，它们各占一页的整数倍，总共需要 3 页；如果先把属性相同的 section 合并成一个大段 **segment**，再一起搬进内存，只需 2 页就够了。这种合并还能让 OS 给整段统一设置访问权限（只读 / 可写 / 可执行），管理起来更高效。

合并规则在链接阶段就已经定好，写在可执行文件的一张清单里，叫 **程序头表（Program Header Table）**。这张表告诉 OS：“请把文件中从第 X 字节到第 Y 字节这一段，加载到内存地址 Z，权限设为只读。”

```bash
readelf -S a.out   # 查看文件内所有 section 清单（链接视角）
readelf -l a.out   # 查看 section 被合并成哪些 segment（执行视角）
```

> **操作系统真正加载进内存的不是零散 section，而是按属性合并后的 segment；合并方式记录在程序头表中。**

#### 两个视角：链接视图 vs 执行视图

同一份 ELF 文件，在不同阶段被不同角色阅读，关注点不一样：

| 视角 | 专业名称 | 依赖的表 | 关注者 | 作用 |
|---|---|---|---|---|
| 链接视角 | Linking View | 节头表（Section Header Table） | 链接器 | 文件内部细粒度划分，关心 `.text`、`.data` 等功能模块怎么拼 |
| 执行视角 | Execution View | 程序头表（Program Header Table） | 操作系统 | 告诉 OS 怎么加载、初始化进程内存，哪些块可读可写 |

节头表把文件切成很多小房间，方便链接器做静态拼装；程序头表把这些小房间按属性打包成大件，方便 OS 往内存里搬。目标文件 `.o` 只有链接视角——它的程序头表数量为 0，入口地址也是 0，因为它还没准备好被直接执行。

#### 链接视图里常见的 section

- `.text`：放编译后的机器指令，即你的代码本体。
- `.data`：放已经赋过初值的全局变量和局部静态变量。
- `.rodata`：放只读数据，例如字符串常量 `"hello"`，它只存在于只读的 text 段范畴内。
- `.BSS`：给未初始化的全局变量和局部静态变量预留位置。它在文件里不占用实际空间，加载时由 OS 申请内存并清零。
- `.symtab`：符号表，记录函数名和变量名对应的“门牌号”，方便链接时互相查找。
- `.got` / `.got.plt`：全局偏移表和过程链接表，是调用共享库函数时的“临时通讯录”。程序启动后由动态链接器把真实地址填进去。

#### 执行视图里的关键 segment

程序头表中，类型为 **LOAD** 的 segment 才是真的要被操作系统搬进内存的部分。还有一个特殊类型叫 **INTERP**，它里面记录的是动态链接器的路径，例如 `/lib64/ld-linux-x86-64.so.2`，作用是在你的程序正式跑起来之前，先启动这位“中介”来帮忙加载共享库。

#### ELF 文件头：文件的身份证与目录

每个 ELF 文件开头都有一个固定格式的 **ELF Header（文件头）**，你可以把它理解成快递单上的基本信息：

- **Magic**：开头 4 个字节固定为 `\x7fELF`，像文件身份证，系统用它们识别“这是不是 ELF 文件”。
- **Class**：`ELF64` 表示 64 位程序。
- **Data**：说明数据存储的字节序，小端（Least Significant Byte first）是 x86 平台常见方式。
- **Type**：标明文件身份——`REL` 是可重定位的目标文件（`.o`），`EXEC` 是传统可执行文件，`DYN` 是共享库或动态链接可执行文件。
- **Machine**：目标 CPU 架构，例如 `x86-64`。
- **Entry point address**：程序第一条指令在内存中的地址，即“从哪里开始执行”。
- **Start of program/section headers**：两个表在文件内部的偏移量，相当于告诉阅读器“目录从第几页开始”。
- **各表条目大小与数量**：每条记录多长、共有多少条。

> **核心要求：建立 ELF 文件头、节头表、程序头表与文件内部偏移量之间的空间关系。** 目标文件 `.o` 没有执行视图，因此它的 Entry point address 为 0，程序头表数量也为 0。

## 8. 理解连接与加载

---

### 8-1 静态链接

你写了一个大程序，把它拆成两个 C 文件：`hello.c` 里写 `main` 函数，`code.c` 里写 `run` 函数。先用 `gcc -c` 把它们各自编译成 `.o` 文件（已学过的编译过程），这时每个 `.o` 都是"半成品"——里面已经有机器指令，但还不是一个能双击运行的完整程序。**链接**就是把这些半成品拼装成独立可执行文件的过程；无论这些 `.o` 是你自己写的，还是从静态库里拆出来的，本质都一样。

```bash
gcc -c hello.c code.c   # 把两个 .c 各自编译成 .o 半成品
gcc hello.o code.o -o main.exe   # 把两个 .o 链接成最终可执行文件
```

用 `objdump -d`（查看机器码的工具）拆开 `hello.o` 看看，会发现 `main` 里调用 `printf` 和 `run` 的跳转指令后面，地址居然写的是 `0`。为什么？因为编译 `hello.c` 时，编译器根本不知道 `printf` 和 `run` 这两个函数住在哪里、代码有多长，只能先填 `0` 占个位置。

```bash
objdump -d hello.o   # 反汇编 hello.o，观察 call 指令的目标地址
```

这些被 `0` 占位的地址并不是随便写的，`.o` 文件内部有一张"待修正地址清单"，专业上叫**重定位表**：它精确记录了哪些地方需要事后填地址。链接器就是靠这张表，在拼装时把 `0` 改成真正的地址。

再看**符号表**——可以理解为 `.o` 文件的"记账本"，记录着本文件有哪些函数、哪些是从外面借用的。用 `readelf -s` 查看：

```bash
readelf -s code.o   # 查看 code.o 的符号表，puts 标记为 UND（undefined，在本 .o 里找不到定义）
readelf -s hello.o  # 查看 hello.o 的符号表，run 和 puts 都标记为 UND
```

`UND` 表示"这个函数我用了，但在我这个 `.o` 里没定义"。链接之后，两个 `.o` 的代码段被合并到一起并统一编址，`run` 有了真实地址：

```bash
readelf -s main.exe   # 链接后 run 有真实地址（如 0000000000001149）、类型 FUNC、所在 section 下标 16（.text）
```

用 `objdump -d main.exe` 验证，会发现原来 `call 0` 的位置变成了 `callq 1149 <run>` 和 `callq 1050 <puts@plt>`。两个 `.o` 的代码段被合并到同一片连续区域，统一分配了地址；链接器根据重定位表，把所有占位的 `0` 修正成了最终地址。

> **静态链接的本质就是"合并 + 重定位"：把所有目标文件连同用到的静态库里的 `.o` 拼装成一个独立可执行文件，统一编址并修正所有未确定的函数地址。**

### 8-2 ELF 加载与进程地址空间

#### 8-2-1 虚拟地址/逻辑地址

一个程序还躺在磁盘上、没被加载进内存时，它里面的代码和数据有没有地址？**有。** Linux 上的可执行程序遵循一种叫 **ELF** 的标准档案格式（你可以把它理解成"书包的固定分层"），编译器在生成这个文件时，就已经用**平坦模式**给它内部的代码和数据统一编好了地址：从 `0` 开始，每个字节都有自己的"门牌号"。用 `objdump -S` 查看，最左侧的地址就是 ELF 给自己规划的地址，严格说是**逻辑地址**（起始地址 `0` + 偏移量）。

```bash
objdump -S main.exe   # 最左侧的地址就是 ELF 在磁盘上已编好的虚拟地址
```

> **虚拟地址在程序还没加载到内存时，就已经在磁盘上统一编址好了。**

如果 ELF 里每个段（segment）的起始地址都想象成 `0`，那么所有函数、变量的偏移量都从 `0` 开始计算；这就意味着，磁盘上可执行程序的编址本身就是虚拟地址的统一编址。虚拟地址机制不只是操作系统管理内存的方式，**编译器在生成程序时就已经在配合这套规则**。

程序加载时，操作系统根据 ELF 中各个 segment 的起始地址和长度，去初始化进程的 `mm_struct` 和 `vm_area_struct`（你已学过的进程地址空间内核结构），再填充页表。

#### 8-2-2 重新理解进程虚拟地址空间

ELF 文件在编译链接完成后，会把程序第一条指令的地址记录在 ELF 头部的 `Entry` 字段里，用 `readelf -h` 能看到：

```bash
readelf -h main.exe   # 查看 ELF Header，其中 Entry point address 如 0x1060
```

程序启动的完整链条是：磁盘上的可执行程序带着入口地址 `0x1060` → 被加载进物理内存 → CPU 的 `EIP` 寄存器被设为 `0x1060`，`CR3` 寄存器指向当前进程的页表 → MMU 通过页表把虚拟地址转换成物理地址 → 从入口开始执行。CPU 之所以知道从哪开始执行，是因为操作系统在加载时读取了 ELF Header 的 `Entry point`，把它塞进了 `EIP`。

进程地址空间的初始化链条是：`task_struct` → `mm_struct`（含 `mmap`） → 一串 `vm_area_struct`（每个包含 `vm_start`、`vm_end`、`vm_next`） → 每个区域对应一个 VMA：栈区、堆区、代码区、数据区、BSS 段、文件映射区等，**每个 VMA 对应 ELF 中的一个 segment**。内核空间位于最上方。

当需要加载动态库时，操作系统同样通过文件系统找到库文件：`struct file` → `struct path` → `struct dentry` → `struct inode`（含 `i_ino`、`i_block`） → 磁盘数据块 → 加载入库。页表把虚拟地址映射到物理内存页，库内部本质上就是文件内容按原样加载到对应区块中。用 `objdump -d` 看可执行程序的前几条指令（如 `0x1000`、`0x1003` 等），它们就是磁盘上 ELF 里的指令原样搬进来的。

### 8-3 动态链接与动态库加载

#### 8-3-1 进程如何看到动态库

如果十个程序都静态链接 `printf`，磁盘和内存里就会出现十份相同的 `printf` 代码，浪费空间。**动态库**就是为解决这个麻烦而生的：把大家都要用的代码单独抽成一个文件（如 `libc.so`），程序运行时才搬进来，多进程共用同一份。

动态库也是磁盘上的普通文件，要访问就得先加载，要加载就得先被打开。但调用库函数不是读文件内容那么简单，而是靠**虚拟地址跳转**来访问的，所以操作系统必须把动态库映射到进程的地址空间里。进程的 `mm_struct` 中有一块**共享区**（位于堆区上方），通过页表映射到物理内存中的 `XXX.so`；进程像访问自己的内存一样，通过虚拟地址看到并使用共享库。

#### 8-3-2 进程间如何共享库的

进程 A 和进程 B 各有自己的 `task_struct`、`mm_struct` 和页表，但两个进程地址空间中的共享区，通过各自的页表映射到**物理内存中同一份** `XXX.so`。磁盘上只有一份 `.so` 文件，物理内存中只有一份库代码，逻辑上每个进程都觉得自己有一份——这就是虚拟地址空间"解耦合"收益的具体落地。

> **动态库中的代码不会出现重复，多进程共享同一份物理副本。**

#### 8-3-3 动态链接

##### 8-3-3-1 概要

用 `ldd` 可以查看一个程序依赖哪些动态库：

```bash
ldd main.exe   # 列出 main.exe 依赖的动态库，如 libc.so.6、ld-linux-x86-64.so.2 等
```

`libc.so.6` 是 C 运行时库，里面包含标准 IO、字符串处理等常用函数。编译器默认优先使用动态链接，是因为静态链接会把所有目标文件和库代码合并成一个文件，体积庞大；不同软件重复包含相同代码，浪费大量磁盘和内存空间。

动态链接的做法是：把需要共享的代码单独提取成独立的动态库，程序运行时才加载进内存；同一模块在内存中只需一份副本，被多进程共享，既省空间，也便于库的更新维护。

> **动态链接实际上把整个"链接"过程推迟到了程序加载的时候：** 操作系统先把程序本身的代码数据加载进内存，再把它依赖的一系列动态库也加载进来；每个动态库的加载地址不固定，OS 根据当前内存使用情况动态分配；库的内存地址一旦确定，就修正那些待定的函数跳转地址。

##### 8-3-3-2 我们的可执行程序被编译器动了手脚

你以为程序一运行就进 `main`？**真正入口不是 `main`，而是 `_start`**（由 glibc 或链接器提供）。完整的启动链条是：`_start` → 设置堆栈 → 初始化数据段（已初始化数据复制、未初始化清零）→ **动态链接**（调用动态链接器解析加载所有依赖库、完成符号解析与重定位）→ `__libc_start_main`（设置信号处理、初始化线程库等）→ 调用 `main` → `main` 返回后由 `__libc_start_main` 处理返回值并调用 `_exit` 终止程序。

**动态链接器**（`ld-linux.so`）是操作系统派来的"搬家公司"，负责在程序运行时加载动态库、解析依赖关系、完成重定位。它搜索库的路径包括环境变量 `LD_LIBRARY_PATH`、配置文件 `/etc/ld.so.conf` 及其子配置，以及缓存文件 `/etc/ld.so.cache`。这些 `main` 之前的操作对程序员完全透明。

##### 8-3-3-3 动态库中的相对地址

动态库要被随时加载、可能映射到任意进程的任意位置，所以库内部的方法统一采用**相对编址**：把库自己的起始地址看成 `0`，所有方法都记录成"从 `0` 开始偏移多少"。可执行程序也遵守平坦模式，只不过它是直接加载的。

```bash
objdump -S /lib/x86_64-linux-gnu/libc-2.31.so   # 查看库内的相对地址（Ubuntu 示例）
```

> **库内方法的地址理解成偏移量：若库内方法偏移为 `0x123`，加载后库起始虚拟地址是 `0x1000`，则实际访问地址 = `0x1000 + 0x123`。**

##### 8-3-3-4 我们的程序，怎么和库具体映射起来的

完整映射链条：磁盘上的 `XXX.so` 文件 → 加载到物理内存 → 进程地址空间的共享区（`mm_struct` 的某个 `vm_area_struct`，范围 `vm_start` ~ `vm_end`）→ 页表把共享区虚拟地址映射到物理内存中库的页。操作系统找到库文件的过程依然走文件系统链条：`struct file` → `struct path` → `struct dentry` → `struct inode` → `i_block` → 磁盘数据块。

库内部就是文件内容，按原样加载到对应区块中；所以**库的起始虚拟地址一旦确定，加上每个方法已知的偏移量，就能定位任意函数**。

##### 8-3-3-5 我们的程序，怎么进行库函数调用

调用公式非常直接：

> **访问库中任意方法 = 库的起始虚拟地址 + 方法偏移量。**

整个过程在进程地址空间内部完成：从代码区跳转到共享区，调用完毕再返回代码区。前提是在程序运行前，操作系统已把所有库加载并映射好，所有库的起始虚拟地址都已确定，然后对加载到内存中的程序进行地址修改——这叫**加载地址重定位**。

但这引出一个矛盾：要修改的是代码区里的调用地址，可代码区在进程中不是只读的吗？怎么改？

##### 8-3-3-6 全局偏移量表 GOT（global offset table）

解决矛盾的做法是：**不在代码区里改地址，而是在可读写数据区预留一张表。** 这张表叫 **GOT**（全局偏移量表），放在 `.data` 段中（`readelf -S` 可见 `.got` 节，加载时与 `.data` 合并成一个 segment）。GOT 的每一项都是本运行模块要引用的全局变量或函数的实际地址。代码段保持只读、不变、可共享；不同进程各自维护自己的 GOT，里面填上本进程中动态库的实际地址。

GOT 机制的四条核心要点：

1. 代码段只读不能改，但有了 GOT，同一段库代码可被所有进程共享；不同进程加载库的绝对地址不同，所以**每个进程的每个动态库都有独立的 GOT，进程间不共享 GOT 表。**
2. 单个 `.so` 内部，GOT 表与 `.text` 代码段的相对位置固定，CPU 可以用相对寻址快速找到 GOT。
3. 调用函数时先查 GOT，按表中地址跳转；表中地址在动态库加载时被动态链接器修改为真正的内存地址。
4. 这种编写方式叫 **PIC**（地址无关代码）：动态库本身不做任何修改，被加载到任意内存地址都能正常运行并被所有进程共享；编译时加 `-fPIC` 就是为此。PIC = 相对编址 + GOT。

调用时，源代码里的 `call 0x112233`（库内相对地址）→ 加载后假设库起始地址为 `0x443322` → 实际调用地址为 `0x112233 + 0x443322`，通过查 GOT 完成组合。

用 `objdump -S` 看可执行程序，会发现 `main` 里并不是直接跳到库，而是 `callq 1050 <puts@plt>`——先跳到 **PLT**（过程链接表，一段配合 GOT 的"跳板代码"）。

**延迟绑定优化：** 程序依赖的库函数可能成百上千，如果启动时全部重定位，非常耗时。与其一开始就全部修正，不如推迟到函数**第一次被调用**时。GOT 中的跳转地址默认指向一段辅助桩代码（stub），第一次调用时这段代码负责去查询真正函数的地址并更新 GOT 表；再次调用时，就直接从 GOT 跳到库中真正的函数实现，省去重复查询。

> **动态链接把符号查询、地址重定位从编译时推迟到运行时，牺牲一定性能和加载时间，换来了磁盘与内存的高效利用、代码的方便更新维护、以及二进制级别的代码复用。**

##### 8-3
##### 8-3-3-7 库间依赖（简单说明即可）

不仅可执行程序会调用动态库，**动态库之间也会互相调用**。库 A 调用库 B 的函数时，同样需要地址无关，因此库内部也维护自己的 GOT 表，与可执行程序机制完全一致——这正是所有模块都统一采用 ELF 格式的原因。动态链接器加载主程序后，会递归解析依赖关系，逐层加载并完善每个库的 GOT 表。

---

#### 8-3-4 总结

> **静态链接 = 编译期合并 + 重定位。** 多个 `.o` 与静态库在链接阶段直接拼装成独立可执行文件，链接器一次性修正所有模块间的函数跳转地址（静态重定位），适合大项目模块化开发与独立测试，但会带来磁盘和内存的代码冗余。

> **动态链接 = 运行期加载 + 映射 + GOT 二次重定位。** 链接的全过程被推迟到程序加载时；动态库加载到内存的实际地址不固定，但无论落到哪，都通过页表映射到进程地址空间的共享区，程序借助各自独立的 GOT 表完成最终的地址修正（动态地址重定位）。它用少量启动开销换取了多进程共享同一份物理代码、节省空间、便于库升级维护的收益。

对照记忆：静态重定位在编译链接阶段把地址直接写死；动态重定位在运行加载阶段通过 GOT 把最终地址填到可写的数据区，代码段始终保持不变、可被多进程共享。

## 附录:操作大全

### 附录1:ELF结构

#### 为什么需要ELF格式
你写完C代码，经过编译链接，硬盘上会出现一个可执行文件。操作系统面对这个文件时，必须回答三个问题：这是程序还是普通文本？如果是程序，该从内存哪里开始运行？代码和数据又该放到内存哪里？如果每个编译器都按自己的格式生成文件，操作系统就没法统一加载。于是大家约定了一种标准说明书格式，叫做ELF（Executable and Linkable Format，可执行与可链接格式）。操作系统只认这种格式的可执行文件，就像火车票必须有条形码，检票机才能识别。

#### ELF Header：可执行文件的"封面"
ELF文件的开头是一个固定结构的"封面"，叫做ELF Header。它用C语言的结构体描述，32位系统叫`Elf32_Ehdr`，64位系统叫`Elf64_Ehdr`。这个封面告诉操作系统：我是谁、为谁编译、入口在哪、两张核心表存在文件的什么位置。

关键字段可以用生活类比理解：
- `e_ident`（魔数）：文件的身份证。前几个字节固定为`0x7f 'E' 'L' 'F'`，操作系统一读就知道"这是ELF文件，我能处理"。
- `e_type`：文件类型，比如是可执行程序、动态库还是目标文件。
- `e_machine`：CPU平台，比如x86-64或ARM。
- `e_entry`：入口虚拟地址。程序加载进内存后，CPU从这儿开始取第一条指令执行。
- `e_phoff`：程序头表（Program Header Table）在文件中的偏移位置。
- `e_shoff`：节头表（Section Header Table）在文件中的偏移位置。
- `e_phnum` / `e_shnum`：两张表各自有多少条记录。
- `e_ehsize`：封面本身占多少字节。

> **操作系统必须能识别特定格式的可执行程序，ELF Header就是这种识别的依据。**

### 附录2:查看ELF Header

查看封面信息的命令是`readelf -h`，`-h`表示header。

```bash
readelf -h main    # 读取main文件的ELF Header
```

输出中你能直接读到：文件类型、机器类型、版本、入口地址，以及程序头表和节头表分别藏在文件的第几个字节、各占多大空间。

### 附录3:ELF Program Header Table

#### 加载视角：哪些内容要进内存
程序运行前，操作系统需要把文件内容搬进内存。但一个ELF文件里有很多内容，比如调试信息、链接符号表，这些在运行时并不需要占用内存。Program Header Table就是给操作系统看的"加载说明书"，它一条条列出：请把文件的这一段，加载到虚拟地址的这一块，大小是多少，权限是读还是写还是执行。

查看命令：

```bash
readelf -l main    # -l 即 --program-headers，查看程序头表
```

#### Phdr结构体关键字段
每一条记录对应一个`Elf64_Phdr`结构体（64位系统），关键字段含义如下：
- `p_type`：段的类型。最常见的是`LOAD`，表示"这一段要加载进内存"；还有`INTERP`、`DYNAMIC`等。
- `p_offset`：这段内容在ELF文件中的起始偏移。
- `p_vaddr`：加载到进程虚拟地址空间的哪里。这与你已学过的程序地址空间布局直接对应。
- `p_paddr`：物理地址，现代操作系统都使用虚拟内存，这个字段基本忽略。
- `p_filesz`：这段在文件中占多少字节。
- `p_memsz`：这段在内存中占多少字节。通常`p_memsz`大于等于`p_filesz`，因为.bss段在文件里不占空间，但进内存时要预留零初始化空间。
- `p_flags`：内存权限标志，如`R`（读）、`W`（写）、`E`（执行）。
- `p_align`：对齐要求，保证加载到内存时地址是某个数的整数倍，提高访问效率。

#### LOAD与INTERP标记
- `LOAD`：只有被标记为`LOAD`的段，操作系统才会在创建进程时把它们从磁盘搬进内存。其余段（如调试信息）留在文件里即可。
- `INTERP`：这一项会指出动态链接器的路径，例如`/lib64/ld-linux-x86-64.so.2`。程序启动时，操作系统会先加载这个"解释器"，由它帮忙完成动态库的加载和地址绑定——这与你已学过的动态链接机制直接相关。

---

### 附录4:ELF Section Header Table

#### 链接视角：程序零件清单
如果说Program Header Table是操作系统加载时看的"搬运指南"，Section Header Table就是给链接器和程序员看的"零件清单"。它把文件内部按功能切成一个个节（Section），比如代码节`.text`、已初始化数据节`.data`、未初始化数据节`.bss`等，记录每节的名字、大小、位置、属性。

查看命令：

```bash
readelf -S main    # -S 即 --section-headers，查看节头表
```

#### Shdr结构体关键字段
每一条记录是一个`Elf64_Shdr`结构体：
- `sh_name`：节的名字，在字符串表中的索引。
- `sh_type`：节的类型，如`PROGBITS`（程序数据）、`SYMTAB`（符号表）。
- `sh_flags`：属性标志，如`W`（可写）、`A`（可分配进内存）、`X`（可执行）。
- `sh_addr`：如果这节要装进内存，运行时对应的虚拟地址。
- `sh_offset`：这节在文件中的起始位置。
- `sh_size`：这节有多大。
- `sh_link` / `sh_info`：与链接相关的附加信息，指向其他节。

#### .got全局偏移表
`.got`（Global Offset Table，全局偏移表）是动态链接用到的一个特殊小节。你可以把它理解成一张"函数地址通讯录"：程序编译时还不知道外部动态库函数（如`printf`）最终住在内存哪里，于是先留一个空位列表；程序启动后，动态链接器把真实的函数地址填进这张表；之后程序通过查表就能跳转到真正的函数实现，而不需要在编译时固定地址。

---

### 附录5:查看具体的sections信息

#### objdump看反汇编与桩代码
`objdump`能把机器码还原成汇编指令。带`-S`选项时，还会把C源代码穿插显示，方便对照。

```bash
objdump -S main    # 对main进行带源码的反汇编
```

在输出中你会看到`.plt`（Procedure Linkage Table，过程链接表）和`.plt.got`里的"桩代码"，比如`write@plt`、`printf@plt`。这些桩代码是动态链接的跳板：程序调用`printf`时，先跳到`printf@plt`，这条桩代码再执行`jmpq *GOT[n]`，也就是跳到`.got`表中对应的项。如果该函数是第一次调用，动态链接器会先把真实地址写进`.got`，后续调用就直接跳转，不再绕弯。

#### 链接前后的地址差异
用`objdump -d`查看尚未链接的目标文件（`.o`文件），你会发现对外部函数的`call`指令后面跟的地址是`0x00000000`。这是因为编译阶段根本不知道这些函数最终在哪，地址要等链接阶段甚至运行时才能确定。

```bash
objdump -d hello.o    # hello.o是链接前的目标文件，观察call地址为0
```
