# 本节重点

## 什么是库

你写代码时用过的 `printf`、`strlen`、`cin`，你从来没有亲手实现过它们，但它们就是能跑——因为它们躺在**库**里。

库就是**别人写好的、成熟的、可以复用的代码**，以二进制形式存在，操作系统可以把它载入内存执行。就像装修房子：你不会自己烧砖，而是直接买现成的砖、地板、灯具。每个程序都依赖很多底层库，谁也不可能从零造轮子。

库有两种：

| 类型 | Linux 后缀 | Windows 后缀 | 链接时机 |
|---|---|---|---|
| 静态库 | `.a` | `.lib` | 编译链接时把代码**拷进**可执行文件 |
| 动态库 | `.so` | `.dll` | **运行时**才去加载库代码，多进程共享 |

> **关键结论**：静态库 = 把答案抄进自己卷子（运行时不再依赖库文件）；动态库 = 大家共用一本参考书（运行时才去翻，内存里只放一份）。

---

## 静态库的制作与使用

静态库的本质是把多个 `.o` 目标文件**打包归档**。Linux 用 `ar` 工具完成：

```bash
ar -rc libmystdio.a my_stdio.o my_string.o
# ar = 归档工具，r = replace，c = create
```

使用时只需要记住**链接三件套**：

- `-L<路径>`：告诉编译器去哪里找库文件
- `-I<路径>`：告诉编译器去哪里找头文件
- `-l<名字>`：链接哪个库。库名规则是去掉前缀 `lib` 和后缀 `.a`/`.so`，比如 `libmystdio.a` → `-lmystdio`

```bash
gcc main.c -I./include -L./lib -lmystdio
```

> **关键结论**：静态库链接完成后可执行文件就自带全部代码，把 `.a` 删掉程序照样能跑。

---

## 动态库的制作与使用

动态库生成和静态库只差两个编译选项：

```bash
gcc -fPIC -c my_stdio.c        # -fPIC：产生位置无关码
gcc -o libmystdio.so my_stdio.o my_string.o -shared   # -shared：生成共享库格式
```

编译链接方法和静态库一样（`-I -L -l`），但**运行时会遇到一个经典坑**：编译能过，一运行就报 `libmystdio.so => not found`。因为 gcc 只管编译期找库，程序运行时是**操作系统（动态链接器）**在找库，它只认自己的搜索路径。

四种解决方案（从简单到正规）：

1. 把 `.so` 直接拷到系统库目录 `/usr/lib64`、`/usr/local/lib` 等处
2. 在系统库目录下给 `.so` 建软链接
3. 把库所在目录加进环境变量 `LD_LIBRARY_PATH`（临时）
4. 在 `/etc/ld.so.conf.d/` 下写一个 conf 文件，然后执行 `ldconfig` 刷新缓存（永久、最正规）

> **关键结论**：编译期找库靠 `-L`，运行期找库靠系统搜索路径，两者是独立的。

## ELF 文件

Linux 下 `.o` 目标文件、可执行程序、`.so` 动态库，全是同一种格式——**ELF**（Executable and Linkable Format）。ELF 由四部分组成：

| 组成 | 大白话 | 作用 |
|---|---|---|
| ELF 头 | 文件的"封面" | 记录文件类型、入口地址，用来定位其他部分 |
| 程序头表 | 装载说明书 | 告诉操作系统加载时如何划分 segment |
| 节头表 | 内容目录 | 描述文件里各个 section 的位置和属性 |
| 节 | 真正的内容 | `.text` 放代码、`.data` 放已初始化数据、`.rodata` 放只读数据等 |

ELF 有两个视角：**链接视图**（看 section，链接器用，粒度细）和**执行视图**（看 segment，操作系统加载用）。加载时把属性相同的 section 合并成 segment，减少内存页碎片，并按合并结果设置读/写/执行权限。

> **关键结论**：一个管链接、一个管加载——节头表给链接器看，程序头表给操作系统看。

## 静态链接与重定位

分别编译 `hello.c` 和 `code.c`，用 `objdump -d` 反汇编 `.o` 文件，会看到 `call` 指令后面的地址全是 **0**。

为什么是 0？因为编译单个文件时，编译器根本不知道 `run`、`printf` 这些函数在别处长什么样、住在哪，只能先填 0 占位，同时在 `.o` 里生成一张**重定位表**，记录"哪些地址需要修正"。

链接的时候，所有 `.o` 合并、统一编址，链接器按重定位表把 0 改成真正的函数地址。这就是静态链接的全部秘密：**合并 + 重定位**。

> **关键结论**：编译 = 翻译出占位地址；链接 = 合并 section + 按重定位表修正地址。

---

## 动态链接与 GOT

动态链接把"链接"这件事推迟到了**程序运行时**。库加载到内存的哪个地址，要到加载那一刻才确定，所以动态库内部统一采用**相对编址**（`-fPIC`，位置无关码）。

可是代码段在进程里是**只读**的，运行时改不了 call 后面的地址怎么办？动态链接的做法是在可写的 `.data` 区里预留一张**全局偏移表 GOT**，存所有外部函数的跳转地址。函数调用时不直接跳，而是先查 GOT，按表里的地址跳转；GOT 表项在库加载时被动态链接器填成真地址——由于 `.data` 可写，修改合法。

再配合 **PLT（延迟绑定）**：函数第一次被调用时才去解析地址并回填 GOT，之后直接走快路径，避免程序启动时重定位所有函数的开销。

> **关键结论**：PIC = 相对编址 + GOT。动态库不做修改就能加载到任意地址、被任意进程共享。

## 1. 什么是库

### 1-1 库的存在意义

先问一个问题：你写的程序里调用了 `printf`，但你从来没写过 `printf` 的实现，编译器也从来没报错说找不到，这是为什么？

答案：系统里早就躺着一大堆**写好的、成熟的、可复用的代码**，这就是库。本质上，库是一种**可执行代码的二进制形式**，可以被操作系统载入内存执行。

现实中每个程序都要依赖大量底层库——如果每个人连"读文件""开窗口"都要从零写起，软件行业就不会存在。库的意义就是把公共能力沉淀下来，让所有程序员站在同一块地基上写自己的业务。

验证一下，你的系统里现在就摆着这些库：

```bash
# ubuntu：C 语言的动态库和静态库
$ ls -l /lib/x86_64-linux-gnu/libc-2.31.so
-rwxr-xr-x 1 root root 2029592 May  1 02:20 /lib/x86_64-linux-gnu/libc-2.31.so

$ ls -l /lib/x86_64-linux-gnu/libc.a
-rw-r--r-- 1 root root 5747594 May  1 02:20 /lib/x86_64-linux-gnu/libc.a

# C++ 标准库（.so 是个软链接，指向带版本号的真实文件）
$ ls -l /usr/lib/gcc/x86_64-linux-gnu/9/libstdc++.so
lrwxrwxrwx 1 root root 40 Oct 24  2022 /usr/lib/gcc/x86_64-linux-gnu/9/libstdc++.so -> ../../../x86_64-linux-gnu/libstdc++.so.6
```

注意 `.so` 是一个软链接——这是动态库的常见形态：真实文件带版本号（`libstdc++.so.6.0.19`），链接名保持稳定，程序升级时只需改链接指向，所有程序无感更新。

### 1-2 动静态库对比

| 类型 | Linux 后缀 | Windows 后缀 | 什么时候链接 | 运行时还需要库文件吗 |
|---|---|---|---|---|
| 静态库 | `.a` | `.lib` | 编译链接时把库代码拷进可执行文件 | 不需要 |
| 动态库 | `.so` | `.dll` | 运行时才去加载 | 需要 |

类比：

- **静态库**像把整本《新华字典》复印进自己的笔记本——考试（运行）时不用带字典，但笔记本特别厚。
- **动态库**像全班共用一本字典放在讲台上——谁的笔记本都薄，但考试时必须保证讲台上有这本书。

一个可执行程序可能同时用到静态库和动态库。gcc 编译**默认采用动态链接**，只有在该路径下找不到动态 `.so` 时才退而采用同名静态库；也可以用 `-static` 强制全静态链接。

### 1-3 预备工作：准备我们自己的代码

接下来我们要亲手把自己的代码打成库。准备一个简化版 stdio 封装（接口部分）：

```c
// my_stdio.h
#pragma once

#define SIZE 1024

#define FLUSH_NONE 0    // 不刷新
#define FLUSH_LINE 1    // 行刷新：遇到 \n 就刷新
#define FLUSH_FULL 2    // 全刷新：缓冲区满才刷新

struct IO_FILE
{
    int flag;           // 刷新方式
    int fileno;         // 文件描述符
    char outbuffer[SIZE];  // 输出缓冲区
    int cap;            // 容量
    int size;           // 当前已有数据量
};

typedef struct IO_FILE mFILE;

mFILE *mfopen(const char *filename, const char *mode);
int mfwrite(const void *ptr, int num, mFILE *stream);
void mfflush(mFILE *stream);
void mfclose(mFILE *stream);
```

实现部分（核心逻辑：先写进用户级缓冲区，再按策略刷到内核）：

```c
// my_stdio.c（节选核心逻辑）
mFILE *mfopen(const char *filename, const char *mode)
{
    int fd = -1;
    if(strcmp(mode, "r") == 0)      fd = open(filename, O_RDONLY);
    else if(strcmp(mode, "w") == 0) fd = open(filename, O_CREAT|O_WRONLY|O_TRUNC, 0666);
    else if(strcmp(mode, "a") == 0) fd = open(filename, O_CREAT|O_WRONLY|O_APPEND, 0666);
    if(fd < 0) return NULL;

    mFILE *mf = (mFILE*)malloc(sizeof(mFILE));
    if(!mf) { close(fd); return NULL; }

    mf->fileno = fd;
    mf->flag = FLUSH_LINE;
    mf->size = 0;
    mf->cap = SIZE;
    return mf;
}

void mfflush(mFILE *stream)
{
    if(stream->size > 0)
    {
        write(stream->fileno, stream->outbuffer, stream->size); // 写到内核文件缓冲区
        fsync(stream->fileno);                                  // 再刷到外设
        stream->size = 0;
    }
}

int mfwrite(const void *ptr, int num, mFILE *stream)
{
    // 1. 拷贝进用户级缓冲区
    memcpy(stream->outbuffer + stream->size, ptr, num);
    stream->size += num;

    // 2. 行刷新模式下，最后一个是 \n 就刷新
    if(stream->flag == FLUSH_LINE && stream->size > 0
       && stream->outbuffer[stream->size-1] == '\n')
        mfflush(stream);
    return num;
}
```

再配一个极简的字符串模块 `my_string.c`（实现 `my_strlen`）。这套 `my_stdio + my_string` 就是接下来要打包成库的"原材料"。

> **关键结论**：库不是什么神秘东西，本质就是把你写好的 `.c` 编译出的 `.o` 文件们打包在一起，配上头文件当说明书。

## 2. 静态库

### 2-1 静态库生成

把 `.o` 打包成 `.a`，用 GNU 归档工具 `ar`：

```makefile
# Makefile
libmystdio.a: my_stdio.o my_string.o
	@ar -rc $@ $^
	@echo "build $^ to $@ ... done"

%.o:%.c
	@gcc -c $<
	@echo "compling $< to $@ ... done"

.PHONY:clean
clean:
	@rm -rf *.a *.o stdc*

.PHONY:output
output:
	@mkdir -p stdc/include
	@mkdir -p stdc/lib
	@cp -f *.h stdc/include     # 头文件放 include，当"说明书"
	@cp -f *.a stdc/lib         # 库文件放 lib，当"产品"
	@tar -czf stdc.tgz stdc     # 打成压缩包，方便发布
	@echo "output stdc ... done"
```

- `ar` 是 GNU 归档工具，`rc` = replace and create（替换并创建）。
- `output` 目标演示了一个**库的发布姿势**：`include/` 放头文件，`lib/` 放库文件，两者成对交付。别人拿到你的库，就是拿到"头文件 + 库文件"这两样东西。

打包完可以验货：

```bash
$ ar -tv libmystdio.a
rw-rw-r-- 1000/1000   2848 Oct 29 14:35 2024 my_stdio.o
rw-rw-r-- 1000/1000   1272 Oct 29 14:35 2024 my_string.o
```

- `t`：列出静态库中的文件
- `v`：verbose，显示详细信息

可以看到 `libmystdio.a` 里装的就是两个 `.o`——静态库本质上是个"`.o` 的压缩包"。

> **核心结论：静态库 = ar 工具把一组 `.o` 归档成一个 `.a` 文件。**

### 2-2 静态库使用

任意目录下新建 `main.c` 使用这个库：

```c
#include "my_stdio.h"
#include "my_string.h"
#include <stdio.h>

int main()
{
    const char *s = "abcdefg";
    printf("%s: %d\n", s, my_strlen(s));

    mFILE *fp = mfopen("./log.txt", "a");
    if(fp == NULL) return 1;

    mfwrite(s, my_strlen(s), fp);
    mfwrite(s, my_strlen(s), fp);
    mfwrite(s, my_strlen(s), fp);

    mfclose(fp);
    return 0;
}
```

编译时按头文件、库文件的摆放位置，分三种场景：

```bash
# 场景1：头文件和库文件都装到了系统默认路径下
$ gcc main.c -lmystdio

# 场景2：头文件、库文件和 main.c 在同一目录
$ gcc main.c -L. -lmystdio

# 场景3：头文件和库文件各有自己的独立目录（最常见）
$ gcc main.c -I头文件路径 -L库文件路径 -lmystdio
```

三个选项记牢：

- `-L`：指定**库文件**搜索路径
- `-I`：指定**头文件**搜索路径
- `-l`：指定**库名**（去掉 `lib` 前缀和 `.a`/`.so` 后缀，`libc.so` → `c`）

测试：目标文件生成后，把静态库删掉，程序照样能运行——因为库代码在链接时已经**整体拷贝**进可执行文件了。

> **核心结论：链接三件套 `-I -L -l`，静态库链接后"自带干粮"，删库不影响运行。**

## 3. 动态库

### 3-1 动态库生成

生成动态库只比静态库多两个选项：

```makefile
# Makefile
libmystdio.so: my_stdio.o my_string.o
	gcc -o $@ $^ -shared

%.o:%.c
	gcc -fPIC -c $<

.PHONY:clean
clean:
	@rm -rf *.so *.o stdc*

.PHONY:output
output:
	@mkdir -p stdc/include
	@mkdir -p stdc/lib
	@cp -f *.h stdc/include
	@cp -f *.so stdc/lib
	@tar -czf stdc.tgz stdc
	@echo "output stdc ... done"
```

- `-shared`：表示生成共享库格式
- `-fPIC`：产生**位置无关码**（Position Independent Code）——先记住这个名字，第 8 节会揭开它的真正含义
- 库名规则：`libxxx.so`

### 3-2 动态库使用

编译方法和静态库完全一样：

```bash
# 场景2示例：同目录下编译
$ gcc main.c -L. -lmystdio
$ ll
-rwxrwxr-x 1 whb whb 8600 Oct 29 14:51 a.out
-rwxrwxr-x 1 whb whb 8592 Oct 29 14:50 libmystdio.so
-rw-rw-r-- 1 whb whb  359 Oct 19 16:07 main.c
...
```

可以用 `ldd` 查看一个库或可执行程序依赖了哪些动态库：

```bash
$ ldd libmystdio.so
        linux-vdso.so.1 =>  (0x00007fffacbbf000)
        libc.so.6 => /lib64/libc.so.6 (0x00007f8917335000)
        /lib64/ld-linux-x86-64.so.2 (0x00007f8917905000)
```

编译能通过，但一运行就出问题了——这正是动态库最经典的一个坑。

### 3-3 库运行搜索路径

#### 问题

编译时明明指定了 `-L.`，编译也成功了，但运行时报错：

```bash
$ ldd a.out
        linux-vdso.so.1 =>  (0x00007fff4d396000)
        libmystdio.so => not found        <-- 找不到！
        libc.so.6 => /lib64/libc.so.6 (0x00007fa2aef30000)
        /lib64/ld-linux-x86-64.so.2 (0x00007fa2af2fe000)
```

为什么 `-L` 明明写了还找不到？

因为 `-L` 只是**编译期**给链接器看的；程序运行时，是**操作系统（动态链接器 ld-linux.so）**负责去找库，它根本不知道你的 `-L`，只按自己的搜索规则找。

#### 解决方案（四种）

1. **拷贝**：把 `.so` 直接拷到系统共享库路径下（`/usr/lib`、`/usr/local/lib`、`/lib64` 等）。
2. **软链接**：在系统共享库路径下给库建同名软链接。
3. **环境变量**：把库目录加进 `LD_LIBRARY_PATH`：
   ```bash
   export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/your/path
   ```
4. **ldconfig 方案**（最正规）：在 `/etc/ld.so.conf.d/` 下写一个配置文件，然后刷新：
   ```bash
   [root@localhost linux]# echo /root/tools/linux > /etc/ld.so.conf.d/bit.conf
   [root@localhost linux]# ldconfig    # 重新加载库搜索路径，否则不生效
   ```

系统还会维护一个缓存文件 `/etc/ld.so.cache`，记录所有已知动态库的路径，动态链接器找库时先查这个缓存，所以改完配置必须 `ldconfig` 才生效。

> **核心结论：编译期找库靠 `-L`，运行期找库靠系统搜索路径（系统目录 / LD_LIBRARY_PATH / ld.so.conf + ldconfig），两套体系互不相通。**

## 5. 目标文件

现在换个视角：库和可执行文件到底是什么东西？要回答它，得先看清编译和链接的中间产物。

编译的过程，就是把我们程序的源代码**翻译成 CPU 能直接运行的机器代码**。看一个最简单的多文件工程：

```c
// hello.c
#include <stdio.h>
void run();
int main() {
    printf("hello world!\n");
    run();
    return 0;
}

// code.c
#include <stdio.h>
void run() {
    printf("running...\n");
}
```

用 `gcc -c` 分别编译（只编译不链接）：

```bash
$ gcc -c hello.c
$ gcc -c code.c
$ ls
code.c  code.o  hello.c  hello.o
```

生成的 `.o` 文件叫**目标文件**。注意一个工程实践要点：修改了某一个源文件，只需单独重编译那一个 `.o`，不必重编整个工程——这正是"分文件编译"省时间的原因。

目标文件是二进制文件，格式是 **ELF**——对二进制代码的一种封装格式。用 `file` 命令验明正身：

```bash
$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

`relocatable`（可重定位）这个词先记住，第 8 节解释重定位时你就明白它的分量了。

> **核心结论：`.o` 目标文件 = 源码翻译后的机器码封装，格式是 ELF。**

## 6. ELF 文件

### 6-1 四种 ELF 文件

其实以下四种文件都是 ELF 格式：

| 类型 | 例子 | 说明 |
|---|---|---|
| 可重定位文件 | `xxx.o` | 等着和其他目标文件链接，拼成可执行文件 |
| 可执行文件 | `a.out` / `main.exe` | 能直接被操作系统加载运行的程序 |
| 共享目标文件 | `xxx.so` | 动态库，可被多个程序共享 |
| 内核转储 | core dump | 进程崩溃现场快照，用于调试 |

也就是说，`.o`、可执行程序、`.so` 是"一家人"，只是处于不同的加工阶段。理解了 ELF 格式，就同时理解了编译、链接、加载三个环节的载体。

### 6-2 ELF 的组成

一个 ELF 文件由四部分组成：

- **ELF 头（ELF header）**：位于文件开头，描述文件主要特性（类型、架构、入口地址等），主要目的是**定位文件的其他部分**。
- **程序头表（Program header table）**：列举所有有效的**段（segment）**及其属性——每段从哪开始、偏移多少、多长。段在文件里是紧密摆放的，没有这张表就没法把它们切开。
- **节头表（Section header table）**：包含对**节（section）**的描述。
- **节（Section）**：ELF 文件的基本组成单位，不同类型的数据放在不同的节里。

最常见的节：

- **代码节（.text）**：保存机器指令，程序的主要执行部分。
- **数据节（.data）**：保存已初始化的全局变量和局部静态变量。

用 `size` 命令可以快速查看一个可执行程序各部分大小：

```bash
$ size code
   text    data     bss     dec     hex filename
   3312     636       4    3952     f70 code
```

### 6-3 两个视角：链接视图与执行视图

这是本节最重要的一个认识框架。ELF 对外提供**两个视角**，分别服务两个不同阶段的"读者"：

**链接视图——对应节头表（Section header table）**

- 粒度细，按功能模块把文件切开：`.text`（代码）、`.data`（已初始化数据）、`.rodata`（只读数据，如字符串常量——注意它在只读的 text 段里，不在 data 段）、`.bss`（为未初始化全局变量预留位置）、`.symtab`（符号表：函数名/变量名与代码位置的对应关系）、`.got`/`.plt`（后面动态链接的主角）。
- **静态链接分析时看这个视角**。链接器会把许多细碎的节合并、规整成段——为什么急着合并？因为物理内存按页（比如 4KB）整数倍分配，一个很小的节单独占一页，浪费太大。

**执行视图——对应程序头表（Program header table）**

- 告诉操作系统：哪些部分要加载进内存、加载后哪段可读、哪段可写、哪段可执行，指导完成进程内存的初始化。
- **运行加载时看这个视角**。每个可执行程序一定有程序头表。

> **核心结论：节头表给链接器看（链接时用），程序头表给操作系统看（加载时用）。一个管链接，一个管加载。**

ELF 头里就有定位这两张表的信息，自己可以验证：

```bash
$ readelf -h hello.o
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 ...      # 魔数，ELF 文件身份证
  Class:               ELF64                # 64 位架构
  Data:                little endian        # 小端序
  Type:                REL (Relocatable)    # 可重定位文件
  Entry point address: 0x0                  # 目标文件没有入口（还没链接）
  Start of program headers: 0 (bytes)       # 目标文件没有程序头表！
  Start of section headers: 728 (bytes)     # 有节头表，在 728 字节处
  Number of section headers: 13             # 13 个节
```

对比可执行程序的 ELF 头：`Type` 变成 `EXEC` 或 `DYN`、有了 `Entry point address`（入口地址）、有了程序头表——链接前后的差别一目了然。

## 7. ELF 从形成到加载

### 7-1 ELF 如何形成可执行文件

两步走：

- **step-1**：把多份 C/C++ 源代码翻译成目标 `.o` 文件（此时的库也是 ELF 形式）。
- **step-2**：链接器把多份 `.o` 文件的 section 进行**合并**。

注意：实际合并在链接时进行，但并不是简单拼接，还涉及对库的合并，细节不展开——抓住"合并"这个关键词即可。

### 7-2 ELF 如何被加载

加载时还有一次合并：**多个 section 在加载进内存时合并成 segment**。

- **合并原则**：属性相同（可读/可写/可执行、是否需要加载时申请空间）。
- 合并方案在形成 ELF 时就已确定，记录在**程序头表**里。

用 `readelf -S` 看 section 清单，用 `readelf -l` 看 segment 划分，还能看到"section → segment"的映射关系：

```bash
$ readelf -l a.out
Program Headers:
  Type           Offset             VirtAddr           ...
  LOAD           0x0000000000000000 0x0000000000400000  R E    # 一个 LOAD 段
  LOAD           0x0000000000000e10 0x0000000000600e10  RW     # 另一个 LOAD 段

  Section to Segment mapping:
   02     .interp .note... .init .plt .text .fini .rodata ...   # 只读可执行段
   03     .init_array .dynamic .got .data .bss                  # 读写段
```

为什么要合并？两个理由：

1. **减少页面碎片**：内存按页（4KB）管理。如果 `.text` 有 4097 字节、`.init` 有 512 字节，不合并要占 3 页，合并后只要 2 页。
2. **便于权限管理**：相同属性的 section 合并成一个 segment，可以给整段统一设置访问权限，优化内存管理和权限控制（代码那段只读可执行，数据那段可读写）。

另外注意程序头表里的 `LOAD` 类型：不是所有 section 都要加载进内存，带 `LOAD` 标记的才是将来要真正加载的部分。

> **核心结论：链接时合并 section（省文件空间），加载时按属性合并成 segment（省内存页 + 权限隔离），方案由程序头表提前记录。**

## 8. 理解链接与加载

这是全节的核心大戏。前面是"会用库"，这一节回答"库到底是怎么被接进去、被跑起来的"。

### 8-1 静态链接

#### 8-1-1 观察 .o 文件

无论自己的 `.o` 还是静态库里的 `.o`，静态链接本质都是 `.o` 文件的连接过程。所以研究静态链接 = 研究 `.o` 怎么链接。

还是 hello.c + code.c 那组文件：

```bash
$ gcc -c *.c
$ gcc *.o -o main.exe
```

用 `objdump -d` 把 `.o` 的代码段反汇编出来看：

```bash
$ objdump -d hello.o
0000000000000000 <main>:
   0:   f3 0f 1e fa          endbr64
   4:   55                   push   %rbp
   8:   48 89 e5             mov    %rsp,%rbp
   8:   48 8d 3d 00 00 00 00 lea    0x0(%rip),%rdi
   f:   e8 00 00 00 00       callq  14 <main+0x14>    <-- 调 printf，地址是 0！
  14:   b8 00 00 00 00       mov    $0x0,%eax
  19:   e8 00 00 00 00       callq  1e <main+0x1e>    <-- 调 run，地址也是 0！
```

**关键现象**：`call` 指令后面的跳转地址全是 0。

为什么？因为编译 `hello.c` 时，编译器**完全不知道** `printf` 和 `run` 的存在——它们在内存哪个区块、代码长什么样，编译器一概不知，只能先把跳转地址填 0 占位。

#### 8-1-2 重定位表：待修正地址的登记表

地址什么时候被修正？**链接的时候**。

为了让链接器将来能定位这些待修正的地址，`.o` 文件里还有一张**重定位表**，记录"哪些位置的地址需要修正"。链接时按表逐项修正。

#### 8-1-3 符号表：谁认识谁

每个 `.o` 里还有一张**符号表**，可以看作"这个文件的通讯录——我定义了谁、我引用了谁"：

```bash
$ readelf -s hello.o
Symbol table '.symtab' contains 14 entries:
  Num:    Value          Size Type    Bind   Vis      Ndx Name
   10: 0000000000000000    37 FUNC    GLOBAL DEFAULT  1 main        # 我定义了 main
   12: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND puts     # 我用 puts，但本地没有！
   13: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND run      # 我用 run，但本地没有！

# UND = undefined：本 .o 文件里找不到定义
# puts 就是 printf 的底层实现（printf 会优化成 puts）
```

链接前：hello.o 有 `UND run`，code.o 定义了 `run`——两个 `.o` 彼此不认识，各留各的坑。

链接后：查看 main.exe 的符号表，`run` 有了真实地址：

```bash
$ readelf -s main.exe
   52: 0000000000001149    23 FUNC    GLOBAL DEFAULT  16 run    # 有地址了！
   63: 0000000000001160    37 FUNC    GLOBAL DEFAULT  16 main
# 1149：run 函数的最终地址
# 16：run 所在 section 的编号（.text 被合并后排在第 16 位）
```

#### 8-1-4 反汇编验证地址被修正

```bash
$ objdump -d main.exe
...
0000000000001149 <run>:
    1149:   ...                     # run 的真实地址，不再是 0
0000000000001160 <main>:
    1160:   ...
    1179:   e8 cb ff ff ff          callq  1149 <run>    # call 地址修正为 1149！
    116f:   e8 dc fe ff ff          callq  1050 <puts@plt>
```

对比链接前后的两份反汇编：链接前 `call` 后是 `00 00 00 00`，链接后变成了真实地址。**两个 `.o` 的代码段合并到了一起，并进行了统一编址；链接时根据重定位表修正了所有未确定的函数地址。**

#### 8-1-5 总结静态链接

静态链接就是把库中的 `.o` 也拿进来做同样的合并。整个过程：

1. 编译各自出 `.o`（带 0 占位地址 + 重定位表 + 符号表）；
2. 链接器合并所有 `.o`（含静态库中的），统一编址；
3. 按重定位表修正外部符号地址（这叫**编译重定位 / 静态重定位**）；
4. 产出一个独立的、不依赖库文件的可执行文件。

> **核心结论：链接 = 合并 section + 统一编址 + 按重定位表修正地址。**

### 8-2 ELF 加载与进程地址空间

#### 8-2-1 两个问题

- 问题 1：ELF 程序在**没加载到内存之前**，有没有地址？
- 问题 2：进程创建时，`mm_struct`、`vm_area_struct` 这些地址空间结构的初始化数据从哪来？

#### 8-2-2 答案

**问题 1：有地址，而且早就编好了。**

现代计算机工作在"平坦模式"下——程序认为自己独占一整条连续平坦的地址空间。所以 ELF 在编译时就必须对自己的代码和数据**统一编址**。用 `objdump -S` 反汇编可执行程序，最左边一列就是它的虚拟地址（严格说是逻辑地址 = 起始地址 + 偏移量，只是起始地址视为 0）。

也就是说：**虚拟地址在程序还没加载进内存时就已经编好了**，写在 ELF 文件里。

**问题 2：从 ELF 的 segment 来。**

ELF 的每个 segment 都有自己的起始地址和长度。进程创建时，内核读取程序头表，用这些 `[起始, 结束]` 范围去初始化 `mm_struct`、`vm_area_struct`，再按详细地址填充页表。

另外一个铁证：ELF 头里的 `Entry point address`（入口地址），就是程序未来在虚拟地址空间中的入口，程序被加载后从这条地址开始执行。

```bash
$ readelf -h a.out
  Entry point address:  0x1060    # 程序入口，编译时就定好了
```

> **核心结论：虚拟地址机制不光操作系统要支持，编译器也要支持——编译期就完成统一编址，加载时照单全收。**

### 8-3 动态链接与动态库加载

#### 8-3-1 为什么主流是动态链接

先看事实：`ldd main.exe` 显示它依赖 `libc.so.6`——C 语言运行时库，提供标准输入输出、字符串处理等所有常用功能。

那为什么编译器默认不用静态链接？静态链接产出的独立文件确实方便，但它有两个大问题：

1. **体积大**：所有用到的库代码都被拷进每一个可执行文件。
2. **浪费内存**：一百个程序都静态链接 libc，内存里就有一百份相同的 libc 代码。

动态链接的思路：把需要共享的代码单独提取成动态库，程序**运行时**才加载，而且同一份库在内存中只保留一份副本，被所有进程**共享**。省磁盘、省内存，还能做到二进制级别的代码复用。

#### 8-3-2 动态链接如何工作：推迟到运行时

动态链接把链接的整个过程**推迟到程序加载时**：

- 运行程序时，操作系统先把程序的数据代码连同它依赖的一系列动态库加载进内存；
- 每个动态库的加载地址**不固定**，由操作系统根据当前地址空间使用情况动态分配；
- 库的地址一旦确定，再去修正程序中那些函数跳转地址。

一句话：静态链接是"编译时一次定终身"，动态链接是"运行时现场补作业"。

#### 8-3-3 程序入口的秘密：main 之前发生了什么

你以为程序从 `main` 开始？其实不是。可执行程序的真正入口是 `_start`（glibc 或链接器提供的特殊函数），它依次完成：

1. **设置堆栈**：搭建初始栈环境；
2. **初始化数据段**：搬运初始化数据、清零 `.bss`；
3. **动态链接**（关键步骤）：调用**动态链接器**（`ld-linux.so`）解析并加载所有依赖的动态库，完成符号解析和重定位——之前 `call` 后面那些"待定地址"就是在这里被补上的；
4. **调用 `__libc_start_main`**：做剩余初始化（信号处理、线程库等）；
5. **调用 `main`**：控制权这才交到你手里；
6. **处理返回值**：`main` 返回后由 `__libc_start_main` 接住返回值，最终调 `_exit` 结束进程。

所以真实流程是：`_start → 动态链接器加载库并重定位 → __libc_start_main → main`。这些对你完全透明，但理解它，你才能看懂"程序没跑到 main 就崩了"这类诡异问题。

#### 8-3-4 动态库中的相对编址

动态库要"随叫随到"——随时被加载、映射到任意进程的**任意位置**，所以它内部的地址不能写死绝对值，统一采用**相对编址**（可执行程序其实也一样遵守平坦模式，只是 exe 被直接加载，起始位置固定）。

类比：一本活页笔记本，每页只记"相对于第一页偏移几页"。无论这本笔记塞进书架第几格，第 5 页永远是"从第一页往后数 5 页"，永远找得到。

```bash
$ objdump -S /lib/x86_64-linux-gnu/libc-2.31.so | less   # 亲自看：库内全是相对地址
```

这就是 `-fPIC`（位置无关码）的用途：编译出的代码不含写死的绝对地址，加载到哪儿都能跑。

#### 8-3-5 进程怎么看到动态库

动态库也是一个文件——要访问就必须先加载，要加载就必须先打开。

但注意：进程访问库函数是通过**虚拟地址跳转**访问的，所以单纯"读文件"不够，必须把动态库**映射到进程的地址空间**中（还记得进程地址空间的"共享区"吗？动态库就映射在这里）。

映射完成后：库的虚拟起始地址知道了，库内每个方法相对库起始位置的偏移量也知道（相对编址给的），于是：

> **访问库中任意方法 = 库的起始虚拟地址 + 方法偏移量。**

整个调用过程是从进程的代码区跳到共享区，调用完毕再返回代码区，全程都在进程地址空间内完成。

#### 8-3-6 GOT：全局偏移表

现在撞上一个矛盾：

- 库加载地址运行时才确定，所以必须**运行时修改**调用地址（这叫**加载地址重定位 / 运行重定位**）；
- 可是代码段在进程中是**只读**的，改代码 = 违规。

动态链接的解法非常聪明：**不改代码，改数据**。

在可执行程序或库自己的 `.data` 区（可读写！）中预留一片区域，专门存放函数跳转地址，这就是**全局偏移表 GOT（Global Offset Table）**。表中每一项记录本模块要引用的一个全局变量或函数的地址。

```bash
$ readelf -S a.out
...
[24] .got PROGBITS 0000000000003fb8 00002fb8    # .got 就是个数据节
...

$ readelf -l a.out    # .got 加载时和 .data 合并成同一个读写 segment
...
05 .init_array .fini_array .dynamic .got .data .bss
...
```

GOT 的运行规则：

1. 代码段只读、不能改，但 GOT 在可写区，随便改。代码本身可以被所有进程共享（一份只读副本），而 GOT 是每个进程**独立一份**——不同进程里库加载位置不同，GOT 内容自然不同。
2. 单个 `.so` 内部，GOT 与 `.text` 的**相对位置固定**，利用 CPU 相对寻址就能找到 GOT。
3. 调用函数时**先查 GOT**，按表内地址跳转；表项在动态库加载时被改成真地址。
4. 这种实现方式叫**地址无关代码 PIC**。换句话说：`PIC = 相对编址 + GOT`——动态库不做任何修改，加载到任意内存地址都能正常运行、被所有进程共享。这就是编译动态库必须加 `-fPIC` 的原因。

反汇编里能看到 puts 的调用绕经了跳转表：

```bash
$ objdump -S a.out
...
0000000000001050 <puts@plt>:
    1050:   ...  bnd jmpq *0x2f75(%rip)   # 3fd0 <puts@GLIBC_2.2.5>  <-- 跳到 GOT 表项
0000000000001149 <main>:
    1158:   e8 f3 fe ff ff   callq  1050 <puts@plt>                 <-- main 先跳到 PLT
```

> **核心结论：代码只读不能改 → 把跳转地址搬进可写的 .data 区做成 GOT → 运行时只改表、不改代码。**

#### 8-3-7 PLT 与延迟绑定

还有性能问题：动态链接要在加载时对**大量函数**重定位，非常耗时。可绝大多数库函数，程序运行期间可能**一次都不会被调用**——加载时全解析一遍纯属浪费。

优化方案叫**延迟绑定**，由 **PLT（Procedure Linkage Table，过程链接表）**实现：

- GOT 中的跳转地址默认指向一段**桩代码（stub，即 PLT 表项）**；
- 第一次调用函数时：走桩代码 → 查询函数真实地址 → **回填 GOT**；
- 之后再调用：GOT 里已是真地址，直接跳转，不再绕桩。

类比：第一次打某人电话要先查 114 查号台（桩代码），查到后把号码记进自己的通讯录（回填 GOT），以后直接拨号。

总而言之：动态链接把符号查询、地址重定位从编译时推迟到运行时，牺牲了一点加载时间和性能，换来磁盘/内存的高效利用、方便的库升级维护，以及最关键的——**二进制级别的代码复用**。

#### 8-3-8 库间依赖

最后补一刀认识：不只是可执行程序调用库，**库也会调用其他库**（libc 依赖 ld-linux、你链接 ncurses 时它内部还要用别的库）。那库和库之间怎么做到地址无关？

答案：**库自己也有 GOT**，机制与可执行程序完全一样——这也是为什么大家统统都是 ELF 格式，一套规则走天下。解析依赖关系的过程，就是加载各库并完善互相之间 GOT 表的过程。

### 8-4 全节总结

| 对比项 | 静态链接 | 动态链接 |
|---|---|---|
| 链接时机 | 编译时 | 运行时（加载时） |
| 重定位名称 | 编译重定位（静态重定位） | 运行重定位（动态地址重定位） |
| 修正对象 | 直接修正代码中的 call 地址 | 修正 GOT 表项（代码只读不能改） |
| 库代码去向 | 拷贝进可执行文件 | 留在共享库，多进程映射共享 |
| 运行时依赖 | 无 | 需要库文件在搜索路径中 |
| 体积 | 大 | 小 |
| 关键工具 | 链接器 ld | 动态链接器 ld-linux.so + GOT/PLT |

- **静态链接**提高了程序模块化水平：大项目中不同的人可独立开发、测试自己的模块，最后合并成可执行文件。
- **动态链接**把链接推迟到加载时，库加载地址不固定但必须映射进进程地址空间，通过 GOT 完成调用，实现多进程共享同一份库代码。

## 附录：命令速查

```bash
# ===== 库的制作 =====
ar -rc libxxx.a x.o y.o                  # 制作静态库
ar -tv libxxx.a                          # 查看静态库内容
gcc -fPIC -c x.c                         # 编译位置无关目标文件
gcc -shared -fPIC -o libxxx.so x.o y.o   # 制作动态库

# ===== 库的使用 =====
gcc main.c -I./include -L./lib -lmystdio  # 三件套链接
gcc main.c -L. -lmystdio -static          # 强制静态链接

# ===== 运行期找库 =====
ldd a.out                                 # 查看依赖的动态库
export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/your/path   # 临时方案
echo "/your/path" > /etc/ld.so.conf.d/my.conf        # 永久方案
ldconfig                                  # 刷新库缓存（必须执行）

# ===== 查看 ELF =====
readelf -h a.out      # ELF 头（类型/入口/两张表的偏移）
readelf -S a.out      # 节头表（链接视图）
readelf -l a.out      # 程序头表（执行视图，segment）
readelf -s a.out      # 符号表（定义了谁/引用了谁）
objdump -d a.out      # 反汇编代码段
objdump -S a.out      # 带源码的反汇编
file a.out            # 辨识文件类型
size a.out            # 查看 text/data/bss 大小
```

### 学习路径建议

1. **先动手做一遍**：用自己的 `.c/.h` 走完"静态库制作 → 使用 → 动态库制作 → 使用 → 解决 not found"全流程，四种库路径方案各试一次。
2. **用 readelf/objdump 亲眼看**：对照本文各输出，看自己程序的 ELF 头、符号表、反汇编里 call 地址从 0 变真值的过程。
3. **抓住三个"表"**：符号表（谁认识谁）、重定位表（哪些地址要改）、GOT（运行时改的地址表）——静态链接用前两个，动态链接用后两个。
4. **理解两个视图**：节头表（链接器视角）vs 程序头表（OS 加载视角），section vs segment。
5. **记住一组等式**：`PIC = 相对编址 + GOT`；`静态链接 = 合并 + 编译期重定位`；`动态链接 = 推迟 + 运行期重定位（GOT/PLT）`。
