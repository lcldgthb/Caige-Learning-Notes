# 4. 进程控制

## 1. 进程创建

### fork 函数原型与返回值

你已掌握 `pid_t fork(void)`（声明在头文件 `<unistd.h>`）：调用一次返回两次，父进程拿到子进程的 PID，子进程拿到 0，失败时返回 -1；配合 if/else 分流让父子各走各路。下面的重点是 fork 在内核里怎么“接生”子进程，以及工程上怎么用它。

---

### fork 内部：内核的四步操作

当你代码里写下 `fork()`，真正干活的是操作系统内核。内核会按固定流程“造”出一个新进程：

1. **批地皮**：先给新进程分配新的内存块和内核数据结构——这里的数据结构就是操作系统用来登记进程身份的管理表格（PCB/task_struct）。
2. **遗传**：把父进程管理表格里的关键信息复制给子进程，比如当前打开了哪些文件、代码和数据在哪里、当前工作目录等。
3. **上户口**：把新进程加入系统进程列表，让调度器能看到它。
4. **各自回家**：fork 在父进程里返回子进程的 PID，在子进程里返回 0；返回后两者都站在 fork 调用结束的位置，调度器决定接下来谁用 CPU。

> **结论**：子进程不是从 main 开头重新执行，而是直接从 fork 返回处接着跑，仿佛“复制粘贴”了父进程当时的现场。

---

### fork 之后：谁先执行？

父子进程的代码段完全相同，程序计数器也指向同一位置。但谁先抢到 CPU **不由代码顺序决定**，而由调度器根据当时系统负载随机分配。写代码时绝不能假设父进程一定先执行，也不能假设子进程一定先执行。

---

### 写时拷贝的本质

你已学过写时拷贝：父子先共享同一份物理数据，哪一方要写入才私下复制一份。今天要补充它的另一个名字——**延时申请技术**。内核不会在 fork 瞬间就把父进程的所有数据页全盘复制，而是能拖就拖，真正写入时才申请新物理内存。这样做让同一时间系统能容纳的进程数量更多，提高了整机内存使用率。

---

### fork 的两种工程用法（板书强调）

**用法一：父子分工协作。** 父进程守在门口接客（如等待网络请求），每来一个请求就 fork 一个子进程，让儿子去处理具体业务，父亲继续等待下一个请求。这就是把之前学的 if/else 分流用在实际服务器模型里。

**用法二：子进程“换脸”执行新程序。** 子进程 fork 返回后，立刻调用 exec 函数族——这是一套能把当前进程替换成全新程序的函数。比如你在 shell 输入 `ls`，bash 先 fork 出子进程，子进程再 exec 变成 `ls` 程序去执行；bash 自己不动，继续等待你的下一条命令。

> **核心区别**：fork 是“克隆人”，exec 是“灵魂夺舍”。两者经常配套使用：先 fork 复制一份，再 exec 换成新程序。

---

### fork 为什么会失败

虽然 fork 看起来只是调一行代码，但系统资源耗尽时会返回 -1。常见原因有两个：一是系统里进程太多，内存或 PID 编号已被耗尽；二是当前实际用户创建的进程数超过了系统软限制（Linux 中可用 `ulimit -u` 查看上限）。实际工程中遇到 fork 失败，通常选择延迟重试或释放部分资源后再 fork。

```cpp
#include <unistd.h>
#include <sys/types.h>
#include <iostream>

int main() {
    pid_t id = fork();  // 尝试创建子进程
    if (id == -1) {     // 返回 -1 表示系统拒绝分配新进程
        perror("fork"); // 打印具体失败原因
        return 1;       // 退出程序
    }
    // 父子分流逻辑已学过，此处省略
    return 0;
}
```

## 2. 进程终止

### 2-1 进程退出场景

一个程序跑完有三种结局：第一，任务完成，结果也对；第二，任务跑完了，但结果算错了；第三，跑到一半被外界强行打断，比如你在键盘上按了 Ctrl+C。前两种属于正常退场，第三种属于异常终止。

---

### 2-2 常见退出方法

正常退场有三条路：main 函数执行到末尾自然结束；程序任何地方调用 exit；或者调用 _exit。异常退场最常见的就是按 Ctrl+C，这会给当前进程发送 SIGINT 信号，强行终止。

进程在命令行里死亡后，会留下一个数字给它的父进程 bash。你不需要翻日志，直接输入 `echo $?` 就能看到上一个刚结束的命令或程序留下的这个数字。

---

### 2-2-1 退出码

这个数字叫退出码，也叫退出状态。0 表示“我成功做完了”，非 0 表示“我出了问题”。退出码 1 通常表示“操作不被允许”，比如普通用户没加 sudo 就执行需要权限的 yum，或者程序里出现了除以 0 的非法运算。如果进程是被信号终止的，bash 会把退出码编码成 128 加上信号编号：按 Ctrl+C 对应 SIGINT（信号编号 2），`echo $?` 就会显示 130；收到 SIGTERM（编号 15）终止则显示 143。

C 语言里可以用 strerror 把数字翻译成人类可读的错误描述：

```c
#include <stdio.h>
#include <string.h>

int main() {
    printf("%s\n", strerror(1));    // 将退出码 1 转为文字描述
    printf("%s\n", strerror(130));  // 将退出码 130 转为文字描述
    return 0;
}
```

这个退出码最终写到进程的 task_struct 里，父进程通过 wait 来读取。不同的数值对应不同的失败原因，就像医院诊断书上的不同编码。但要特别注意：操作系统会往同一个整数里打包两份信息——高位记录退出码，低位记录“是否被信号杀死”。一旦低 7 个比特位不为 0，就说明进程死于信号，此时高位的退出码数值不再具有实际意义。

---

### 2-3-2 _exit 函数

`_exit` 是操作系统内核提供的系统调用，直接让内核把进程抹掉，头文件是 unistd.h，原型如下：

```c
#include <unistd.h>

void _exit(int status);  // status：想告知父进程的终止状态
```

父进程通过 wait 只能拿到这个 status 的低 8 位（0~255）。因此如果你写 `_exit(-1)`，-1 的二进制低 8 位全是 1，换算后就是 255，所以终端里 `echo $?` 会看到 255。

因为 _exit 直接找内核，不经过 C 标准库的善后流程，**进程退出时不会刷新 C 语言库的缓冲区**——你之前学过的行缓冲数据如果还留在库里，会直接丢失。

---

### 2-3-3 exit 函数

`exit` 是 C 标准库函数（声明在 stdlib.h），它最后也会调用 _exit，但在“自尽”之前还会做三件后事：第一，执行你通过 atexit 或 on_exit 提前注册的清理函数；第二，关闭所有打开的文件流，并把 C 库缓冲区里的数据刷到屏幕上或文件里（和你已学过的 fflush 逻辑一脉相承）；第三，才调用 _exit 真正退出。

所以 exit（库函数）与 _exit（系统调用）的本质区别只有一条：**exit 会刷新 C 标准库的缓冲区，_exit 不会**。另外必须记牢，这个缓冲区是 C 语言库自己维护的，不是操作系统内核里的缓冲区。

下面这段代码能直观看到差别：

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main() {
    printf("hello");      // 没换行，字符串暂存在 C 库缓冲区
    // exit(0);           // 刷新缓冲区，终端能看到 hello
    _exit(0);             // 直接走人，不刷新，终端看不到 hello
    return 0;
}
```

---

### 2-3-4 return 退出

平常写代码最常用的还是 return。在 main 函数里写 `return n;` 和执行 `exit(n);` 效果完全一样——运行时会把你 return 的值转交给 exit。但这条等式只在 main 里成立：**main 函数结束代表整个进程结束；其他函数里的 return 仅仅是那个函数调用完毕，把控制权交回上一层，进程继续跑**。另外，exit 无论在哪个深层函数里被调用，都会直接终止整个进程，并把退出码交给父进程 bash。

```c
#include <stdio.h>
#include <stdlib.h>

void foo() {
    return;               // foo 返回，main 继续执行
    // exit(5);           // 若换成 exit，整个进程立刻结束
}

int main() {
    foo();
    printf("still alive\n");  // return 时这行会执行；exit 时不会
    return 0;                 // 等价于 exit(0)，bash 用 echo $? 读到 0
}
```

## 3. 进程等待

### 3-1 进程等待必要性

子进程执行完任务退出后，如果父进程不处理，就会变成前面学过的僵尸进程，导致内存泄漏。更麻烦的是，僵尸进程已经"死"了，`kill -9` 也杀不掉它。另一方面，父进程通常还想知道子进程任务完成得怎么样——比如是正常算完了，还是中途被信号杀死了。因此，父进程必须主动进行进程等待：一是**必须回收子进程的资源**，防止内存泄漏；二是**可以选择性地获取
### 3-2 进程等待的方法

Linux 提供了两个系统调用让父进程回收子进程资源：`wait` 和 `waitpid`。两者的关系类似于"基础版"和"专业版"。

---

#### 3-2-1 wait 方法

`wait` 是最简单的等待函数，它的作用是：阻塞等待任意一个子进程结束。

```c
#include <sys/types.h>
#include <sys/wait.h>

pid_t wait(int* status);
```

- **返回值**：成功返回被等待子进程的 PID，失败返回 -1。
- **`status`**：输出型参数——你传一个整型变量的地址进去，函数返回时操作系统会把子进程的退出信息填到这个地址里。如果你不关心退出原因，直接传 `NULL` 即可。

**关键特性**：如果子进程还在运行没退出，父进程调用 `wait` 后会**阻塞**在原地，直到子进程结束才会继续往下执行。

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>

int main() {
    pid_t id = fork();          // 创建子进程
    if (id < 0) {
        perror("fork");         // fork失败打印错误
        exit(1);
    } else if (id == 0) {
        printf("child %d running\n", getpid());
        sleep(3);               // 模拟子进程工作3秒
        exit(0);                // 子进程正常退出，返回码为0
    } else {
        printf("father waiting...\n");
        pid_t ret = wait(NULL); // 阻塞等待，子进程没结束就在这里卡住
        if (ret > 0) {
            printf("wait success, child pid: %d\n", ret);
        }
    }
    return 0;
}
```

> **`wait(NULL)` 只能随机等任意一个子进程，无法精确指定等谁，也无法设置非阻塞。**

---

#### 3-2-2 waitpid 方法

`waitpid` 功能更强，可以精确指定等哪一个子进程，也可以设置是否阻塞。

```c
pid_t waitpid(pid_t pid, int *status, int options);
```

**返回值**：
- `> 0`：成功等到子进程，返回该子进程 PID。
- `== 0`：仅在非阻塞模式下，表示目标子进程还没结束。
- `< 0`：出错（比如等了一个不存在的进程）。

**`pid` 参数**（重点）：
- `pid > 0`：精确等待进程 ID 等于这个值的子进程。
- `pid == -1`：等任意子进程，效果和 `wait` 一样。
- `pid == 0`：等待和父进程同属一个"进程组"的子进程（进程组：一批进程编成的协作小组，有个共同的组号）。
- `pid < -1`：等待进程组 ID 等于 `pid` 绝对值的任意子进程。

后两种场景在基础开发中较少用到，重点记住：**`waitpid(-1, &status, 0)` 等价于 `wait(NULL)`**。

**`options` 参数**：
- `0`：默认阻塞等待。
- `WNOHANG`：非阻塞等待（后面详细讲）。

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>

int main() {
    pid_t id = fork();
    if (id == 0) {
        sleep(2);               // 子进程工作2秒
        exit(10);               // 子进程退出码设为10
    }
    int status = 0;
    pid_t ret = waitpid(id, &status, 0);  // 指定等id这个子进程，阻塞模式
    if (ret > 0) {
        printf("waitpid success, ret = %d\n", ret);  // ret就是id的值
    }
    return 0;
}
```

> **如果子进程已退出，`wait/waitpid` 立刻返回并回收资源；如果子进程还在跑，调用可能阻塞；如果等的子进程不存在，立刻报错返回。**

---

#### 3-2-3 获取子进程 status

`status` 这个整数不能当成普通数学数字直接用，要把它看成**一组二进制位拼接而成**（只研究低 16 位），不同段代表不同含义。

低 16 位的结构如下：

```text
正常终止： | 退出状态(8位) | 0(1位) | 0(7位) |
被信号杀死：|   未用(8位)   | core dump(1位) | 终止信号(7位) |
```

- **高 8 位（15~8）**：子进程的退出码（正常终止时才有意义）。
- **低 7 位（6~0）**：终止信号编号（被信号杀死时非 0）。
- **第 7 位**：core dump 标志（先不管）。

因为进程结束只有两种情况：要么自己执行完 `exit` 正常退出，要么被外界信号（如 `kill -9`）强行杀死。操作系统把这两种信息压缩到一个整数里传给父进程。

系统提供了两个宏来解析，不需要手动算位：
- `WIFEXITED(status)`：如果子进程是正常终止，返回真。
- `WEXITSTATUS(status)`：如果正常终止，提取出退出码（0~255）。

**关键判断逻辑**：先看低 7 位是否为 0。如果低 7 位非 0，说明是异常退出（被信号杀死），此时高 8 位的退出码没有意义。

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <signal.h>
#include <sys/types.h>
#include <sys/wait.h>

int main() {
    // 场景1：子进程正常退出，退出码42
    pid_t id = fork();
    if (id == 0) {
        exit(42);
    }
    int st = 0;
    waitpid(id, &st, 0);
    
    if (WIFEXITED(st)) {                        // 判断是否正常退出
        printf("normal exit, code: %d\n", WEXITSTATUS(st));  // 提取退出码
    }
    printf("manual code: %d\n", (st >> 8) & 0xFF);  // 手工提取高8位：右移8位再&0xFF
    printf("manual signal: %d\n", st & 0x7F);       // 手工提取低7位：& 0x7F（低7位全1）
    
    // 场景2：子进程被信号杀死
    pid_t id2 = fork();
    if (id2 == 0) {
        while (1) sleep(1);  // 死循环
    }
    kill(id2, 9);           // 父进程发9号信号杀死子进程
    int st2 = 0;
    waitpid(id2, &st2, 0);
    printf("killed by signal: %d\n", st2 & 0x7F);   // 低7位非0，值为9
    printf("core dump flag: %d\n", (st2 >> 7) & 1); // 提取第7位
    
    return 0;
}
```

> **操作系统把子进程的 `exit_code` 和 `exit_signal` 保存在它的 `task_struct` 里；父进程调用 `wait/waitpid` 时，内核把这些信息拷贝到 `status` 变量中。异常退出时低 7 位非 0，此时退出码无意义。**

---

#### 3-2-4 阻塞与非阻塞等待

这两个概念的区别在于：父进程调用 `waitpid` 时，如果子进程还没结束，父进程是**干等着**还是**先去做别的事**。

| 方式 | 选项 | 行为 | 类比 |
|------|------|------|------|
| 阻塞等待 | `0` | 父进程挂起，直到子进程结束才返回 | 打电话找人，对方不接，你一直拿着电话干等 |
| 非阻塞等待 | `WNOHANG` | 子进程没结束，函数立刻返回 0，父进程可以继续执行 | 打电话找人，对方不接，你挂了电话去忙别的，过会儿再打 |

`WNOHANG` 全称 "No Hang"，意思是如果子进程没退出，不要挂起父进程，立即返回 0。

非阻塞等待的真正用法是**轮询**：父进程循环调用 `waitpid(WNOHANG)`，每次返回 0 就说明子进程还在跑，父进程趁机做自己的业务，过一会儿再查。

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>

void handler() {
    printf("father doing other work...\n");
    sleep(1);
}

int main() {
    pid_t id = fork();
    if (id == 0) {
        int cnt = 5;
        while (cnt--) {
            printf("child running: %d\n", cnt);
            sleep(1);
        }
        exit(0);
    }
    
    int status = 0;
    pid_t ret = 0;
    do {
        ret = waitpid(id, &status, WNOHANG);  // 非阻塞：子进程没结束就返回0
        if (ret == 0) {
            printf("child is still running, father check again later\n");
            handler();  // 父进程做其他事情
        }
    } while (ret == 0);  // ret为0表示还没等到，继续循环轮询
    
    if (ret > 0) {
        printf("wait success, pid: %d\n", ret);
    }
    return 0;
}
```

如何让父进程"做其他事情"更灵活？可以准备一批函数，用**函数指针数组**（C 风格）或 `std::function`（C++ 风格）来注册回调，轮询期间依次调用。

> **`waitpid(-1, &status, 0)` 是阻塞等待，父进程挂起直到子进程结束；`waitpid(-1, &status, WNOHANG)` 是非阻塞等待，子进程未结束立刻返回 0，父进程通过循环轮询实现"边等边干活"。**

## 4. 进程程序替换

### 4-1 替换原理

用fork创建子进程后，子进程起初和父进程执行完全相同的代码。但实际工作中常常需要子进程去做截然不同的事，例如执行系统命令`ls`，或运行另一个独立的可执行文件。如果在一个源文件里用`if/else`硬编码所有分支，程序会臃肿到无法控制。进程程序替换就是解决这个问题的机制：把磁盘上一个新程序的代码和数据加载到当前进程的地址空间中，直接覆盖掉旧内容。

> **调用exec并不创建新进程：进程PID保持不变，内核数据结构task_struct纹丝不动，只有用户空间的代码和数据被替换。**

替换成功后，CPU从新程序的启动入口开始执行。原代码中位于exec调用之后的指令已经被物理覆盖，永久消失，永远不会执行。因此exec系列函数有一个反直觉的约定：

> **exec系列函数只有失败返回值-1；一旦替换成功，函数根本不会返回。**

这意味着代码中exec调用后面通常直接紧跟错误处理逻辑，只要返回就一定是出错了。

---

### 4-2 替换函数

系统提供六个exec函数：`execl`、`execlp`、`execle`、`execv`、`execvp`、`execve`。名字的后缀决定如何寻找程序和传递参数，规律如下：

| 后缀 | 含义 | 作用 |
| :--- | :--- | :--- |
| `l` | list | 参数逐个列出，像排队报数，最后以`NULL`结尾 |
| `v` | vector | 参数先装进`char* argv[]`数组，传数组名即可 |
| `p` | path | 带`p`则自动到环境变量PATH中搜索程序，无需写全路径 |
| `e` | env | 带`e`可自定义环境变量表；不带`e`则继承当前进程的环境变量 |

四种最常用的组合写法：

```cpp
#include <unistd.h>

// l版：写完整路径，参数逐个传，NULL结尾
execl("/usr/bin/ls", "ls", "-l", "-a", NULL);  // 路径, argv[0](程序名), 参数1, 参数2, 结束哨兵NULL

// p版：只传程序名，系统自动去PATH里搜索完整路径
execlp("ls", "ls", "-l", "-a", NULL);          // 程序名, argv[0], 参数1, 参数2, 结束哨兵NULL

// v版：完整路径 + 参数数组
char* argv[] = {"ls", "-l", "-a", NULL};
execv("/usr/bin/ls", argv);                    // 路径字符串 + 参数数组首地址

// vp版：程序名自动搜PATH + 参数数组
execvp("ls", argv);                            // 程序名字符串 + 参数数组首地址
```

`execle`和`execve`在最后多出一个参数`char *const envp[]`，用于传入全新的环境变量表。

**环境变量传入有三种方式：**
1. `putenv`新增环境变量，这会修改当前进程的环境表，影响后续fork出的子进程。
2. `execle`/`execve`通过参数传入自定义的`envp`列表，仅影响被替换的那个进程。
3. 使用不带`e`的exec函数，默认继承父进程的环境变量。

> **只有`execve`是真正的系统调用**（操作系统内核直接提供的接口），其余五个都是C库函数对`execve`的封装，最终都会调用`execve`。

exec替换为什么不影响父进程？因为fork之后父子进程地址空间已经通过写时拷贝分离，子进程在自己的地址空间里加载新程序，父进程的代码和数据保持原样。

最后，exec不仅能替换系统命令，**也能替换你自己写的程序**。只要给出正确的可执行文件路径，例如`execl("./other", "other", NULL);`，子进程就会开始执行你编译出的`other`程序。

## 5. 自主 Shell 命令行解释器

### 5-1 目标

平时你在 XShell 里敲命令，背后是 bash 这个“命令行解释器”在帮你跑腿。本节我们要自己写一个迷你版的 bash，亲手把命令分成两类：一类像 `ls` 这种，必须派小弟（子进程）去做；另一类像 `cd` 这种，必须 bash 亲自动手。写完你就能彻底理解：为什么 `export` 设置的环境变量能影响后面的命令，而普通命令跑完就消失；shell 的提示符是怎么拼出来的；`echo $?` 为什么能拿到上一个命令的返回值。

---

### 5-2 实现原理

**shell 的典型互动**  
shell 其实是个死循环：打印提示符 → 等你输入 → 把输入切成一份一份 → 判断是自己做还是派别人做 → 做完再回到第一步。

**自主 shell 循环过程**（板书强调）

1. 打印命令行提示符：`[用户名@主机名 当前目录]# `
2. `fgets` 读取一整行
3. `strtok` 按空格切成数组 `gargv`，末尾放 `NULL`
4. 检查是不是内建命令（`cd` / `export` / `env` / `echo`），是则自己执行
5. 普通命令：`fork` 创建子进程 → 子进程 `execvp`
→ 子进程 `execvp(gargv[0], gargv)` 加载新程序运行 → 父进程 `waitpid` 阻塞等待收尸 → 用 `WEXITSTATUS` 提取退出码保存到 `lastcode` → 回到第 1 步读取下一行。

**内建命令 vs 普通命令**（板书强调）

普通命令如 `ls` / `ps` / `cat`，必须由子进程执行。原因在于 `execvp` 会用新程序的代码和数据替换掉当前进程；如果 shell 亲自执行 `execvp`，shell 自身就被覆盖掉了，循环直接中断，你再也看不到提示符。

内建命令如 `cd` / `export` / `env` / `echo`，绝对不能派子进程执行，必须由 shell 自己完成。因为这些命令改的是 shell 自身的“状态”：例如 `cd` 改的是当前工作目录，如果让子进程去改，子进程目录变完立刻退出，shell 仍站在原地，用户会感觉“cd 没生效”；`export` 改的是环境变量表，必须由 shell 亲自写入，后续 `fork` 出的子进程才能继承到新变量。

| 对比项 | 普通命令 | 内建命令 |
|---|---|---|
| 代表命令 | ls、ps、cat | cd、export、env、echo |
| 执行者 | 子进程 | shell 自己 |
| 是否影响 shell 自身状态 | 不影响 | 直接影响 |
| 是否创建子进程 | 是（fork + exec） | 否 |

**内建命令的本质**：shell 直接调用 C 函数或系统调用来完成工作，全程不创建子进程（板书强调）。

---

### 5-3 源码关键结构

实现这个迷你 shell，核心靠几张全局表和一套固定流程。

**全局数据结构**

```cpp
char *gargv[64];   // 存命令行切分后的单词，如 ["ls", "-l", NULL]
int gargc = 0;     // 记录当前有多少个单词

char *genv[64];    // shell 自己的环境变量表，从父 shell 的 environ 拷贝而来
char pwd[1024];    // 存当前工作目录的绝对路径
char pwdenv[1024]; // 拼成 "PWD=/home/xxx" 格式，供 putenv 使用
int lastcode = 0;  // 上一个命令的退出码，供 echo $? 使用
```

为什么非得把父 shell 的环境变量拷贝到 `genv`？因为 shell 需要自己做管家：后续 `export` 新增变量时，往自己的 `genv` 里追加即可，不应破坏父进程传入的原始环境表（板书强调）。

**提示符生成与输入读取**

```cpp
// 从 getpwuid/gethostname/getcwd 等拿到信息，用 snprintf 拼成字符串
snprintf(command_line, size, "[%s@%s %s]# ", 用户名, 主机名, 当前目录名);

// fgets 从标准输入读一整行，包含换行符
fgets(command_buffer, sizeof(command_buffer), stdin);
```

**解析命令行：strtok 切分**

```cpp
// 以空格为分隔符，把 "ls -l /tmp" 切成 gargv[0]="ls", gargv[1]="-l"...
gargc = 0;
gargv[gargc] = strtok(command_buffer, " ");
while (gargv[gargc]) {
    gargc++;
    gargv[gargc] = strtok(NULL, " ");
}
// 循环结束时 gargv 以 NULL 结尾，正好满足 execvp 对 argv 的要求
```

**执行普通命令**

```cpp
pid_t id = fork();               // 创建子进程
if (id == 0) {
    // 子进程：代码和数据被替换成目标程序
    execvp(gargv[0], gargv);     // gargv[0] 是命令名，gargv 是整个参数数组
    exit(1);                     // exec 失败才走到这里，返回错误码
}
// 父进程：阻塞等待子进程结束，收尸避免僵尸进程
int status = 0;
waitpid(id, &status, 0);         // 第三个参数 0 表示阻塞等待
lastcode = WEXITSTATUS(status);  // 从 status 中提取子进程 exit 的低 8 位
```

**内建命令实现**（板书强调）

```cpp
// cd：改变 shell 自身的当前目录，并更新 PWD 环境变量
if (strcmp(gargv[0], "cd") == 0) {
    if (gargv[1]) chdir(gargv[1]);          // 系统调用，改变当前工作目录
    getcwd(pwd, sizeof(pwd));               // 获取新的绝对路径
    snprintf(pwdenv, sizeof(pwdenv), "PWD=%s", pwd);
    putenv(pwdenv);                         // 更新环境变量表中的 PWD
}

// export：把 "MYVAR=123" 这样的字符串加入 genv 数组
if (strcmp(gargv[0], "export") == 0) {
    if (gargv[1]) {
        genv[env_index++] = strdup(gargv[1]); // strdup 复制字符串到堆
        genv[env_index] = NULL;               // 保持数组以 NULL 结尾
    }
}

// env：遍历自己的 genv 表，逐行打印
if (strcmp(gargv[0], "env") == 0) {
    for (int i = 0; genv[i]; i++) {
        printf("%s\n", genv[i]);
    }
}

// echo：支持 echo $? 和 echo $VAR
if (strcmp(gargv[0], "echo") == 0) {
    if (strcmp(gargv[1], "$?") == 0) {
        printf("%d\n", lastcode);           // 打印上一个命令退出码
    } else if (gargv[1][0] == '$') {
        char *val = getenv(gargv[1] + 1);   // 跳过 $ 取变量名
        printf("%s\n", val ? val : "");
    } else {
        printf("%s\n", gargv[1]);           // 普通字符串直接打印
    }
}
```

**环境变量初始化**

程序启动时，从父 shell 传入的 `extern char **environ` 逐条拷贝到 `genv`，这样迷你 shell 拥有了一张独立的环境变量表（板书强调）。后续所有子进程都会继承这张表的副本。

**TrimSpace 宏**

处理用户不小心输入的前导空格，例如 `" file.txt"`：

```cpp
#define TrimSpace(start) do { \
    while (isspace(*start)) start++; \
} while(0)
```

### 5-4 总结

> **exec/exit 就像 call/return：C 语言中函数通过 call/return 通信；Linux 中进程通过 fork/exec/wait/exit 通信。**

一个 C 程序可以 `fork` 出子进程，在子进程中 `execvp` 加载另一个程序并传参；被调用程序执行完毕后通过 `exit(n)` 把返回值交给操作系统；调用进程通过 `wait(&ret)` 回收子进程并获取这个返回值。自主 shell 把这四个系统调用串成一个循环，便实现了命令行解释器的核心机制。
