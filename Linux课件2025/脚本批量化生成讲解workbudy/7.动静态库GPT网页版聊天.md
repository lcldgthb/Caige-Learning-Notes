# Linux 系列（07）——库制作与原理

这节课的核心其实只有一条主线：

库是什么 → 如何制作和使用库 → 程序如何链接库 → ELF 如何组织程序 → 程序如何加载动态库并运行。

本节内容比较多，但不需要把所有 ELF 字段都记下来。重点是理解静态链接、动态链接、ELF 和动态库加载之间的关系。

## 一、库是什么？为什么需要库？

库（Library）就是别人已经写好、编译好的、可以重复使用的代码。

例如，我们使用 `printf()`，不需要自己实现它，直接调用 C 标准库即可。

Linux 下主要有两种库：

| 类型  | 后缀    | 核心特点                |
| --- | ----- | ------------------- |
| 静态库 | `.a`  | 链接时将需要的代码复制到可执行程序中  |
| 动态库 | `.so` | 程序运行时加载，多个进程可以共享库代码 |

重点理解

可以把它们想象成两种使用工具的方式：

- 静态库：把工具直接装进自己的工具箱，之后不需要再找原来的工具仓库。
- 动态库：工具放在公共仓库，需要时去取，多个程序可以共同使用。

两者最重要的区别：库代码什么时候进入程序的运行过程。

## 二、静态库的制作与使用

先记住静态库的制作流程：

源文件 `.c`

gcc -c 编译

目标文件 `.o`

ar 归档

静态库 `libxxx.a`

1\. 制作静态库

```
# 将源文件编译成目标文件
gcc -c my_stdio.c my_string.c

# 将目标文件打包成静态库
ar -rc libmystdio.a my_stdio.o my_string.o

# 查看静态库里面有哪些目标文件
ar -tv libmystdio.a
```

记住：

- `ar`：GNU 归档工具。
- `r`：替换已有成员。
- `c`：创建归档文件。

2\. 使用静态库

```
# -I 指定头文件搜索路径
# -L 指定库文件搜索路径
# -l 指定库名称（去掉 lib 前缀和 .a 后缀）
gcc main.c -I./include -L./lib -lmystdio
```

三个参数一定要区分：

| 参数   | 作用    |
| ---- | ----- |
| `-I` | 找头文件  |
| `-L` | 找库文件  |
| `-l` | 指定库名称 |

例如 `libmystdio.a`，使用时写 `-lmystdio`。

重要结论

静态库在链接阶段就把需要的代码合并到可执行程序中，因此生成可执行程序后，即使删除原来的 `.a` 文件，程序通常仍然可以运行。

## 三、动态库的制作与使用

动态库的制作流程与静态库类似，但有两个关键区别：

1. 需要生成位置无关代码（PIC）。
2. 使用 `-shared` 生成共享库。

1\. 制作动态库

```
# -fPIC：生成位置无关代码
gcc -fPIC -c my_stdio.c my_string.c

# -shared：生成动态共享库
gcc -shared -o libmystdio.so my_stdio.o my_string.o
```

重点理解：

- `-fPIC`：Position Independent Code，位置无关代码。
- `-shared`：生成共享库。

为什么需要位置无关代码？

因为动态库在不同进程中的加载地址可能不同。

如果代码里面写死了某个函数的绝对地址，那么换一个加载位置就可能无法正常执行。

所以需要通过相对寻址等方式，让代码不依赖固定的加载地址。

2\. 使用动态库

```
# 编译链接动态库
gcc main.c -I./include -L./lib -lmystdio

# 查看程序依赖了哪些动态库
ldd a.out
```

这里有一个非常容易混淆的地方：

编译时找到了动态库，不代表程序运行时一定能找到动态库！

编译链接阶段的 `-L` 只是告诉链接器去哪里寻找库。

程序运行时，还需要动态链接器找到对应的 `.so` 文件。

## 四、动态库找不到怎么办？

例如：

```
# 查看程序依赖
ldd a.out

# 发现自己的动态库没有找到
libmystdio.so => not found
```

这是因为运行时动态库搜索路径中没有对应的库。

Ubuntu 下主要有以下几种解决办法：

| 方式                | 作用          |
| ----------------- | ----------- |
| 拷贝到系统库目录          | 让系统能够找到库    |
| 建立软链接             | 通过链接指向实际库文件 |
| `LD_LIBRARY_PATH` | 临时添加搜索路径    |
| `ldconfig`        | 更新系统动态库缓存   |

例如：

```
# 临时添加动态库搜索路径
export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/home/caige/lib

# 配置永久搜索路径
sudo vim /etc/ld.so.conf.d/mylib.conf

# 在配置文件中写入库所在目录
# /home/caige/lib

# 更新动态库缓存
sudo ldconfig
```

另外，记住一个命令：

`ldd`：查看可执行程序依赖的动态库。

## 五、目标文件与 ELF 格式

前面我们使用过：

```
gcc -c hello.c
```

它会生成：

```
hello.c → hello.o
```

这里的 `.o` 就是目标文件（Object File）。

而目标文件并不是普通文本，它是一种二进制文件，采用 ELF 格式。

ELF 全称：

Executable and Linkable Format（可执行与可链接格式）。

Linux 下常见的 ELF 文件有四种：

| 类型            | 含义     | 示例         |
| ------------- | ------ | ---------- |
| Relocatable   | 可重定位文件 | `.o`       |
| Executable    | 可执行文件  | 可执行程序      |
| Shared Object | 共享目标文件 | `.so`      |
| Core Dump     | 内核转储   | 程序崩溃时的转储文件 |

### 1. ELF 文件的组成

ELF 主要由四部分组成：

- ELF Header：文件头，描述文件基本信息。
- Program Header Table：程序头表，描述程序如何加载。
- Section Header Table：节头表，描述文件中的各个节。
- Section：节，存放具体的代码和数据。

其中最重要的是理解 Section 和 Segment 的区别。

### 2. Section 和 Segment

Section（节）：从链接的角度组织文件。

常见的节：

| 节         | 作用               |
| --------- | ---------------- |
| `.text`   | 存放机器指令           |
| `.data`   | 已初始化的全局变量、静态变量   |
| `.rodata` | 只读数据，例如字符串常量     |
| `.bss`    | 未初始化的全局变量、静态变量   |
| `.symtab` | 符号表，记录函数、变量等符号信息 |
| `.got`    | 全局偏移表            |

Segment（段）：从程序加载执行的角度组织文件。

操作系统加载程序时，不需要关心每个 Section 的具体细节，而是按照相应的属性，将多个 Section 组织成 Segment。

例如：

- 可读、可执行的段。
- 可读、可写的段。
- 只读的段。

## Section 与 Segment 的关系

链接视图 · Section

.text

代码

.rodata

只读数据

.data

可写数据

按照加载属性组织

执行视图 · Segment

LOAD 段 1

包含代码及只读数据

LOAD 段 2

包含可读写数据

为什么要这样组织？

因为内存管理通常以页为单位，如果每个小 Section 都单独加载和管理，会产生大量空间浪费。

因此，将具有相同访问属性的 Section 组织起来，可以提高内存利用率，也方便权限管理。

必须记住

- Section 对应节头表，主要服务于链接视图。
- Segment 对应程序头表，主要服务于执行视图。
- `readelf -S`：查看 Section。
- `readelf -l`：查看 Segment。

### 3. ELF 文件常用命令

```
# 查看文件类型
file a.out

# 查看 ELF 文件头
readelf -h a.out

# 查看 Section
readelf -S a.out

# 查看 Segment
readelf -l a.out

# 查看符号表
readelf -s a.out

# 反汇编机器指令
objdump -d a.out
```

不需要背输出的每一个字段，重点是知道不同命令查看什么。

## 六、静态链接的原理

这是本节非常重要的部分。

先看一个例子：

`hello.c` 中调用了 `run()`，但 `run()` 实际定义在 `code.c` 中。

```
// hello.c
#include <stdio.h>
void run(); // 声明 run 函数

int main()
{
    printf("hello world!\n");
    run(); // 调用另一个源文件中的函数
    return 0;
}
```

```
// code.c
#include <stdio.h>

void run()
{
    printf("running...\n");
}
```

第一步：分别编译。

```
gcc -c hello.c
gcc -c code.c
```

生成：

```
hello.o
code.o
```

此时有一个问题：

`hello.o` 并不知道 `run()` 函数具体在哪里。

因为编译 `hello.c` 时，编译器只看到了函数声明，并不知道另一个目标文件中函数的实际地址。

因此，编译器会先留下需要修正的位置，并记录在重定位信息中。

第二步：链接。

```
gcc hello.o code.o -o main.exe
```

链接器做了什么？

1. 将多个 `.o` 中的 Section 合并。
2. 对合并后的代码和数据统一编址。
3. 根据重定位信息，修正外部函数和变量的地址。

例如原来 `hello.o` 中调用 `run()` 的地址还没有确定，链接完成后，就能找到 `run()` 的实际位置。

## 静态链接过程

hello.o

main 函数

code.o

run 函数

链接器：合并 + 统一编址 + 重定位

main.exe

形成完整的可执行程序

核心结论

静态链接 = 合并目标文件 + 统一编址 + 地址重定位。

静态库本质上也是一组 `.o` 文件，使用静态库时，链接器会从库中提取需要的目标文件参与链接。

## 七、虚拟地址空间与 ELF 加载

这一部分是理解动态库加载的前置知识。

先思考一个问题：

程序还没有运行、还没有加载到内存中，ELF 文件有没有地址？

答案：有。

ELF 在链接过程中，就已经对程序的代码和数据进行了统一编址。

例如：

```
0000000000001149 <run>:
0000000000001160 <main>:
```

这些地址就是程序预先确定的地址布局。

当程序真正运行时，操作系统会根据 ELF 的 Segment 信息，建立进程对应的虚拟地址空间。

这里联系之前学过的进程地址空间：

- `mm_struct`：描述进程的虚拟地址空间。
- `vm_area_struct`：描述虚拟地址空间中的一段区域。
- 页表：负责虚拟地址与物理地址之间的映射。

ELF 的 Segment 信息，是内核初始化进程地址空间的重要依据。

可以这样理解：

ELF 事先规划好了程序代码和数据应该放在哪里，操作系统负责根据这些规划建立进程的内存布局。

## ELF 到进程地址空间

ELF 文件

记录代码、数据、入口地址和 Segment 信息

操作系统加载

根据 Program Header 组织内存映射

进程虚拟地址空间

mm_struct、vm_area_struct、页表

这里还要记住：

程序真正的入口并不是我们写的 `main()`，而是 `_start`。

通常的启动过程可以简化为：

```
_start
   ↓
__libc_start_main
   ↓
main
```

中间还涉及运行环境初始化等工作。

## 八、动态链接与动态库加载原理

这是整节课最核心、也最难理解的部分。

### 1. 为什么需要动态链接？

假设电脑上有三个程序，都使用了 C 标准库。

如果使用静态链接：

三个程序都把需要的库代码分别复制到自己的可执行文件中。

这样会造成：

- 可执行文件体积增大。
- 磁盘空间浪费。
- 相同代码重复占用资源。

如果使用动态链接：

将公共代码放在 `.so` 文件中，程序运行时加载动态库。

多个进程可以共享动态库的代码部分，从而节约内存和磁盘空间。

### 2. 动态库为什么需要 PIC？

动态库可能被多个进程加载，而每个进程的虚拟地址空间布局并不一定相同。

例如：

```
进程 A：动态库加载到 0x10000000
进程 B：动态库加载到 0x30000000
```

如果动态库内部写死了绝对地址，那么加载到不同位置就可能出问题。

因此需要 PIC（位置无关代码）。

核心思想：

尽可能通过相对地址访问代码和数据，避免依赖固定的绝对地址。

### 3. GOT 和 PLT

这是动态链接中最重要的两个概念。

GOT：Global Offset Table，全局偏移表。

可以把 GOT 理解为一张地址表，保存动态库函数实际地址等信息。

为什么需要它？

动态库加载位置不固定，函数的实际地址也需要在运行时才能确定。

所以不能直接把最终函数地址写死在代码中，而是通过 GOT 间接访问。

PLT：Procedure Linkage Table，过程链接表。

PLT 主要用于实现延迟绑定。

什么叫延迟绑定？

假设一个程序依赖 100 个动态库函数，但实际运行时只调用了其中 10 个。

如果程序启动时就把 100 个函数全部解析完毕，就会产生不必要的开销。

因此可以采用延迟绑定：

- 第一次调用函数：通过 PLT 进入辅助代码，查找真实函数地址，并更新 GOT。
- 第二次调用函数：直接通过 GOT 找到真实函数地址。

## GOT + PLT 工作过程

程序调用外部函数

PLT 入口

GOT 地址表

第一次调用时指向辅助解析代码

动态链接器解析真实地址

查找函数并更新 GOT

以后再次调用：通过 GOT 直接跳转到真实函数

注意区分：

- GOT：存放需要动态解析的地址。
- PLT：提供函数调用的跳转入口，配合 GOT 实现延迟绑定。

### 4. 动态链接的完整过程

把前面的知识串起来：

1. 编译器生成可执行文件，并记录程序依赖的动态库。
2. 运行程序，操作系统根据 ELF 信息加载程序。
3. 动态链接器（例如 Ubuntu 下的 `ld-linux`）参与动态库加载。
4. 动态链接器查找所需的动态库，并将其映射到进程虚拟地址空间。
5. 解析动态库之间的依赖关系。
6. 根据实际加载地址进行动态重定位。
7. 通过 GOT、PLT 完成动态函数调用。

最终，程序就可以正常调用动态库中的函数。

核心结论

动态链接 = 将符号解析和地址重定位推迟到运行时，通过动态链接器完成动态库加载和地址修正。

## 九、本节知识体系总结

把整节课压缩成下面这张知识清单：

| 知识点               | 必须掌握的内容                      |
| ----------------- | ---------------------------- |
| 库                 | 静态库 `.a`、动态库 `.so`           |

| 动态库制作             | `-fPIC`、`-shared`            |

| 静态链接              | 合并、统一编址、重定位                  |
| 虚拟地址              | ELF 预先编址，操作系统建立进程地址空间        |
| 动态链接              | 运行时加载、动态重定位                  |
| PIC               | 位置无关代码                       |
| GOT / PLT         | 地址表、延迟绑定                     |

### 最后，记住这四句话

1. 静态库：编译链接时，把需要的库代码合并进可执行程序。
2. 动态库：程序运行时加载，多个进程可以共享库代码。
3. 静态链接：链接器合并目标文件，通过重定位修正地址。
4. 动态链接：动态链接器在运行时解析符号、加载库并完成动态重定位。

这四句话是本节最核心的知识。

我的学习建议：

本节不需要一开始就钻研 ELF 的每个字段。建议优先掌握三个层次：

- 第一层：动静态库的制作、使用和搜索路径，要求能够独立操作。
- 第二层：ELF、Section、Segment、静态链接，要求能够解释原理。
- 第三层：虚拟地址、PIC、GOT、PLT、动态链接，要求能够串联整个运行过程。

其中，第六节静态链接和第八节动态链接是最值得花时间理解的内容。只要真正理解了它们，整节课的知识就基本串起来了。
