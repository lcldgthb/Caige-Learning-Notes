## 1. 什么是库

- 库 = 写好的、现有的、成熟的、可复用的代码；每个程序都要依赖大量底层库，不可能从零开始
- 本质：库是可执行代码的二进制形式，可以被操作系统载入内存执行
- 两种：静态库（Linux `.a` / Windows `.lib`）、动态库（Linux `.so` / Windows `.dll`）
- 看系统的库：ubuntu 下 `/lib/x86_64-linux-gnu/libc-2.31.so`、`libc.a`、`libstdc++.so.6`（软链接指向 `libstdc++.so.6.0.19`）；Centos 下 `/lib64/libc-2.17.so`、`/lib64/libc.a`
- 【板书强调】库的本质：屏蔽所有实现细节，库文件本质都是源文件对应的 .o！（静态库本质就是打包好的 .o；动态库本质也是目标文件，不需要编译器编码，直接用 gcc/g++ 链接即可）
- 【板书强调】问题：库中需要包含 main 函数吗？——不需要！库是被别人调用的，入口在调用者手里
- 预备工作：把上一节自己封装的 libc 代码拿来当库素材——`my_stdio.h/my_stdio.c`（struct IO_FILE{flag,fileno,outbuffer,cap,size}，mfopen/mfwrite/mfflush/mfclose，刷新策略 FLUSH_NONE/LINE/FULL）、`my_string.h/my_string.c`（my_strlen）

## 2. 静态库

- 定义：程序在编译链接时把库的代码链接（拷贝）进可执行文件，程序运行时不再需要静态库【板书强调：静态库拷贝到可执行文件里，所以运行时删掉库照样跑】
- 编译默认动态链接，只有找不到动态 .so 才采用同名静态库；gcc `-static` 强制静态链接
- 一个可执行程序可能同时用到多个库，有的静态有的动态

### 2-1 静态库生成

- 工具：`ar` 是 gnu 归档工具，`rc` = replace and create
- Makefile：`libmystdio.a: my_stdio.o my_string.o` → `ar -rc $@ $^`；`%.o:%.c` → `gcc -c $<`
- 清理 `clean`、打包 `output`：mkdir stdc/include、stdc/lib，cp 头文件与 .a，`tar -czf stdc.tgz stdc`【板书强调：库发布 = 头文件 + 库文件一起打包，使用者拿到的是两样东西】
- `ar -tv libmystdio.a` 查看库内容（t 列出文件，v 详细信息）：里面就是 `my_stdio.o`、`my_string.o`
- 板书示例：`ar -rc mylibc.a *.o`（replace and create）→ 生成 `libmyc.a`

### 2-2 静态库使用

- main.c 引头文件（`my_stdio.h`、`my_string.h`），调用 `my_strlen`、`mfopen`、`mfwrite`、`mfclose`
- 【板书强调】三个使用场景：
  - 场景 1：头文件和库安装到系统路径 → `gcc main.c -lmystdio`（gcc 默认搜索系统头文件/库路径）
  - 场景 2：头文件和库与源文件同目录 → `gcc main.c -L. -lmystdio`
  - 场景 3：头文件和库有独立路径 → `gcc main.c -I头文件路径 -L库文件路径 -lmystdio`
- 【板书强调】`-L`：指定库路径；`-I`：指定头文件搜索路径；`-l`：指定库名（如果你要链接任何 C/C++ 库，包括第三方的和自己的，都要指明 -I -L）
- 【板书强调】库名规则：去掉前缀 `lib`、去掉后缀 `.a`/`.so`，`libc.so -> c`，即 `-lc`
- 【板书强调】库也要被"安装"到系统中的思想：别人的库最终要么进系统路径，要么每次编译都指路径
- 板书完整命令示例：`gcc usercode.c -I lib/include/ -L lib/mylib/ -lmyc`
- 验证：目标文件生成后删掉静态库，程序照样运行（代码已经拷进去了）

## 3. 动态库

- 定义：程序运行的时候才去链接动态库的代码，多个程序共享使用库的代码
- 可执行文件只包含它用到的函数入口地址表，不含外部函数整个机器码
- 程序运行前，OS 从磁盘把动态库加载到内存的过程叫动态链接（dynamic linking）
- 动态库多程序共享 → 可执行文件更小、省磁盘；虚拟内存机制让物理内存中一份动态库被所有需要的进程共用，省内存

### 3-1 动态库生成

- Makefile：`libmystdio.so: my_stdio.o my_string.o` → `gcc -o $@ $^ -shared`；`%.o:%.c` → `gcc -fPIC -c $<`
- `shared`：生成共享库格式；`fPIC`：产生位置无关码（position independent code）
- 库名规则：`libxxx.so`
- output 打包方式与静态库相同（.h 进 include、.so 进 lib、tar 打包）

### 3-2 动态库使用

- 编译命令三场景与静态库完全相同（`-I`、`-L`、`-l`）
- `ldd libmystdio.so`：查看库或可执行程序的依赖（能看到 libc.so.6、/lib64/ld-linux-x86-64.so.2）
- 编译链接能通过，运行 `./a.out` 报错（见 3-3）

### 3-3 库运行搜索路径

#### 3-3-1 问题

- 【板书强调】现象：`./usercode` → `error while loading shared libraries: libmyc.so: cannot open shared object file: No such file or directory`；`ldd usercode` 显示 `libmyc.so => not found`
- 【板书强调】关键问题：静态库怎么没有这个问题？！——因为静态库代码已经拷贝进可执行文件，运行时根本不需要库；动态库运行时必须真的找到库
- 【板书强调】为什么会找不到：链接时 gcc 被告知了库在哪（-L 只在编译时有效），但运行程序的是 OS——OS 要加载动态库时，按自己的路径规则去找，环境变量 `LD_LIBRARY_PATH` 是系统默认提供的查找位置（`echo $LD_LIBRARY_PATH` 查看）
- 对比：`ldd` 输出里 libc.so.6 能找到（在系统路径），libmyc.so 找不到（在自己目录）

#### 3-3-2 解决方案

- 【板书强调】四种方案：
  1. 拷贝 `.so` 到系统共享库路径：`/usr/lib`、`/usr/local/lib`、`/lib64`
  2. 向系统共享库路径下建立同名软链接
  3. 更改环境变量 `LD_LIBRARY_PATH`（`export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/your/path`，进程内有效）
  4. `ldconfig` 方案：往 `/etc/ld.so.conf.d/` 写配置文件（内容为库路径一行），然后执行 `ldconfig` 重新加载库搜索路径（`ls /etc/ld.so.conf.d/` 看已有配置）
- 板书结论集【板书强调】：
  - 结论 1：gcc/g++ 默认使用动态链接
  - 结论 2：Linux 系统下，默认情况安装的大部分库，都以动态库形式安装
  - 结论 3：库和应用程序的关系是 1 : n（一份库被多个程序使用）
  - 结论 4：gcc 既能形成可执行程序，也能形成动静态库
  - 补充：一旦 `-static`，若系统只有动态库没有静态库，链接失败；可执行程序可以用静态库，对于库本身只能用静态方式

## 5. 目标文件

- Windows 下 IDE 把编译链接封装得很完美，出了链接错误没人会查；Linux 下用 gcc 看全程
- 编译 = 把源代码翻译成 CPU 能直接运行的机器代码
- 示例：hello.c（main 调用 printf 和 run）+ code.c（定义 run），`gcc -c hello.c`、`gcc -c code.c` 各自生成 `.o`
- 目标文件 `.o`：二进制文件，格式是 ELF，是对二进制代码的一种封装
- 修改一个源文件只需单独编译它，不用重编整个工程
- `file hello.o`：`ELF 64-bit LSB relocatable`（可重定位）
- 【板书强调】`.o`/`.obj` 叫可重定位目标文件；编译器把 add.c/sub.c/xxx.c 翻译成 add.o/sub.o/xxx.o，链接器把它们和库组装成可执行程序——编译、链接两个阶段
- 【板书强调】可执行程序、.o 文件都是 ELF 格式的！库也是！以一定的格式融入进二进制文件中

## 6. ELF 文件

- 四种文件都是 ELF：
  - 可重定位文件（Relocatable）= `.o`
  - 可执行文件（Executable）= 可执行程序
  - 共享目标文件（Shared Object）= `.so`
  - 内核转储（core dumps）= 存放进程执行上下文，用于 dump 信号触发
- ELF 组成四部分：
  - ELF 头（ELF header）：描述文件主要特性，位于文件开始，目的是定位文件的其他部分【板书强调】
  - 程序头表（Program header table）：列举所有有效的段（segments）和属性（每段的位置 offset、长度）——段紧密放在二进制文件中，靠段表描述信息才能分割开
  - 节头表（Section header table）：包含对节（sections）的描述
  - 节（Section）：ELF 的基本组成单位，各种信息和数据存在不同节中
- 最常见的节：
  - 代码节 `.text`：机器指令，程序主要执行部分
  - 数据节 `.data`：已初始化的全局变量和局部静态变量
  - `size code` 命令可看 text/data/bss 大小
- 【板书强调】ELF 结构框图：ELF Header → Program Header Table → Section 1/2/.../n → Section Header Table（从上到下的文件布局）
- 【板书强调】`.symtab` 节：Symbol Table 符号表 = 源码里面函数名、变量名和代码的对应关系
- 【板书强调】字符串表：`char lable[] = "helloworld\0func\0lib\0a\0ob\0o"` —— 符号名以 \0 分隔连续存放，符号表里只记偏移量
- 【板书强调】`readelf -h /usr/bin/ls`：Entry point address（如 0x4042d4）= 入口地址！！！程序从哪里开始执行就记录在这里

## 7. ELF 从形成到加载轮廓

### 7-1 ELF 形成可执行

- step-1：多份 C/C++ 源代码翻译成目标 `.o` 文件 + 动静态库（都是 ELF）
- step-2：把多份 `.o` 文件的 section 进行合并
- 注意：合并发生在链接时，还会涉及对库的合并，细节不深究

### 7-2 ELF 可执行文件加载

- ELF 有多种 Section，加载到内存时会进行 Section 合并形成 segment
- 合并原则：相同属性（可读/可写/可执行/是否需要加载时申请空间）
- 合并方式在形成 ELF 时已确定，记录在程序头表中
- 【板书强调】为什么要合并成 segment：减少页面碎片提高内存使用效率（页面 4KB，.text 4097 字节 + .init 512 字节不合并占 3 页，合并后 2 页）；相同属性 section 合并成 segment 后可设置不同访问权限，优化内存管理与权限控制
- `readelf -S a.out` 看 section 清单；`readelf -l a.out` 看 section→segment 合并映射（Segment Sections...）
- 两个视角【板书强调】：
  - 链接视图（linking view）↔ 节头表：粒度细，按功能模块划分，静态链接分析时关注；链接器趁链接把小块合并规整成段，否则很小的 section 未来物理内存页浪费太大（内存按 4K 整数倍分配）
  - 执行视图（execution view）↔ 程序头表：告诉 OS 如何加载可执行文件、完成进程内存初始化；告诉 OS 哪些模块可加载进内存、加载后哪些分段可读可写/只读/可执行
  - 说白了：一个在链接时起作用，一个在运行加载时起作用
- 链接视图常见节：
  - `.text` 代码节；`.data` 初始化全局变量和局部静态变量；`.rodata` 只读数据（字符串常量），只存在于只读段（text 段）中；`.BSS` 未初始化全局变量和局部静态变量预留位置；`.symtab` 符号表；`.got`/`.got.plt` 全局偏移表-过程链接表：对导入共享库函数的访问入口，由动态链接器运行时修改（后面细讲），readelf -S 查看 .so 可见
- 执行视图：Program Headers 里的 LOAD 段才是真正要加载进内存的部分；INTERP 指明程序解释器（动态链接器）`/lib64/ld-linux-x86-64.so.2`
- ELF Header 字段：Magic（魔数 7f 45 4c 46 = \x7fELF）、Class（ELF64）、Data（小端）、Type（REL/DYN/EXEC）、Machine（x86-64）、Entry point address、Start of program/section headers、各表条目大小与数量【板书强调：每个 ELF 区域和文件偏移量之间的关系要理解】
- 注意：目标文件 .o 的 Entry point address 为 0、程序头表数量 0（没有执行视图，不需加载）

## 8. 理解连接与加载

### 8-1 静态链接

- 【板书强调】无论自己的 `.o` 还是静态库中的 `.o`，本质都是 `.o` 文件连接的过程——研究静态链接 = 研究 `.o` 如何链接
- 示例：hello.c + code.c → `gcc -c *.c` → `gcc *.o -o main.exe`
- 【板书强调】`objdump -d` 反汇编看代码段：hello.o 的 main 里 `call` printf 和 run 的跳转地址都是 0！
- 【板书强调】为什么地址是 0：编译 hello.c 时编译器完全不知道 printf 和 run 的存在（在哪个区块、代码长什么样），只能先把跳转地址设为 0 占位
- 【板书强调】地址什么时候修正？——链接的时候！为了让链接器能定位这些待修正地址，`.o` 中存在重定位表，链接时按表里记录的地址进行修正
- 符号表证据【板书强调】：`readelf -s code.o` 中 `puts`（printf 的实现）为 UND（undefined，本 .o 找不到）；`readelf -s hello.o` 中 `run`、`puts` 都是 UND
- 链接后：`readelf -s main.exe` 中 run 有真实地址（如 0000000000001149）、FUNC 类型、所在 section 下标 16（.text）
- 【板书强调】`objdump -d main.exe` 验证：两个 .o 的 .text 合并到一起并统一编址；原来 0 地址的 call 被改成最终函数地址（callq 1149 <run>、callq 1050 <puts@plt>）
- 最终结论：
  1. 两个 .o 的代码段合并到一起，进行统一编址
  2. 链接时修改 .o 中没有确定的函数地址，合并完成后完成代码调用
- 【板书强调】静态链接就是把库中的 .o 进行合并，和上述过程完全一样
- 链接 = 把编译之后的所有目标文件连同用到的静态库组合拼装成一个独立可执行文件；链接器根据重定位表找到需要重定位的函数/全局变量并修正地址——静态链接 = 合并 + 重定位

### 8-2 ELF 加载与进程地址空间

#### 8-2-1 虚拟地址/逻辑地址

- 【板书强调】问题 1：一个 ELF 程序没被加载到内存时，有没有地址？——有地址！平坦模式编址
- ELF 对自己的代码和数据统一编址（平坦模式）：`objdump -S` 反汇编最左侧就是 ELF 的虚拟地址，严格说是逻辑地址（起始地址+偏移量），起始地址认为 0【板书强调：虚拟地址在程序还没加载到内存时就已经统一编址好了】
- 【板书强调】板书推导：如果每个 seg 的开始地址都是 0 呢？——所有可执行程序就是一个 seg，那么所有 seg 内函数、变量的起始偏移量都从 0 开始（32 位 && 64 位皆然）→ 磁盘上可执行程序的代码和数据编址其实就是虚拟地址的统一编址！！！
- 【板书强调】这不仅仅是进程看待内存的方式！——虚拟地址机制，不光 OS 要支持，编译器也要支持
- 问题 2：进程 mm_struct、vm_area_struct 在进程刚创建时的初始化数据从哪来？——从 ELF 各 segment 来：每个 segment 有自己的起始地址和长度，用来初始化内核结构中的 [start, end] 范围数据，再用详细地址填充页表

#### 8-2-2 重新理解进程虚拟地址空间

- ELF 编译好后，把未来程序入口地址记录在 ELF header 的 Entry 字段中（readelf -h 可见，如 0x1060）
- 【板书强调】启动链条（板书画图）：磁盘上可执行程序（Entry point address 0x1060）→ 加载进物理内存 → CPU 里 EIP 指向 0x1060 入口地址、CR3 指向页表 → MMU 通过页表把逻辑/虚拟地址转成物理地址 → 从入口开始执行
- 【板书强调】CPU 怎么知道你的可执行程序起始地址？也就是 CPU 怎么知道从哪里开始执行？——读 ELF Header 的 Entry point，放到 EIP
- 【板书强调】进程地址空间初始化链条：task_struct{pid, files, mm} → mm_struct{mmap} → 一串 struct vm_area_struct{vm_start, vm_end, vm_next} → 每个区域一个 VMA：栈区(VMA_STACK)、文件映射与匿名映射区(VMA_FILE)、堆区(VMA_HEAP)、BSS 段(VMA_BSS)、数据段(VMA_DATA)、代码区(VMA_TEXT)——每个 VMA 对应一个 segment
- 内核空间在最上方；各 vm_area_struct 通过 mmap 与文件关联
- 【板书强调】文件关联链条（库如何被找到）：struct file → struct path{vfsmount, dentry} → struct dentry{d_inode} → struct inode{i_ino, i_block} → 可以找到磁盘文件中的数据块 → 库加载
- 页表映射：页表把虚拟地址映射到物理内存；备注：库内部其实就是文件内容加载（加载到对应区块中）；页表项与物理内存页一一对应
- 板书反汇编片段（可执行程序前几条指令 0x1000/0x1003/0x1010/0x1015）：就是磁盘上 ELF 里的指令被原样加载

### 8-3 动态链接与动态库加载

#### 8-3-1 进程如何看到动态库

- 【板书强调】动态库也是文件，要访问就要先加载，要加载就要先被打开
- 【板书强调】让进程找到动态库的本质也是文件操作，但访问库函数是通过虚拟地址跳转访问的，所以需要把动态库映射到进程的地址空间
- 【板书强调】板书画图：进程 A 的 mm_struct 中有共享区（堆区上方）→ 页表 → 物理内存中的 XXX.so（还有加载箭头：磁盘 XXX.so 库 → 物理内存 XXX.so）→ 通过虚拟地址看到共享库
- 动态库加载后映射进进程地址空间的共享区，进程像访问自己的内存一样访问库

#### 8-3-2 进程间如何共享库的

- 【板书强调】板书画图：进程 A 和进程 B 各有自己的 task_struct、mm_struct、页表，两个进程地址空间中的共享区都映射到物理内存中的同一份 XXX.so【板书强调：动态库中的代码不会出现重复了！共享库！】
- 物理内存中一份库代码 + 各进程一份页表映射；磁盘上只有一份 XXX.so 库
- 这就是虚拟地址空间解耦合收益的落地：物理内存一份，逻辑上每进程各有一份

#### 8-3-3 动态链接

##### 8-3-3-1 概要

- `ldd main.exe`：看到依赖的动态库（linux-vdso.so.1、libc.so.6、/lib64/ld-linux-x86-64.so.2）；libc.so 是 C 运行时库（标准 IO、字符串处理等）
- 【板书强调】为什么编译器默认不静态链接：静态链接把所有目标文件连同库合并成独立可执行文件，体积大、耗内存；不同软件都包含相同功能和代码，浪费大量硬盘空间
- 【板书强调】动态链接优势：需要共享的代码单独提取成独立的动态库，运行时再加载进内存；同一模块内存中只需一份副本被多进程共享，省空间、省内存，还便于库的更新维护
- 【板书强调】核心结论：动态链接实际上把链接的整个过程推迟到了程序加载的时候——运行程序时 OS 先把程序的代码数据和它用的一系列动态库加载进内存，每个动态库的加载地址不固定，OS 根据当前地址空间使用情况动态分配；库的内存地址一旦确定，就可以修正动态库中那些函数跳转地址
- `ldd /usr/bin/ls`：系统命令也依赖一堆动态库（libselinux、libpcre2、libdl、libpthread 等）

##### 8-3-3-2 我们的可执行程序被编译器动了手脚

- 【板书强调】程序入口不是 main！真正入口是 `_start`（由 glibc 或链接器提供）；完整链条：_start → 设置堆栈 → 初始化数据段（已初始化数据复制、未初始化清零）→ 动态链接（调用动态链接器解析加载所有依赖动态库、完成符号解析与重定位）→ 调用 __libc_start_main（设置信号处理、初始化线程库等）→ 调用 main → main 返回后由 __libc_start_main 处理返回值并调 _exit 终止程序
- 动态链接器：ld-linux.so，负责程序运行时加载动态库、解析依赖、重定位
- 搜索路径：环境变量 LD_LIBRARY_PATH + 配置文件 /etc/ld.so.conf 及子配置；缓存文件 /etc/ld.so.cache 包含系统中所有已知动态库路径，动态链接器加载时首先搜索缓存
- 这些 main 之前的操作对程序员透明，但理解底层细节有助于调试

##### 8-3-3-3 动态库中的相对地址

- 【板书强调】动态库为了随时加载、支持映射到任意进程的任意位置，对库中方法统一采用相对编址（起始地址 0 + 偏移量）；可执行程序也一样遵守平坦模式，只不过 exe 是直接加载的
- `objdump -S /lib/x86_64-linux-gnu/libc-2.31.so`（ubuntu）或 `/lib64/libc-2.17.so`（Centos）可看库内相对地址
- 【板书强调】板书示例：库内方法地址理解成 0x123，加载后库起始地址是 0x1000 → 实际访问 = 起始地址 + 偏移量

##### 8-3-3-4 我们的程序，怎么和库具体映射起来的

- 【板书强调】板书画图完整链条：磁盘上的 XXX.so（文件）→ 有加载 → 物理内存中的 XXX.so 的代码和数据 → 进程地址空间：库中的代码和数据被映射进共享区（mm_struct 的 vm_area_struct 之一，vm_start~vm_end）→ 页表把共享区虚拟地址映射到物理内存中库的页
- 【板书强调】找到库文件的链条（同 8-2-2）：struct file → struct path → struct dentry → struct inode{i_ino, i_block} → 找到磁盘文件中的数据块 → 库加载
- 【板书强调】库中方法的偏移量：备注——库内部其实就是文件内容，按文件内容加载到对应区块中；所以库的起始虚拟地址已知、每个方法的偏移量已知

##### 8-3-3-5 我们的程序，怎么进行库函数调用

- 【板书强调】调用公式：访问库中任意方法 = 库的起始虚拟地址 + 方法偏移量
- 【板书强调】整个调用过程：从代码区跳转到共享区，调用完毕返回代码区，完全在进程地址空间内部进行
- 前提：程序运行之前先把所有库加载并映射，所有库的起始虚拟地址都提前知道，然后对加载到内存中的程序的库函数调用进行地址修改——在内存中二次完成地址设置（加载地址重定位）
- 【板书强调】矛盾：修改的是代码区？代码区在进程中不是只读的吗？怎么修改？

##### 8-3-3-6 全局偏移量表 GOT（global offset table）

- 【板书强调】解决矛盾的做法：在 `.data`（可执行程序或库自己的）中专门预留一片区域存放函数跳转地址，叫全局偏移表 GOT；表中每一项都是本运行模块要引用的一个全局变量或函数的地址——.data 可读写，支持动态修改【板书强调：因为代码段只读，不能直接改代码段，所以把要改的地址挪到可写的 .data 中】
- readelf -S 可见 `.got` 节；readelf -l 可见 .got 加载时与 .data 合并成一个 segment 加载在一起
- 【板书强调】四条要点：
  1. 代码段只读不能改，但有了 GOT，代码可被所有进程共享；不同进程地址空间中各动态库的绝对地址、相对位置都不同 → 每个进程的每个动态库都有独立的 GOT 表，进程间不能共享 GOT 表
  2. 单个 .so 下，GOT 表与 .text 的相对位置固定，可以用 CPU 的相对寻址找到 GOT 表
  3. 调用函数时先查表，按表中地址跳转；表中地址在动态库加载时被修改为真正的地址
  4. 这种动态链接方式叫地址无关代码 PIC：动态库不做任何修改，被加载到任意内存地址都能正常运行并被所有进程共享——这就是编译时指定 `-fPIC` 的原因；PIC = 相对编址 + GOT
- 【板书强调】板书画图（GOT 内容示例）：got 表中有 puts(0x112233)(libc.so)、strcopy(0x111111)(libc.so) 等条目，指向中转的 lib.so；加载成功后修改 got 表中 lib.so 的起始地址
- 【板书强调】板书画图（重编址示例）：源代码 call 0x112233（库内相对地址）→ 加载后假设库起始地址 0x443322 → 实际调用 puts(0x112233 + 0x443322)——调用时查 GOT 完成偏移量+起始地址的组合
- `objdump -S a.out` 可见：main 里 `callq 1050 <puts@plt>`——先跳到 PLT 桩代码
- PLT（Procedure Linkage Table，过程链接表）备注：配合 GOT 的中转跳板
- 【板书强调】延迟绑定优化：动态链接在加载时要对大量函数重定位，非常耗时；与其程序一开始就对所有函数重定位，不如推迟到函数第一次被调用时（绝大多数库函数可能一次都不会被用到）；GOT 中的跳转地址默认指向一段辅助代码（桩代码/stub），第一次调用时这段代码负责查询真正函数的跳转地址并更新 GOT 表，再次调用就直接跳转到库中真正的函数实现
- 总：动态链接把符号查询、地址重定位从编译时推迟到运行时，牺牲一定性能和加载时间，但换来了磁盘/内存的高效利用、代码的方便更新维护、二进制级别的代码复用

##### 8-3-3-7 库间依赖（简单说明即可）

- 【板书强调】不仅可执行程序调用库，库也会调用其他库！库和库之间要互相调用也要与地址无关——库中也有 .GOT，和可执行程序一样！这就是为什么大家都是 ELF 格式！
- 解析依赖关系的过程 = 加载并完善互相之间的 GOT 表的过程
- 可用 gdb 调试观察 GOT 表地址变化（选做，知道原理即可）

#### 8-3-4 总结

- 【板书强调】静态链接：提高程序模块化水平，大项目不同人独立开发测试自己的模块，静态链接生成最终可执行文件；链接时修正模块间函数跳转地址——编译重定位（静态重定位）
- 【板书强调】动态链接：链接整个过程推迟到程序加载时；动态库加载地址不固定，但无论加载到哪都映射到进程对应地址空间，通过 .GOT 方式调用——运行重定位（动态地址重定位）
- 对照记忆：静态 = 编译期合并 + 重定位；动态 = 运行期加载 + 映射 + GOT 二次重定位

### 附录2:查看ELF Header

- `readelf -h main`（-h / --file-header）：文件类型、机器类型、版本、入口地址、程序头表和节头表位置与大小

### 附录3:ELF Program Header Table

- `readelf -l main`（-l / --program-headers）：段信息，可执行文件内存布局和加载过程的关键
- Phdr 结构体：p_type、p_flags、p_offset（段在文件偏移）、p_vaddr（段虚拟地址）、p_paddr（物理地址，现代 OS 不考虑）、p_filesz（文件中大小）、p_memsz（内存中大小）、p_align
- LOAD：不是所有 section 都要加载进内存，有 LOAD 标记的才是将来要加载的部分
- INTERP：Requesting program interpreter /lib64/ld-linux-x86-64.so.2

### 附录4:ELF Section Header Table

- `readelf -S main`（-S / --section-headers）：各节的起始地址、大小、标志
- Shdr 结构体：sh_name、sh_type、sh_flags、sh_addr（执行时虚拟地址）、sh_offset（文件偏移）、sh_size、sh_link、sh_info、sh_addralign、sh_entsize
- .got 需要简化讲解（全局偏移表）

### 附录5:查看具体的sections信息

- `objdump -S main`：含源码反汇编；可见 .plt/.plt.got 各桩代码（write@plt、printf@plt、close@plt、__libc_start_main@plt），桩代码 jmpq *GOT 项 实现中转
- `objdump -d hello.o`：目标文件 main 的 call 地址为 0（链接前）
