# 一、理解磁盘：数据究竟存储在哪里？

## 1.1 磁盘的物理结构

首先回忆机械硬盘的基本组成：

[cs4118.github.io](https://cs4118.github.io/www/2023-1/lect/22-hdd-ssd.html?utm_source=chatgpt.com)

| 概念           | 含义                |
| ------------ | ----------------- |
| 盘片（Platter）  | 真正存储数据的圆形盘片       |
| 主轴           | 带动盘片旋转            |
| 磁头（Head）     | 负责读取和写入数据         |
| 传动臂          | 控制磁头移动            |
| 磁道（Track）    | 盘片上的同心圆           |
| 扇区（Sector）   | 磁道划分出的扇形区域        |

重点理解三个概念：磁道、柱面、扇区。

- 磁道：一个盘面上的同心圆。
- 扇区：磁道进一步划分的存储区域。
- 柱面：所有盘面上相同位置的磁道组成的集合。

其中：

- 一个扇区通常为 512 字节。
- 扇区是磁盘读写数据的基本物理单位。
- 传动臂上的多个磁头是同步移动的。

注意：这里沿用课件的传统机械硬盘模型，后续主要用于理解寻址原理。

## 1.2 CHS 寻址：通过物理位置定位数据

既然磁盘由磁道、磁头和扇区组成，那么如何找到一个扇区？

自然可以通过三个参数：

- C（Cylinder）：柱面号。
- H（Head）：磁头号。
- S（Sector）：扇区号。

这就是 CHS 寻址方式。

[CHS](https://images.openai.com/static-rsc-4/w-hsJRNM_pSXZJQ2T33XRK_B97vO-TS-UyGsEOIvOIA1x-yKE06WkPHqO60LVRjOUV3Y0pjGr--n6zbJ9dtu3UjwwkU-gF4Uca23igFoTjCRURIunzOrasUVku9NkLSruGZ6nP56J-VOHokCQUVfezKM2isdMxMVuMmAbALkeN8?purpose=inline)

[blocksandfiles.com](https://www.blocksandfiles.com/glossary/2022/04/20/chs/1614178?utm_source=chatgpt.com)

例如：

```
CHS = (2, 1, 5)
```

表示：

1. 找到 2 号柱面。
2. 选择 1 号磁头。
3. 读取该磁道上的 5 号扇区。

这样就能确定一个扇区的位置。

为什么后来不再直接使用 CHS？

因为 CHS 的地址空间有限。

课件给出的传统 CHS 地址位数：

| 参数   | 位数     | 可表示数量           |
| ---- | ------ | --------------- |
| 磁头 H | 8 bit  | 256             |
| 柱面 C | 10 bit | 1024            |
| 扇区 S | 6 bit  | 63（实际采用的最大扇区编号） |

最大寻址容量：

\\[ 256\times1024\times63\times512B \\]

约为 8.4GB（十进制）。

因此，CHS 不适合现代大容量磁盘的寻址需求。

## 1.3 LBA 寻址：把磁盘看成一维数组

这是本节非常重要的一个知识点。

回忆 C/C++ 数组：

```
int arr[5] = {10, 20, 30, 40, 50};
// 通过下标访问元素
cout << arr[2] << endl;
```

虽然数组在物理内存中有具体的存储位置，但程序员通常不需要关心具体的物理位置，只需要使用下标。

磁盘也可以采用类似的思想。

把整个磁盘看成一个巨大的、以扇区为元素的一维数组。

[Hidden Files | C64 OS](https://images.openai.com/static-rsc-4/wMJAO5n_dy50UgJtUjVgBvFU42jwEJXD64WZz6hg6eUqg4_28MURi99xwnWIIseBPEQxT9uAQ8WLx1TzxaacRXG5S5oWKuLrEfDnqxJWUngsXvNksKTQytuUHFu75zZ2izKWzCzpStRkFiGxAVwdHIKHlP5XvRoux_EiBH04vkk?purpose=inline)

[c64os.com](https://www.c64os.com/post/hiddenfiles?utm_source=chatgpt.com)

每个扇区对应一个唯一的线性地址，这就是：

LBA（Logical Block Address，逻辑块地址）。

例如：

| LBA | 对应扇区  |
| --- | ----- |
| 0   | 第一个扇区 |
| 1   | 第二个扇区 |
| 2   | 第三个扇区 |
| 3   | 第四个扇区 |
| ... | ...   |

这样，操作系统只需要告诉磁盘：

```
读取 LBA = 1000 的扇区
```

就可以定位数据。

那么问题来了：

磁盘物理上还是由柱面、磁头、扇区组成的，LBA 如何找到实际物理位置？

答案是：磁盘内部的固件负责地址转换，操作系统不需要直接处理 CHS。

### CHS 和 LBA 的转换

这部分保留公式，理解每个公式的来源即可。

设：

- C：柱面号。
- H：磁头号。
- S：扇区号。
- 磁头数：一个柱面包含的磁道数。
- 每磁道扇区数：每条磁道拥有的扇区数。

一个柱面的扇区总数：

\\[ 柱面扇区数=磁头数\times每磁道扇区数 \\]

CHS 转 LBA：

\\[ \boxed{LBA=C\times(H数\times S数)+H\times S数+S-1} \\]

注意：公式中的 H数、S数表示总数量，而 H、S 表示当前编号。

为什么最后要减 1？

因为：

- 柱面号从 0 开始。
- 磁头号从 0 开始。
- 扇区号从 1 开始。
- LBA 从 0 开始。

所以扇区号需要减 1。

LBA 转 CHS：

\\[ C=LBA//(H数\times S数) \\]

\\[ H=(LBA\\%(H数\times S数))//S数 \\]

\\[ S=(LBA\\%S数)+1 \\]

其中 `//` 表示整除，`%` 表示取余。

用一个例子理解转换

假设磁盘有 4 个磁头，每条磁道有 8 个扇区，给定：

\\[ CHS=(2,1,3) \\]

那么：

\\[ LBA=2\times(4\times8)+1\times8+3-1 \\]

\\[ =64+8+2=\boxed{74} \\]

即 CHS 地址 `(2,1,3)` 对应 LBA 地址 `74`。

本节结论

从操作系统的角度看，磁盘就是一个以扇区为元素的一维数组，LBA 就是数组下标。

## 1.4 Block：为什么还需要块？

现在我们已经可以通过 LBA 定位一个扇区了。

但是操作系统如果每次读写文件，都只读取一个 512B 的扇区，效率会比较低。

因此引入了一个更高层次的概念：Block（块）。

课件给出的典型配置：

- 一个扇区：512B。
- 一个 Block：4KB。
- 一个 Block：连续 8 个扇区。

[브런치](https://images.openai.com/static-rsc-4/1_WqgJyXN33CbZWhIRC8BggJwmn73rpMJ2-ak2PbU4Smbu2Rcm_AkbvIDShlYs_mc92jk-xdGw_r8Jek07fC-PKcGeCyiHYVCk6_RxOHLfDmyz07-kAKJAtCAFh3xHYtLv2z-vTKJdbojHClAVNbqdYxq3pdIPsAyPKaKcybU24?purpose=inline)

[brunch.co.kr](https://brunch.co.kr/%40jyoo212/8?utm_source=chatgpt.com)

两者区别：

| 比较 | Sector   | Block     |
| -- | -------- | --------- |
| 层次 | 磁盘物理层    | 文件系统层     |
| 大小 | 通常 512B  | 课件示例为 4KB |
| 组成 | 基本物理存储单位 | 多个连续扇区    |
| 用途 | 磁盘寻址     | 文件存储与管理   |

假设一个 Block 包含 8 个扇区：

LBA 与 Block 号转换：

\\[ Block号=LBA/8 \\]

\\[ LBA=Block号\times8+n \\]

其中 n 是块内扇区的偏移量，从 0 开始。

例如：

```
Block 10
对应 LBA：80 ~ 87
```

所以 LBA 83 对应 Block 10 中的第 4 个扇区（偏移量为 3）。

容易混淆

- LBA：定位扇区。
- Block：文件系统管理数据的基本单位。
- Block 号：定位文件系统中的数据块。

不要把扇区和块混为一谈。

## 1.5 分区：一块磁盘为什么可以划分成多个区域？

一块物理磁盘可以划分成多个分区。

例如 Windows 中的 C、D、E 盘，本质上就是对磁盘空间进行划分。

在课件介绍的传统磁盘模型中：

柱面是分区的最小单位。

分区可以通过起始柱面和结束柱面来描述。

但是，分区本身还不能直接按照文件系统的规则存储文件。

# 二、inode：Linux 如何管理文件？

## 2.1 重新理解文件 = 内容 + 属性

我们之前学习 Linux 基础 IO 时，已经接触过一个重要观点：

文件不仅有内容，还有属性。

例如：

```
ls -l
```

可能看到：

```
-rw-r--r-- 1 caige caige 1024 Nov 6 14:00 test.c
```

这里展示了文件的权限、硬链接数、所有者、所属组、大小、修改时间和文件名等信息。

这些信息属于文件的属性。

再使用：

```
stat test.c
```

可以看到更加详细的文件元信息，其中就有：

```
Inode: 263715
Links: 1
Size: 1024
```

那么问题来了：

文件内容存储在 Data Block 中，文件属性应该存储在哪里？

答案就是：

inode（Index Node，索引节点）。

## 2.2 inode 的核心作用

Linux 文件系统采用一种重要的设计：

inode

文件属性

权限、所有者

文件大小

时间信息

数据块指针

Data Block

文件内容

实际存储的数据

代码、文本

图片、视频

文件名不存储在 inode 中！

inode 主要负责保存：

- 文件类型与权限。
- 文件所有者和所属组。
- 文件大小。
- 文件访问、修改等时间。
- 硬链接数量。
- 文件数据块的位置。

课件给出的 inode 大小通常为 128 字节或 256 字节。

这里需要记住一个重要特点：

同一个文件系统中，每个 inode 的结构大小相同，但不同文件的内容大小可以不同。

另外：

- 一个文件对应一个 inode。
- 每个 inode 有自己的 inode 号。
- 文件名不属于 inode 的属性结构。

## 2.3 inode 如何找到文件内容？

这是 inode 最重要的底层设计。

课件给出了 Ext2 的 inode 结构，其中有一个关键成员：

```
#define EXT2_NDIR_BLOCKS 12
#define EXT2_IND_BLOCK  EXT2_NDIR_BLOCKS
#define EXT2_DIND_BLOCK (EXT2_IND_BLOCK + 1)
#define EXT2_TIND_BLOCK (EXT2_DIND_BLOCK + 1)
#define EXT2_N_BLOCKS   (EXT2_TIND_BLOCK + 1)
```

inode 中有：

```
__le32 i_block[EXT2_N_BLOCKS];
```

也就是说：

inode 内部保存了指向文件数据块的指针。

总共 15 个指针：

[聊聊ext系列文件系统-腾讯云开发者社区-腾讯云](https://images.openai.com/static-rsc-4/ukAVt6B4cnw6oOhLMk2ocCyZL3Fm-l7y9tDTphXTLcYj5vMX4DqKi-X0ja45dVqSVYVClJLnwar3b8nSzp0vvtBvCLJQO0dhsvfAxIQcDAlrGPeD0ynSxg5wJ2lcV760L1yNtDrrlDrjsE-qPDhbcdk8b_ehRgwzre_WmwhSzHo?purpose=inline)

[cloud.tencent.com](https://cloud.tencent.com/developer/article/2074590?utm_source=chatgpt.com)

| 索引                 | 类型    | 作用            |
| ------------------ | ----- | ------------- |
| i_block[0] \~ [11] | 直接块   | 直接指向数据块       |
| i_block[12]        | 一级间接块 | 指向一个存储数据块地址的块 |
| i_block[13]        | 二级间接块 | 通过两级指针找到数据块   |
| i_block[14]        | 三级间接块 | 通过三级指针找到数据块   |

为什么需要直接、一级、二级、三级间接块？

因为 inode 本身空间有限，如果所有数据块地址都直接放在 inode 中，那么能够管理的文件大小就会受到限制。

通过多级间接索引，可以管理更多的数据块。

这里课件标注为弱化内容，复习时重点掌握：

inode 不仅存储文件属性，还通过 i_block 记录文件内容所在的数据块位置。

至此，我们已经解决了两个问题：

1. 文件属性在哪里？inode。
2. 文件内容在哪里？Data Block。

但是，还有一个问题：

我们平时访问文件使用的是文件名，为什么现在讨论的全是 inode 号？

这就引出了目录文件。

# 三、Ext2 文件系统：如何组织整个分区？

## 3.1 为什么需要文件系统？

先回顾一下目前已经知道的知识：

- 磁盘由扇区组成，可以通过 LBA 定位。
- 文件系统以 Block 为单位管理数据。
- 文件属性保存在 inode 中。
- 文件内容保存在 Data Block 中。

但是，现在又出现两个问题：

1. 一个分区中有大量 Block，如何知道哪些 Block 已经使用，哪些还空闲？
2. inode 存储在哪里？如何快速找到某个文件的 inode？

文件系统就是为了解决这些问题而设计的。

课件以 Ext2 为例，介绍 Linux 文件系统的组织方式。Ext3、Ext4 都是在 Ext2 基础上发展而来的，核心组织思想有延续。

## 3.2 Ext2 的整体结构

Ext2 将一个分区划分成多个大小相同的 Block Group（块组）。

课件中的结构：

```
整个分区
│

│
```

## 3.3 Block Group 内部结构

这是本节最重要的结构图之一。

[ext Linux Filesystem | Dhananjay's Blog](https://images.openai.com/static-rsc-4/fDVJUF5RfnDaJxij8tyFNYpovNmdr13TERalJejKYX_JQf8BH6KDBBM-RCc26O2K0k7dVAPjpMTa5IEQ5HujN_DfAFaQz1FAEbAABvb5pBHRumzg5zrxkZ0en-Ke8m-suLFguRXROF7qToCSLAsM_J-Qp-o5_vnZ2JiKstIvHco?purpose=inline)

[dhananjaylatkar.github.io](https://dhananjaylatkar.github.io/posts/ext-linux-filesystem/?utm_source=chatgpt.com)

每个 Block Group 主要包含六个部分：

1. Super Block（超级块）
2. GDT（块组描述符表）
3. Block Bitmap（块位图）
4. Inode Bitmap（inode 位图）
5. Inode Table（inode 表）
6. Data Block（数据区）

下面逐个理解它们的作用。

### ① Super Block：超级块

超级块保存的是整个文件系统的整体信息。

主要包括：

- Block 总量。
- inode 总量。
- 空闲 Block 数量。
- 空闲 inode 数量。
- Block 大小。
- inode 大小。
- 文件系统挂载时间。
- 最近写入时间。
- 文件系统状态等。

可以把它理解成整个文件系统的总账本。

为什么重要？

因为操作系统需要通过超级块了解整个文件系统的基本情况。

如果超级块损坏，文件系统就可能无法正确识别和管理。

为了提高可靠性，Ext2 会在多个块组中保存超级块的备份（并非每个块组都一定有）。



重点

&#x20;超级块描述的是整个文件系统，而不是仅仅描述当前块组。



### ② GDT：Group Descriptor Table

GDT 是块组描述符表。

既然一个分区被划分成多个 Block Group，那么就需要记录每个块组的具体情况。

GDT 中的每个描述符对应一个 Block Group。

它主要记录：

- 当前块组的 Block Bitmap 在哪里。
- 当前块组的 Inode Bitmap 在哪里。
- 当前块组的 Inode Table 在哪里。
- 当前块组还剩多少空闲 Block。
- 当前块组还剩多少空闲 inode。

可以把它理解为：

Super Block 管整个分区，GDT 管理和描述各个 Block Group。

课件中还提到，GDT 也有备份。

### ③ Block Bitmap：数据块位图

它的作用非常直接：

记录当前块组中哪些 Data Block 已经被使用，哪些还没有被使用。

例如：

```
Block Bitmap：

Block 0  → 1（已使用）
Block 1  → 0（空闲）
Block 2  → 1（已使用）
Block 3  → 0（空闲）
Block 4  → 1（已使用）
```

每一个 bit 对应一个数据块。

当创建文件，需要分配数据块时，文件系统就可以通过 Block Bitmap 寻找空闲位置。

### ④ Inode Bitmap：inode 位图

原理和 Block Bitmap 一样。

区别是：

- Block Bitmap：管理 Data Block。
- Inode Bitmap：管理 inode。

每一个 bit 表示一个 inode 是否空闲可用。

例如：

```
Inode Bitmap：

inode 0 → 1（已使用）
inode 1 → 1（已使用）
inode 2 → 0（空闲）
inode 3 → 1（已使用）
```

创建新文件时，需要先找到空闲 inode。

### ⑤ Inode Table：inode 表

它保存当前块组中所有 inode 的属性信息。

例如：

```
Inode Table
│
├── inode 100
├── inode 101
├── inode 102
├── inode 103
└── ...
```

每个 inode 保存对应文件的属性，以及指向数据块的指针。

这里要记住一个重要限制：

inode 编号以文件系统（分区）为单位管理，不能跨文件系统直接定位。

### ⑥ Data Block：数据区

真正存储文件内容的地方。

这里有一个容易忽略的知识点：

目录也是文件。

因此 Data Block 不仅可以保存普通文件内容，也可以保存目录内容。

- 普通文件：Data Block 保存实际文件内容。
- 目录文件：Data Block 保存目录项，即文件名与 inode 号之间的映射关系。

例如：

```
当前目录的数据块：

test.c  → inode 100
main.c  → inode 101
linux   → inode 102
```

注意：文件名保存在目录的数据块中，而文件的其他属性保存在对应 inode 中。

## 3.4 六大结构之间的关系

把刚才的内容放在一起：

| 组成部分         | 核心作用       | 解决的问题          |
| ------------ | ---------- | -------------- |
| Super Block  | 保存文件系统整体信息 | 整个分区有多大、还剩多少空间 |
| GDT          | 描述各个块组     | 块组中的管理结构在哪里    |
| Block Bitmap | 管理数据块      | 哪些数据块空闲        |
| Inode Bitmap | 管理 inode   | 哪些 inode 空闲    |
| Inode Table  | 保存 inode   | 文件属性在哪里        |
| Data Block   | 保存实际数据     | 文件内容在哪里        |

可以用一句话记忆：

超级块看全局，GDT 找管理结构，位图找空闲资源，inode 表存属性，Data Block 存内容。

## 3.5 格式化究竟做了什么？

现在可以回答之前留下的问题了。

假设我们有一个刚刚分区的磁盘区域。

此时它只是一块可以存储数据的空间，还没有建立完整的文件系统组织结构。

执行格式化：

```
# 将分区格式化为 ext4 文件系统
sudo mkfs.ext4 /dev/sdb1
```

其核心工作就是：

在分区中建立文件系统需要的管理结构。

例如：

- 建立 Super Block。
- 建立 GDT。
- 建立 Block Bitmap。
- 建立 Inode Bitmap。
- 建立 Inode Table。
- 组织 Data Block。

这样，原本没有文件系统结构的分区，就具备了管理文件的能力。

分区与格式化的区别

分区（Partition）

将一块磁盘空间划分为多个独立区域。

格式化（Formatting）

在指定分区中建立文件系统的组织结构。

文件系统

可以按照 inode、Block 等规则管理文件。

# 四、目录与路径解析：为什么知道文件名还不够？

## 4.1 目录本质上也是文件

我们平时使用：

```
ls
```

看到的是当前目录中的文件和子目录。

但从文件系统的角度看：

目录也是一个普通的文件类型，它同样有自己的 inode 和 Data Block。

区别在于：

- 普通文件的 Data Block 保存文件内容。
- 目录文件的 Data Block 保存文件名与 inode 号的对应关系。

例如：

目录文件：/home/caige

目录自己的 inode

保存目录权限、所有者、大小等属性

指向目录数据块

目录 Data Block

| 文件名    | inode 号 |
| ------ | ------- |
| test.c | 100     |
| main.c | 101     |
| linux  | 102     |

这就解释了为什么 inode 中不需要保存文件名。

文件名与 inode 号的映射关系由目录负责维护。

课件提供了 `readdir()` 示例，可以直接读取目录中的目录项：

```
#include <stdio.h>
#include <stdlib.h>
#include <dirent.h>
#include <string.h>
int main(int argc, char *argv[]) {
    // 检查命令行参数
    if (argc != 2) {
        fprintf(stderr, "Usage: %s <directory>\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    // 打开指定目录
    DIR *dir = opendir(argv[1]);
    if (dir == NULL) {
        perror("opendir");
        exit(EXIT_FAILURE);
    }
    struct dirent *entry;
    // 逐个读取目录项
    while ((entry = readdir(dir)) != NULL) {
        // 跳过当前目录和上级目录
        if (strcmp(entry->d_name, ".") == 0 || strcmp(entry->d_name, "..") == 0) {
            continue;
        }
        // 输出文件名和对应的 inode 号
        printf("Filename: %s, Inode: %lu\n", entry->d_name, (unsigned long)entry->d_ino);
    }
    // 关闭目录
    closedir(dir);
    return 0;
}
```

这段程序最重要的是：

```
entry->d_name
entry->d_ino
```

前者是文件名，后者是目录项记录的 inode 号。

这也从实际编程角度验证了目录保存文件名与 inode 之间的对应关系。

## 4.2 为什么访问文件必须通过路径？

现在假设你要访问：

```
/home/caige/test.c
```

我们知道：

```
test.c → inode → 文件内容
```

但是问题来了：

系统最开始并不知道 test.c 的 inode 号，怎么办？

答案是：从目录中查找。

要找到 `test.c`，首先需要找到它所在的目录 `/home/caige`，然后在这个目录中找到 `test.c` 对应的 inode。

但 `/home/caige` 本身也是一个目录文件，它也需要 inode。

那么它的 inode 又从哪里来？

继续向上查找：

```
/
└── home
    └── caige
        └── test.c
```

最终找到根目录 `/`。

根目录是整个 Linux 文件系统路径解析的起点。

## 4.3 Linux 路径解析过程

这就是课件所说的 Path Resolution（路径解析）。

假设我们访问：

```
/home/caige/code/test.c
```

内核需要依次完成：

① 根目录 `/`

找到根目录 inode。

在根目录中查找 home

② home 目录

获得 home 对应的 inode。

在 home 中查找 caige

③ caige 目录

获得 caige 对应的 inode。

在 caige 中查找 code

④ code 目录

获得 code 对应的 inode。

在 code 中查找 test.c

⑤ test.c

找到目标文件的 inode，进而找到文件数据。

因此：

访问文件，本质上就是沿着目录结构逐级查找 inode 的过程。

## 4.4 进程为什么需要 CWD？

课件在这里引出了一个很重要的概念：

CWD（Current Working Directory），当前工作目录。

之前我们学习 Linux 进程时，已经知道每个进程都有自己的工作目录。

例如：

```
# 查看当前工作目录
pwd
# 切换工作目录
cd /home/caige
```

进程访问文件时，可以提供绝对路径，也可以提供相对路径。

- 绝对路径：从根目录 `/` 开始解析。
- 相对路径：从进程当前工作目录 CWD 开始解析。

例如：

```
# 绝对路径
cat /home/caige/test.c
# 相对路径（假设 CWD 是 /home/caige）
cat test.c
```

这就解释了为什么进程需要保存当前工作目录。

CWD 不仅影响 `pwd` 的结果，也决定了相对路径从哪里开始解析。

另外，课件强调：

Linux 的路径结构是由系统和用户共同构建的。根目录及其下的系统目录构成初始路径体系，用户也可以继续创建目录和文件。

# 五、路径缓存：struct dentry

## 5.1 每次访问文件都从根目录开始吗？

前面我们讲过，访问文件需要进行路径解析。

例如：

```
/home/caige/code/test.c
```

理论上需要从 `/` 开始，依次查找每一级目录。

但如果每次访问文件都要重新读取磁盘上的目录数据，效率会很低。

因此，Linux 引入了路径缓存机制。

核心思想：把已经访问过的路径结构缓存在内存中，后续访问时优先查找缓存。

## 5.2 struct dentry：目录项缓存

Linux 内核使用 `struct dentry` 维护路径相关的信息。

课件给出的结构体中，重点关注以下成员：

```
struct dentry {
    // 当前目录项对应的 inode
    struct inode *d_inode;
    // 当前目录项的父目录
    struct dentry *d_parent;
    // 当前目录项的名称
    struct qstr d_name;
    // 当前目录项的子目录链表
    struct list_head d_subdirs;
    // 当前目录项所属的超级块
    struct super_block *d_sb;
};
```

这里不需要记忆完整结构体，重点理解三个关系：

- `d_name`：当前节点叫什么。
- `d_parent`：当前节点的父节点是谁。
- `d_inode`：当前节点对应哪个 inode。

通过这些结构，内核可以在内存中维护类似下面的树状结构：

```
/
└── home
    └── caige
        └── code
            └── test.c
```

## 5.3 dentry 的作用

课件强调了三个方面：

| 机制   | 作用          |
| ---- | ----------- |
| 树形结构 | 维护目录之间的父子关系 |
| Hash | 方便快速查找目录项   |
| LRU  | 管理缓存节点的淘汰   |

整个过程可以理解为：

```
访问文件
   ↓
根据路径查找 dentry 缓存
   ↓
找到？
   ├── 是：利用缓存中的信息继续访问
   └── 否：从文件系统中查找相应信息
             ↓
          建立新的 dentry
             ↓
          加入缓存
```

重点区分

inode 和 dentry 不是同一个东西。

| 对比    | inode           | dentry           |
| ----- | --------------- | ---------------- |
| 主要用途  | 描述文件属性          | 维护路径与目录项关系       |
| 存储位置  | 文件系统中有磁盘结构      | 内核内存缓存结构         |
| 主要内容  | 权限、大小、时间、数据块指针等 | 名称、父节点、inode 引用等 |
| 解决的问题 | 文件是什么、数据在哪里     | 如何通过路径找到文件       |

特别注意：

inode 是文件系统中的核心文件元数据结构，dentry 是 VFS 在内存中用于路径管理和缓存的结构。

另外，一个 inode 可能被多个 dentry 引用，这一点在理解硬链接时尤其重要。

# 六、挂载：多个分区如何组成一个 Linux 文件系统？

## 6.1 为什么需要挂载？

现在我们已经知道：

- 一个分区有自己的文件系统。
- 一个文件系统有自己的 inode 和 Data Block。
- inode 编号只能在对应文件系统中定位。

那么问题来了：

Linux 可以有多个分区，不同分区中的 inode 又不能混在一起，系统如何统一访问这些文件？

答案就是：挂载（Mount）。

挂载的核心作用：

将一个已经具有文件系统的分区，关联到 Linux 目录树中的某个目录。

例如：

```
/dev/sda1  →  /
/dev/sdb1  →  /mnt/data
```

这样，访问 `/mnt/data` 下的文件，实际上就会进入第二个文件系统。

## 6.2 通过实验理解挂载

课件提供了一个非常好的实验：使用普通文件模拟磁盘。

先创建一个 5MB 的文件：

```
# 创建一个 5MB 的空文件，使用零填充
dd if=/dev/zero of=./disk.img bs=1M count=5
```

然后格式化：

```
# 将文件格式化为 ext4 文件系统
mkfs.ext4 disk.img
```

创建一个空目录：

```
# 创建挂载点
mkdir /mnt/mydisk
```

执行挂载：

```
# 将 disk.img 对应的文件系统挂载到指定目录
sudo mount -t ext4 ./disk.img /mnt/mydisk/
```

查看当前文件系统：

```
# 查看已经挂载的文件系统及容量
df -h
```

这时会看到类似：

```
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        50G   20G   28G  42% /
/dev/loop0      4.9M   24K  4.5M   1% /mnt/mydisk
```

这里出现了一个新的设备：

`/dev/loop0`。

## 6.3 Loop Device：循环设备

正常情况下，块设备通常对应磁盘、分区等硬件存储设备。

但是 Linux 允许把一个普通文件当作块设备使用，这就需要 Loop Device（循环设备）。

例如：

```
disk.img
   ↓
Loop Device
   ↓
/dev/loop0
   ↓
mount
   ↓
/mnt/mydisk
```

所以，我们虽然没有真正创建一块新硬盘，却可以通过普通文件模拟一个磁盘分区，并在上面建立文件系统。

卸载：

```
# 卸载挂载点
sudo umount /mnt/mydisk
```

核心结论

分区写入文件系统之后，还需要通过挂载将它关联到目录树，才能通过正常的 Linux 路径访问。

## 6.4 如何判断文件属于哪个分区？

课件给出的理解方式是：

根据访问目标文件的路径前缀，判断它属于哪个挂载点对应的文件系统。

例如：

```
/dev/sda1 → /
/dev/sdb1 → /mnt/data
```

那么：

| 文件路径                 | 所属文件系统      |
| -------------------- | ----------- |
| `/home/caige/test.c` | `/dev/sda1` |
| `/etc/passwd`        | `/dev/sda1` |
| `/mnt/data/a.txt`    | `/dev/sdb1` |

这也解释了为什么不同分区可以存在相同的 inode 号。

因为 inode 号必须结合所属文件系统才能确定具体文件。

# 七、软硬链接：多个文件名如何对应同一个文件？

这是本节最后一个重点。

前面我们已经知道：

```
文件名 → inode → Data Block
```

那么，如果两个文件名指向同一个 inode，会发生什么？

这就是硬链接。

## 7.1 硬链接（Hard Link）

先创建一个文件：

```
# 创建文件 abc
touch abc
# 查看 inode 号
ls -i abc
```

然后创建硬链接：

```
# 创建 abc 的硬链接 def
ln abc def
# 查看两个文件的 inode 号
ls -li abc def
```

可能得到：

```
263466 abc
263466 def
```

注意：

abc 和 def 的 inode 号完全相同。

这说明它们不是两个独立的文件内容，而是两个文件名对应同一个 inode。

[Inode in the Linux file system - SoByte](https://images.openai.com/static-rsc-4/RUNzYyA6XyIhjjEswd5kmHNbMYmwzzU2votAu5_s0rtTbktYZaTAW1WfkX2y6N-1SgkIym8ZBX_l5QyxXjw9wOaAx_Eyn_n9LxrBL_FoU8O5fWBceRC__cqgbGtn62l9gfLfw7tbLNL5Ef7njd04Frl2mbRXUGk1zsijCjqzUNw?purpose=inline)

[sobyte.net](https://www.sobyte.net/post/2022-08/linux-inode/?utm_source=chatgpt.com)

可以这样理解：

```
abc ──┐
      ├── inode 263466 ── Data Block
def ──┘
```

### 删除硬链接会发生什么？

假设：

```
abc ──┐
      ├── inode 263466
def ──┘
```

执行：

```
# 删除 abc 这个目录项
rm abc
```

实际上主要发生两件事：

1. 从目录中删除 `abc` 对应的目录项。
2. inode 的硬链接计数减 1。

此时：

```
def → inode 263466 → Data Block
```

文件仍然可以通过 `def` 正常访问。

只有当硬链接计数变为 0，并且没有其他引用等阻止释放的条件时，文件系统才可以回收对应的 inode 和数据块。

所以删除文件名，不等于立即删除文件内容。

### 硬链接的特点

- 多个文件名对应同一个 inode。
- 硬链接之间没有主从关系。
- 删除其中一个名字，不影响其他名字。
- 不能跨文件系统创建硬链接。

课件还提到：

`.` 和 `..` 也是硬链接相关的典型例子。

## 7.2 软链接（Symbolic Link）

软链接的本质与硬链接完全不同。

创建方式：

```
# 创建 abc 的软链接 abc.s
ln -s abc abc.s
# 查看文件及链接关系
ls -li
```

例如：

```
263563 -rw-r--r-- 2 root root 0 abc
263563 -rw-r--r-- 2 root root 0 def
261678 lrwxrwxrwx 1 root root 3 abc.s -> abc
```

注意观察：

- abc 和 def 的 inode 相同。
- abc.s 的 inode 不同。
- abc.s 的类型是符号链接。
- abc.s 的内容记录目标路径 `abc`。

[thenodebook.com](https://www.thenodebook.com/file-system/permissions-metadata-edge-cases?utm_source=chatgpt.com)

可以这样理解：

```
abc.s
 │
 └── 保存目标路径 "abc"
                │
                ↓
               abc
                │
                ↓
              inode
                │
                ↓

```

软链接本身是一个独立文件。

当访问软链接时，系统会根据软链接中保存的目标路径继续解析。

### 软链接的特点

- 软链接是独立文件。
- 软链接有自己的 inode。
- 软链接保存的是目标路径。
- 可以跨文件系统。
- 如果目标文件被删除，软链接可能变成悬空链接。

## 7.3 软硬链接对比

| 对比      | 硬链接            | 软链接          |
| ------- | -------------- | ------------ |
| 本质      | 文件名与 inode 的映射 | 独立的链接文件      |
| inode   | 与目标文件相同        | 自己拥有独立 inode |
| 保存内容    | 不保存目标路径        | 保存目标路径       |
| 删除目标文件名 | 其他硬链接仍可访问      | 可能变成悬空链接     |
| 跨文件系统   | 不可以            | 可以           |
| 主要用途    | 多个名字访问同一文件     | 类似快捷方式       |

### 7.4 软硬链接的用途

硬链接：

- 多个文件名访问同一份文件数据。
- 课件提到的文件备份用途。
- `.` 和 `..` 的目录链接关系。

软链接：

- 类似 Windows 快捷方式。
- 可以为文件或目录建立一个方便访问的路径。
- 可以跨文件系统引用目标。

## 7.5 顺便回顾文件的三个时间

课件最后还补充了文件的三个时间：

| 时间            | 含义         |
| ------------- | ---------- |
| Access（atime） | 最后访问时间     |
| Modify（mtime） | 文件内容最后修改时间 |
| Change（ctime） | 文件属性最后修改时间 |

注意：ctime 不是文件创建时间，而是 inode 状态或属性最后一次发生变化的时间。

例如：

- 读取文件：可能更新 atime。
- 修改文件内容：更新 mtime，通常也会更新 ctime。
- 修改文件权限：更新 ctime。

## 8.2 必须记住的四组关系

第一组：磁盘寻址

```
磁盘
  ↓
扇区（Sector）
  ↓
LBA 地址定位扇区
  ↓
多个扇区组成 Block
  ↓
文件系统以 Block 管理数据
```

第二组：文件存储

```
文件
 ├── 属性 → inode
 │           └── i_block → Data Block
 │
 └── 内容 → Data Block
```

第三组：文件访问

```
路径
 ↓
目录
 ↓
文件名 → inode 号
 ↓
inode
 ↓
Data Block
 ↓
文件内容
```

第四组：文件系统组织

```
分区
 ↓
格式化
 ↓
文件系统
 ↓
Block Group
 ├── Super Block
 ├── GDT
 ├── Block Bitmap
 ├── Inode Bitmap
 ├── Inode Table
 └── Data Block
```

## 8.3 本节最重要的结论

我认为这节课真正需要建立的是下面五个认识：

1. 磁盘是如何被访问的？ 通过 LBA 将磁盘抽象成线性扇区数组，再通过 Block 进行文件系统层面的管理。
2. 文件是如何存储的？ 属性和内容分离，inode 保存属性，Data Block 保存内容。
3. 文件系统如何管理空间？ 通过 Block Group、位图、inode 表等结构组织和管理整个分区。
4. 文件名如何找到文件？ 目录保存文件名与 inode 的映射，内核通过路径解析逐级找到目标文件。
5. 多个分区如何统一访问？ 通过挂载将不同文件系统接入同一棵目录树。
