# 3. 进程概念

## 1. 冯诺依曼体系结构

电脑里有键盘、显示器、CPU、内存、磁盘等许多部件。新手容易产生一个疑问：键盘输入的数据，究竟怎样才能被 CPU 处理，再显示到屏幕上？

冯诺依曼体系结构，就是一种规定电脑各部件如何分工、如何传递数据的基本组织方式。

### 1.1 五大部件

为了解决“各部件如何配合”的问题，可以把电脑看成由五类部件组成：

| 部件 | 大白话作用 | 例子 |
|---|---|---|
| 输入单元 | 把外部信息送进电脑 | 键盘、鼠标、网卡 |
| CPU | 负责计算和指挥 | 运算器、控制器 |
| 存储器 | 暂时保存正在使用的数据 | 内存 |
| 输出单元 | 把电脑处理后的信息送出去 | 显示器、网卡、磁盘 |
| 外部设备 | 与电脑外部交换信息的设备 | 键盘、网卡、显示器等 |

#### 输入单元

输入单元负责把外界信息交给电脑。例如，按下键盘上的 `A`，键盘就产生了一个输入数据。

网卡也可以是输入单元：网络上的数据到达本机时，网卡负责把数据接收进来。

#### CPU

CPU 是电脑中负责“计算和指挥”的部件，由两部分组成：

- **运算器**：负责加减乘除、比较等计算。
- **控制器**：负责决定下一步做什么，例如取数据、执行指令、保存结果。

#### 存储器就是内存

存储器负责暂时保存 CPU 正在使用的数据和程序。现代电脑中，这个存储器主要就是我们常说的**内存**。

例如，打开一个程序后，程序通常要先放入内存，CPU 才能使用其中的指令和数据。

> **板书重点：存储器就是内存，负责暂时保存 CPU 正在使用的数据和程序。**

#### 输出单元

输出单元负责把处理结果送到电脑外部。例如：

- 显示器显示文字和图片；
- 网卡把数据发送到网络；
- 磁盘把数据保存下来。

同一个设备可能承担不同方向的工作。网卡接收网络数据时是输入单元，发送网络数据时是输出单元。

---

### 1.2 CPU、外设与内存之间的数据关系

如果键盘、CPU、显示器都能互相直接传数据，连接关系会非常复杂：

```text
键盘 ↔ CPU
键盘 ↔ 显示器
键盘 ↔ 磁盘
CPU  ↔ 显示器
CPU  ↔ 磁盘
...
```

设备一多，连接和管理都会变得困难。因此，电脑需要一个统一的数据中转站，这个中转站就是内存。

数据传递通常遵循这样的路线：

```text
输入设备 → 内存 → CPU → 内存 → 输出设备
```

例如，键盘输入一个数字：

1. 键盘把数字送入内存；
2. CPU 从内存中取出数字；
3. CPU 处理后，把结果放回内存；
4. 显示器从内存取得结果并显示。

这里说的“CPU 只能和内存打交道”，是指**在数据传递层面**，CPU 不直接从键盘、显示器、磁盘等外设取得或交付数据；数据必须经过内存。

同样，外设之间也不直接交换数据，而是通过内存完成中转：

```text
外设 A → 内存 → 外设 B
```

例如，网卡收到的数据先进入内存，CPU 需要处理时再从内存读取。

> **板书重点：CPU 在数据层面只和内存打交道，外设之间的数据传递也必须经过内存。**

这种设计解决了两个问题：

- 内存成为统一的数据交换中心；
- CPU 不需要为每一种外设设计一套直接连接方式。

---

### 1.3 不同设备的速度差异

如果所有设备速度差不多，数据经过内存中转似乎不会带来太大问题。但实际情况是，不同设备的速度差异非常大。

**纳秒**是十亿分之一秒，**毫秒**是千分之一秒。毫秒比纳秒慢很多数量级。

大致可以这样理解：

- CPU 内部的寄存器：纳秒级，速度极快；
- 键盘、磁盘、网络等外设：通常是毫秒级或更慢。

**寄存器**是 CPU 内部用来临时保存少量数据的高速存储位置。CPU 如果每次都直接等待慢速外设，绝大部分时间都会处于等待状态。

因此，数据通常先放到内存中，让 CPU 和外设分别按照自己的速度工作：

```text
慢速外设 → 内存 ←→ CPU
```

例如，键盘输入很慢，CPU 计算很快。键盘输入一个字符后，字符先放入内存；CPU 可以先做其他工作，等需要时再从内存读取这个字符。

#### “拷贝”为什么重要

这里的“拷贝”，就是把数据从一个位置复制到另一个位置。例如：

```text
键盘 → 内存
内存 → CPU
CPU → 内存
内存 → 显示器
```

每次复制都需要时间。如果复制过程设计得低效，CPU 即使很快，也会因为等待数据而浪费时间。

所以，冯诺依曼体系结构的整体效率，不只取决于 CPU 有多快，还取决于各设备之间传递数据的效率。

> **板书重点：设备速度差异巨大，体系结构的效率很大程度上取决于设备之间的拷贝效率。**

---

### 1.4 存储金字塔

电脑中不只有一种存储位置。不同存储位置的速度、成本和用途不同，可以从上到下看成一座“存储金字塔”：

```text
寄存器
  ↓
高速缓存 L1 ~ L3
  ↓
内存 DRAM
  ↓
磁盘
  ↓
网盘
```

越靠上，通常访问越快，但单位容量的成本越高；越靠下，通常访问越慢，但适合保存更多数据。

#### 寄存器

寄存器位于 CPU 内部，离运算部件最近，速度最快，但能保存的数据很少。

#### 高速缓存

**高速缓存**是位于 CPU 和内存之间的高速存储区域，用来保存 CPU 最近可能再次使用的数据。

高速缓存通常使用 **SRAM**，即“静态随机存取存储器”。它速度快，但成本高，所以容量较小，并分为 `L1`、`L2`、`L3` 等层次。

一般来说：

```text
L1 比 L2 快，L2 比 L3 快
```

#### 内存

内存通常使用 **DRAM**，即“动态随机存取存储器”。它比寄存器和高速缓存慢，但容量更大、成本更低，适合保存正在运行的程序和数据。

#### 磁盘

磁盘用于长期保存数据，例如程序、文档、图片和视频。电脑断电后，磁盘中的数据通常仍然存在。

#### 网盘

网盘把数据保存在网络上的服务器中。访问网盘时，数据需要经过网络，因此速度还会受到网络状况影响。

> **板书重点：存储金字塔从上到下依次是寄存器、高速缓存、内存、磁盘、网盘；越靠上越快、越贵。**

需要注意，`L1`、`L2`、`L3` 不是三种完全独立的用途，而是高速缓存的不同层次；越靠近 CPU 的层次通常越快。

### 1.5 QQ 聊天和发文件的数据流

假设 A 通过 QQ 给 B 发送一条消息。A 和 B 不共用同一套电脑部件，而是各自拥有一套冯诺依曼体系结构。

#### 发送文字消息

A 输入文字后，数据经过如下路径：

```text
A 的键盘
  ↓
A 的内存
  ↓
A 的网卡
  ↓
网络
  ↓
B 的网卡
  ↓
B 的内存
  ↓
B 的显示器
```

具体过程是：

1. A 的键盘产生输入数据；
2. 数据进入 A 的内存；
3. A 的网卡从内存取得数据并发送到网络；
4. 网络把数据传到 B；
5. B 的网卡接收数据并放入 B 的内存；
6. B 的显示器从 B 的内存取得数据并显示出来。

#### 发送文件

发送文件时，基本路线相同，只是数据量更大：

```text
A 的磁盘
  ↓
A 的内存
  ↓
A 的网卡
  ↓
网络
  ↓
B 的网卡
  ↓
B 的内存
  ↓
B 的磁盘
```

A 的文件先从磁盘进入 A 的内存，再由网卡发送；B 的网卡接收后，数据进入 B 的内存，最后保存到 B 的磁盘。

网卡在这条流程中承担两个方向的工作：

- A 发送数据时，网卡是输出设备；
- B 接收数据时，网卡是输入设备。

> **板书重点：QQ 的数据传递必须经过两台机器各自的内存；网卡既可以是输入设备，也可以是输出设备。**

## 2. 操作系统（Operating System，操作系统）

### 2-1 概念与定位

#### 操作系统到底是什么

假设你想运行一个程序、读取一个文件、把文字显示到屏幕上。程序本身通常不能直接指挥硬盘、内存、显示器等硬件，否则每个程序都要自己处理一套复杂的硬件规则，系统会混乱。

所以需要一个统一的管理者：**操作系统（OS）就是一款专门“搞管理”的软件**。它负责管理计算机中的进程、内存、文件、设备等资源，并为程序提供运行所需的环境。

> **操作系统的本质定位：它不是某个具体应用，而是负责统一管理计算机资源的软件。**

操作系统通常可以分成两部分：

- **内核（kernel）**：操作系统最核心的部分，负责进程、内存、文件和设备驱动等管理。
- **其他程序**：例如 `shell`、函数库和各种系统工具。`shell` 是一个接收并执行用户命令的外壳程序；函数库是别人已经写好的、可以被程序重复使用的功能集合。

因此有两种范围不同的“操作系统”说法：

```text
广义操作系统
├── 外壳：shell、glibc、各种程序
└── 狭义操作系统：内核
```

- **狭义 OS**：只指内核。
- **广义 OS**：指内核加上 shell、函数库和其他配套程序。

`glibc` 是 Linux 中常用的 C 语言函数库，许多 C 程序使用的标准函数都来自这里。

> **广义 OS = 外壳（shell、glibc、程序）+ 狭义 OS（内核）。**

#### `printf` 的本质

初学时容易觉得 `printf` 只是“把文字打印出来”。但如果追问“文字最终去了哪里”，就会发现它需要经过一整套系统。

```cpp
#include <stdio.h>                         // 引入 printf 的声明

int main()                                  // 程序入口
{
    printf("hello\n");                     // 把数据写入标准输出，通常最终显示在终端
    return 0;                               // 正常结束程序
}
```

`printf` 首先把数据交给标准输出。通常标准输出连接着终端，因此文字会显示到显示器上；如果把输出重定向到文件，数据也可能写入文件。

所以，从最终效果看：

> **`printf` 的本质，是把程序中的数据通过操作系统提供的通道，交给硬件设备（通常是显示器）呈现出来。**

`printf` 自己并不懂显示器的电信号和具体硬件规则。它需要通过函数库、系统调用、内核和驱动，最后才能让显示器显示内容。

### 2-2 设计目的

#### 对下：管理软硬件资源

程序要使用 CPU、内存、硬盘、网卡、显示器等资源，但这些硬件各自有不同的工作方式。如果每个程序都直接操作硬件，就会出现资源冲突，例如两个程序同时修改同一块内存。

因此，操作系统需要向下管理所有软硬件资源：

- 管理哪些程序正在运行；
- 分配和回收内存；
- 管理文件和磁盘空间；
- 通过驱动控制各种硬件设备。

**驱动（driver）** 是专门负责让操作系统能够控制某类硬件的软件。例如，显卡驱动负责帮助操作系统使用显卡。

这些工作是操作系统实现目标的手段，而不是最终目的。

#### 对上：提供良好的执行环境

用户真正关心的不是“内核内部怎样管理内存”，而是：

- 程序能不能运行；
- 文件能不能读写；
- 文字能不能显示；
- 多个程序能不能同时工作；
- 程序出错时是否不会破坏整个系统。

所以，操作系统向上为用户程序提供一个统一、方便、安全的执行环境。程序只需要按照操作系统规定的方式提出请求，不必直接面对各种硬件细节。

```text
用户程序提出需求
        ↓
操作系统统一处理
        ↓
硬件完成实际工作
```

> **对下管理资源是手段，对上为用户程序提供良好的执行环境才是操作系统的目的。**

### 2-3 如何理解“管理”

#### 管理中的三个关键特点

生活中，管理者不一定需要亲自接触每一个被管理者。例如校长不需要每天逐个询问学生的情况，也可以通过表格、统计数据和辅导员的反馈进行管理。

计算机中的管理也有类似特点：

1. **管理者和被管理者可以不见面**  
   操作系统不需要像人一样直接“观察”每个进程，而是通过数据了解进程状态。

2. **管理依靠数据**  
   进程是否运行、占用了多少内存、打开了哪些文件，都要记录成数据。

3. **数据由中间层获取**  
   管理者不一定直接获取原始信息，而是由其他程序或硬件把信息整理后交给管理者。

```text
被管理对象
    ↓
中间层获取并整理信息
    ↓
形成描述对象的数据
    ↓
管理者依据数据做决策
```

#### 管理的本质：管理数据

例如，校长可以使用 Excel 表记录学生姓名、班级、成绩和考勤情况，再根据这些数据做出管理决定。校长不需要每天亲自跟着每个学生，辅导员负责具体执行。

计算机中也是如此：

- **管理者**：操作系统；
- **被管理者**：进程、内存、文件、设备等；
- **管理依据**：描述这些对象的数据；
- **具体执行者**：内核中的相关模块和驱动。

因此，操作系统并不是直接凭空管理一个进程，而是先为进程建立一份“档案”，再根据档案中的数据进行调度、暂停、唤醒和回收等操作。

#### 计算机管理的方法论

如果要管理一个对象，首先必须回答：“这个对象有哪些重要信息？”

例如，描述一个进程，至少需要知道：

- 它的身份；
- 它当前的状态；
- 它使用了哪些资源；
- 它需要执行什么任务。

在 Linux 内核中，用来描述进程的核心结构叫 `task_struct`。它可以理解为一份记录进程信息的数据结构。

但只有一份份独立的记录还不够。操作系统还需要快速找到所有进程、按照状态分类进程、遍历进程等，因此需要把这些描述对象组织起来，常见方式就是使用链表等数据结构。

```text
先描述对象
    ↓
用结构体保存对象信息
    ↓
再组织对象
    ↓
用链表等数据结构管理多个对象
```

> **计算机管理的核心方法：先描述，再组织；先用结构体描述对象，再用数据结构组织对象。**

### 2-4 系统调用和库函数

#### 软硬件层次结构

假设程序要把一个字符显示到屏幕上。程序不能直接跳过操作系统去操作显示器，因为硬件细节复杂，而且直接操作会破坏系统的统一管理。

因此，访问硬件必须经过完整的软件层次：

```text
用户
  ↓
库函数 / shell
  ↓
系统调用接口
  ↓
内核
  ↓
设备驱动
  ↓
硬件
```

每一层负责不同的工作：

- **用户**：提出需求，例如“显示这段文字”。
- **库函数 / shell**：提供更容易使用的操作方式。
- **系统调用接口**：用户程序请求内核服务的正式入口。
- **内核**：判断请求是否合法，并负责资源管理。
- **设备驱动**：把内核的通用要求转换成某种硬件能够理解的操作。
- **硬件**：真正完成显示、读写或计算。

> **用户程序访问硬件时，必须通过“库函数或 shell → 系统调用 → 内核 → 驱动 → 硬件”的层次。**

#### 系统调用是什么

如果用户程序可以随意进入内核、随意修改内存或直接控制硬件，任何一个程序出错都可能破坏整个系统。因此，操作系统不能相信任何用户程序。

**系统调用（system call）** 是操作系统提供给用户程序的正式接口，也就是用户程序请求内核服务的“窗口”。

可以把它类比成银行柜台：

- 用户程序相当于客户；
- 内核相当于银行内部系统；
- 系统调用相当于柜台窗口；
- 参数相当于客户提交的业务信息；
- 返回值相当于柜员返回的办理结果。

用户程序不能直接进入银行内部，只能通过柜台提交请求。内核也会检查请求是否合理，例如：

- 参数是否合法；
- 地址是否可访问；
- 文件是否有权限；
- 请求的资源是否存在。

系统调用通常包含三类信息：

1. **调用哪个服务**；
2. **传入哪些参数**；
3. **得到什么返回值**。

例如，程序想读取文件，就需要告诉操作系统读取哪个文件、把数据放到哪里，以及操作是否成功。

#### 库函数与系统调用的关系

**库函数** 是为了让程序员更方便使用而提供的函数；**系统调用** 是进入内核、请求操作系统服务的接口。

库函数可能在底层封装了系统调用，但二者不是同一个层次的东西：

| 对比项 | 库函数 | 系统调用 |
|---|---|---|
| 所在位置 | 用户程序一侧的函数库 | 操作系统提供的内核接口 |
| 主要作用 | 提供更方便、更易用的编程方式 | 请求内核执行受保护的系统服务 |
| 是否一定进入内核 | 不一定 | 会进入内核 |
| 典型关系 | 可能进一步调用系统调用 | 直接连接内核服务 |

`printf` 就是一个库函数。它负责格式化输出内容，并把结果交给标准输出；当输出需要交给文件、终端等操作系统管理的对象时，底层通常还要借助系统调用完成。

```text
C 程序
  ↓
printf 等 C 函数
  ↓
系统调用接口
  ↓
Linux 内核
  ↓
设备驱动
  ↓
显示器或其他硬件
```

不同操作系统提供的底层系统调用不同，但程序员通常通过 C 语言函数来使用操作系统能力：

```text
Linux / Windows / macOS
            ↓
         C 语言
            ↓
        C 函数
```

这也是库函数存在的意义之一：它把不同操作系统的底层差异包装起来，让上层程序可以用更统一的方式完成常见任务。

#### 承上启下：操作系统如何管理进程

现在可以把前面的内容连起来：

- 操作系统需要管理进程；
- 管理不能只靠“看”，而要依靠数据；
- 所以必须先为每个进程建立描述信息；
- 再把这些描述信息组织起来，方便查找和管理。

Linux 内核使用 `task_struct` 描述进程，再通过链表等数据结构组织多个进程。

> **操作系统管理进程的基本思路：先用 `task_struct` 描述进程，再用链表等数据结构组织进程。**

## 3. 进程

### 3-1 基本概念与基本操作

#### 1. 进程的基本概念：从三个视角理解

假设你把多个程序加载到内存中：浏览器、音乐播放器、终端都在同时运行。操作系统必须知道每个程序的状态、位置和资源使用情况，否则就无法调度和管理它们。

##### 第一种视角：课本概念

课本常把进程定义为“程序的一次执行实例”。这个说法能帮助入门，但不够准确，因为它只强调了“程序正在执行”，没有说明操作系统如何管理它。

##### 第二种视角：内核观点

内核需要给每个程序分配和管理资源，例如：

- CPU 时间；
- 内存；
- 打开的文件；
- 键盘、磁盘等 I/O 设备；
- 进程的运行状态。

因此，从内核角度看，进程是“操作系统分配系统资源的实体”。

但是，操作系统不能直接管理一段没有格式的信息。它需要先为每个进程建立一份管理档案，这份档案在 Linux 中叫 `task_struct`。

`task_struct`：内核中描述一个进程的结构体，里面记录了进程的各种管理信息。

##### 第三种视角：当前结论

一个进程不只是代码，也不只是一个结构体，而是两部分共同组成：

```text
进程
├── task_struct：内核管理进程所需的数据
└── 代码和数据：程序真正执行和使用的内容
```

> **进程 = 内核数据结构 `task_struct` + 自己的代码和数据。**

代码和数据属于用户程序；`task_struct` 属于内核。用户程序不能直接随意修改 `task_struct`，必须通过系统调用请求内核完成操作。

#### 2. 操作系统如何管理进程：先描述，再组织

假设内存中有 100 个进程。如果操作系统只知道“内存里有一些程序”，却没有记录每个程序的状态、优先级和资源信息，就无法管理它们。

因此，操作系统管理对象通常分两步：

1. **描述**：用结构体记录对象的信息；
2. **组织**：用链表、队列等数据结构把这些结构体连接起来。

对于进程，描述对象就是 `task_struct`，组织方式通常是链表或各种调度队列。

```text
多个 task_struct
      ↓
通过链表或队列组织起来
      ↓
操作系统可以遍历、查找、插入、删除和修改进程
```

> **对进程的管理，本质上就是对 `task_struct` 双向链表进行增、删、查、改。**

`task_struct` 中通常包含以下信息：

| 信息 | 作用 |
|---|---|
| 标示符 | 区分不同进程，例如 PID |
| 状态 | 表示进程正在运行、睡眠、停止等 |
| 优先级 | 决定调度时谁更有机会先获得 CPU |
| 程序计数器 | 记录下一条要执行的指令位置 |
| 内存指针 | 找到进程的代码、数据和地址空间 |
| 上下文数据 | 保存进程暂时离开 CPU 时的寄存器信息 |
| I/O 状态 | 记录打开了哪些文件、正在等待什么设备 |
| 记账信息 | 记录进程使用了多少 CPU 时间等 |

#### 3. 查看和控制进程

##### 查看进程：`ps`

`ps`：查看当前系统中进程信息的命令。

常用语法：

```bash
ps aux   # 按用户格式显示所有用户的进程，包括没有终端的进程
ps axj   # 显示所有进程，并以作业格式展示父子关系等信息
```

`ps aux` 中各选项的含义：

| 选项 | 含义 |
|---|---|
| `a` | 显示所有用户的进程 |
| `u` | 使用面向用户的格式显示 |
| `x` | 显示没有终端的进程 |

`ps axj` 中：

| 选项 | 含义 |
|---|---|
| `a` | 显示所有用户的进程 |
| `x` | 显示没有终端的进程 |
| `j` | 显示作业信息，例如 PID、PPID、进程组等 |

`PID`：进程 ID，每个进程的身份编号。  
`PPID`：父进程 ID，表示创建当前进程的进程编号。

##### 查看单个进程：`/proc/PID/`

Linux 把许多内核信息以文件和目录的形式提供出来。`/proc` 是一个虚拟文件系统，里面的内容主要由内核动态生成，并不是真正存放在磁盘上的普通文件。

```bash
ls -l /proc/进程PID/       # 查看指定进程的内核信息目录
ls -l /proc/进程PID/exe    # 查看该进程对应的可执行文件
ls -l /proc/进程PID/cwd    # 查看该进程当前工作目录
```

例如，假设进程号是 `1234`：

```bash
ls -l /proc/1234/exe       # exe 指向该进程运行的可执行文件
ls -l /proc/1234/cwd       # cwd 指向该进程当前所在的工作目录
```

`exe`：executable 的缩写，表示进程正在执行的程序。  
`cwd`：current working directory 的缩写，表示进程当前工作目录。

##### 结束进程：`kill` 和 `Ctrl+C`

`kill`：向进程发送信号的命令，信号是操作系统通知进程发生某件事情的方式。

```bash
kill -9 PID                 # 发送 9 号信号，强制结束指定进程
```

例如：

```bash
kill -9 1234                # 强制结束 PID 为 1234 的进程
```

`Ctrl+C` 也会向当前终端中的前台进程发送中断信号，因此常用于结束正在前台运行的程序。

二者的区别是：

| 方式 | 作用范围 |
|---|---|
| `Ctrl+C` | 当前终端正在运行的前台进程 |
| `kill -9 PID` | 根据 PID 结束指定进程 |

#### 4. `getpid` 和 `getppid`

程序有时需要知道“我是谁”和“是谁创建了我”。Linux 提供了两个系统调用：

- `getpid`：获取当前进程的 PID；
- `getppid`：获取当前进程的 PPID。

系统调用：程序向操作系统内核请求服务的接口。它们属于 `man` 手册的第 2 区。

```bash
man 2 getpid              # 查看 getpid 系统调用的手册
man 2 getppid             # 查看 getppid 系统调用的手册
```

示例：

```cpp
#include <iostream>       // 提供输出功能
#include <unistd.h>       // 提供 getpid 和 getppid
using namespace std;      // 使用标准命名空间

int main()                // 程序入口
{
    cout << "PID: " << getpid() << endl;    // 输出当前进程 ID
    cout << "PPID: " << getppid() << endl;  // 输出父进程 ID
    return 0;                               // 正常结束
}
```

编译和运行：

```bash
g++ pid.cpp -o pid       # 编译程序
./pid                    # 运行程序并查看 PID、PPID
```

##### 为什么命令行进程的父进程通常是 `bash`？

`bash`：一种命令行解释器，负责读取你输入的命令、创建进程并让命令运行。

登录 Linux 后，系统通常会为你启动一个 `bash`。之后你在命令行中输入的程序，通常由这个 `bash` 创建，因此这些程序的 PPID 通常就是 `bash` 的 PID。

```text
登录系统
   ↓
bash 启动
   ↓
bash 创建 ls、vim、a.out 等子进程
```

所以，用 `getppid()` 查看一个通过命令行启动的程序时，通常会发现它的父进程是 `bash`。

### 3-1-6 `fork` 初识

#### 1. 为什么需要 `fork`

如果一个进程想创建另一个进程，就需要向操作系统申请创建。Linux 中最常用的创建进程接口是 `fork`。

`fork`：复制当前进程，创建一个新的子进程。

父进程：调用 `fork` 的原进程。  
子进程：`fork` 创建出来的新进程。

#### 2. `fork` 的语法和返回值

语法：

```cpp
#include <unistd.h>       // 提供 fork 函数

pid_t fork();              // 创建子进程并返回结果
```

返回值：

| 执行结果 | 父进程中的返回值 | 子进程中的返回值 |
|---|---:|---:|
| 创建成功 | 子进程 PID | `0` |
| 创建失败 | `-1` | 不产生子进程 |

`pid_t`：专门用于表示进程 ID 的整数类型。

```cpp
#include <iostream>       // 提供输出功能
#include <unistd.h>       // 提供 fork、getpid、getppid
using namespace std;      // 使用标准命名空间

int main()                // 程序入口
{
    pid_t ret = fork();   // 创建子进程，并保存返回值

    if (ret < 0)          // ret 小于 0 表示创建失败
    {
        cout << "fork failed" << endl;  // 输出失败信息
        return 1;         // 用非 0 值表示异常结束
    }
    else if (ret == 0)    // 子进程中的 fork 返回 0
    {
        cout << "child: pid=" << getpid()
             << ", ppid=" << getppid() << endl;  // 输出子进程信息
    }
    else                  // 父进程中的 fork 返回子进程 PID
    {
        cout << "parent: pid=" << getpid()
             << ", child pid=" << ret << endl;   // 输出父进程和子进程信息
    }

    return 0;             // 父子进程分别执行到这里并结束
}
```

编译运行：

```bash
g++ fork.cpp -o fork     # 编译程序
./fork                    # 运行程序
```

> **`fork` 成功后，父进程返回子进程 PID，子进程返回 `0`，失败返回 `-1`；因此可以用 `if/else` 让父子进程执行不同代码。**

#### 3. 父子进程如何共享代码和数据

`fork` 并不是简单地把父进程的所有内容机械复制一份。创建后：

- 父子进程可以执行同一份代码；
- 父子进程拥有各自独立的数据；
- 子进程最开始以父进程为模板；
- 对数据进行写操作时，系统才为修改者准备独立副本。

这种机制叫**写时拷贝**。

写时拷贝：开始时父子进程共用同一份数据，谁要修改，系统再复制一份给修改者。

```text
fork 创建后：
父进程 ─┐
        ├── 共同使用代码
子进程 ─┘

数据开始时可共享
        ↓
某一方写数据
        ↓
系统复制数据
        ↓
父子进程分别拥有自己的数据
```

> **父子进程共享代码，但数据彼此私有；数据在写入时通过写时拷贝分离。**

实验：

```cpp
#include <iostream>       // 提供输出功能
#include <unistd.h>       // 提供 fork 和 sleep
using namespace std;      // 使用标准命名空间

int g_val = 100;          // 定义一个全局变量

int main()                // 程序入口
{
    pid_t ret = fork();   // 创建子进程

    if (ret < 0)          // 判断创建是否失败
    {
        cout << "fork failed" << endl;  // 输出失败信息
        return 1;         // 异常结束
    }

    if (ret == 0)         // 子进程执行这里
    {
        g_val = 200;      // 子进程修改自己的数据副本
        cout << "child: g_val=" << g_val << endl;  // 输出子进程的值
    }
    else                  // 父进程执行这里
    {
        sleep(1);         // 让子进程先运行，便于观察结果
        cout << "parent: g_val=" << g_val << endl; // 父进程仍看到原值
    }

    return 0;             // 进程结束
}
```

父进程输出 `100`，子进程输出 `200`，说明修改发生在各自的进程数据中，互不影响。

#### 4. `fork` 的三个经典问题

##### 问题一：为什么父子进程要返回不同的值？

父进程可能创建多个子进程：

```text
一个父进程
├── 子进程 1
├── 子进程 2
└── 子进程 3
```

父进程需要知道每个子进程的 PID，才能分别管理它们，例如等待某个子进程结束或向某个子进程发送信号。

因此：

- 父进程返回子进程 PID；
- 子进程返回 `0`，因为它只需要知道“自己是子进程”；
- 创建失败返回 `-1`。

父进程与子进程的数量关系可以是 `1:n`，所以父进程必须获得子进程的唯一编号。

##### 问题二：为什么一个函数看起来返回了两次？

从源代码看，`fork()` 只有一次调用；但从运行结果看，父子进程都继续执行了 `fork` 后面的代码。

原因是 `fork` 内部大致完成了这些操作：

```text
申请子进程的 task_struct
        ↓
复制父进程的 task_struct
        ↓
把子进程挂入进程管理链表和调度队列
        ↓
分别让父子进程继续运行
        ↓
父进程得到子进程 PID，子进程得到 0
```

这里的“返回两次”并不是同一个函数被同一个进程调用两次，而是：

1. 原来的父进程继续执行并得到一个返回值；
2. 新创建的子进程也从相应位置继续执行并得到另一个返回值。

从实现角度看，`return` 的本质是把返回值写入约定的位置，然后让调用者继续执行。`fork` 返回时，子进程已经被创建并可以独立参与调度。

##### 问题三：一个变量为什么能让 `if/else` 同时成立？

父子进程拥有各自独立的执行流。虽然它们从同一个 `fork` 位置继续执行，但看到的返回值不同：

```text
父进程：ret = 子进程 PID
子进程：ret = 0
```

所以在父进程中，`ret == 0` 不成立，执行 `else`；在子进程中，`ret == 0` 成立，执行 `if`。

更深层的原因涉及虚拟地址空间和写时拷贝：父子进程可以使用相同的变量地址，但这些地址在不同进程中属于各自的地址空间。这个问题会在程序地址空间部分进一步说明。

### 3-2 进程状态

#### 理论基础

##### 1. 运行状态：进入运行队列

一个 CPU 同一时刻通常只能真正执行一个进程，但系统中可能有很多进程都准备使用 CPU。

因此，操作系统会建立一个运行队列 `runqueue`。

`runqueue`：保存准备使用 CPU 的进程的调度队列。

```text
一个 CPU
   ↓
一个 runqueue
   ↓
多个等待使用 CPU 的进程
```

这里的 `running` 不一定表示“此刻正在 CPU 上执行”。它表示进程已经准备好运行，或者正在 CPU 上运行。

> **在一个 CPU 中，进入 `runqueue` 的进程状态都可以看作 `running`，但同一时刻真正占用 CPU 的通常只有一个。**

##### 2. 阻塞状态：等待非 CPU 资源

进程运行时可能需要读取键盘、磁盘或网络数据。此时问题不是 CPU 不够，而是数据还没有准备好。

如果进程继续占用 CPU 等待，就会浪费 CPU。因此，操作系统会让它暂时离开运行队列，进入对应设备的等待队列。

`wait_queue`：等待某个设备或事件完成的进程队列。

```text
进程需要键盘输入
        ↓
键盘数据还没准备好
        ↓
进程进入键盘 wait_queue
        ↓
进程让出 CPU
        ↓
键盘输入到达后，进程重新进入 runqueue
```

操作系统管理硬件时同样遵循“先描述，再组织”的原则。内核会用类似 `struct device` 的结构体描述设备，再通过链表或队列管理设备和等待它们的进程。

> **阻塞不是等待 CPU，而是等待键盘、磁盘等非 CPU 资源；进程会从运行队列转移到设备等待队列。**

##### 3. 挂起状态：暂时换出内存

如果内存不足，所有进程的代码和数据无法同时留在内存中，操作系统会把暂时不用的进程代码和数据写到磁盘的 `swap` 分区。

`swap`：磁盘上用于临时保存内存数据的区域。

注意，换出时通常保留进程的 `task_struct` 在内存中，因为内核还需要继续管理这个进程。

```text
内存不足
   ↓
进程代码和数据换到 swap
   ↓
进程的 task_struct 仍留在内存
   ↓
需要运行时再换回内存
```

这类状态叫挂起。挂起的核心特征是：进程暂时不占用内存中的代码和数据空间，但进程管理信息仍然存在。

##### 4. 状态变化的本质

进程状态发生变化时，操作系统通常不是简单地修改一个文字标签，而是同时调整进程所在的数据结构：

```text
runqueue
   ↔
设备 wait_queue
   ↔
挂起相关队列
```

例如，进程从运行变为阻塞，本质上是：

1. 从 `runqueue` 中删除；
2. 加入设备的 `wait_queue`；
3. 修改进程的状态字段。

> **进程状态变化，本质上是进程在不同队列之间流动，也就是对数据结构进行增、删、查、改。**

#### Linux 内核双向链表：`list_head`

Linux 内核大量使用双向链表。双向链表：每个节点同时保存前一个节点和后一个节点的地址。

```cpp
struct list_head
{
    struct list_head *next;  // 指向下一个节点
    struct list_head *prev;  // 指向上一个节点
};
```

Linux 的做法不是让 `task_struct` 继承某个链表节点，而是直接把 `list_head` 嵌入 `task_struct`：

```cpp
struct task_struct
{
    int pid;                       // 保存进程 ID
    struct list_head task_list;    // 嵌入双向链表节点
};
```

链表操作只需要处理 `task_list` 的 `next` 和 `prev`，但遍历到某个链表节点后，还需要找到它所属的 `task_struct`。

问题在于：拿到的是成员地址，不是结构体首地址。

```text
task_struct 起始地址
        ↓ 偏移若干字节
task_list 成员地址
```

因此，内核使用 `offsetof` 计算成员相对于结构体起始位置的偏移量，再用：

```text
结构体首地址 = 成员地址 - 成员偏移量
```

`offsetof`：计算结构体成员距离结构体起始位置多少字节的工具。

这使得 Linux 可以通过嵌入式 `list_head` 管理各种不同结构体，而不需要为每种结构体重新实现一套链表。

### 内核状态

Linux 用状态字母表示进程当前处于什么状态。使用 `ps axj` 或 `ps aux` 时，可以在 `STAT` 列看到这些字母。

#### 1. `R`：运行状态

`R`：running，表示进程在运行队列中，处于可运行状态。

它不保证进程此刻正在 CPU 上执行，只表示它已经准备好运行。

#### 2. `S`：可中断睡眠

`S`：interruptible sleep，可中断睡眠，也叫浅睡眠。

进程正在等待某个事件，例如键盘输入、网络数据或定时器，但在等待期间仍可以被信号唤醒或终止。

```text
等待事件
   ↓
进入 S 状态
   ↓
事件到达或收到可处理信号
   ↓
恢复运行或结束
```

#### 3. `D`：不可中断睡眠

`D`：uninterruptible sleep，不可中断睡眠，也叫深睡眠。

常见场景是进程正在等待磁盘 I/O 完成。在这种状态下，进程通常不能被普通信号打断，甚至 `kill -9` 也不能立即杀掉它，必须等 I/O 操作返回。

可以用 `dd` 制造大量磁盘 I/O 来观察这种状态：

```bash
dd if=/dev/zero of=bigfile bs=1M count=1024   # 连续向文件写入约 1GB 数据
```

`if`：输入文件。  
`of`：输出文件。  
`bs`：每次读写的数据块大小。  
`count`：读写多少个数据块。

> **`D` 状态表示进程正在等待不可中断的 I/O 操作完成，因此不能被普通方式立即杀掉。**

#### 4. `T`：停止状态

`T`：stopped，表示进程被暂停，暂时不会继续执行。

可以使用信号暂停和恢复进程：

```bash
kill -STOP PID             # 发送暂停信号，让进程进入 T 状态
kill -CONT PID             # 发送继续信号，让进程恢复运行
```

调试器在断点处暂停程序时，进程也会进入 `T` 状态。

在调试场景中，`t` 还可以理解为 `tracing stop`，表示进程正在被调试器追踪并暂停。

#### 5. `X`：死亡状态

`X`：dead，表示进程已经死亡。

这是一个非常短暂的内部状态，进程列表通常来不及观察到它。

#### 6. `Z`：僵尸状态

`Z`：zombie，僵尸进程。

子进程已经退出，但父进程还没有读取它的退出信息。此时子进程已经不能继续执行，却还保留着 `task_struct`，所以在进程表中仍然占据一个位置。

> **子进程退出、父进程仍在运行但没有读取退出信息时，子进程会进入 `Z` 状态。**

##### 为什么进程退出后还要保留信息？

子进程执行任务后退出，父进程通常需要知道任务结果，例如：

- 是否正常完成；
- 是否发生错误；
- 返回值是多少；
- 是否被信号杀死。

因此，退出信息会暂时保存在子进程的 `task_struct` 中，等待父进程读取。

```text
子进程完成任务
       ↓
子进程退出
       ↓
退出信息保存在 task_struct
       ↓
父进程读取退出信息
       ↓
内核回收 task_struct
```

#### 7. 僵尸进程的危害

僵尸进程的危害可以按以下链条推导：

```text
退出状态必须保留
        ↓
task_struct 必须继续存在
        ↓
父进程不读取退出信息
        ↓
task_struct 一直不能释放
        ↓
内核内存和进程表项持续被占用
        ↓
形成内存泄漏
```

> **僵尸进程不能继续运行，但会持续占用 `task_struct` 等内核资源；大量僵尸进程会造成资源泄漏。**

创建僵尸进程的实验：

```cpp
#include <iostream>       // 提供输出功能
#include <unistd.h>       // 提供 fork 和 sleep
#include <cstdlib>        // 提供 exit
using namespace std;      // 使用标准命名空间

int main()                // 程序入口
{
    pid_t ret = fork();   // 创建子进程

    if (ret < 0)          // 判断创建是否失败
    {
        return 1;         // 创建失败，异常退出
    }

    if (ret == 0)         // 子进程分支
    {
        cout << "child exit" << endl;  // 输出子进程即将退出
        exit(0);          // 子进程退出
    }

    cout << "parent sleep" << endl;    // 父进程继续运行
    sleep(60);            // 父进程暂时不读取子进程退出信息
    return 0;             // 父进程结束
}
```

另开一个终端查看：

```bash
ps axj | grep Z          # 查找状态中包含 Z 的进程
```

如果父进程在 60 秒内没有回收子进程，子进程通常会显示为 `Z+`。其中 `+` 表示该进程属于当前前台进程组。

#### 8. 孤儿进程

孤儿进程：父进程先退出、子进程仍在运行的进程。

```text
父进程退出
      ↓
子进程失去原父进程
      ↓
1 号进程 init/systemd 领养子进程
      ↓
子进程结束后由 1 号进程负责回收
```

Linux 中的 1 号进程通常是 `init` 或 `systemd`。它会负责接管这些孤儿进程，并在它们退出后读取退出信息、回收相关资源。

> **孤儿进程会被 1 号 `init/systemd` 进程领养；僵尸进程则是父进程没有及时回收已经退出的子进程。**

二者不要混淆：

| 对比项 | 僵尸进程 | 孤儿进程 |
|---|---|---|
| 父进程情况 | 父进程仍在运行 | 父进程已经退出 |
| 子进程情况 | 子进程已经退出 | 子进程仍在运行 |
| 主要问题 | 退出信息未被回收 | 原父进程消失 |
| 后续处理 | 父进程读取退出信息后回收 | 由 1 号进程领养和回收 |

### 3-3 进程优先级

#### 1. 为什么需要优先级

CPU 数量通常比进程数量少。多个进程都想使用有限的 CPU，因此会产生竞争。

竞争性：多个进程争夺有限 CPU 资源的现象。

```text
进程很多
   +
CPU 较少
   ↓
多个进程竞争 CPU
   ↓
操作系统需要决定谁先运行
   ↓
需要优先级
```

#### 2. `PRI`：进程优先级

`PRI`：priority 的缩写，表示进程优先级。

在本课程所用 Linux 调度模型中：

- `PRI` 越小，表示优先级越高；
- 优先级越高，越早获得 CPU；
- 默认 `PRI` 为 `80`。

> **`PRI` 越小，进程越容易优先获得 CPU；`PRI` 是进程的实际优先级。**

#### 3. `NI`：优先级修正值

`NI`：nice 值，是对进程优先级进行调整的修正数据，不是优先级本身。

关系为：

```text
PRI(new) = PRI(old) + nice
```

普通进程中：

- `nice` 范围为 `-20` 到 `19`；
- 总共有 40 个等级；
- `nice` 越小，最终 `PRI` 越小，进程优先级越高；
- 调整进程优先级，本质上是调整 `nice`。

例如：

```text
原 PRI = 80，nice = 5
新 PRI = 80 + 5 = 85
```

由于 `85` 大于 `80`，这个进程相对原来优先级降低。

| 概念 | 含义 |
|---|---|
| `PRI` | 进程当前实际优先级 |
| `NI` / `nice` | 用来修正优先级的数据 |
| 调整优先级 | 调整 `nice`，从而改变 `PRI` |

#### 4. 修改进程优先级

使用 `top` 修改：

```text
top                         # 打开进程监控界面
按 r                       # 进入修改优先级功能
输入 PID                   # 输入要调整的进程 ID
输入 nice 值               # 输入新的 nice 修正值
```

也可以使用命令：

```bash
nice -n 10 ./program       # 以 nice 值 10 启动 program
renice 10 -p 1234          # 把 PID 1234 的 nice 值调整为 10
```

`nice`：启动程序时指定优先级修正值。  
`renice`：修改已经运行的进程的优先级修正值。

程序也可以通过系统函数完成：

- `getpriority`：获取进程优先级；
- `setpriority`：设置进程优先级。

#### 5. 竞争性、独立性、并行和并发

这四个概念描述的是不同问题，不能混为一谈。

| 概念 | 大白话解释 | 关键条件 |
|---|---|---|
| 竞争性 | 多个进程争夺有限资源 | 进程多、CPU 少 |
| 独立性 | 进程之间互不干扰 | 各自拥有独立资源和地址空间 |
| 并行 | 多个进程在同一时刻真正执行 | 通常需要多个 CPU |
| 并发 | 多个进程交替推进，让人感觉同时执行 | 一个 CPU 也可以实现 |

单 CPU 并发：

```text
时间 →  t1    t2    t3    t4
进程 →   A     B     A     B
```

多 CPU 并行：

```text
CPU1 → 进程 A
CPU2 → 进程 B
```

> **并发强调“交替推进”，并行强调“同一时刻同时执行”；竞争性是资源不足产生的争夺，独立性是进程互不干扰的能力。**

### 3-4 进程切换

#### 1. 时间片

分时操作系统：把 CPU 时间划分成许多小段，轮流分配给不同进程的操作系统。

时间片：一个进程连续占用 CPU 的一小段时间。

如果一个进程一直占用 CPU，其他进程就没有机会运行。因此，操作系统规定每个进程只能运行一个时间片：

```text
进程 A 获得 CPU
       ↓
时间片耗尽
       ↓
操作系统把 A 从 CPU 上剥离
       ↓
进程 B 获得 CPU
```

> **分时操作系统为每个进程分配时间片，时间片耗尽后，操作系统会把进程从 CPU 上切换下来。**

#### 2. 什么是上下文

上下文：进程当前运行所需要的 CPU 寄存器状态。

CPU 中有许多寄存器，例如：

- 程序计数器；
- 通用寄存器；
- 栈指针；
- 状态寄存器。

一个进程运行到一半时，寄存器中保存的是它自己的运行现场。如果直接让另一个进程使用这些寄存器，原进程就无法从正确位置继续执行。

因此，切换时必须：

1. 保存当前进程的寄存器内容；
2. 加载下一个进程之前保存的寄存器内容。

这个过程叫上下文切换。

> **进程切换 = 上下文切换 = CPU 寄存器内容的保存与恢复。**

#### 3. 为什么每个进程都能保存自己的上下文

CPU 内的寄存器通常只有一套，但系统中可以有许多进程。

解决方法是：

- 当前进程的寄存器内容保存到它自己的 `task_struct`；
- 下次运行该进程时，再从它的 `task_struct` 恢复；
- 其他进程也各自保存一份。

```text
CPU 寄存器只有一套
        ↓
进程 A 的上下文保存到 A.task_struct
进程 B 的上下文保存到 B.task_struct
进程 C 的上下文保存到 C.task_struct
        ↓
需要谁运行，就恢复谁的上下文
```

> **CPU 寄存器只有一套，但每个进程都可以把自己的上下文保存到各自的 `task_struct` 中。**

#### 4. 上下文切换过程

可以把 CPU 想象成一名士兵，正在执行进程 A 的任务。轮换时，他要把 A 的工作现场记录下来，再拿出进程 B 上次留下的工作现场继续执行。

```text
进程 A 正在 CPU 上运行
          ↓
A 离开 CPU
          ↓
保存 A 的寄存器内容到 A.task_struct
          ↓
读取 B.task_struct 中保存的上下文
          ↓
恢复到 CPU 寄存器
          ↓
进程 B 从上次暂停的位置继续运行
```

保存和恢复上下文的过程由操作系统内核完成，用户程序通常感知不到这个细节。

### 3-5 Linux 2.6 内核 `O(1)` 调度队列

#### 1. 一个 CPU 对应一个 `runqueue`

在 Linux 2.6 的经典调度模型中，每个 CPU 都有自己的运行队列：

```text
CPU0 ── runqueue0
CPU1 ── runqueue1
CPU2 ── runqueue2
```

如果某个 CPU 的进程太多，而另一个 CPU 很空，就会出现负载不均衡。因此，多 CPU 系统还需要进行负载均衡，把部分进程从繁忙 CPU 的队列转移到空闲 CPU 的队列。

#### 2. 优先级分区

Linux 2.6 调度队列使用 140 个优先级：

| 优先级范围 | 类型 | 是否重点讨论 |
|---|---|---|
| `[0, 99]` | 实时优先级 | 本节不考虑 |
| `[100, 139]` | 普通进程优先级 | 本节重点 |

普通优先级与 `nice` 的对应关系：

```text
nice = -20  →  普通优先级 100
nice =  19  →  普通优先级 139
```

因此普通进程共有 40 个优先级等级。

#### 3. `queue[140]`：按优先级分队列

调度器为每个优先级准备一个队列：

```text
queue[0]    → 优先级 0 的进程
queue[1]    → 优先级 1 的进程
...
queue[100]  → 优先级 100 的进程
...
queue[139]  → 优先级 139 的进程
```

数组下标就是优先级。相同优先级的进程在同一个队列中按照 FIFO 顺序排队。

`FIFO`：先进先出，先进入队列的进程先被处理。

```text
queue[120]
   ↓
进程 A → 进程 B → 进程 C
   ↓
先调度 A，再调度 B，再调度 C
```

> **`queue[140]` 用数组下标直接对应优先级；同一优先级的进程按照 FIFO 排队。**

#### 4. `bitmap[5]`：快速寻找非空队列

如果每次调度都从 `queue[0]` 开始逐个检查到 `queue[139]`，最坏情况下需要检查 140 个队列。

为避免逐个查找，Linux 使用 `bitmap[5]`。

`bitmap`：用每一位表示一个队列是否为空的数据结构。

140 个优先级需要 140 个比特位：

```text
5 × 32 = 160 个比特位
```

其中足够标记 140 个优先级。

- 某个优先级队列非空，对应位设为 `1`；
- 某个优先级队列为空，对应位设为 `0`。

```text
bitmap
位：  0 1 2 3 ... 139
值：  0 0 1 0 ...  1
```

调度器可以快速找到最高优先级的非空队列，而不必扫描所有进程。

> **`bitmap[5]` 只记录哪些优先级队列非空，使调度器能够快速定位最高优先级进程。**

这里的 `O(1)` 是时间复杂度，表示查找调度进程所需的步骤数量是常数级，不会随着进程总数增加而线性增加。

#### 5. `active` 和 `expired`

调度队列分为两个部分：

- `active`：活动队列，保存时间片还没有耗尽的进程；
- `expired`：过期队列，保存时间片已经耗尽的进程。

`active`：当前仍然可以继续参与调度的进程集合。  
`expired`：本轮时间片已经用完、等待下一轮调度的进程集合。

运行过程：

```text
active 中的进程获得 CPU
        ↓
进程时间片逐渐耗尽
        ↓
进程从 active 移动到 expired
        ↓
active 越来越少，expired 越来越多
```

如果所有活动进程都已经用完时间片，活动队列就可能为空，而过期队列中有一批已经等待下一轮调度的进程。

#### 6. 交换两个队列指针

如果把 `active` 中的进程逐个复制到新的活动队列，会产生不必要的开销。

Linux 的做法是直接交换两个指针：

```text
交换前：
active  → 原活动队列
expired → 原过期队列

交换后：
active  → 原过期队列
expired → 原活动队列
```

原来的 `expired` 中保存着一批已经等待下一轮运行的进程。交换指针后，它们立刻成为新的 `active` 队列中的进程。

> **`active` 和 `expired` 通过交换指针完成队列轮换，不需要逐个移动进程，因此可以快速获得一批新的活动进程。**

#### 7. `O(1)` 调度的核心

整个调度过程可以概括为：

```text
bitmap 快速定位最高优先级非空队列
        ↓
queue[优先级] 找到该优先级的进程
        ↓
从队首取出进程
        ↓
时间片耗尽后放入 expired
        ↓
active 为空时交换 active 和 expired 指针
```

> **Linux 2.6 的 `O(1)` 调度队列通过优先级数组、非空位图以及 `active/expired` 指针交换，让寻找合适进程的时间复杂度不随进程数量增长。**

## 4. 命令行参数和环境变量

程序运行时，除了代码本身，还经常需要两类外部信息：

- 用户在命令后面输入的内容，例如 `ls -a -l`；
- 操作系统提供的运行环境信息，例如当前用户、命令搜索路径。

如果每次都把这些信息写死在程序里，程序就无法灵活适应不同用户和不同机器。因此，系统提供了**命令行参数**和**环境变量**两种传递信息的方式。

---

### 4-1 基本概念

#### 环境变量是什么

假设程序需要知道当前用户是谁、主目录在哪里、应该去哪些目录寻找命令。如果每个程序都自己保存这些信息，就会重复、难以修改。

于是，操作系统使用**环境变量**：环境变量就是“描述程序运行环境的名称和值”，格式为：

```text
NAME=内容
```

例如：

```text
USER=root
HOME=/root
SHELL=/bin/bash
```

其中：

- `USER`、`HOME`、`SHELL` 是变量名；
- `root`、`/root`、`/bin/bash` 是变量内容；
- `=` 用来连接名称和内容。

环境变量具有**全局属性**，这里的“全局”不是指整台机器上所有程序都共享同一份，而是指：一个进程可以把环境变量传给它创建的子进程。

例如：

```text
bash
 └── 子进程程序
      └── 更深层的子进程
```

父进程导出的环境变量会沿着这条进程关系向下继承。

> **环境变量的核心特点：父进程设置并导出后，子进程可以继承，但子进程的修改不会反过来改变父进程。**

#### bash 和两张表

用户输入命令后，需要有一个程序负责理解命令、找到要执行的程序并启动它。这个程序叫 **bash**，它是“命令行解释器”，也就是负责读取和解释命令行输入的程序。

bash 中可以理解为保存着两张重要的表：

```text
bash
├── 命令行参数表 argv
└── 环境变量表 environ
```

- `argv`：记录一次命令后面跟着的参数；
- `environ`：记录当前进程可以使用的环境变量。

例如输入：

```bash
ls -a -l
```

可以理解为：

```text
argv[0] = "ls"
argv[1] = "-a"
argv[2] = "-l"
```

而 `PATH`、`HOME`、`USER` 等信息则属于环境变量表。

#### 环境变量从哪里来

bash 启动时，需要先知道当前用户的环境设置。它会从系统配置文件中读取初始环境变量，常见文件包括：

```text
~/.bash_profile
~/.bashrc
```

- `~` 表示当前用户的主目录；
- `~/.bash_profile` 常用于登录时的配置；
- `~/.bashrc` 常用于 bash 启动时的配置。

因此，配置文件中的环境变量设置，会影响之后启动的命令和程序。

例如配置了：

```bash
export PATH=$PATH:/home/user/bin  # 把自定义程序目录加入命令搜索路径
```

之后启动的子进程就可以继承新的 `PATH`。

### 4-2 常见环境变量与命令

#### 常见环境变量

| 环境变量 | 含义 | 示例 |
|---|---|---|
| `PATH` | 命令搜索路径，多个目录用冒号分隔 | `/usr/local/bin:/usr/bin:/bin` |
| `HOME` | 当前用户的主目录 | `/home/user` |
| `SHELL` | 当前使用的命令行解释器 | `/bin/bash` |

#### PATH 如何让命令不用写完整路径

假设 `ls` 程序实际位于：

```text
/usr/bin/ls
```

如果每次执行都要写完整路径：

```bash
/usr/bin/ls  # 直接指定 ls 程序的完整位置
```

使用起来很麻烦。于是系统把常用程序所在的目录放进 `PATH`：

```text
PATH=/usr/local/bin:/usr/bin:/bin
```

当输入：

```bash
ls  # bash 会根据 PATH 搜索 ls
```

bash 会依次检查：

```text
/usr/local/bin/ls
/usr/bin/ls
/bin/ls
```

找到后就执行它。

> **PATH 本质上是 bash 查找命令的目录清单，所以系统指令通常不需要写完整路径。**

#### 添加自己的程序目录

##### 语法

```bash
export PATH=$PATH:路径
```

##### 功能

把新的目录追加到当前 `PATH` 的末尾，并导出给之后启动的子进程。

##### 示例

```bash
export PATH=$PATH:$HOME/bin  # 在 PATH 末尾加入当前用户的 bin 目录
```

如果目录中有自己的可执行程序，例如：

```text
/home/user/bin/mycmd
```

之后就可以直接输入：

```bash
mycmd  # bash 会从 PATH 中寻找 mycmd
```

##### 注意事项

不要直接覆盖原来的 `PATH`：

```bash
export PATH=$HOME/bin  # 会丢失原来的命令搜索目录
```

正确做法是使用 `$PATH` 保留旧内容：

```bash
export PATH=$PATH:$HOME/bin  # 在原 PATH 基础上追加目录
```

#### echo：显示变量内容

##### 语法

```bash
echo $变量名
```

##### 功能

显示指定变量的内容。变量名前的 `$` 表示“取出这个变量的值”。

##### 示例

```bash
echo $PATH    # 显示命令搜索路径
echo $HOME    # 显示当前用户主目录
echo $SHELL   # 显示当前使用的 shell
```

#### export：设置并导出环境变量

##### 语法

```bash
export 变量名=内容
```

##### 功能

设置变量，并让之后启动的子进程可以继承它。

##### 示例

```bash
export MYENV="hello"  # 设置并导出名为 MYENV 的环境变量
```

字符串包含空格时应使用引号：

```bash
export MESSAGE="hello linux"  # 把带空格的内容作为一个整体保存
```

#### env：显示环境变量

##### 语法

```bash
env
```

##### 功能

显示当前进程的环境变量表。

##### 示例

```bash
env  # 显示当前环境中的全部环境变量
```

变量较多时，可以配合筛选：

```bash
env | grep '^PATH='  # 只显示名称为 PATH 的环境变量
```

#### unset：清除变量

##### 语法

```bash
unset 变量名
```

##### 功能

删除当前 bash 中的指定变量。

##### 示例

```bash

```

#### set：显示本地变量和环境变量

##### 语法

```bash
set
```

##### 功能

显示当前 bash 中的变量，包括：

- 只在当前 bash 中使用的本地变量；
- 可以被子进程继承的环境变量。

##### 示例

```bash
set  # 显示当前 bash 的本地变量和环境变量
```

`set` 的输出通常比 `env` 多，因为 `env` 主要显示环境变量，而 `set` 还会显示 bash 自己的本地变量和其他信息。

### 4-3 代码获取环境变量

程序也需要读取环境变量。例如程序可以通过 `HOME` 找到用户主目录，通过 `USER` 判断当前用户名。

C 程序获取环境变量有三种方式。

#### 方式一：main 的第三个参数 `env`

##### 语法

```cpp
int main(int argc, char* argv[], char* env[])
```

这里的第三个参数 `env` 是环境变量表。

环境变量表的本质是：

```text
char* env[]
```

它是一个字符指针数组：

```text
env
├── 指向 "NAME=value"
├── 指向 "PATH=/usr/bin:/bin"
├── 指向 "HOME=/root"
└── NULL
```

每一项都是一个以 `'\0'` 结尾的字符串，最后用空指针表示表结束。

##### 完整示例

```cpp
#include <stdio.h>  // 提供 printf 函数

int main(int argc, char* argv[], char* env[])  // 接收命令行参数和环境变量表
{
    int i = 0;  // 保存当前环境变量下标

    while (env[i] != NULL)  // 环境表最后一项之后是空指针
    {
        printf("%s\n", env[i]);  // 输出一条 NAME=value 环境字符串
        i++;  // 继续访问下一项
    }

    return 0;  // 程序正常结束
}
```

编译并运行：

```bash
g++ env_main.cpp -o env_main  # 编译程序并生成 env_main
./env_main                    # 输出当前进程继承到的环境变量
```

这里的 `main` 是一种常见的原始形式：启动函数会把命令行参数表和环境变量表传给 `main`。

#### 方式二：使用 `extern char **environ`

##### 语法

```cpp
extern char** environ;
```

##### 功能

`environ` 是 C 运行库提供的全局变量，它指向当前进程的环境变量表。

这种方式不需要把环境表写成 `main` 的第三个参数。

##### 完整示例

```cpp
#include <stdio.h>  // 提供 printf 函数

extern char** environ;  // 声明 C 运行库中的环境变量表

int main()
{
    int i = 0;  // 保存当前环境变量下标

    while (environ[i] != NULL)  // 遍历环境变量表直到空指针
    {
        printf("%s\n", environ[i]);  // 输出一条环境字符串
        i++;  // 移动到下一项
    }

    return 0;  // 程序正常结束
}
```

#### 方式三：使用 `getenv`

##### 语法

```cpp
char* getenv(const char* name);
```

##### 功能

根据变量名查找一个指定的环境变量，找到后返回它的内容；如果变量不存在，返回空指针。

这是最常用的方式，因为程序通常只需要某一个变量，而不是整个环境表。

##### 完整示例

```cpp
#include <stdio.h>   // 提供 printf 函数
#include <stdlib.h>  // 提供 getenv 函数

int main()
{
    char* path = getenv("PATH");  // 查找 PATH 环境变量

    if (path != NULL)  // 判断 PATH 是否存在
    {
        printf("PATH=%s\n", path);  // 输出 PATH 的内容
    }
    else
    {
        printf("PATH not found\n");  // 变量不存在时输出提示
    }

    return 0;  // 程序正常结束
}
```

编译并运行：

```bash
g++ get_env.cpp -o get_env  # 编译读取环境变量的程序
./get_env                   # 输出 PATH 的内容
```

三种方式对比如下：

| 方式 | 获取内容 | 适合场景 |
|---|---|---|
| `main` 第三个参数 `env` | 整张环境表 | 需要遍历全部环境变量 |
| `extern char** environ` | 整张环境表 | 在程序其他位置访问环境表 |
| `getenv("NAME")` | 一个指定变量 | 只查某个变量，最常用 |

> **需要全部环境变量时遍历环境表，只需要一个变量时优先使用 `getenv`。**

#### 命令行参数的意义

程序有时需要根据用户输入的选项改变行为。例如：

```bash
ls -a -l
```

这里：

- `ls` 是要执行的程序；
- `-a` 和 `-l` 是命令行参数；
- `ls` 根据这些参数决定显示隐藏文件、显示详细信息等。

C 程序通过 `argc` 和 `argv` 获取这些参数：

- `argc`：参数总数；
- `argv`：保存参数字符串的数组；
- `argv[0]`：通常是程序名；
- `argv[1]` 及之后：用户输入的选项或其他参数。

##### 完整示例

```cpp
#include <stdio.h>  // 提供 printf 函数
#include <string.h> // 提供 strcmp 函数

int main(int argc, char* argv[])  // 接收命令行参数
{
    int show_all = 0;  // 保存是否显示全部文件的选项
    int long_format = 0;  // 保存是否使用详细格式的选项

    for (int i = 1; i < argc; i++)  // 从 argv[1] 开始检查用户参数
    {
        if (strcmp(argv[i], "-a") == 0)  // 判断参数是否为 -a
        {
            show_all = 1;  // 开启显示全部内容的功能
        }
        else if (strcmp(argv[i], "-l") == 0)  // 判断参数是否为 -l
        {
            long_format = 1;  // 开启详细格式功能
        }
    }

    printf("show all: %s\n", show_all ? "yes" : "no");  // 输出 -a 是否存在
    printf("long format: %s\n", long_format ? "yes" : "no");  // 输出 -l 是否存在

    return 0;  // 程序正常结束
}
```

编译并运行：

```bash
g++ options.cpp -o options  # 编译参数解析程序
./options -a -l              # 把 -a 和 -l 传给程序
```

命令行参数的本质是：让同一个程序通过不同输入执行不同功能，而不是为每种功能编写一个新程序。

> **命令行参数是程序实现选项功能的入口，`argc/argv` 负责告诉程序用户输入了哪些选项。**

### 4-4 全局属性实验

#### 本地变量不会被子进程继承

在 bash 中直接写：

```bash
a=10  # 创建只属于当前 bash 的本地变量
```

此时变量存在于当前 bash 内部，但没有被导出。启动一个子进程查看环境变量：

```bash
a=10        # 在当前 bash 中设置本地变量
env | grep '^a='  # 在环境变量表中查找 a
```

通常没有输出，因为 `a` 只是 bash 的本地变量，不属于环境变量表。

可以再启动一个程序验证：

```bash
cat > check_a.cpp <<'EOF'  # 创建用于检查 a 的 C++ 源文件
#include <stdio.h>         // 提供 printf 函数
#include <stdlib.h>        // 提供 getenv 函数

int main()
{
    char* value = getenv("a");  // 从环境表中查找 a

    if (value != NULL)  // 判断 a 是否存在
    {
        printf("a=%s\n", value);  // 输出 a 的值
    }
    else
    {
        printf("a not found\n");  // a 不在环境表中
    }

    return 0;  // 程序正常结束
}
EOF

g++ check_a.cpp -o check_a  # 编译检查程序
a=10                        # 设置当前 bash 的本地变量
./check_a                   # 子进程无法读取未导出的 a
```

#### export 后子进程可以读取

##### 语法

```bash
export 变量名=内容
```

##### 实验

```bash
export MYENV="hello"  # 设置并导出 MYENV
env | grep '^MYENV='  # 查看 MYENV 是否进入环境变量表
./check_a             # 这里只检查 a，无法检查 MYENV
```

为了检查 `MYENV`，使用下面的程序：

```cpp
#include <stdio.h>   // 提供 printf 函数
#include <stdlib.h>  // 提供 getenv 函数

int main()
{
    char* value = getenv("MYENV");  // 从环境表中查找 MYENV

    if (value != NULL)  // 判断 MYENV 是否存在
    {
        printf("MYENV=%s\n", value);  // 输出 MYENV 的值
    }
    else
    {
        printf("MYENV not found\n");  // MYENV 不在环境表中
    }

    return 0;  // 程序正常结束
}
```

编译并实验：

```bash
g++ check_myenv.cpp -o check_myenv  # 编译检查程序
MYENV="hello"                       # 只设置本地变量
./check_myenv                       # 子进程通常读不到 MYENV
export MYENV="hello"                # 设置并导出 MYENV
./check_myenv                       # 子进程可以读到 MYENV=hello
```

这个实验说明：

```text
bash 中的变量
├── 未 export：只在当前 bash 中存在
└── 已 export：进入环境表，可被子进程继承
```

> **`export` 的作用不是简单地“给变量赋值”，而是把变量放入子进程可以继承的环境表。**

#### export 是 bash 内建命令

有些命令是独立的可执行程序，例如：

```bash
ls  # bash 根据 PATH 找到并启动 ls 程序
```

而 `export` 是 **bash 内建命令**，也就是 bash 内部已经实现好的功能函数。

它不能通过启动一个普通子进程完成。原因是：如果 `export` 在子进程中修改变量，子进程结束后，父 bash 的变量不会改变。

执行：

```bash
type export  # 查看 export 的命令类型
type ls      # 查看 ls 的命令类型
```

通常会看到：

```text
export is a shell builtin
ls is aliased to ... 或 ls is /usr/bin/ls
```

`export` 的工作过程可以理解为：

```text
用户输入 export MYENV=hello
        ↓
bash 自己调用内部函数
        ↓
修改 bash 自己的环境变量表
        ↓
之后启动的子进程继承 MYENV
```

> **必须修改当前 bash 自己的数据时，命令就不能只依靠普通子进程，`export` 因此是 bash 的内建命令。**

#### 使用 getenv 判断身份的权限思想实验

假设想写一个程序，只有指定用户才能执行。程序可以读取 `USER` 环境变量：

```cpp
#include <stdio.h>   // 提供 printf 函数
#include <stdlib.h>  // 提供 getenv 函数
#include <string.h>  // 提供 strcmp 函数

int main()
{
    char* user = getenv("USER");  // 获取当前环境中的用户名

    if (user == NULL)  // 判断 USER 是否存在
    {
        printf("cannot identify user\n");  // 无法确认身份
        return 1;  // 返回失败状态
    }

    if (strcmp(user, "alice") != 0)  // 判断当前用户名是否为 alice
    {
        printf("permission denied\n");  // 非指定用户时拒绝执行
        return 1;  // 返回失败状态
    }

    printf("program started\n");  // 指定用户通过检查后执行功能
    return 0;  // 程序正常结束
}
```

编译运行：

```bash
g++ only_alice.cpp -o only_alice  # 编译身份判断程序
./only_alice                      # 根据 USER 的内容决定是否允许执行
```

这个实验体现的是“先读取环境信息，再决定程序行为”的思想。

但要注意，`USER` 只是一个环境变量，普通用户可能通过 `export USER=alice` 修改它，因此它不能作为真正可靠的安全认证依据。真正的权限控制应依靠操作系统的用户身份和文件权限。

> **环境变量可以帮助程序了解运行环境，但仅凭 `getenv("USER")` 做安全认证并不可靠。**

## 5. 程序地址空间

程序运行时会使用很多地址：函数地址、全局变量地址、`malloc` 返回的地址、局部变量地址等。问题是：这些地址到底对应哪块物理内存？不同进程之间为什么可以使用相同的地址而互不干扰？

---

### 5-1 布局与验证

#### 1. 先区分两种“地址空间”

**物理内存**：电脑中真正的内存条空间。  
**虚拟地址空间**：操作系统给每个进程安排的一套“地址地图”，进程平时看到的地址属于这张地图，而不是内存条的真实编号。

如果程序直接使用物理地址，就会遇到两个问题：

- 不同程序可能访问同一块内存，互相破坏；
- 程序必须知道自己被加载到物理内存的哪个位置，难以运行。

所以操作系统让每个进程先使用自己的虚拟地址空间，再负责把虚拟地址转换成物理地址。

#### 2. 32 位和 64 位地址空间

32 位地址由 32 个二进制位组成，因此一共可以表示：

```text
2^32 = 4GB
```

在典型的 32 位 Linux 划分中：

```text
4GB 地址空间
├── 1GB 内核空间
└── 3GB 用户空间
```

用户程序通常只能使用用户空间，内核空间由操作系统使用。

64 位地址理论上可以表示：

```text
2^64 个地址
```

但实际 CPU 和操作系统通常不会把全部 `2^64` 地址都拿来使用。

> **32 位平台的典型划分是 1GB 内核空间 + 3GB 用户空间；这些是虚拟地址空间，不是物理内存大小。**

#### 3. 从低地址到高地址的布局

一个进程的用户空间通常从低地址到高地址排列如下：

```text
低地址
│
├── 代码段：函数机器指令
├── 已初始化数据段：有初始值的全局变量、静态变量
├── 未初始化数据段 bss：没有显式初始值的全局变量、静态变量
├── 堆：malloc、new 动态申请的空间，通常向高地址增长
├── 共享区：动态库等多个进程可以共同使用的代码区域
├── 栈：函数参数、局部变量等，通常向低地址增长
├── 命令行参数和环境变量
└── 内核空间
高地址
```

堆和栈从相反方向增长：

```text
低地址
│
│  堆向上增长
│       ↑
│      堆
│
│      栈
│       ↓
│  栈向下增长
│
高地址
```

这里的“向上”和“向下”说的是地址数值变化：

- 堆申请新空间时，地址通常越来越大；
- 栈继续使用空间时，局部变量地址通常越来越小。

实际布局会受到系统、编译器和地址随机化影响，但整体关系通常符合上图。

#### 4. 用程序验证布局

下面的程序分别打印代码、全局变量、堆、栈、命令行参数和环境变量的地址。

```cpp
#include <cstdio>      // 提供 printf
#include <cstdlib>     // 提供 malloc 和 free

int g_init = 10;       // 已初始化的全局变量，通常位于数据段
int g_uninit;          // 未初始化的全局变量，通常位于 bss 段

void code_function()   // 函数代码位于代码段
{
}

int main(int argc, char* argv[], char* envp[])
{
    int stack_var = 20;                    // 局部变量，通常位于栈
    void* heap1 = malloc(1);               // 从堆申请第一块空间
    void* heap2 = malloc(1);               // 从堆申请第二块空间

    printf("code   : %p\n", (void*)code_function); // 打印代码段地址
    printf("global : %p\n", (void*)&g_init);       // 打印全局变量地址
    printf("bss    : %p\n", (void*)&g_uninit);     // 打印 bss 地址
    printf("heap1  : %p\n", heap1);                // 打印第一块堆空间地址
    printf("heap2  : %p\n", heap2);                // 打印第二块堆空间地址
    printf("stack  : %p\n", (void*)&stack_var);    // 打印栈变量地址
    printf("argv   : %p\n", (void*)argv);          // 打印命令行参数地址
    printf("env    : %p\n", (void*)envp);          // 打印环境变量地址

    free(heap1);                                 // 释放第一块堆空间
    free(heap2);                                 // 释放第二块堆空间
    return 0;                                    // 正常结束程序
}
```

编译并运行：

```bash
g++ -o layout layout.cpp             # 编译布局验证程序
./layout hello                       # 运行程序，并传入一个命令行参数
```

典型结果会表现为：

```text
code   : 较小地址
global : 比 code 大
bss    : 比 global 大
heap1  : 比 bss 大
heap2  : 通常比 heap1 大
stack  : 比 heap 大
argv   : 接近 stack
env    : 接近 argv
```

连续调用 `malloc` 时，返回地址通常向高地址方向变化；连续创建局部变量时，变量地址通常向低地址方向变化。不过，堆分配器可能复用旧空间，不能把“每次一定连续”当成语言保证。

地址每次运行可能不同，这是地址随机化等机制造成的，不影响区域之间的整体关系。

> **程序中看到的代码、全局变量、堆、栈地址，全部属于虚拟地址；它们不是内存条上的物理地址。**

### 5-2 虚拟地址实验

#### 1. fork 后地址相同但内容不同

假设有一个全局变量 `g_val`。父进程和子进程都打印它的地址，然后子进程把它改成 `100`：

```cpp
#include <cstdio>      // 提供 printf
#include <unistd.h>    // 提供 fork
#include <sys/wait.h>  // 提供 waitpid

int g_val = 0;         // 父子进程都会看到的全局变量

int main()
{
    pid_t pid = fork();                         // 创建子进程

    if (pid < 0) {                             // 判断 fork 是否失败
        return 1;                              // 失败时退出
    }

    if (pid == 0) {                            // 子进程执行这里
        printf("child: address=%p, value=%d\n", // 打印子进程中的地址和值
               (void*)&g_val, g_val);
        g_val = 100;                           // 子进程修改自己的变量副本
        printf("child: address=%p, value=%d\n", // 再次打印修改后的结果
               (void*)&g_val, g_val);
        return 0;                              // 子进程结束
    }

    waitpid(pid, nullptr, 0);                  // 父进程等待子进程结束
    printf("parent: address=%p, value=%d\n",    // 打印父进程中的地址和值
           (void*)&g_val, g_val);
    return 0;                                  // 父进程结束
}
```

编译并运行：

```bash
g++ -o fork_addr fork_addr.cpp       # 编译实验程序
./fork_addr                          # 运行父子进程实验
```

典型结果类似：

```text
child:  address=0x..., value=0
child:  address=0x..., value=100
parent: address=0x..., value=0
```

现象分成两部分：

1. 父子进程中 `&g_val` 的数值相同；
2. 子进程修改后变成 `100`，父进程仍然是 `0`。

#### 2. 从实验结果进行推理

推理链如下：

```text
父子进程中的内容不同
        ↓
它们绝对不是同一个物理变量
        ↓
但打印出来的地址数值相同
        ↓
这个地址不可能直接代表物理地址
        ↓
C/C++ 程序使用的地址都是虚拟地址
```

如果这个地址是物理地址，那么父子进程修改同一个地址后，父进程也应该看到 `100`。但实际父进程仍然看到 `0`，说明相同的地址数值在不同进程中可以指向不同的物理内存。

物理地址由操作系统统一管理，普通用户程序不能直接看到和随意修改。

> **C/C++ 中看到的地址是虚拟地址；物理地址对用户程序隐藏，由操作系统负责管理。**

#### 3. 页表：完成地址转换

**页表**：记录“某个虚拟地址对应哪一个物理地址”的映射表。

```text
进程使用的虚拟地址
        │
        ▼
      页表
        │
        ▼
实际物理地址
```

每个进程通常拥有：

```text
1 个进程
├── 1 个虚拟地址空间
└── 1 套页表
```

因此，父进程和子进程可以拥有相同的虚拟地址数值，但各自的页表可以把它们映射到不同的物理内存。

#### 4. 写时拷贝

**写时拷贝**：刚创建子进程时先共享同一份物理数据，只有某一方真正修改时，操作系统才复制一份。

`fork` 刚完成时，可以理解为：

```text
父进程虚拟地址 g_val ──父页表──┐
                                ├── 同一个物理页
子进程虚拟地址 g_val ──子页表──┘
```

此时父子进程都可以读取相同内容。

当子进程执行：

```cpp
g_val = 100;
```

操作系统会完成以下过程：

```text
子进程尝试写入
      ↓
发现该物理页当前被父子共享
      ↓
复制出一个新的物理页
      ↓
把子进程页表改为指向新页
      ↓
子进程修改新页，父进程仍使用原页
```

最终关系变为：

```text
父进程虚拟地址 g_val ──父页表──> 物理页 A，内容为 0

子进程虚拟地址 g_val ──子页表──> 物理页 B，内容为 100
```

所以父子进程看见的虚拟地址可以相同，但修改后仍然互不影响。

> **写时拷贝让父子进程先共享、修改时再分离，从而同时节省资源并保持进程独立性。**

这里的“进程独立性”包括两层：

- 内核中的进程管理数据结构彼此独立；
- 进程使用的代码和数据在修改后彼此独立。

### 5-3 如何理解（两个类比）

#### 1. 大富翁类比

大富翁对 4 个私生子分别承诺：

```text
“我给你 10 亿元。”
```

于是 4 个孩子都认为自己拥有 10 亿元。但如果他们同时真的去银行取钱，大富翁才需要想办法兑现。

进程也类似：

```text
每个进程都认为自己独占一整套 4GB 虚拟地址空间
```

但这不代表系统已经为每个进程准备了完整的 4GB 物理内存。只有程序真正访问某个地址时，操作系统才根据需要准备物理内存和映射关系。

从操作系统实现角度看，虚拟地址空间的本质不是一块真实内存，而是一个描述地址区域的数据结构：

```cpp
struct mm_struct
{
    // 描述代码区、堆、栈等虚拟区域
};
```

> **虚拟地址空间的本质是一个描述进程地址布局的数据结构，而不是一块提前分配好的物理内存。**

#### 2. “38 线”类比

地图上划分一块区域，并不需要把区域内每一平方米都单独记录，只要知道边界：

```text
区域 = 起始位置 + 结束位置
```

虚拟内存区域也一样。比如代码段只需要记录：

```text
start_code
end_code
```

堆可以记录：

```text
start_brk
brk
```

栈可以记录：

```text
start_stack
```

调整区域时，本质上主要是修改这些数值，而不是搬运整块数据。例如扩大堆，通常就是把堆的结束地址向高处调整。

### 5-4 `mm_struct` 与 VMA

#### 1. `mm_struct`

**`mm_struct`**：描述一个进程虚拟地址空间整体情况的内核数据结构。

每个进程有一个 `task_struct`。`task_struct` 是操作系统描述进程的结构体；其中有一个指针指向该进程的 `mm_struct`：

```text
task_struct
    │
    └── mm ──> mm_struct
                 ├── 代码区边界
                 ├── 数据区边界
                 ├── 堆边界
                 ├── 栈边界
                 └── 虚拟区域管理信息
```

通常可以理解为：

```text
一个进程 = 一个 task_struct + 一个 mm_struct + 一套页表
```

#### 2. VMA：描述一块具体区域

**VMA（Virtual Memory Area，虚拟内存区域）**：描述虚拟地址空间中一段连续区域的数据结构。

例如，一个进程可能拥有这些 VMA：

```text
VMA 1：代码段
VMA 2：数据段
VMA 3：堆
VMA 4：动态库区域
VMA 5：栈
```

每个 VMA 通常记录：

```text
起始地址
结束地址
访问权限：可读、可写、可执行
区域用途
```

#### 3. VMA 的两种组织方式

Linux 同时用两种方式管理 VMA：

| 组织方式 | 作用 | 优点 |
|---|---|---|
| 单链表，`mmap` 指向 | 按地址顺序串起来 | 结构简单，占用空间少 |
| 红黑树，`mm_rb` 管理 | 按地址组织起来查找 | 区域很多时查找更快 |

**红黑树**：一种能够保持较平衡高度的二叉搜索树，适合快速查找。

两种方式并存，是因为它们各有侧重：

1. 虚拟区域较少时，用链表就足够，能够减少额外内存；
2. 虚拟区域较多时，用红黑树查找更快，能够减少查找时间。

> **VMA 同时用链表和红黑树组织：链表节省空间，红黑树加快查找。**

#### 4. `mm_struct` 如何初始化

程序启动时，操作系统需要知道代码段、数据段、堆、栈等区域在哪里。

这些区域的初始信息来自可执行程序文件的加载信息。操作系统加载可执行程序时，读取其中记录的区域范围和权限，然后填写进程的 `mm_struct`，并建立相应的 VMA。

```text
可执行程序文件
        ↓ 加载区域信息
mm_struct
        ↓
多个 VMA
        ↓
建立虚拟地址到物理地址的映射
```

#### 5. 创建进程不一定立刻加载代码和数据

创建进程时，可以先完成：

```text
task_struct
mm_struct
页表
```

并不要求此刻已经把所有代码和数据都加载进物理内存。

因为虚拟地址空间可以先记录“未来允许使用哪些地址”，等程序真正访问某一页时，再按需分配物理内存并建立页表映射。

这就是“地址空间的描述”和“物理内存的实际占用”可以分离的原因。

### 5-5 为什么要有虚拟地址空间

#### 1. 直接使用物理内存的三个问题

假设每个程序都直接使用物理地址，会产生以下麻烦。

##### 问题一：安全风险

恶意程序如果知道物理地址，就可能直接修改其他程序甚至操作系统的数据：

```text
程序 A 直接写物理地址
        ↓
修改程序 B 的数据
        ↓
甚至破坏内核数据
```

这样任何程序都可能破坏整个系统。

##### 问题二：地址不确定

程序每次运行时，可能被加载到不同的物理位置：

```text
第一次运行：代码在物理地址 1000
第二次运行：代码在物理地址 8000
```

如果程序内部直接写死物理地址，那么换一个位置就无法运行。

##### 问题三：换出效率低

**换出**：内存紧张时，把暂时不用的数据从内存保存到磁盘。

如果程序直接占用一整块连续物理内存，那么换出时可能需要整体搬运大量数据，效率很低。程序越大，搬运成本越高。

#### 2. 虚拟地址空间的三个收益

##### 收益一：地址从无序变有序

物理内存可能被多个程序分散占用，空闲区域不连续：

```text
物理内存：
已用 | 空闲 | 已用 | 空闲 | 已用
```

虚拟地址空间可以为程序提供整齐、连续的地址布局：

```text
虚拟地址空间：
代码 → 数据 → 堆 → 共享区 → 栈
```

程序只需要面对这套有序地图，不需要关心物理内存到底分散在哪里。

##### 收益二：地址转换时进行合法性检查

程序访问虚拟地址时，CPU 和操作系统会检查页表中的映射和权限。

例如，程序试图修改只读的常量区：

```text
程序写入常量区
        ↓
地址转换和权限检查
        ↓
发现该区域不可写
        ↓
拦截访问，程序崩溃
```

这样程序不能随意修改任意物理内存。常见的野指针错误，也会在访问无效区域时被拦截，而不是悄悄破坏系统数据。

##### 收益三：进程管理和内存管理解耦

**解耦**：两个部分彼此分开，修改其中一个不必影响另一个。

程序只申请虚拟地址：

```cpp
int* p = new int;       // 先申请虚拟地址空间
```

操作系统不一定立刻为它准备对应的物理内存。等程序真正访问 `*p` 时，操作系统才分配物理页并建立映射：

```text
new / malloc
    ↓
先得到虚拟地址
    ↓
真正访问该地址
    ↓
操作系统按需分配物理页
    ↓
建立页表映射
```

因此：

- 物理内存可以把程序加载到任意空闲位置；
- 程序不需要知道物理地址；
- 物理内存可以按页分配、换出和回收；
- 用户程序通常感觉不到底层物理内存的变化。

> **虚拟地址空间在进程和物理内存之间扩展了一层：进程只使用虚拟地址，不直接接触物理地址。**
