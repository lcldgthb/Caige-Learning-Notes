## **一、先建立整体认知：什么是进程间通信？**

### **1.1 为什么需要进程间通信？**

先回忆一下之前学过的进程知识。

我们知道：

- 进程是操作系统进行资源分配的基本单位。
- 每个进程都有自己独立的虚拟地址空间。
- 一个进程不能直接访问另一个进程的私有地址空间。

例如：

**进程 A**

# **进程 A**

自己的虚拟地址空间

# **100**

变量 num

地址空间相互隔离，不能直接访问

**进程 B**

# **进程 B**

自己的虚拟地址空间

# **200**

变量 num

假设：

- 进程 A 负责计算数据。
- 进程 B 负责处理数据。

那么问题来了：

**进程 A 计算出结果后，如何把结果交给进程 B？**

这就是进程间通信（IPC，Inter-Process Communication）要解决的问题。

IPC 本质上就是：**让不同进程之间能够交换数据、协调工作。**

### **1.2 进程间通信的目的**

主要有三个：

1. **数据传输**：一个进程把数据发送给另一个进程。
2. **资源共享**：多个进程共同访问一份资源。
3. **进程控制与协同**：多个进程之间相互通知、同步执行顺序。

举个实际例子：

假设一个服务器程序：

- 进程 A：接收客户端请求。
- 进程 B：处理业务逻辑。
- 进程 C：负责写入日志。

这几个进程需要交换数据、协调工作，就需要 IPC。

### **1.3 进程间通信的发展**

这里了解发展脉络即可：

- 早期：通过文件等方式交换数据。
- 后来：出现管道等机制。
- 再后来：出现 System V IPC（共享内存、消息队列、信号量）。
- 现代 Linux：还广泛使用 Socket、内存映射等机制。

注意：这些方式不是简单的淘汰关系，而是各有适用场景。

### **1.4 进程间通信的分类**

这是本节最重要的知识地图。

Linux 常见 IPC 方式：

**进程间通信 IPC**

**管道**

匿名管道

命名管道

**System V IPC**

共享内存

消息队列

信号量

**网络通信**

Socket

**其他方式**

内存映射等

接下来重点学习：

| 方式   | 核心思想              |
| ---- | ----------------- |
| 匿名管道 | 通过内核中的缓冲区传递数据     |
| 命名管道 | 有名字的管道，不要求进程有亲缘关系 |
| 共享内存 | 多个进程直接访问同一块物理内存   |
| 消息队列 | 通过内核维护的消息结构传递数据   |
| 信号量  | 控制多个进程对共享资源的访问    |

先记住一个关键区别：

**管道和消息队列偏向于数据传递；共享内存偏向于数据共享；信号量偏向于同步与互斥。**

# **二、管道（Pipe）**

管道是 Linux 中非常经典的一种 IPC 方式。

先理解一个生活中的例子：

两个人之间有一根水管。

- A 往水管里面放水。
- B 从水管另一端取水。
- 水管负责传输。

Linux 管道也是类似的思想：

- 一个进程写入数据。
- 另一个进程读取数据。
- 内核负责在中间传递数据。

## **2.1 管道的本质**

**管道是内核提供的一段缓冲区，用于实现进程之间的数据传输。**

这里要特别注意：

管道不是两个进程之间直接传递变量，也不是一个进程直接读取另一个进程的内存。

实际过程是：

1. 进程 A 调用 write()。
2. 数据从进程 A 的用户空间复制到内核管道缓冲区。
3. 进程 B 调用 read()。
4. 数据从内核管道缓冲区复制到进程 B 的用户空间。

## **管道的数据流动过程**

**进程 A 用户空间**

write("hello")

**内核空间：管道缓冲区**

# **hello**

暂存传输的数据

**进程 B 用户空间**

read() 读取数据

这个过程也说明了一个重要知识点：

**管道是半双工通信的。**

也就是通常一个管道负责一个方向的数据传输：

- A → B
- 如果想要 B → A，通常再创建一条管道。

# **三、匿名管道（Anonymous Pipe）**

这是本节第一个重点，也是后面理解命名管道的基础。

## **3.1 什么是匿名管道？**

匿名管道就是没有文件名的管道。

它有一个非常重要的特点：

**通常用于具有亲缘关系的进程之间通信，例如父子进程。**

为什么通常是父子进程？

因为匿名管道创建后，返回两个文件描述符，父进程可以通过 fork() 创建子进程，而子进程会继承父进程的文件描述符。

这样父子进程就能访问同一个管道。

## **3.2 创建匿名管道：pipe()**

Linux 提供 pipe() 系统调用。

```
int pipe(int pipefd[2]);
```

成功返回 0，失败返回 -1。

参数 `pipefd` 是一个数组，里面有两个文件描述符：

```
int pipefd[2];
pipe(pipefd);
```

**pipe() 创建的两个文件描述符**

# **pipefd[0]**

**读端**

read()

# **pipefd[1]**

**写端**

write()

**数据流向：pipefd[1] → pipefd[0]**

记忆方法：

- `pipefd[0]`：0 对应标准输入 stdin，读。
- `pipefd[1]`：1 对应标准输出 stdout，写。

注意：这里是记忆辅助，真正决定读写方向的是 pipe() 的接口规定。

## **3.3 实例代码：父子进程通过匿名管道通信**

下面看一个完整实例。

需求：

- 父进程创建管道。
- 父进程 fork() 创建子进程。
- 子进程向管道写入数据。
- 父进程从管道读取数据。

```

#include &lt;stdio.h&gt;
#include &lt;unistd.h&gt;
#include &lt;string.h&gt;
#include &lt;sys/wait.h&gt;
int main()
{
    int pipefd[2];
    // 创建匿名管道：pipefd[0]读，pipefd[1]写
    if (pipe(pipefd) == -1)
    {
        perror("pipe");
        return 1;
    }
    pid_t id = fork();
    if (id == -1)
    {
        perror("fork");
        return 1;
    }
    if (id == 0)
    {
        // 子进程只负责写入，关闭不需要的读端
        close(pipefd[0]);
        const char *msg = "hello father";
        write(pipefd[1], msg, strlen(msg));
        close(pipefd[1]);
        return 0;
    }
    else
    {
        // 父进程只负责读取，关闭不需要的写端
        close(pipefd[1]);
        char buffer[128] = {0};
        ssize_t n = read(pipefd[0], buffer, sizeof(buffer) - 1);
        if (n > 0)
            printf("father read: %s\n", buffer);
        close(pipefd[0]);
        waitpid(id, NULL, 0);
    }
    return 0;
}

```

预期输出：

```
father read: hello father
```

这段代码有三个重点：

1. `pipe()` 必须在 `fork()` 之前调用，才能让子进程继承管道文件描述符。
2. 子进程关闭读端，父进程关闭写端。
3. 使用完毕后关闭文件描述符，避免资源泄漏。

这里特别强调：`read()` 返回的是实际读取的字节数，不保证一次就读完所有数据。这个简单例子只发送一条短消息，所以足够演示原理。

## **3.4 用 fork() 来共享管道：为什么父子进程可以通信？**

这是理解匿名管道最关键的原理。

你之前学习过 fork()，应该还记得：

**fork() 创建子进程时，子进程会继承父进程的文件描述符。**

现在把这个知识和 pipe() 联系起来。

假设：

```
int pipefd[2];
pipe(pipefd);
fork();
```

执行过程如下：

## **fork() 前后文件描述符的变化**

**fork() 之前：父进程**

fd 3：读端

fd 4：写端

**fork()**

**父进程**

fd 3：读端

fd 4：写端

**子进程**

fd 3：读端

fd 4：写端

**同一个内核管道对象**

## **共享管道缓冲区**

父子进程的文件描述符最终指向同一个管道

注意一个细节：

父子进程各自拥有自己的文件描述符表，但是对应的文件描述符引用的是同一个内核管道对象。

因此：

- 父进程向 fd 4 写入。
- 子进程可以通过 fd 3 读取。
- 不需要复制一份管道缓冲区给子进程。

这就是匿名管道能够实现父子进程通信的原因。

## **3.5 站在文件描述符角度，深度理解管道**

还记得之前学过的 Linux 基础 IO 吗？

当时我们学习了：

- 文件描述符 fd。
- 进程的文件描述符表。
- `struct file`。
- `file_operations`。
- 一切皆文件。

现在这些知识全部串起来了。

普通文件和管道虽然用途不同，但是 Linux 可以通过统一的文件 IO 接口访问它们。

例如：

```
write(fd, buffer, size);
read(fd, buffer, size);
close(fd);
```

对于普通文件，fd 指向对应的文件对象。

对于管道，fd 指向管道对应的内核对象。

**重点：文件描述符只是一个整数索引，它不是文件本身，而是用来找到内核中对应对象的入口。**

## **3.6 站在内核角度：管道的本质**

进一步深入内核。

管道的核心是内核维护的一块缓冲区。

可以把它理解为一个循环队列：

- 写入数据时，数据进入缓冲区。
- 读取数据时，数据从缓冲区取出。
- 缓冲区满了，写入可能阻塞。
- 缓冲区空了，读取可能阻塞。

注意：管道不是磁盘文件。它的核心数据缓冲区位于内核内存中，不是把数据先写入磁盘再读取。

这也解释了为什么管道可以通过 read()、write() 操作，却不需要真实的磁盘文件。

## **3.7 管道样例**

### **3.7.1 测试管道读写**

Linux 命令行中最常见的管道：

```
ls | grep ".c"
```

这里：

- `ls`：列出目录内容。
- `grep ".c"`：筛选包含 `.c` 的内容。
- `|`：创建管道，把前一个命令的标准输出连接到后一个命令的标准输入。

**ls 进程**

标准输出 stdout

**内核管道**

缓冲区

**grep 进程**

标准输入 stdin

这就是 Linux Shell 中管道符 `|` 的工作原理。

它实际上也是通过创建子进程、创建管道、重定向文件描述符等操作完成的。

### **3.7.2 创建进程池处理任务**

这个例子有一定的工程意义。

假设一个程序需要处理 100 个任务。

如果只使用一个进程：

```
主进程
  ├── 任务1
  ├── 任务2
  ├── 任务3
  └── ...
```

如果创建多个子进程：

```
             父进程
          /    |    \
        子1   子2   子3
        /      |      \
      任务    任务    任务
```

可以让父进程负责分配任务，子进程负责执行任务。

管道可以用来实现父子进程之间的任务分发和结果回传。

不过要注意：**管道只是通信手段，进程池是一种并发任务管理设计。**

如果想实现双向通信，通常需要两条管道。

## **3.8 管道读写规则（重点）**

这是考试和实际编程都很重要的内容。

管道读写有四种典型情况：

| 情况       | 结果                                |
| -------- | --------------------------------- |
| 管道为空，有写端 | read() 阻塞等待                       |
| 管道有数据    | read() 读取数据                       |
| 管道满了，有读端 | write() 阻塞等待                      |
| 管道没有读端   | 写入触发 SIGPIPE，通常进程终止；忽略信号时返回 EPIPE |

还有两个非常重要的规则：

**规则一：读端关闭后，写端继续写入。**

会产生 `SIGPIPE` 信号。如果程序忽略或处理了该信号，write() 会返回 -1，错误码为 `EPIPE`。

**规则二：所有写端关闭后，读端继续读取。**

当管道缓冲区中的数据被读完，read() 返回 0，表示 EOF（文件结束）。

注意：只关闭一个进程的写端，不一定会产生 EOF。必须所有引用该管道的写端都关闭。

### **一个重要概念：PIPE_BUF**

管道还有一个容易混淆的知识点：

`PIPE_BUF` 是保证原子写入的最大字节数。

当多个进程同时向一个管道写入数据时：

- 单次写入不超过 `PIPE_BUF`，可以保证这次写入不会与其他写入交错。
- 超过 `PIPE_BUF`，不保证原子性。

注意：`PIPE_BUF` 不等于管道缓冲区的总容量。

## **3.9 管道的特点**

总结一下：

1. **半双工通信**：通常一个管道只负责一个方向的数据传输。
2. **面向字节流**：没有消息边界，读取时不保证一次读到一条完整消息。
3. **具有亲缘关系的进程通信**：匿名管道通常用于父子进程等有继承关系的进程。
4. **生命周期随引用关闭而结束**：匿名管道没有独立的文件名。
5. **自带同步行为**：空管道读取、满管道写入时可能阻塞。

# **四、命名管道（FIFO）**

匿名管道存在一个局限：

**通常只能用于具有亲缘关系的进程之间通信。**

那么，如果两个完全独立的进程想要通信怎么办？

例如：

```
进程 A：一个独立运行的服务程序
进程 B：另一个独立运行的客户端程序
```

它们没有通过 fork() 建立父子关系，怎么办？

这时候就可以使用命名管道。

## **4.1 什么是命名管道？**

命名管道（Named Pipe），也叫 FIFO。

它与匿名管道最大的区别：

**命名管道在文件系统中有一个对应的路径名，两个无亲缘关系的进程可以通过这个路径访问同一个管道。**

例如：

```
/tmp/myfifo
```

注意：

它虽然在文件系统中有名字，但它不是普通文件，数据仍然通过内核中的管道缓冲区传输，不会像普通文件那样持久化保存。

## **命名管道通信**

**进程 A**

独立进程

write()

**进程 B**

独立进程

read()

都通过路径打开

**/tmp/myfifo**

## **FIFO 管道**

内核管道对象和缓冲区

## **4.2 创建命名管道**

有两种常见方式：

**方式一：命令行创建**

```
mkfifo myfifo
```

查看：

```
ls -l myfifo
```

如果权限信息开头显示 `p`，就表示它是 FIFO 类型。

**方式二：代码创建**

```
#include <sys/types.h>
#include <sys/stat.h>
int main()
{
    // 创建命名管道，权限为所有者读写、同组和其他用户只读
    if (mkfifo("myfifo", 0644) == -1)
    {
        perror("mkfifo");
        return 1;
    }
    return 0;
}
```

## **4.3 匿名管道与命名管道的区别**

| 对比     | 匿名管道    | 命名管道     |
| ------ | ------- | -------- |
| 是否有名字  | 没有      | 有        |
| 文件系统路径 | 没有      | 有        |
| 通信进程   | 通常有亲缘关系 | 可以无亲缘关系  |
| 创建方式   | pipe()  | mkfifo() |
| 数据传输   | 内核缓冲区   | 内核缓冲区    |
| 通信方式   | 半双工     | 通常半双工    |

记忆重点：**匿名管道依靠 fork() 继承文件描述符；命名管道依靠文件系统中的路径建立联系。**

## **4.4 命名管道的打开规则**

这里有一个很重要的知识点。

命名管道的 `open()` 存在阻塞规则：

| 打开方式              | 行为                 |
| ----------------- | ------------------ |
| 只读打开 O_RDONLY     | 默认阻塞，等待写端打开        |
| 只写打开 O_WRONLY     | 默认阻塞，等待读端打开        |
| 只读打开 + O_NONBLOCK | 没有写端时也可以打开         |
| 只写打开 + O_NONBLOCK | 没有读端时打开失败，返回 ENXIO |

为什么会这样？

因为 FIFO 的设计目标是让读写双方建立通信关系。

如果只有读端，没有写端，那么读端通常需要等待写端到来。

反过来也一样。

## **4.5 实例：用命名管道实现文件拷贝**

这里理解一下整体设计：

```
读取源文件
    ↓
进程 A
    ↓ write()
命名管道
    ↓ read()
进程 B
    ↓ write()
目标文件
```

本质上就是：

一个进程负责读取源文件并写入 FIFO，另一个进程负责从 FIFO 读取并写入目标文件。

这和普通文件拷贝最大的区别是：中间多了一条 IPC 通道。

## **4.6 实例：用命名管道实现 Server & Client**

这是命名管道非常典型的应用。

假设：

- Server 创建 FIFO，等待客户端发送消息。
- Client 打开 FIFO，向 Server 发送消息。
- Server 收到消息后进行处理。

需要注意：如果 Server 和 Client 都需要双向通信，通常设计两条 FIFO，分别负责两个方向。

例如：

```
Client  ── FIFO 1 ──> Server
Client  <── FIFO 2 ── Server
```

到这里，管道部分就结束了。

**管道的核心思想：通过内核缓冲区实现数据传输。**

接下来要学习一种效率更高的 IPC 方式：共享内存。

# **五、System V 共享内存（重点）**

这是整节课最值得深入理解的部分之一。

前面学的管道有一个特点：

数据从进程 A 的用户空间复制到内核缓冲区，再从内核缓冲区复制到进程 B 的用户空间。

这就意味着数据至少经历两次复制。

那么，有没有办法减少这种数据复制？

有，这就是共享内存。

## **5.1 什么是共享内存？**

共享内存的核心思想：

**让多个进程映射同一块物理内存，从而直接访问同一份数据。**

看图理解：

## **共享内存的核心原理**

**进程 A**

虚拟地址空间

映射地址 A

**进程 B**

虚拟地址空间

映射地址 B

页表映射到同一组物理内存页

# **同一块物理内存**

进程 A 修改数据，进程 B 可以看到变化

注意这里有一个关键细节：

进程 A 和进程 B 的虚拟地址可以不同，但它们映射到的是同一块物理内存。

所以：

- A 修改共享内存中的数据。
- B 访问共享内存时，也能看到修改后的数据。

这就是共享内存的本质。

## **5.2 为什么共享内存速度快？**

对比管道：

**管道通信**

进程 A 用户空间

第一次复制

内核管道缓冲区

第二次复制

进程 B 用户空间

**共享内存**

进程 A

进程 B

**共同访问同一块物理内存**

共享内存不需要每次通信都通过内核缓冲区进行两次数据复制。

所以在大量数据传输的场景下，共享内存通常效率更高。

但是有一个问题：

**共享内存本身不负责同步。**

假设：

- A 正在修改数据。
- B 同时读取数据。

如果没有同步机制，就可能发生数据竞争。

因此，共享内存通常需要配合信号量、互斥锁等机制使用。

## **5.3 System V 共享内存数据结构**

System V 共享内存是 Linux 提供的一套 IPC 接口。

其核心流程可以理解为：

```
创建/获取共享内存
       ↓
将共享内存映射到进程地址空间
       ↓
访问共享内存
       ↓
解除映射
       ↓
删除共享内存对象
```

这里要区分两个概念：

- 共享内存对象：由内核管理。
- 共享内存映射：让当前进程可以访问共享内存。

## **5.4 共享内存函数（重点）**

这几个函数一定要认识。

| 函数       | 作用               |
| -------- | ---------------- |
| shmget() | 创建或获取共享内存        |
| shmat()  | 将共享内存连接到当前进程地址空间 |
| shmdt()  | 将共享内存从当前进程地址空间分离 |
| shmctl() | 控制共享内存，例如删除      |

### **① shmget()**

```
int shmget(key_t key, size_t size, int shmflg);
```

作用：创建或获取共享内存。

主要参数：

- `key`：共享内存的标识键。
- `size`：共享内存大小。
- `shmflg`：创建权限和标志，例如 IPC_CREAT。

### **② shmat()**

```
void *shmat(int shmid, const void *shmaddr, int shmflg);
```

作用：把共享内存连接到当前进程的虚拟地址空间。

注意返回值：

- 成功：返回映射后的地址。
- 失败：返回 `(void *)-1`。

### **③ shmdt()**

```
int shmdt(const void *shmaddr);
```

作用：解除当前进程对共享内存的映射。

注意：它只是让当前进程解除映射，并不代表删除共享内存对象。

### **④ shmctl()**

```
int shmctl(int shmid, int cmd, struct shmid_ds *buf);
```

作用：对共享内存进行控制。

例如：

```
shmctl(shmid, IPC_RMID, NULL);
```

表示标记删除共享内存对象。通常在最后一个进程解除映射后，内核才真正释放它。

### **这四个函数的关系**

1. **shmget()**

   创建或获取共享内存，得到 shmid
2. **shmat()**

   映射到当前进程，得到可访问的地址
3. **读写共享内存**

   直接通过映射地址操作数据
4. **shmdt()**

   解除当前进程的映射
5. **shmctl(IPC_RMID)**

   标记删除共享内存对象

这几个函数的顺序和作用一定要建立清晰的认识。

## **5.5 实例：使用共享内存实现通信**

两个进程可以通过相同的 key 获取同一块共享内存。

一个进程负责写：

```
#include <stdio.h>
#include <sys/ipc.h>
#include <sys/shm.h>
#include <string.h>
int main()
{
    // 创建或获取一块共享内存，大小为4096字节
    int shmid = shmget(1234, 4096, IPC_CREAT | 0666);
    if (shmid == -1)
    {
        perror("shmget");
        return 1;
    }
    // 将共享内存映射到当前进程地址空间
    char *p = (char *)shmat(shmid, NULL, 0);
    if (p == (void *)-1)
    {
        perror("shmat");
        return 1;
    }
    // 向共享内存写入数据
    strcpy(p, "hello shared memory");
    // 解除当前进程的映射
    shmdt(p);
    return 0;
}
```

另一个进程使用相同的 key，通过 `shmget()` 获取同一个共享内存，再通过 `shmat()` 映射后读取。

注意：上面只是演示基本操作。真实的两个独立进程通信，还需要考虑共享内存的创建时机、数据是否已经写入、同步和清理，不能仅仅依靠两个进程碰巧按正确顺序运行。

## **5.6 借助管道实现访问控制版的共享内存**

这个实例主要想说明一个问题：

**共享内存负责数据共享，管道可以辅助实现进程间的执行顺序控制。**

例如：

```
进程 A：
写入共享内存
    ↓
通过管道发送通知
    ↓
进程 B：

等待管道通知
    ↓
读取共享内存
```

这样就避免了 B 在 A 尚未写入数据时提前读取。

不过这种方式只是教学演示，不是实际项目中首选的同步方案。

真正的并发程序通常使用进程共享的 POSIX 信号量、System V 信号量或进程共享互斥锁等机制。

# **六、System V 消息队列（选学了解）**

消息队列也是一种 IPC 方式。

前面学习的管道是按照字节流传输数据，没有消息边界。

而消息队列不同：

**消息队列是内核维护的消息链表，进程可以向队列发送消息，也可以从队列接收消息。**

例如：

```
进程 A                 内核消息队列                 进程 B
  │                         │                         │
  │──── 发送消息 A ────────>│                         │
  │                         │<──── 接收消息 ──────────│
  │──── 发送消息 B ────────>│                         │
  │                         │<──── 接收消息 ──────────│
```

与管道相比，消息队列有一个重要特点：

**它以消息为单位组织数据，而不是简单的字节流。**

## **6.1 主要函数**

| 函数       | 作用        |
| -------- | --------- |
| msgget() | 创建或获取消息队列 |
| msgsnd() | 发送消息      |
| msgrcv() | 接收消息      |
| msgctl() | 控制消息队列    |

典型使用流程：

```
msgget()   创建/获取消息队列
    ↓
msgsnd()   发送消息
    ↓
msgrcv()   接收消息
    ↓
msgctl()   删除消息队列
```

实际开发中，消息队列适合需要按消息组织、异步传递数据的场景。

本节按照老师要求，知道基本思想和函数即可。

# **七、System V 信号量（选学了解）**

这一部分虽然是选学，但我建议你理解基本原理。

因为它涉及一个非常重要的计算机概念：**并发编程中的同步与互斥。**

## **7.1 为什么需要同步与互斥？**

先看一个场景：

两个进程同时访问一块共享内存。

假设共享变量：

```
int count = 100;
```

进程 A 执行：

```
count++;
```

进程 B 执行：

```
count--;
```

你可能觉得：

一个加一，一个减一，最后应该还是 100。

但实际上，`count++` 并不是一个不可分割的操作。

它大致包含：

```
1. 读取 count
2. 计算 count + 1
3. 将结果写回 count
```

假设发生以下情况：

```
初始 count = 100

进程 A 读取 count = 100
进程 B 读取 count = 100

进程 A 计算得到 101
进程 B 计算得到 99

进程 A 写入 101
进程 B 写入 99

最终 count = 99
```

原本应该得到 100，结果却变成了 99。

这就是典型的竞态条件（Race Condition）。

## **7.2 什么是临界资源？**

多个进程共同访问的共享资源，如果同时访问可能导致数据错误，那么这部分资源就需要进行保护。

例如：

- 共享内存中的变量。
- 公共文件。
- 数据库中的共享数据。

这些需要保护的共享资源称为临界资源。

而访问临界资源的代码区域，称为临界区。

## **7.3 什么是信号量？**

信号量（Semaphore）可以理解为一个用于管理资源访问的计数器。

它的核心作用：

**控制多个进程对共享资源的访问，实现进程间的同步与互斥。**

例如：

假设共享资源只有一个访问名额：

```
信号量 = 1
```

进程 A 申请访问：

```
信号量 = 0
进程 A 进入临界区
```

进程 B 也想访问：

```
信号量 = 0
进程 B 必须等待
```

进程 A 释放资源：

```
信号量 = 1
进程 B 可以继续访问
```

## **信号量实现互斥**

**进程 A 申请资源**

**信号量 = 1**

允许进入

**进程 A 进入临界区**

**进程 B 申请资源**

等待

**进程 A 释放资源，B 获得访问机会**

这里需要知道两个概念：

- P 操作：申请资源，信号量减一；资源不可用时可能阻塞。
- V 操作：释放资源，信号量加一；可能唤醒等待进程。

它们通常是原子操作。

## **7.4 System V 信号量函数**

| 函数       | 作用            |
| -------- | ------------- |
| semget() | 创建或获取信号量集     |
| semop()  | 执行 P/V 等信号量操作 |
| semctl() | 控制信号量集        |

记住：

**共享内存解决数据共享问题，信号量解决共享资源的访问控制问题。**

这两个东西经常搭配使用。

# **八、内核是如何组织和管理 IPC 资源的？**

这是本节最后一个知识点，也是对前面内容的总结。

前面我们学习了：

- 管道
- 命名管道
- 共享内存
- 消息队列
- 信号量

那么问题来了：

这些 IPC 资源由谁管理？

答案：**Linux 内核。**

## **8.1 内核为什么要管理 IPC 资源？**

假设进程 A 创建了一个共享内存，进程 B 也想使用它。

那么操作系统必须解决：

1. 如何找到这块共享内存？
2. 如何判断进程有没有权限访问？
3. 如何记录有多少进程正在使用？
4. 如何释放不再使用的资源？

这些都需要内核统一管理。

## **8.2 System V IPC 的管理方式**

System V IPC 资源由内核维护相应的数据结构。

每个 IPC 对象都有自己的标识符 ID。

例如：

```
共享内存：
key → shmid → 内核共享内存对象

消息队列：
key → msqid → 内核消息队列对象

信号量：
key → semid → 内核信号量对象
```

其中：

- key：用于标识和查找 IPC 对象。
- ID：内核分配的对象标识符。
- 内核数据结构：保存对象的属性、权限、状态等信息。

注意：key 和 ID 不是一回事。key 用于获取对象，ID 用于后续操作对象。

## **8.3 如何查看 IPC 资源？**

Ubuntu 下可以使用：

```
ipcs
```

查看 System V IPC 资源。

分别查看：

```
ipcs -m    # 查看共享内存
ipcs -q    # 查看消息队列
ipcs -s    # 查看信号量
```

删除资源：

```
ipcrm -m shmid    # 删除指定共享内存
ipcrm -q msqid    # 删除指定消息队列
ipcrm -s semid    # 删除指定信号量
```

这些命令在实际 Linux 开发和排查 IPC 资源残留时很有用。
