# 本节重点

## 磁盘物理结构

电脑关机后，你的文档和照片存在哪里？内存断电就丢，所以必须有个**硬盘**（也叫磁盘）当永久仓库。机械硬盘的内部像一台精密唱片机：

- **盘片**：圆形的磁性碟片，通常 2~5 片叠在一起，由主轴马达带动高速旋转。
- **磁头**：每个盘片上下各一个，悬浮在盘片表面上方，负责读写数据，就像不接触碟面的唱针。
- **磁道**：盘片表面一圈圈同心圆，数据画在这些圆圈上。
- **扇区**：把磁道切成很多小段，每段是一个扇区（传统 512 字节，现代常见 4KB），是硬盘读写的最小单位。

把数据存进硬盘，本质是用磁头找到正确的盘片、正确的圆圈、正确的段，然后改变那段位置的磁性。

---

## CHS 与 LBA 地址

磁头怎么知道去哪个扇区找数据？就像快递需要地址，硬盘也需要定位方式。

**CHS（柱面-磁头-扇区）** 是早期的物理地址。它用三个数描述位置：
- **柱面**：所有盘片上，半径相同的磁道从上到下组成一个圆柱面。因为所有磁头绑在一起移动，如果数据在同一柱面的不同盘片上，切换磁头就能读，磁臂不用动，速度最快。
- **磁头**：用第几个磁头，对应第几个盘片的哪一面。
- **扇区**：该磁道上的第几段。

**麻烦来了**：操作系统要记三个数，而且不同硬盘磁道数量不同，程序很难统一编写，大容量硬盘还会出现数字不够用的情况。

**LBA（逻辑块地址）** 解决了这个麻烦。它把所有扇区从 0 开始连续编号，0、1、2、3……排成一条逻辑长龙。操作系统只需要说“我要第 12345 个扇区”，硬盘控制器自己把这个数翻译成 CHS 去控制磁头。

> **关键结论**：LBA 是操作系统看到的“扁平”门牌号，CHS 是硬盘内部的真实物理坐标。

## Ext 系列文件系统原理

磁盘出厂只是一块空白磁性材料，必须有一套“管理办法”才能像文件夹一样存取文件。这套办法就是**文件系统**。Linux 最常用的家族是 Ext 系列（ext2/ext3/ext4）。

它的核心思路是：把磁盘空间切成大小相等的**块**（Block，通常 4KB），再把块分成几个功能区管理。

一个硬盘分区会被划分为很多**块组**（Block Group），就像把大超市分成几个区域，每个区域自己管自己的货架。

每个块组内部结构如下：

| 区域 | 大白话 | 作用 |
|---|---|---|
| **超级块** (Super Block) | 整个分区的“总账本” | 记录分区总大小、已用空间、未用空间等全局信息 |
| **块组描述符** | 本区域的“分区简介” | 记录这个块组从哪里开始、到哪里结束 |
| **块位图** (Block Bitmap) | 块的“占用登记表” | 每一位对应一个块，0 表示空闲，1 表示已用 |
| **inode 位图** (inode Bitmap) | inode 的“占用登记表” | 每一位对应一个 inode 是否被使用 |
| **inode 表** (inode Table) | 每个文件的“档案袋” | 每个文件对应一个 inode，里面存属性、权限、大小，以及数据块位置 |
| **数据块** (Data Blocks) | 真正放文件内容的地方 | 文档、照片的二进制数据都躺在这里 |

**inode（索引节点）** 是最重要的概念。每个文件有一个“身份证号”叫 inode 号。inode 里不存文件名，只存文件属性和一组块指针，指向数据块在哪里。

那文件名存在哪？**目录的数据块里**。目录不是柜子，它本身也是一种特殊文件，它的数据块里存着一张映射表，每一行是“文件名 ↔ inode 号”的关系。

因此，当你打开 `/home/user/a.txt` 时，系统实际做的是：从根目录的 inode 出发 → 读根目录的数据块 → 找到 "home" 对应的 inode 号 → 读 home 的数据块 → 找到 "user" 对应的 inode 号 → 读 user 的数据块 → 找到 "a.txt" 对应的 inode 号 → 读 a.txt 的 inode → 找到数据块 → 读出内容。

## 分区、格式化、路径解析与挂载

### 分区与格式化

**分区**就是把一块物理硬盘逻辑上切成几段，比如 200GB 给系统、800GB 给数据。每段叫一个分区，分区信息存在硬盘最开头的分区表里。

**格式化**不是删除数据，而是**给分区建立文件系统的管理结构**。就像把空仓库安上货架、贴上编号、建好台账。快速格式化只重写超级块和位图，不擦除老数据；低级格式化才会逐块擦除。

### 路径解析

在 Linux 里，所有路径都是一棵倒挂树的遍历。系统从根 inode 出发，逐层查目录数据块里的“文件名 → inode 号”映射，把人类认识的路径翻译成机器认识的 inode 和块号。

### 挂载

Windows 用 C:、D: 盘符区分分区；Linux 只有一棵文件树，起点是 `/`。要把一个新分区（或 U 盘、光盘）塞到树里供用户访问，必须把它**挂载**到某个目录下。

```bash
mount /dev/sdb1 /data   # 把 sdb1 分区接到 /data 目录上
# 从此访问 /data，就是访问 sdb1 分区里的内容
mount                   # 查看当前所有挂载情况
```

> **关键结论**：分区是空间切割，格式化是建立管理系统，挂载是把分区挂到目录树上让用户访问。

## 软硬链接

### 硬链接

**问题**：同一个文件想在两个不同目录下都看到，但复制一份浪费空间。

**原理**：不复制数据，只在另一个目录的数据块里新增一条记录，让新文件名**指向同一个 inode 号**。inode 里有个**链接计数**（硬链接数），记录有几个文件名指向自己。

```bash
ln file.txt hard_link.txt      # 给 file.txt 建立硬链接 hard_link.txt
ls -li file.txt hard_link.txt  # -i 查看 inode 号，你会发现两者相同
```

删除其中一个文件名，只是删掉目录里的一条记录，链接计数减 1。只有计数变成 0，系统才真正释放数据块。

**限制**：不能跨分区（inode 号只在当前文件系统内唯一），默认不能链接目录（防止目录成环，让路径解析死循环）。

### 软链接

**原理**：新建一个独立的文件，有自己的 inode，数据块里存的是**目标路径字符串**。就像 Windows 的快捷方式。

```bash
ln -s /very/long/path/to/file.txt shortcut.txt   # -s 表示 soft，建立软链接
cat shortcut.txt                                 # 打开时，系统自动去读目标路径的内容
```

原文件删掉后，软链接还存在，但指向一个不存在的路径，变成“断链”。

| 对比项 | 硬链接 | 软链接 |
|---|---|---|
| inode | 与原文件相同 | 新建独立 inode |
| 数据 | 共享原数据块 | 数据块存的是路径字符串 |
| 跨分区 | 不支持 | 支持 |
| 链接目录 | 不支持 | 支持 |
| 原文件删除 | 不影响访问（计数减 1） | 断链，无法访问 |

> **关键结论**：硬链接是多名字共享一份数据，软链接是新文件里存了个路径；软链接更灵活，硬链接更安全防误删。

## 1. 理解硬件

### 1-1 磁盘、服务器、机柜、机房

磁盘是计算机内部罕见的“机械设备”——主板、内存、CPU 都是纯电子元件，只有磁盘里装着会转动的盘片和会移动的磁头。作为外设，它离 CPU 远，读写速度比内存慢得多，但优势是容量大、断电数据不丢失、单位价格便宜。可以把内存比作办公桌，磁盘比作档案室：办公桌小但拿东西快，档案室大但走动取文件慢。

---

### 1-2 磁盘物理结构

一块机械磁盘内部有几个核心部件：盘片（存储数据的圆形碟片）、主轴（带动盘片旋转）、读写磁头（像唱针一样贴近盘片表面读写）、传动臂（带动磁头水平摆动）。

**磁头共进退**：磁盘通常由多张盘片叠成，每张盘片上下两面各有一个磁头。所有磁头都固定在同一根传动臂上，就像钢琴的琴键被同一根连杆带动——传动臂往里推，所有磁头一起往里；传动臂往外拉，所有磁头一起往外。它们永远处于相同的半径位置，不会各自乱跑。

**向柱面批量写入**：因为磁头共进退，磁盘在大量写入数据时，不会让某个磁头在一个盘面上画完圆圈再去下一个盘面，而是利用所有磁头同时工作，把同一半径上的所有磁道一起写满。这就像仓库里有上下多层货架，叉车一次性对齐某一层后，把该层所有货位先存满，再整体移动到下一半径。

---

### 1-3 磁盘的存储结构

**扇区**：盘片表面被划分成很多同心圆环（磁道），每个磁道又被切成一段段小圆弧，每一段就是一个扇区。扇区是磁盘存储数据的最小单元，固定为 512 字节。磁盘属于“块设备”——数据必须按整块（扇区）读写，不能像键盘那样一次读一个字节。

**一个问题：操作系统说“把这 512 字节写到某个扇区里”，磁盘硬件要动哪些部件？**
答案是三步走：第一步，选磁头，确定操作哪个盘面；第二步，传动臂带动所有磁头水平移动，到达目标半径（即目标柱面）；第三步，等待盘片旋转，让目标扇区正好转到磁头下方，然后写入。这三步对应三个坐标：**柱面（Cylinder）、磁头（Head）、扇区（Sector）**，合称 **CHS 定址**。

定位顺序之所以是“先磁头、再柱面、后扇区”，是由物理动作的成本决定的：选磁头是电子开关，瞬间完成；移动传动臂是机械运动，需要毫秒级时间；等待盘片旋转也是机械运动，平均要等半圈。后两者都比电子动作慢成千上万倍，所以算法设计会尽量减少它们的次数。

各参数的含义如下：磁头数等于盘片数乘以 2（每片两面）；磁道从外圈往内圈编号，最内圈靠近主轴的几个同心圆不存数据，是专门停放磁头的“停泊区”；柱面数等于磁道数，因为同一半径的所有磁道上下对齐，在空间里形成一个虚拟的“圆柱面”；每个磁道的扇区数相同。于是磁盘总容量为：

```
容量 = 磁头数 × 柱面数 × 每道扇区数 × 512 字节
```

CHS 定址在早期硬盘中直接可用，但有个先天瓶颈：BIOS 时代给磁头、柱面、扇区分配的地址位数有限（8 位磁头 + 10 位柱面 + 6 位扇区），算出来的最大寻址空间只有约 8.4 GB。硬盘容量超过这个数值后，CHS 就编不过来了。

---

### 1-4 磁盘的逻辑结构

#### 1-4-1 理解过程

怎么突破 8.4 GB 的限制？思路是换一套编址方式，让操作系统不再关心磁头在哪、传动臂在哪。

想象一盒磁带：平时卷在带盘里，看起来是一圈圈同心圆；但如果把它拉直，就变成了一根长长的带子，每个位置只要一个编号就能定位。磁盘虽然是硬的、圆的，但在逻辑上完全可以想象成“卷起来的磁带”——把所有扇区从头到尾排成一条直线，每个扇区给一个连续编号。这个编号就是 **LBA（Logical Block Address，逻辑块地址）**，本质上就是数组下标。对操作系统来说，磁盘不再是一堆盘片和磁头，而是一个巨大的线性数组，访问一个扇区只需要一个数字。

#### 1-4-2 真实过程

物理上磁盘确实分了很多盘面，每个盘面有很多磁道。因为磁头共进退，所有盘面上相同半径的磁道在空间里上下对齐，构成一个柱面。如果把一个磁道拉直，它是一维数组；把一个柱面上的所有磁道（每个磁道扇区数相同）并排展开，就是一张二维数组表；整个磁盘有多个柱面，相当于多张这样的二维数组表。逻辑上，把这些表按柱面顺序首尾相接“卷”成一根长线，所有扇区就有了连续的线性编号。

---

### 1-5 CHS && LBA 地址

**LBA**：每个扇区的线性下标。操作系统只使用 LBA 与磁盘交互，不再过问 CHS。那么物理磁盘怎么知道磁头该移到哪？**LBA 与 CHS 之间的换算由磁盘内部的固件（硬件电路和伺服系统）自动完成**，对上层完全透明。

地址换算的核心是把三维坐标压扁成一维下标，或者反过来展开。设单个柱面的扇区总数为 `HPC`（Heads Per Cylinder），它等于磁头数乘以每磁道扇区数。

**CHS → LBA** 的推导：先跳过完整柱面，再跳过同一柱面上的完整磁道，最后加上扇区偏移。因为扇区号从 1 开始而 LBA 从 0 开始，要减 1。

```bash
# CHS 转 LBA
# C: 柱面号(从0开始), H: 磁头号(从0开始), S: 扇区号(从1开始)
# heads: 磁头总数, sectors_per_track: 每磁道扇区数

HPC=$((heads * sectors_per_track))          # 一个柱面包多少扇区
LBA=$((C * HPC + H * sectors_per_track + S - 1))
```

**LBA → CHS** 的推导：用除法和取模把一维下标还原成三维坐标。

```bash
# LBA 转 CHS
# C: 柱面号, H: 磁头号, S: 扇区号

C=$((LBA / HPC))                            # 落在第几个柱面
tmp=$((LBA % HPC))                          # 柱面内的剩余偏移
H=$((tmp / sectors_per_track))              # 落在该柱面的第几个磁头
S=$((tmp % sectors_per_track + 1))          # 落在该磁道的第几个扇区（回到1-based）
```

磁盘的总柱面数、磁头数、每道扇区数等信息由磁盘固件内部维护，计算机开机时通过标准接口自动获取，操作系统不需要手动测量。

> **最终结论：在使用者看来，磁盘就是一个元素为 512 字节扇区的一维数组，下标即 LBA。操作系统只需要一个数字，就能让磁盘访问到任意扇区，背后的机械运动对软件完全不可见。**

**块号与 LBA 的对应**：实际文件系统中常以多个扇区为一个“块”（例如 8 扇区 = 4KB）。若已知块号，块内扇区的 LBA 范围可直接算出：

```bash
# 假设每块包含 8 个扇区
start_LBA=$((block_number * 8))             # 该块第一个扇区的 LBA
end_LBA=$((block_number * 8 + 7))           # 该块最后一个扇区的 LBA
```

## 2. 引入文件系统

### 2-1 引入"块"概念

磁盘里最底层的存储格子叫扇区，每个扇区512字节。如果OS每次读文件都一个一个扇区去搬，机械臂要来回跑几十万次，速度极慢。解决思路是把位置上相邻的8个扇区捆成一大包，这一包就叫块，通常4KB。OS跟硬盘打交道时，一次性搬一包，而不是一格一格搬。

LBA（逻辑块地址）是给硬盘上所有扇区从头到尾编的连续号码，比如0号扇区、1号扇区……OS不用记盘片在哪、机械臂在哪，只认这个统一编号。既然一个块占8个扇区，那么：

- 块号 = LBA / 8
- 知道块号后，这块对应的8个扇区号就是：LBA = 块号 × 8 + n（n 取 0~7）

```text
磁盘物理扇区（LBA 连续编号）:
[512B][512B][512B][512B][512B][512B][512B][512B] [512B]...
 \---------------- 块 0 ----------------/  \-- 块 1 开始 --
           = 4KB
```

块的大小在格式化时确定，之后改不了。

> **块是OS访问磁盘的最小单位，一个块通常等于连续8个扇区（4KB），格式化时定下就改不了。**

---

### 2-2 引入"分区"概念

一块800GB的大硬盘，如果把所有数据全堆在一起管理，一旦出问题全部数据都可能遭殃，而且找东西像在整个城市里翻一根针。解决方法是像Windows的C盘、D盘那样，把大硬盘切成几个独立区域，各管各的，这就叫分区。

分区时以柱面为最小边界。柱面是硬盘里很多圆形盘片叠在一起后，每个盘片上相同半径的圆圈组成的一个圆柱面。因为盘片同步转，读同一个柱面上的数据时机械臂不用换位置，速度最快。又因为每个柱面包含的扇区数一样，所以只要记下起始柱面号和结束柱面号，这块分区有多大、LBA从哪到哪，立刻就能算出来。

> **大磁盘必须分区分治管理，柱面是分区的最小单位。**

---

### 2-3 引入"inode"概念

一个文件不只有你看得到的内容（数据），还有创建者、大小、权限、修改时间等一堆属性。如果属性和内容混着存，查属性得翻遍整个文件，又慢又乱。Linux的做法是把内容和属性分开存放：所有属性被抽出来，装进一个固定大小的结构体里，这个结构体就叫inode（索引节点）。每个常规文件必须有且只有一个inode，inode里带一个唯一编号叫inode号。

用 `ls -l` 能看到文件的部分属性列表；用 `stat` 命令能调出更全的属性档案：

```bash
stat test.c   # 查看文件的完整属性信息
```

ext2文件系统里，inode用结构体描述，里面记录着：

```cpp
struct ext2_inode {
    i_mode;          // 文件类型与权限
    i_uid;           // 拥有者用户ID
    i_size;          // 文件大小（字节）
    i_atime;         // 最后访问时间
    i_ctime;         // 最后状态改变时间
    i_mtime;         // 最后修改时间
    i_dtime;         // 删除时间
    i_gid;           // 所属组ID
    i_links_count;   // 硬链接计数
    i_blocks;        // 占用的块数
    i_flags;         // 标志
    i_block[EXT2_N_BLOCKS]; // 指向实际数据块的编号数组
};
```

老师板书会把它画得更简单，核心只记这个逻辑：

```cpp
struct inode {
    int  type;           // 文件类型
    int  size;           // 大小
    // ... 其他属性 ...
    int  inode_number;   // 唯一身份证号
    int  datablock[N];   // 这个文件的数据存在哪几个块上
};
```

这里有三个必须记住的要点：

1. **文件名不在inode里**。inode只存属性，不存文件名。
2. **inode大小固定为128字节**。不管文件内容有多大，它的属性袋都是一样大的。
3. **一个块能装多个inode**。4KB的块 / 128字节 = 32个。OS以4KB为单位读写，读一次块就能抓出32个文件的属性。

```text
一个 4KB 数据块内部：
[inode 0][inode 1][inode 2]...[inode 31]  ← 共32个，每个128字节
```

但这里留下两个必须解决的核心问题，这也正是文件系统存在的意义：
- ① 这些块在分区上到底怎么排列？怎么根据编号快速找到对应的块？
- ② 这么多inode，在硬盘上究竟放在哪里？怎么通过inode号定位到它？

> **Linux下文件内容和属性分开存储；inode是固定128字节的属性容器，一个4KB块可存储32个inode。**

---

## 3. ext2 文件系统

### 3-1 宏观认识

硬盘要能存文件，不能直接把数据扔进去，否则将来根本找不到。必须先格式化成某种文件系统——文件系统就是一套组织和管理硬盘文件的方法，让数据有迹可循。Linux里最常用的是ext2系列，后来的ext3、ext4都是在ext2核心设计上做的增强，所以我们以ext2为例。ext2的做法是：把整个分区切成若干个大小相同的块组（Block Group），只要能把一个块组管明白，所有块组都能如法炮制，整个分区也就管明白了。

---

### 3-2 Block Group

一个分区动辄几百GB，从头看到尾太累。ext2把它划分成数个Block Group，每个块组内部结构完全相同，就像市政府管理各个行政区，每个区的部门设置一样。层次关系上，整块硬盘先分成若干分区，每个分区开头有一个启动块（Boot Block/Sector），固定1KB
，由 PC 标准规定，里面存着分区表和启动信息，任何文件系统都动不了它；启动块之后，ext2 才算真正开始管理这片空间。面对 300GB 的庞大数据，ext2 的做法就是分组：group 0、group 1……group n，每个组内部结构完全一致，把大化小，管理起来才能有的放矢。

---

### 3-3 块组内部构成

每个 Block Group 的开头都按相同顺序排着六样东西，这就是文件系统最具体的分层（板书强调）：

```text
Super Block | GDT | Block Bitmap | inode Bitmap | inode Table | Data Blocks
```

下面逐个说明它们各自解决什么问题。

#### 3-3-1 超级块(Super Block)

Super Block 是文件系统的"物业总台账"，存放的是整个文件系统本身的结构信息，比如这个分区里 block 和 inode 的总数、还剩多少没用完、单个 block 和 inode 有多大、最近一次挂载和写入是什么时候。这些数据描述的是"整片小区"的情况，而不是某一户。

正因为太重要，Super Block 一旦被破坏，整个文件系统的结构就全乱了。所以 ext2 会在多个块组里给它做备份，保持内容一致；第一个块组里必须有，后面的块组可以没有。

C 语言里用结构体 `struct ext2_super_block` 来描述它，里面关键字段的含义直白对应上述信息：`s_inodes_count`（inode 总数）、`s_blocks_count`（block 总数）、`s_free_blocks_count`（空闲 block 数）、`s_free_inodes_count`（空闲 inode 数）、`s_first_data_block`（第一个数据块位置）、`s_log_block_size`（块大小）、`s_blocks_per_group`（每组 block 数）、`s_mtime`（最后挂载时间）、`s_wtime`（最后写入时间）、`s_magic`（魔数，用来识别这是 ext2 文件系统）。

#### 3-3-2 GDT(Group Descriptor Table)

如果 Super Block 是全市总台账，GDT 就是每个区的"区志书"。它的全称叫块组描述符表，里面有多少个条目，这个分区就被切成了多少个块组；每个条目（块组描述符）记录对应块组的属性，比如本块组的 inode Table 从哪开始、Data Blocks 从哪开始、还剩余多少个空闲的 inode 和数据块。

GDT 的核心作用就是定位（板书强调：据此定位本块组管理数据的起始位置！）。每个块组的开头都会存一份 GDT 拷贝，这样即使某个块组损坏，也能从别的块组读出描述信息。

对应结构体 `struct ext2_group_desc`，关键字段包括：`bg_block_bitmap`（块位图位置）、`bg_inode_bitmap`（inode 位图位置）、`bg_inode_table`（inode 表位置）、`bg_free_blocks_count`（空闲块数）、`bg_free_inodes_count`（空闲 inode 数）、`bg_used_dirs_count`（已用目录数）。

> **概括化管理的本质，就是把文件系统的管理信息深入写入磁盘；读取第一个分组，就能拿到整个分区的管理框架。**

#### 3-3-3 块位图(Block Bitmap)

Data Blocks 有成百上千个块，系统怎么知道哪块被占、哪块还空着？Block Bitmap 用每一位（bit）对应一个数据块，0 表示空闲，1 表示占用（板书：0000 0000 位示意）。申请空间时扫一眼位图，就能快速找到空地。

#### 3-3-4 inode位图(Inode Bitmap)

与块位图思路完全一样，Inode Bitmap 的每个 bit 对应一个 inode 是否空闲可用（板书强调）。

这里要注意两个编号规则：inode 编号和数据块编号都是按整个分区来划分的，不能跨分区；同一个分区内部，这套编号机制是唯一的（板书强调：同一分区内的 inode 编号机制等都是唯一的！）。

#### 3-3-5 i节点表(Inode Table)

Inode Table 存放的是文件属性，也就是文件大小、所有者、最近修改时间等元数据；它是当前这个块组里所有 inode 属性的集合（板书强调）。

inode 编号以分区为单位整体划分，不可跨分区。可以把 Inode Table 想象成一张表格，每一列是一项属性：

| Inode Number | File Type | Permissions | Link Count | UID | GID | size | ... | pointer |
|---|---|---|---|---|---|---|---|---|

这里的 pointer 指向真正的数据块。只要拿到一个文件的第一个 inode，顺着指针就能找到该文件的所有内容（板书强调）。

那么问题来了：你怎么知道自己在分组中对应的是哪一个具体位置？答案就是通过 inode 编号结合 GDT 里记录的 `bg_inode_table` 起始位置来计算偏移。

#### 3-3-6 Data Block

Data Block 是数据区，存放真正的文件内容。普通文件的数据直接存在这里；目录比较特殊——目录也是文件，它的 Data Block 里存的并不是普通文本，而是这个目录下所有文件名和子目录名，以及它们对应的 inode 号。换句话说，目录的"内容"就是一张"文件名→inode"的映射表。

而 `ls -l` 看到的文件权限、大小、时间等属性，则保存在各个文件自己的 inode 里，不在目录的数据块中。Block 号同样按分区划分，不可跨分区。

---

### 3-4 inode和datablock映射（弱化）

inode 内部有一个数组 `i_block[EXT2_N_BLOCKS]`，其中 `EXT2_N_BLOCKS` 等于 15，这个数组记录的就是该文件占用了哪些 Data Block 的编号（板书强调：该文件所对应的数据块的编号！）。有了 inode 就能找到属性，有了 `i_block` 就能找到内容，于是文件 = 内容 + 属性就都能找到了。

---

### 3-5 目录与文件名

现在思考一个问题：在已知 inode 号的前提下，在指定分区里对文件进行增、删、查、改，本质上是在做什么？

答案是：你只是在读写 inode 和 Data Block，并在目录的数据块里维护映射关系。所谓格式化分区，其实就是先分组，然后在每个组里写入 Super Block、GDT、Block Bitmap、Inode Bitmap 等管理信息；这些管理信息合起来，就是文件系统本身。

只要知道一个文件的 inode 号，就能确定它在哪个分组、哪个 inode 位置，进而拿到它的属性和内容（板书强调）。但用户平时并不直接拿 inode 号操作，而是用文件名。这就引出了创建文件时的完整流程。

以 `touch abc` 后 `ls -i abc` 显示 inode 为 263466 为例，内核实际做了 4 件事（板书强调）：

1. **存储属性**：找到一个空闲 inode（如 263466），把文件大小、权限等信息填进去。
2. **存储数据**：找到三个空闲块（如 300、500、800），把数据复制进去。
3. **记录分配情况**：在 inode 的 `i_block` 数组里记下这三个块号。
4. **添加文件名到目录**：把 `(263466, abc)` 这条记录写入当前目录这个"文件"的内容里——文件名和 inode 的对应关系，把文件名和文件的内容及属性彻底连接起来。

那目录自己是不是文件？是的。磁盘上根本没有"目录"这种实体，只有"属性+内容"；目录的属性存在它自己的 inode 里，内容存的就是文件名与 inode 号的映射关系（板书强调）。

可以用一段代码验证：遍历根目录，打印每个条目（跳过 `.` 和 `..`）的文件名和 inode 号。

```cpp
#include <stdio.h>
#include <dirent.h>

int main() {
    DIR *dir = opendir("/");              // 打开根目录（返回一个目录流指针）
    struct dirent *entry;
    while ((entry = readdir(dir)) != NULL) { // 逐个读取目录项
        if (entry->d_name[0] == '.') continue; // 跳过 . 和 ..
        printf("Filename: %s, Inode: %lu\n", entry->d_name, entry->d_ino);
    }
    closedir(dir);                        // 关闭目录流
    return 0;
}
```

编译运行后，将结果与 `ls -li /` 对照，会看到文件名和 inode 的对应关系完全一致。

> **磁盘上的文件系统只认 inode！查找文件时，实际上是在当前文件所属目录的数据内容当中，根据文件名找到对应的 inode 号。**
> **访问任何文件都是通过文件名：先打开所在目录 → 根据文件名与 inode 的映射关系拿到 inode → 再访问文件的内容和属性！**

因此，访问 `test.c` 之前，必须先打开它所在的当前工作目录，才能从目录内容里查到 `test.c` 对应的 inode。

---

### 3-6 路径解析

既然访问文件必须先打开所在目录，那当前工作目录自己也是文件，访问它岂不是也要知道它的 inode？→ 那就得再打开它的上级目录……如此一层层往上，形成类似递归的结构。

> **我们访问任何文件都必须要有的路径！** 例如 `ls /home/whb/code/code/merge class/lessons21/code.c`，系统必须从根目录开始，依次打开每一个目录，根据目录名逐级向下，直到找到目标文件。

这个"递归"的出口是根目录 `/`（板书强调）。根目录的文件名和 inode 号是固定的，系统开机之后就必须知道，无需查找。

为什么一定要有"目录+文件名=路径"？因为脱离路径就无法完成这层递归解析。那路径是谁提供的？你执行命令或程序时，本质上是进程在访问文件，而进程自己有一个 CWD（当前工作目录），路径由进程提供（板书强调：我的路径，谁提供的？→ 进程提供当前路径！）。

最开始这些路径从哪来？Linux 的根目录、系统缺省目录、用户家目录，本质都是在磁盘文件系统里新建出来的目录文件；新建的文件必然挂在某个已有目录下，天然就带有路径。整个 Linux 的树状路径结构，是系统初始化与用户共同搭建出来的。

---

### 3-7 路径缓存

这里有三个关键问题：

**问题1：Linux 磁盘中存在真正的目录吗？**
不存在。磁盘上只有文件，保存的是属性加内容；目录只是一种特殊的文件（板书强调）。

**问题2：访问任何文件都要从 `/` 目录开始做路径解析吗？**
原则上是，但如果每次打开文件都从根目录一层层查磁盘，效率太低（板书强调）。所以 Linux 会把已经解析过的路径结构缓存在内存里。

**问题3：Linux 目录的概念是怎么产生的？**
当一个目录被打开时，操作系统在内存中自己维护一棵多叉树，把各级路径关系缓存起来；你在 Shell 里看到的树状目录结构，就是这棵内存树的体现（板书强调）。

内核里用来维护这棵树的结构体叫 `struct dentry`（板书强调）。它的关键字段包括：`d_count`（引用计数）、`d_inode`（指向文件对应的 inode，若为 NULL 表示 negative）、`d_parent`（父目录）、`d_name`（名字）、`d_subdirs`（子目录链表）、`d_hash`（哈希表节点，加速查找）、`d_lru`（LRU 链表节点）。每个被打开的文件（包括普通文件）都会有一个对应的 `dentry`，所有被打开的文件在内存中共同构成整棵树形结构。

这棵树同时还是 LRU（最近最少使用）结构，不常用的节点会被淘汰；又通过哈希表组织，方便按路径快速查找（板书强调）。

整个树形结构就是 Linux 的路径缓存：打开任何文件时，系统先在这棵树上按路径查找；找到了就直接返回 inode 和内容；没找到再去磁盘加载路径，新建 `dentry` 并缓存。

---

### 3-8 挂载分区

前面说过，inode 号不能跨分区。但 Linux 机器上往往有好几个分区，系统怎么知道你操作的是哪一个分区？

#### 3-8-1 一个实验

可以用一个文件模拟一块分区，完整走一遍挂载流程：

```bash
dd if=/dev/zero of=./disk.img bs=1M count=5   # 创建一个 5MB 的空文件，当作一块磁盘分区
mkfs.ext4 disk.img                              # 在文件里写入 ext4 文件系统
mkdir /mnt/mydisk                               # 准备一个空目录作为挂载点
df -h                                           # 查看当前已有的挂载分区
sudo mount -t ext4 ./disk.img /mnt/mydisk/      # 把文件系统挂载到目录上
df -h                                           # 此时会多出一行 /dev/loop0 挂在 /mnt/mydisk
sudo umount /mnt/mydisk                         # 卸载
df -h                                           # 恢复原来的样子
```

`/dev/loop0` 是第一个循环设备，它是一个伪设备，能把普通文件当成块设备来用；`ls /dev/loop* -l` 可以查看这些设备文件。

#### 3-8-2 一个结论

> **分区写入文件系统后无法直接使用，必须和某个指定目录关联起来，进行挂载后才能访问；系统根据你要访问的路径前缀，就能准确判断你落在哪个分区上（理解到这个层面）。**

---

### 3-9 文件系统总结

最后从大到小把层次再理一遍（板书强调：文件系统的具体分层！）：

```text
Disk
 └── Partition（分区）
      └── EXT2 File System
           └── Block Group 0 / 1 / ... / N
                ├── Super Block      （整个分区的总台账）
                ├── GDT              （本组区志书，定位各区域起点）
                ├── Block Bitmap     （数据块占用情况）
                ├── inode Bitmap     （inode 占用情况）
                ├── inode Table      （文件属性集合）
                └── Data Blocks      （文件内容/目录的映射表）
```

而 Inode Table 里的每一行，又细化为 Inode Number、File Type、Permissions、Link Count、UID、GID、size、pointer……等具体列结构。文件系统正是通过这套分层，把硬盘上一堆无差别的二进制块，组织成你能看到的文件和目录。

## 4. 软硬连接

你在 Windows 上用过快捷方式吗？Linux 里也有类似机制，而且有两种：硬链接和软链接。它们解决同一个麻烦：如何让一个文件出现在多个地方，却不用真的复制好几份占用磁盘空间。

---

### 4-1 硬链接

#### 文件名不是文件本身

你平时用文件名找文件，但系统内部不靠名字定位。第 5 课提到过 inode，它是文件在磁盘上的唯一身份证号。一个 inode 指向一块真实的磁盘数据，而文件名只是挂在 inode 上的门牌号。既然多个门牌号可以指向同一套房子，Linux 就允许多个文件名对应同一个 inode，这就是硬链接。

#### 创建与观察

语法：`ln 源文件 硬链接名`

功能：为已存在的文件创建一个新的文件名，两者共享同一个 inode 和同一份数据。

示例：

```bash
touch abc              # 新建一个普通文件（你已学过 touch）
ln abc def             # 为 abc 创建硬链接 def
ls -li abc def         # -i 显示 inode 编号，观察两者是否相同
```

执行后你会看到 `abc` 和 `def` 的 inode 编号完全相同，权限、大小、时间也完全一致。此时这两个名字没有主次之分，删掉任何一个，另一个照样能打开文件。

#### 链接数与删除机制

内核会在 inode 里维护一个**链接数**（link count），记录有多少个文件名指向这个 inode。刚用 `touch` 创建文件时链接数是 1，执行 `ln` 创建硬链接后变成 2。

你执行 `rm` 删除文件时，系统其实只做了两件事：第一，在当前目录的记录里抹掉这个名字；第二，把对应 inode 的链接数减 1。只有当链接数减到 0 时，系统才会认为真的没有名字需要这块数据了，于是把它标记为可用空间。

> **核心结论：删除文件只是删除一个名字；只有当所有硬链接都被删除，链接数归零，磁盘数据才会真正释放。**

---

### 4-2 软链接

#### 通过名字指路

硬链接有一个限制：它直接绑定 inode，而 inode 只在当前文件系统（分区）内有效，也不能给目录创建硬链接（防止形成环路）。如果你需要跨分区引用，或者想要一个明确的“指路牌”，就需要软链接。

软链接是一个**真正独立的新文件**，它有自己的 inode，文件内容里只保存着目标文件的路径名字符串。你可以把它想象成 Windows 的快捷方式。

#### 创建与识别

语法：`ln -s 目标文件 软链接名`

功能：创建一个独立的链接文件，指向目标文件的路径。

示例：

```bash
ln -s abc abc.s        # 创建软链接 abc.s，指向 abc
ls -li abc abc.s       # 对比 inode 和文件类型
```

你会看到 `abc.s` 的 inode 和 `abc` 完全不同。文件类型显示为 `lrwxrwxrwx`，其中开头的 `l` 表示这是一个链接文件；大小显示为 3，因为里面存的路径字符串 `"abc"` 只有 3 个字节。箭头 `->` 后面会标出它指向谁。

> **核心结论：软链接是独立文件，存的是目标路径；原文件删除后，软链接会失效（悬空）。**

#### 文件的时间戳

每个文件带有三个时间：

- **Access**：最后一次访问文件内容的时间（比如读取）。
- **Modify**：最后一次修改文件内容的时间。
- **Change**：最后一次修改文件属性（权限、链接关系、所有者等）的时间。

当你创建或删除链接时，通常只会影响 Change 时间；修改原文件内容则会更新 Modify 时间。

---

### 4-3 软硬连接对比

| 对比项 | 硬链接 | 软链接 |
| :--- | :--- | :--- |
| inode | 与目标文件**相同** | 与目标文件**不同**，是独立文件 |
| 链接数 | 创建后目标文件的链接数 +1 | 目标文件链接数不变 |
| 跨目录/跨分区 | **不能**跨分区（inode 只在分区内部有效） | **可以**跨分区，甚至可以跨文件系统 |
| 删除原文件后 | 数据仍然可用（还有其他硬链接指着） | 链接失效，打开会报文件不存在 |
| 文件内容 | 与目标文件共享同一份数据 | 内部只保存目标路径字符串 |

---

### 4-4 软硬连接的用途

**硬链接的典型用途**

你在第 1 课已学过 `.`（当前目录）和 `..`（上级目录），它们本质上就是目录的硬链接。此外，硬链接可用于重要文件的本地备份：一份数据多个名字，不额外占用空间，任意一个名字被误删都不影响数据本身。

**软链接的典型用途**

和快捷方式一样，软链接常用于：把深层目录里的可执行文件链接到 `bin` 目录方便执行；或者程序升级后保留旧版本路径名指向新版本，避免其他脚本失效。
