# 1. 软件包管理器

## 1-1 什么是软件包

### 从源码安装为什么麻烦

**源码**：软件作者写出来的原始代码，人通常不能直接双击运行。传统安装方式是先下载源码，再编译成当前电脑能运行的程序，还可能要手动补齐其他软件。

例如，安装一个程序时可能遇到：

- 缺少编译工具；
- 缺少它依赖的其他软件；
- 依赖的软件版本不兼容；
- 不同电脑需要重复配置。

于是，软件作者或社区会提前把源码编译好，整理成可以直接安装的文件，并放到服务器上供下载。这种整理好的安装文件叫**软件包**：可以理解为“已经打包好的软件成品”。

**软件包管理器**：专门负责搜索、下载、安装、升级和卸载软件包的工具。它很像手机上的应用商店：你搜索软件，点击安装，工具会自动下载并完成安装。

> **软件包管理器 ≈ 手机应用商店；它把“找软件、下载、安装、处理依赖”集中完成。**

Linux 中常见的软件包管理器如下：

| Linux 系统 | 常用软件包管理器 |
|---|---|
| CentOS、Red Hat | `yum` |
| Ubuntu | `apt` |

### 包管理器解决什么问题：依赖

软件通常不是单独工作的。例如，软件 A 运行时还需要软件 B 提供功能，软件 B 就是 A 的**依赖**：这个软件运行还需要陪着它的其他软件。

如果依赖没有安装，软件启动时就会报错；如果依赖版本太旧或太新，也可能无法正常工作。因此，包管理器不只是下载目标软件，还会检查并安装它需要的依赖。

```text
安装软件 A
    ↓
发现缺少依赖 B
    ↓
下载并安装 B
    ↓
安装 A
```

包管理器主要自动处理两类麻烦：

1. **依赖缺失**：需要的软件没有安装；
2. **版本兼容性**：已经安装的软件版本不适合当前软件。

> **包管理器的核心价值是自动解决依赖问题：发现缺失的依赖，并尽量选择兼容的版本。**

### 安装软件的本质

安装软件并不是把程序“变魔法”放进电脑，而是完成两件事：

1. 通过网络下载软件包；
2. 把其中的文件复制到系统规定的位置，并记录安装信息。

Linux 中有一个特殊用户叫 **root**：拥有整台电脑最高管理权限，可以修改系统文件、安装全系统软件。因为安装软件需要写入系统目录，所以通常必须使用 root 权限，或者用 `sudo` 临时借用 root 权限。

**`sudo`**：让当前命令临时以管理员身份执行。它可能要求输入当前用户密码。

软件安装到系统目录后，通常一次安装即可让这台电脑上的所有用户使用，而不是只对某一个用户有效。

## 1-2 Linux 软件生态

### 评估操作系统不能只看系统本身

**操作系统（OS）**：管理电脑硬件，并为其他软件提供运行环境的基础软件，例如 Linux、Windows。

判断一个操作系统是否好用，不能只看界面或某一个功能，还要看它周围的**软件生态**：围绕这个系统形成的内核、社区、文档、用户群体和配套软件。

| 组成部分 | 作用 |
|---|---|
| 内核 | 负责管理 CPU、内存、硬盘等硬件 |
| 社区 | 用户和开发者交流、解决问题 |
| 文档 | 说明如何安装、配置和使用 |
| 用户群体 | 使用者越多，经验和解决方案通常越丰富 |
| 配套软件 | 能否方便地安装开发工具、服务器软件等 |

> **操作系统的好坏不仅取决于系统本身，还取决于内核、社区、文档、用户群体和配套软件组成的软件生态。**

### Linux 软件是怎样到达电脑的

Linux 中的软件通常经历下面的链条：

```text
开发者发布源码
    ↓
社区编译并打包
    ↓
软件包放到官方源服务器
    ↓
yum 或 apt 下载
    ↓
安装到用户的 Linux 电脑
```

这里的**软件源**：存放软件包、供包管理器下载的服务器地址或服务器集合。软件源里的“源”可以理解为软件的下载仓库。

### 开源与软件生态

**开源**：软件作者公开源代码，其他人可以查看、修改和传播，但必须遵守对应的授权规则。

开源并不等于“没有商业价值”。企业可以围绕开源软件提供服务器、技术支持、定制开发、培训和云服务。大量开发者共同维护软件，也能降低软件传播和改进的成本。

> **开源本质上是一种商业模式：代码可以开放，但企业仍可通过服务、支持、定制和平台获得收入。**

### 软件源与镜像源

`yum` 或 `apt` 内部已经保存了软件源的下载链接，所以用户通常只需要输入安装命令，不必自己寻找每个软件的下载地址。

如果某个软件源距离电脑很远，下载速度可能较慢；这时可以把内置链接改成另一个服务器的地址。这个过程叫**切换镜像源**。

**镜像源**：保存了同样软件包内容的另一台服务器，可以理解为软件源的“复制站点”。

国内常见镜像源包括：

- 阿里云镜像；
- 清华大学镜像；
- 中国科学技术大学镜像。

## 1-3 `yum` 具体操作

### 使用前先确认网络

包管理器需要从服务器下载软件。如果网络不通，就算命令写对了，也无法安装。

**`ping`**：向指定地址发送测试数据，用来检查网络是否能连通。

#### 语法

```bash
ping 地址
```

#### 功能

测试当前电脑是否能访问指定地址。

#### 示例

```bash
ping www.baidu.com
```

如果持续显示收到回复，通常说明网络基本连通。按 `Ctrl+C` 可以停止测试。

#### 注意事项

`ping` 能够连通，只能说明基本网络可用，不代表所有软件源都一定正常；但如果完全无法连通，就应先解决网络问题。

### CentOS 的三板斧

在 CentOS 中，最常用的操作可以记成“查、装、卸”：

```text
查：yum list | grep 包名
装：sudo yum install [-y] 包名
卸：sudo yum remove [-y] 包名
```

#### 1. 查询软件：`yum list | grep 包名`

**`grep`**：从一大段文字中筛选出包含指定内容的行。这里先列出软件包，再用 `grep` 找出名称中包含目标文字的结果。

##### 语法

```bash
yum list | grep 包名
```

##### 功能

查询软件源中是否存在指定软件包，并显示相关版本信息。

##### 示例

```bash
yum list | grep vim
```

这会筛选出名称中包含 `vim` 的软件包。

##### 注意事项

- `|` 叫**管道**：把前一个命令的输出交给后一个命令处理；
- `grep` 匹配的是文字，输入的名称不一定必须完整；
- 查不到结果，可能是包名写错、软件源未配置或网络有问题。

#### 2. 安装软件：`sudo yum install [-y] 包名`

##### 语法

```bash
sudo yum install [-y] 包名
```

其中，`[-y]` 表示这个选项可以省略。`-y` 的作用是自动回答安装过程中的确认问题。

##### 功能

下载并安装指定软件包，同时自动处理它的依赖。

##### 示例

```bash
sudo yum install -y vim
```

这个命令会以管理员权限安装 `vim`，并自动确认安装。

##### 注意事项

- `sudo` 表示临时使用管理员权限；
- 不写 `-y` 时，`yum` 通常会先询问是否继续；
- 软件包安装通常需要网络；
- 同一时刻只能运行一个安装、卸载或更新操作，否则可能发生软件包管理器被占用的错误。

#### 3. 卸载软件：`sudo yum remove [-y] 包名`

##### 语法

```bash
sudo yum remove [-y] 包名
```

##### 功能

卸载已经安装的软件包。

##### 示例

```bash
sudo yum remove -y vim
```

##### 注意事项

卸载某个软件时，可能连带处理只为它服务的依赖。执行前应确认软件名称，避免误删仍在使用的程序。

### Ubuntu 中的对应操作

Ubuntu 使用 `apt`，操作思路与 `yum` 类似，但命令名称不同。

| 目的 | `yum` | `apt` |
|---|---|---|
| 搜索软件 | `yum list \| grep 包名` | `apt search 包名` |
| 查看信息 | 通过查询结果查看 | `apt show 包名` |
| 安装 | `sudo yum install 包名` | `sudo apt install 包名` |
| 卸载 | `sudo yum remove 包名` | `sudo apt remove 包名` |

#### 搜索软件：`apt search`

##### 语法

```bash
apt search 包名
```

##### 功能

在 Ubuntu 的软件源中搜索相关软件包。

##### 示例

```bash
apt search vim
```

#### 查看软件信息：`apt show`

##### 语法

```bash
apt show 包名
```

##### 功能

查看软件包的详细信息，例如版本、大小和依赖等。

##### 示例

```bash
apt show vim
```

#### 安装和卸载：`apt install`、`apt remove`

##### 语法

```bash
sudo apt install 包名
sudo apt remove 包名
```

##### 示例

```bash
sudo apt install vim
sudo apt remove vim
```

##### 注意事项

`apt` 同样通常需要 `sudo`，并且同一时刻只能进行一个软件包管理操作。遇到报错时，应把完整报错文字复制出来搜索，因为报错信息通常会说明缺少什么或哪里不匹配。

### 如何读软件包名称

查询结果中经常会出现类似下面的内容：

```text
some-package.x86_64  1.0-3.el7  base
```

各部分含义如下：

| 部分 | 含义 |
|---|---|
| `x86_64` | 适用于 64 位处理器的版本 |
| `el7` | 面向 Enterprise Linux 7，也就是 CentOS 7 等系统 |
| `base` | 提供这个软件包的软件源名称 |

**软件包名称中包含系统版本和处理器架构信息，是为了让包管理器选择适合当前系统的版本。**

### 软件由需求驱动

不需要的软件不应为了“先装上”而安装。因为软件越多，管理、升级和排查问题的范围就越大；真正需要某个功能时，再根据需求搜索并安装对应软件。

> **软件安装应由实际需求驱动：需要什么功能，就查找并安装什么软件。**

## 1-4 安装源

### CentOS 的软件源配置位置

CentOS 会把 `yum` 的软件源配置文件放在：

```text
/etc/yum.repos.d/
```

**配置文件**：保存程序运行所需设置的文本文件。这里的文件记录了软件源的地址、名称以及是否启用等信息。

常见文件如下：

| 文件 | 作用 |
|---|---|
| `CentOS-Base.repo` | CentOS 标准软件源，通常更稳定 |
| `epel.repo` | EPEL 扩展软件源，软件种类更多 |

**EPEL**：为 Enterprise Linux 系统提供额外软件包的扩展源。它的特点是软件更全，但首先要安装对应的源配置。

> **`CentOS-Base.repo` 偏重稳定，`epel.repo` 偏重软件齐全；使用哪一个取决于当前需求。**

### 安装 EPEL 扩展源

#### 语法

```bash
sudo yum install -y epel-release
```

#### 功能

安装 `epel-release` 软件包，使系统获得 EPEL 软件源的配置。

#### 示例

```bash
sudo yum install -y epel-release
```

安装完成后，`yum` 就可以从 EPEL 扩展源中搜索和安装其中提供的软件。

#### 注意事项

- 命令需要 `sudo`，因为它会修改系统软件源配置；
- 需要网络正常；
- 云服务器通常已经配置好国内软件源，速度较快，一般不需要再手动更换镜像源；
- 软件源配置错误可能导致后续软件搜索和安装失败。

## 2. 编辑器 Vim

### 2-1 Linux 编辑器：Vim 使用

写程序时，通常需要完成三件不同的事：写代码、把代码变成可运行程序、查找程序中的错误。因为这三件事解决的问题不同，所以分别由不同工具完成：

| 工具 | 解决的问题 | 典型操作 |
|---|---|---|
| 编辑器 | 编写和修改文字、代码 | 输入、删除、复制 |
| 编译器 | 把源代码翻译成程序 | 将 `.cpp` 文件编译成可执行文件 |
| 调试器 | 查找程序运行中的错误 | 单步执行、查看变量 |

`Vim` 是一个**编辑器：专门用来打开、修改和保存文件的工具**，它本身不是编译器，也不是调试器。

`IDE` 是**集成开发环境：把编辑器、编译器、调试器等工具集中到一个软件里**。例如，IDE 里可以一边写代码、一边点击按钮编译和调试；而使用 Vim 时，这些工具通常要分别使用。

> **Vim 只是编辑器，不能把编辑、编译、调试混为一谈；它与 IDE 的主要区别是功能更加分散。**

`vi` 是 Linux/Unix 中较早的编辑器，`vim` 是它的升级版。`vim` 兼容 `vi` 的全部指令，并增加了更多功能，因此课堂统一使用 `vim`。

### 2-2 Vim 的基本概念

#### 多模式是 Vim 的核心

新手使用普通文本框时，键盘输入的内容通常会直接出现在文件里。但 Vim 中，同一个按键在不同情况下可能有不同作用：有时表示输入字母，有时表示删除或移动光标。

为了解决“同一个按键如何完成不同操作”的问题，Vim 把操作分成不同的**模式：决定键盘按键当前用途的工作状态**。

Vim 最重要的是三种模式：

| 模式 | 主要用途 | 典型操作 |
|---|---|---|
| 正常模式，也叫命令模式 | 操作已有内容 | 移动光标、删除、复制 |
| 插入模式 | 输入新文字 | 编写代码、修改文字 |
| 末行模式 | 执行文件级命令 | 保存、退出、查找、替换 |

Vim 实际上共有 12 种模式，但日常学习和使用时，掌握上面 3 种即可。

```text
打开 Vim
   ↓
正常模式
   ├── i/a/o → 插入模式 → ESC → 正常模式
   └── :     → 末行模式 → Enter/ESC → 正常模式
```

> **Vim 的所有操作都围绕模式展开：想输入文字要进入插入模式，想移动或删除通常回到正常模式，想保存或退出进入末行模式。**

### 2-3 Vim 的基本操作

#### 进入 Vim 和切换模式

在终端中使用下面的命令打开文件：

```bash
vim 文件名
```

例如：

```bash
vim main.cpp
```

功能：打开 `main.cpp`；如果文件不存在，保存时可以创建它。进入 Vim 后，默认处于正常模式，此时直接按字母不会正常输入文字，而是在执行命令。

常用的进入插入模式的方式如下：

| 按键 | 功能 |
|---|---|
| `i` | 在光标前开始输入 |
| `a` | 在光标后开始输入 |
| `o` | 在当前行下方新建一行并开始输入 |

示例：打开文件后按 `i`，再输入以下代码：

```cpp
#include <iostream>

int main() {
    std::cout << "Hello Vim" << std::endl;
    return 0;
}
```

在插入模式中输入完成后，按 `Esc` 回到正常模式。`Esc` 很重要，因为保存、删除、复制等操作通常要在正常模式下执行。

在正常模式按 `:`，底部会出现命令输入位置，进入末行模式。例如：

```text
:w
```

输入完成后按 `Enter` 执行命令。

#### 保存和退出

| 命令 | 功能 |
|---|---|
| `:w` | 保存文件，继续留在 Vim 中 |
| `:wq` | 保存文件并退出 Vim |
| `:q!` | 不保存修改，强制退出 Vim |

例如，修改文件后执行：

```text
:wq
```

功能：先保存，再退出。

如果文件有未保存修改，直接执行 `:q` 通常会退出失败；如果确定不要这些修改，可以执行：

```text
:q!
```

注意：`!` 表示强制执行，使用 `:q!` 会丢失本次未保存的内容。

#### 批量注释

逐行输入注释符号很麻烦。例如，下面三行代码都要加上 `//`：

```cpp
int a = 1;
int b = 2;
int c = 3;
```

因为这些行的位置连续，所以可以一次选中同一列，再统一插入 `//`。Vim 中这种按矩形区域选择文字的方式叫**块选择：按列选择一块区域**。

操作步骤：

1. 回到正常模式，按 `Ctrl+v` 开始块选择。
2. 使用方向键或 `h/j/k/l` 选中多行开头的位置。
3. 按 `Shift+i`，也就是大写 `I`，进入插入状态。
4. 输入 `//`。
5. 按 `Esc`，Vim 会在选中的每一行开头插入 `//`。

结果：

```cpp
//int a = 1;
//int b = 2;
//int c = 3;
```

去掉这些注释时：

1. 回到正常模式，按 `Ctrl+v`。
2. 选中每行开头的 `//`。
3. 按 `d` 删除选中的区域。

> **批量注释的核心是：`Ctrl+v` 按列选中，`Shift+i` 统一插入，`Esc` 应用到所有选中行；去注释则选中注释符号后按 `d`。**

### 2-4 Vim 正常模式命令集

正常模式主要负责移动、删除、复制和修改已有内容。下面的 `#` 表示一个数字，例如 `3x` 中的 `3` 可以替换为任意数量。

#### 移动光标

| 命令 | 功能 |
|---|---|
| `h` | 向左移动 |
| `j` | 向下移动 |
| `k` | 向上移动 |
| `l` | 向右移动 |
| `G` | 移动到文件末尾 |
| `gg` | 移动到文件开头 |
| `$` | 移动到当前行行尾 |
| `^` | 移动到当前行行首 |
| `w` | 跳到下一个单词开头 |
| `e` | 跳到当前或下一个单词结尾 |
| `b` | 跳到上一个单词开头 |
| `Ctrl+f` | 向后翻一整页 |
| `Ctrl+b` | 向前翻一整页 |
| `Ctrl+d` | 向后翻半页 |
| `Ctrl+u` | 向前翻半页 |

这里的方向可以理解为：`j` 对应向下，`k` 对应向上；`h` 和 `l` 分别对应左、右。

#### 删除

| 命令 | 功能 |
|---|---|
| `x` | 删除光标所在字符 |
| `#x` | 连续删除 `#` 个字符 |
| `dd` | 删除当前行 |
| `#dd` | 从当前行开始删除 `#` 行 |

例如：

```text
3x
```

# 3. 编译器 `gcc/g++`

`gcc` 和 `g++` 是把源代码转换成可运行程序的工具：通常 `gcc` 用于编译 C 代码，`g++` 用于编译 C++ 代码。

## 3-1 背景知识

### 语言 → 编译器 → 可执行程序

我们写的代码是给人看的，例如：

```c
#include <stdio.h>

int main(void) {
    printf("hello\n");
    return 0;
}
```

但计算机处理器不能直接理解 `printf`、`main` 这些文字，它只能执行机器指令。因此需要**编译器**：把人写的源代码翻译成计算机能执行的指令。最后得到的**可执行程序**，就是可以直接运行的文件。

```text
C/C++源代码
    ↓ 编译器 gcc/g++
可执行程序
    ↓
计算机运行
```

> **语言解决“如何描述任务”，编译器负责“翻译任务”，可执行程序负责“真正运行”。**

### 编译的四个阶段

完整编译不是一步完成的，而是依次经过四个阶段：

```text
预处理 → 编译 → 汇编 → 链接
```

| 阶段 | 主要工作 | 产生的结果 |
|---|---|---|
| 预处理 | 修改源代码文本，例如展开头文件、替换宏 | 处理后的源代码 |
| 编译 | 把源代码翻译成汇编代码 | 汇编代码 |
| 汇编 | 把汇编代码翻译成机器码 | 目标文件 `.o` |
| 链接 | 合并多个目标文件，并补上库中的代码 | 可执行程序 |

**汇编代码**是机器指令的可读写法，例如用 `add` 表示加法。**机器码**是处理器真正执行的二进制指令，人通常不直接阅读它。**链接**是把多个编译结果和需要的库代码合并起来。

> **编译过程不是“源代码直接变成程序”，而是预处理、编译、汇编、链接四步逐层转换。**

---

## 3-2 `gcc` 编译选项

### 基本格式

```bash
gcc [选项] 源文件 -o 目标文件
```

- `gcc`：调用 C 编译器。
- `[选项]`：指定编译阶段或其他行为。
- `源文件`：我们写的代码文件，例如 `hello.c`。
- `-o`：指定输出文件名。
- `目标文件`：编译后生成的文件。

例如，将 `hello.c` 编译成名为 `hello` 的可执行程序：

```bash
gcc hello.c -o hello
```

运行程序：

```bash
./hello
```

`./` 表示“当前目录”。Linux 默认不会因为文件在当前目录，就自动搜索并运行它，所以需要写出 `./hello`。

### 预处理

源代码中经常有头文件、宏和条件编译。**预处理**就是在正式编译前，先根据规则修改源代码文本。

预处理主要完成：

- 宏替换；
- 删除注释；
- 条件编译；
- 展开头文件。

命令格式：

```bash
gcc -E 源文件 -o 预处理结果
```

示例：

```bash
gcc -E hello.c -o hello.i
```

这里：

- `-E`：只执行预处理；
- `hello.c`：输入的 C 源文件；
- `-o hello.i`：把预处理后的文本保存为 `hello.i`。

可以查看结果：

```bash
less hello.i
```

> **预处理的本质就是修改我们的文本代码，而不是生成机器码。**

例如，源文件中有：

```c
#define NUMBER 100

int main(void) {
    return NUMBER;
}
```

预处理后，宏 `NUMBER` 会被替换成 `100`，效果类似：

```c
int main(void) {
    return 100;
}
```

#### 条件编译

有时同一份源代码需要根据不同版本保留不同功能。例如，专业版包含收费功能，普通版不包含；或者内核根据硬件情况裁剪功能。**条件编译**就是根据条件决定哪些代码参与编译。

示例文件 `feature.c`：

```c
#include <stdio.h>

int main(void) {
#ifdef PRO版
    printf("professional feature\n");
#else
    printf("basic feature\n");
#endif

    return 0;
}
```

不定义宏时：

```bash
gcc feature.c -o feature
./feature
```

输出：

```text
basic feature
```

编译时通过命令行定义宏：

```bash
gcc -DPRO版 feature.c -o feature
./feature
```

输出：

```text
professional feature
```

命令行宏定义的语法是：

```bash
gcc -DM 源文件 -o 目标文件
gcc -DM=100 源文件 -o 目标文件
```

- `-DM`：定义宏 `M`，相当于在代码中写 `#define M`。
- `-DM=100`：定义宏 `M`，并令它的值为 `100`，相当于写 `#define M 100`。

条件编译常用于专业版和普通版的功能裁剪，也用于根据硬件、平台或配置裁剪内核源代码。

### 编译：生成汇编代码

预处理后的代码仍然是 C 语言，处理器不能直接执行。编译器需要把它翻译成**汇编代码**，即用容易阅读的文字表示机器指令。

命令格式：

```bash
gcc -S 输入文件 -o 汇编文件
```

示例：

```bash
gcc -S hello.i -o hello.s
```

- `-S`：执行到编译阶段，停止生成汇编代码；
- `hello.i`：预处理后的 C 代码；
- `hello.s`：生成的汇编文件。

### 汇编：生成目标文件

**目标文件**是已经包含机器码、但还没有完成最终合并的文件，通常使用 `.o` 作为后缀。

命令格式：

```bash
gcc -c 汇编文件 -o 目标文件
```

示例：

```bash
gcc -c hello.s -o hello.o
```

- `-c`：执行汇编，但暂时不进行链接；
- `hello.s`：汇编代码；
- `hello.o`：包含机器码的目标文件。

### 链接：生成可执行程序

目标文件中可能还缺少其他代码。例如，程序调用了 `printf`，但 `printf` 的具体实现不在 `hello.o` 中，因此需要**链接器**：把目标文件和库中的代码、地址等信息合并起来，生成最终程序。

命令格式：

```bash
gcc 目标文件 -o 可执行程序
```

示例：

```bash
gcc hello.o -o hello
```

完整的分阶段流程是：

```bash
gcc -E hello.c -o hello.i
gcc -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello
```

也可以直接让 `gcc` 自动完成全部阶段：

```bash
gcc hello.c -o hello
```

#### 为什么先生成汇编代码

最早的计算机编程甚至使用打孔纸带或打孔卡片：不同孔洞组合代表不同指令。这样编程非常困难，于是人们发明了用短单词表示机器指令的**汇编语言**，例如用 `add` 表示加法。

后来又出现了更接近人类表达方式的高级语言，例如 C 语言。高级语言不能直接被处理器执行，所以需要：

```text
高级语言 → 汇编语言 → 机器码
```

这种逐层转换，是从打孔编程到汇编，再到高级语言的发展结果。

**编译器自举**是指用某种语言编写这门语言自己的编译器。例如，C 编译器可以用 C 语言编写。这个概念只需理解为“编译器也可以由同类语言编写”。

## 3-3 动态链接和静态链接

### 多文件编译

一个大型程序通常不写在一个文件中，而是分成多个源文件。每个源文件可以单独编译成 `.o` 目标文件，最后再统一链接。

例如：

```bash
gcc -c main.c -o main.o
gcc -c math.c -o math.o
gcc main.o math.o -o app
```

流程如下：

```text
main.c → main.o ┐
                ├→ 链接 → app
math.c → math.o ┘
```

这样修改 `math.c` 时，只需重新生成 `math.o`，不必重新编译没有变化的 `main.c`。

### 静态链接

**静态链接**是指在生成程序时，把需要的库代码直接复制进可执行程序。

它的优点是：

- 程序运行时不需要再寻找外部库；
- 运行环境更独立；
- 库代码已经放入程序，运行时通常更直接。

它的缺点是：

- 多个程序都使用同一份库时，每个程序都保存一份副本，浪费磁盘空间和内存；
- 库更新后，已经生成的程序不会自动获得新库，通常需要重新链接甚至重新编译所有程序。

### 动态链接

**动态链接**是指程序运行时，才加载需要的库。库代码不直接复制到每个程序中，而是由多个程序共同使用。

查看程序依赖哪些动态库：

```bash
ldd hello
```

`ldd` 是查看动态链接依赖的命令。输出中通常会看到类似：

```text
libc.so.6 => /lib64/libc.so.6
```

`printf` 的具体实现就在 C 标准库的动态库 `libc.so.6` 中。`gcc` 链接程序时，会根据需要去系统库目录中寻找它，常见目录包括 `/usr/lib` 或 `/lib64`。这就是链接的作用之一：找到程序所需的外部代码，并记录或合并它们。

> **动态链接把公共库留在系统中，程序运行时再加载；静态链接则在生成程序时把库代码复制进去。**

## 3-4 静态库和动态库

### 静态库 `.a`

**静态库**是提前打包好的代码集合，文件后缀通常是 `.a`。进行静态链接时，库中被需要的代码会被复制到可执行文件中。

```text
静态库 .a + 目标文件 .o
              ↓ 链接
       可执行程序
```

程序生成后，即使删除这个静态库，程序通常仍然可以运行，因为所需代码已经被放进可执行文件。

### 动态库 `.so`

**动态库**也是提前准备好的公共代码集合，文件后缀通常是 `.so`。进行动态链接时，库代码不会全部复制进可执行文件，而是在程序运行时才加载。

```text
可执行程序 + 动态库 .so
       ↓ 运行时加载
       程序运行
```

`gcc` 默认使用动态链接。也就是说，直接执行：

```bash
gcc hello.c -o hello
```

通常会生成依赖动态库的程序。

Windows 中对应的常见文件类型是：

| Linux | Windows |
|---|---|
| 动态库 `.so` | 动态库 `.dll` |
| 静态库 `.a` | 静态库 `.lib` |

### 网吧例子

动态链接可以类比为去网吧上网：

- 网吧相当于动态库；
- 每个人的程序相当于去上网的人；
- 大家共同使用网吧的电脑，不需要每个人都买一台电脑；
- 如果网吧关门，依赖它的人都无法继续上网。

静态链接可以类比为把网吧电脑买回家：

- 链接时把库代码复制到自己的程序中；
- 程序生成后，原来的静态库就不再是运行所必需的；
- 但每个人都买一台电脑，会占用更多空间和成本。

### 动态链接和静态链接对比

| 对比项 | 动态链接 | 静态链接 |
|---|---|---|
| 库代码位置 | 运行时从动态库加载 | 生成程序时复制进程序 |
| 可执行程序体积 | 较小 | 较大 |
| 是否依赖外部库 | 依赖，动态库不能缺失 | 通常不依赖对应的外部库 |
| 多个程序共享代码 | 可以共享 | 每个程序各有副本 |
| 内存和磁盘 | 节省资源 | 可能有大量重复代码 |
| 库更新 | 替换动态库后，多个程序可能共同使用新版本 | 通常需要重新链接程序 |
| `gcc` 默认方式 | 是 | 否 |

动态库的关键本质是：同一份公共代码可以被多个程序共同使用，在内存中尽量只保留一份，而不是每个程序都复制一份。

> **动态链接的本质，是让多个程序共享内存中的同一份公共代码，从而节省内存和磁盘空间。**

### 云服务器上使用静态链接

有些云服务器默认没有安装静态库文件。`yum` 是一些 Linux 系统中用于安装软件包的工具；下面的命令安装 C 运行库和 C++ 标准库的静态版本：

```bash
yum install glibc-static libstdc++-static -y
```

- `glibc-static`：C 运行库的静态库；
- `libstdc++-static`：C++ 标准库的静态库；
- `-y`：安装时自动回答确认。

安装后，才可以尝试静态链接：

```bash
gcc -static hello.c -o hello
```

如果没有安装所需静态库，可能出现：

```text
cannot find -lc
```

其中 `-lc` 表示需要链接 C 标准库；`cannot find` 表示找不到它。

### 验证链接方式

使用 `file` 查看文件基本信息：

```bash
file hello
```

如果是动态链接程序，输出中通常包含：

```text
dynamically linked
```

如果是静态链接程序，输出中通常包含：

```text
statically linked
```

使用 `ldd` 查看动态库依赖：

```bash
ldd hello
```

- 能列出多个 `.so` 动态库，说明程序依赖动态库；
- 静态链接程序通常不会列出动态库依赖，可能显示 `not a dynamic executable`。

## 3-5 `gcc` 其他常用选项

以下选项先了解用途：

| 选项 | 功能 |
|---|---|
| `-E` | 只进行预处理 |
| `-S` | 编译到汇编代码后停止 |
| `-c` | 编译、汇编生成 `.o`，但不链接 |
| `-o` | 指定输出文件名 |
| `-static` | 使用静态链接 |
| `-g` | 加入调试信息，供 `gdb` 调试器使用 |
| `-shared` | 生成动态库 |
| `-O0` 到 `-O3` | 设置优化级别 |
| `-w` | 关闭警告 |
| `-Wall` | 打开常用编译警告 |

**调试信息**是程序中帮助定位错误的额外信息，例如源代码行号；`gdb` 是调试器，即帮助逐步运行程序、查看变量和定位错误的工具。因此使用 `gdb` 调试时通常需要：

```bash
gcc -g hello.c -o hello
```

`-O0` 到 `-O3` 是优化级别：

- `-O0`：不优化，便于调试；
- `-O1`、`-O2`：逐步增加优化；
- `-O3`：进行更积极的优化。

`-w` 会关闭警告：

```bash
gcc -w hello.c -o hello
```

`-Wall` 会打开一组常用警告：

```bash
gcc -Wall hello.c -o hello
```

实际开发中通常更推荐使用 `-Wall`，因为警告能够提前提示潜在问题。

# 4. 自动化构建：`make` / `Makefile`

## 4-1 背景

### 手动编译遇到的问题

小程序只有一个源文件时，可以手动执行：

```bash
gcc -o myproc myproc.c
```

`gcc` 是编译器：把人写的源代码转换成计算机可以运行的程序。

但大型工程可能有成千上万个源文件。每次修改一个文件后，如果都手动输入编译命令，就会遇到两个问题：

1. 需要记住大量编译命令；
2. 没修改的文件也可能被重复编译，浪费时间。

因此，需要一个文件先记录“哪些文件依赖哪些文件”以及“如何生成它们”，再用一个命令自动完成编译。

### `make` 和 `Makefile` 的区别

- `make`：一个命令，负责读取规则并执行编译。
- `Makefile`：一个文件，负责保存编译规则。

**`make` 是命令，`Makefile` 是文件；两者搭配完成自动化构建。**

> **关键结论：`Makefile` 负责说明“怎么编译”，`make` 负责按照说明自动执行。**

---

## 4-2 理解

### 依赖关系和依赖方法

假设要生成一个程序 `myproc`，它需要源文件 `myproc.c`。如果没有 `myproc.c`，就无法生成 `myproc`，这就是**依赖关系**：一个文件的生成需要另一个文件。

但是，仅仅知道依赖谁还不够，还需要知道如何根据 `myproc.c` 生成 `myproc`，这就是**依赖方法**：生成目标时要执行的命令。

因此，一条规则可以理解为：

```text
目标文件  ←  依赖文件
生成目标文件的方法
```

`Makefile` 中的基本形式是：

```makefile
目标:依赖
	生成目标的命令
```

其中：

- **目标**：想生成或操作的文件；
- **依赖**：生成目标所需要的文件；
- **命令**：生成目标时执行的操作。

### 月底要钱的例子

把“月底儿子向父亲要钱”类比成一条构建规则：

- 儿子：目标；
- 父亲：依赖；
- 打钱：依赖方法。

先要确定“儿子和父亲之间存在关系”，然后才有“打钱”这个动作。对应到构建过程，就是先写清楚目标依赖哪些文件，再写生成目标时执行什么命令。

**依赖关系决定“先找谁”，依赖方法决定“找到后做什么”。**

> **核心概念只有两个：依赖关系 + 依赖方法。先有依赖关系，才有执行依赖方法的依据。**

---

## 4-3 基本使用

### 一个完整的 `Makefile`

```makefile
myproc:myproc.c
	gcc -o myproc myproc.c

.PHONY:clean
clean:
	rm -f myproc
```

这个文件包含两条主要规则：

```text
myproc  ←  myproc.c
clean   ←  无文件依赖
```

第一条规则表示：程序 `myproc` 依赖源文件 `myproc.c`，生成它时执行：

```bash
gcc -o myproc myproc.c
```

第二条规则表示：目标 `clean` 被调用时，执行：

```bash
rm -f myproc
```

`rm` 是删除文件的命令，`-f` 表示即使文件不存在，也尽量不要报错。

### 规则的书写格式

#### 语法

```makefile
目标:依赖
	命令
```

#### 功能

- `目标:依赖`：声明目标和依赖之间的关系；
- 下一行的命令：说明如何生成或处理目标；
- 目标和依赖必须顶格写；
- 命令前必须使用一个真正的 `Tab`，不能用空格代替。

#### 示例

```makefile
myproc:myproc.c
	gcc -o myproc myproc.c
```

#### 注意事项

下面的缩进必须是 `Tab`：

```makefile
myproc:myproc.c
	gcc -o myproc myproc.c
```

如果把 `gcc` 前面的 `Tab` 换成空格，`make` 可能报错，因为 `make` 用缩进区分“规则声明”和“要执行的命令”。

### 使用 `make`

#### 语法

```bash
make [目标]
```

#### 功能

- 直接执行 `make`：执行 `Makefile` 中的第一个目标；
- 执行 `make clean`：明确要求执行名为 `clean` 的目标。

#### 示例

在包含 `Makefile` 和 `myproc.c` 的目录中执行：

```bash
make
```

等价于让 `make` 根据第一条规则决定是否执行：

```bash
gcc -o myproc myproc.c
```

执行清理操作：

```bash
make clean
```

这会执行：

```bash
rm -f myproc
```

#### 注意事项

`clean` 不会因为写在 `Makefile` 中就自动执行。直接执行 `make` 时，默认只处理第一个目标，也就是 `myproc`。

### `.PHONY` 和伪目标

#### 语法

```makefile
.PHONY:目标
```

#### 功能

`.PHONY` 用来声明一个**伪目标**。伪目标是“名字看起来像目标，但不一定对应真实文件”的目标。

例如：

```makefile
.PHONY:clean
clean:
	rm -f myproc
```

这里的 `clean` 通常不是一个真实文件，而是一个“执行清理命令”的名称。

#### 注意事项

如果当前目录中恰好存在一个名为 `clean` 的文件，没有声明 `.PHONY` 时，`make clean` 可能认为目标已经完成，从而不执行命令。

声明后：

```makefile
.PHONY:clean
```

`make` 会忽略同名文件的影响，每次执行：

```bash
make clean
```

都会运行清理命令。

> **`.PHONY` 的作用：让 `make` 忽略源文件和目标文件的时间对比，把目标当成每次都需要执行的伪目标。**

### 为什么不会重复编译

第一次执行：

```bash
make
```

如果 `myproc` 不存在，`make` 会执行编译命令，生成 `myproc`。

第二次执行：

```bash
make
```

如果 `myproc.c` 没有修改，`make` 通常不会再次编译。原因是 `make` 会比较目标文件和依赖文件的修改时间。

#### 文件的时间属性

文件不仅包含内容，还包含属性。常见的时间属性有：

| 属性 | 含义 |
|---|---|
| `Modify` | 文件内容最后一次被修改的时间 |
| `Change` | 文件属性或文件内容最后一次发生变化的时间 |
| `Access` | 文件最后一次被访问的时间 |

在判断是否需要重新构建时，`make` 主要比较文件的 `Modify` 时间。

#### 判断规则

假设有：

```text
myproc  ←  myproc.c
```

- `myproc` 不存在：执行命令；
- `myproc.c` 的修改时间比 `myproc` 新：执行命令；
- `myproc.c` 没有比 `myproc` 新：通常不执行命令。

因为依赖文件更新后，目标文件可能已经过时，所以需要重新生成。

> **`make` 默认不重复编译，是因为它比较目标文件和依赖文件的 `Modify` 时间；只有目标不存在或依赖更新得更晚时，才重新执行命令。**

## 4-4 推导过程

### 从源文件到可执行文件

程序通常不是直接从 `.c` 文件一步理解成最终程序，而是经过多个阶段。用依赖关系表示，可以写成：

```text
myproc
  ← myproc.o
    ← myproc.s
      ← myproc.i
        ← myproc.c
```

这些后缀表示不同阶段的文件：

- `.c`：C 源代码；
- `.i`：预处理后的代码；
- `.s`：汇编代码；
- `.o`：目标文件；
- `myproc`：最终可执行程序。

每个文件都依赖它下面的文件。例如：

```text
myproc  依赖 myproc.o
myproc.o  依赖 myproc.s
myproc.s  依赖 myproc.i
myproc.i  依赖 myproc.c
```

### 像栈一样执行

**栈**是一种“后进先出”的结构：最后放进去的内容最先取出来。

`make` 处理依赖链时，先沿着依赖关系向下查找，直到找到最底层的源文件；然后再从底层向上逐层生成目标：

```text
向下查找：myproc → myproc.o → myproc.s → myproc.i → myproc.c
向上生成：myproc.c → myproc.i → myproc.s → myproc.o → myproc
```

因此，依赖关系像入栈，生成过程像出栈。

> **`make` 先沿依赖链向下寻找最底层文件，再从底层向上逐层执行命令。**

### `make` 的工作方式

`make` 的基本流程是：

```text
查找 Makefile
    ↓
选择第一个目标作为默认最终目标
    ↓
判断目标是否不存在，或依赖是否比目标更新
    ↓
如果需要更新，执行当前目标的命令
    ↓
如果依赖不存在，继续向下寻找生成依赖的规则
    ↓
找不到规则时，报错并退出
```

具体来说：

1. `make` 先寻找 `Makefile`；
2. 直接执行 `make` 时，把第一个目标作为最终目标；
3. 如果目标不存在，执行它的命令；
4. 如果目标存在，但依赖文件比目标更新，执行它的命令；
5. 如果依赖文件不存在，继续查找“如何生成这个依赖”的规则；
6. 如果既找不到依赖文件，也找不到生成它的规则，就报错退出。

### `make` 不检查命令是否正确

`make` 只负责根据文件的依赖关系决定“是否执行命令”，不负责判断命令本身是否正确。

例如：

```makefile
myproc:myproc.c
	gcc -o myproc myproc.c
```

`make` 能判断 `myproc` 是否需要重新生成，但不会保证：

- `gcc` 是否安装；
- `myproc.c` 是否存在语法错误；
- 命令是否写错；
- 命令执行后是否真的生成了正确程序。

因此，`make` 管的是“文件之间的依赖性”，真正执行编译的仍然是命令本身。

## 4-5 适度扩展语法

### 变量

#### 语法

```makefile
变量名=值
```

使用变量时写成：

```makefile
$(变量名)
```

变量就是一个可以反复使用的名字，用来保存文件名、命令名或文件列表，避免同样的内容重复书写。

#### 示例

```makefile
BIN=proc.exe
CC=gcc
SRC=$(wildcard *.c)
OBJ=$(SRC:.c=.o)
```

各变量含义如下：

| 变量 | 含义 |
|---|---|
| `BIN` | 保存最终程序名 `proc.exe` |
| `CC` | 保存编译器命令 `gcc` |
| `SRC` | 保存当前目录下所有 `.c` 文件 |
| `OBJ` | 把 `SRC` 中每个 `.c` 文件名替换成对应的 `.o` 文件名 |

`$(wildcard *.c)` 的作用是查找当前目录中所有匹配 `*.c` 的文件。

`$(SRC:.c=.o)` 的作用是进行后缀替换，例如：

```text
a.c b.c
```

变成：

```text
a.o b.o
```

### 自动变量

自动变量只能在规则的命令中使用，`make` 会根据当前规则自动为它们填入内容。

| 自动变量 | 含义 |
|---|---|
| `$@` | 当前目标文件 |
| `$^` | 当前规则的全部依赖 |
| `$<` | 当前规则的第一个依赖 |

#### 示例

```makefile
myproc:myproc.c
	gcc -o $@ $<
```

执行这条规则时：

```text
$@  → myproc
$<  → myproc.c
```

因此等价于：

```bash
gcc -o myproc myproc.c
```

如果有多个依赖：

```makefile
myproc:main.o print.o
	gcc -o $@ $^
```

执行时：

```text
$@  → myproc
$^  → main.o print.o
```

因此等价于：

```bash
gcc -o myproc main.o print.o
```

### 模式匹配

#### 语法

```makefile
%.o:%.c
	命令
```

#### 功能

`%` 表示一个可以变化的部分。`%.o:%.c` 表示：

- 任意一个 `.o` 文件；
- 依赖同名的 `.c` 文件。

例如：

```text
main.o  ← main.c
print.o ← print.c
```

都可以匹配这条规则。

#### 示例

```makefile
%.o:%.c
	$(CC) -c $< -o $@
```

当处理 `main.o` 时：

```text
$<  → main.c
$@  → main.o
```

命令等价于：

```bash
gcc -c main.c -o main.o
```

### `@`：不回显命令

#### 语法

```makefile
目标:
	@命令
```

#### 功能

默认情况下，`make` 执行命令前，通常会先把命令显示在屏幕上。在命令前加 `@`，可以只执行命令而不显示这行命令。

#### 示例

```makefile
clean:
	@rm -f myproc
```

执行：

```bash
make clean
```

仍然会删除 `myproc`，但不会先显示：

```text
rm -f myproc
```

#### 注意事项

`@` 只影响命令是否回显，不改变命令本身的功能。

# 5. Linux 第一个系统程序——进度条

进度条看起来只是不断改变一行文字，但它依赖三个关键知识：

```text
打印文字
  ↓
控制光标回到行首
  ↓
刷新输出缓冲区
  ↓
同一行被不断覆盖，形成动态效果
```

---

## 5-1 补充：回车与换行

### 5-1-1 为什么要区分回车和换行

老式打字机有两个不同动作：打字头左右移动，纸张上下移动。如果只做其中一个动作，下一段文字的位置就可能不对。

因此，计算机把这两个动作分别表示为：

| 写法 | 名称 | 实际动作 |
|---|---|---|
| `\r` | 回车 | 回到当前行的行首 |
| `\n` | 换行 | 移动到下一行 |

`\r` 不会换到下一行，它只把光标拉回当前行开头；`\n` 也不负责回到行首，它只负责向下移动一行。

键盘上的回车键通常表示“回到下一行”，因此可以看作两个动作合在一起：

```text
\r\n = 回到行首 + 换到下一行
```

> **板书强调：`\r` 是回到行首，`\n` 是换到下一行，它们是两个动作；键盘回车键通常对应 `\r\n`。**

例如：

```cpp
#include <stdio.h>

int main(void)
{
    printf("第一行\r\n");
    printf("第二行\r\n");

    return 0;
}
```

这里的 `\r\n` 让光标先回到行首，再移动到下一行，所以两句话会显示在不同的行上。

---

## 5-2 行缓冲区

### 5-2-1 为什么调用 `printf` 后不一定马上看见文字

假设程序打印一段文字后要等待 3 秒：

```cpp
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hello");
    sleep(3);

    return 0;
}
```

有时程序运行后，等待期间看不到 `hello`，直到程序结束才显示。这不是 `printf` 没有执行，而是文字暂时没有送到显示器。

程序通常会先把输出文字放进一块临时内存中，等条件合适时再一次性送出去。这块临时内存叫**缓冲区**：可以把它理解为“先暂存数据的中转区”。

```text
printf
  ↓
输出缓冲区
  ↓
显示器
```

> **板书强调：文字可能已经被 `printf` 放进缓冲区，但还没有真正显示出来。**

### 5-2-2 什么是行缓冲

**行缓冲**：程序暂时保存一行输出，遇到换行符 `\n` 时，通常把这一行送到显示设备。

下面的程序通常会立即显示第一句话，因为它带有 `\n`：

```cpp
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hello\n");
    sleep(3);

    return 0;
}
```

而下面的程序没有 `\n`：

```cpp
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hello");
    sleep(3);

    return 0;
}
```

此时 `hello` 可能仍然停留在缓冲区中。除了遇到换行，缓冲区满了或程序结束时，也可能触发刷新。

**刷新**：把缓冲区中的内容真正发送到显示设备。

### 5-2-3 使用 `fflush(stdout)` 立即刷新

如果不想等待换行或程序结束，可以手动刷新输出。

```cpp
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hello");
    fflush(stdout);

    sleep(3);

    return 0;
}
```

`fflush(stdout)` 的含义是：立即把标准输出缓冲区中的内容发送出去。

#### 语法

```cpp
fflush(输出流);
```

#### 功能

强制刷新指定的输出流，让其中暂存的内容立即输出。

#### 示例

```cpp
printf("正在处理...");
fflush(stdout);
```

#### 注意事项

- `stdout` 表示标准输出，通常就是终端显示器。
- `fflush(stdout)` 只负责“把内容送出去”，不会自动换行。
- 动态进度条通常需要同时使用 `\r` 和 `fflush(stdout)`。

### 5-2-4 `stdin`、`stdout` 和 `stderr`

程序和外部设备之间的输入输出，通常通过几个标准流完成。

**标准流**：程序预先准备好的输入或输出通道。

```cpp
extern FILE *stdin;
extern FILE *stdout;
extern FILE *stderr;
```

| 名称 | 作用 |
|---|---|
| `stdin` | 标准输入，通常来自键盘 |
| `stdout` | 标准输出，通常显示到屏幕 |
| `stderr` | 标准错误输出，通常也显示到屏幕，用于错误信息 |

`FILE *` 可以先理解为“指向一个文件或输入输出通道的指针”。这里的 `stdout` 虽然名字中有“文件”，但它也可以连接到终端。

显示器本质上只能接收一个个字符，所以终端可以看作一种**字符设备**：按字符顺序接收并显示内容。

---

## 5-3 练手：倒计时程序

### 5-3-1 倒计时遇到的问题

普通写法会把每个数字打印到新位置：

```cpp
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    for (int i = 5; i >= 0; i--) {
        printf("%d\n", i);
        sleep(1);
    }

    return 0;
}
```

如果想让数字在同一行不断变化，就不能每次都换行。此时需要：

1. 用 `\r` 把光标移回当前行开头；
2. 用 `fflush(stdout)` 立即显示新数字。

### 5-3-2 `printf("%-2d\r", i);`

#### 语法

```cpp
printf("%-2d\r", i);
```

#### 功能

- `%d`：按照十进制整数输出 `i`；
- `2`：输出宽度至少为 2 个字符；
- `-`：内容靠左对齐；
- `\r`：输出后把光标移回当前行开头。

例如，数字从 `10` 变成 `9` 时，如果不补空格，旧字符可能残留在后面。`%-2d` 会让 `9` 占用两个字符宽度，相当于输出：

```text
9 
```

这样可以覆盖掉之前的 `10`。

#### 完整示例

```cpp
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    for (int i = 10; i >= 0; i--) {
        printf("%-2d\r", i);
        fflush(stdout);
        sleep(1);
    }

    printf("\n");

    return 0;
}
```

程序运行时，终端上会看到同一个位置的数字从 `10` 变到 `0`。

> **动态显示的核心组合是：`\r` 回到行首覆盖打印，`fflush(stdout)` 强制立即刷新。**

## 5-4 进度条代码

### 5-4-1 进度条的显示结构

一个简单的进度条可以设计成：

```text
[#########################                         ][53%][/]
```

其中：

- 第一部分表示已经完成的进度；
- `[53%]` 表示百分比；
- 最后的 `|`、`/`、`-`、`\` 是旋转光标，用来表示程序仍在工作。

旋转光标按照下面的顺序变化：

```text
| → / → - → \ → |
```

注意：反斜杠在 C 字符串中有特殊含义，因此要写成 `\\`。

---

### 5-4-2 version1：固定 101 格的原理版本

#### 解决的问题

最开始可以不考虑真实下载量，只模拟从 0% 增长到 100%。为了让进度条逐格增加，准备一个固定长度的字符数组：

```text
[                                                  ]
```

每完成一点，就把其中一个空格改成 `#`，然后重新输出整条进度条。

这里使用 100 个位置表示 0% 到 100%，数组还要额外留一个位置存放字符串结束标记 `\0`，所以数组大小是 `101`。

#### 完整代码

```cpp
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    char buffer[101];
    int spinner_index = 0;
    const char spinner[] = "|/-\\";

    memset(buffer, ' ', 100);
    buffer[100] = '\0';

    for (int i = 0; i <= 100; i++) {
        if (i > 0) {
            buffer[i - 1] = '#';
        }

        printf("\r[%s][%3d%%][%c]",
               buffer,
               i,
               spinner[spinner_index]);

        fflush(stdout);

        spinner_index = (spinner_index + 1) % 4;
        usleep(50000);
    }

    printf("\n");

    return 0;
}
```

#### 代码中的关键点

`memset(buffer, ' ', 100)` 把前 100 个位置全部填成空格，先得到一条空进度条。

```cpp
buffer[i - 1] = '#';
```

每循环一次，就把一个空格替换成 `#`。

```cpp
printf("\r[%s][%3d%%][%c]",
       buffer,
       i,
       spinner[spinner_index]);
```

- `\r`：回到当前行开头；
- `%s`：输出进度条字符串；
- `%3d`：百分比至少占 3 个字符，避免数字宽度变化导致画面抖动；
- `%%`：在 `printf` 中输出字面量 `%`；
- `%c`：输出一个旋转光标字符。

```cpp
spinner_index = (spinner_index + 1) % 4;
```

`spinner_index` 会在 `0`、`1`、`2`、`3` 之间循环，因此依次取出 `|`、`/`、`-`、`\`。

```cpp
fflush(stdout);
```

如果没有这一句，输出可能留在缓冲区中，进度条就不会及时变化。

> **version1 的核心是：用固定长度的字符数组保存进度条，每次填充一个位置，再用 `\r` 和 `fflush(stdout)` 重绘当前行。**

### 5-4-3 version2：根据真实进度更新

#### 为什么需要真实进度

模拟程序可以直接用 `i` 表示百分比，但真实下载时通常知道的是：

- 总大小 `total`；
- 当前已经下载的大小 `current`。

例如，总文件大小是 200 MB，已经下载 100 MB：

```text
百分比 = current / total × 100
       = 100 / 200 × 100
       = 50%
```

因此，需要一个函数根据总量和当前量计算进度。

### `FlushProcess(total, current)`

#### 语法

```cpp
void FlushProcess(int total, int current);
```

#### 功能

根据 `current` 占 `total` 的比例，刷新一次进度条。

#### 完整代码

```cpp
#include <stdio.h>
#include <unistd.h>

void FlushProcess(int total, int current)
{
    const int bar_width = 50;
    const char spinner[] = "|/-\\";
    static int spinner_index = 0;

    if (total <= 0) {
        return;
    }

    if (current > total) {
        current = total;
    }

    int percent = current * 100 / total;
    int filled = current * bar_width / total;

    printf("\r[");

    for (int i = 0; i < bar_width; i++) {
        if (i < filled) {
            printf("#");
        } else {
            printf(" ");
        }
    }

    printf("][%3d%%][%c]",
           percent,
           spinner[spinner_index]);

    fflush(stdout);

    spinner_index = (spinner_index + 1) % 4;
}

int main(void)
{
    int total = 100;

    for (int current = 0; current <= total; current++) {
        FlushProcess(total, current);
        usleep(50000);
    }

    printf("\n");

    return 0;
}
```

#### 关键计算

```cpp
int percent = current * 100 / total;
```

根据当前进度占总量的比例计算百分比。

```cpp
int filled = current * bar_width / total;
```

把百分比转换成进度条中需要填充的格数。这里进度条宽度是 50 格，所以完成一半时会填充 25 个 `#`。

#### 在下载场景中的使用方式

假设下载程序每次下载一部分数据，就调用一次：

```cpp
FlushProcess(total_size, downloaded_size);
```

完整流程是：

```text
下载一部分数据
  ↓
更新 current
  ↓
调用 FlushProcess(total, current)
  ↓
计算百分比和填充格数
  ↓
回到行首并刷新
```

例如，真实代码中可以是：

```cpp
int total_size = 1000;
int downloaded_size = 0;

while (downloaded_size < total_size) {
    downloaded_size += 20;
    FlushProcess(total_size, downloaded_size);
    usleep(100000);
}
```

实际项目中，`downloaded_size` 应该来自真实下载过程，而不是手动增加。

> **version2 的核心是：每下载一部分，就用 `current / total` 计算进度，再刷新同一行的进度条。**

### 5-4-4 配套 Makefile：自动化构建多个源文件

#### 为什么需要 Makefile

当程序只有一个 `.c` 文件时，手动编译还可以；但当项目有多个源文件时，每次都手动写编译命令容易漏文件、写错参数。

`Makefile`：记录“如何编译项目”的文本文件。`make` 会根据这些规则自动完成编译。

#### `wildcard`

`wildcard`：按照文件名模式批量找出符合条件的文件。

```makefile
SRCS := $(wildcard *.c)
```

表示找出当前目录下所有 `.c` 文件。

#### 模式规则

模式规则：用一个通用规则描述“某种文件应该如何生成”。

```makefile
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@
```

含义是：任何 `.c` 文件都可以按照这条规则编译成同名的 `.o` 文件。

- `$<`：当前规则的输入文件；
- `$@`：当前规则的输出文件；
- `-c`：只编译，不进行最后的链接；
- 命令前必须使用一个制表符，不能使用普通空格。

#### 完整 Makefile

```makefile
CC := gcc
CFLAGS := -Wall -Wextra -std=c11

TARGET := progress
SRCS := $(wildcard *.c)
OBJS := $(SRCS:.c=.o)

$(TARGET): $(OBJS)
	$(CC) $(OBJS) -o $(TARGET)

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

.PHONY: clean

clean:
	rm -f $(OBJS) $(TARGET)
```

#### 常用命令

```bash
make
```

根据 Makefile 编译程序。

```bash
./progress
```

运行生成的程序。

```bash
make clean
```

删除编译生成的 `.o` 文件和可执行文件。

Makefile 的自动化关系可以表示为：

```text
多个 .c 文件
  ↓ 逐个编译
多个 .o 文件
  ↓ 链接
progress 可执行程序
```

# 6. 版本控制器 Git

## 6-1 版本控制器

### 手动保存副本有什么问题

写报告或程序时，如果只靠手动复制文件，可能会出现：

```text
报告-v1
报告-v2
报告-最终版
报告-最终版2
报告-究极进化版
```

文件一多，就很难回答三个问题：哪一版是最新的？这次改了什么？如果改错了，怎样恢复到之前的版本？

**版本控制器：自动记录文件每次改动和版本变化的软件。**它不仅能保存历史版本，还能帮助多人同时开发同一个项目。

版本控制器主要解决两个问题：

1. **数据安全**：文件改错或误删后，可以找回以前的版本。
2. **协作开发**：多人修改同一个项目时，可以交换各自的修改，并记录是谁、什么时候改了什么。

> **版本控制器的两大价值是：数据安全和协作开发。**

### Git、本地仓库和远端仓库

如果每个人都把项目文件放在自己电脑上，其他人无法方便地获取最新修改。因此，需要一个专门保存项目历史记录的地方。

**Git：一种版本控制器软件，负责记录文件变化、保存版本并同步修改。**

**仓库：保存项目文件和版本历史记录的地方。**可以把它理解成“项目文件夹加上完整的修改记录”。

Git 通常涉及两个仓库：

| 名称 | 保存位置 | 作用 |
|---|---|---|
| 本地仓库 | 自己的电脑 | 保存自己提交的版本 |
| 远端仓库 | 云服务器或其他服务器 | 让多人共享和备份项目 |

Git 既可以作为操作本地仓库的工具，也可以通过网络和其他仓库交换数据，所以它既是 **client（客户端：主动连接并操作其他仓库的一方）**，也能作为 **server（服务器端：向其他电脑提供仓库数据的一方）**。

**GitHub** 和 **Gitee** 是基于 Git 建立的网站平台。它们提供云端仓库、网页管理和多人协作功能，但它们本身不是 Git 软件。

Git 是**分布式版本控制系统**：每个开发者的本地仓库都保存完整的版本历史，不是只能依赖一个中央服务器。即使暂时没有网络，也可以在本地查看历史、创建版本；联网后再与远端仓库同步。

```text
本地工作目录
    ↓ git add
暂存区
    ↓ git commit
本地仓库
    ↓ git push
远端仓库
```

> **本地仓库保证本地开发和历史记录，远端仓库用于备份和多人共享。**

---

## 6-2 Git 简史

Linux 内核是一个非常大的开源项目，需要很多人长期共同维护。早期没有 Git，开发者主要依靠手工发送和合并补丁。

**补丁：描述“应该对原文件做哪些修改”的文件。**

发展过程如下：

```text
1991—2002：主要依靠手工补丁维护 Linux 内核
       ↓
2002：使用商业版本控制软件 BitKeeper
       ↓
2005：BitKeeper 不再免费提供
       ↓
Linus Torvalds 自己开发 Git
```

Git 的设计目标是：

- **速度快**：快速处理大量文件和修改记录。
- **设计简单**：核心操作尽量清晰直接。
- **支持非线性开发**：可以让很多开发分支同时进行，再合并结果。
- **完全分布式**：每个本地仓库都拥有完整历史，不完全依赖中央服务器。
- **适合超大项目**：能够高效管理像 Linux 内核这样的巨大工程。

**分支：从项目当前版本分出的一条独立开发线路。**例如，一组人开发登录功能，另一组人开发支付功能，可以分别在不同分支中工作。

## 6-5 Git 三板斧

手动修改文件后，Git 不会自动把修改提交到仓库。因为有些修改可能只是临时尝试，Git 需要先让你选择哪些修改要保存。

Git 的基本流程是：

```text
修改工作目录中的文件
    ↓ git add
暂存区：准备提交的修改
    ↓ git commit
本地仓库：形成一个版本
    ↓ git push
远端仓库：与他人共享
```

**暂存区：提交前临时放置“准备保存哪些修改”的区域。**

### 第一板斧：`git add`

**语法：**

```bash
git add 文件名
```

**功能：**把指定文件当前的修改放入暂存区，告知 Git“这个文件的修改准备提交”。

**示例：**

```bash
git add main.cpp
```

如果要暂存当前目录下所有已修改文件，可以使用：

```bash
git add .
```

**注意事项：**

- `git add` 只是放入暂存区，还没有形成正式版本。
- 文件名必须写对。
- `.` 表示当前目录，使用时要确认当前目录中的文件都应该提交。

### 第二板斧：`git commit`

**语法：**

```bash
git commit -m "日志"
```

**功能：**把暂存区中的修改保存到本地仓库，形成一个新的版本；`-m` 后面的内容是本次提交的说明。

**示例：**

```bash
git commit -m "修复登录错误"
```

**注意事项：**

- 只有已经执行 `git add` 的修改，才会被这次 `commit` 提交。
- 日志应说明本次做了什么，例如“增加用户注册功能”，不要只写“修改”。
- `commit` 默认只保存发生变化的部分，不会把整个项目每次都复制一份。

> **提交只提交发生变化的部分，因此 Git 能节省空间，并清楚记录每次修改。**

### 第三板斧：`git push`

**语法：**

```bash
git push
```

**功能：**把本地仓库中已经提交的版本上传到远端仓库。

**示例：**

```bash
git push
```

**注意事项：**

- `push` 只能上传已经 `commit` 的内容，不能直接上传只执行了 `add` 的内容。
- 第一次推送时，可能需要登录 GitHub，或按提示设置远端分支。
- `push` 成功后，其他协作者才能从远端获取你的提交。

### 首次使用配置用户名和邮箱

Git 需要知道每次提交是谁完成的，因此第一次使用时要配置用户名和邮箱。

**语法：**

```bash
git config --global user.name "用户名"
git config --global user.email "邮箱"
```

**功能：**设置当前用户的提交身份；`--global` 表示对当前电脑上的所有 Git 项目生效。

**示例：**

```bash
git config --global user.name "Zhang San"
git config --global user.email "zhangsan@example.com"
```

**注意事项：**

- 邮箱应填写自己使用的邮箱。
- 这只是记录提交者身份，不等同于完成 GitHub 登录。

### 版本管理只管理源文件

**源文件：程序员编写、可以直接阅读和修改的代码文件。**例如 `.cpp`、`.h`、`.py` 等。

编译程序时，通常还会生成可执行文件、临时文件或缓存文件。这些文件可以由程序重新生成，不需要放进版本仓库，因此版本管理主要保存源文件和必要的配置文件。

> **版本管理主要管理源文件，不要把可执行文件、临时文件和缓存文件全部提交进去。**

### 使用 `.gitignore` 忽略文件

如果每次执行 `git add .` 都把临时文件加入暂存区，就需要反复手动删除。因此，可以告诉 Git 哪些文件不要管理。

**`.gitignore`：列出需要被 Git 忽略的文件名或文件后缀的配置文件。**

在项目根目录创建名为 `.gitignore` 的文件，例如：

```text
*.o
*.out
build/
```

含义是：

- `*.o`：忽略所有以 `.o` 结尾的文件。
- `*.out`：忽略所有以 `.out` 结尾的文件。
- `build/`：忽略名为 `build` 的目录。

**注意事项：**

- `.gitignore` 本身通常应该提交到仓库，让所有协作者使用同一套忽略规则。
- 已经被 Git 提交过的文件，后来再写入 `.gitignore`，不会自动从历史中消失；`.gitignore` 主要防止尚未被管理的文件被加入。

> **`.gitignore` 用来提前排除不应进入版本仓库的文件和目录。**

### `git push` 被拒绝时的冲突

有时执行 `git push` 会出现 `rejected`。这通常表示：远端仓库已经有了本地没有的更新。

例如：

```text
远端仓库：A —— B
本地仓库：A —— C
```

因为远端比本地更新，如果直接推送，Git 不知道如何安全地覆盖远端内容，所以拒绝操作。

**解决流程：**

```bash
git pull
git push
```

**`git pull`：从远端获取最新内容，并尝试合并到当前本地分支。**

先执行：

```bash
git pull
```

同步成功后，再执行：

```bash
git push
```

如果两边修改了同一位置，可能产生**冲突**。冲突就是 Git 无法自动判断应该保留哪一份修改，需要手动修改文件后，再执行 `git add`、`git commit` 和 `git push`。

> **远端比本地新时，先用 `git pull` 同步，再用 `git push` 上传。**

### 其他常用命令

#### `git status`

**语法：**

```bash
git status
```

**功能：**查看当前仓库状态，例如哪些文件被修改、哪些文件已经进入暂存区、哪些文件还没有被 Git 管理。

**示例：**

```bash
git status
```

它适合在 `add`、`commit` 前检查当前状态。

#### `git log`

**语法：**

```bash
git log
```

**功能：**查看本地仓库的提交历史，包括提交者、提交时间和提交日志。

**示例：**

```bash
git log
```

#### `git pull`

**语法：**

```bash
git pull
```

**功能：**获取远端仓库的新提交，并合并到当前本地仓库。

**示例：**

```bash
git pull
```

一个最基本的完整提交流程如下：

```bash
git status
git add main.cpp
git commit -m "完成主要功能"
git push
```

如果 `push` 被拒绝，则先同步：

```bash
git pull
git push
```

## 7. 调试器-gdb/cgdb使用

调试器：用来让程序暂停、逐步执行，并查看程序运行过程中变量值的工具。程序“能编译”不代表“运行结果正确”，调试器可以帮助我们找到错误发生的位置。

---

### 7-1 样例代码

如果直接运行程序，只能看到最终结果；如果结果不对，却不知道哪一步出错，就需要让程序在中途暂停，观察变量变化。下面的程序计算 `1+2+...+100`，后面用它演示调试。

`Sum` 是一个函数：把一段独立功能封装起来，需要时可以调用。

```c
#include <stdio.h>

int Sum(int start, int end)
{
    int i;
    int sum = 0;

    for (i = start; i <= end; i++)
    {
        sum = sum + i;
    }

    return sum;
}

int main()
{
    int result = Sum(1, 100);

    printf("sum = %d\n", result);

    return 0;
}
```

把代码保存为 `mycmd.c`。其中：

- `i` 表示当前累加到的数字；
- `sum` 保存当前累加结果；
- `Sum(1, 100)` 表示调用 `Sum` 函数，计算从 `1` 到 `100` 的累加值；
- `result` 保存 `Sum` 函数最终返回的结果。

---

### 7-2 预备

#### debug 和 release

程序发布时通常有两种模式：

- `debug`：测试用版本，保留调试所需信息，方便查看源码、变量和函数调用过程；
- `release`：上线用版本，通常更关注运行效率和文件大小，不保留完整调试信息。

**因为测试阶段需要定位错误，所以要使用 `debug`；因为上线阶段不需要调试信息，所以使用 `release`。**

> **板书强调：`debug` → 测试，`release` → 上线。**

`gcc` 是编译 C 语言程序的工具，`g++` 是编译 C++ 程序的工具。它们默认生成的程序通常是 `release` 类型，因此直接用默认命令编译，`gdb` 可能无法对应到源码和变量。

`-g` 的作用是把调试信息写入程序，所以调试时必须使用它：

```bash
gcc -g mycmd.c -o mycmd
```

命令含义如下：

- `gcc`：调用 C 语言编译器；
- `-g`：生成调试信息；
- `mycmd.c`：输入的源代码文件；
- `-o mycmd`：把生成的可执行程序命名为 `mycmd`。

如果不使用 `-g`：

```bash
gcc mycmd.c -o mycmd
```

程序通常可以运行，但调试器不能完整地把机器指令对应回源码行和变量名。

> **板书强调：默认编译通常没有调试信息；必须使用 `gcc -g` 编译 debug 版本，才能方便调试。**

#### 验证程序是否包含调试信息

仅看编译命令容易忘记是否加了 `-g`，因此可以检查生成的程序。

##### 使用 `file`

语法：

```bash
file 程序名
```

功能：查看文件类型以及是否包含调试信息。

示例：

```bash
file mycmd
```

如果输出中包含类似：

```text
with debug_info
```

说明程序包含调试信息，可以用于源码级调试。

注意：如果没有看到 `with debug_info`，通常说明程序不是用 `-g` 编译的，需要重新编译。

##### 使用 `readelf` 和 `grep`

`readelf`：读取可执行文件内部结构信息的工具。  
`grep`：从输出文字中筛选包含指定内容的行。

语法：

```bash
readelf -S 程序名 | grep -i debug
```

示例：

```bash
readelf -S mycmd | grep -i debug
```

这里的 `|` 叫管道：把前一个命令的输出交给后一个命令继续处理。

- `readelf -S mycmd`：查看 `mycmd` 的各个段；
- `grep -i debug`：筛选包含 `debug` 的内容，`-i` 表示不区分大小写；
- 如果看到 `.debug_info`、`.debug_line` 等段，说明程序包含调试信息。

> **板书强调：检查 debug 版本时，可以用 `file mycmd` 看 `with debug_info`，也可以用 `readelf -S mycmd | grep -i debug` 看 `.debug_info` 等段。**

### 7-3 常见使用

#### 进入和退出 `gdb`

如果程序运行结果不符合预期，只看最终输出无法知道错误发生在哪一步，于是需要进入 `gdb`。`gdb` 是 GNU 调试器，可以控制程序运行并查看内部状态。

语法：

```bash
gdb 程序名
```

示例：

```bash
gdb mycmd
```

进入后，命令行前通常会出现：

```text
(gdb)
```

退出方式：

```text
quit
```

也可以按：

```text
Ctrl+D
```

注意：必须先用带 `-g` 的程序进入 `gdb`，否则源码和变量信息可能无法正常显示。

#### 查看源码和运行程序

##### `list` / `l`

语法：

```text
list
```

或：

```text
l
```

功能：查看当前程序附近的源代码。

示例：

```text
(gdb) l
```

注意：`l` 是 `list` 的缩写，缩写命令通常更适合调试时快速输入。

##### `run` / `r`

语法：

```text
run
```

或：

```text
r
```

功能：从头运行程序，直到程序结束或遇到断点。

示例：

```text
(gdb) r
```

#### 设置和查看断点

程序运行太快，直接运行通常看不到中间过程。断点：让程序运行到指定位置时自动暂停的标记。

##### `break` / `b`

按行号设置断点：

```text
b 行号
```

示例：

```text
(gdb) b 9
```

表示运行到第 `9` 行时暂停。

也可以按函数名设置断点：

```text
b 函数名
```

示例：

```text
(gdb) b Sum
```

表示进入 `Sum` 函数时暂停。

##### `info b`

语法：

```text
info b
```

功能：查看当前已经设置的断点，包括断点编号、位置和是否启用。

示例：

```text
(gdb) info b
```

断点编号后面会用于删除、禁用或启用断点。

#### 逐步执行：`next` 和 `step`

程序暂停后，如果直接输入 `c`，会继续运行，可能再次错过中间过程。逐步执行可以让程序一条一条地走，观察每一步的变化。

##### `next` / `n`

语法：

```text
n
```

功能：执行当前行，然后停在下一行；如果当前行调用了函数，不进入函数内部。

示例：

```text
(gdb) n
```

例如当前行是：

```c
int result = Sum(1, 100);
```

使用 `n` 后，会把 `Sum` 当成一个整体执行完，再停到下一行。

`n` 大致对应图形化调试器中的 `F10`。

##### `step` / `s`

语法：

```text
s
```

功能：执行下一条语句；如果当前语句调用了函数，则进入函数内部。

示例：

```text
(gdb) s
```

执行 `int result = Sum(1, 100);` 时，使用 `s` 会进入 `Sum` 函数，停在函数内部的代码上。

`s` 大致对应图形化调试器中的 `F11`。

| 命令 | 是否进入被调用函数 | 类比 |
|---|---|---|
| `n` / `next` | 不进入，把函数整体执行完 | `F10` |
| `s` / `step` | 进入函数内部逐步执行 | `F11` |

> **板书强调：`n` 是逐过程，不进函数；`s` 是逐语句，会进函数。**

#### 从函数返回：`finish`

如果已经进入函数，但不想继续一行一行查看函数内部代码，可以让它执行到函数返回。

语法：

```text
finish
```

功能：继续执行当前函数，直到函数执行完并返回到调用位置。

示例：

```text
(gdb) finish
```

例如已经进入 `Sum` 函数，执行 `finish` 后，会回到 `main` 中调用 `Sum` 的位置附近。

#### 查看和修改变量

##### `print` / `p`

语法：

```text
p 变量名
```

功能：打印变量当前的值。

示例：

```text
(gdb) p sum
(gdb) p i
```

如果当前停在 `Sum` 函数中，就可以查看 `sum` 和 `i` 的值。

##### `set var`

语法：

```text
set var 变量名=值
```

功能：直接修改程序当前运行状态中的变量值。

示例：

```text
(gdb) set var sum=0
```

这只修改本次调试运行中的值，不会修改源代码文件。

#### 继续运行：`continue` / `c`

语法：

```text
c
```

或：

```text
continue
```

功能：从当前暂停位置继续运行，直到遇到下一个断点、程序结束或其他暂停原因。

示例：

```text
(gdb) c
```

#### 删除、禁用和启用断点

##### `delete` / `d`

语法：

```text
d 断点编号
```

功能：删除指定断点。

示例：

```text
(gdb) d 2
```

表示删除编号为 `2` 的断点。

##### `disable`

语法：

```text
disable 断点编号
```

功能：暂时禁用断点，但不删除它。

示例：

```text
(gdb) disable 2
```

##### `enable`

语法：

```text
enable 断点编号
```

功能：重新启用已经禁用的断点。

示例：

```text
(gdb) enable 2
```

`gdb` 不退出时，新设置的断点编号会依次递增。例如先设置了编号 `1` 和 `2` 的断点，删除 `2` 后，再设置新断点时通常会使用更大的编号，而不是自动补回 `2`。

#### 自动显示变量：`display`

逐步执行时，如果每次都手动输入 `p i`，会比较麻烦。`display` 可以让变量在程序每次暂停时自动显示。

语法：

```text
display 变量名
```

功能：每次程序暂停时，自动打印该变量的当前值。

示例：

```text
(gdb) display i
```

以后每次遇到断点或执行完 `n`、`s` 后，`gdb` 都会自动显示 `i`。

##### `undisplay`

语法：

```text
undisplay 显示编号
```

功能：取消某个自动显示项。

示例：

```text
(gdb) undisplay 1
```

其中 `1` 是 `display` 项的编号，不一定等于变量名。

#### 执行到指定行：`until`

逐行调试循环时，如果循环次数很多，一直输入 `n` 很慢。`until` 可以直接执行到指定行。

语法：

```text
until 行号
```

功能：继续执行，直到到达指定行。

示例：

```text
(gdb) until 14
```

注意：它适合快速跳过一段不想逐行观察的代码，但仍然可能受到断点等暂停条件影响。

#### 查看调用栈：`bt`

调用栈：记录“当前函数是由哪个函数调用而来”的函数调用路径。

例如 `main` 调用了 `Sum`，当前停在 `Sum` 中，调用关系就是：

```text
main → Sum
```

语法：

```text
bt
```

功能：查看当前函数由谁调用，以及调用层次。

示例：

```text
(gdb) bt
```

当程序在多个函数之间调用，或者程序崩溃时，`bt` 可以帮助确认程序是怎样走到当前位置的。

#### 查看局部变量：`info locals`

局部变量：只在当前函数内部有效的变量。

语法：

```text
info locals
```

功能：一次查看当前函数中的局部变量及其值。

示例：

```text
(gdb) info locals
```

注意：它只查看当前函数的局部变量，不等同于查看所有变量。

#### 重复输入上一条命令

`gdb` 会自动记录最近输入的调试命令。按键盘的上方向键 `↑`，可以取出上一条命令，再按回车执行，适合反复执行 `n`、`p` 等命令。

### 7-4 常见技巧-加餐（三个 debug 技巧）

#### 技巧一：`watch` 监视变量变化

有时我们知道某个变量一开始的值是正确的，但运行一段时间后突然变错，却不知道是哪一行修改了它。此时可以使用 `watch`。

语法：

```text
watch 变量名
```

功能：监视变量；变量值一发生变化，程序就暂停，并显示旧值和新值。

示例：

```text
(gdb) watch sum
(gdb) c
```

当 `sum` 被修改时，`gdb` 会暂停并通知变量发生了变化。

适用场景：怀疑某个本来不应该改变的变量被错误修改时使用。

> **板书强调：`watch` 用来查“变量在哪一刻被改了”。**

#### 技巧二：现场修改变量验证猜想

有时我们怀疑某个变量的值导致了错误，但还不确定。如果修改源代码、重新编译再测试，过程比较慢。`set var` 可以在程序暂停时直接改当前运行中的变量，快速验证猜想。

语法：

```text
set var 变量名=值
```

示例：

```text
(gdb) set var flag=1
```

假设程序因为 `flag=0` 导致结果为 `0`，可以在暂停时把它改成 `1`，然后继续运行：

```text
(gdb) set var flag=1
(gdb) c
```

如果结果恢复正常，就说明 `flag` 的值很可能与问题有关；这只是验证思路，不会修改源代码。

> **板书强调：`set var` 可以现场改值，用来快速验证猜想。**

#### 技巧三：条件断点

普通断点只要运行到指定行就暂停，但循环中的某一行可能会执行很多次。如果只关心 `i==30` 时的情况，就需要条件断点。

条件断点：只有满足指定条件时，程序才暂停。

##### 新增带条件的断点

语法：

```text
b 行号 if 条件
```

示例：

```text
(gdb) b 9 if i==30
```

含义：新增一个位于第 `9` 行的断点，但只有 `i` 等于 `30` 时才暂停。

这里必须写 `if`，因为这是在设置一个“带条件的新断点”。

##### 给已有断点追加条件

语法：

```text
condition 断点编号 条件
```

示例：

```text
(gdb) condition 2 i==30
```

含义：给编号为 `2` 的已有断点增加条件，只有 `i==30` 时才暂停。

这里不能写 `if`，并且 `2` 是已有断点的编号。

| 目的 | 正确语法 | 是否写 `if` |
|---|---|---|
| 新增条件断点 | `b 9 if i==30` | 要写 |
| 修改已有断点条件 | `condition 2 i==30` | 不写 |

> **板书强调：新增断点用 `b 行号 if 条件`；已有断点追加条件用 `condition 断点编号 条件`，第二种没有 `if`。**

#### `cgdb`：分屏可视化版 `gdb`

纯文本的 `gdb` 中，源码和命令通常分开查看，调试时不容易同时看到当前代码位置。`cgdb`：带源码分屏界面的 `gdb`，可以一边看代码，一边输入调试命令。

安装命令：

CentOS 系统：

```bash
yum install -y cgdb
```

Ubuntu 系统：

```bash
apt install -y cgdb
```

启动方式：

```bash
cgdb ./mycmd
```

进入后：

- 按 `ESC`：进入代码窗口；
- 按 `i`：回到 `gdb` 命令窗口。

`cgdb` 的调试命令仍然是 `gdb` 命令，例如 `b`、`n`、`s`、`p`、`c` 等。它主要改变显示方式，不改变调试命令的含义。
