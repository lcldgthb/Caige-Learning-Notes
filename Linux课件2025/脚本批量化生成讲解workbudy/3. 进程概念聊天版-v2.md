# 3. 进程概念

## 1. 冯诺依曼体系结构

### 五大部件

冯诺依曼体系结构规定，一台计算机由五大部件组成：**输入设备**、**输出设备**、**运算器**、**控制器**和**存储器**。其中运算器和控制器合在一起就是常说的 **CPU**（相当于工厂的“生产车间+调度室”）；这里的存储器特指 **内存**（相当于流水线上的“临时中转仓库”）。输入设备负责从外部捞数据进来，包括键盘、鼠标、话筒、摄像头、网卡、磁盘；输出设备负责把结果送出去，包括显示器、打印机、网卡、磁盘。为什么要拆成五块？想象一家工厂：如果没有临时仓库，工人每加工一个零件都亲自去外地拉原材料，流水线根本跑不起来，所以必须有输入→内存→CPU→内存→输出这样的协作。

### 站在内存角度理解 IO

**IO** 就是 Input/Output 的缩写，大白话说叫“数据搬家”——把数据从一个部件挪到另一个部件。为什么要**站在内存角度理解 IO**？因为内存是整个计算机的“中央车站”：键盘打字、磁盘读文件、网卡收消息，本质都是把数据“拷贝”进内存；CPU 要加工数据，也只能从内存里取。任何 IO 操作，起点或终点总有一端是内存。

### 软件运行必须先加载

你双击桌面图标启动程序，为什么总要等一小会儿？因为程序没运行时，它只是磁盘上的一个文件（像躺在遥远仓库里的图纸），而 **CPU 只能从内存中获取和写入数据**。所以操作系统必须先把磁盘上的程序代码和数据“拷贝”到内存，CPU 才能一条一条执行你的指令、访问你的变量。没有这一步“加载”，CPU 连程序的影子都看不见。

> **任何软件要被 CPU 执行，必须先加载到内存。**

### CPU、内存与外设的关系

这套体系有一条铁律：**CPU 在数据层面只和内存打交道，外设也只和内存打交道**。CPU 不会直接问磁盘要数据，键盘也不会直接把字符塞给 CPU；任何两个设备之间的数据传递，本质都是先把数据“拷贝”到内存，再从内存“拷贝”到目标设备。因此，**整个计算机体系的效率，就由这些设备之间“拷贝”的效率决定**。中央车站要是堵车，全厂都得停工。

> **CPU 只和内存打交道，外设也只和内存打交道；体系结构的效率由设备间“拷贝”的效率决定。**

### 速度差：外设毫秒级 vs CPU 纳秒级

为什么非得绕内存这个弯子？因为速度差实在太悬殊：**CPU 是纳秒级干活，外设是毫秒级响应**。1 毫秒等于 100 万纳秒，外设比 CPU 慢上百万倍。如果让 CPU 直接等磁盘转完一圈，就像让一位博士每写一个字都等快递送一支笔，绝大多数时间都在发呆，算力被白白浪费。

### 存储金字塔

为了不让 CPU 干等，现代计算机设计了**存储金字塔**，用多级缓冲来填平速度鸿沟。从上到下：

| 层级 | 名称 | 特点 |
|---|---|---|
| L0 | 寄存器 | CPU 肚子里的储物格，速度最快、容量最小、最贵 |
| L1~L3 | 高速缓存（SRAM） | 紧挨着 CPU 的快递柜 |
| L4 | 主存（DRAM） | 你写 C 程序时 `malloc` 申请到的空间就在这层，即通常说的内存 |
| L5 | 本地磁盘 | 仓库级容量，速度骤降到毫秒级 |
| L6 | 远程二级存储 | 网盘、Web 服务器，速度看网速 |

越往上越快、越贵、容量越小。当代计算机并不是盲目追求极致速度，而是在芯片技术与摩尔定律下寻找**性价比最优**的方案——让博士手边总有笔，但不必把整座文具厂都摆在桌上。

### 经典应用题：QQ 聊天的数据流

假设你给好友发一条“你好”。数据这样流动：你的键盘（输入设备）把按键信息送入**你的内存**；CPU 处理后，数据从你的内存搬到**你的网卡**（此时网卡充当输出设备），进入网络；经过网线传到好友的电脑，先进入**好友的网卡**（此时网卡充当输入设备），再写入**好友的内存**，最后由内存送到**好友的显示器**（输出设备）显示出来。两台机器各自独立，各自都是一套完整的冯诺依曼体系，网卡在不同阶段身份不同，既是输入也是输出设备。

## 2. 操作系统（Operating System）

### 2-1 概念与定位

你每天开电脑时，屏幕上显示的 Windows 桌面、或者你通过 XShell 连接到的 Linux 黑框框，背后真正让机器运转起来的核心，是一套叫做操作系统（OS）的软件。认识任何技术对象都可以按同一个框架拆成三问：它是什么？为什么要有它？它具体怎么做到的？下面围绕这三问展开。

**操作系统就是一个专门负责"管理"的大管家程序**——它管理 CPU、内存、磁盘这些硬件，也管理你安装的各种软件。不过这个词有宽窄两层意思。**狭义的操作系统**单指**内核（kernel）**，这是最直接和硬件打交道的部分，负责进程调度、内存分配、读写文件、指挥硬件驱动。**广义的操作系统**则把外壳也包进来——包括你敲命令用的 shell、编程用到的函数库、甚至系统预装的软件。就像一部手机，安卓系统你能看到的界面和应用生态是"外壳"，底下跑着的 Linux 内核才是"狭义 OS"。你之前通过 yum 或 apt 安装软件时，装的大多都属于广义 OS 里的"外壳"部分。

内核具体管什么？进程管理决定 CPU 时间分给谁；内存管理决定程序用哪块内存；文件管理组织硬盘上的数据；驱动管理则让每个硬件（键盘、显卡、显示器）能被系统认出来。除此之外，函数库、shell 程序等配合内核，共同组成了完整的操作系统。

这里连着一个重要的认知：**你写 C 语言时用的 `printf`，最终并不是魔法般让字符飘到屏幕上，而是操作系统层层向下，把你的数据真正写进了硬件——也就是显示器里**。硬件只听得懂电信号，是操作系统内核通过驱动程序，把"打印 hello"翻译成了显示器能理解的信号。

---

### 2-2 设计目的

操作系统做这么多事，到底为了什么？记住两层关系：对上，操作系统存在的**真正目的**是给用户程序（比如你自己写的 C 程序、或者浏览器）提供一个稳定、安全、方便运行的环境。你写代码时不需要关心怎么让 CPU 轮转、怎么给磁盘发信号，因为 OS 帮你铺好了路。对下，操作系统确实要直接和硬件打交道，管理所有软硬件资源，但**这只是手段，不是目的**。管理资源是为了更好地服务上层的应用程序。

把这两层关系叠起来，就得到了计算机的**层状结构**，这也是理解后续一切的基础：

```text
用户（你写的程序 / 你敲的指令）
    ↓
用户操作接口（shell 外壳 / 函数库 / 部分命令）
    ↓
系统调用接口（system call）
    ↓
内核（kernel）
    ↓
驱动程序
    ↓
硬件（CPU / 内存 / 磁盘 / 显示器...）
```

**系统调用**是什么？你可以把它理解为操作系统对外开的"窗口"——内核不相信任何人直接闯进来乱动硬件，所以只提供一批经过严格检查的函数。用户程序想请内核办事（比如读写文件、申请内存），必须通过这些函数。后面会细讲这个窗口。

---

### 2-3 如何理解"管理"

操作系统内核本质上是一个"管理者"。理解它的管理逻辑，只需要记住三句话：**第一**，管理者和被管理者不需要见面；**第二**，管理者是根据"数据"来做决策的；**第三**，不见面时，数据由中间层去采集和传达。

用一个学校的例子串起来：校长要管理全校学生，但他不可能每天到宿舍点名。于是校长制定规则（决策权），辅导员跑腿执行（中间层），学生乖乖被管（被管理者）。具体怎么做？校长手里有一张 Excel 表格，里面记着每个学生的姓名、性别、年龄、籍贯、成绩、宿舍号。他调整奖学金、分配宿舍、处理违纪，其实就是在表格里做增删查改。**所以，校长管理学生的本质，是在管理 Excel 里的数据。**

如果把校长升级成程序员思维，Excel 就变成你已学过的结构体：

```cpp
struct stu {
    char name[20];      // 姓名
    int age;            // 年龄
    char addr[50];      // 籍贯
    // ... 其他信息
    struct stu* next;   // 已学过的链表指针，把对象串起来
};
```

每一个学生对象被结构体描述出来，再用链表组织在一起。日常的管理工作——查找某个学生、开除（删除）某个学生、新增一个学生——就变成了对链表的增删查改。**这就是"建模"：把现实世界里的管理问题，翻译成计算机能处理的数据结构操作。**

由此提炼出计算机管理一切事物的核心方法论：**先描述，再组织**。先用结构体把要管的东西"描述"清楚，再用链表（或你已学过的 STL 容器）把这些对象"组织"起来。C++ 里把描述升级成了类，把组织升级成了 STL，背后的思想完全一致。

---

### 2-4 系统调用和库函数

前面层状结构里提到了系统调用，现在要把它钉死在你的认知里：**任何程序想访问操作系统的能力，都必须经过系统调用**。系统调用本质上就是函数，只不过它们是操作系统提供的，而不是你自己写的。

有一个硬性结论：**你的程序只要碰了硬件——无论是打印到屏幕、写入磁盘还是播放声音——它的请求就必须从最上层贯穿到最下层**：用户程序 → 库/外壳 → 系统调用 → 内核 → 驱动 → 硬件。没有捷径。

为什么必须绕这么一大圈？因为**操作系统不相信任何用户，也不相信任何普通程序**。就像银行不信任储户直接进金库，只开一个窗口给你。你填单子（输入参数），柜员在内部操作（内核执行），然后把结果和回单给你（返回值）。这个窗口就是系统调用。

而你平时写 C 语言用的 `printf`、打开文件的函数，属于"库函数"。它们站在系统调用的上层，相当于银行里的大堂经理——帮你填表、整理材料，最后在底层替你走到窗口（系统调用）去办手续。所以**库函数在底层往往封装了系统调用**，两者是上下层关系，不是互斥关系。无论你用的是 Linux、Windows 还是 MacOS，只要你通过 C 语言的标准函数去请求系统服务，最终都会走到这套体系里。

## 3. 进程

### 3-1 基本概念与基本操作

你电脑上同时开着微信、浏览器和音乐，操作系统怎么区分这一个个“正在跑的程序”？课本上说进程是“程序的一个执行实例”，但这不够准确——硬盘里的安装包是程序，双击打开后正在聊天的那个才是进程。从操作系统内核来看，**进程是操作系统分配资源（CPU 时间、内存）的基本单位**。最终结论：**进程 = 内核数据结构 PCB（也叫 task_struct）+ 自己的代码和数据**。PCB（Process Control Block，进程控制块）就是操作系统给每个进程建的一张“户口档案”，记录了进程的所有信息；代码和数据就是程序本体和运行时用到的数据。

既然内存里同时存在多个进程，操作系统必然要管理它们。方法还是“先描述，再组织”：先给每个进程建一张档案（task_struct），再把所有档案用双向链表串起来。因此，**对进程的管理本质上就是对 task_struct 双向链表的增删查改**：创建进程就是插入节点，结束进程就是删除节点。

task_struct 这张档案袋里装了什么：

| 字段 | 大白话解释 |
|---|---|
| 标示符 | 进程的身份证号（PID），全局唯一 |
| 状态 | 进程现在在干嘛（运行中、睡觉、要死了） |
| 优先级 | 排队拿 CPU 的先后顺序 |
| 程序计数器 | 做到哪一步了，下一条指令的地址 |
| 内存指针 | 代码和数据放在内存哪里 |
| 上下文数据 | 做到一半被打断时，CPU 寄存器里的临时结果 |
| I/O 状态信息 | 打开了哪些文件、用了哪些设备 |
| 记账信息 | 用了多少 CPU 时间 |

**进程的所有属性最终都落在 task_struct 里；历史上你执行的每一条命令、每一个自己写的程序，运行起来全部是进程**。

查看进程直接使用已学过的 `ps` 和 `grep`：

```bash
ps ajx | head -1 && ps ajx | grep myprocess  # 打印表头并过滤目标进程
```

结束进程用 `kill -9 PID`；前台进程也可以按 `ctrl+c` 终止。

获取自身和父进程的编号需要系统调用（直接请求操作系统办事的接口）：

```cpp
#include <stdio.h>
#include <sys/types.h>  // pid_t
#include <unistd.h>     // getpid / getppid

int main()
{
    pid_t id = getpid();    // 本进程身份证号 PID
    pid_t fid = getppid();  // 父进程身份证号 PPID
    printf("pid: %d, ppid: %d\n", id, fid);
    return 0;
}
```

Linux 把每个进程的信息暴露成虚拟目录 `/proc/PID/`。其中 `exe` 指向该进程对应的可执行文件；`cwd` 指向进程记录的当前工作目录——这就是你写 `fopen("./a.txt","w")` 时，“./”到底相对谁的答案：相对的是 cwd，不是可执行文件所在的位置。

**PPID 实验**：多次运行同一个程序，PID 每次都变，但 PPID 始终不变（比如 19811）。查一下会发现父进程是 `-bash`。结论：**命令行解释器 bash 本身就是一个进程；操作系统给每一个登录用户分配一个 bash**。你启动的程序都是 bash 的子进程，就像王婆（bash）带实习生（用户进程），实习生干活，王婆负责对接和回收。

**fork 初识**：`fork` 是创建子进程的系统调用。

```cpp
#include <stdio.h>
#include <unistd.h>

int main()
{
    pid_t id = fork();      // 从此处开始，父子进程分道扬镳
    if (id < 0) {
        perror("fork");     // 创建失败
        return 1;
    }
    else if (id == 0) {
        printf("子进程, pid=%d\n", getpid());  // 子进程返回 0
    }
    else {
        printf("父进程, pid=%d, 子进程=%d\n", getpid(), id);  // 父进程返回子进程 PID
    }
    return 0;
}
```

**fork 有两个返回值**：父进程拿到子进程的 PID（正数），子进程拿到 0。父进程将来要管理多个子进程，必须知道每个孩子的 PID；子进程只需要知道自己是孩子，返回 0 就够了。

**为什么一个函数能返回两次？** 因为 fork 内部在执行到 return 之前，子进程的 PCB 已经被创建并放入调度队列，甚至可能已经开始运行；return 语句本身也是一行代码，父子进程各执行一次，各自写入自己的变量。

**子进程没有自己的新代码和数据**，它把父进程作为模板——**代码共享（只读）、数据各自私有**。如果你修改子进程的全局变量 `g_val`，父进程的 `g_val` 不会变，因为操作系统底层会触发**写时拷贝**：谁改数据，OS 就给谁单独拷贝一份去改，不影响另一方。**这证明了进程具有独立性**。

第三个经典问题（一个变量 `id` 既等于 0 又大于 0，导致 if/else 同时成立）先留到“程序地址空间”一节解答。

### 3-2 进程状态

#### 理论基础（课本+队列模型）

**进程状态本质就是 task_struct 里的一个整数**。课本上的状态转换是：创建 → 就绪 → 运行 →（时间片用完回就绪 / 等待事件转阻塞 / 结束）。另外还有挂起：内存不够用时，操作系统把进程的代码和数据暂时搬到磁盘的 swap 交换分区（唤出），但 PCB 档案还留在内存；需要时再唤回。阻塞 + 换出 = 阻塞挂起。

**运行 && 阻塞 && 挂起的队列模型**：

- **运行**：每个 CPU 有一个调度队列（runqueue）。只要 PCB 在这个队列里，状态就是 running，不代表此刻一定在 CPU 上跑。调度算法之一是 FIFO。
- **阻塞**：进程等待某种设备或资源（等键盘输入、等磁盘读完），它的 PCB 就会从 CPU 运行队列摘下来，挂到对应设备的等待队列（wait_queue）里。操作系统管理硬件也是先描述再组织——每个设备有结构体，结构体里有一个指向等待该设备的进程链表的指针。
- **挂起**：内存不足时，代码和数据换出到 swap 分区，PCB 仍留内存；激活时再换入。

**进程状态的变化，表现就是在不同的队列之间流动，本质上都是数据结构的增删查改**。

Linux 内核链表的实现：task_struct 内部嵌入 `struct list_head {struct list_head *next, *prev;}`。通过偏移量换算可以找回结构体首地址（offsetof 思想）。**一个 task_struct 可以包含多对 next/prev，同时挂在多个队列里**。全局进程链表通过 `struct list_head tasks` 串起所有进程。

#### Linux 内核状态

内核源码中定义了状态数组 `task_state_array[]`：

- `R (running)`：在运行队列里即 running，不一定正在 CPU 上执行。
- `S (sleeping)`：**可中断休眠（浅睡眠）**，等某个事件完成，可以被信号叫醒。
- `D (disk sleep)`：**不可中断休眠（深度睡眠）**，通常等磁盘 I/O 结束，不可被 `kill -9` 杀死，中断它可能导致磁盘数据混乱。可用下面命令观察进程短暂进入 D 状态：

```bash
dd if=/dev/zero of=~/test.txt bs=4096 count=100000  # 向磁盘写入约 100MB，观察 STAT 列
```

- `T (stopped)`：**暂停**。发送 19 号信号 SIGSTOP 暂停，发送 18 号信号 SIGCONT 恢复。被 gdb 调试命中断点时进程也会进入 T/t 状态。
- `t (tracing stop)`：被 gdb 追踪中的暂停。
- `X (dead)`：死亡，瞬时状态，任务列表里看不到。
- `Z (zombie)`：**僵尸**。

**僵尸状态**：子进程执行完了，但父进程还在运行，并且没有读取子进程的退出信息，子进程就会变成 Z 状态。用 `ps axj` 看会显示 `Z+`，命令名变成 `[myprocess] <defunct>`。

**为什么要有僵尸？** 因为你创建子进程是为了让它办事，办得怎么样（退出码、退出信号）父进程得知道。这些退出信息就保存在子进程的 task_struct 里，所以子进程结束后 PCB 不能立即销毁，要等着父进程来读。

模拟验证：让子进程先调用 `exit(0)` 退出，父进程 `sleep(100)` 不去回收，然后用 `ps axj` 观察。

**僵尸危害推理链**：子进程已经结束 → 但退出状态必须维持 → PCB 必须留在内存 → 父进程永远不回收 → PCB 永远占内存 → **内存泄漏**。

补充两点：
1. 进程退出了，内存泄漏问题还在不在？如果进程不是常驻内存的，退出后资源会被系统回收；但**常驻内存的进程**有内存泄漏就很麻烦。
2. task_struct 这种内核结构对象的内存，由 **slab 分配器**管理——内核有一个专门缓存小对象的内存池，避免频繁申请释放大块内存。

#### 孤儿进程

**父子进程关系中，如果父进程先退出，子进程要被 1 号进程（init/systemd，即操作系统）领养，被领养的子进程叫做孤儿进程**。为什么要领养？不领养的话子进程将来进入僵尸后无人回收，一直占内存。

实验现象：父进程退出后，子进程的 PPID 变成 1，并且自动变成后台进程（类似 `./cmd &` 的运行形式），只能用 `kill -9` 才能结束。

### 3-3 进程优先级

三个基本问题：
- **是什么**：进程拿到 CPU 资源的先后顺序（能得到资源，但谁先谁后）。
- **为什么**：目标资源稀缺，必须排队确认先后。
- **怎么办**：task_struct 里的一个 int 数字，**值越小优先级越高**。

**优先级 vs 权限**：优先级 = 先得到还是后得到资源；权限 = 是否能得到某种资源。

基于时间片的分时操作系统要考虑公平性，优先级可以动态变化，但变化幅度不能太大。

用 `ps -al` 查看，其中 PRI 列是进程优先级（默认 80），NI 列是 nice 值。注意 **NI 不是优先级本身，而是修正数据**。真实的优先级计算公式：

> **进程真实优先级 = PRI(默认 80) + NI**

nice 值范围是 **[-20, 19]**，共 40 级。因此 **Linux 普通进程优先级范围是 [60, 99]**。

修改方法示例：

```bash
renice -n -5 -p 1234   # 把 PID 1234 的 nice 改为 -5，优先级变高
```

如果设置超出范围会被截断：设 `-100` 会变成 `-20`，设 `100` 会变成 `19`。也可在 top 里按 `r`，或用 `nice` 命令，或用系统调用 `getpriority` / `setpriority`。

优先级设立不合理的后果：低优先级进程长时间得不到 CPU 资源 → **进程饥饿**。

小知识：**系统怎么判断访问文件时是拥有者、所属组还是 other？** Linux 中访问任何资源都是进程在访问，进程就代表用户。进程的 UID（用户 ID）决定了它此刻的身份。

四个概念：

| 概念 | 含义 |
|---|---|
| **竞争性** | 系统进程众多，CPU 稀少，进程间必须竞争资源，于是需要优先级 |
| **独立性** | 多进程运行时互不干扰，独享资源 |
| **并行** | 多个进程在多个 CPU 下分别同时运行 |
| **并发** | 多个进程在一个 CPU 下通过切换轮流推进，一段时间内都得以运行 |

### 3-4 进程切换

一个死循环进程会把代码跑完吗？**不会**——操作系统给每个进程分配了**时间片**（比如 10 毫秒），时间一到就必须让出 CPU。所以
所以死循环进程不会卡死系统，时间片一到操作系统就会强行把它切下来，让别人跑。关键问题是：**进程被切走后，下次怎么接着原来的地方继续跑？**

CPU 里有一组高速临时存储单元，叫做**寄存器**（可以理解为 CPU 内置的"草稿纸"）。常见寄存器包括 pc/EIP（下一条指令地址）、ebp/esp（栈底/栈顶指针）、eax/ebx/ecx/edx（通用计算）、cs/ds 等（段选择子）、eflags（运算标志位）、cr0~cr4（控制寄存器）。

要明白两点：
1. **寄存器是 CPU 内部的临时空间**，速度极快。
2. **寄存器 ≠ 寄存器里面的数据**。寄存器硬件只有一份，但里面的数据是"谁在用就属于谁"的临时财产，会随着进程切换不断变化。

怎么理解"切走再回来"？用"大学生当兵"的故事：把学校看作 CPU，你是进程，辅导员是调度器。你大二去当兵（进程被切走），学校必须给你保留学籍（保存你读到哪门课、学分多少等临时信息）。两年后你回来，学校恢复你的学籍（把信息装回系统），你接着读大三，而不是重新读大一。这就是一次**进程切换**。

具体到技术细节：**CPU 里的寄存器硬件只有一份，但每个进程都有一份属于自己的"上下文数据"**——比如进程 A 执行到第 100 行、eax 里存着 10；进程 B 执行到第 1000 行、eax 里存着 100。进程 A 被切下来时，必须把自己的寄存器内容打包带走，保存起来；下次轮到它时，再把这些数据恢复到 CPU 寄存器里，保证"接着上次的后半截继续运行"。

> **进程切换最核心的就是保存和恢复当前进程的硬件上下文数据，即 CPU 内寄存器的内容。**

这些上下文数据保存到哪里？**保存到进程自己的 task_struct 里面，具体是一个叫 TSS（任务状态段，struct tss_struct）的结构**——你可以把它理解成"专门存放 CPU 草稿纸快照的小仓库"。里面记录了 back_link、esp0、eip、eflags、eax~ebx、esp、ebp 等所有寄存器的现场值。在 task_struct 源码末尾内嵌了 `struct tss_struct tss;`。

内核里有一个全局指针 `struct task_struct *current`，始终指向当前正在 CPU 上运行的进程。调度器就是通过操作 current 来实现切换的。

补充：Linux 属于**分时操作系统**（大家轮流用 CPU，追求公平响应，你聊微信时音乐也在播）；与之相对的是**实时操作系统**（某些任务必须在截止时间内完成，用于工厂机械臂、飞机控制）。Linux 也支持优先级抢占，高优先级进程可以打断低优先级进程。

### 3-5 Linux2.6 内核 O(1) 调度队列

前面说过每个 CPU 有一个运行队列 runqueue。如果系统里有几百个进程，调度器怎么快速挑一个来运行？不能从头扫到尾，那样越来越慢。Linux 2.6 内核设计了一个 O(1) 调度器，意思是**挑进程的时间复杂度是常数，不随进程数量增加而变慢**。

调度器挑进程分两步：**先挑队列，再挑进程**。

首先要了解优先级的分区：Linux 把优先级分成两类——[0,99] 叫做实时优先级（这节课不展开）；**[100,139] 是普通优先级，正好对应 nice 值 [-20,19]**。

runqueue 里有两个核心结构：

**1. queue[140]：优先级哈希桶**
`struct task_struct *queue[140];` 是一个指针数组。**数组下标就是优先级**，下标 100~139 对应普通进程。相同优先级的进程用链表 FIFO 排队。这就把"按优先级排队"的问题变成了"数组下标定位"。

**2. bitmap[5]：位图快速定位**
`unsigned int bitmap[5];` 一共 5×32=160 个比特位，覆盖 140 个优先级槽位。**比特位的位置对应 queue 数组的哪一个下标，比特位的 1/0 表示该优先级队列是否为空**。调度器只要找 bitmap 里最高位的 1，就能直接定位当前最高优先级的非空队列，这一步是 O(1)。

**3. active 与 expired 双队列**
`prio_array_t arrays[2];` 每个元素都包含 {nr_active; bitmap[5]; queue[140]}。系统维护两个指针：
- `active`：指向当前活动队列，里面放的是**时间片还没用完**的进程。
- `expired`：指向过期队列，里面放的是**时间片已经耗尽**的进程。

调度器只从 active 队列里挑进程运行。当 active 里的进程时间片用完，就把它移到 expired 队列。随着时间推移，**active 队列里的进程越来越少，expired 队列里的越来越多**。一旦 active 空了，调度器不需要搬任何数据，只需要**`swap(&active, &expired)` 交换两个指针**，expired 立刻变成新的 active，马上又有一批进程可以调度。

> **O(1) 调度的本质：用 bitmap 在常数时间内找到最高优先级非空队列，用 active/expired 双指针交换避免队列搬移，使得调度耗时与进程总数无关。**

## 4. 命令行参数和环境变量

### 4-1 概念介绍

用 gcc 编译程序时，你从没手动告诉过它标准库的头文件和动态库躺在硬盘哪个角落，但它总能找到。这不是魔法，而是操作系统里提前贴好了一些**全局便签**，上面写着"库去哪里找"这类信息，编译器启动后会自己读取。这些全局便签就是**环境变量**——操作系统用来指定运行环境参数的全局配置。

它有两个关键特点：一是**全局特性**，当前系统里启动的程序基本都能读到；二是你平时在 bash 里敲命令，bash 会替你把这些便签传给接下来的程序，所以用户是**间接地**在使用它们。

> **环境变量是操作系统级别的全局配置，具有全局特性；bash 利用它，用户便间接享受了便利。**

---

### 4-2 命令行参数

你敲 `ls -a -l` 时，`ls` 是程序名，`-a` 和 `-l` 就是给它的额外指令。程序怎么收到这些词？bash 会把你敲的整行命令按空格切成几段，程序启动时通过一张叫 **argv** 的表接收。argv 本质就是一个字符指针数组 `char *argv[]`。

```cpp
#include <stdio.h>

int main(int argc, char *argv[])
{
    for (int i = 0; i < argc; i++) {
        printf("argv[%d]: %s\n", i, argv[i]);  // 依次打印程序名和每个参数
    }
    return 0;
}
```

编译后执行 `./code a b c d`，输出：
```
argv[0]: ./code
argv[1]: a
argv[2]: b
argv[3]: c
argv[4]: d
```

argv 的完整结构长这样：

```text
argv[0]  argv[1]  argv[2]  argv[3]  argv[4]  argv[5]
  |        |        |        |        |        |
  v        v        v        v        v        v
./code    a        b        c        d       NULL
```

- `[0]` 固定存程序名。
- 其后依次存放各个参数。
- **表尾一定是 NULL**，标记结束。
- 这些字符串由 **bash 切分** 后填入。

所以 `ls -a -b -c` 的本质，就是 ls 程序拿到 argv 后检查 argv[1] 是不是 `"-a"`、argv[2] 是不是 `"-b"`，然后决定开启哪些功能。用 `file /usr/bin/ls` 可确认它就是个普通可执行文件，和你写的程序没有区别。

> **进程拥有一张 argv 表，用来支持实现选项功能；main 的命令行参数是实现程序不同子功能的方法——这就是指令选项的实现原理。**

---

### 4-3 一个例子：PATH

要执行一个程序，系统必须先找到它在硬盘上的位置。既然系统指令如 `ls`、`pwd` 你从不告诉系统它们在哪里，却能直接跑，而自己编译的程序必须写成 `./a.out`，那就说明系统中一定存在某个环境变量在帮系统定位目标二进制文件。这个变量就是 **PATH**。

```bash
echo $PATH  # 显示当前PATH的内容
```

输出示例：
```
/usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin:/home/whb/.local/bin:/home/whb/bin
```

冒号 `:` 是分隔符，把多个文件夹路径隔开。当你敲一个不带路径的命令时，bash 按顺序去这些文件夹里找，找到了就执行。系统指令都放在 PATH 包含的目录里，所以直接打名字就行；你自己的程序所在目录通常**不在** PATH 里，因此必须写 `./a.out`，意思是"别去 PATH 清单找了，就在当前文件夹"。

你可以把自定义目录追加进去：

```bash
export PATH=$PATH:/your/program/path  # 在原有路径后用冒号追加新目录
```

> **PATH 等于系统中搜索指令的默认搜索路径；它解释了为什么系统指令不用带路径，而自己编译的程序要带 `./`。**

---

### 4-4 环境变量从哪来、bash 两张表

bash 内部维护着两张表：一张是**命令行参数表 argv**，另一张是**环境变量表**，通过全局的 `char **environ` 可以访问到。bash 自己先拿到环境变量，再交给它启动的程序。

环境变量最开始从系统的配置文件里读进来，主要是家目录下的 `.bash_profile` 和 `.bashrc`，后者还会再引入 `/etc/bashrc` 这类全局配置。

如果系统上有 10 个用户同时登录，就会存在 10 个 bash 进程，**每个 bash 各自维护两张表**，互不干扰。

常见的环境变量有很多，用 `env` 可查看全部：

```bash
env         # 列出当前所有环境变量
```

经常遇到的有：
- **PATH**：找命令的默认路径
- **HOME**：家目录绝对路径，`cd ~` 就是读它
- **SHELL**：当前 shell，通常是 `/bin/bash`
- **USER / LOGNAME**：当前用户名
- **PWD**：当前所在目录绝对路径
- **LANG**：系统语言和编码
- **LD_LIBRARY_PATH**：动态链接库搜索路径

相关操作命令：
```bash
echo $XXX       # 显示某个环境变量的值
export XXX=val  # 设置或导出一个环境变量
unset XXX       # 清除某个环境变量
set             # 本地变量和环境变量全部显示
```

> **bash 内部有两张表：环境变量表（environ）和命令行参数表（argv）；环境变量最开始从系统的相关配置文件中来；10 个用户登录就存在 10 个 bash，各自维护两张表。**

---

### 4-5 获取环境变量的方法

操作级的 `export`、`env`、`echo`、`unset` 刚才已经见过。下面是在 C/C++ 代码里获取的三种方式。

**方式一：main 的第三个参数**

```cpp
#include <stdio.h>

int main(int argc, char *argv[], char *env[])
{
    for (int i = 0; env[i]; i++) {  // env 是以 NULL 结尾的指针数组
        printf("%s\n", env[i]);     // 每个元素是 "NAME=VALUE" 格式的字符串
    }
    return 0;
}
```

程序启动时，底层会根据参数个数选择调用哪种形式的 main，传三个参数时就能把环境表带进来。

**方式二：getenv（最常用）**

```cpp
#include <stdio.h>
#include <stdlib.h>

int main()
{
    char *path = getenv("PATH");   // 传入变量名，返回对应值的字符串
    if (path != NULL) {
        printf("PATH=%s\n", path); // 只查特定变量，不用遍历整张表
    }
    return 0;
}
```

**方式三：libc 全局变量 environ**

```cpp
#include <stdio.h>

extern char **environ;  // 声明 C 库中的全局变量，直接指向环境表

int main()
{
    for (int i = 0; environ[i]; i++) {
        printf("%s\n", environ[i]);  // 遍历打印所有环境变量
    }
    return 0;
}
```

无论哪种方式，环境表的结构都一样：它是一个字符指针数组，每一项指向一个 `'0'` 结尾的环境字符串，**表尾以 NULL 结尾**。

> **代码获取环境变量有三种方式：main 第三参数、getenv、extern char **environ；环境表是指针数组，表尾 NULL 结尾。**

---

### 4-6 环境变量的全局特性

环境变量最核心的特性是**可以被子进程继承**。bash 是你命令行的父进程，你从 bash 里启动的新程序就是它的子进程；子进程会复制一份 bash 的环境变量表，还能继续传给孙进程，形成树形继承。

验证：

```bash
export MYENV=xxx      # 在 bash 里新建一个环境变量
./myprogram           # myprogram 里用 getenv("MYENV") 能读到 xxx
```

与此相对的是**本地变量**：它不会被子进程继承，只在 bash 内部自己用。

```bash
i=10        # 定义本地变量
echo $i     # bash 自己能打印出 10
./myprogram # myprogram 里 getenv("i") 读不到任何东西
```

bash 同时记录着两套变量：环境变量（能继承）和本地变量（不能继承）。想把本地变量升级成环境变量，用 `export`：

```bash
export i    # 把本地变量 i 导出为环境变量，之后子进程就能看到了
```

`export` 是**内建命令**，意思是 bash 不会创建子进程去执行它，而是**自己亲自改自己的表**。如果像普通命令那样派个子进程去改，改的是子进程的表，bash 自己不变，那就永远改不了当前 shell 的环境了。

> **环境变量可以被子进程继承，本地变量不会；bash 记录两套变量；export 是内建命令，由 bash 亲自执行，因此对 bash 自身的修改才能生效。**

最后做一个思想实验：如果你想写一个程序，只允许自己执行，别人一律不让执行，怎么办？程序启动后用 `getenv("USER")` 拿到当前用户名，判断一下即可。

```cpp
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main()
{
    char *user = getenv("USER");        // 从环境变量读取当前用户名
    if (user != NULL && strcmp(user, "whb") == 0) {
        printf("Access granted\n");     // 是本人，允许执行
    } else {
        printf("Permission denied\n");  // 其他人，拒绝执行
    }
    return 0;
}
```

## 5. 程序地址空间

### 5-1 布局与验证

你写C程序时用过全局变量、局部变量、malloc申请内存、定义字符串常量。程序跑起来后，这些东西到底放在哪里？如果你以为它们直接落在内存条的真实位置上，后面会碰到一个巨大的困惑——两个完全不同的程序，可能同时说"我的变量在地址 0x60104c"。这怎么可能？

所以操作系统给每个进程发了一张**虚拟地址空间**：它不是内存条本身，而是操作系统维护的一套"地址编号规则"，是一张每个进程独享的地图。注意，这是操作系统层面的概念，不是C/C++语言本身的概念。

地图能编多少号，取决于CPU的位数。32位机器一共能编出 2^32 个地址；如果每个地址对应1个字节（1字节编址），总空间就是 4GB。64位机器则是 2^64 个地址。

这张地图从低地址到高地址的布局是固定的：

```text
低地址
├── 正文代码（你的函数指令）
├── 初始化数据（已赋值的全局变量）
├── 未初始化数据（未赋值的全局变量，也叫BSS段）
├── 堆（malloc 的地盘，向高地址增长 ↑）
├── 一大段镂空空隙
├── 共享区（动态库映射在这里）
├── 栈（局部变量，向低地址增长 ↓）
├── 命令行参数 / 环境变量
└── 内核空间（32位Linux占最高1GB，即 [3G,4G]；用户只能用 [0,3G)）
高地址
```

你可以写一段代码验证这个布局，打印各类数据的地址：

```cpp
#include <stdio.h>
#include <stdlib.h>

int g_init = 10;               // 已初始化的全局变量
int g_uninit;                  // 未初始化的全局变量
const char *str = "hello";     // 只读字符串常量

int main(int argc, char *argv[], char *env[])
{
    static int s = 5;          // 静态局部变量
    int local = 1;             // 栈上的局部变量
    int *p = (int*)malloc(sizeof(int));   // 堆上第一次申请
    int *p2 = (int*)malloc(sizeof(int));  // 堆上第二次申请

    printf("code:        %p\n", (void*)main);       // 正文代码区
    printf("init global: %p\n", (void*)&g_init);    // 初始化数据区
    printf("uninit global:%p\n", (void*)&g_uninit); // 未初始化数据区
    printf("heap1:       %p\n", (void*)p);          // 堆区（地址较小）
    printf("heap2:       %p\n", (void*)p2);         // 堆区（地址较大，向上增长）
    printf("stack:       %p\n", (void*)&local);     // 栈区（地址高，向下增长）
    printf("read only:   %p\n", (void*)str);        // 只读常量区
    printf("static local:%p\n", (void*)&s);         // 静态变量实际在全局数据区
    printf("argv:        %p\n", (void*)argv);       // 命令行参数
    printf("env:         %p\n", (void*)env);        // 环境变量

    free(p);
    free(p2);
    return 0;
}
```

> **程序地址空间不是内存条！它是操作系统给每个进程发的虚拟地址空间，是一个系统概念，不是语言层的概念。**

### 5-2 虚拟地址实验（fork+g_val）

先看一个反直觉的实验。定义一个全局变量，用 fork 创建一个子进程，父子都打印这个变量的地址和值：

```cpp
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int g_val = 100; // 全局变量

int main()
{
    pid_t id = fork(); // 创建子进程：返回 0 表示子进程，返回大于 0 表示父进程
    if(id == 0){
        g_val = 105; // 子进程修改值
        printf("child : &g_val=%p, g_val=%d\n", (void*)&g_val, g_val);
    } else {
        sleep(1); // 让子进程先跑完
        printf("parent: &g_val=%p, g_val=%d\n", (void*)&g_val, g_val);
    }
    return 0;
}
```

运行后会看到：父子打印的 `&g_val` 地址完全一样（比如都是 `0x60104c`），但子进程的值变成了 105，父进程仍然是 100。

同一个地址怎么可能同时存 100 和 105？如果这是内存条上的真实地址，那就是硬件 bug。唯一的解释是：**这个地址不是物理内存地址，而是虚拟地址。**

C/C++ 代码里指针打印出来的地址、你看到的 `&变量`，全部是虚拟地址。真正的物理地址由操作系统统一管理，普通用户程序一辈子也看不到。

为了把虚拟地址翻译成物理地址，系统给每个进程准备了两样东西：一张地图（虚拟地址空间）和一本翻译手册（页表）。由此得到三个预备结论：
- 一个进程，独占一张虚拟地址空间；
- 一个进程，独占一套页表；
- 页表专门负责虚拟地址和物理地址的映射。

fork 创建子进程时，为了快和省，操作系统不会立刻复制所有物理内存。子进程先照搬父进程的页表，父子虚拟地址相同，也映射到同一个物理地址。但当子进程要去修改 `g_val` 时，操作系统会触发**写时拷贝**：立刻在物理内存上另找一块新地方，把原来的值 100 拷过去，让子进程的页表指向新物理地址（比如 `0x223344`），然后在新地址上改成 105。父进程的页表仍然指向老物理地址（比如 `0x112233`），值保持 100。

```text
fork 之后、写入之前：
  父/子虚拟地址 0x111111 ──页表──→ 物理地址 0x112233 (值100)

子进程 g_val++ 之后（写时拷贝）：
  父虚拟 0x111111 ──页表──→ 物理 0x112233 (值100)
  子虚拟 0x111111 ──页表──→ 物理 0x223344 (值105)
```

> **进程具有独立性：①内核数据结构独立；②加载进内存的代码和数据独立。** 这就是"同一个变量为什么有两个值"的答案。

为什么要搞写时拷贝？核心原因就两条：**第一，减少创建进程的时间；第二，减少内存浪费。** 如果子进程只读不改，物理内存根本不用复制。

### 5-3 如何理解虚拟地址空间（两个类比）

虚拟地址空间看不见摸不着，怎么管理它？操作系统里有一条万能法则：**先描述，再组织。** 不管什么资源，先用数据结构把它描述出来，再把数据结构关联起来。

**类比一：大富翁分家产**
假设大富翁（操作系统）手里真的有 10 个亿（物理内存）。他有 4 个私生子（4 个进程）。如果直接把钱拆开分，既麻烦又死板。于是大富翁给每个儿子各画了一张 10 亿的饼（虚拟地址空间），让每个儿子都觉得自己独占 10 亿。儿子们平时各看各的饼，互不影响；真到用钱的时候，大富翁再从兜里实际掏出来兑现。这张"饼"要不要管理？当然要。管理的方法就是用一个结构体把它描述清楚。

**类比二：课桌三八线**
一张 100 厘米的桌子，画一条线分成两个区域。什么叫划分区域？其实只需要记录两组数字：张三的起始和结束、李四的起始和结束。比如 `{0, 49, 50, 99}`。张三越界了？把李四的起始减 20、张三的结束加 20 就行——全程只是在改数值。

虚拟地址空间的本质，就是一个名叫 `struct mm_struct` 的结构体，里面没有真的内存，只有一堆"起始-结束"数值：

```cpp
struct mm_struct {
    unsigned long start_code, end_code;   // 正文代码区域边界
    unsigned long start_data, end_data;   // 初始化数据边界
    unsigned long start_brk, brk;         // 堆的当前边界
    unsigned long start_stack;            // 栈起始
    unsigned long arg_start, arg_end;     // 命令行参数边界
    unsigned long env_start, env_end;     // 环境变量边界
    // ... 其他成对的 start / end
};
```

内核里，每个进程只有一个 `mm_struct`。进程的"身份证" `task_struct` 里面有一个指针 `struct mm_struct *mm`，专门指向它。

这个结构体一诞生就会遇到两个问题：①空间怎么开辟？②里面的初始值从哪来？答案是在**加载可执行程序**的时候，操作系统根据程序本身的信息把 `mm_struct` 初始化好。

### 5-4 VMA 与页表

页表是什么？你可以把它想象成一张翻译表，左边是虚拟地址，右边是物理地址。但页表不止两列，还有一列**权限**（比如 `rw-` 可读可写，`r--` 只读，`rwx` 可执行）。CPU 里有一个硬件叫 MMU，它拿着虚拟地址，自动查页表、翻成物理地址。

如果进程里堆区很碎，malloc 了很多次，难道 `mm_struct` 里只记一个堆起始就够了吗？不够。**地址空间需要再扩展一层**：内核把每个连续的区间拆成一个个"小块"，用 `struct vm_area_struct`（简称 VMA）来描述每个小块的起止、权限、标志等。

```cpp
struct vm_area_struct {
    struct mm_struct *vm_mm;    // 属于哪个地址空间
    unsigned long vm_start;     // 本区间起始虚拟地址
    unsigned long vm_end;       // 本区间结束虚拟地址
    pgprot_t vm_page_prot;      // 访问权限
    unsigned long vm_flags;     // 标志位
    struct vm_area_struct *vm_next, *vm_prev; // 链表指针
};
```

所有 VMA 在 `mm_struct` 里通过 `struct vm_area_struct *mmap` 串成一个链表。如果区间数量少，用单链表就行；如果数量多，内核还会同时用红黑树组织，加快查找速度、减少内存浪费。

完整的视角是这样的：

```text
task_struct (进程的身份证)
    ├── files_struct *files   (已学过，管理打开的文件)
    ├── mm_struct *mm         (指向虚拟地址空间描述)
          ├── pgd (页表：虚拟↔物理映射 + 权限列)
          └── mmap (VMA 链表/红黑树，每个节点带读写执行权限)
                → 分别对应：内核空间 / 栈 / 共享映射 / 堆 / BSS / 数据段 / 代码段
```

程序加载时的大致流程：
1. 在虚拟地址空间里用 `mm_struct/VMA` 圈出一块地；
2. 在物理内存里真正申请页面；
3. 把映射关系填进页表。

之后 CPU 访问虚拟地址，MMU 查页表拿物理地址。如果页表发现这页还没配物理内存，会触发**缺页中断**，操作系统趁机去分配物理页并填好表。

### 5-5 为什么要有虚拟地址空间

费了这么大劲画饼、建结构、查页表，好处是什么？

**收益一：把地址从无序变成有序**
没有虚拟地址空间时，程序直接怼物理内存，哪个程序加载到哪里完全看当时哪块空着，布局乱七八糟。有了虚拟地址空间后，每个进程看到的都是一套整整齐齐的 0~4GB 布局，代码在哪、堆在哪、栈在哪，永远不变。

**收益二：访问时做合法性判定，保护物理内存**
页表里有权限列。当你写代码时用了野指针
页表里有权限列。当你写代码时用了野指针，或者试图修改只读数据（比如 `char *str = "helloworld"; *str = 'H';`），MMU 查页表会发现目标页权限是 `r--`（只读），CPU 立刻触发权限异常，操作系统将进程杀死。这就是字符串常量写入崩溃的本质——不是 C/C++ 语法在拦你，而是硬件查页表时权限不匹配。所以虚拟地址空间配合页表，成了一道保护物理内存的安检门。

**收益三：让进程管理和内存管理解耦合**
以前程序直接面对物理内存时，加载地址必须固定，malloc 多少就要立刻占用多少物理页。有了虚拟地址空间后，malloc 先在 `mm_struct` 和 VMA 里把虚拟区域画出来，页表暂时不填物理映射；等你真的读写时，触发缺页中断，操作系统才从物理内存任意位置挑空闲页填进去。物理页散落在内存条何处，进程完全无感知。进程只管地址空间的布局，操作系统只管物理页的分配，两边互不干扰。

> **虚拟地址空间的三大收益：①地址有序化；②访问合法性判定保护物理内存；③进程管理与内存管理解耦。**

最后澄清三个常见的边界问题。第一，一个进程可以只有 `task_struct`、`mm_struct`、页表，完全不加载代码和数据，这种"光杆司令"在理论上是存在的。第二，创建进程时，一定是先建立 `task_struct`、`mm_struct`、页表等内核数据结构，之后才加载或映射代码和数据。第三，所谓进程挂起，就是把进程的代码和数据换出到磁盘（swap），但 `task_struct`、`mm_struct`、页表仍然留在内存里——进程的"户口"还在，只是"身体"临时出去了。
