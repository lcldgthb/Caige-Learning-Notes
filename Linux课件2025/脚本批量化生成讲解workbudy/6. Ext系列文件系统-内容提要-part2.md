# 6. Ext系列文件系统-内容提要（后半部分）
## 3. ext2 文件系统

### 3-1 宏观认识
- 想在硬盘上存文件，必须先把硬盘格式化为某种格式的文件系统；文件系统的目的就是组织和管理硬盘中的文件
- Linux 最常见 ext2 系列（ext3/ext4 核心设计不变，以 ext2 为演示对象）
- ext2 将整个分区划分成若干个同样大小的块组(Block Group)；能管理一个分区就能管理所有分区

### 3-2 Block Group
- ext2 根据分区大小划分出数个 Block Group，每个 Block Group 结构相同（政府管理各区的类比）
- 板书层次图：Disk(MBR | Partition 1..4) → Partition(Boot Sector | EXT2 File System) → File System(Block Group 0 | 1 | ... | N)【板书强调：文件系统的具体分层！】
- 启动块 Boot Block/Sector 大小固定 1KB，由 PC 标准规定，存磁盘分区信息和启动信息，任何文件系统都不能修改；启动块之后才是 ext2 文件系统的开始
- 板书：300GB 的 Linux 管理方式 → 分组！group 0 / group 1 / ... / group n【板书强调】

### 3-3 块组内部构成
- 板书块组结构：Super Block | GDT | Block Bitmap | inode Bitmap | inode Table | Data Blocks【板书强调：文件系统的具体分层！】

#### 3-3-1 超级块(Super Block)
- 存放文件系统本身的结构信息，描述整个分区的文件系统信息：block 和 inode 的总量、未使用的数量、block 和 inode 的大小、最近一次挂载/写入/检验磁盘的时间等
- Super Block 被破坏整个文件系统结构就被破坏；会在多个 block group 中备份保持一致（第一个块组必须有，后面的可以没有）
- struct ext2_super_block：s_inodes_count/s_blocks_count/s_free_blocks_count/s_free_inodes_count/s_first_data_block/s_log_block_size/s_blocks_per_group/s_mtime/s_wtime/s_magic 等

#### 3-3-2 GDT(Group Descriptor Table)
- 块组描述符表：描述块组属性信息，整个分区有多少个块组就对应多少个块组描述符
- 每个块组描述符存储一个块组的描述信息：该块组中从哪里开始是 inode Table、从哪里开始是 Data Blocks、空闲的 inode 和数据块还有多少个等【板书强调：据此定位本块组管理数据的起始位置！】
- 块组描述符在每个块组的开头都有一份拷贝
- 【板书强调】你怎么知道，就读取第一个分组？？——概括化的本意，就是深入写入文件系统的管理信息！
- struct ext2_group_desc：bg_block_bitmap/bg_inode_bitmap/bg_inode_table/bg_free_blocks_count/bg_free_inodes_count/bg_used_dirs_count

#### 3-3-3 块位图(Block Bitmap)
- Block Bitmap 记录 Data Block 中哪个数据块已被占用、哪个没有被占用（板书：0000 0000 位示意）【板书强调】

#### 3-3-4 inode位图(Inode Bitmap)
- 每个 bit 表示一个 inode 是否空闲可用【板书强调】
- 板书对比：inode 和数据块都有各自的位图、刷出编号；inode 编号跟分区走，不能跨分区【板书强调：同一分区内的 inode 编号机制等都是唯一的！】

#### 3-3-5 i节点表(Inode Table)
- 存放文件属性（文件大小、所有者、最近修改时间等）；当前分组所有 inode 属性的集合【板书强调】
- inode 编号以分区为单位整体划分，不可跨分区
- 板书 inode 表格列：Inode Number | File Type | Permissions | Link Count | UID | GID | size | ... | pointer【板书强调】
- 知道第一个文件的 inode 就可以找到该文件的所有内容【板书强调】
- 【板书强调】你怎么知道，我在分组中对应的是哪一个位置！

#### 3-3-6 Data Block
- 数据区：存放文件内容，即一个个 Block
- 普通文件：数据存储在数据块中；目录：该目录下所有文件名和目录名存储在所在目录的数据块中（文件名除外的其他 ls -l 信息保存在该文件的 inode 中）
- Block 号按照分区划分，不可跨分区

### 3-4 inode和datablock映射（弱化）
- inode 内部 i_block[EXT2_N_BLOCKS]，EXT2_N_BLOCKS = 15，用来进行 inode 和 block 的映射【板书强调：int datablock[N] 该文件所对应的数据块的编号！】
- 这样文件 = 内容 + 属性就都能找到了

### 3-5 目录与文件名
- 思考：知道 inode 号的情况下，在指定分区对文件进行增、删、查、改是在做什么？
- 结论：分区后的格式化 = 对分区进行分组，在每个分组中写入 SB、GDT、Block Bitmap、Inode Bitmap 等管理信息，这些管理信息统称文件系统
- 只要知道文件的 inode 号，就能在指定分区确定是哪一个分组，进而确定是哪一个 inode；拿到 inode，文件属性和内容就全都有了【板书强调】
- touch abc 后 `ls -i abc` 显示 263466；创建新文件的 4 个操作【板书强调】：①存储属性：内核找到一个空闲 i-node(263466)，把文件信息记录其中 ②存储数据：找三个空闲块 300/500/800，依次复制数据 ③记录分配情况：inode 上的磁盘分布区记录块列表 ④添加文件名到目录：内核将入口(263466, abc)添加到目录文件——文件名和 inode 的对应关系将文件名和文件内容及属性连接起来
- 问题：访问文件都用文件名没用 inode 号？目录是文件吗？
- 答案：目录也是文件，但磁盘上没有"目录"的概念，只有文件属性+文件内容；目录的属性不用多说，内容保存的是：文件名和 inode 号的映射关系【板书强调】
- 验证代码 readdir.c：opendir/readdir/closedir，遍历 entry 打印 Filename 和 Inode（跳过 . 和 ..）；运行结果与 `ls -li /` 对照
- 【板书强调】磁盘上的文件系统，只认 inode！查找在当前文件所属目录的数据内容当中！
- 【板书强调】访问任何文件都是用文件名访问：先打开所在目录，根据文件名和 inode 的映射关系：文件名 → inode → 访问文件的内容！
- 所以访问文件必须打开当前目录，根据文件名获得对应 inode 号再进行文件访问；访问文件必须知道当前工作目录，本质是必须能打开当前工作目录文件、查看目录文件的内容
- 例：访问 test.c 必须打开 test(当前工作目录)，才能获取 test.c 对应的 inode

### 3-6 路径解析
- 问题：当前工作目录也是文件，访问它不也得知道它的 inode 吗？→ 也要打开它的上级目录……递归
- 【板书强调】我们访问任何文件都必须要有的路径！例：ls /home/whb/code/code/merge class/lessons21/code.c
- 类似"递归"，需要把路径中所有目录全部解析，出口是 "/" 根目录【板书强调】
- 路径解析：访问 /home/whb/code/test/test/test.c 都要从根目录开始，依次打开每一个目录，根据目录名依次访问每个目录下指定的目录，直到访问到目标文件
- 访问文件必须要有 目录+文件名=路径 的原因；根目录固定文件名、inode 号，无需查找，系统开机之后就必须知道
- 路径谁提供？访问文件都是指令/工具访问，本质是进程访问，进程有 CWD！进程提供路径【板书强调：我的路径，谁提供的？→ 进程提供当前路径！】
- 最开始的路径从哪里来？Linux 为什么要有根目录、根目录下为什么有那么多缺省目录？为什么要有家目录、自己可以新建目录？——这些行为本质都是在磁盘文件系统中新建目录文件，新建的文件都在指定目录下，天然就有路径了；系统+用户共同构建 Linux 路径结构

### 3-7 路径缓存
- 问题1：Linux 磁盘中存在真正的目录吗？——不存在，只有文件，只保存文件属性+文件内容【板书强调】
- 问题2：访问任何文件都要从 / 目录开始路径解析？——原则上是，但一直做路径解析效率太低【板书强调】，所以 Linux 会缓存历史路径结构【板书强调：OS 会将加载的目录形成一棵多叉树进行缓存！】
- 问题3：Linux 目录的概念怎么产生？——打开的文件是目录的话，由 OS 自己在内存中进行路径维护；Linux 系统的树状目录结构【板书强调】
- 内核中维护树状路径结构的内核结构体：struct dentry【板书强调】
- struct dentry 关键字段：d_count/d_flags/d_lock/d_inode(文件对应的 inode，NULL 为 negative)/d_hash(哈希表节点)/d_parent(父目录)/d_name/d_lru(LRU 链表)/d_child/d_subdirs(子目录)/d_op/d_sb 等
- 每个（被打开的）文件都要有对应的 dentry 结构，包括普通文件，所有被打开的文件在内存中形成整个树形结构
- 树形节点同时属于 LRU(Least Recently Used 最近最少使用)结构进行节点淘汰；同时属于 Hash 方便快速查找
- 整个树形结构构成 Linux 的路径缓存结构：打开访问任何文件都先在这棵树下根据路径查找，找到就返回属性 inode 和内容；没找到就从磁盘加载路径、添加 dentry 结构、缓存新路径

### 3-8 挂载分区
- 问题：inode 不能跨分区，Linux 可以有多个分区，我怎么知道我在哪一个分区？？？

#### 3-8-1 一个实验
- `dd if=/dev/zero of=./disk.img bs=1M count=5`（制作一个大的磁盘块，当作一个分区）
- `mkfs.ext4 disk.img`（格式化写入文件系统）
- `mkdir /mnt/mydisk`（建立空目录）；`df -h`（查看可使用的分区）
- `sudo mount -t ext4 ./disk.img /mnt/mydisk/`（将分区挂载到指定目录）；df -h 多出 /dev/loop0 挂在 /mnt/mydisk
- `sudo umount /mnt/mydisk`（卸载分区）后 df -h 恢复
- /dev/loop0 是第一个循环设备（loop device），伪设备，允许将文件作为块设备使用，可将文件（如 ISO 镜像）挂载为文件系统；ls /dev/loop* -l 查看

#### 3-8-2 一个结论
- 分区写入文件系统后无法直接使用，需要和指定的目录关联，进行挂载才能使用【板书强调】
- 可以根据访问目标文件的"路径前缀"准确判断我在哪一个分区（理解到这个层面）

### 3-9 文件系统总结
- 几张图从不同角度总结：Disk → Partition → Block Group → (Super Block/GDT/Block Bitmap/Inode Bitmap/Inode Table/Data Blocks) → Inode Table 列结构【板书强调：文件系统的具体分层！】

## 4. 软硬连接

### 4-1 硬链接
- 真正找到磁盘上文件的不是文件名，而是 inode；Linux 中可以让多个文件名对应同一个 inode
- `touch abc`、`ln abc def`、`ls -li abc def`：abc 和 def 的 inode 都是 263466，链接状态完全相同，称为指向文件的硬链接
- 内核记录连接数：inode 263466 的硬链接数为 2
- 删除文件干了两件事情：①在目录中将对应的记录删除 ②将硬链接数 -1，如果为 0，则将对应的磁盘释放

### 4-2 软链接
- 硬链接是通过 inode 引用另外一个文件；软链接是通过名字引用另外一个文件，新文件和被引用文件的 inode 不同，应用上可想象成快捷方式
- `ln -s abc abc.s`；`ls -li`：abc.s 是独立文件（inode 261678，类型 lrwxrwxrwx，大小 3，abc.s -> abc）
- 文件的三个时间：Access 最后访问时间、Modify 文件内容最后修改时间、Change 属性最后修改时间

### 4-3 软硬连接对比
- 软连接是独立文件；硬链接只是文件名和目标文件 inode 的映射关系
- （表格对比：inode 是否相同、链接数、跨目录/跨分区、删除原文件后的表现）

### 4-4 软硬连接的用途
- 硬链接：. 和 .. 就是硬链接；文件备份
- 软连接：类似快捷方式
