## 1. 进程间通信介绍

### 1-1 进程间通信目的【板书强调——四大目的逐条展开】
- 数据传输：一个进程需要将它的数据发送给另一个进程
- 资源共享：多个进程之间共享同样的资源
- 通知事件：一个进程需要向另一个或一组进程发送消息，通知它们发生了某种事件（如进程终止时要通知父进程）【板书强调】
- 进程控制：有些进程希望完全控制另一个进程的执行（如 Debug 进程），控制进程希望拦截另一个进程的所有陷入和异常，并能及时知道它的状态改变

### 1-2 通信的本质【板书强调——开头整块画图展开】
- 每个进程有独立的地址空间，任何一个进程没办法直接和别的进程通信！
- **进程间通信的本质：最先让不同的进程，先看到同一份资源（内存），然后才有通信的条件**【板书强调——本节总纲，反复出现】
- "进程间通信的本质是：先让不同的进程，看到同一份'内存'（资源），然后才有通信的条件"（板书原文）
- 什么是通信：IPC（Inter-Process Communication）是指运行在同一台计算机或分布式计算机上的多个进程之间进行数据交换和通信的技术。由于每个进程都有自己的地址空间，它们无法直接访问彼此的数据。因此需要通过特定的机制和协议实现，IPC 是操作系统和应用程序之间的一个重要概念，广泛应用于分布式系统、多任务操作系统以及各种应用程序之中
- 系统调用 → OS 的接口 → 设计统一的通信接口标准 / 方案【板书强调——OS 层面设计统一接口】
- 具体通信方式（代称）：1. 基于文件的，管道通信；2. System V - 标准通信【板书强调】

## 2. 管道

### 2-1 什么是管道
- 管道是 Unix 中最古老的进程间通信形式
- 把从一个进程连接到另一个进程的一个数据流称为一个"管道"
- 【板书强调】管道是基于文件的，直接进行通信；匿名管道通常用来父子通信【板书强调】

## 3. 匿名管道

### 3-0 pipe 函数原型
- `#include <unistd.h>`，功能：创建一无名管道
- 原型：`int pipe(int fd[2]);`
- 参数：fd 为文件描述符数组，fd[0] 表示读端，fd[1] 表示写端
- 返回值：成功返回 0，失败返回错误代码

### 3-1 实例代码
- 从键盘读取数据，写入管道，读取管道，写到屏幕（fgets 读 stdin → write 写 fds[1] → read 读 fds[0] → write 写到 fd 1）

### 3-2 用 fork 来共享管道原理【板书强调——画图展开】
- 管道靠 fork 让父子进程共享：先 pipe 再 fork，父子拿到同一组 fd
- 【板书强调】**子进程要继承父进程的文件描述符表！**（files_struct 指针数组 fd_array，子进程指向同一批 struct file）

### 3-3 站在文件描述符角度-深度理解管道【板书强调——整块画图】
- fd[0]=3 读端，fd[1]=4 写端（板书实测 ./testPipe：fds[0]:3 fds[1]:4）
- 【板书强调】读写管道时，数据不落磁盘、不刷新——"文件的里面，不需要磁盘，和磁盘是没有关系的！"
- 管道中间是**内核缓冲区**，这个管道是被 OS 单独设计的【板书强调】
- 父子 struct file：f_mode / f_pos / f_flags / f_count / f_owner / f_op / f_version / private_data；一个管管道写操作 write，一个管管道读操作 read
- 【板书强调】**管道也是文件，属于文件！** 迎合"Linux 一切皆文件"思想
- 父子要沟通！读写权限要正确设置

### 3-4 站在内核角度-管道本质
- 所以，看待管道，就如同看待文件一样！管道的使用和文件一致，迎合了"Linux 一切皆文件思想"

### 3-5 管道样例
#### 3-5-1 测试管道读写
- 父进程 pipe → fork → 子进程 close 读端、write 写端 "hello"、exit；父进程 close 写端、read 读端、printf（完整代码见课件）

#### 3-5-2 创建进程池处理任务【板书强调——大图展开+运行验证】
- 四个文件：Channel.hpp / ProcessPool.hpp / Task.hpp / Main.cc + Makefile
- Channel 类（先描述）：_wfd / _name（"Channel-<wfd>-<pid>"）/ _who；Send(cmd) 用 write 发整数、Close() 关写端、Id()/wFd() 取属性
- ProcessPool：InitProcessPool（每个子进程一对：先 pipe → fork → 子进程**关闭历史 wfd**、close(pipefd[1])、**dup2(pipefd[0], 0)** 把管道重定向到标准输入、执行 work()；父进程 close(pipefd[0])、channels.emplace_back(pipefd[1], id)）
- DispatchTask：SelectTask 随机选任务 → 轮询选 Channel（who++ % size）→ Send 派发
- CleanProcessPool：三个 version——先 Close 再 waitpid（v3 先关后收、v2 倒着关、v1 全关再收），板书讨论关闭顺序的坑
- TaskManager：tasks.push_back 若干 lambda 任务（访问数据库 / url 解析 / 加密 / 数据持久化），SelectTask = rand()%size，Excute 按 cmd 执行
- Worker 子进程主循环：read(0, &cmd, sizeof(cmd)) 读标准输入；n == sizeof(cmd) 执行任务；n == 0（写端全关）则打印 quit 并退出
- 【板书强调】运行输出验证：channel-4-689101 ~ channel-3-689105，ps 查看 S+ 状态；"我先子进程，我先父进程"
- 【板书强调】负载均衡三方案：1. 轮询、2. 随机、3. channel 负载消除（否则负载不均衡）
- 【板书强调】父子关闭顺序问题：第一种方案"倒着关闭！！！"；或者"真的让父进程一人指向所有管道 w 端"（vector 记录 wfd：vector=4,1,5……解决写端引用计数问题）

### 3-6 管道读写规则
- 当没有数据可读时：O_NONBLOCK disable → read 阻塞等待；O_NONBLOCK enable → read 返回 -1，errno 为 EAGAIN
- 当管道满的时候：O_NONBLOCK disable → write 阻塞直到有进程读走数据；O_NONBLOCK enable → 返回 -1，errno 为 EAGAIN
- 如果所有管道**写端**对应的文件描述符被关闭，则 read 返回 0【板书强调】
- 如果所有管道**读端**对应的文件描述符被关闭，则 write 操作会产生信号 SIGPIPE，进而可能导致 write 进程退出【板书强调】
- 当要写入的数据量不大于 PIPE_BUF 时，Linux 将保证写入的原子性；大于 PIPE_BUF 时不再保证原子性
- 【板书强调】POSIX.1：write(2) 少于 PIPE_BUF 字节必须是原子的；Linux 上 PIPE_BUF 是 4096 字节

### 3-7 管道特点【板书强调——5 条逐条板书展开】
- 只能用于具有共同祖先（具有亲缘关系）的进程之间通信；通常一个管道由一个进程创建，该进程调用 fork，此后父子进程应用该管道【板书强调】
- 管道提供流式服务【板书强调】
- 进程退出，管道释放，所以管道的生命周期随进程【板书强调】
- 内核会对管道操作进行同步与互斥（板书：管道通信自带同步和互斥，属于半双工的一种特殊情况）【板书强调】
- 管道是半双工的，数据只能向一个方向流动；需要双方通信时，需要建立起两个管道【板书强调——板书辨析：任一时刻一个读一个写 = 半双工；任一时刻可同时读写 = 全双工】

### 3-8 验证管道通信的 4 种情况【板书强调——逐条实验+输出】
- 读正常 && 写满：写阻塞
- 写正常 && 读空：读阻塞
- 写关闭 && 读正常：read 返回 0，表示读到文件结尾
- 读关闭 && 写正常：写进程被 SIGPIPE 杀死
- 【板书强调】管道容量实测：65536（4096×16）= 64KB（ulimit/实验验证）
- 【板书强调】读写快慢没有关系（写的慢读的快 / 写的快读的慢，管道都在，没有关系！），板书用 child say 大段乱序/有序输出演示两种节奏

## 4. 命名管道

### 4-1 为什么需要命名管道【板书强调——从匿名管道局限引出】
- 匿名管道只能用于具有血缘关系的进程间通信；如果两个进程不相关？该如何进行通信呢？
- 【板书强调】进程 A 打开了 /a/b/c.txt，进程 B 也打开 /a/b/c.txt：内核中，操作系统会不会把这个文件（inode/文件内容等）在内存中加载两次？**不会，因为没必要！**
- 【板书强调】**路径具有唯一性！** 文件有路径、有名字 → **让不同的进程看到同一份资源的办法：通过打开同一个路径下的同一个文件！**（所以父子进程可以向同一个显示器文件进行打印）
- 【板书强调】管道文件！只会被打开，不需要刷新！（不落盘）
- 命名管道是一种特殊类型的文件（FIFO）

### 4-2 创建一个命名管道
- 命令行创建：`$ mkfifo filename`
- 程序内创建：`int mkfifo(const char *filename, mode_t mode);`（例：mkfifo("p2", 0644); return 0;）

### 4-3 匿名管道与命名管道的区别【板书强调——文件级/代码级】
- 匿名管道由 pipe 函数创建并打开；命名管道由 mkfifo 函数创建，打开用 open
- FIFO 与 pipe 之间唯一的区别在它们创建与打开的方式不同，一旦这些工作完成之后，它们具有相同的语义
- 【板书强调】命名管道特性和匿名管道一致的，只有一点不同：**命名管道可以用来进行不相关的进程间通信**（板书标注"文件级 / 代码级"差异维度）

### 4-4 命名管道的打开规则
- 为读而打开 FIFO：O_NONBLOCK disable → 阻塞直到有相应进程为写而打开；O_NONBLOCK enable → 立刻返回成功
- 为写而打开 FIFO：O_NONBLOCK disable → 阻塞直到有相应进程为读而打开；O_NONBLOCK enable → 立刻返回失败，错误码 ENXIO

### 4-5 实例1：用命名管道实现文件拷贝
- 进程一：mkfifo("tp", 0644) → open("abc", O_RDONLY) → open("tp", O_WRONLY) → 循环 read/write → close
- 进程二：open("abc.bak", O_WRONLY|O_CREAT|O_TRUNC, 0644) → open("tp", O_RDONLY) → 循环 read/write → close → unlink("tp")
- （板书图：abc → 管道 → abc.bak 两侧画 struct file 与内核缓冲区）

### 4-6 实例2：用命名管道实现 server&client 通信
- Makefile：.PHONY:all，all:clientPipe serverPipe 两个目标
- serverPipe.c：umask(0) → mkfifo("mypipe", 0644) → open 只读 → 循环 read：s>0 打印 client say#；s==0 打印 client quit, exit now！；s<0 报错
- clientPipe.c：open("mypipe", O_WRONLY) → 循环 read(0) 读标准输入 → write 进管道
- 结果：两个不相关进程通过 mypipe 通信

## 5. system V 共享内存

### 5-0 前置结论【板书强调】
- 共享内存区是**最快的 IPC 形式**：一旦这样的内存映射到共享它的进程的地址空间，这些进程间数据传递不再涉及内核，即进程不再通过执行进入内核的系统调用来传递彼此的数据【板书强调】
- 【板书强调】IPC 本质（板书总纲重现）：让不同的进程，先看到同一份资源
- system V 是一种标准，Linux 内核支持了这种标准，专门设计了一个 IPC 通信模块【板书强调】
- 通信接口设计：原理、接口、脱抖性（板书语）

### 5-1 共享内存示意图【板书强调——整块画图】
- 进程 A / 进程 B 的虚拟地址空间（argp,envion / 栈 / 堆 / 为堆扩充预留 / 未初始化数据 bss / 初始化数据 / 文本程序代码）通过**页表**映射到物理内存中的一段**共享内存**
- step 1：通过某种方式建立映射（mmap 概念关联）【板书强调】
- 【板书强调】读共享内存，并没有出现调用系统调用！**共享区属于用户空间，可以让用户直接使用！**
- 【板书强调】共享内存进程通信中，速度最快的方式：1. 映射之后，读写，直接被对方看到！2. 不需要进行系统调用来获取或写入内容（板书标"优点！"）
- 【板书强调】通信双方，没有所谓的"同步机制"！数据不一致！**共享内存没有保护机制！** → 对共享内存，数据的保护是问题（板书演示 AA BB CC / AA B / AA BB C 竞争乱序）
- 如果非要给共享内存保护起来，有没有其他方案可以选择呢？命名管道呢？（引出实例2）
- 【板书强调】在内核中，共享内存在创建的时候，它的大小必须是 **4KB(4096) 的整数倍**；4097 → 4098?? → 4096×2 → **向上 4KB 取整**（板书：我查出来的大小 40977？你要 4097！）

### 5-2 共享内存数据结构
- `struct shmid_ds`：shm_perm（操作权限）、shm_segsz（段大小字节）、shm_atime/dtime/ctime（最近挂接/脱离/修改时间）、shm_cpid（创建者 pid）、shm_lpid（最近操作者 pid）、shm_nattch（当前挂接数）等【板书强调——源码展开】
- `struct ipc_perm`：key_t key（shmget(2) 供给的 key）、uid/gid（owner）、cuid/cgid（creator）、mode（权限 + SHM_DEST/SHM_LOCKED 标志）、__seq【板书强调——源码展开】
- 【板书强调】我们 shmget(key) 后，key 就会被设置到共享内存的描述结构体中！

### 5-3 共享内存函数【板书强调——四件套逐一原型展开】
- **shmget**：`int shmget(key_t key, size_t size, int shmflg);` 用来创建共享内存；key 是这个共享内存段名字，size 是大小，shmflg 由九个权限标志构成（用法同文件 mode）；IPC_CREAT：不存在则创建并返回、已存在则获取并返回；IPC_CREAT|IPC_EXCL：不存在则创建并返回、已存在则出错返回；成功返回非负整数（共享内存段的标识码），失败返回 -1
  - 【板书强调】不同的进程拿 shm 来进行通信，标识共享内存的唯一性！
  - 【板书强调】key 不是内核直接形成的，而是在用户级构建并传给 OS 的！（key 来区分，未来只给内核进行区分唯一性）
  - 【板书强调】构建一个 key：`key_t ftok(const char *pathname, int proj_id);`（命名管道→第一个靠文件唯一性；共享内存→靠构建一个 key；两个进程只要 pathname+proj_id 相同就拿到同一个 key，A/B 进程都拿 key 找操作系统）
  - 【板书强调】只要 shmget 成功创建，一定是一个全新的共享内存！
- **shmat**：`void *shmat(int shmid, const void *shmaddr, int shmflg);` 将共享内存段连接到进程地址空间（shmat = at:attach，关联）；shmaddr 指定连接的地址，shmflg 取 SHM_RND / SHM_RDONLY；成功返回指向共享内存第一个节的指针，失败返回 -1
  - 【板书强调】说明：shmaddr 为 NULL，核心自动选择一个地址；不为 NULL 且无 SHM_RND 则以 shmaddr 为连接地址；不为 NULL 且设 SHM_RND 则自动向下调整为 SHMLBA 整数倍（shmaddr - (shmaddr % SHMLBA)）；SHM_RDONLY 表示只读
  - 【板书强调】板书辨析：起始虚拟地址 / 虚拟地址，固定地址进行处理！0 = 使用默认设置；类比 `void *malloc(size_t size);`
- **shmdt**：`int shmdt(const void *shmaddr);` 将共享内存段与当前进程脱离；成功返回 0 失败返回 -1
  - 【板书强调】**注意：将共享内存段与当前进程脱离不等于删除共享内存段！**
- **shmctl**：`int shmctl(int shmid, int cmd, struct shmid_ds *buf);` 用于控制共享内存；cmd 将要采取的动作（有三个可取值）；buf 指向保存共享内存模式状态和访问权限的数据结构

### 5-4 实例1：共享内存实现通信

## 7. system V 信号量 - 选学了解即可

### 7-1 并发编程概念铺垫【板书强调——层层推导】
- 多个执行流(进程)，能看到的同一份公共资源：**共享资源**
- 被保护起来的共享资源叫做**临界资源**
- 保护的方式常见：**互斥与同步**
- 任何时刻，只允许一个执行流访问资源，叫做**互斥**
- 多个执行流访问临界资源的时候具有一定的顺序性，叫做**同步**
- 系统中某些资源一次只允许一个进程使用，称为**临界资源**或互斥资源
- 进程中涉及到互斥资源的程序段叫**临界区**；你写的代码 = 访问临界资源的代码(临界区) + 不访问临界资源的代码(非临界区)
- 【板书强调】所谓的对共享资源进行保护，**本质是对访问共享资源的代码进行保护**（保护临界区代码 = 就是变相的保护临界资源！）
- 【板书强调】推导链：1. 没有做保护起来的共享资源；2. 单独的代码，访问了这个没有被保护的公共资源
- 【板书强调】原子性：要么做，要么不做（申请锁→临界区→释放锁 图）；**锁本身也要被共享！** 怎么保证锁的安全？**申请锁的时候，必须是原子的！**
- 【板书强调】共享内存没有"保护机制"，数据不一致！解决方案：信号量——按照目的方案！（引出信号量）

### 7-2 信号量【板书强调——四方面+电影院例子整块展开】
- 特性方面：IPC 资源必须删除，否则不会自动清除，除非重启，所以 system V IPC 资源的生命周期随内核
- 理解方面：**信号量是一个计数器**【板书强调：本质是一个计数器！用来描述临界资源中，资源的数量多少】
- 作用方面：保护临界区
- 本质方面：**信号量本质是对资源的预订机制**【板书强调】
- 操作方面：申请资源，计数器 --，**P 操作**；释放资源，计数器 ++，**V 操作**【板书强调：P/V 操作是原子完成的资源预订机制；申请信号量 -- 原子性；释放 sem++ 原子性】
- 【板书强调】所有进程，访问临界资源中的一小块，就必须先申请信号量！——进程访问资源前，先申请信号量，本质：是对资源的预订机制！！！
- 【板书强调】电影院例子：电影院 XX 的放映厅就是一个临界资源；最适合两个问题：1. 票卖完了、2. 要买票；内部含了很多个子资源（板书画座位格：int sem=16 //bug sem--; if(sem<0) 阻塞挂起；int pos=0 选座位）
- 【板书强调】使用守则：1. 不要访问同一个位置，2. 不要塞入过多的进程进来 → **把共享内存按照不同的区域，部分使用！并发访问 && 不出现问题！**（资源整体使用 vs 资源不是整体使用）
- 【板书强调】细节1：**信号量本身就是共享资源**（申请 -- 要原子性、sem++ 要原子性）
- 【板书强调】细节2：信号量只有 1 或者 0 两种值的信号量，叫做**二元信号量**！就是互斥！
- 【板书强调】多张票（多值信号量）→ 电影院的座位图（申请哪个座位给你；要防止你和别人抢到）
- 信号量的内部结构：`struct sem { int count; task_struct* waitqueue; }`【板书强调】
- 【板书强调】信号量和通信有什么关系？1. 先问问信号量，每个进程都得看到同一个信号量！！2. 不是通信数据，才是通信吗？IPC 通知、同步互斥，也算！！！**system V 解决的就是这个问题！**
