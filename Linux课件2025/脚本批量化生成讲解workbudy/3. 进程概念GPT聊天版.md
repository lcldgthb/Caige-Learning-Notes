# 1. 冯诺依曼体系结构

## 1.1 五大部件

电脑里有很多设备。新手容易把键盘、CPU、内存、硬盘看成一堆零散部件，但它们其实可以分成五类，各自负责不同工作。

### 输入设备

**输入设备**：把外部信息送进电脑的设备。

常见输入设备包括：

- 键盘、鼠标：输入文字和操作指令
- 话筒、摄像头：输入声音和图像
- 网卡：接收网络数据
- 磁盘：把已经保存的数据读入电脑

### 输出设备

**输出设备**：把电脑处理后的信息送到外部的设备。

常见输出设备包括：

- 显示器：显示文字和图像
- 磁盘：保存电脑产生的数据
- 网卡：把数据发送到网络
- 打印机：打印文字和图像

同一个设备可能既是输入设备也是输出设备。例如，网卡接收网络数据时是输入设备，发送网络数据时是输出设备。

### CPU

**CPU**：电脑中负责执行指令、处理数据的核心部件，可以理解为电脑的“计算和指挥中心”。

CPU 由两部分组成：

- **运算器**：进行加法、比较等数据运算
- **控制器**：决定下一步执行哪条指令、从哪里取数据

### 存储器

**存储器**：保存程序和数据的部件。在冯诺依曼体系结构中，提到“存储器”通常主要指**内存**。

内存可以理解为 CPU 工作时使用的临时工作区域：程序和数据必须进入内存，CPU 才能使用它们。

因此，五大部件可以表示为：

```text
输入设备 → 存储器（内存）↔ CPU（运算器 + 控制器）→ 输出设备
```

> **冯诺依曼体系结构的五大部件是：输入设备、输出设备、存储器、运算器和控制器；其中运算器和控制器合称 CPU。**

---

## 1.2 从内存角度理解 IO

只看“输入”和“输出”容易混淆：磁盘既能读数据又能写数据，网卡既能收数据又能发数据。更清楚的判断方式，是站在**内存**的角度看数据方向。

**IO** 是 `Input/Output` 的缩写，表示输入和输出。

- 数据从外部设备进入内存：这是输入
- 数据从内存离开，前往外部设备：这是输出

例如：

```text
键盘 → 内存
```

键盘产生的数据进入内存，所以键盘是输入设备。

```text
内存 → 显示器
```

数据从内存送到显示器，所以显示器是输出设备。

磁盘的情况是：

```text
磁盘 → 内存：输入
内存 → 磁盘：输出
```

网卡的情况也是根据方向判断：

```text
网络 → 网卡 → 内存：输入
内存 → 网卡 → 网络：输出
```

> **判断一个设备此时属于输入还是输出，要看数据相对于内存的方向：进入内存是输入，离开内存是输出。**

---

## 1.3 软件运行必须先加载

假设电脑里有一个程序文件。程序刚开始只是保存在磁盘上的文件，CPU 不能直接从磁盘中执行它；如果直接执行，CPU 就必须等待速度较慢的磁盘不断提供数据。

因此，程序运行前要先完成“加载”。

**加载**：把磁盘上的程序文件复制到内存中，让 CPU 能够使用它。

运行过程可以表示为：

```text
程序文件在磁盘上
        ↓ 加载
程序进入内存
        ↓
CPU 从内存获取指令和数据
        ↓
CPU 执行程序
```

程序运行时，CPU 需要做两件事：

1. 从内存中获取程序指令
2. 从内存中读取、修改和写入数据

例如，一个计算程序要计算两个数相加，程序指令和这两个数都必须先位于内存中，CPU 才能读取它们并完成计算。

> **程序运行之前通常保存在磁盘上；运行时必须先加载到内存，CPU 才能从内存获取指令和数据并执行。**

---

## 1.4 CPU、外设和内存之间的数据关系

CPU 处理数据时，并不是直接和键盘、磁盘、网卡等所有外设进行数据交换。数据通常先到内存，再由 CPU 使用。

例如，键盘输入字符时：

```text
键盘 → 内存 → CPU
```

显示器显示结果时：

```text
CPU → 内存 → 显示器
```

因此，从数据传输角度看：

- CPU 获取数据，要从内存获取
- CPU 写入数据，要写入内存
- 外设把数据交给电脑，通常先交给内存
- 电脑把数据交给外设，通常先由内存提供

这里的“拷贝”不是一定指 C 语言中的某个函数，而是指数据从一个部件转移到另一个部件。

```text
设备 A → 内存 → 设备 B
```

如果设备 A 和设备 B 不能直接高效交换数据，就需要经过内存完成中转。数据转移的速度越慢，整个操作等待的时间就越长。

> **在数据层面，CPU 主要和内存打交道，外设也主要和内存打交道；设备之间传递数据，本质上经常表现为数据在不同部件之间的拷贝。**

---

## 1.5 设备速度差异

不同部件的速度差距非常大。外设通常按毫秒级计算，而 CPU 通常按纳秒级计算。

- **毫秒**：`ms`，千分之一秒
- **纳秒**：`ns`，十亿分之一秒

两者之间相差：

```text
1 毫秒 = 1,000,000 纳秒
```

因此，如果 CPU 每次都直接等待磁盘、键盘或网络设备，CPU 的大量时间就会浪费在等待上。

这说明计算机系统不仅要关心 CPU 算得快不快，还要关心数据能不能快速到达 CPU。数据在设备之间拷贝得越慢，整体运行效率越低。

> **计算机体系结构的整体效率，不只取决于 CPU 的计算速度，还取决于设备之间的数据拷贝速度；外设与 CPU 之间存在巨大的速度差距。**

## 1.6 存储金字塔

### 为什么需要多层存储

如果只使用最快的存储部件，电脑会很快，但成本高、容量小；如果只使用容量大的存储部件，成本低，但速度慢。

因此，计算机采用多层存储结构：越靠近 CPU 的存储越快，但通常越贵、容量越小；越远离 CPU 的存储越慢，但通常容量越大、成本越低。

这就是**存储金字塔**：按照速度、价格和容量，把不同存储部件从上到下排列起来。

```text
             L0  寄存器
          L1～L3 高速缓存
              L4  主存
          L5  本地磁盘
       L6  远程二级存储
```

### 各层存储

| 层级 | 名称 | 大白话理解 | 主要特点 |
|---|---|---|---|
| L0 | 寄存器 | CPU 手边直接拿来用的极小存储位置 | 速度最快，容量最小 |
| L1～L3 | 高速缓存 | CPU 和内存之间的快速中转区 | 使用 SRAM，速度很快 |
| L4 | 主存 | 通常所说的内存 | 使用 DRAM，容量比缓存大 |
| L5 | 本地二级存储 | 本机的磁盘，如硬盘、固态硬盘 | 容量大，速度比内存慢 |
| L6 | 远程二级存储 | 通过网络访问的存储，如文件服务器 | 距离最远，速度受网络影响 |

**SRAM**：一种速度较快、价格较高、容量较小的存储器，常用于高速缓存。

**DRAM**：一种容量较大、价格相对较低、速度不如 SRAM 的存储器，通常用于主存，也就是内存。

**远程二级存储**：不在本机上的存储，需要通过网络访问，例如分布式文件系统或 Web 服务器上的文件。

存储金字塔的总体规律是：

```text
越靠近 CPU
    ↓
速度越快、单位成本越高、容量越小
    ↓
越远离 CPU
    ↓
速度越慢、单位成本越低、容量越大
```

### 为什么不只使用最快的存储

最快的寄存器容量太小，无法保存完整程序和大量数据；容量大的磁盘虽然能保存很多内容，但速度又无法满足 CPU 的高速处理。

所以计算机把不同存储组合起来：

- 用寄存器和高速缓存满足 CPU 的快速访问
- 用内存保存正在运行的程序和数据
- 用磁盘保存大量文件
- 用远程存储保存更大规模的数据

这种设计是在速度、容量和成本之间取得平衡。现代计算机是性价比的产物，芯片技术的发展以及**摩尔定律**推动了这种多层存储结构不断发展。

**摩尔定律**：经验规律，指集成电路中可容纳的晶体管数量大约会定期增加，从而推动计算能力提高、单位成本下降。

> **存储金字塔的规律是：越靠近 CPU 越快、越贵、越小；越远离 CPU 越慢、越便宜、越大。**

## 1.7 经典应用题：QQ 聊天和发文件的数据流

假设 A 给 B 发送一条聊天消息。消息从 A 的键盘输入，到 B 的显示器显示，中间要经过两台电脑各自的冯诺依曼体系结构。

完整数据流如下：

```text
A 的键盘
    ↓
A 的内存
    ↓
A 的网卡
    ↓
网络
    ↓
B 的网卡
    ↓
B 的内存
    ↓
B 的显示器
```

分步骤看：

1. A 敲击键盘，文字数据进入 A 的内存。
2. A 的程序处理这段文字，并把待发送数据交给 A 的网卡。
3. A 的网卡把数据发送到网络。
4. 数据通过网络到达 B 的网卡。
5. B 的网卡把接收到的数据放入 B 的内存。
6. B 的程序从内存中读取数据，并要求显示器显示。
7. 数据从 B 的内存送到 B 的显示器。

两台电脑各自都有一套冯诺依曼体系结构：

```text
A 的输入设备 → A 的内存 ↔ A 的 CPU → A 的输出设备
B 的输入设备 → B 的内存 ↔ B 的 CPU → B 的输出设备
```

网卡在这个过程中同时承担两种角色：

- A 的网卡把内存中的数据发送出去：它是输出设备
- B 的网卡把网络数据接收进内存：它是输入设备

因此，网卡并不是固定只能属于输入设备或输出设备，而是要根据当前的数据方向判断。

> **QQ 聊天的数据流可以概括为：A 的键盘 → A 的内存 → A 的网卡 → 网络 → B 的网卡 → B 的内存 → B 的显示器；网卡既是输入设备也是输出设备。**

# 2. 操作系统（Operating System，OS）

## 2-1 概念与定位

### 2-1-1 OS 是什么

电脑中有很多硬件，例如 CPU、内存、硬盘、显示器；也有很多软件，例如浏览器、编辑器、游戏。它们数量多、使用方式不同，如果每个应用程序都直接控制硬件，程序之间就容易互相干扰，因此需要一个统一的管理者。

**操作系统（OS）：一组最基本的程序集合，负责管理计算机中的软件和硬件资源。**

理解 OS 时，可以始终追问三个问题：

1. **是什么？**——OS 是什么程序，处在什么位置？
2. **为什么？**——为什么需要 OS，它要解决什么麻烦？
3. **怎么办？**——OS 具体通过什么结构和机制完成管理？

> **关键结论：OS 不只是“让电脑运行起来的软件”，更重要的是统一管理软硬件，并为应用程序提供运行环境。**

### 2-1-2 OS 由什么组成

OS 不是一个单独的文件，而是由多部分组成：

- **内核（kernel）**：OS 最核心的部分，直接负责进程管理、内存管理、文件管理和驱动管理。
- **函数库**：提供很多已经写好的功能，应用程序可以调用。
- **shell 程序**：接收用户输入的命令，再请求 OS 完成对应工作。
- 其他预装程序和工具。

可以把 OS 分成两层：

```text
广义 OS
├── 外壳：shell、glibc、原生库、预装软件
└── 狭义 OS：内核 kernel
```

**狭义 OS** 通常指内核；**广义 OS** 则包括内核以及围绕内核工作的外壳、函数库和其他程序。

安卓可以用这个关系理解：

```text
安卓系统 = 安卓外壳 + Linux 内核
```

安卓提供了界面、应用框架和各种工具，而底层真正负责进程、内存、文件等核心管理工作的，是 Linux 内核。

### 2-1-3 `printf` 的本质

程序调用 `printf` 时，表面上只是输出一段文字，但这段文字最终需要显示器显示出来。显示器是硬件，所以程序不能绕过 OS 直接随意操作它，而要经过系统提供的管理路径。

```cpp
#include <stdio.h>                 // 引入 printf 所在的函数库

int main()                         // 程序入口
{
    printf("hello os\n");           // 请求把文字输出到显示设备
    return 0;                       // 返回程序执行结果
}
```

`printf` 通常由函数库提供，函数库在底层会进一步请求 OS，OS 再通过驱动控制显示相关硬件。

> **关键结论：`printf` 的最终效果，是把程序中的数据经过 OS 和驱动，写到显示器等硬件上。**

## 2-2 设计目的

### 2-2-1 OS 的真正目的

应用程序开发者不应该关心每一种硬盘、显示器、键盘的具体控制细节。否则，同一个程序换一台电脑就可能无法运行。

因此，OS 对上层应用程序提供一个统一、稳定、方便的运行环境。

- **对上**：为用户程序，也就是各种应用程序，提供良好的执行环境。
- **对下**：与硬件交互，管理全部软硬件资源。

二者地位不同：

- 为应用程序提供良好执行环境，是 OS 的**目的**。
- 与硬件交互、管理资源，是 OS 实现这个目的的**手段**。

> **关键结论：OS 管理硬件不是最终目的；最终目的是让应用程序能够方便、可靠地运行。**

### 2-2-2 软硬件体系结构

应用程序访问硬件时，不能直接跳到硬件，中间必须经过多层。每一层只负责自己擅长的工作，并向上一层提供更方便的接口。

```text
用户
  ↓ 指令、开发、管理操作
用户操作接口
  ↓ shell、函数库、部分指令
system call 系统调用接口
  ↓
内核 kernel
  ↓
驱动
  ↓
硬件
```

各层的作用可以这样理解：

- **用户**：提出需求，例如运行程序、读取文件、输出文字。
- **用户操作接口**：把用户的操作转换成程序能够执行的请求。
- **系统调用接口**：应用程序向 OS 提出请求的正式入口。
- **内核**：根据请求进行进程、内存、文件和设备管理。
- **驱动**：专门负责和某一种硬件沟通的软件。
- **硬件**：真正执行计算、存储、显示和输入输出。

程序越接近硬件，越需要处理具体设备细节；程序越接近用户，使用方式越简单。

## 2-3 如何理解“管理”

### 2-3-1 管理的三个基本认识

现实中的管理者不可能亲自盯着每一个被管理对象，也不一定需要和被管理对象直接见面。例如校长不需要每天逐个询问学生情况，就可以管理整个学校。

因此，管理通常遵循三句话：

1. 管理者和被管理者可以不需要见面。
2. 管理者根据记录下来的**数据**进行管理。
3. 管理者不直接见面时，需要由中间层获取和整理数据。

> **关键结论：管理的本质，是管理者根据数据，对被管理对象做决策和操作。**

### 2-3-2 校长 1.0：根据表格管理学生

假设校长要管理全校学生，直接记住每个学生的信息是不现实的，所以可以建立一张 Excel 表格：

```text
姓名 | 性别 | 年龄 | 籍贯 | 紧急联系人 | 各科成绩 | 职位 | 宿舍号
```

当学生转宿舍、修改成绩、查询信息或毕业离校时，校长实际上是在对这张表做四类操作：

- **增加**：录入新学生。
- **删除**：删除已经离校的学生。
- **查询**：查找某个学生的信息。
- **修改**：更新宿舍号、成绩等信息。

所以：

> **管理学生 = 对描述学生的数据进行增删查改。**

这里，学生是被管理对象，表格是对学生信息的记录，中间层负责收集和整理数据，校长根据表格做决定。

### 2-3-3 校长 2.0：用程序和数据结构管理

如果学生数量非常多，手工维护 Excel 会变得低效。程序员可以先用结构体描述一个学生对象，再用链表把多个学生对象组织起来。

```cpp
struct stu
{
    char name[32];                 // 保存姓名
    int age;                       // 保存年龄
    char hometown[32];             // 保存籍贯
    struct stu* next;              // 指向下一个学生对象
};
```

结构体解决“一个学生有哪些信息”的问题；链表解决“多个学生如何组织起来”的问题。

```text
学生对象 1 → 学生对象 2 → 学生对象 3 → NULL
```

之后，新增学生就是把对象插入链表，删除学生就是从链表中移除对象，查询学生就是遍历链表，修改学生就是更新对象中的数据。

这就是“校长 2.0”：

- 校长的决策工作由程序逻辑完成。
- 学生信息由结构体描述。
- 多个学生由链表组织。
- 日常管理转化成对链表的增删查改。

这里的核心不是某一种表格或链表，而是先把现实对象转换成计算机能够处理的数据，再设计数据之间的组织方式。

### 2-3-4 计算机管理的方法论

面对任何管理问题，都可以按两步处理：

```text
现实对象
  ↓ 描述
结构体 / 类
  ↓ 组织
链表、树、哈希等数据结构
  ↓ 操作
增删查改
```

- **先描述**：明确对象有哪些属性，用 `struct` 结构体表示。
- **再组织**：明确多个对象之间如何保存和联系，用链表等数据结构组织。

这就是计算机管理的基本方法论：

> **关键结论：先描述，再组织；先用结构体或类表示对象，再用数据结构组织多个对象。**

在 C++ 中，这条思路进一步发展为“先描述、再组织”：

```text
对象描述 → 类 → STL 容器和算法
```

## 2-4 系统调用和库函数

### 2-4-1 为什么需要系统调用

应用程序如果想使用硬件，不能直接操作硬件。因为多个程序可能同时请求同一个硬件，且用户程序可能存在错误甚至恶意行为；如果谁都能直接控制硬件，整个系统就不安全。

因此，OS 设置了统一的正式入口。

**系统调用（system call）：应用程序向操作系统请求服务时使用的函数接口，本质上是 OS 提供的函数。**

例如，程序需要读取文件、创建进程、申请内存或输出数据时，都要通过系统调用请求内核完成。

> **关键结论：访问操作系统必须使用系统调用；系统调用本质上就是系统提供的函数。**

### 2-4-2 为什么不能直接访问硬件

以银行为例：

- **银行系统**：相当于操作系统。
- **银行窗口**：相当于系统调用。
- **客户**：相当于用户程序。
- **大堂经理**：相当于库、外壳和指令。
- **账户、现金和存取设备**：相当于系统中的资源和硬件。

客户不能直接进入金库修改账户数据，只能通过银行窗口提交信息，再根据窗口返回的结果完成业务。

同样，用户程序不能直接控制硬盘、显示器或内存，而要通过系统调用：

```text
用户程序
  ↓ 提交参数
系统调用
  ↓
操作系统内核
  ↓
驱动
  ↓
硬件
  ↑
返回结果
```

系统调用通常通过两类信息与程序交互：

- **输出参数**：程序提交给 OS 的数据，例如要打开的文件名。
- **返回值**：OS 执行后返回给程序的结果，例如是否成功、读取了多少数据。

OS 不相信任何用户或程序，因此必须通过统一入口检查请求、判断权限、分配资源，再决定是否执行。

> **关键结论：OS 不允许用户程序绕过系统调用直接控制硬件；系统调用就是用户程序和 OS 之间的安全窗口。**

### 2-4-3 系统调用和库函数的关系

直接使用系统调用通常需要处理较多底层细节。为了让程序更容易编写，函数库会提供更符合人类使用习惯的函数。

**库函数：函数库提供给程序员使用的函数，通常封装了更底层的系统调用。**

例如，程序员使用 `printf` 输出文字时，不需要自己处理显示设备的具体控制过程。`printf` 由 C 函数库提供，底层可能继续调用 OS 的系统调用。

二者关系如下：

| 对比项 | 库函数 | 系统调用 |
|---|---|---|
| 提供者 | 函数库 | 操作系统内核 |
| 面向对象 | 程序员 | 函数库或应用程序 |
| 作用 | 封装复杂操作，方便使用 | 正式请求 OS 管理资源 |
| 是否一定直接接触内核 | 不一定 | 是 |
| 例子 | `printf`、字符串处理函数 | 文件、进程、内存、设备相关请求 |

它们不是互相独立的两套功能，而是上下层关系：

```text
应用程序
  ↓
C 函数库
  ↓ 可能封装
系统调用
  ↓
操作系统内核
  ↓
驱动和硬件
```

不同操作系统提供的底层系统调用不同，但程序员通常可以通过 C 函数库使用较统一的接口。

```text
Linux / Windows / macOS
          ↓
       C 语言
          ↓
       C 函数
```

> **关键结论：库函数是方便程序员使用的上层封装，系统调用是程序真正请求 OS 服务的底层入口；库函数底层可能包含系统调用。**

# 3. 进程

## 3-1 基本概念与基本操作

### 1. 什么是进程：三种视角

电脑中可能同时打开浏览器、编辑器、终端和播放器。操作系统必须知道每个程序在哪里、占用了多少内存、是否正在运行，以及下一步应该执行什么。

因此，“进程”可以从三个角度理解：

| 视角 | 解释 |
|---|---|
| 课本概念 | 程序的一次执行实例 |
| 内核观点 | 操作系统用来分配 CPU 时间、内存等资源的实体 |
| 最终结论 | 进程 = `task_struct` + 自己的代码和数据 |

`task_struct`：Linux 内核中描述一个进程的结构体，也叫进程控制块 PCB（Process Control Block）。

程序只是磁盘上的文件；程序被加载、运行，并且需要操作系统管理时，才成为进程。`task_struct` 相当于进程的“档案”，代码和数据则是进程真正要执行、要使用的内容。

> **进程 = 内核数据结构 PCB（`task_struct`）+ 自己的代码和数据。**

### 2. 操作系统如何管理进程

系统中可能同时存在很多进程。操作系统不可能只靠“记住它们”来管理，而要先把每个进程描述成一个 `task_struct`，再把这些结构组织起来。

这就是“先描述，再组织”：

```text
进程
  ↓ 描述
task_struct
  ↓ 组织
进程链表、运行队列、等待队列……
```

Linux 内核会把多个 `task_struct` 组织成双向链表。于是，进程管理就变成了对这些链表的增、删、查、改：

- 增：创建进程并加入链表；
- 删：进程退出后从链表中移除；
- 查：查找某个 PID 对应的进程；
- 改：修改进程状态、优先级等属性。

> **对进程的管理，本质上就是对 `task_struct` 双向链表的增删查改。**

### 3. `task_struct` 中保存什么

一个进程的所有重要属性，都可以直接或间接通过它的 `task_struct` 找到。

| 属性分类 | 保存的信息 |
|---|---|
| 标识符 | 唯一标识本进程的 PID 等信息 |
| 状态 | 任务状态、退出代码、退出信号等 |
| 优先级 | 本进程相对于其他进程的优先级 |
| 程序计数器 | 下一条即将执行的指令地址 |
| 内存指针 | 代码、数据以及共享内存的位置 |
| 上下文数据 | 进程暂停时，CPU 寄存器中的数据 |
| I/O 状态信息 | 正在等待的 I/O、使用的设备和文件 |
| 记账信息 | 已使用的处理器时间、时钟数、时间限制等 |

程序计数器可以理解为“书签”：程序执行到哪里，就记录下一次应该从哪里继续。

上下文数据是进程暂时离开 CPU 时保存的“现场”，例如下一条指令的位置、计算中间结果等。

因此，历史上执行过的命令、工具和自己编写的程序，只要运行起来，全部都是进程。

> **进程的所有属性，都可以直接或间接通过 `task_struct` 找到。**

### 4. 查看和终止进程

#### 查看进程：`ps ajx`

语法：

```bash
ps ajx  # 查看系统中的进程及其父子关系、状态等信息
```

常见列的含义：

| 列 | 含义 |
|---|---|
| `PPID` | 父进程 ID |
| `PID` | 当前进程 ID |
| `PGID` | 进程组 ID |
| `SID` | 会话 ID |
| `TTY` | 进程关联的终端 |
| `TPGID` | 前台进程组 ID |
| `STAT` | 进程状态 |
| `UID` | 启动进程的用户 ID |
| `TIME` | 进程占用的 CPU 时间 |
| `COMMAND` | 启动进程的命令 |

如果输出较长，可以只看表头或筛选内容：

```bash
ps ajx | head -1  # 只显示 ps 输出的第一行表头
ps ajx | grep bash  # 筛选命令行中含 bash 的进程
ps aux  # 以另一种格式查看进程
```

#### 终止进程：`kill`

语法：

```bash
kill -9 PID  # 向指定 PID 的进程发送 9 号信号，强制终止它
```

`PID` 要替换成具体的进程 ID。前台进程通常可以用 `Ctrl+C` 终止：

```text
Ctrl+C  → 终止当前终端前台运行的进程
```

### 5. 获取进程 ID：`getpid` 和 `getppid`

程序有时需要知道“我是谁”以及“是谁启动了我”。这两个信息分别由两个系统调用提供。

系统调用：程序请求操作系统内核提供服务的函数接口。

| 函数 | 作用 |
|---|---|
| `getpid()` | 获取当前进程的 PID |
| `getppid()` | 获取当前进程的父进程 PID，也就是 PPID |

头文件和函数声明：

```cpp
#include <sys/types.h>  // 提供 pid_t 类型
#include <unistd.h>  // 提供 getpid 和 getppid

pid_t getpid(void);  // 获取当前进程的 PID
pid_t getppid(void);  // 获取当前进程的父进程 PID
```

它们属于系统调用，使用 `man 2 getpid` 或 `man 2 getppid` 可以查看第 2 区手册。

完整程序：

```cpp
#include <iostream>  // 提供 cout
#include <sys/types.h>  // 提供 pid_t 类型
#include <unistd.h>  // 提供 getpid 和 getppid

int main() {  // 程序入口
    std::cout << "pid: " << getpid() << '\n';  // 打印当前进程 ID
    std::cout << "ppid: " << getppid() << '\n';  // 打印父进程 ID
    return 0;  // 正常结束进程
}
```

编译运行：

```bash
g++ myprocess.cpp -o myprocess  # 编译程序并生成 myprocess
./myprocess  # 运行程序
```

### 6. `/proc/PID`：查看进程的内核信息

Linux 把许多内核信息以文件形式放在 `/proc` 目录中。`/proc/PID/` 中的 `PID` 替换成具体数字后，就可以查看某个进程的信息。

```bash
ls /proc/PID -l  # 查看指定 PID 对应的进程目录
```

其中两个特别重要的链接：

| 项目 | 含义 |
|---|---|
| `exe` | 该进程对应的可执行文件 |
| `cwd` | 该进程记录的当前工作目录 |

例如程序中打开：

```cpp
fopen("./b/c/d.txt", "w");
```

`./b/c/d.txt` 是相对路径。它不是相对于可执行文件所在目录，而是相对于该进程的当前工作目录，也就是 `/proc/PID/cwd` 指向的目录。

### 7. PPID 实验：`bash` 也是进程

多次运行同一个程序：

```bash
./myprocess  # 第一次运行程序
./myprocess  # 第二次运行程序
./myprocess  # 第三次运行程序
```

通常可以观察到：

- 每次运行得到的 `PID` 都不同，因为每次都创建了新的进程；
- `PPID` 可能保持不变，因为它们都是同一个命令行解释器启动的；
- 查看这个父进程，会发现它通常是 `-bash`。

假设父进程 ID 是 `19811`：

```bash
ps ajx | grep 19811  # 查找 PID 或 PPID 中包含 19811 的进程
```

`bash` 是命令行解释器：它读取用户输入的命令，再创建进程执行命令。它本身也是一个进程。通常每个登录用户都会获得一个自己的 `bash`，用户输入的命令可以看成由这个“负责人”安排执行的任务。

## 8. 创建进程：`fork`

### `fork` 的语法和返回值

语法：

```cpp
#include <unistd.h>  // 提供 fork

pid_t fork(void);  // 创建一个子进程
```

`fork`：复制当前进程，创建一个新的子进程。

调用成功后，原来的进程称为父进程，新创建的称为子进程：

| 执行者 | `fork()` 返回值 |
|---|---:|
| 父进程 | 子进程的 PID，大于 0 |
| 子进程 | `0` |
| 创建失败 | 父进程返回 `-1` |

错误可以用 `perror` 打印：

```cpp
perror("fork");  // 根据 errno 打印 fork 失败原因
```

典型写法：

```cpp
#include <iostream>  // 提供 cout
#include <unistd.h>  // 提供 fork
#include <cstdio>  // 提供 perror

int main() {  // 程序入口
    pid_t id = fork();  // 创建子进程并保存返回值

    if (id < 0) {  // 返回负数表示创建失败
        perror("fork");  // 打印失败原因
        return 1;  // 用非零值表示异常退出
    } else if (id == 0) {  // 子进程执行这里
        std::cout << "child: pid=" << getpid() << '\n';  // 打印子进程 PID
    } else {  // 父进程执行这里
        std::cout << "parent: child pid=" << id << '\n';  // 打印子进程 PID
    }

    return 0;  // 父子进程分别结束
}
```

### `fork` 后代码和数据是什么关系

子进程并没有重新加载一个新的程序，因此它没有一份“全新的代码和数据”。它以父进程为模板：

- 父子进程的代码通常共享；
- 父子进程的数据逻辑上各自私有；
- 一方修改数据，不应影响另一方。

这里的“共享代码”通常是只读共享；数据在真正修改时，操作系统才进行复制，这就是写时拷贝。

### 为什么父子进程返回不同的值

父进程可能有多个子进程：

```text
一个父进程
  ├── 子进程 1
  ├── 子进程 2
  └── 子进程 3
```

父进程必须知道每个子进程的 PID，才能区分和管理它们；而子进程只需要知道自己是子进程，所以返回 `0` 即可。

> **父进程返回子进程 PID，子进程返回 0，是为了让父子进程进入不同的执行逻辑。**

### 为什么一个函数会“返回两次”

`fork` 并不是先返回，再创建子进程。它大致会先完成：

```text
申请子进程的 task_struct
        ↓
复制父进程的 task_struct
        ↓
把子进程加入进程链表和调度队列
        ↓
父子进程各自从 fork 返回
```

当执行到 `return` 之前，子进程已经创建，甚至可能已经被调度运行。因此，父进程和子进程会分别执行一次返回动作。

这里的“返回两次”不是同一个函数在同一条执行流中返回两次，而是父子两个进程各自从自己的 `fork` 调用点继续执行。

### 为什么一个变量既等于 `0` 又大于 `0`

例如：

```cpp
pid_t id = fork();  // 父子进程各自拥有一份 id
```

父进程中的 `id` 是子进程 PID，大于 `0`；子进程中的 `id` 是 `0`。虽然变量名相同，但父子进程已经拥有各自独立的地址空间，因此是两个不同进程中的两个变量。地址空间的具体原理将在后续内容中解释。

### 用返回值分流

```text
fork()
  ├── id < 0   → 创建失败
  ├── id == 0  → 子进程逻辑
  └── id > 0   → 父进程逻辑
```

### 写时拷贝实验

```cpp
#include <iostream>  // 提供 cout
#include <unistd.h>  // 提供 fork 和 sleep
#include <cstdio>  // 提供 perror

int g_val = 100;  // 定义全局变量

int main() {  // 程序入口
    pid_t id = fork();  // 创建子进程

    if (id < 0) {  // 判断创建是否失败
        perror("fork");  // 打印错误信息
        return 1;  // 异常退出
    } else if (id == 0) {  // 子进程执行这里
        g_val += 5;  // 子进程修改自己的数据副本
        std::cout << "child g_val = " << g_val << '\n';  // 输出 105
    } else {  // 父进程执行这里
        sleep(1);  // 等待子进程先输出
        std::cout << "parent g_val = " << g_val << '\n';  // 仍然输出 100
    }

    return 0;  // 进程结束
}
```

父进程和子进程最初看到相同的 `g_val`。当子进程修改它时，操作系统才把对应的数据复制一份，让子进程修改自己的副本。

> **写时拷贝：父子进程一开始尽量共享数据；某一方真正修改时，操作系统才复制被修改的数据。**

> **进程具有独立性：一个进程修改自己的数据，通常不会影响另一个进程。**

## 3-2 进程状态

### 1. 状态是什么

进程并不总是在 CPU 上运行。它可能刚被创建、正在等待 CPU、等待磁盘或键盘，也可能已经退出。

进程状态就是 `task_struct` 中的一个整数。这个整数告诉操作系统：当前进程应该被放在哪个队列，以及接下来能否继续运行。

> **进程状态本质上是 `task_struct` 内的一个整数。**

### 2. 课本中的状态转换

```text
创建
  ↓
就绪
  ↓ 被调度
运行
  ├── 时间片用完 → 就绪
  ├── 等待事件   → 阻塞
  └── 执行结束   → 结束

阻塞
  └── 等待事件完成 → 就绪
```

挂起表示暂时不让进程继续占用内存：

```text
就绪 ──换出──> 就绪挂起 ──激活──> 就绪
阻塞 ──换出──> 阻塞挂起 ──激活──> 阻塞
```

### 3. 运行、阻塞和挂起的队列模型

#### 运行：`runqueue`

一个 CPU 对应一个运行队列 `runqueue`。在这个队列中的进程状态都属于 `running`，但这不表示它们同时都在 CPU 上执行；单核 CPU 同一时刻只能真正执行一个进程。

调度器可以按 FIFO（先进先出）等算法，从运行队列中挑选进程。

#### 阻塞：设备等待队列

如果进程需要等待键盘、磁盘、网卡、摄像头等设备，就不能继续占用 CPU。操作系统会把它放到对应设备的 `wait_queue` 中。

```cpp
struct device {  // 描述一个硬件设备
    int id;  // 设备编号
    int vender;  // 设备厂商信息
    int status;  // 设备状态
    void *data;  // 指向设备相关数据
    struct device *next;  // 指向下一个设备
    struct task_struct *wait_queue;  // 等待该设备的进程
};
```

操作系统管理设备时，也使用“先描述，再组织”的方法。设备有自己的结构体，设备结构体中又保存等待该设备的进程队列。

#### 挂起：换出到磁盘

当内存不足时，操作系统可以把某些进程的代码和数据暂时写到磁盘的交换分区，这个过程叫换出；需要时再从磁盘读回内存，叫换入。

进程的 PCB 仍然要保留在内存中，因为操作系统还要知道这个进程的状态和其他属性。

```text
进程代码和数据 → 磁盘 swap 交换分区
进程 PCB       → 仍然留在内存
```

阻塞状态再加上换出，就是阻塞挂起。

> **进程状态变化的一个表现，就是进程在不同队列之间流动；本质仍是数据结构的增删查改。**

### 4. Linux 内核链表

Linux 内核通常不是把完整的 `task_struct` 复制到每个队列中，而是把链表节点作为成员嵌入结构体：

```cpp
struct list_head {  // 内核通用双向链表节点
    struct list_head *next;  // 指向下一个节点
    struct list_head *prev;  // 指向上一个节点
};
```

`task_struct` 中可以有一个或多个这样的成员：

```cpp
struct task_struct {  // 进程控制块
    int pid;  // 保存进程 ID
    struct list_head tasks;  // 接入全局进程链表
    struct list_head run_links;  // 接入运行队列
    struct list_head wait_links;  // 接入等待队列
};
```

链表节点只知道自己的 `next` 和 `prev`，但内核需要根据节点地址反推出外层的 `task_struct` 地址。这依靠成员偏移量，也就是 `offsetof` 思想：

```cpp
(struct task_struct*)((char*)links - &((struct task_struct*)0)->links)  // 根据 links 地址反推出 task_struct 地址
```

一个 `task_struct` 可以有多个 `next/prev` 对，因此同一个进程可以同时挂到不同类型的队列中，例如一个链表成员用于全局进程链表，另一个用于运行队列。

全局进程链表通常可以表示为：

```cpp
struct list_head tasks;  // 保存所有进程的全局链表入口
```

## Linux 内核状态

Linux 常见状态如下：

| 状态 | 含义 |
|---|---|
| `R` | `running`，运行或在运行队列中 |
| `S` | 可中断休眠 |
| `D` | 不可中断的磁盘休眠 |
| `T` | 停止 |
| `t` | 正在被调试器追踪而停止 |
| `X` | 死亡，瞬时状态 |
| `Z` | 僵尸 |

### `R`：运行

`R` 的准确含义是进程处于运行状态或运行队列中，不一定代表此刻正在 CPU 上执行。

### `S`：可中断休眠

`S` 是浅睡眠。进程正在等待某个事件，例如等待键盘输入；收到合适的信号后，可以被唤醒或中断。

### `D`：不可中断磁盘休眠

`D` 是深度睡眠，通常表示正在等待磁盘 I/O 完成。此时进程不能被普通信号打断，甚至不能用 `kill -9` 立即杀掉，因为内核必须先保证底层 I/O 状态安全。

可以用大量磁盘写入制造观察机会：

```bash
dd if=/dev/zero of=~/test.txt bs=4096 count=100000  # 向文件写入约 400 MB 的零数据
```

`bs=4096` 表示每次写入 4096 字节，`count=100000` 表示写入 100000 次。实际观察到 `D` 状态的时间可能很短。

### `T` 和 `t`：停止

`T` 表示进程被暂停。信号 19（`SIGSTOP`）可以暂停进程，信号 18（`SIGCONT`）可以恢复进程：

```bash
kill -19 PID  # 向指定进程发送 SIGSTOP，暂停进程
kill -18 PID  # 向指定进程发送 SIGCONT，恢复进程
ps axj  # 查看进程状态
```

进程被调试器暂停、断点命中时，通常显示为 `T` 或 `t`；其中 `t` 表示 tracing stop，也就是被调试器追踪而停止。

### `X`：死亡

`X` 表示进程已经死亡。它一般只是内核内部的瞬时状态，因此用 `ps` 通常看不到。

### `Z`：僵尸进程

子进程退出后，父进程还在运行，但没有读取子进程的退出信息，此时子进程会暂时保留为 `Z` 状态。

模拟僵尸进程：

```cpp
#include <iostream>  // 提供 cout
#include <unistd.h>  // 提供 fork 和 sleep
#include <cstdlib>  // 提供 exit
#include <cstdio>  // 提供 perror

int main() {  // 程序入口
    pid_t id = fork();  // 创建子进程

    if (id < 0) {  // 判断 fork 是否失败
        perror("fork");  // 打印失败原因
        return 1;  // 异常退出
    }

    if (id == 0) {  // 子进程执行这里
        std::cout << "child exit" << '\n';  // 输出子进程即将退出
        exit(0);  // 子进程退出
    }

    sleep(30);  // 父进程暂时不读取子进程退出信息
    return 0;  // 父进程结束
}
```

另开一个终端查看：

```bash
ps axj | grep myprocess  # 查找程序对应的进程
```

僵尸进程常见显示形式：

```text
STAT=Z+
[myprocess] <defunct>
```

为什么需要僵尸？父进程创建子进程，通常是为了让子进程完成任务。子进程退出后，退出码等结果仍然需要交给父进程。退出信息会暂时保存在子进程的 `task_struct` 中，父进程读取后，内核才能彻底清理它。

> **僵尸进程就是已经退出、但父进程尚未读取退出信息的子进程。**

僵尸的危害可以按以下链条理解：

```text
退出信息必须保留
  ↓
task_struct 必须保留
  ↓
父进程不回收
  ↓
task_struct 一直占用内存
  ↓
形成内存泄漏
```

这里更准确地说，是内核对象的资源泄漏。`task_struct` 这类内核结构对象通常由 `slab` 分配器管理；`slab` 是专门缓存和分配内核数据结构对象的内存分配器。

如果进程本身已经退出，它占用的普通代码和数据通常会被释放；但只要退出信息没有被回收，常驻内存中的 `task_struct` 仍可能持续占用资源。因此，常驻运行且不断产生未回收子进程的父进程尤其危险。

## 孤儿进程

如果父进程先退出，而子进程仍然运行，子进程就失去了原来的父进程。此时，1 号进程会接管它。

1 号进程通常是 `init` 或 `systemd`，可以把它看成操作系统负责管理系统进程的进程。被 1 号进程领养的子进程叫孤儿进程。

> **父进程先退出后，子进程会被 1 号进程领养，成为孤儿进程。**

之所以要领养，是因为子进程将来仍然可能退出；如果没有父进程负责读取退出信息，它就可能变成无人回收的僵尸进程。

模拟孤儿进程：

```cpp
#include <iostream>  // 提供 cout
#include <unistd.h>  // 提供 fork、getpid、getppid 和 sleep
#include <cstdio>  // 提供 perror

int main() {  // 程序入口
    pid_t id = fork();  // 创建子进程

    if (id < 0) {  // 判断 fork 是否失败
        perror("fork");  // 打印失败原因
        return 1;  // 异常退出
    }

    if (id == 0) {  // 子进程执行这里
        sleep(3);  // 等待父进程先退出
        std::cout << "child pid=" << getpid() << '\n';  // 打印自己的 PID
        std::cout << "new ppid=" << getppid() << '\n';  // 打印被领养后的 PPID
    } else {  // 父进程执行这里
        std::cout << "parent exit" << '\n';  // 父进程打印提示
    }

    return 0;  // 父子进程分别结束
}
```

父进程退出后，子进程的 `PPID` 通常会变成 `1`。如果程序以后台方式运行：

```bash
./myprocess &  # 让程序在后台运行
```

终端不再直接等待它。需要强制结束时，可以使用：

```bash
kill -9 PID  # 强制结束指定 PID 的后台进程
```

# 3-3 进程优先级

## 1. 优先级是什么

CPU 资源有限，但系统中的进程可能很多。多个进程都想运行时，操作系统必须决定谁先得到 CPU。

因此可以从三个问题理解优先级：

| 问题 | 答案 |
|---|---|
| 是什么 | 进程得到 CPU 资源的先后顺序 |
| 为什么需要 | CPU 等资源稀缺，必须决定谁先运行 |
| 怎么实现 | 在 `task_struct` 中保存一个整数 |

> **优先级解决的是“谁先得到资源”的问题。**

### 优先级和权限的区别

| 概念 | 解决的问题 |
|---|---|
| 优先级 | 谁先得到资源、谁后得到资源 |
| 权限 | 是否有资格得到某种资源 |

例如，一个进程权限足够，表示它“可以”访问文件；但它的优先级较低，表示它可能要“晚一些”获得 CPU。

### 数值和优先级的关系

Linux 中通常是数值越小，优先级越高。分时操作系统还要考虑公平性，不能让高优先级进程永远霸占 CPU，因此优先级可能动态调整，但调整幅度不能过大。

## 2. 查看进程优先级

```bash
ps -al  # 查看进程的详细优先级信息
```

常见列：

| 列 | 含义 |
|---|---|
| `UID` | 用户 ID |
| `PID` | 进程 ID |
| `PPID` | 父进程 ID |
| `PRI` | 进程优先级 |
| `NI` | nice 值，优先级修正数据 |
| `SZ` | 进程占用的内存规模 |
| `WCHAN` | 进程正在等待的内核位置 |
| `TTY` | 关联的终端 |
| `TIME` | 使用的 CPU 时间 |
| `CMD` | 命令名 |

`PRI` 和 `NI` 不要混淆：

- `PRI` 是进程优先级；
- `NI` 是优先级的修正值，不是优先级本身；
- 默认情况下，`PRI` 常显示为 `80`；
- 真实优先级可以表示为：

```text
真实优先级 = PRI + NI
```

`nice` 值范围是 `[-20, 19]`，共 40 个等级。数值越小，优先级越高。Linux 普通进程优先级范围通常是 `[60, 99]`。

## 3. 修改优先级

### `renice`

语法：

```bash
renice -n 数值 -p PID  # 修改指定 PID 进程的 nice 值
```

例如：

```bash
renice -n 5 -p 1234  # 把 PID 为 1234 的进程 nice 值设置为 5
```

超出范围的值会被截断：

```bash
renice -n -100 -p 1234  # 过小的值会被截断为 -20
renice -n 100 -p 1234  # 过大的值会被截断为 19
```

普通用户通常不能随意提高自己进程的优先级，因为这可能影响其他用户和系统进程。

### 其他修改方式

在 `top` 中可以按 `r` 修改进程的 nice 值：

```text
top → 按 r → 输入 PID → 输入新的 nice 值
```

也可以在启动程序时使用 `nice`：

```bash
nice -n 5 ./myprocess  # 以 nice 值 5 启动程序
```

程序接口：

```cpp
#include <sys/time.h>  // 提供时间相关类型
#include <sys/resource.h>  // 提供进程资源和优先级接口

int getpriority(int which, int who);  // 获取指定对象的优先级
int setpriority(int which, int who, int prio);  // 设置指定对象的优先级
```

如果低优先级进程长时间得不到 CPU，就会产生进程饥饿。

> **优先级设置不合理，可能导致低优先级进程长期得不到 CPU，形成进程饥饿。**

## 4. 进程为什么能代表用户访问资源

Linux 判断文件访问者时，需要知道“是谁”在访问文件。实际上，访问文件、设备等资源的直接执行者都是进程；进程中保存了启动它的用户身份，因此进程可以代表用户。

查看文件的数字 UID：

```bash
ls -ln  # 用数字形式显示文件拥有者和所属组的 UID、GID
```

操作系统根据进程携带的 UID，判断它是文件拥有者、所属组成员，还是 other。

## 5. 竞争性、独立性、并行、并发

| 概念 | 解释 |
|---|---|
| 竞争性 | 进程很多而 CPU 资源有限，进程之间竞争 CPU |
| 独立性 | 一个进程使用自己的资源，运行时尽量不干扰其他进程 |
| 并行 | 多个 CPU 同时分别执行多个进程 |
| 并发 | 一个 CPU 通过快速切换，让多个进程在一段时间内都向前推进 |

```text
多个 CPU：进程 A、B 可以真正同时运行 → 并行
一个 CPU：A、B 交替运行 → 并发
```

# 3-4 进程切换

## 1. 为什么死循环不会占死 CPU

假设一个进程执行死循环：

```cpp
while (true) {  // 不断重复执行
}  // 永远不会自然结束
```

如果操作系统让它一直占有 CPU，其他程序就无法运行。但实际中，死循环进程不会打死系统，因为操作系统会给进程分配时间片。

时间片：进程一次连续占用 CPU 的最长时间。时间片用完后，操作系统可以把当前进程切下来，让其他进程运行。

```text
进程 A 运行一段时间
        ↓ 时间片用完
保存 A 的现场
        ↓
恢复进程 B 的现场
        ↓
进程 B 继续运行
```

## 2. CPU 寄存器和上下文

寄存器：CPU 内部速度很快、容量很小的临时存储空间。

常见寄存器包括：

| 寄存器 | 作用概念 |
|---|---|
| `pc` / `EIP` | 下一条指令的位置 |
| `ebp` / `esp` | 栈帧和栈顶位置 |
| `eax`、`ebx`、`ecx`、`edx` | 保存运算数据和中间结果 |
| `cs`、`ds`、`es`、`fs`、`gs` | 保存代码段、数据段等信息 |
| `eflags` | 保存 CPU 标志位 |
| `cr0`～`cr4` | 保存 CPU 控制信息 |

必须区分：

- 寄存器：CPU 中保存数据的硬件位置；
- 寄存器里的数据：会随着程序执行不断变化的内容。

例如：

```cpp
int a = 10;  // 某个寄存器或内存位置中保存 10
a = 20;  // 保存的值变成 20
int b = a;  // 另一个位置得到 20
```

寄存器只有一组，但程序运行过程中会出现很多不同的数据状态。

## 3. 如何切回进程：保存和恢复上下文

可以把进程切换类比为学生暂时去当兵：

| 类比对象 | 操作系统对象 |
|---|---|
| 学校 | CPU |
| 导员 | 调度器 |
| 学生 | 进程 |
| 学籍 | 进程的上下文数据 |
| 保留学籍 | 保存上下文 |
| 恢复学籍 | 恢复上下文 |
| 去当兵 | 进程被从 CPU 切下 |

CPU 内部的寄存器只有一份，但不同进程各自拥有自己的上下文：

```text
进程 A 上下文：EIP=100，EAX=10
进程 B 上下文：EIP=1000，EAX=100
```

当进程 A 被切下时，必须把当前寄存器内容保存起来；下次 A 再被调度时，操作系统把 A 的上下文恢复到 CPU 寄存器中，A 才能从原来的位置继续执行。

> **进程切换最核心的工作，就是保存和恢复当前进程的硬件上下文，也就是 CPU 寄存器的内容。**

## 4. 上下文保存在哪里

上下文会保存到进程的 `task_struct` 中，相关结构称为 `TSS`，即任务状态段：

```cpp
struct tss_struct {  // 保存任务切换相关硬件上下文
    unsigned long eip;  // 保存下一条指令地址
    unsigned long eflags;  // 保存 CPU 标志位
    unsigned long eax;  // 保存 eax 寄存器内容
    unsigned long ebx;  // 保存 ebx 寄存器内容
    unsigned long esp;  // 保存栈顶位置
    unsigned long ebp;  // 保存栈帧位置
    unsigned long cr3;  // 保存地址空间相关信息
};
```

实际内核结构还包含 `back_link`、`esp0`、`ss0`、`esi`、`edi`、`es`～`gs`、`ldt` 等字段。`task_struct` 的末尾会内嵌一个 `struct tss_struct tss`。

内核中常见：

```cpp
struct task_struct *current;  // 指向当前正在运行的进程
```

补充：

- 内核优先级抢占：高优先级任务到来时，内核可以抢占当前任务；
- 分时操作系统：通过时间片让多个进程轮流推进；
- 实时操作系统：重点是保证任务在规定时间内响应，应用场景不同。

# 3-5 Linux 2.6 内核 O(1) 调度队列

## 1. 一个 CPU 对应一个运行队列

Linux 2.6 调度器中，一个 CPU 对应一个 `runqueue`。运行队列中保存等待该 CPU 调度的进程。

`runqueue` 中常见字段：

| 字段 | 含义 |
|---|---|
| `lock` | 保护运行队列并发访问 |
| `nr_running` | 队列中可运行进程数量 |
| `cpu_load` | 根据队列中进程数量计算的负载因子 |
| `active` | 当前活动优先级队列 |
| `expired` | 时间片已经耗尽的队列 |
| `arrays[2]` | 活动队列和过期队列的数组 |

多 CPU 系统还可以依据 `cpu_load` 做负载均衡，把部分进程从繁忙 CPU 转移到较空闲的 CPU。

## 2. 调度器如何快速挑选进程

调度器分两步：

```text
第一步：挑选优先级队列
        ↓
第二步：从该队列中挑选具体进程
```

### 优先级分区

Linux 调度器把优先级分为：

| 范围 | 类型 |
|---|---|
| `[0, 99]` | 实时优先级，本节暂不考虑 |
| `[100, 139]` | 普通进程优先级 |

普通进程对应 `nice` 值 `[-20, 19]`。常见换算可以写成：

```text
PRI = 60 + 40 + nice
```

因此：

```text
nice = -20 → PRI = 80
nice = 19  → PRI = 119
```

这里的 `PRI` 展示方式可能因工具和内核版本存在差异，核心规律仍是：数值越小，优先级越高。

## 3. `queue[140]`：按优先级分组

调度器可以为每个优先级准备一个队列：

```cpp
struct task_struct *queue[140];  // 每个下标对应一个优先级队列
```

含义是：

- 数组下标就是优先级；
- `queue[100]` 保存优先级为 100 的进程；
- `queue[101]` 保存优先级为 101 的进程；
- 相同优先级的进程在同一个队列中按 FIFO 排队。

问题是：如果有 140 个优先级，调度器逐个检查 140 个队列，仍然不够高效。

## 4. `bitmap[5]`：快速找到非空队列

调度器使用位图 `bitmap` 标记哪些优先级队列非空：

```cpp
unsigned int bitmap[5];  // 5 个 unsigned int 共提供 160 个比特位
```

因为：

```text
5 × 32 = 160 ≥ 140
```

每一个比特位对应 `queue[140]` 中的一个优先级位置：

- 比特位为 `1`：对应队列非空；
- 比特位为 `0`：对应队列为空。

例如：

```text
bitmap 对应位置： 0 0 1 0 0 1 0 ...
queue 对应位置：  空 空 非空 空 空 非空 空 ...
```

调度器可以直接定位最高优先级的非空队列，而不需要从头检查所有队列，因此查找时间是常数级 `O(1)`。

> **位图让调度器能够在常数时间内定位最高优先级的非空队列。**

## 5. 活动队列和过期队列

调度器使用两个优先级数组：

```cpp
struct prio_array {  // 一组按优先级组织的运行队列
    int nr_active;  // 当前数组中的进程数量
    unsigned int bitmap[5];  // 标记哪些优先级队列非空
    struct task_struct *queue[140];  // 保存各优先级进程
};

struct prio_array arrays[2];  // 保存活动数组和过期数组
```

两个数组分别表示：

- `active`：时间片还没有耗尽的进程；
- `expired`：时间片已经耗尽的进程。

可以表示为：

```text
active  → 时间片未耗尽的进程
expired → 时间片已耗尽的进程
```

调度过程开始时，调度器从 `active` 中选择进程。随着运行，进程的时间片逐渐耗尽：

```text
active 中的进程越来越少
expired 中的进程越来越多
```

当 `active` 为空时，直接交换两个指针：

```cpp
swap(&active, &expired);  // 交换活动队列和过期队列
```

交换后，原来的 `expired` 变成新的 `active`，调度器立即获得一批新的可运行进程，不需要重新创建和搬运所有队列。

> **活动队列耗尽后，通过交换 `active` 和 `expired` 指针，可以直接获得下一批活动进程。**

## 6. O(1) 的含义

Linux 2.6 调度器通过：

1. `queue[140]` 按优先级组织进程；
2. `bitmap[5]` 快速定位非空优先级队列；
3. `active` 和 `expired` 管理时间片；

使得选择最合适进程的时间复杂度为 `O(1)`。

> **O(1) 调度的核心是：挑选下一个进程所需的时间，不随系统进程数量增长。**

# 4. 命令行参数和环境变量

程序运行时，除了程序本身，还可能需要两类外部信息：

- 用户在命令后面临时输入的信息，例如 `./code a b c`
- 操作系统提前准备好的运行环境信息，例如当前用户是谁、程序应该去哪些目录寻找命令

前者通过**命令行参数**传给程序，后者通过**环境变量**传给程序。

---

## 4-1 概念介绍

### 环境变量是什么

假设程序运行时需要知道“当前用户是谁”“家目录在哪里”“某个命令应该去哪儿找”。如果每个程序都自己询问、自己保存这些信息，就会非常麻烦。

因此，操作系统和命令解释器会提前准备一些“名字—值”形式的信息，程序直接读取即可。这些信息叫**环境变量**：用来指定操作系统运行环境参数的变量。

例如：

```text
USER=whb
HOME=/home/whb
SHELL=/bin/bash
```

环境变量通常具有特殊用途，并且会影响当前进程以及它启动的子进程，因此具有一定的**全局特性**。这里的“全局”不是指所有用户共享，而是指它可以在一个进程及其子进程组成的范围内传递。

> **环境变量就是操作系统和程序之间共享的运行环境信息，常用形式是 `变量名=变量值`。**

### 引入例：编译器为什么能找到库

编译、链接时，程序需要找到动态库或静态库。但我们通常没有告诉编译器每个库文件的完整路径，链接却仍然可能成功。

原因是：编译工具会按照默认规则和相关环境信息搜索库。例如某些环境变量可以告诉工具去哪些目录查找库文件。于是，用户不需要每次都手动写完整路径。

这和命令行中的 `PATH` 思路类似：**工具需要寻找文件时，可以使用环境中提前准备好的搜索路径。**

### `bash` 如何使用环境变量

`bash` 是用户输入命令时使用的命令解释器。它会读取环境变量，并据此完成很多工作，例如：

- 根据 `PATH` 搜索命令
- 根据 `HOME` 确定用户家目录
- 根据 `SHELL` 知道当前使用的命令解释器
- 启动新程序时，把环境变量传给新程序

所以，用户虽然没有直接调用操作系统内部的环境变量机制，但每天使用 `bash` 时已经间接使用了环境变量。

---

## 4-2 命令行参数

### 为什么需要命令行参数

同一个程序可能需要根据用户输入执行不同任务。例如：

```bash
./code a b c d
```

这里的 `a`、`b`、`c`、`d` 是运行程序时临时交给程序的信息。

C 语言通过 `main` 函数的参数接收这些内容：

```cpp
#include <stdio.h>  // 提供 printf

int main(int argc, char *argv[]) {  // argc 是参数个数，argv 是参数表
    for (int i = 0; i < argc; ++i) {  // 遍历所有命令行参数
        printf("argv[%d]: %s\n", i, argv[i]);  // 打印下标和参数内容
    }

    return 0;  // 程序正常结束
}
```

编译并运行：

```bash
g++ code.cpp -o code  # 编译代码并生成名为 code 的可执行程序
./code a b c d        # 启动程序，并传入 a、b、c、d
```

输出类似：

```text
argv[0]: ./code
argv[1]: a
argv[2]: b
argv[3]: c
argv[4]: d
```

### `argv` 表的结构

`argv` 的类型是 `char *argv[]`，可以理解为“字符指针组成的数组”，每个元素都指向一个字符串：

```text
argv
 ├── argv[0] -> "./code"
 ├── argv[1] -> "a"
 ├── argv[2] -> "b"
 ├── argv[3] -> "c"
 ├── argv[4] -> "d"
 └── argv[5] -> NULL
```

其中：

- `argv[0]` 通常保存程序名或程序路径
- `argv[1]` 开始保存用户传入的参数
- `argv[argc]` 是 `NULL`，表示表尾
- 每个参数都是一个以 `'\0'` 结尾的字符串

用户输入的整行命令并不会原样直接放进 `argv`。命令首先由 `bash` 按空格等规则切分，再把切分后的字符串填入 `argv`。

例如：

```bash
./code a b c  # bash 将这行切分成 5 个字符串：./code、a、b、c
```

因此，参数个数 `argc` 等于 `argv` 中有效字符串的数量，不包括表尾的 `NULL`。

### 命令行参数如何实现选项功能

很多命令都支持选项，例如：

```bash
ls -a -b -c  # 启动 ls，并把 -a、-b、-c 作为命令行参数传入
```

`ls` 程序内部读取 `argv`，发现参数中有 `-a`，就执行“显示隐藏文件”等对应功能。

也就是说：

1. `bash` 把命令切分成字符串
2. 操作系统启动程序
3. 程序通过 `argv` 读取这些字符串
4. 程序根据不同参数选择不同功能

`ls` 本身也是一个可执行程序，可以用 `file` 查看其文件类型：

```bash
file /usr/bin/ls  # 查看 ls 文件的类型
```

如果结果中包含 `ELF`，说明它是 Linux 使用的可执行文件格式。

> **命令行选项的本质，就是程序读取 `argv` 中的不同字符串，选择执行不同的子功能。**

## 4-3 一个例子：`PATH`

### 为什么系统命令不需要写路径

要执行一个程序，系统首先必须找到这个程序。

例如输入：

```bash
ls  # 直接执行 ls
```

系统需要找到 `ls` 文件。如果系统没有搜索规则，就必须每次写完整路径：

```bash
/usr/bin/ls  # 通过完整路径执行 ls
```

但实际使用中，`ls`、`pwd` 等命令都可以直接输入。原因是系统有一个专门帮助搜索命令的环境变量：`PATH`。

### `PATH` 的含义

`PATH` 是系统搜索命令时使用的默认目录列表。

查看它：

```bash
echo $PATH  # 显示 PATH 环境变量的值
```

可能得到：

```text
/usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin:/home/whb/.local/bin:/home/whb/bin
```

这里的多个目录使用冒号 `:` 分隔。系统会按照从左到右的顺序搜索：

```text
/usr/local/bin
    ↓ 找不到再查找
/usr/bin
    ↓ 找不到再查找
/usr/local/sbin
    ↓ 找不到再查找
/usr/sbin
    ↓ ...
```

### 为什么自己编译的程序要加 `./`

假设当前目录中有一个自己编译的程序 `code`：

```bash
code  # bash 通常不会默认搜索当前目录，可能提示找不到命令
```

如果明确告诉系统“执行当前目录下的 `code`”，就要写：

```bash
./code  # ./ 表示当前目录，执行当前目录下的 code
```

系统命令通常安装在 `PATH` 中的目录，例如 `/usr/bin`，所以不用写路径；自己编译的程序通常在当前目录，不在 `PATH` 中，所以需要 `./`。

### 把目录加入 `PATH`

语法：

```bash
export PATH=$PATH:目录路径  # 在原 PATH 后追加一个目录
```

示例：

```bash
export PATH=$PATH:/home/whb/bin  # 将 /home/whb/bin 加入命令搜索路径
```

之后，如果 `/home/whb/bin` 中有可执行程序，就可以直接输入程序名运行。

注意，不能写成下面这样：

```bash
export PATH=/home/whb/bin  # 覆盖原来的 PATH，可能导致很多系统命令找不到
```

因为这会删除原来的搜索目录。通常应使用 `$PATH:新目录` 保留旧内容。

> **`PATH` 决定系统搜索命令的目录；当前目录通常不在其中，所以自己编译的程序常用 `./程序名` 执行。**

## 4-4 环境变量从哪来、`bash` 两张表

### `bash` 内部的两张表

`bash` 启动并运行时，需要维护两类信息：

1. **环境变量表**：会传给它启动的子进程
2. **命令行参数表 `argv`**：描述某一次启动程序时传入的参数

从 C 语言角度看，环境变量表可以表示为：

```cpp
char **environ;  // 指向环境变量字符串表
```

而每次启动一个程序时，操作系统会准备该程序的 `argv` 表。

两者用途不同：

| 内容 | 保存什么 | 是否随子进程传递 |
|---|---|---|
| `argv` | 某次启动程序时的命令行参数 | 只属于这次启动的程序 |
| 环境变量表 | 程序运行所需的环境信息 | 通常会被子进程继承 |

### 环境变量的初始来源

`bash` 启动时，不是凭空得到环境变量的。系统会读取相关配置文件，例如：

- 用户家目录下的 `.bash_profile`
- 用户家目录下的 `.bashrc`
- `.bashrc` 中还可能通过 `source` 读取 `/etc/bashrc`

这些文件中可以设置环境变量、别名和其他 `bash` 配置。

# 5. 程序地址空间

## 5-1 布局与验证

### 1. 为什么需要“地址空间”

程序运行时会使用代码、全局变量、堆、栈等不同区域。如果所有程序都直接使用物理内存，就必须自己寻找空闲内存，还要避免和其他程序冲突，管理非常困难。

操作系统因此为每个进程安排一套“地址编号体系”，让进程先按照统一规则使用地址，操作系统再负责把这些地址对应到真正的物理内存。

**虚拟地址空间：进程看到并使用的一套地址范围，不等于真实的物理内存。**

> **虚拟地址空间一共会讲 4 次，本节先建立整体概念，后续课程再逐步深入。**

---

### 2. 编址计算

**编址：给每个存储单元分配地址。**

通常采用“1 字节编址”，也就是每个地址对应 1 字节空间。

#### 32 位机器

32 位地址可以表示：

```text
00000000 ~ FFFFFFFF
```

一共有：

```text
2^32 个地址 × 1 字节 = 2^32 字节 = 4GB
```

#### 64 位机器

64 位地址理论上可以表示：

```text
2^64 个地址
```

理论地址空间为：

```text
2^64 字节
```

实际操作系统通常不会把全部 64 位地址都拿来使用，但地址范围的计算方式仍然如此。

> **32 位机器的地址空间大小是 `2^32` 字节，也就是 4GB；地址本身通常以字节为单位编址。**

---

### 3. 地址空间从低地址到高地址的布局

以 32 位 Linux 的典型布局为例，用户空间占 `[0, 3G]`，内核空间占 `[3G, 4G]`：

```text
高地址
┌──────────────────────────────┐
│ 内核空间 [3G, 4G]             │
├──────────────────────────────┤
│ 命令行参数、环境变量           │
├──────────────────────────────┤
│ 栈 stack                      │
│ 向低地址增长 ↓                 │
├──────────────────────────────┤
│ 大段镂空空间                   │
├──────────────────────────────┤
│ 共享区                         │
├──────────────────────────────┤
│ 堆 heap                       │
│ 向高地址增长 ↑                 │
├──────────────────────────────┤
│ 未初始化数据 BSS               │
├──────────────────────────────┤
│ 初始化数据                     │
├──────────────────────────────┤
│ 正文代码                       │
└──────────────────────────────┘
低地址
```

这里的“增长”指的是：程序继续申请空间时，通常朝哪个地址方向扩展。

- 堆通常向高地址增长。
- 栈通常向低地址增长。
- 中间保留一大段空间，供共享库、内存映射等内容使用。
- 用户程序不能直接访问内核空间。

> **典型布局从低地址到高地址是：代码 → 初始化数据 → BSS → 堆 → 镂空空间 → 共享区 → 栈 → 参数和环境变量 → 内核空间。**

---

### 4. 程序地址空间是内存吗

“程序地址空间”容易让人误以为是一块真实内存，但它不是。

- **物理内存**：计算机中真实存在的内存条空间。
- **虚拟地址空间**：操作系统为进程规划的一套地址编号。

一个进程看到的地址，例如变量地址、指针保存的地址，都是虚拟地址。操作系统会通过页表把虚拟地址转换成物理地址。

> **程序地址空间不是内存，而是操作系统为进程建立的虚拟地址空间；它属于系统概念，不是 C/C++ 语言层的概念。**

---

### 5. 区域验证实验

下面的程序分别打印代码、全局数据、堆、栈、只读字符串、静态变量、命令行参数和环境变量的地址。

```cpp
#include <stdio.h>      // 提供 printf
#include <stdlib.h>     // 提供 malloc 和 free

int init_global = 100;  // 有初始值的全局变量，位于初始化数据区
int uninit_global;      // 没有初始值的全局变量，位于 BSS 区
static int test_static = 200;  // 静态全局变量，属于静态存储区

void code_function()    // 函数代码位于代码区
{
}

int main(int argc, char *argv[], char *env[])
{
    int stack_a = 1;    // 局部变量，通常位于栈区
    int stack_b = 2;    // 另一个局部变量，用于观察栈的增长方向

    char *read_only_string = "helloworld";  // 字符串常量通常位于只读区域

    void *heap_a = malloc(10);  // 第一次申请堆空间
    void *heap_b = malloc(10);  // 第二次申请堆空间

    printf("code          : %p\n", (void *)code_function);       // 打印代码区地址
    printf("init_global   : %p\n", (void *)&init_global);        // 打印初始化数据地址
    printf("uninit_global : %p\n", (void *)&uninit_global);      // 打印 BSS 地址
    printf("heap_a        : %p\n", heap_a);                      // 打印第一次堆地址
    printf("heap_b        : %p\n", heap_b);                      // 打印第二次堆地址
    printf("stack_a       : %p\n", (void *)&stack_a);            // 打印第一个栈变量地址
    printf("stack_b       : %p\n", (void *)&stack_b);            // 打印第二个栈变量地址
    printf("read_only     : %p\n", (void *)read_only_string);    // 打印只读字符串地址
    printf("test_static   : %p\n", (void *)&test_static);        // 打印静态变量地址

    if (argc > 0) {                                             // 确认命令行参数存在
        printf("argv[0]       : %p\n", (void *)argv[0]);         // 打印程序名地址
    }

    if (env[0] != NULL) {                                       // 确认环境变量存在
        printf("env[0]        : %p\n", (void *)env[0]);          // 打印第一个环境变量地址
    }

    free(heap_a);                                                // 释放第一次堆空间
    free(heap_b);                                                // 释放第二次堆空间
    return 0;                                                    // 程序正常结束
}
```

编译并运行：

```bash
g++ address_space.cpp -o code  # 编译程序并生成 code
./code                        # 运行程序并查看各区域地址
```

通常可以观察到：

- `heap_b` 的地址高于 `heap_a`，说明堆通常向高地址增长。
- `stack_b` 的地址可能低于 `stack_a`，说明栈通常向低地址增长。
- 函数地址位于代码区域。
- 全局变量、静态变量位于静态存储区域。
- 字符串常量位于只读区域。
- `argv` 和 `env` 位于地址空间较高的位置。

注意：由于编译器优化、地址随机化和具体系统实现不同，地址数值不会固定，栈变量的具体排列也不应当当作 C/C++ 语言保证。

## 5-2 虚拟地址实验：`fork` 与 `g_val`

### 1. 实验现象

下面的程序让父进程和子进程分别打印全局变量 `g_val` 的地址和数值。

```cpp
#include <stdio.h>      // 提供 printf
#include <unistd.h>     // 提供 fork
#include <sys/wait.h>   // 提供 waitpid

int g_val = 100;        // 定义一个初始值为 100 的全局变量

int main()
{
    pid_t id = fork();  // 创建子进程

    if (id < 0) {       // 判断创建是否失败
        perror("fork"); // 打印错误信息
        return 1;       // 返回失败状态
    }

    if (id == 0) {      // 子进程执行这里
        printf("child: before, &g_val=%p, g_val=%d\n",
               (void *)&g_val, g_val);  // 打印子进程修改前的地址和值

        g_val += 5;     // 子进程把自己的 g_val 修改为 105

        printf("child: after,  &g_val=%p, g_val=%d\n",
               (void *)&g_val, g_val);  // 打印子进程修改后的地址和值
        return 0;       // 子进程结束
    }

    waitpid(id, NULL, 0);  // 父进程等待子进程结束

    printf("parent: &g_val=%p, g_val=%d\n",
           (void *)&g_val, g_val);  // 打印父进程中的地址和值
    return 0;               // 父进程正常结束
}
```

编译并运行：

```bash
g++ fork_addr.cpp -o fork_addr  # 编译程序
./fork_addr                     # 运行程序
```

典型现象如下：

```text
child: before, &g_val=0x60104c, g_val=100
child: after,  &g_val=0x60104c, g_val=105
parent: &g_val=0x60104c, g_val=100
```

地址数值可能不同，但在同一次运行中，父子进程打印出的 `&g_val` 通常相同，而修改结果不同。

---

### 2. 从现象推出虚拟地址

推理过程如下：

1. 父子进程打印出的 `&g_val` 相同。
2. 如果这个地址是真实物理地址，那么父子进程修改同一个物理位置，父进程也应该看到 `105`。
3. 实际父进程仍看到 `100`，说明父子进程并没有直接共享同一个可写物理位置。
4. 所以 `&g_val` 不是物理地址，而是虚拟地址。
5. C/C++ 指针中保存的地址，也都是虚拟地址。
6. 物理地址由操作系统管理，普通用户不能直接看到。

> **C/C++ 指针使用的地址全部是虚拟地址；物理地址由操作系统统一管理，用户程序不能直接看到。**

---

### 3. 三个预备结论

后续理解页表和写时拷贝，需要先记住三个关系：

1. 一个进程对应一个虚拟地址空间。
2. 一个进程对应一套页表。
3. 页表负责建立虚拟地址和物理地址之间的映射。

**页表：记录“某个虚拟地址实际对应哪个物理地址”，同时记录访问权限的数据结构。**

---

### 4. 写时拷贝

假设父进程中 `g_val` 的虚拟地址是 `0x111111`，物理地址是 `0x112233`：

```text
父进程虚拟地址 0x111111
        │
        │ 页表映射
        ▼
父进程物理地址 0x112233，内容为 100
```

执行 `fork` 后，子进程暂时不立即复制全部代码和数据，而是先建立相同的映射：

```text
父进程虚拟地址 0x111111 ──┐
                           ├──> 物理地址 0x112233，内容为 100
子进程虚拟地址 0x111111 ──┘
```

此时：

- 父进程和子进程的虚拟地址相同。
- 父进程和子进程暂时指向同一个物理页。
- 如果只是读取，直接共享即可。

当子进程执行 `g_val++`，它需要写入数据。操作系统发现这个页面正在被共享，于是执行写时拷贝：

```text
子进程尝试写入
      │
      ▼
操作系统申请新物理页
      │
      ▼
复制原页面内容 100
      │
      ▼
修改子进程页表：
0x111111 ──> 0x223344
      │
      ▼
子进程在新页面中写入 105
```

最终关系变成：

```text
父进程虚拟地址 0x111111 ──> 物理地址 0x112233，内容 100

子进程虚拟地址 0x111111 ──> 物理地址 0x223344，内容 105
```

因此，父子进程看到的虚拟地址仍然相同，但它们实际使用的物理地址已经不同。

**写时拷贝：只有某一方真正要修改共享数据时，操作系统才复制一份新的物理空间。**

> **写时拷贝让父子进程可以先共享数据，真正写入时再分离，从而减少进程创建时间和内存浪费。**

---

### 5. 进程的独立性

进程具有独立性，主要包括：

1. 内核中保存进程信息的数据结构相互独立。
2. 进程加载到内存中的代码和数据相互独立。

因此，子进程修改自己的 `g_val`，不会直接修改父进程的 `g_val`。

这也回答了 `fork` 的第三个问题：

> **父子进程的虚拟地址可以相同，但通过不同的页表和物理映射，最终能够保存不同的数据。**

## 5-3 如何理解虚拟地址空间

### 1. 大富翁类比

假设大富翁是操作系统，他实际只有 10 亿元现金，却给 4 个孩子每人画出一张“自己有 10 亿元”的账本。

- 10 亿元现金：物理内存。
- 每个孩子的账本：一个进程的虚拟地址空间。
- 大富翁：操作系统。
- 4 个孩子：4 个进程。

每个进程都认为自己拥有一套完整的地址空间，甚至认为自己独占物理内存。但进程真正使用某个地址时，操作系统才把它安排到实际物理内存中。

所以，虚拟地址空间不能只画一张图，还必须由操作系统保存“地址范围如何划分、哪些地址能访问”等信息。

> **虚拟地址空间的思路是：先为进程描述一套完整、有序的地址范围，真正使用时再由操作系统把它兑现到物理内存。**

---

### 2. 虚拟地址空间的本质

虚拟地址空间的本质不是一块物理内存，而是内核中的一个数据结构，例如：

```cpp
struct mm_struct
{
    long code_start;       // 代码区起始地址
    long code_end;         // 代码区结束地址
    long init_start;       // 初始化数据区起始地址
    long init_end;         // 初始化数据区结束地址
    long uninit_start;     // 未初始化数据区起始地址
    long uninit_end;       // 未初始化数据区结束地址
    long heap_start;       // 堆区起始地址
    long heap_end;         // 堆区结束地址
    long stack_start;      // 栈区起始地址
    long stack_end;        // 栈区结束地址
};
```

这个结构体用一组数字描述各个区域的位置。

---

### 3. 用桌子理解区域划分

假设一张 100 厘米的桌子用一条线分成两个区域：

```text
0cm                         49cm | 50cm                         99cm
├────────────── 左区域 ───────────┼────────────── 右区域 ──────────┤
```

要描述这两个区域，不需要记录每一个厘米，只需要记录每个区域的开始和结束位置。

```cpp
struct Desktop
{
    int size;       // 桌子总大小
    int left_start; // 左区域起点
    int left_end;   // 左区域终点
    int right_start;// 右区域起点
    int right_end;  // 右区域终点
};

struct Desktop area = {100, 0, 49, 50, 99};  // 描述两个区域
```

如果要让左区域扩大 20 厘米，只需修改边界数字：

```cpp
area.right_start -= 20;  // 右区域起点向左移动 20
area.left_end += 20;     // 左区域终点向右移动 20
```

同理，`2^32` 个地址也不需要为每个地址单独保存信息，只需要记录各个区域的边界。32 位地址可以使用足够大的整数类型保存。

> **区域划分的核心不是逐个记录所有位置，而是记录区域的开始和结束。**

---

### 4. 内核中的 `mm_struct`

Linux 内核中的 `mm_struct` 会保存类似信息：

```cpp
struct mm_struct
{
    unsigned long start_code;  // 代码区起始地址
    unsigned long end_code;    // 代码区结束地址
    unsigned long start_data;  // 数据区起始地址
    unsigned long end_data;    // 数据区结束地址
    unsigned long start_brk;   // 堆区起始位置
    unsigned long brk;         // 当前堆顶位置
    unsigned long start_stack; // 栈区起始位置
    unsigned long arg_start;   // 命令行参数起始地址
    unsigned long arg_end;     // 命令行参数结束地址
    unsigned long env_start;   // 环境变量起始地址
    unsigned long env_end;     // 环境变量结束地址
};
```

这些字段大多成对出现：

```text
start_code / end_code
start_data / end_data
arg_start   / arg_end
env_start   / env_end
```

一对起始值和结束值，就能描述一个区域。

此外还可能记录：

- `total_vm`：进程使用的虚拟内存总量。
- `locked_vm`：被锁定在物理内存中的虚拟内存量。
- `stack_vm`：栈相关的虚拟内存量。

每个进程只有一个 `mm_struct`，而 `task_struct` 中保存指向它的指针：

```cpp
struct task_struct
{
    int pid;                    // 进程编号
    struct mm_struct *mm;       // 指向该进程的地址空间描述结构
};
```

> **每个进程只有一个 `mm_struct`，它是该进程虚拟地址空间的总体描述。**

---

### 5. `mm_struct` 的两个问题

建立 `mm_struct` 时需要解决两个问题：

1. 为它开辟内存空间。
2. 给各个字段填入正确的初始值。

这些初始值不是凭空产生的，而是在加载可执行程序时，根据程序的代码区、数据区、堆、栈、参数和环境变量等内容进行初始化。

---

## 5-4 VMA 与页表

### 1. 页表不仅记录地址映射

页表负责把虚拟地址映射到物理地址，同时还要记录访问权限。

常见权限表示如下：

| 权限 | 含义 |
|---|---|
| `rw-` | 可读、可写、不可执行 |
| `r--` | 可读、不可写、不可执行 |
| `rwx` | 可读、可写、可执行 |

处理器访问虚拟地址时，会由 `MMU` 完成地址转换。

**MMU：处理器中负责把虚拟地址转换为物理地址的硬件单元。**

```text
CPU 产生虚拟地址
        │
        ▼
MMU 查询页表
        │
        ├── 检查虚拟地址是否有效
        ├── 检查当前操作是否有权限
        └── 找到对应的物理地址
        │
        ▼
访问物理内存
```

---

### 2. 为什么还需要 VMA

`mm_struct` 可以记录代码区、数据区、堆区等大范围的起止位置，但一个区域内部还可能继续划分。

例如，堆区并不一定只有一个连续的使用范围；程序可能通过不同方式申请内存，也可能使用文件映射、共享内存等区域。因此，需要对地址空间再细分。

**VMA：虚拟内存区域，描述虚拟地址空间中的一个连续区域。**

一个简化的 `vm_area_struct` 如下：

```cpp
struct vm_area_struct
{
    struct mm_struct *vm_mm;       // 指向所属的地址空间
    unsigned long vm_start;        // 该区域起始虚拟地址
    unsigned long vm_end;          // 该区域结束虚拟地址
    unsigned long vm_prot;         // 该区域的保护属性
    unsigned long vm_flags;        // 该区域的其他标志
    struct vm_area_struct *vm_next;// 指向下一个区域
    struct vm_area_struct *vm_prev;// 指向上一个区域
};
```

`mm_struct` 中的 `mmap` 指针可以指向 VMA 链表：

```text
mm_struct
    │
    ▼
mmap ──> VMA ──> VMA ──> VMA ──> ...
          │        │        │
          ▼        ▼        ▼
       代码区    数据区    堆区
```

每个 VMA 至少需要知道：

- 起始虚拟地址。
- 结束虚拟地址。
- 是否可读。
- 是否可写。
- 是否可执行。
- 属于哪个进程地址空间。
- 前后相邻的 VMA。

---

### 3. 进程、地址空间、页表和 VMA 的完整关系

```text
task_struct
├── pid
├── files_struct *files
└── mm_struct *mm
        │
        ├── pgd：页表入口
        │       │
        │       └── 虚拟地址 ↔ 物理地址 + 访问权限
        │
        └── VMA 链表
                ├── 内核空间
                ├── 栈
                ├── 文件映射区
                ├── 匿名映射区
                ├── 堆
                ├── BSS 段
                ├── 数据段
                └── 代码段
```

其中：

- `task_struct`：内核保存进程信息的数据结构。
- `mm_struct`：描述进程整体虚拟地址空间。
- `VMA`：描述地址空间中的一个具体区域。
- `pgd`：页表的入口位置。
- 页表：完成虚拟地址到物理地址的映射，并检查访问权限。

---

### 4. VMA 的两种组织方式

VMA 通常同时使用两种组织方式：

| 组织方式 | 适合场景 | 特点 |
|---|---|---|
| 链表 | 地址区域较少 | 结构简单，但查找可能较慢 |
| 红黑树 | 地址区域较多 | 查找更快，同时减少不必要的空间浪费 |

红黑树是一种保持平衡的搜索树。它的作用不是改变区域内容，而是让操作系统能够更快地找到“某个虚拟地址属于哪个 VMA”。

---

### 5. 加载与换页

程序加载到内存时，大致经历以下过程：

```text
在虚拟地址空间中申请指定大小的区域
        │
        ▼
为程序申请或准备物理内存
        │
        ▼
建立虚拟地址到物理地址的页表映射
        │
        ▼
程序通过虚拟地址访问数据
```

这里要注意：程序使用的是虚拟地址，物理地址由页表和 MMU 完成转换。

**换页：当程序访问的虚拟页面暂时不在物理内存中时，操作系统把它从磁盘等存储设备加载到物理内存，并建立映射。**

如果访问的页面没有当前映射，就会触发缺页中断：

```text
访问虚拟地址
      │
      ▼
页表发现页面不在内存
      │
      ▼
触发缺页中断
      │
      ▼
操作系统加载页面
      │
      ▼
更新页表
      │
      ▼
重新执行访问
```

## 5-5 为什么要有虚拟地址空间

### 1. 将地址从无序变有序

如果进程直接使用物理地址，那么不同进程可能申请到完全不同、甚至互相冲突的物理位置，程序还必须处理内存碎片和冲突问题。

使用虚拟地址空间后，每个进程看到的都是类似的布局：

```text
0 ──> 代码 ──> 数据 ──> 堆 ──> ... ──> 栈 ──> 4GB
```

实际物理内存可以位于任意位置，但进程不需要关心。

> **虚拟地址空间把杂乱的物理内存，组织成每个进程都能理解的统一地址布局。**

---

### 2. 对地址和操作进行合法性判定

虚拟地址转换时，操作系统和硬件不仅查找“对应哪个物理地址”，还会检查访问是否合法。

**野指针：指向无效地址、已释放空间或无权限区域的指针。**

例如：

```cpp
char *str = "helloworld";  // str 指向字符串常量区域
*str = 'H';                // 尝试修改只读区域
```

字符串常量通常位于只读区域，页表中对应权限类似：

```text
虚拟地址 ──> 物理地址，权限为 r--
```

执行 `*str = 'H'` 时，程序发起的是写操作，但页表权限不允许写入：

```text
写入请求
   │
   ▼
查询页表
   │
   ▼
发现该页面只有 r-- 权限
   │
   ▼
权限检查失败
   │
   ▼
操作系统终止程序
```

所以程序会崩溃，不是因为字符内容特殊，而是因为页表在地址转换过程中拦截了非法写操作。

> **虚拟地址转换同时完成权限检查，因此能够阻止野指针和越权访问，保护物理内存。**

---

### 3. 解耦合进程管理和内存管理

**解耦合：让两个系统部分可以相对独立地工作。**

有了虚拟地址空间后：

- 进程只需要使用自己的虚拟地址。
- 物理内存可以把页面放在任意空闲位置。
- `malloc` 可以先在虚拟地址空间中划出范围。
- 物理内存可以等到真正访问时再分配。
- 这些物理位置变化通常不会被用户程序感知。

例如，程序申请一大块堆空间时，可以先完成：

```text
虚拟地址空间：划出一块区域
物理内存：暂时不立即全部分配
```

等程序第一次访问某个页面时，操作系统再分配物理页并建立映射。

> **虚拟地址空间让进程只面对连续、有序的虚拟地址，而把物理内存的分配、移动和回收交给操作系统管理。**

---

### 4. 三个澄清问题

#### 问题一：可以不加载代码和数据吗

可以。

一个进程最基本的内核管理对象包括：

```text
task_struct
mm_struct
页表
```

代码和数据可以暂时不全部加载到物理内存中。等进程真正执行或访问某个页面时，再按需加载。

#### 问题二：创建进程时，先建结构还是先加载代码

先建立管理结构：

```text
创建 task_struct
        │
        ▼
创建并初始化 mm_struct
        │
        ▼
建立页表和虚拟地址区域描述
        │
        ▼
加载或按需加载代码、数据
```

因为操作系统必须先知道“这个进程是谁、拥有哪套地址空间、地址区域如何划分”，才能继续管理代码和数据。

#### 问题三：如何理解进程挂起

**进程挂起：进程的管理结构仍然保留，但代码和数据暂时被换出物理内存。**

可以理解为：

```text
task_struct、mm_struct、页表等结构仍在
代码和数据页面暂时不在物理内存
进程恢复运行时，再把需要的页面换入
```

因此，进程并不等于“当前全部装在物理内存中的代码和数据”。进程还包括操作系统为它维护的各种管理结构。

> **进程可以暂时没有全部代码和数据在物理内存中，但它的内核管理结构仍然存在，操作系统仍能继续管理它。**
