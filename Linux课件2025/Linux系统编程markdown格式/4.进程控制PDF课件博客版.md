## 1. 进程创建：fork 到底干了什么

### 1.1 fork 函数初识

在 Linux 中，`fork` 是最重要的函数之一：**它从已存在的进程（父进程）中创建出一个新进程（子进程）**。

```c
#include <unistd.h>
pid_t fork(void);
```

**返回值**（重点，也是最反直觉的地方）：

| 调用者 | 返回值 | 含义 |
|--------|--------|------|
| 子进程 | `0` | "我是孩子" |
| 父进程 | 子进程的 PID（> 0） | "我孩子的身份证号" |
| 出错 | `-1` | 创建失败 |

### 1.2 课件三问（补充解答）

课件在这里抛了三个问题但没给答案，这正是理解 fork 的钥匙，逐一补上：

> **Q1：为什么要给子进程返回 0，而给父进程返回子进程的 pid？**

- **子进程视角**：任何一个进程**只有一个父进程**，想知道自己爹是谁，随时调 `getppid()` 就能查到，所以不需要 fork 告诉它；返回 0 只是给它一个"我是孩子"的身份标记。
- **父进程视角**：一个父进程**可能有很多子进程**，它必须拿到每个孩子的 pid，才能对孩子进行管理（比如后面要讲的 `waitpid` 回收指定孩子）。

一句话：**0 是身份标记，pid 是管理凭证。**

> **Q2：为什么一个函数 fork 会有"两个"返回值？**

严格来说不是"一个函数返回两次"，而是 **fork 在内核里把进程一分为二之后，父子两个进程各自从 fork 返回一次**。fork 调用陷入内核后，内核做了这些事：

1. 给子进程分配新的内存块和内核数据结构（task_struct 等）；
2. 把父进程的部分数据结构内容拷贝给子进程；
3. 把子进程挂进系统进程列表；
4. fork 返回，交给调度器调度。

第 4 步发生时，**两个进程都已经存在**，各自带着自己的栈和返回上下文，于是同一条 `return` 语句在两个进程里各执行了一次。

> **Q3：为什么同一个变量（如 `pid`）既等于 0 又大于 0？**

因为 fork 之后父子进程拥有**各自独立的地址空间**。两个 `pid` 变量虽然名字一样、虚拟地址一样，但落在**两块不同的物理内存**上，装的是各自的值（父进程里是 43677，子进程里是 0），互不干扰。这也是"进程独立性"的体现。

### 1.3 fork 之后：两个执行流

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

int main(void)
{
    printf("Before: pid is %d\n", getpid());   // 只有父进程打印

    pid_t pid = fork();
    if (pid == -1) perror("fork"), exit(1);

    // fork 之后，父子都从这里继续往下跑
    printf("After: pid is %d, fork return %d\n", getpid(), pid);
    sleep(1);
    return 0;
}
```

运行结果（三行输出：一行 Before，两行 After）：

```text
[root@localhost linux]# ./a.out
Before: pid is 43676
After: pid is 43676, fork return 43677   ← 父进程
After: pid is 43677, fork return 0       ← 子进程（注意它没有打印 Before）
```

执行流示意：

```text
父进程 43676: ──Before──fork()──┬──After(return=43677)──→ 结束
                                │
子进程 43677:                   └──After(return=0)─────→ 结束
                        （谁先跑、谁后跑，完全由调度器决定）
```

> **记忆要点**：fork 之前父进程独立执行；fork 之后父子两条执行流**并发执行**，谁先运行由调度器说了算，写代码时不能假设顺序。

### 1.4 写时拷贝：进程独立性的技术保证

通常父子进程**代码共享**；数据在不写入时也是共享的。一旦任意一方试图写入，内核就以**写时拷贝（Copy-On-Write, COW）**的方式，为写入方单独复制一份副本。

```text
写入前（共享）：              写入后（各回各家）：

父进程 ──┐                    父进程 ──→ [数据页 A]（新副本，被修改）
         ├──→ [数据页]                     ↓
子进程 ──┘                    子进程 ──→ [数据页 B]（原样保留）
```

- 正因为有写时拷贝，父子进程才能**彻底分离**——这是进程独立性的技术保证。
- 写时拷贝本质上是一种**延时申请技术**：能不复制就不复制，等真要写才复制，从而提高整机内存使用率。

### 1.5 fork 常规用法与失败原因

**常规用法**：

1. 父进程复制自己，父子同时执行**不同的代码段**。例如：父进程等待客户端请求，fork 出子进程去处理请求（并发服务器的经典模型）。
2. 子进程要执行一个**完全不同的程序**。例如：子进程从 fork 返回后调用 exec 函数（第 4 节的主角）。

**fork 失败的原因**（返回 -1）：

- 系统中进程总数太多；
- 实际用户的进程数超过了限制。

## 2. 进程终止：退出也要"死得明白"

**进程终止的本质 = 释放系统资源**：释放进程申请的内核数据结构，以及对应的代码和数据。

### 2.1 进程退出的三种场景

1. 代码运行完毕，结果**正确**；
2. 代码运行完毕，结果**不正确**；
3. 代码**异常终止**（收到了信号，如 `Ctrl+C`）。

对应到两种退出方式：

- **正常终止**：① 从 main 返回；② 调用 `exit`；③ 调用 `_exit`。
- **异常终止**：信号杀死，如 `Ctrl+C`（SIGINT）。

### 2.2 退出码：进程留给世界的遗言

退出码（exit code）告诉我们最后一次执行的命令是成功还是失败，用 `echo $?` 查看：

- **0**：执行成功，这是理想状态；
- **非 0**：失败，不同的值代表不同的失败原因。

**Linux Shell 中常见的退出码**：

| 退出码 | 含义 |
|--------|------|
| **0** | 命令执行无误 |
| **1** | 通用错误码，可理解为"不被允许的操作"。例如没有 sudo 权限使用 yum、除以 0 |
| **130** | 被 `Ctrl+C`（SIGINT，信号 2）终止：128 + 2 |
| **143** | 被 SIGTERM（信号 15）终止：128 + 15 |
| **128+n** | 通用规律：被信号 n 终止 |

> **板书要点**：
> - 退出码写在进程的 **task_struct** 内部（`exit_code` 字段）。
> - 进程异常一般是收到了信号；一旦 status 低 7 个比特位非 0（异常退出），**退出码就没有意义了**——人死不能复生，先看病因而非遗言。
> - 可以用 `strerror()` 把退出码翻译成文字描述。

### 2.3 _exit：直接撒手人寰

```c
#include <unistd.h>
void _exit(int status);
```

- `status` 定义进程的终止状态，父进程通过 `wait` 获取。
- 虽然 `status` 是 int，但**只有低 8 位能被父进程拿到**。所以 `_exit(-1)` 时，终端里 `$?` 显示的是 **255**（-1 的低 8 位）。
- `_exit` 是**系统调用**，进程退出时**不刷新缓冲区**。

### 2.4 exit：走完流程再闭眼

```c
#include <stdlib.h>
void exit(int status);
```

`exit` 是 C 库函数，它最后也会调用 `_exit`，但在那之前多做三件事：

1. 执行用户通过 `atexit` / `on_exit` 注册的清理函数；
2. 关闭所有打开的流，**刷新缓冲区**，把缓存数据写出去；
3. 调用 `_exit`。

一组对比实验最能说明问题：

```c
// 实验一：用 exit —— 缓冲区被刷新，能看到 hello
int main() { printf("hello"); exit(0); }
```

```text
[root@localhost linux]# ./a.out
hello[root@localhost linux]#     ← hello 输出了（没有换行符也照样显示）
```

```c
// 实验二：用 _exit —— 缓冲区不刷新，hello 直接丢失
int main() { printf("hello"); _exit(0); }
```

```text
[root@localhost linux]# ./a.out
[root@localhost linux]#          ← 什么都没有
```

> **板书要点**：exit 和 _exit 的本质区别就是**刷不刷缓冲区**；而且这个缓冲区**不是操作系统内核里的缓冲区，是 C 语言库维护的用户级缓冲区**。

### 2.5 return 退出

`return n` 是最常见的退出方式，**它等同于 `exit(n)`**——因为调用 main 的运行时函数（启动例程）会把 main 的返回值当作 `exit` 的参数。

> **板书要点**：main 函数结束 = 进程结束；而**其他函数的 return 只表示函数调用返回**，不代表进程结束。任何地方调用 `exit` 都表示进程立刻结束。

## 3. 进程等待：父进程的"收尸"义务

### 3.1 为什么必须等待

- 子进程退出后，如果父进程不管不顾，子进程就会变成**僵尸进程（Zombie）**，其 task_struct 一直占着内存 → **内存泄漏**。
- 僵尸进程"刀枪不入"：连 `kill -9` 都杀不死它——**你没法杀死一个已经死了的进程**。
- 父进程派给子进程的任务完成得如何（结果对不对、是否正常退出），父进程需要知道。

> **板书要点**：进程等待的两个目的——**回收子进程资源（最重要的）** + 获取子进程退出信息（可选的）。

### 3.2 wait：最朴素的等待

```c
#include <sys/types.h>
#include <sys/wait.h>

pid_t wait(int* status);
```

- **返回值**：成功返回被等待子进程的 PID，失败返回 -1。
- **status**：输出型参数（由操作系统填充），拿回子进程退出状态；不关心就传 `NULL`。
- 如果子进程还没退出，父进程会**阻塞**在 wait 调用处。

### 3.3 waitpid：可指定对象、可非阻塞

```c
pid_t waitpid(pid_t pid, int *status, int options);
```

**pid 参数**（等待谁）：

| pid 取值 | 等待对象 |
|----------|----------|
| `< -1` | 进程组 ID 等于 pid 绝对值的任意子进程 |
| `-1` | 任意一个子进程（与 `wait` 等效） |
| `0` | 进程组 ID 与调用进程相同的任意子进程 |
| `> 0` | 进程 ID 恰好等于 pid 的那个子进程 |

**options 参数**（怎么等）：

- `0`（默认）：**阻塞等待**，子进程不退出父进程就一直挂起；
- `WNOHANG`：**非阻塞等待**——若子进程没结束，`waitpid` 立即返回 0 不等了；若已结束则返回该子进程 PID。

**返回值**：正常返回收集到的子进程 PID；设了 WNOHANG 且暂无已退出子进程时返回 0；出错返回 -1（errno 指示原因）。

**补充说明**：

- 子进程**已经退出**时调用 wait/waitpid → 立即返回，释放资源，拿到退出信息；
- 子进程**正在运行**时调用 → 可能阻塞（取决于 options）；
- **不存在**该子进程 → 立即出错返回。

### 3.4 status 位图：退出信息怎么读

`status` 不能简单当作整型看，要当作**位图**看（只研究低 16 位）：

```text
bit:  15 ────────── 8 │ 7        │ 6 ─────── 0
     ┌────────────────┬──────────┬────────────┐
正常终止│   退出状态(8位) │ 0        │ 0          │
被信号杀│   未用(8位)     │ core dump│ 终止信号(7位)│
     └────────────────┴──────────┴────────────┘
```

- **低 7 位（6~0）**：终止信号。全 0 表示正常退出；非 0 表示被信号杀死，此时退出码无意义。
- **第 7 位**：core dump 标志。
- **次低 8 位（15~8）**：退出状态（正常终止时的 exit code）。

手动位运算读取的精简示例：

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    pid_t pid = fork();
    if (pid == -1) { perror("fork"); exit(1); }

    if (pid == 0) {          // 子进程：睡 20 秒后以退出码 10 正常退出
        sleep(20);
        exit(10);
    } else {                 // 父进程：阻塞等待并解析 status
        int st;
        int ret = wait(&st);

        if (ret > 0 && (st & 0x7F) == 0)              // 低7位为0 → 正常退出
            printf("child exit code: %d\n", (st >> 8) & 0xFF); // 取8~15位
        else if (ret > 0)                             // 低7位非0 → 被信号杀死
            printf("sig code: %d\n", st & 0x7F);
    }
    return 0;
}
```

```text
# ./a.out（等 20 秒正常退出）
child exit code: 10

# ./a.out（另开一个终端 kill 掉子进程）
sig code: 9
```

> **板书要点**：OS 会把子进程的退出信息（exit_code、exit_signal）保存在 task_struct 中，父进程调 wait/waitpid 时，内核把它拷贝给父进程——**这就是"父子之间靠 wait 通信"的真相**。

> 实际开发中不必手写位运算，直接用宏：`WIFEXITED(status)`（是否正常退出）、`WEXITSTATUS(status)`（提取退出码）、`WIFSIGNALED(status)` / `WTERMSIG(status)`（是否被信号杀、取信号值）。

### 3.5 阻塞 vs 非阻塞等待

> **类比理解**（板书原类比）：
> - **阻塞等待** = 打电话给李四，李四不接，你一直拿着电话干等（挂起，啥也干不了）；
> - **非阻塞等待** = 李四不接，你挂了电话先去做别的事，过一会儿再打（轮询）。

阻塞式等待（父进程挂起 5 秒，直到子进程退出）：

```c
// 父进程片段：options 传 0 → 阻塞等待
int status = 0;
pid_t ret = waitpid(-1, &status, 0);      // 卡在这里，直到任一子进程退出
if (WIFEXITED(status) && ret == pid)
    printf("child return code: %d\n", WEXITSTATUS(status));
```

> 小彩蛋：课件里子进程故意 `exit(257)`，而打印出的退出码是 **1**——正好验证 2.3 节"只有低 8 位有效"（257 的低 8 位 = 1）。

非阻塞轮询（父进程边等边干活）：

```c
// 父进程片段：WNOHANG + 轮询，等待期间穿插执行自己的任务
int status = 0;
pid_t ret = 0;
do {
    ret = waitpid(-1, &status, WNOHANG);   // 非阻塞：没退出立即返回 0
    if (ret == 0)
        printf("child is running\n");
    handler();                              // 趁等待的空档做自己的事
} while (ret == 0);                         // 轮询直到子进程退出

if (WIFEXITED(status) && ret == pid)
    printf("child return code: %d\n", WEXITSTATUS(status));
```

这里的 `handler()` 通常用**函数指针数组 / `std::function` 回调机制**实现：把一批临时任务装进数组，每次轮询空档拿出来跑一遍。这就是非阻塞等待的价值——**等待期间父进程不必傻等，可以并发处理自己的任务**。

## 4. 进程程序替换：换个灵魂接着跑

fork 之后，子进程执行的还是父进程的代码（只是可以走不同分支）。如果子进程想执行一个**全新的程序**呢？——靠**程序替换**。

**程序替换**：通过 exec 系列接口，把磁盘上一个全新的程序（代码和数据）加载到**调用进程的地址空间中**，替换掉原来的内容。

### 4.1 替换原理

- 进程调用 exec 后，其**用户空间的代码和数据被新程序完全替换**，从新程序的启动例程开始执行。
- **调用 exec 并不创建新进程，所以替换前后 PID 不变。**

> **板书要点**：
> - 进程 = **内核数据结构（task_struct）+ 代码和数据**。程序替换只换代码和数据，task_struct 原封不动——所以 PID 不变。
> - 一旦替换成功，旧程序的后半部分代码**已经不存在了**，不可能再"回来"。
> - exec 系列函数**只有失败返回值 -1，没有成功返回值**——只要 exec 返回了，就说明失败了。

### 4.2 exec 函数簇：六个变体一条心

```c
#include <unistd.h>

int execl(const char *path, const char *arg, ...);
int execlp(const char *file, const char *arg, ...);
int execle(const char *path, const char *arg, ..., char *const envp[]);
int execv(const char *path, char *const argv[]);
int execvp(const char *file, char *const argv[]);
int execve(const char *path, char *const argv[], char *const envp[]);
```

命名看着晕，其实规律就四个字母：

| 字母 | 全称 | 含义 |
|------|------|------|
| **l** | list | 参数用**列表**形式（可变参数，以 `NULL` 结尾） |
| **v** | vector | 参数用**数组**形式（`char *const argv[]`） |
| **p** | path | 自动搜索环境变量 **PATH**，程序名不用写全路径 |
| **e** | env | 自己传入**环境变量**数组 `envp` |

精简对照示例：

```c
#include <unistd.h>
#include <stdlib.h>

int main()
{
    char *const argv[] = {"ps", "-ef", NULL};              // v 系列用的参数数组
    char *const envp[] = {"PATH=/bin:/usr/bin", NULL};     // e 系列用的环境变量数组

    execl("/bin/ps", "ps", "-ef", NULL);   // 全路径 + 参数列表（NULL 收尾）
    execlp("ps", "ps", "-ef", NULL);       // 带 p：只写程序名，自动搜 PATH
    execv("/bin/ps", argv);                // 全路径 + 参数数组
    execvp("ps", argv);                    // 带 p + 参数数组
    execle("/bin/ps", "ps", "-ef", NULL, envp);  // 带 e：自带环境变量
    execve("/bin/ps", argv, envp);               // 唯一的真·系统调用
    exit(0);                               // 只有 exec 失败才会执行到这行
}
```

> **使用要点**（板书）：以 `execl("/usr/bin/ls", "ls", "-l", "-a", NULL)` 为例——第一个参数是**路径 + 程序名**；第二个参数是**程序名本身**（命令行怎么写就怎么传）；后面依次是选项；**必须以 NULL 结尾**标记参数传完。

**exec 函数簇的关系**：

```text
execl ──┐
execlp ─┤
execle ─┼──→ 库函数封装（man 第 3 节）──→ execve（man 第 2 节，真正的系统调用）
execv ──┤
execvp ─┘
```

**环境变量的三种传入方式**（板书要点）：

1. 用 `putenv()` 直接新增/修改环境变量（影响**当前进程**及其后代）；
2. 用 `execle` / `execve` 传入全新的 `envp` 列表（只影响**被替换的那个进程**）；
3. 什么都不做 → 默认**继承父进程**的环境变量。

**补充解答两个思考题**：

> **Q：为什么 exec 替换子进程不会影响父进程？**
> 两个原因：① 进程具有独立性；② 数据层面有写时拷贝。子进程加载新程序时，内核为它准备独立的代码和数据，父进程的地址空间纹丝不动。

> **Q：能替换成我们自己写的程序吗？**
> 能！只要编译出可执行文件（如 `./other`），`execl("./other", "other", NULL)` 一样好使——exec 不认识"系统命令"和"我的程序"的区别，它只认可执行文件。

## 5. 自主 Shell 命令行解释器：把前五节拼起来

### 5.1 目标

- 能处理**普通命令**（ls、ps 等，fork + exec + wait）；
- 能处理**内建命令**（cd、export 等，shell 自己执行）；
- 借此理解**内建命令 / 本地变量 / 环境变量**的概念；
- 借此理解 **shell 的运行原理**。

### 5.2 实现原理

先看 shell 与用户的典型互动：敲入 `ls` → shell 列出文件；敲入 `ps` → 看到 `bash` 和 `ps` 两个进程。用时间轴表示：

```text
时间 →
shell(sh):  读入"ls" ──fork──┐            ┌── 读入"ps" ──fork──┐
            等待子进程结束 ←──┘            │    等待子进程结束 ←──┘
子进程:              执行 ls 退出          │              执行 ps 退出
```

所以要写一个 shell，本质就是**一个循环**：

1. 获取命令行（打印提示符 + 读入一行）；
2. 解析命令行（按空格切分成 argv）；
3. fork 建立子进程；
4. execvp 替换子进程执行命令；
5. 父进程 wait 等待子进程退出，记录退出码。

> **板书要点**：内建命令 vs 普通命令——
> - **普通命令**：必须由子进程执行（如 ls/ps/cat）；
> - **内建命令**：不能交给子进程，**必须由 shell 自己执行**（本质是 shell 调用自己的函数或系统调用）。原因很直白：`cd` 要改的是 shell 自己的当前目录，`export` 要改的是 shell 自己的环境变量表——交给子进程改了也没用（进程独立性），所以必须 shell 亲自动手。

### 5.3 核心代码（精简骨架版）

完整源码约 270 行，这里提炼出带注释的骨架，保留全部关键动作：

```cpp
#include <cstdio>
#include <cstring>
#include <cstdlib>
#include <unistd.h>
#include <sys/wait.h>

const int basesize = 1024;
const int argvnum  = 64;
const int envnum   = 64;

char *gargv[argvnum];   // 全局命令行参数表（execvp 要用）
int   gargc = 0;
char *genv[envnum];     // 我的 shell 自己的环境变量表
int   lastcode = 0;     // 上一条命令的退出码（供 echo $? 使用）

// 3. 解析命令行："ls -a -l" → gargv = {"ls","-a","-l",NULL}
void ParseCommandLine(char command_buffer[])
{
    memset(gargv, 0, sizeof(gargv));
    gargc = 0;
    gargv[gargc++] = strtok(command_buffer, " ");
    while ((bool)(gargv[gargc++] = strtok(nullptr, " ")));  // = 是刻意写的
    gargc--;                                   // 去掉多算的 NULL
}

// 4a. 检查并执行内建命令：shell 自己动手，不创建子进程
bool CheckAndExecBuiltCommand()
{
    if (strcmp(gargv[0], "cd") == 0) {         // cd：改 shell 自己的工作目录
        gargc == 2 ? chdir(gargv[1]), lastcode = 0 : lastcode = 1;
        return true;
    }
    if (strcmp(gargv[0], "export") == 0) {     // export：把变量加进 genv 表
        gargc == 2 ? AddEnv(gargv[1]), lastcode = 0 : lastcode = 2;
        return true;
    }
    if (strcmp(gargv[0], "env") == 0) {        // env：打印自己的环境变量表
        for (int i = 0; genv[i]; i++) printf("%s\n", genv[i]);
        lastcode = 0;
        return true;
    }
    if (strcmp(gargv[0], "echo") == 0) {       // echo $? / echo 字符串
        if (gargc == 2 && gargv[1][0] == '$' && gargv[1][1] == '?')
            printf("%d\n", lastcode);
        else if (gargc == 2)
            printf("%s\n", gargv[1]);
        lastcode = 0;
        return true;
    }
    return false;                              // 不是内建命令 → 走普通命令
}

// 4b. 执行普通命令：fork → execvp → waitpid，三步走
bool ExecuteCommand()
{
    pid_t id = fork();
    if (id < 0) return false;
    if (id == 0) {
        execvpe(gargv[0], gargv, genv);        // 子进程替换成目标程序
        exit(1);                               // 只有替换失败才会走到这行
    }
    int status = 0;
    if (waitpid(id, &status, 0) > 0)           // 父进程阻塞等待回收
        lastcode = WIFEXITED(status) ? WEXITSTATUS(status) : 100;
    return true;
}

int main()
{
    InitEnv();                                 // 从父 shell 的 environ 拷贝环境变量
    char command_buffer[basesize];
    while (true) {                             // shell 本质 = 无限循环
        PrintCommandLine();                    // 1. 打印 [user@host dir]#
        if (!GetCommandLine(command_buffer, basesize)) continue;  // 2. 读入一行
        ParseCommandLine(command_buffer);      // 3. 解析成 argv
        if (CheckAndExecBuiltCommand()) continue;  // 4. 内建命令优先
        ExecuteCommand();                      // 5. 普通命令交给子进程
    }
    return 0;
}
```

几个值得注意的细节：

- **环境变量从哪来**：`InitEnv()` 用 `extern char **environ` 拿到父 shell 的环境变量，逐条深拷贝进自己的 `genv` 表；
- **提示符怎么生成**：`snprintf` 拼出 `[用户名@主机名 当前目录]#`，用户名/主机名来自 `getenv("USER")` / `getenv("HOSTNAME")`；
- **`echo $?` 的秘密**：每次命令执行完把退出码存进全局 `lastcode`，echo 时打印它——这就是真实 shell 里 `$?` 的实现原理。

### 5.4 总结：exec/exit 就像 call/return

最后思考一个有意思的问题：**函数和进程有多像？**

一个 C 程序由很多函数组成：函数调用函数，传参，干活，返回值——call/return 是结构化程序设计的基础。Linux 鼓励把这套模式**从程序内部扩展到程序之间**：

```text
程序内部：main ──call(传参)──> func ──return(返回值)──> main 用返回值
程序之间：父进程 ──fork/exec(传参)──> 子进程 ──exit(n)(返回值)──> 父进程 wait(&ret) 取回
```

一个程序可以 fork/exec 出另一个程序并传参，被调用的程序干完活通过 `exit(n)` 交回结果，调用方通过 `wait(&ret)` 收结果。**函数通信那一套，在进程层面原样复刻了一遍。**

## 全文总结

本节围绕**进程生命周期控制**展开，是操作系统进程管理的核心内容。

**主要知识点框架**：

| 模块 | 核心要点 |
|------|---------|
| **进程创建** | `fork()` 创建子进程；父子代码共享，数据写时拷贝 |
| **fork 返回值** | 子进程得 0（身份标记），父进程得子 pid（管理凭证），失败 -1 |
| **进程终止** | 正常：main return / `exit()` / `_exit()`；异常：信号 |
| **退出码** | 0 成功，非 0 失败；128+n 表示被信号 n 终止 |
| **exit vs _exit** | exit 刷 C 库缓冲区（用户级），_exit 不刷 |
| **进程等待** | `wait()` / `waitpid()` 回收子进程；阻塞 vs 非阻塞（WNOHANG 轮询） |
| **status 位图** | 低 7 位终止信号，第 7 位 core dump，8~15 位退出码 |
| **程序替换** | exec 簇：只换代码数据不换 task_struct，PID 不变 |
| **exec 命名** | l=list，v=vector，p=PATH，e=env；只有 execve 是真系统调用 |
| **shell 本质** | 循环：读命令 → 解析 → 内建自己做 / 普通命令 fork+execvp+wait |

**核心结论**：

1. **进程独立性的技术保证**：fork + 写时拷贝让父子彻底分离；写时拷贝是延时申请技术，提高整机内存使用率。
2. **退出码机制**：`echo $?` 查看上一条命令的退出码；exit code 走 status 的 8~15 位，signal 走 0~6 位；**低 7 位非 0 时退出码无意义**。
3. **进程等待的必要性**：父进程必须回收子进程（防僵尸/内存泄漏），顺带获取退出信息。
4. **exec 替换的本质**：不创建新进程，只替换代码和数据；PID 不变，旧代码一去不返；exec 只要返回就是失败。
5. **shell 的本质**：一个循环执行的进程——普通命令交给子进程（fork + execvp + wait），内建命令自己动手（cd/export/env/echo $?）。
6. **进程与函数的相似性**：exec/exit ≈ call/return，把函数间的通信模式扩展到进程间，是结构化程序设计思想的延伸。
