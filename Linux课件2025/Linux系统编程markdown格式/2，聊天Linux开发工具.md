# 2. 基础开发工具

## 1. 软件包管理器

这一部分其实是 Linux 开发环境的“入口知识”。后面我们要安装 `vim`、`gcc/g++`、`git`，甚至安装一些库，本质上都会不断接触软件包管理器。

先建立一条完整的认识链：

```text
Linux 软件
   ↓
软件包（Package）
   ↓
软件包仓库（Repository）
   ↓
软件包管理器（Package Manager）
   ↓
安装 / 升级 / 卸载 / 查询软件
```

你以后在 Linux 上搭开发环境，会反复用到这套机制。

---

# 1-1 什么是软件包

## 1. 为什么需要“软件包”

我们平时在 Windows 安装软件，可能会接触：

```text
.exe
.msi
.zip
```

例如下载一个软件安装包，双击之后一路“下一步”就安装好了。

Linux 也需要安装软件，但它通常不是让你手动找一个安装程序，而是把软件整理成一种**标准的软件包格式**，交给系统的软件包管理体系处理。

所谓**软件包（Package）**，简单理解就是：

> **把一个软件运行所需要的文件、信息以及安装规则，按照统一格式打包起来。**

例如一个软件可能包含：

```text
可执行文件
配置文件
动态库
帮助文档
版权信息
版本信息
依赖关系
安装/卸载相关信息
```

所以软件包并不只是“一个可执行文件”。

---

## 2. 一个软件为什么可能依赖其他软件？

这是理解软件包管理器最重要的地方之一。

例如我们安装一个程序：

```text
A
```

但 A 运行时需要：

```text
B
C
D
```

其中 B 又依赖：

```text
E
```

于是实际关系可能是：

```text
        A
      / | \
     B  C  D
     |
     E
```

如果没有软件包管理器，你就需要自己：

```text
下载 A
↓
发现缺 B
↓
下载 B
↓
发现 B 需要 E
↓
下载 E
↓
再处理 C
↓
再处理 D
```

不仅麻烦，而且很容易出现**版本不匹配、依赖缺失**等问题。

所以软件包管理器最重要的能力之一就是：

> **自动处理软件之间的依赖关系。**

这也是后面你使用 `yum install xxx` 时，为什么它有时会顺便安装一大堆其他软件。

---

# 1-2 Linux软件生态

理解 Linux 软件生态，先不要死记各种命令，而要先认识三个东西：

```text
软件包
软件包管理器
软件包仓库
```

它们不是一个东西。

| 概念     | 作用         |
| ------ | ---------- |
| 软件包    | 软件的标准化安装载体 |
| 软件包管理器 | 管理软件包的软件   |
| 软件包仓库  | 存放大量软件包的地方 |

可以把它类比成手机：

```text
APK
≈ 软件包

应用商店
≈ 软件包仓库

应用商店客户端
≈ 软件包管理器
```

当然 Linux 的机制比手机应用商店更加开放，但这个类比非常适合理解三者关系。

---

## 1. Linux 为什么有这么多软件生态？

因为 Linux 并不是一个单独的“操作系统发行版”。

更准确地说：

```text
Linux Kernel
    +
系统工具
    +
软件包系统
    +
安装配置工具
    +
桌面环境等
    ↓
Linux 发行版
```

常见发行版例如：

```text
CentOS
Rocky Linux
AlmaLinux
RHEL
Ubuntu
Debian
Fedora
Arch Linux
```

不同发行版往往采用不同的软件包格式和管理工具。

例如：

| 发行版生态             | 常见软件包        | 常见管理工具        |
| ----------------- | ------------ | ------------- |
| CentOS / RHEL 系   | `.rpm`       | `yum` / `dnf` |
| Ubuntu / Debian 系 | `.deb`       | `apt`         |
| Arch 系            | Arch Package | `pacman`      |

所以：

> **`yum` 不是 Linux 通用命令，而是特定 Linux 发行版生态中的软件包管理工具。**

这点非常重要。

你以后在 Ubuntu 上输入：

```bash
yum install gcc
```

通常就不是正确的做法；Ubuntu 使用的是：

```bash
apt install gcc
```

# 1-3 yum具体操作

由于你当前课程这里讲的是 `yum`，我们以 **CentOS/RHEL 系**为主。

先建立一个最基本的认识：

> `yum` 是一个软件包管理工具，可以帮助我们从软件仓库中查询、安装、升级、卸载软件，并处理依赖关系。

可以把它理解成：

```text
你
 ↓
yum
 ↓
软件仓库
 ↓
下载软件包
 ↓
处理依赖
 ↓
安装到系统
```

# 1-3-1 查看软件包

学习 `yum`，先学“查”。

## ① 查看仓库中有哪些软件包

```bash
yum list
```

它会列出软件包信息。

一般可以看到类似：

```text
软件包名       版本             仓库
gcc.x86_64     xxx              base
git.x86_64     xxx              ...
vim.x86_64     xxx              ...
```

你不需要现在去背每一列，先理解：

```text
yum list
```

就是：

> **查看软件包信息。**

---

## ② 查看指定软件包

例如：

```bash
yum list gcc
```

意思是：

> 查询名为 `gcc` 的软件包。

还可以：

```bash
yum list installed
```

查看**已经安装的软件包**。

这两个非常容易混：

```bash
yum list
```

偏向于查看软件包列表；

```bash
yum list installed
```

专门查看已经安装的软件包。

---

## ③ 搜索软件包

假设你只知道某个软件大概和“网络工具”有关，但不知道具体包名，可以：

```bash
yum search network
```

它会搜索相关的软件包。

这在实际使用中特别有用：

```text
不知道软件包叫什么
        ↓
yum search 关键词
        ↓
找到可能的包名
        ↓
yum install 包名
```

---

## ④ 查看软件包详细信息

```bash
yum info gcc
```

可以查看某个软件包的详细信息，例如：

```text
Name
Version
Release
Architecture
Size
Repository
Summary
Description
```

所以可以形成一组非常清晰的命令：

| 命令                   | 作用        |
| -------------------- | --------- |
| `yum list`           | 查看软件包     |
| `yum list installed` | 查看已安装软件包  |
| `yum search xxx`     | 搜索软件包     |
| `yum info xxx`       | 查看软件包详细信息 |

---

# 1-3-2 安装软件

最核心的命令：

```bash
yum install 软件包名
```

例如：

```bash
yum install tree
```

意思就是：

> 使用 yum 安装 `tree` 软件包。

---

## 1. yum 安装时到底发生了什么？

假设你执行：

```bash
yum install tree
```

并不是简单地：

```text
下载 tree
↓
复制到某个目录
```

它实际上会做很多事情，大致可以理解为：

```text
yum install tree
        ↓
查询仓库
        ↓
找到 tree 软件包
        ↓
检查 tree 的依赖
        ↓
计算依赖关系
        ↓
下载 tree 以及必要依赖
        ↓
安装
        ↓
更新软件包数据库
```

这就是为什么我们说：

> **软件包管理器不仅仅负责“下载”，更重要的是负责“管理”。**

---

## 2. 为什么有时会安装多个软件？

例如：

```bash
yum install A
```

最后你发现它说：

```text
Install package A
Install package B
Install package C
Install package D
```

不要觉得奇怪。

可能是：

```text
A
├── B
├── C
└── D
```

因为：

```text
A 依赖 B
A 依赖 C
B 又依赖 D
```

所以 yum 会自动把依赖补齐。

这就是软件包管理器非常重要的价值。

---

## 3. `-y` 是什么？

有时候执行：

```bash
yum install tree
```

会看到类似：

```text
Is this ok [y/d/N]:
```

让你确认。

这个时候输入：

```text
y
```

继续。

如果你明确知道自己要安装什么，可以：

```bash
yum install -y tree
```

`-y` 可以理解为：

> **自动对需要确认的问题回答 yes。**

例如：

```bash
yum install -y gcc
```

在脚本、自动化环境中非常常见。

但初学阶段我反而建议你多看看 yum 输出的内容，不要什么都无脑加 `-y`。

因为 yum 会告诉你：

```text
安装什么
升级什么
删除什么
需要下载多少
需要占用多少空间
```

这些信息本身就是很重要的。

# 1-3-3 卸载软件

卸载同样很简单：

```bash
yum remove 软件包名
```

例如：

```bash
yum remove tree
```

也可以理解成：

```text
remove
≈ 删除软件包
```

某些环境中也可以使用：

```bash
yum erase tree
```

不过你现在记住：

```bash
yum remove tree
```

就够用了。

# 2. 把整个 yum 操作串起来

现在假设：

> 我想在 Linux 上使用 `tree`，但是不知道有没有安装。

你可以按照这个思路：

### 第一步：看看有没有

```bash
yum list installed | grep tree
```

这里顺便提前接触一个你前面已经学过的重要知识：

```text
|
```

是管道。

意思是把：

```bash
yum list installed
```

的输出交给：

```bash
grep tree
```

进行筛选。

所以：

```bash
yum list installed | grep tree
```

就是：

> 查看已经安装的软件包，再从中筛选出包含 `tree` 的行。

这正好把之前学过的**管道**和现在的**软件包管理**联系起来。

---

### 第二步：如果没有安装，就搜索

```bash
yum search tree
```

找到正确的软件包。

---

### 第三步：查看详细信息

```bash
yum info tree
```

---

### 第四步：安装

```bash
yum install tree
```

或者：

```bash
yum install -y tree
```

---

### 第五步：使用软件

```bash
tree
```

---

### 第六步：不需要了就卸载

```bash
yum remove tree
```

于是完整流程就是：

```text
查询
 ↓
搜索
 ↓
查看信息
 ↓
安装
 ↓
使用
 ↓
卸载
```

你以后安装 `vim`、`git`、某些开发库，本质上也是这一套逻辑。

# 3. 一个非常重要的认识：软件包名 ≠ 命令名

这个地方特别容易产生误解。

例如：

```bash
yum install gcc
```

安装的是一个名叫 `gcc` 的软件包。

安装之后使用：

```bash
gcc test.c
```

这里的 `gcc` 是**可执行程序/命令**。

两者经常同名，但并不是概念上完全相同。

再例如：

```bash
yum install git
```

安装 Git 相关软件包，然后你使用：

```bash
git --version
```

这里的 `git` 是命令。

所以不要建立这样的死板认识：

> “yum 后面写的东西就是命令。”

实际上：

```text
yum install xxx
        ↑
     软件包名

xxx
↑
可能是安装后提供的命令
```

至于一个软件包到底提供哪些命令、文件，后面深入 Linux 软件管理时还会继续接触。

---

# 4. yum 和 rpm 是什么关系？

这里给你提前建立一个很重要的框架。

CentOS/RHEL 体系里面经常看到：

```text
RPM
yum
```

它们不是同一个东西。

可以先粗略理解：

```text
RPM
↓
更底层的软件包管理工具

YUM
↓
更上层的软件包管理工具
↓
能够从仓库获取软件
↓
解决依赖关系
```

例如你直接拿到一个：

```text
xxx.rpm
```

可以使用 `rpm` 操作。

而：

```bash
yum install xxx
```

则更加偏向于：

> **从软件仓库找到软件包，并自动处理依赖。**

因此对于日常安装软件来说，`yum` 通常更加方便。

后面讲到动态库、静态库以及软件安装时，你还会再次遇到 RPM 的概念，现在先建立这个层次感就够了。

---

# 5. 和 Ubuntu 的 apt 对照起来理解

你以后同时接触 CentOS 和 Ubuntu，这张表建议记住：

| 功能     | CentOS/RHEL 系     | Ubuntu/Debian 系   |
| ------ | ----------------- | ----------------- |
| 软件包格式  | RPM               | DEB               |
| 常用管理工具 | yum / dnf         | apt               |
| 安装     | `yum install xxx` | `apt install xxx` |
| 卸载     | `yum remove xxx`  | `apt remove xxx`  |
| 搜索     | `yum search xxx`  | `apt search xxx`  |
| 查看信息   | `yum info xxx`    | `apt show xxx`    |

核心不是背命令，而是理解：

```text
不同 Linux 发行版
        ↓
可能采用不同的软件包体系
        ↓
对应不同的软件包管理器
```

所以以后看到：

```bash
apt install gcc
```

不要觉得“怎么突然不是 yum 了”。

这是**发行版不同**导致的。

---

# 6. 到这里，你应该建立这张知识地图

```text
Linux 发行版
│
├── CentOS / RHEL
│   ├── RPM 软件包体系
│   └── yum / dnf
│
├── Ubuntu / Debian
│   ├── DEB 软件包体系
│   └── apt
│
└── 其他发行版
```

以 CentOS/RHEL 为例：

```text
软件
 ↓
打包成 RPM 软件包
 ↓
放入软件仓库
 ↓
yum 从仓库寻找
 ↓
解析依赖
 ↓
下载安装
 ↓
软件进入系统
```

而你作为使用者，最常做的事情就是：

```bash
yum search xxx
yum info xxx
yum install xxx
yum remove xxx
```

# 本节总结

这一次最重要的不是记住几个 `yum` 命令，而是理解 **Linux 软件是如何被组织和管理的**：

**1. 软件包（Package）**：把软件运行所需的文件和相关元信息按照标准格式组织起来。

**2. 软件包管理器**：负责软件包的查询、安装、卸载、升级以及依赖处理。

**3. 软件包仓库（Repository）**：集中存放大量软件包，`yum` 可以从仓库中找到并获取软件。

**4. 不同发行版的软件生态不同**：CentOS/RHEL 常见 RPM + `yum/dnf`，Ubuntu/Debian 常见 DEB + `apt`。

**5. yum 基本操作**：

```bash
yum list
yum list installed
yum search xxx
yum info xxx
yum install xxx
yum remove xxx
```

**6. 最重要的核心思想**：

```text
yum 不只是“下载软件”
而是“管理软件及其依赖关系”
```

# 2. 基础开发工具

## 1-3-4 注意事项

前面我们已经知道：

```bash
yum install xxx
```

背后不是简单地“下载一个文件”，而是：

```text
yum
 ↓
软件仓库
 ↓
查找软件包
 ↓
解决依赖
 ↓
下载
 ↓
安装
```

因此，`yum` 能不能正常工作，**很大程度上取决于软件仓库，也就是安装源是否正常**。

---

## 1. 不要随便卸载系统软件

例如：

```bash
yum remove xxx
```

看起来只是删除一个软件，但这里有一个危险情况：

```text
A 依赖 B
C 依赖 B
```

如果你删除 B：

```text
B 被删除
 ↓
A 可能无法运行
C 可能无法运行
```

因此使用 `yum remove` 时，尤其是服务器环境，不要只看：

```text
是否删除了我想删除的软件
```

还要看 yum 给出的操作计划：

```text
Removed:
    xxx

Dependencies removed:
    ...
```

**重点：软件包之间存在依赖关系。**

这也是为什么前面说：

> 软件包管理器的核心价值之一，就是管理依赖关系。

---

## 2. `yum update` 不要随便执行

我们经常会看到：

```bash
yum update
```

它的作用大致是：

> **根据当前软件仓库，把系统中可以更新的软件包进行升级。**

这和：

```bash
yum install xxx
```

是两个不同概念。

```text
install
→ 安装指定软件

update
→ 更新系统中已有的软件包
```

服务器上不要形成“看到 update 就直接执行”的习惯。

因为系统更新可能涉及：

```text
库版本
系统组件
网络组件
服务程序
内核相关组件
```

开发学习环境问题相对小一些，但生产服务器上的更新应该经过明确评估。

---

## 3. 安装软件时注意软件包名称

例如你想安装 Git：

```bash
yum install git
```

这里的：

```text
git
```

是**软件包名称**。

但实际存在的软件包可能非常多：

```text
git
git-core
git-all
git-svn
...
```

所以：

```bash
yum search git
```

是很有价值的。

不要因为“命令叫 git”，就认为所有发行版、所有相关功能都对应一个叫 `git` 的包。

---

## 4. `yum` 不是万能的

例如：

```bash
yum install abc
```

如果系统告诉你：

```text
No package abc available.
```

这不一定代表：

> Linux 上不存在 abc 软件。

更准确地说，它可能代表：

```text
当前 yum 配置的软件仓库
        ↓
没有找到名为 abc 的可用软件包
```

可能的原因包括：

```text
软件包真的不存在
        ↓
包名写错
        ↓
仓库没有配置
        ↓
仓库中没有这个版本
        ↓
仓库已经失效
        ↓
网络无法访问仓库
```

因此：

> **“yum 找不到” ≠ “Linux 没有这个软件”。**

这是非常重要的思维方式。

# 1-4 安装源

## 1. 什么叫安装源？

你前面已经知道：

```text
yum
 ↓
去某个地方寻找软件包
```

那么这个“地方”就是我们经常说的：

> **软件源 / 软件仓库 / Repository**

所谓**安装源**，本质上就是告诉软件包管理器：

> **“你去哪里寻找软件包。”**

例如：

```text
你的 Linux
    ↓
yum
    ↓
软件源
    ↓
服务器上的软件仓库
    ↓
gcc / git / vim / tree ...
```

---

## 2. 为什么一个 Linux 可以配置多个源？

因为软件包不一定只有一个服务器提供。

例如：

```text
官方源
   \
    \
     → yum
    /
镜像源
   /
校园镜像
```

这些服务器可能提供相同或者相近的软件仓库内容。

这样做最大的好处就是：

> **降低访问距离、提高下载速度，同时增加可用性。**

---

## 3. 什么是镜像源？

例如一个官方软件仓库可能位于某个地区：

```text
用户
 ↓
很远的官方服务器
```

如果我们在国内：

```text
用户
 ↓
国内镜像服务器
 ↓
获取软件包
```

一般情况下网络路径可能更合适，下载体验也可能更好。

所以你经常会看到：

```text
阿里云镜像
清华大学镜像
中科大镜像
```

这类地址。

需要注意：

> **镜像源 ≠ 一个“不同的软件”。**

它通常只是对软件仓库内容进行镜像。

# 4. yum 的仓库配置在哪里？

这一点值得记住：

```bash
/etc/yum.repos.d/
```

这个目录非常重要。

你可以：

```bash
ls /etc/yum.repos.d/
```

看看里面有什么。

通常可以看到：

```text
xxx.repo
xxx.repo
...
```

`.repo` 文件就是 yum 的仓库配置文件。

例如：

```text
/etc/yum.repos.d/CentOS-Base.repo
```

它里面会描述仓库相关信息。

可以简单理解成：

```text
.repo 文件
    ↓
告诉 yum：
“软件仓库在哪里”
```

---

# 5. `.repo` 文件里面有什么？

打开一个 `.repo` 文件，你经常会看到类似：

```ini
[base]
name=Base
baseurl=http://example.com/...
enabled=1
gpgcheck=1
gpgkey=...
```

现在先理解几个核心字段即可。

### `[base]`

这是一个仓库的标识名称。

---

### `name`

仓库的人类可读名称。

例如：

```ini
name=Base
```

---

### `baseurl`

软件仓库真正访问的位置。

例如概念上：

```ini
baseurl=http://example.com/centos/...
```

也就是说：

```text
yum
 ↓
baseurl
 ↓
找到仓库
```

---

### `enabled`

例如：

```ini
enabled=1
```

代表启用。

如果：

```ini
enabled=0
```

则表示这个仓库当前不启用。

可以简单理解：

```text
1 → 开
0 → 关
```

---

### `gpgcheck`

例如：

```ini
gpgcheck=1
```

它和软件包签名校验有关，用于帮助确认软件包的来源和完整性。

这里先记住：

> **GPG 校验是软件包安全验证机制的一部分。**

不要把它简单理解成“下载成功就行”。

# 2-2 vim的基本概念

## 1. Vim 为什么设计成“模式”？

普通编辑器一般是：

```text
打开文件
 ↓
直接输入
 ↓
Ctrl+S 保存
```

而 Vim 不是。

Vim 默认进入的是：

> **普通模式（Normal Mode）**

这个模式下：

```text
你按 j
```

它可能不是输入字符 `j`，而是：

> **让光标向下移动。**

这就是第一次接触 Vim 最容易懵的地方。

---

# 2. Vim 最核心的几个模式

课程后面会详细讲，但现在必须先知道：

```text
             ┌──────────────┐
             │   Normal     │
             │   普通模式    │
             └──────┬───────┘
                    │
                  i / a
                    ↓
             ┌──────────────┐
             │    Insert    │
             │    插入模式   │
             └──────┬───────┘
                    │
                   Esc
                    ↓
             ┌──────────────┐
             │   Normal     │
             └──────┬───────┘
                    │
                    │ :
                    ↓
             ┌──────────────┐
             │ Command-line │
             │   末行模式    │
             └──────────────┘
```

这里最重要的是：

```text
普通模式
插入模式
末行模式
```

先理解三个就够。

# 2-3 vim的基本操作

## 1. 进入 Vim

```bash
vim test.c
```

打开：

```text
test.c
```

此时默认处于：

```text
普通模式
```

---

## 2. 进入插入模式

在普通模式下按：

```text
i
```

进入：

```text
插入模式
```

这时候你就可以正常输入：

```cpp
#include <iostream>

int main()
{
    std::cout << "hello linux" << std::endl;
    return 0;
}
```

---

## 3. 返回普通模式

编辑完成后按：

```text
Esc
```

重新回到：

```text
普通模式
```

所以你需要牢牢记住：

```text
i
↓
进入插入模式

Esc
↓
返回普通模式
```

这是 Vim 最基本的操作闭环。

---

# 4. 保存文件

Vim 的保存不是：

```text
Ctrl + S
```

而是先进入：

```text
普通模式
```

然后输入：

```text
:
```

进入末行模式。

再输入：

```text
w
```

最后回车：

```text
:w
```

含义：

```text
:
→ 我要执行一个末行命令

w
→ write

:w
→ 保存文件
```

所以：

```text
Esc
↓
:w
↓
Enter
```

就是保存。

---

# 5. 保存并退出

最经典的命令：

```text
:wq
```

含义：

```text
w → write，保存
q → quit，退出
```

操作：

```text
Esc
↓
:wq
↓
Enter
```

---

# 6. 不保存直接退出

```text
:q!
```

其中：

```text
q
→ quit

!
→ 强制
```

也就是：

> **放弃当前修改，强制退出 Vim。**

因此最常见的三个操作：

```text
:w
→ 保存

:wq
→ 保存并退出

:q!
→ 不保存，强制退出
```

---

# 7. 一个完整 Vim 操作流程

假设：

```bash
vim test.c
```

打开文件。

你可以：

```text
① 默认进入普通模式
        ↓
② 按 i
        ↓
③ 进入插入模式
        ↓
④ 输入代码
        ↓
⑤ 按 Esc
        ↓
⑥ 回到普通模式
        ↓
⑦ 输入 :wq
        ↓
⑧ Enter
        ↓
⑨ 保存并退出
```

可以把它记成：

```text
普通模式
   ↓ i
插入模式
   ↓ Esc
普通模式
   ↓ :
末行模式
   ↓ Enter
执行命令
```

# 8. 为什么 Vim 一直强调“先按 Esc”？

因为 Vim 中最重要的一个习惯是：

> **不知道自己现在在哪个模式，就先按 `Esc`。**

例如你刚刚正在输入代码：

```cpp
int main()
```

如果此时你不知道自己当前是什么模式，可以：

```text
Esc
```

它会把你带回普通模式。

然后再：

```text
:wq
```

这是 Vim 初学者非常实用的习惯。

---

# 9. Vim 与普通编辑器的本质区别

| 对比     | 普通编辑器      | Vim         |
| ------ | ---------- | ----------- |
| 默认输入文字 | 通常可以直接输入   | 默认是普通模式     |
| 移动光标   | 鼠标/方向键     | 命令也可以完成     |
| 保存     | `Ctrl+S` 等 | `:w`        |
| 退出     | `Alt+F4` 等 | `:q`        |
| 保存并退出  | 常见快捷键      | `:wq`       |
| 核心设计   | 直接编辑       | **模式 + 命令** |

因此：

> **Vim 的核心不是“命令特别多”，而是“不同模式下，同一个按键具有不同意义”。**

后面学习 Vim 正常模式命令集之后，你会发现：

```text
h
j
k
l
w
b
dd
yy
p
u
```

这些看起来乱七八糟的东西，其实都是建立在**普通模式**这个核心概念之上的。

# 2-4 Vim正常模式命令集

上一节最核心的认识是：

```text

        ↓
普通模式下，键盘不是主要用来“输入文字”

```

所以这一节开始，真正进入 Vim 的核心。

---

## 1. 光标移动：`h` `j` `k` `l`

Vim 最经典的移动命令：

```text
        k
        ↑
h  ←    ·    →  l
        ↓
        j
```

也就是：

| 按键  | 作用 |
| --- | -- |
| `h` | 左  |
| `j` | 下  |
| `k` | 上  |
| `l` | 右  |

例如：

```text
hello world
     ↑
   光标
```

按：

```text
l
```

光标向右移动。

按：

```text
h
```

向左移动。

### 为什么不用方向键？

当然可以使用方向键，但 Vim 的设计理念是让你尽可能**不离开主键区**。

而且后面会发现：

```text
移动命令 + 编辑命令
```

可以组合起来使用。

例如：

```text
dw
```

就是删除一个单词。

因此 `h/j/k/l` 不是“为了装高手”，而是 Vim 整个命令体系的一部分。

---

# 2. 按单词移动：`w` `b`

除了一个字符一个字符移动，Vim 还可以按“单词”移动。

### `w`

```text
w
```

向后移动到下一个单词的位置。

例如：

```text
This is a Linux system
↑
```

不断按：

```text
w
```

可以快速跳过：

```text
This → is → a → Linux → system
```

---

### `b`

```text
b
```

向前移动到上一个单词的位置。

所以：

```text
w → 往后
b → 往前
```

可以记成：

```text
word
 ↑
w：向后找下一个单词
b：向前找上一个单词
```

这里的“单词”是 Vim 对文本的一种定义，不完全等同于自然语言中的单词；标点、符号等会影响移动边界，这一点先知道即可。

---

# 3. 移动到行首、行尾：`0` `$`

### `0`

```text
0
```

移动到当前行的**行首**。

例如：

```text
        ↓
    int main()
```

按：

```text
0
```

就跳到：

```text
↓
int main()
```

---

### `$`

```text
$
```

移动到当前行的**行尾**。

因此：

```text
0 → 行首
$ → 行尾
```

这两个非常常用。

---

# 4. 文件开头和文件结尾：`gg` `G`

这两个也非常重要。

### `gg`

```text
gg
```

跳到文件开头。

### `G`

```text
G
```

跳到文件末尾。

所以：

```text
gg → 文件第一部分
G  → 文件最后
```

例如一个 1000 行的文件：

```text
1   ...
2   ...
3   ...
...
1000 ...
```

当前在第 500 行：

```text
gg
```

直接到第 1 行。

```text
G
```

直接到最后一行。

---

# 5. 删除：`x`

在普通模式下：

```text
x
```

删除当前光标所在位置的字符。

例如：

```text
abc
 ↑
```

按：

```text
x
```

变成：

```text
ac
```

所以：

```text
x
```

可以简单理解为：

> 删除当前字符。

---

# 6. 删除整行：`dd`

这就是 Vim 非常经典的命令：

```text
dd
```

删除当前行。

例如：

```cpp
int a = 10;
int b = 20;
int c = 30;
```

光标在：

```cpp
int b = 20;
```

执行：

```text
dd
```

结果：

```cpp
int a = 10;
int c = 30;
```

---

## 为什么是两个 `d`？

这是 Vim 很有代表性的设计：

```text
d
```

表示：

> delete，删除

再来一个：

```text
d
```

表示：

> 对整行执行删除。

以后你会发现很多 Vim 命令都是这种**动作 + 范围**的思想。

因此不要把 `dd` 单独死记成一个毫无规律的快捷键。

---

# 7. 删除多个字符 / 单词：`dw`

例如：

```text
hello linux world
      ↑
```

执行：

```text
dw
```

可以删除从当前光标开始的一个单词范围。

这里你第一次看到 Vim 很重要的一种思想：

```text
d
+
w
↓
删除 + 单词移动范围
↓
dw
```

也就是说：

```text
d
```

负责“删”。

```text
w
```

负责“到下一个单词”。

两个组合起来，就形成：

```text
dw
```

> 删除一个单词范围。

这也是为什么 Vim 学到后面会越来越“有规律”。

---

# 8. 复制：`yy`

```text
yy
```

复制当前行。

例如：

```cpp
int a = 10;
```

光标在这一行，执行：

```text
yy
```

这一行就被复制到了 Vim 的寄存器中。

注意：

> `yy` 是复制，不是直接出现第二行。

复制以后还需要粘贴。

---

# 9. 粘贴：`p`

```text
p
```

粘贴。

比如：

```cpp
int a = 10;
int b = 20;
```

光标在第一行执行：

```text
yy
p
```

就会得到类似：

```cpp
int a = 10;
int a = 10;
int b = 20;
```

---

## `p` 到底粘在哪里？

对于整行复制，通常可以简单记忆：

```text
p → 粘贴到当前行的下面
```

对应地还有：

```text
P
```

通常表示粘贴到当前行的上面。

所以：

```text
p → 后面
P → 前面
```

---

# 10. 撤销：`u`

如果误删了：

```text
dd
```

怎么办？

普通模式输入：

```text
u
```

即可撤销。

所以：

```text
u
```

就是：

> undo，撤销。

---

## 恢复撤销：`Ctrl + r`

如果：

```text
u
```

撤销过头了，可以：

```text
Ctrl + r
```

恢复刚才撤销的操作。

因此：

```text
u
→ 撤销

Ctrl + r
→ 重做 / 恢复被撤销的修改
```

这里非常容易记混：

> `Ctrl + r` 在 Vim 普通模式中是 redo，不是 Windows 中常见的“替换”概念。

---

# 11. 替换一个字符：`r`

假设：

```text
hello
  ↑
```

当前字符是：

```text
l
```

按：

```text
r
```

再输入：

```text
x
```

那么：

```text
hello
```

可以变成：

```text
hexlo
```

也就是说：

```text
r + 字符
```

执行**单字符替换**。

例如：

```text
ra
```

就是把当前字符替换成 `a`。

注意它和插入模式不同：

```text
r
→ 只是替换当前字符

i
→ 进入插入模式，可以连续输入
```

---

# 12. 进入插入模式的几个命令

上一节我们只学了：

```text
i
```

其实常见的还有：

| 命令  | 作用               |
| --- | ---------------- |
| `i` | 在当前字符前进入插入模式     |
| `a` | 在当前字符后进入插入模式     |
| `I` | 到当前行行首并进入插入模式    |
| `A` | 到当前行行尾并进入插入模式    |
| `o` | 当前行下面新建一行并进入插入模式 |
| `O` | 当前行上面新建一行并进入插入模式 |

例如：

```cpp
int main()
{
    return 0;
}
```

光标在 `return` 上。

执行：

```text
o
```

就会在当前行下面打开一个新行，并直接进入插入模式。

这对于写代码特别方便。

---

# 13. 一个非常重要的概念：命令可以组合

到了这里，你应该开始理解 Vim 的真正设计了。

例如：

```text
d + w
```

得到：

```text
dw
```

而：

```text
d + $
```

就是从当前位置删除到行尾。

又比如：

```text
y + y
```

得到：

```text
yy
```

表示复制整行。

于是可以把 Vim 理解成：

```text
动作
+
范围
↓
组合成操作
```

常见动作：

```text
d → delete
y → yank
c → change
```

常见范围：

```text
w → word
$ → 行尾
0 → 行首
```

于是：

```text
dw
d$
cw
c$
```

都会变得比较容易理解。

这一套思想比单纯背快捷键重要得多。

---

# 14. `c`：修改

例如：

```text
cw
```

可以理解为：

```text
c
+
w
```

其中：

```text
c → change
w → word
```

也就是：

> 修改当前单词范围。

它和 `dw` 有一个重要区别：

```text
dw
→ 删除

cw
→ 删除相应内容，然后进入插入模式，让你直接重新输入
```

例如原来：

```text
hello world
```

光标在 `world` 上，使用：

```text
cw
```

删除相应范围以后，进入插入模式，然后可以直接输入：

```text
Linux
```

最终得到：

```text
hello Linux
```

这就是 Vim 中“修改”的含义。

# 2-5 Vim末行模式命令集

前面已经接触：

```text
:
```

它可以让 Vim 从普通模式进入：

> **末行模式**

这里的命令更多是对**文件、搜索、替换、配置等整体操作**。

---

# 1. 保存：`:w`

```text
:w
```

`w` 是：

```text
write
```

表示保存。

---

# 2. 退出：`:q`

```text
:q
```

表示：

```text
quit
```

退出 Vim。

但是如果文件已经修改、还没有保存：

```text
:q
```

通常会提示不能直接退出。

这时候可以：

```text
:wq
```

或者：

```text
:q!
```

---

# 3. 保存并退出：`:wq`

```text
:wq
```

就是：

```text
write + quit
```

也就是：

```text
保存
+
退出
```

---

# 4. 强制退出：`:q!`

```text
:q!
```

表示：

> 放弃当前修改，强制退出。

所以：

```text
:wq
→ 我要保存这些修改

:q!
→ 我不要这些修改了
```

这两个一定要区分。

---

# 5. 搜索：`/`

Vim 中非常重要的功能：

```text
/foo
```

输入：

```text
/
```

之后输入：

```text
foo
```

再按：

```text
Enter
```

Vim 就会搜索 `foo`。

例如：

```text
/printf
```

会寻找：

```text
printf
```

---

## 搜索下一个：`n`

找到一个以后：

```text
n
```

跳到下一个匹配位置。

例如：

```text
/printf
```

然后不断：

```text
n
n
n
```

就可以继续找。

而：

```text
N
```

表示往相反方向寻找。

因此：

```text
/xxx
↓
搜索 xxx

n
↓
下一个

N
↓
上一个方向
```

---

# 6. 替换：`:s`

Vim 非常强大的功能之一就是文本替换。

例如当前行：

```text
hello hello hello
```

执行：

```text
:s/hello/linux/
```

可以理解成：

```text
:s
 ↓
当前行进行替换

hello
 ↓
寻找 hello

linux
 ↓
替换成 linux
```

所以：

```text
:s/旧内容/新内容/
```

就是：

> 在当前行进行替换。

---

# 7. 替换整篇文件

如果希望整个文件都替换：

```text
:%s/hello/linux/g
```

这个命令第一次看会比较复杂，我们拆开：

```text
:%s/hello/linux/g
 ↑ ↑     ↑      ↑
 │ │     │      └── 全部匹配
 │ │     └───────── 替换成 linux
 │ └─────────────── 搜索 hello
 └───────────────── 整个文件
```

其中：

```text
%
```

表示整个文件范围。

```text
g
```

表示一行中全部匹配的位置都进行替换，而不是只处理一个。

所以：

```text
:%s/hello/linux/g
```

可以理解为：

> **把整个文件中所有匹配的 `hello` 替换成 `linux`。**

这是 Vim 很强大的一个能力。

---

# 8. 显示行号：`:set nu`

执行：

```text
:set nu
```

可以显示行号。

例如：

```text
1  #include <stdio.h>
2
3  int main()
4  {
5      return 0;
6  }
```

这对代码阅读、调试非常有帮助。

关闭：

```text
:set nonu
```

或者：

```text
:set nonumber
```

---

# 9. 跳转到指定行

例如：

```text
:100
```

可以跳转到第 100 行。

这个功能在查看大型代码文件时很实用。

例如：

```text
:500
```

直接跳到第 500 行。

所以：

```text
gg
→ 文件开头

G
→ 文件末尾

:100
→ 第100行
```

# 10. 搜索与替换为什么重要？

因为 Vim 不只是一个“写几行代码”的编辑器。

真正处理 Linux 上的代码和配置文件时，你可能面对：

```text

几千行
几万行
```

这时候：

```text
鼠标拖
疯狂翻页
```

效率就很低。

而 Vim 可以：

```text

+
搜索
+

+

+

```

这也是为什么 Linux 服务器上，即使没有图形界面，我们仍然可以高效修改文件。

# 2-6 vim操作总结

现在把 Vim 的整体结构串起来：

```text
                    Vim
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
       普通模式               末行模式
          │                     │
          │                     │ :
          │                     │
      移动 / 删除 /          保存 / 退出 /
      复制 / 粘贴 /           搜索 / 替换 /
      撤销 / 编辑             配置 / 跳转
          │
          │ i / a / o ...
          ↓
       插入模式
          │
          │ Esc
          ↓
       普通模式
```

这张图非常重要。

Vim 不应该被理解成：

```text
“记住几十个快捷键”
```

而应该理解成：

```text
模式
 ↓
模式决定按键含义
 ↓
普通模式负责高效操作文本
 ↓
插入模式负责输入
 ↓
末行模式负责文件级命令
```

# 2-7 简单 Vim 配置【了解】

前面我们已经学会了：

```text
vim test.c
↓
编辑
↓
:wq
↓
退出
```

但是 Vim 默认的界面其实比较“原始”。实际开发时，我们通常会做一些简单配置。

## 1. Vim 配置文件

Vim 最常见的个人配置文件是：

```bash
~/.vimrc
```

这里：

```text
~
```

代表当前用户的家目录。

例如你的普通用户是 `caige`，那么：

```text
~/.vimrc
```

实际上就是类似：

```text
/home/caige/.vimrc
```

如果是 `root`：

```text
/root/.vimrc
```

注意：

> **每个用户可以有自己的 Vim 配置。**

所以你用普通用户登录和 `root` 登录时，Vim 的配置可能不一样。

---

## 2. 一个最简单的 `.vimrc`

可以执行：

```bash
vim ~/.vimrc
```

然后写：

```vim
set nu
syntax on
set tabstop=4
set shiftwidth=4
set expandtab
```

分别是什么意思？

| 配置                 | 作用          |
| ------------------ | ----------- |
| `set nu`           | 显示行号        |
| `syntax on`        | 开启语法高亮      |
| `set tabstop=4`    | Tab 显示宽度为 4 |
| `set shiftwidth=4` | 自动缩进宽度为 4   |
| `set expandtab`    | Tab 转换成空格   |

保存：

```text
Esc
:wq
Enter
```

重新打开 Vim 后就能看到效果。

---

## 3. 为什么 `.vimrc` 可以改变 Vim 行为？

因为 Vim 启动时会读取配置。

可以简单理解：

```text
启动 vim
   ↓
读取配置
   ↓
设置 Vim 行为
   ↓
打开文件
```

所以：

```bash
vim test.c
```

表面上只是打开文件，实际上 Vim 启动时已经先根据配置完成了一系列初始化。

---

## 4. Vim 配置和普通命令有什么区别？

例如：

```text
:set nu
```

是：

> **这一次 Vim 运行过程中临时打开行号。**

而：

```vim
set nu
```

写进：

```text
~/.vimrc
```

则是：

> **以后启动 Vim 默认都打开行号。**

所以：

```text
:set nu
        ↓
临时设置

~/.vimrc
        ↓
永久保存个人配置
```

当然这里的“永久”是指配置一直存在，直到你修改或删除它。

# 3. 编译器 gcc/g++

这一部分开始非常重要。

你前面已经会：

```text
vim test.c
```

也就是说：

```text
我们已经能够创建源代码
```

但是：

> **源代码本身并不能直接被 CPU 执行。**

例如：

```c
#include <stdio.h>

int main()
{
    printf("hello\n");
    return 0;
}
```

这是给**人和编译器**看的 C 语言源代码。

CPU 最终需要的是：

```text
机器指令
```

所以中间需要一个非常重要的软件：

> **编译器。**

---

# 3-1 背景知识

## 1. 什么是编译器？

简单来说：

> **编译器负责把高级语言源代码转换成机器能够执行的代码。**

例如：

```text
test.c
  ↓
C 编译器
  ↓
可执行程序
```

在 Linux 中，最常接触的就是：

```bash
gcc
g++
```

---

## 2. GCC 是什么？

GCC 最初叫：

> GNU Compiler Collection

现在它已经不是单纯“C 编译器”的意思，而是一套编译器集合。

我们常用：

```bash
gcc
```

来处理 C：

```bash
gcc test.c
```

常用：

```bash
g++
```

来处理 C++：

```bash
g++ test.cpp
```

所以你以后在 C++ 项目中会非常频繁地看到：

```bash
g++
```

---

## 3. `gcc` 和 `g++` 的关系

可以先这样理解：

| 命令    | 常见用途        |
| ----- | ----------- |
| `gcc` | C 程序编译      |
| `g++` | C++ 程序编译/链接 |

例如：

```bash
gcc test.c
```

和：

```bash
g++ test.cpp
```

分别对应：

```text
C
↓
gcc

C++
↓
g++
```

但注意一个比较严谨的地方：

> `gcc`、`g++` 更准确地说是 GCC 提供的编译驱动程序（driver），并不等于“整个编译器内部只有一个程序”。

后面你理解编译四个阶段之后，这个概念会自然清楚。

---

# 3-2 gcc编译选项

这是这一章真正的重点。

很多初学者使用：

```bash
gcc test.c
```

只知道：

```text
“它把 test.c 编译成了程序。”
```

但是不知道中间到底发生了什么。

事实上，经典的 GCC 编译过程可以拆成：

```text
源代码
 ↓
预处理
 ↓
编译
 ↓
汇编
 ↓
链接
 ↓
可执行程序
```

这四个阶段一定要理解。

---

# 3-2-1 预处理（进行宏替换）

首先：

> **预处理器处理源代码中的预处理指令。**

典型包括：

```c
#include
#define
#ifdef
#ifndef
#if
#else
#endif
```

例如：

```c
#include <stdio.h>

#define NUM 100

int main()
{
    printf("%d\n", NUM);
    return 0;
}
```

这里：

```c
#define NUM 100
```

定义了宏：

```text
NUM → 100
```

而：

```c
#include <stdio.h>
```

则需要把相关头文件内容纳入预处理结果。

所以第一阶段可以粗略理解为：

```text
test.c
 ↓
预处理
 ↓
test.i
```

---

## 2. 用 `gcc -E` 观察预处理

执行：

```bash
gcc -E test.c -o test.i
```

这里：

```text
-E
```

表示：

> 只进行预处理。

而：

```text
-o test.i
```

表示：

> 把结果输出到 `test.i`。

因此：

```text
test.c
 ↓ gcc -E
test.i
```

你可以：

```bash
vim test.i
```

或者：

```bash
less test.i
```

查看预处理结果。

---

## 3. 为什么 `.i` 文件通常很大？

这是很多初学者第一次看到预处理结果时的疑问。

你明明只有：

```c
#include <stdio.h>
```

几行代码，结果：

```text
test.i
```

可能一下变成了几百行、几千行甚至更多。

原因就是：

```text
#include
```

在预处理阶段会展开头文件内容。

所以：

```text
原始代码
   ↓
#include 展开
#define 宏替换
条件编译处理
   ↓
更大的文本
```

---

# 3-2-2 编译（生成汇编）

预处理之后进入：

> **编译阶段。**

这里的“编译”是一个容易被混淆的词。

我们平时说：

```text
“gcc 编译 test.c”
```

可能指整个：

```text
预处理
+
编译
+
汇编
+
链接
```

但在这套四阶段划分里：

> **编译阶段特指：把预处理后的代码转换成汇编代码。**

也就是：

```text
test.i
 ↓
编译
 ↓
test.s
```

---

## 1. 汇编代码是什么？

比如：

```text
mov
push
pop
call
add
sub
...
```

这些已经非常接近 CPU 的指令。

它还不是最终的机器二进制，但已经不是 C 语言了。

所以你可以理解为：

```text
C语言
 ↓
预处理后的C代码
 ↓
汇编语言
 ↓
机器代码
```

---

## 2. 用 `gcc -S`

执行：

```bash
gcc -S test.c -o test.s
```

其中：

```text
-S
```

表示：

> 生成汇编代码，然后停止。

得到：

```text
test.s
```

于是：

```text
test.c
 ↓ -E
test.i
 ↓ -S
test.s
```

---

# 3-2-3 汇编（生成机器可识别代码）

接下来：

```text
test.s
 ↓
汇编
 ↓
test.o
```

这一阶段由汇编器完成。

核心任务：

> **把汇编代码转换成机器码，并形成目标文件（Object File）。**

---

## 1. `gcc -c`

执行：

```bash
gcc -c test.c -o test.o
```

得到：

```text
test.o
```

这里：

```text
-c
```

表示：

> **编译并汇编，但不进行最终链接。**

虽然命令从 `test.c` 开始，但是 GCC 会自动完成：

```text
test.c
 ↓
预处理
 ↓
编译
 ↓
汇编
 ↓
test.o
```

并停在这里。

---

## 2. 为什么叫 `.o`？

因为它是：

> **Object File，目标文件。**

例如：

```text
test.o
```

里面已经不是普通 C 源代码，而是机器代码相关内容以及符号、重定位等信息。

但是：

> **它通常还不是一个可以直接运行的完整程序。**

这是非常关键的地方。

---

# 3-2-4 链接（生成可执行文件或库文件）

假设：

```text
test.o
```

已经生成。

为什么不能直接：

```bash
./test.o
```

运行？

因为程序通常不仅包含你自己写的代码。

例如：

```c
printf("hello\n");
```

`printf` 并不是你自己在 `test.c` 中实现的。

它来自 C 标准库相关实现。

因此最终程序需要把不同目标文件以及所需库的信息联系起来。

这个过程就是：

> **链接（Linking）。**

---

## 1. 链接做什么？

可以先简单理解成：

```text
test.o
    +
其他目标文件
    +
相关库
    ↓
链接器
    ↓
可执行程序
```

所以：

```text
test.o
```

还只是一个“组成部分”。

链接之后才形成完整程序。

---

# 4. 四个阶段一定要记住

这是整节最重要的知识图：

```text
                 GCC 编译过程

test.c
  │
  │ 预处理
  │ gcc -E
  ↓
test.i
  │
  │ 编译
  │ gcc -S
  ↓
test.s
  │
  │ 汇编
  │ gcc -c
  ↓
test.o
  │
  │ 链接
  │ gcc / g++
  ↓
可执行程序
```

分别对应：

| 阶段  | 输入            | 输出    | 核心作用            |
| --- | ------------- | ----- | --------------- |
| 预处理 | `.c` / `.cpp` | `.i`  | 宏展开、头文件展开、条件编译等 |
| 编译  | `.i`          | `.s`  | 生成汇编代码          |
| 汇编  | `.s`          | `.o`  | 生成目标机器代码        |
| 链接  | `.o` + 库等     | 可执行文件 | 将各部分组合起来        |



运行。

这个参数非常常用。

例如：

```bash

```

默认输出文件在 GCC 环境下通常名为：

运行。

所以：

```text

```

于是：

```text

```

最后：


# 3-3 动态链接和静态链接

先不要急着记命令，先看一个实际问题。

假设有：

```c
#include <stdio.h>

int main()
{
    printf("hello\n");
    return 0;
}
```

我们执行：

```bash
gcc test.c -o test
```

程序能够运行。

但是：

```cpp
printf
```

这个函数并不是你在 `test.c` 里面实现的。

那么：

```text
printf 的实现在哪里？
```

答案就是：

> **在库中。**

所以链接阶段实际上是在解决：

```text
我的代码
+
别人已经写好的代码
↓
组合成一个完整程序
```

---

# 1. 什么是“库”？

所谓**库（Library）**，可以先理解成：

> **别人已经编写、编译好的可复用代码集合。**

例如你写：

```c
printf(...)
```

不需要自己实现“如何把字符输出到终端”，因为相关功能已经由系统提供的库实现了。

以后你写 C++：

```cpp
std::string
std::vector
std::cout
```

背后同样会涉及大量已经存在的代码和库。

因此：

```text
你写的代码
    +
库提供的代码
    ↓
链接
    ↓
最终程序
```

---

# 2. 静态链接

先看最直观的一种方式：

> **静态链接。**

它的核心思想是：

> **链接时，把需要的库代码直接复制/合并进最终的可执行文件。**

可以画成：

```text
你的代码
   +
库
   ↓
静态链接
   ↓
可执行文件
```

例如概念上：

```text
test.o
  +
libxxx.a
  ↓
test
```

最后得到的 `test` 自己就包含了链接进来的库代码。

所以：

```text
程序运行
 ↓
直接使用可执行文件中已经包含的相关代码
```

---

# 3. 动态链接

动态链接采用另一种思想。

它不是把所有库代码都塞进你的程序，而是：

> **程序运行时，与共享库建立联系，使用已经存在的库。**

可以理解成：

```text
你的程序
    ↓
需要某个库
    ↓
运行时加载 / 使用共享库
    ↓
执行库中的代码
```

例如：

```text
test
 ↓
依赖
 ↓
libxxx.so
```

所以：

```text
静态链接：

test
└── 已经包含相关库代码

动态链接：

test
└── 依赖外部共享库
```

这就是两者最核心的区别。

---

# 4. 为什么需要动态链接？

想象一下：

```text
程序 A → 使用 libc
程序 B → 使用 libc
程序 C → 使用 libc
程序 D → 使用 libc
```

如果全部采用静态链接：

```text
A → 自己带一份 libc 代码
B → 自己带一份 libc 代码
C → 自己带一份 libc 代码
D → 自己带一份 libc 代码
```

这样会产生大量重复。

而动态链接可以变成：

```text
A ─┐
B ─┤
C ─┼──→ 共同使用共享库
D ─┘
```

于是多个程序可以共享同一份库。

这也是动态链接非常重要的原因之一。

---

# 5. 静态链接与动态链接对比

| 对比项          | 静态链接       | 动态链接                   |
| ------------ | ---------- | ---------------------- |
| 库代码放在哪里      | 通常进入可执行文件  | 保留在共享库中                |
| 最终程序体积       | 通常较大       | 通常较小                   |
| 运行时是否依赖对应共享库 | 通常不依赖对应动态库 | 依赖                     |
| 多个程序共享同一库    | 较弱         | 较方便                    |
| 库更新          | 通常需要重新链接程序 | 某些情况下无需重新链接程序即可使用更新后的库 |
| 部署           | 文件可能更自包含   | 需要正确提供共享库及其运行时环境       |

注意这里有个非常重要的限定：

> **“静态链接后不需要任何外部依赖”不能绝对化。**

一个程序即使使用了静态链接，依然可能依赖其他运行时资源、设备、配置文件等。我们这里说的是**对应被静态链接进去的库代码不再要求运行时提供那份共享库**。

---

# 6. 一个重要问题：动态库更新后，程序会怎样？

假设：

```text
程序 A
 ↓
libxxx.so
```

现在系统把：

```text
libxxx.so
```

更新了。

对于动态链接程序：

```text
A
 ↓
运行时使用新的共享库
```

因此：

> **共享库可以被多个程序共同使用，库本身升级后可能让多个程序直接使用新的实现。**

这既是优点，也是风险。

因为：

```text
新库
 ↓
可能与旧程序兼容
```

也可能：

```text
新库
 ↓
发生 ABI 不兼容
 ↓
旧程序出现问题
```

所以共享库不是简单的“更新一下所有程序都更好”。

---

# 7. 怎么看一个程序依赖哪些动态库？

Linux 上非常实用的命令：

```bash
ldd test
```

它可以查看一个动态链接程序所依赖的共享库。

例如可能看到：

```text
linux-vdso.so.1
libc.so.6
/lib64/ld-linux-x86-64.so.2
...
```

你现在重点理解：

```text
ldd test
```

就是：

> **查看 `test` 运行时需要哪些共享库。**

这个命令以后排查：

```text
程序运行时报找不到 .so
```

时非常有用。

# 3-4 静态库和动态库

现在进一步回答：

> **静态链接和动态链接用的库，到底长什么样？**

这就是：

```text
静态库
动态库
```

---

# 1. 静态库：`.a`

Linux 中静态库通常使用：

```text
libxxx.a
```

例如：

```text
libhello.a
libmylib.a
```

这里有一个命名习惯：

```text
lib
 +
库名字
 +
.a
```

例如：

```text
libhello.a
```

通常可以理解为：

```text
lib
 ↓
前缀

hello
 ↓
库名

.a
 ↓
静态库
```

---

# 2. 动态库：`.so`

Linux 中共享库通常使用：

```text
libxxx.so
```

例如：

```text
libhello.so
```

其中：

```text
.so
```

就是共享库常见后缀。

所以先记：

```text
.a → 静态库
.so → 动态库
```

---

# 3. 为什么叫 `libxxx`？

这是 Linux/Unix 生态中非常常见的命名约定。

例如：

```text
libtest.a
libtest.so
```

库的逻辑名字都是：

```text
test
```

于是 GCC 链接时常常可以使用：

```bash
-ltest
```

注意：

```text
-ltest
```

不是：

```text
libtest
```

也不是：

```text
libtest.a
```

而是：

```text
-l + 库名
```

因此：

```text
-ltest
```

通常对应去寻找类似：

```text
libtest.so
libtest.a
```

这样的库文件。

这点非常重要。

---

# 4. 自己制作一个静态库

现在我们自己做一个非常简单的库。

先有：

```text
add.h
add.c
```

### `add.h`

```c
#ifndef ADD_H
#define ADD_H

int Add(int x, int y);

#endif
```

### `add.c`

```c
int Add(int x, int y)
{
    return x + y;
}
```

然后编译：

```bash
gcc -c add.c -o add.o
```

得到：

```text
add.o
```

现在把目标文件打包成静态库：

```bash
ar -rc libadd.a add.o
```

得到：

```text
libadd.a
```

这里：

```text
ar
```

是处理归档文件的工具。

静态库本质上可以理解为：

```text
多个 .o
   ↓
打包
   ↓
.a
```

所以：

```text
add.c
 ↓
add.o
 ↓
libadd.a
```

---

# 5. 使用自己制作的静态库

再写：

```c
#include "add.h"
#include <stdio.h>

int main()
{
    printf("%d\n", Add(10, 20));
    return 0;
}
```

假设文件叫：

```text
main.c
```

编译：

```bash
gcc main.c -L. -ladd -o main
```

这条命令很值得拆解。

```text
gcc main.c -L. -ladd -o main
```

### `main.c`

我们的源代码。

### `-L.`

告诉链接器：

> **额外去当前目录寻找库。**

其中：

```text
-L
```

表示添加库搜索路径。

而：

```text
.
```

代表当前目录。

所以：

```text
-L.
```

就是：

> 当前目录也作为库搜索目录。

---

### `-ladd`

表示：

> 链接名为 `add` 的库。

GCC 会按照库命名规则寻找类似：

```text
libadd.a
libadd.so
```

这样的文件。

---

### `-o main`

表示输出：

```text
main
```

---

# 6. `-L` 和 `-l` 一定要区分

这是以后写 Makefile 时非常重要的一组知识。

```text
-L路径
```

解决：

> **去哪里找库？**

而：

```text
-l库名
```

解决：

> **我要链接哪个库？**

例如：

```bash
gcc main.c -L./lib -ladd -o main
```

可以理解成：

```text
-L./lib
 ↓
去 ./lib 目录找

-ladd
 ↓
找 add 这个库
```

最终可能找到：

```text
./lib/libadd.a
```

或者：

```text
./lib/libadd.so
```

---

# 7. 自己制作动态库

现在改成动态库。

还是：

```text
add.c
```

首先：

```bash
gcc -fPIC -c add.c -o add.o
```

然后：

```bash
gcc -shared add.o -o libadd.so
```

最终得到：

```text
libadd.so
```

这里多了一个：

```text
-fPIC
```

它表示生成与位置无关的代码：

> **Position Independent Code**

动态库通常需要采用适合共享加载的代码形式，因此构建共享库时通常会使用 PIC。

然后：

```text
add.c
 ↓
add.o
 ↓
libadd.so
```

---

# 8. 使用动态库

编译：

```bash
gcc main.c -L. -ladd -o main
```

和前面的命令看起来完全一样。

这其实非常有意思：

```text
main.c
 ↓
-L. -ladd
 ↓
链接器根据可用库选择对应库
```

但是运行时可能遇到：

```text
error while loading shared libraries:
libadd.so: cannot open shared object file
```

为什么？

因为：

```text
main
 ↓
运行时需要
 ↓
libadd.so
```

但 Linux 的动态加载器没有在它的搜索路径中找到这个库。

---

# 9. 为什么 `-L` 能编译，运行时却可能找不到？

这是非常重要的区别。

```text
-L
```

是：

> **链接阶段告诉链接器去哪里找库。**

它并不等于：

> **运行阶段告诉系统去哪里找共享库。**

所以：

```text
编译阶段
 ↓
-L.
 ↓
找到 libadd.so
 ↓
链接成功
```

但运行阶段：

```text
./main
 ↓
动态加载器
 ↓
寻找 libadd.so
 ↓
没找到
 ↓
运行失败
```

这就是很多初学者第一次制作 `.so` 时最容易碰到的问题。

---

# 10. 临时解决运行时动态库搜索

可以使用：

```bash
export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH
```

然后：

```bash
./main
```

这里：

```text
LD_LIBRARY_PATH
```

是一个用于指定动态库搜索目录的环境变量。

当前目录：

```text
.
```

被加入以后，动态加载器就能在当前目录找到：

```text
libadd.so
```

于是程序可以运行。

但是生产环境通常不会简单地长期依赖这种做法，后面学习 Linux 动态库管理时再深入。

---

# 11. `.a` 和 `.so` 最核心的区别

可以把整个关系记成：

```text
静态库
libxxx.a
   ↓
静态链接
   ↓
代码进入可执行文件
```

而：

```text
动态库
libxxx.so
   ↓
动态链接
   ↓
程序运行时依赖共享库
```

---

# 12. 静态库和动态库的对比

| 对比         | 静态库 `.a`  | 动态库 `.so`          |
| ---------- | --------- | ------------------ |
| 链接方式       | 静态链接      | 动态链接               |
| 库代码        | 通常进入可执行文件 | 通常留在共享库中           |
| 可执行文件      | 通常更大      | 通常更小               |
| 运行时依赖对应共享库 | 不需要       | 需要                 |
| 多个程序共享库    | 不方便       | 很方便                |
| 更新库        | 通常要重新链接程序 | 在兼容条件下可直接使用新库      |
| 常见场景       | 某些独立部署场景  | Linux 系统和大型项目中广泛使用 |

---

# 13. 一个非常容易混淆的地方

很多人会认为：

```text
.a = 编译
.so = 运行
```

这是不准确的。

正确理解是：

```text
.a 和 .so
↓
都是库
```

而：

```text
静态链接 / 动态链接
↓
描述的是“程序如何使用这些库”
```

所以：

```text
库的类型
   ↓
.a / .so

链接方式
   ↓
静态链接 / 动态链接
```

虽然两者经常对应，但不要把“文件后缀”和“链接过程”机械地画成完全相同的概念。

# 4. 自动化构建 —— make / Makefile

上一节我们已经知道，程序从源代码到可执行文件，大致经历：

```text id="4d4x0x"
.c
 ↓
预处理
 ↓
编译
 ↓
汇编
 ↓
.o
 ↓
链接
 ↓
可执行程序
```

当项目只有一个 `test.c` 时：

```bash id="x8x97q"
gcc test.c -o test
```

完全没问题。

但是项目一旦变大，例如：

```text id="p2b3nf"
main.c
add.c
sub.c
print.c
test.c
...
```

你每次都手动：

```bash id="w3k5g1"
gcc -c main.c
gcc -c add.c
gcc -c sub.c
gcc -c print.c
...
gcc main.o add.o sub.o print.o -o test
```

就会非常麻烦。

更麻烦的是：

> **如果只修改了 `add.c`，其实没有必要重新编译 `main.c`、`sub.c`、`print.c`。**

这就是 `make` 要解决的问题。

---

# 4-1 背景

## 1. 什么叫“构建”？

这里的“构建（Build）”不要简单理解成“编译”。

一个项目的构建可能包含：

```text id="trzpl0"
检查依赖
 ↓
编译源文件
 ↓
生成目标文件
 ↓
链接
 ↓
生成可执行程序
```

甚至还可能包括：

```text id="q3u8bp"
复制资源
生成代码
运行测试
清理中间文件
安装程序
```

所以：

> **编译是构建的一部分。**

而 `make` 就是一个**自动化构建工具**。

---

# 4-2 理解

## 1. make 最核心的思想

先看一个最简单的项目：

```text id="v6jkqz"
main.c
add.c
sub.c
```

它可能对应：

```text id="e6y8i0"
main.c → main.o
add.c  → add.o
sub.c  → sub.o
```

最后：

```text id="t6nm63"
main.o
add.o
sub.o
   ↓
链接
   ↓
test
```

所以整个项目其实存在一个**依赖关系**：

```text id="78l86i"
             test
            / | \
           /  |  \
          ↓   ↓   ↓
      main.o add.o sub.o
        ↓      ↓     ↓
      main.c  add.c  sub.c
```

这就是 Makefile 最核心的东西：

> **告诉 make：目标依赖哪些东西，以及目标应该如何生成。**

---

# 1. Makefile 是什么？

`Makefile` 可以简单理解成：

> **描述项目构建规则的文件。**

例如：

```makefile id="zfc4is"
test: main.o add.o sub.o
	gcc main.o add.o sub.o -o test

main.o: main.c
	gcc -c main.c -o main.o

add.o: add.c
	gcc -c add.c -o add.o

sub.o: sub.c
	gcc -c sub.c -o sub.o
```

这里就把整个构建过程告诉了 `make`。

---

# 2. Makefile 的基本格式

最重要的语法：

```makefile id="tjv7hd"
目标: 依赖
	命令
```

例如：

```makefile id="e7c1up"
test: main.o add.o
	gcc main.o add.o -o test
```

拆开：

```text id="uvx0zo"
test
 ↓
目标

main.o add.o
 ↓
依赖

gcc main.o add.o -o test
 ↓
生成目标所需要执行的命令
```

所以：

```text id="1cs1eg"
目标 : 依赖
        ↓
      命令
```

这是 Makefile 最基本的骨架。

---

# 3. 一个非常重要的格式要求：命令前面通常是 Tab

例如：

```makefile id="wdjts0"
test: main.o
	gcc main.o -o test
```

`gcc` 前面的缩进是：

```text id="nhr5qs"
Tab
```

不是普通空格。

这是 Makefile 初学时非常经典的错误。

如果写成：

```makefile id="z2r5s0"
test: main.o
    gcc main.o -o test
```

某些情况下会出现：

```text id="m8wh2e"
*** missing separator
```

所以记住：

> **Makefile 的配方（recipe）行，传统写法要求以 Tab 开头。**

---

# 4-3 基本使用

## 1. 最基本的 `make`

当当前目录存在：

```text id="l2lqy4"
Makefile
```

直接：

```bash id="8j5d3a"
make
```

make 会读取：

```text id="2id2yk"
Makefile
```

然后寻找默认目标并尝试把它构建出来。

---

# 2. 什么是默认目标？

例如：

```makefile id="j3p8eq"
test: main.o add.o
	gcc main.o add.o -o test

main.o: main.c
	gcc -c main.c -o main.o
```

执行：

```bash id="4wpu8j"
make
```

make 默认会从 Makefile 中的**第一个目标**开始处理。

所以这里：

```text id="6qs9gw"
test
```

就是默认目标。

---

# 3. 指定目标

也可以：

```bash id="vskkqf"
make test
```

意思：

> 构建 `test` 这个目标。

如果 Makefile 中有：

```makefile id="qf52sh"
test:
	...
clean:
	...
```

那么：

```bash id="cg2nyv"
make clean
```

就是执行 `clean` 目标。

这也是 Linux 项目中非常常见的：

```bash id="a38yqy"
make
make clean
```

---

# 4. `clean` 是干什么的？

通常会在 Makefile 里面写：

```makefile id="8x7r5h"
clean:
	rm -f *.o test
```

然后：

```bash id="k5th7y"
make clean
```

就可以清理：

```text id="zto8zv"
main.o
add.o
sub.o
test
```

这里有一个很重要的认识：

```text id="y7y54r"
clean
```

本身通常并不是一个“要生成的文件”。

它更像一个：

> **伪目标（phony target）**

正式项目里通常会写：

```makefile id="8d1n4c"
.PHONY: clean

clean:
	rm -f *.o test
```

这样更严谨。

这里先建立认知：

```text id="69jz47"
make clean
↓
执行清理命令
```

而不是：

```text id="5o7kkp"
生成一个叫 clean 的文件
```

---

# 5. make 为什么知道“要不要重新编译”？

这是 `make` 最核心、最值得理解的地方。

它会利用**文件时间戳（修改时间）**判断依赖关系是否发生变化。

例如：

```text id="2l6rrf"
main.c
 ↓
main.o
```

假设：

```text id="w6m3ti"
main.c 修改时间：15:00
main.o 修改时间：15:05
```

那么：

```text id="jrv0t0"
main.o 比 main.c 新
```

说明：

```text id="w4j8yo"
main.o
```

很可能已经是根据当前的：

```text id="8t44fu"
main.c
```

生成的。

所以不需要重新编译。

---

## 6. 如果修改了 `main.c`

现在：

```text id="wwac47"
main.c：15:10
main.o：15:05
```

那么：

```text id="x9yusm"
main.c 比 main.o 新
```

意味着：

> `main.o` 依赖的源文件已经更新。

于是 make 会：

```text id="57c9z8"
重新生成 main.o
```

如果最终程序：

```text id="fqa8s5"
test
```

又依赖：

```text id="6z6jjx"
main.o
```

那么 `test` 也需要重新链接。

因此：

```text id="86t5al"
main.c 修改
 ↓
main.o 过期
 ↓
重新生成 main.o
 ↓
test 依赖的 main.o 变化
 ↓
重新链接 test
```

这就是 make 的核心机制。

---

# 7. `touch` 为什么在课堂中经常出现？

你板书里面有通过终端操作文件时间的内容，这其实是在演示 make 的这个机制。

例如：

```bash id="hkzy9h"
touch main.c
```

`touch` 会更新文件的时间信息（在文件存在的情况下，默认更新访问/修改时间；这里我们最关心的是修改时间）。

于是：

```text id="psjy5j"
main.c
```

的修改时间变新了。

再：

```bash id="0t7l2x"
make
```

make 发现：

```text id="1gl3j7"
main.c
   ↓
比 main.o 新
```

于是：

```text id="c0cgsi"
重新编译 main.c
```

所以课堂里使用 `touch` 不是为了“创建一个空文件”这么简单，而是在**人为制造文件发生变化的条件，用来观察 make 的增量构建机制**。

这一点非常值得理解。

---

# 8. 如果目标文件不存在呢？

假设：

```text id="b3l6v3"
main.c
```

存在，但是：

```text id="9n8f0g"
main.o
```

根本不存在。

Makefile：

```makefile id="v7qx7z"
main.o: main.c
	gcc -c main.c -o main.o
```

make 会发现：

```text id="8q6p4m"
目标 main.o 不存在
```

那么当然必须执行：

```text id="0u23xq"
gcc -c main.c -o main.o
```

所以判断可以简单理解成：

```text id="1z08vk"
目标不存在
   ↓
必须生成

目标存在
   ↓
比较目标和依赖的时间戳
   ↓
依赖更新得更晚
   ↓
重新生成
```

这就是 make 最基础的判断逻辑。

---

# 9. 依赖关系是递归处理的

这是 make 很重要的一个特点。

例如：

```makefile id="7g1zuw"
test: main.o add.o
	gcc main.o add.o -o test

main.o: main.c
	gcc -c main.c -o main.o

add.o: add.c
	gcc -c add.c -o add.o
```

执行：

```bash id="3s7yuz"
make
```

make 不是机械地看到：

```text
test
```

马上执行：

```bash id="sv9ol1"
gcc main.o add.o -o test
```

它会先问：

```text id="r48xq8"
test 依赖什么？
```

得到：

```text id="2v3q9x"
main.o
add.o
```

然后继续：

```text id="cbozwk"
main.o 依赖什么？
↓
main.c
```

再判断：

```text id="hm8y0q"
main.o 是否需要重新生成？
```

然后再处理：

```text id="g4ql3h"
add.o
```

最后才：

```text id="6w4v73"
gcc main.o add.o -o test
```

所以：

> **make 会沿着依赖关系递归向下检查，然后从底层依赖开始构建。**

---

# 10. 这个过程和一棵树很像

例如：

```text id="a93zz5"
              test
             /    \
            /      \
        main.o     add.o
          |          |
        main.c      add.c
```

make 相当于：

```text id="nft5wu"
先检查叶子节点
       ↓
需要更新的先更新
       ↓
再向上
       ↓
最终生成 test
```

这就是为什么 Makefile 里的“依赖关系”非常重要。

# 4-4 推导过程

现在我们从手动编译开始，一步一步推导出 Makefile。

## 第一阶段：完全手动

```bash id="3xg5wj"
gcc -c main.c
gcc -c add.c
gcc main.o add.o -o test
```

问题：

```text id="j8x4bc"
命令很多
容易忘
修改一个文件之后还要自己判断重新编译哪些
```

---

## 第二阶段：写一个脚本

例如：

```bash id="2u8xqe"
build.sh
```

里面：

```bash id="gdiqax"
gcc -c main.c
gcc -c add.c
gcc main.o add.o -o test
```

可以自动执行。

但还有问题：

> **它每次都会全部重新执行。**

修改：

```text id="o0f7gm"
main.c
```

其实只需要：

```text id="s3h274"
重新生成 main.o
↓
重新链接
```

却把 `add.c` 也重新编译了。

---

## 第三阶段：引入依赖关系

我们告诉系统：

```text id="j1imx1"
test 依赖 main.o add.o

main.o 依赖 main.c

add.o 依赖 add.c
```

于是形成：

```text id="b4f5jz"
              test
             /    \
        main.o     add.o
           |         |
        main.c     add.c
```

再让系统根据时间戳判断：

```text id="sgy5h1"
哪些东西已经过期？
```

这就是：

> **make 的核心思想。**

所以 Makefile 并不只是“把几条 gcc 命令写到一个文件里”。

真正重要的是：

```text id="hi4f1g"
目标
+
依赖关系
+
生成方法
+
时间戳判断
```

# 4-5 适度扩展语法

这一部分不需要深入到复杂 Makefile，但几个非常实用的语法要认识。

---

# 1. 使用变量

例如：

```makefile id="8vnrxy"
CC = gcc
CFLAGS = -Wall -g

test: main.o add.o
	$(CC) $(CFLAGS) main.o add.o -o test

main.o: main.c
	$(CC) $(CFLAGS) -c main.c -o main.o

add.o: add.c
	$(CC) $(CFLAGS) -c add.c -o add.o
```

这里：

```text id="8ycf1k"
CC
```

代表编译器。

```text id="xs6kha"
CFLAGS
```

表示编译选项。

而：

```text id="c4kk8n"
$(CC)
```

就是取出变量 `CC` 的值。

这样做的好处是：

```text id="e3j99i"
原来很多地方写 gcc
        ↓
现在统一写 $(CC)
```

以后想换编译器，只改：

```makefile id="3rsc5j"
CC = gcc
```

这一处即可。

---

# 2. 自动变量：`$@`、`$^`、`$<`

这个属于 Makefile 非常重要的实用语法。

例如：

```makefile id="qb6k79"
test: main.o add.o
	gcc main.o add.o -o test
```

可以写成：

```makefile id="ptxv1h"
test: main.o add.o
	gcc $^ -o $@
```

这里：

```text id="g97v1x"
$@
```

表示：

> 当前规则的目标。

所以：

```text
$@ = test
```

而：

```text id="4w0sc5"
$^
```

表示：

> 当前规则的所有依赖。

所以：

```text
$^ = main.o add.o
```

于是：

```bash id="mm8k5o"
gcc $^ -o $@
```

实际就相当于：

```bash id="j54ofv"
gcc main.o add.o -o test
```

再看：

```makefile id="b1p2x0"
main.o: main.c
	gcc -c $< -o $@
```

这里：

```text id="5cylcc"
$<
```

表示：

> 当前规则的第一个依赖。

所以：

```text id="u07myu"
$< = main.c
$@ = main.o
```

于是最终：

```bash id="p6s0mz"
gcc -c main.c -o main.o
```

---

# 3. 三个自动变量先记住

| 自动变量 | 含义    |
| ---- | ----- |
| `$@` | 当前目标  |
| `$^` | 所有依赖  |
| `$<` | 第一个依赖 |

这个以后写 Makefile 会非常常见。

---

# 4. 一个比较完整的小型 Makefile

现在把前面的知识组合起来：

```makefile id="m8h3t4"
CC = gcc
CFLAGS = -Wall -g

test: main.o add.o
	$(CC) $(CFLAGS) $^ -o $@

main.o: main.c
	$(CC) $(CFLAGS) -c $< -o $@

add.o: add.c
	$(CC) $(CFLAGS) -c $< -o $@

.PHONY: clean
clean:
	rm -f *.o test
```

这个 Makefile 已经很接近真实项目里的基本形式。

构建：

```bash id="is6ehy"
make
```

清理：

```bash id="eqpggl"
make clean
```

当你修改：

```bash id="h1u8yz"
main.c
```

然后：

```bash id="z7drki"
make
```

make 不需要重新编译 `add.c`。

这就是所谓的：

> **增量构建（Incremental Build）**

---

# 5. 为什么大型项目一定需要这种机制？

假设一个大型 C++ 项目：

```text id="zq8ak3"
1000 个源文件
```

修改：

```text id="b8h8w1"
A.cpp
```

如果每次都：

```text id="d1im9c"
1000 个文件全部重新编译
```

会非常浪费时间。

而 make 的思路是：

```text id="u91hqu"
A.cpp 修改
 ↓
找到依赖 A.o 的目标
 ↓
只重新构建受影响部分
 ↓
最后重新链接需要更新的目标
```

因此：

> **Makefile 的真正价值不是少敲几条命令，而是描述依赖关系并实现自动化、增量构建。**

---

# 6. 一个非常重要的易错点：依赖关系不能乱写

例如：

```makefile id="do81eq"
test: main.o
	gcc main.o -o test
```

如果实际上：

```text id="cgjmja"
test
```

还依赖：

```text id="add.o"
```

却没有写：

```makefile id="pjxwzo"
test: main.o add.o
```

那么 make 根本不知道：

```text
test
```

依赖 `add.o`。

因此：

> **Makefile 中的依赖关系不是装饰，而是 make 判断“什么时候需要重新构建”的依据。**

---

# 7. `.c` 修改了，`.h` 修改怎么办？

这个问题非常重要，而且是后面真正写项目时经常出现的。

例如：

```text id="b7gej9"
main.c
main.h
```

`main.c`：

```c
#include "main.h"
```

那么：

```text id="g8gk46"
main.o
```

实际上不仅依赖：

```text id="4v2i8u"
main.c
```

还依赖：

```text id="y5ixzw"
main.h
```

因此更加合理的写法是：

```makefile id="sp5m4q"
main.o: main.c main.h
	gcc -c main.c -o main.o
```

这样：

```text id="l4fh3v"
main.h 修改
 ↓
main.o 的依赖发生变化
 ↓
重新生成 main.o
```

这就是 Makefile 依赖关系真正有价值的地方。

当然，真实项目通常不会要求程序员手工维护所有头文件依赖，GCC 还有自动生成依赖信息等机制；这个属于后续可以进一步学习的内容。

---

# 8. 现在把 `make` 和 GCC 完整联系起来

你已经学过 GCC 的：

```text id="3xk85k"
.c
 ↓
.i
 ↓
.s
 ↓
.o
 ↓
可执行文件
```

现在 `make` 站在更高一层：

```text id="vzjiwm"
                Make
                 ↓
        管理整个构建过程
                 ↓
    ┌────────────┼────────────┐
    ↓            ↓            ↓
 main.c       add.c        sub.c
    ↓            ↓            ↓
 main.o       add.o        sub.o
    └────────────┼────────────┘
                 ↓
               link
                 ↓
              test
```

因此：

```text id="knj8i9"
gcc/g++
```

负责：

> **实际完成编译、汇编、链接。**

而：

```text id="wxdi7o"
make
```

负责：

> **决定什么时候调用这些编译命令，以及调用它们的顺序。**

这是非常重要的分工。

---

# 9. 一句话区分 gcc 和 make

```text id="o9zsu3"
gcc/g++
→ “怎么编译？”

make
→ “什么时候编译谁，以及按照什么依赖关系构建？”
```

例如：

```text id="fu1w0n"
gcc main.c -o main
```

是在真正执行编译。

而：

```bash id="t6p2m5"
make
```

是在根据 Makefile 的规则决定：

```text
哪些文件需要编译
哪些文件不需要编译
先编译谁
最后怎么链接
```

这就是两者的本质区别。

项目变大后：

```text
源文件多
 ↓
编译命令多
 ↓
依赖关系复杂
 ↓
每次全部重新编译很浪费
```

所以需要：

```text
make
```

自动管理构建过程。

```makefile

```

本质上描述：

```text
目标如何生成
+
目标依赖什么
```

核心依据是：

```text
目标不存在
      ↓
重新构建

目标存在
      ↓
比较目标与依赖的修改时间
      ↓
依赖比目标新
      ↓
重新构建

目标比依赖新
      ↓
通常不需要重新构建
```

课堂中的：

```bash
touch xxx
```

就是很典型的演示方法，用来改变文件时间，从而观察 make 的增量构建。

### 4. make 的执行具有递归性

```text

 ↓

 ↓
main.c
```

make 会从依赖往上检查和构建，而不是简单地把 Makefile 从上到下机械执行。

# 5-1 补充——回车与换行

这个知识非常重要，而且初学 Linux 时很容易混。

## 1. `\n` 是什么？

在 C/C++ 字符串里：

```c
"\n"
```

表示一个**换行字符（Line Feed，LF）**，字符值通常是：

```text
0x0A
```

例如：

```c
printf("hello\n");
printf("world\n");
```

终端显示：

```text
hello
world
```

我们平时把 `\n` 直接叫“换行”，基本没问题。

---

# 2. `\r` 是什么？

```c
"\r"
```

表示：

> **回车（Carriage Return，CR）**

通常是：

```text
0x0D
```

它和 `\n` 的概念不同。

在终端中，可以先这样理解：

```text
\r
↓
光标回到当前行的行首
```

而：

```text
\n
↓
移动到下一行
```

所以：

```text
\r
```

主要解决：

> **“回到这一行的开头。”**

而：

```text
\n
```

主要解决：

> **“进入下一行。”**

---

# 3. 为什么“回车”和“换行”要分开？

这个其实来自早期终端/打印机的设计。

传统机械打字设备需要两个动作：

```text
Carriage Return
↓
让打印头回到这一行开头

Line Feed
↓
让纸张向下移动一行
```

因此：

```text
\r
```

和：

```text
\n
```

历史上就是两个不同的控制动作。

现代 Linux 终端依然保留了这种控制字符语义。

---

# 4. 直接演示 `\r`

看：

```c
#include <stdio.h>

int main()
{
    printf("hello\rworld");
    return 0;
}
```

你不能简单地理解成：

```text
hello
world
```

而应该理解成：

```text
先输出：

hello
↑
光标在这一行末尾

然后：

\r
↓
光标回到行首

再输出：

world
```

最终终端上可能看到：

```text
world
```

因为后面的 `world` 把之前的 `hello` 覆盖掉了。

---

# 5. `\r` 为什么是进度条的核心？

假设现在输出：

```text
[----------] 0%
```

下一秒：

```text
[##--------] 20%
```

再下一秒：

```text
[####------] 40%
```

我们当然可以每次都：

```text
printf("[----------] 0%%\n");
printf("[##--------] 20%%\n");
printf("[####------] 40%%\n");
```

但是这样终端会：

```text
[----------] 0%
[##--------] 20%
[####------] 40%
...
```

越来越长。

进度条更希望：

```text
同一行不断变化
```

这时候：

```c
printf("\r[##--------] 20%%");
```

就很有用了。

因为：

```text
\r
↓
回到当前行行首
↓
重新输出新的进度条
```

于是视觉上就变成：

```text
[----------] 0%
        ↓
[##--------] 20%
        ↓
[####------] 40%
        ↓
[######----] 60%
```

但实际上一直都是**同一行**。

---

# 5-2 行缓冲区

这里是本节真正的原理重点。

为什么有时候：

```c
printf("\rhello");
```

你却发现：

> “怎么终端没有立即显示？”

甚至进度条代码明明一直在循环，屏幕却不动。

这就涉及：

> **stdout 的缓冲。**

---

# 1. 什么是缓冲区？

简单理解：

> **程序输出的数据，不一定每次调用 `printf` 都立刻交给终端设备。**

中间可能存在：

```text
程序
 ↓
stdout 缓冲区
 ↓
终端
```

也就是：

```text
printf(...)
   ↓
先进入缓冲区
   ↓
满足某些条件
   ↓
再真正写出去
```

为什么要这么做？

因为频繁地：

```text
程序
 ↓
系统调用
 ↓
设备
```

开销比较大。

先积攒一部分数据，再统一输出，通常更加高效。

---

# 2. stdout 是什么？

我们前面已经学过 Linux 的：

> **一切皆文件**

这里可以进一步联系起来。

C 标准库给我们提供了：

```c
stdin
stdout
stderr
```

分别对应：

```text
stdin
 ↓
标准输入

stdout
 ↓
标准输出

stderr
 ↓
标准错误
```

最常用的：

```c
printf(...)
```

默认就是输出到：

```text
stdout
```

所以：

```c
printf("hello");
```

可以理解成：

```text
printf
 ↓
stdout
 ↓
终端
```

当然，中间还存在 C 标准 I/O 的缓冲机制。

---

# 3. 什么叫“行缓冲”？

当 `stdout` 连接到终端时，通常采用的是：

> **行缓冲（line buffering）**

它的一个重要表现是：

```c
printf("hello\n");
```

因为出现了换行，通常会触发缓冲区刷新。

而：

```c
printf("hello");
```

因为没有换行，就可能暂时留在缓冲区里。

因此：

```text
有 \n
 ↓
通常更容易立即看到

没有 \n
 ↓
可能继续留在缓冲区
```

注意这里必须严谨一点：

> **不能简单地把“有 `\n` 就一定立刻显示”当成所有环境下的绝对规则。**
> stdout 的缓冲模式与其连接对象、运行环境以及程序设置有关。我们在终端交互场景下通常遇到的是行缓冲。

---

# 4. `\r` 会不会刷新缓冲区？

不会。

这是一个非常重要的易错点：

```text
\r
```

只是一个：

> **回车字符**

它本身并不等于：

> “刷新 stdout 缓冲区”。

所以：

```c
printf("\rhello");
```

即使包含：

```text
\r
```

也不代表 `hello` 一定马上显示。

这就是为什么进度条通常还要：

```c
fflush(stdout);
```

---

# 5. `fflush(stdout)`

例如：

```c
printf("\rhello");
fflush(stdout);
```

其中：

```c
fflush(stdout);
```

表示：

> **刷新 stdout 的输出缓冲区。**

于是：

```text
printf
 ↓
数据进入 stdout 缓冲区
 ↓
fflush(stdout)
 ↓
把缓冲区内容尽快交给实际输出设备
```

这就是动态进度条能够正常刷新的关键。

# 6. 最小演示

先看：

```c
#include <stdio.h>
#include <unistd.h>

int main()
{
    printf("hello");
    sleep(3);

    return 0;
}
```

在典型终端环境中，你可能会发现：

```text
运行程序
 ↓
不一定马上看到 hello
 ↓
等待一段时间
 ↓
程序结束/缓冲刷新
 ↓
才显示
```

改成：

```c
#include <stdio.h>
#include <unistd.h>

int main()
{
    printf("hello");
    fflush(stdout);

    sleep(3);

    return 0;
}
```

这时候：

```text
printf
 ↓
fflush
 ↓
立即刷新
 ↓
hello 出现
 ↓
继续 sleep
```

这个实验非常值得你自己在 Linux 上跑一次。

# 5-3 练手——倒计时程序

有了：

```text
\r
+
fflush(stdout)
+
sleep
```

我们已经可以写出第一个有动态效果的小程序。

---

## 1. 最简单的倒计时

```c
#include <stdio.h>
#include <unistd.h>

int main()
{
    for (int i = 10; i >= 0; --i)
    {
        printf("%2d\r", i);
        fflush(stdout);
        sleep(1);
    }

    printf("\n");

    return 0;
}
```

运行：

```text
10
 9
 8
 7
...
 0
```

但注意：

> **实际上这些数字并不是一行一行打印出来的。**

而是：

```text
10
↓
\r
↓
回到行首
↓
9
↓
\r
↓
回到行首
```

所以视觉效果上是：

```text
10
 ↓
9
 ↓
8
 ↓
...
```

本质上是**同一行不断被重新绘制**。

---

# 2. 为什么这里写 `%2d`？

代码：

```c
printf("%2d\r", i);
```

这里：

```text
%2d
```

表示：

> 至少占两个字符宽度。

因此：

```text
10
 9
 8
 7
```

这样宽度一致。

如果直接：

```c
printf("%d\r", i);
```

也能工作，但输出字符宽度会发生变化。

---

# 3. 为什么最后要 `printf("\n")`？

因为循环结束后：

```text
\r
```

只是回到当前行开头。

如果程序最后停在那里：

```text
0
```

终端后续的提示符可能和 `0` 挤在一起。

所以最后：

```c
printf("\n");
```

让终端：

```text
当前行
 ↓
下一行
```

这样 shell 提示符就会出现在下一行。

---

# 4. `sleep(1)` 是什么？

需要：

```c
#include <unistd.h>
```

然后：

```c
sleep(1);
```

表示：

> **让当前进程暂停约 1 秒。**

所以：

```text
printf
 ↓
显示当前数字
 ↓
sleep(1)
 ↓
下一轮
```

这就产生了倒计时的动态效果。

# 5-4 进度条代码

现在进入本节最终目标。

我们先做一个最容易理解的版本。

```c
#include <stdio.h>
#include <unistd.h>

int main()
{
    char bar[101] = {0};

    for (int i = 0; i <= 100; ++i)
    {
        bar[i] = '#';

        printf("\r[%-100s] %3d%%", bar, i);
        fflush(stdout);

        usleep(50000);
    }

    printf("\n");

    return 0;
}
```

运行后，你会看到：

```text
[##################################################------------------]  50%
```

然后不断增长：

```text
[##------------------------------------------------------------------]   2%
[####--------------------------------------------------------------]   4%
[######------------------------------------------------------------]   6%
...
[################################################################] 100%
```

视觉上就是：

```text
一行
 ↓
不断变化
 ↓
最终 100%
```

---

# 1. 为什么使用数组 `bar`？

这里：

```c
char bar[101] = {0};
```

相当于准备了一个字符数组。

我们希望：

```text
i = 0
→ ""

i = 1
→ "#"

i = 2
→ "##"

i = 3
→ "###"
```

所以循环中：

```c
bar[i] = '#';
```

不断增加 `#`。

---

# 2. 为什么数组初始化成 `{0}`？

```c
char bar[101] = {0};
```

意味着数组元素初始为 0，也就是：

```text
'\0'
```

这个字符非常重要。

因为 C 字符串要求：

> **以 `\0` 作为结尾。**

例如：

```text
"abc"
```

内存实际上类似：

```text
a
b
c
\0
```

所以我们的：

```c
bar
```

才能作为：

```c
%s
```

传给 `printf`。

---

# 3. 为什么数组是 `101`？

我们需要：

```text
0% ~ 100%
```

总共：

```text
101
```

个状态。

而：

```c
bar[i] = '#';
```

最后：

```text
i = 100
```

需要能够访问：

```text
bar[100]
```

所以至少需要：

```text
bar[0] ~ bar[100]
```

即：

```text
101 个元素
```

---

# 4. `%3d%%` 是什么？

代码：

```c
printf("\r[%-100s] %3d%%", bar, i);
```

拆开看。

### `%-100s`

```text
-100s
```

表示：

> 一个宽度为 100 的字符串区域，并左对齐。

例如：

```text
##________________________________________________
```

这样即使 `#` 不够多，进度条后面的区域也有固定宽度。

---

### `%3d`

表示：

> 整数至少占 3 个字符。

于是：

```text
  0
  1
 10
100
```

宽度稳定。

---

### `%%`

因为：

```text
%
```

在 `printf` 中是格式控制的特殊符号。

如果想真正输出：

```text
%
```

就需要：

```c
%%
```

因此：

```c
%3d%%
```

意思就是：

```text
%3d
 ↓
输出进度数字

%%
 ↓
输出一个 %
```

最终：

```text
 50%
```

---

# 5. `usleep(50000)` 是什么？

```c
usleep(50000);
```

单位是：

```text
微秒
```

所以：

```text
50000 μs = 0.05 s
```

也就是：

> 暂停 0.05 秒。

因此 0% 到 100%：

```text
101 次 × 0.05 秒
≈ 5 秒
```

进度条大约持续 5 秒。

---

# 6. 为什么这里一定要 `fflush(stdout)`？

把这一句去掉：

```c
fflush(stdout);
```

你可能发现：

> 进度条不再正常实时变化。

原因不是：

```text
\r 写错了
```

而是：

```text
printf
 ↓
stdout 缓冲
 ↓
数据没有及时刷新
```

加上：

```c
fflush(stdout);
```

就变成：

```text
printf
 ↓
stdout
 ↓
fflush
 ↓
立即刷新
 ↓
终端更新
```

因此进度条的核心实际上是：

```text
\r
+
fflush(stdout)
```

---

# 7. 进度条真正的工作原理

整个程序可以抽象成：

```text
        第一次输出
             ↓
    [#-------------------] 1%
             ↓
          \r
             ↓
       回到行首
             ↓
    [##------------------] 2%
             ↓
          \r
             ↓
       回到行首
             ↓
    [###-----------------] 3%
             ↓
           ...
             ↓
          100%
```

注意：

> **它并没有真正删除上一行。**

只是：

```text
\r
```

把光标重新放回行首，然后新的字符覆盖之前的显示。

所以进度条本质上是：

> **重复在同一终端行重新绘制内容。**

# 9. `\n` 和 `\r` 最终一定要分清

这两个建议你直接记成：

| 字符   | 含义    | 终端中的典型效果 |
| ---- | ----- | -------- |
| `\n` | LF，换行 | 移到下一行    |
| `\r` | CR，回车 | 回到当前行行首  |

所以：

```c
printf("hello\n");
```

是：

```text
hello
↓
下一行
```

而：

```c
printf("hello\r");
```

是：

```text
hello
↓
光标回到这一行开头
```

**`"\r"` 不负责“换到下一行”。**

# 11. 一个需要纠正的常见说法

很多教程会直接说：

> “`\n` 就是回车，`\r` 就是换行。”

这是**不严谨甚至是反过来的**。

正确的是：

```text
\r = Carriage Return = 回车
\n = Line Feed       = 换行
```

Windows 文本换行经常使用：

```text
\r\n
```

而 Linux/Unix 文本中通常使用：

```text
\n
```

这也是以后跨平台处理文本时经常遇到的问题。

# 6. 版本控制器 Git

这次开始进入 Git。结合你刚补充的课堂板书，这一章有一个非常重要的主线：

板书里画出的重点也正是这套关系：**本地工作区、暂存区、版本库、远程仓库之间的数据流动**。这一部分一定要理解，后面的 `add / commit / push / pull / clone` 才不会变成死记命令。

---

# 6-1 版本控制器

## 1. 为什么需要版本控制？

先假设你写一个 C++ 项目。

第一天：

```text
project_v1
```

第二天：

```text
project_v2
```

第三天：

```text
project_v3
```

然后某一次修改把程序改坏了。

你想：

> “回到昨天还能运行的版本。”

如果完全靠手工复制：

```text
project
project_old
project_old2
project_final
project_final2
project_really_final
```

最后你自己都不知道：

```text
哪个才是真的最终版？
```

这就是最原始的问题。

---

# 2. 版本控制器是什么？

**版本控制器（Version Control System，VCS）**就是专门帮助我们：

> **记录文件的历史变化，并管理不同版本。**

它能够记录：

```text
什么时候修改
谁修改
修改了什么
之前是什么状态
现在是什么状态
```

因此：

```text
代码
 ↓
版本控制
 ↓
历史版本
```

就形成了一个可追踪的演化过程。

---

# 3. 版本控制最核心的价值

不要把 Git 单纯理解成：

> “把代码上传到 GitHub。”

Git 首先解决的是：

> **版本管理。**

例如：

```text
v1
 ↓
修改
 ↓
v2
 ↓
修改
 ↓
v3
```

如果 `v3` 出现问题：

```text
v3
 ↓
查看历史
 ↓
找到 v2
 ↓
恢复 / 对比
```

所以：

```text
Git ≠ GitHub
```

这一点从现在就要分清。

---

# 4. Git 和 GitHub 到底是什么关系？

这是最常见的概念混淆之一。

| 名称     | 本质                      |
| ------ | ----------------------- |
| Git    | **版本控制工具**              |
| GitHub | **提供 Git 仓库托管等协作服务的平台** |

也就是说：

```text
Git
↓
安装在你的电脑上
↓
管理代码版本
```

而：

```text
GitHub
↓
远程服务器上的代码仓库服务
↓
存放和协作
```

所以完全可以：

```text
不用 GitHub
```

只使用：

```text
Git + 本地仓库
```

反过来，GitHub 上的仓库本质上也是 Git 仓库，只是托管在远程平台。

---

# 6-2 Git 简史

Git 的出现和 Linux 内核开发有直接关系。

Linux 内核是一个规模非常大的开源项目，需要大量开发者共同维护。

早期 Linux 内核的版本管理经历过不同方案。后来为了满足 Linux 内核开发对分布式版本控制的需求，Git 被创建。

Git 最初由 **Linus Torvalds** 在 2005 年启动开发，之后由社区持续维护和发展。

这里真正值得你理解的不是历史细节，而是：

```text
大型开源项目
      ↓
多人协作
      ↓
代码版本越来越复杂
      ↓
需要高效的分布式版本控制
      ↓
Git
```

这也解释了 Git 为什么从设计之初就非常强调：

```text
分布式
效率
完整的历史
分支
合并
```

# 3. `.git` 能不能删除？

```text
.git
```

但这个目录就不再作为原来的 Git 仓库存在。

因此：

> **`.git` 不是你的源码，而是 Git 管理这个项目所需的重要数据。**

# 6-5 三板斧

# 1. 工作区（Working Directory）


你现在直接编辑：

```cpp
int main()
{

```

这些文件就是你正在工作的地方。

这叫：

> **工作区（Working Tree / Working Directory）**

简单理解：

```text

```

就在工作区。

---

# 2. 暂存区（Staging Area）

假设你修改了：

```text
main.cpp
```

此时：

```bash

```

```text
main.cpp
```

发生了变化。

```bash

```

并不是简单地把“所有当前修改”全部记录下来。

你需要先：

```bash

```

于是：

```text

 ↓ git add
暂存区
```

这就是：

> **Staging Area / Index**

---

# 3. 为什么需要暂存区？

这是理解 Git 非常重要的问题。

假设你修改了三个文件：

```text
main.cpp
network.cpp
test.cpp
```

但是这次你只想提交：

```text
main.cpp
network.cpp
```

那么：

```bash
git add main.cpp
git add network.cpp
```

把这两个放入暂存区。

而：

```text
test.cpp
```

先不加入。

然后：

```bash
git commit
```

提交的就是：

```text
main.cpp
network.cpp
```

而不是简单地把工作区所有修改一股脑提交。

所以暂存区的作用可以理解成：

> **“我这次准备提交哪些修改？”**

---

# 4. 本地仓库（Local Repository）

执行：

```bash
git commit
```

之后：

```text
暂存区
   ↓ commit
本地仓库
```

这时候 Git 才真正创建了一个新的历史版本。

可以理解为：

```text
修改代码
 ↓
git add
 ↓
准备好本次提交内容
 ↓
git commit
 ↓
形成一个版本
```

所以：

```text
git add
```

和：

```text
git commit
```

不是一回事。

---

# 5. `git add`

最简单：

```bash
git add main.cpp
```

意思：

> 把 `main.cpp` 当前的修改放入暂存区。

如果想把当前目录下很多修改一起加入：

```bash
git add .
```

这里：

```text
.
```

表示当前路径范围。

初学时经常看到：

```bash
git add .
```

但你要理解：

> 它不是“提交”。

它只是：

```text
工作区
 ↓
暂存区
```

---

# 6. `git commit`

然后：

```bash
git commit -m "add main"
```

其中：

```text
-m
```

表示指定提交信息。

例如：

```bash
git commit -m "fix login bug"
```

就是创建一次版本提交，并记录说明：

```text
fix login bug
```

这里的 `commit` 非常重要。

可以理解成：

> **给当前准备好的修改拍一个“版本快照”。**

---

# 7. 为什么 commit 很像“存档点”？

例如：

```text
Commit 1
 ↓
Commit 2
 ↓
Commit 3
```

每次 commit 都形成一个新的历史节点。

你可以把它想象成游戏里的：

```text
存档
 ↓
继续玩
 ↓
存档
 ↓
继续玩
 ↓
存档
```

如果后面出了问题：

```text
查看历史
 ↓
找到过去的版本
 ↓
比较 / 恢复
```

这个类比非常适合初学。

---

# 8. `git status`

这是 Git 初学阶段**非常重要**的命令。

```bash
git status
```

作用：

> 查看当前 Git 仓库状态。

它可以帮助你知道：

```text
哪些文件修改了
哪些文件已经加入暂存区
哪些文件还没有被跟踪
当前分支是什么
```

所以实际开发中你会大量使用：

```bash
git status
```

它相当于：

> **“告诉我 Git 现在到底怎么看这个项目。”**

---

# 9. 三板斧完整流程

假设：

```text
main.cpp
```

修改了。

执行：

```bash
git status
```

发现修改。

然后：

```bash
git add main.cpp
```

进入：

```text
工作区 → 暂存区
```

再：

```bash
git commit -m "update main"
```

进入：

```text
暂存区 → 本地仓库
```

所以课堂所谓的核心“三板斧”，你应该形成这个流程：

```text
git add
    ↓
git commit
    ↓
git push
```

不过严格来说，`git status` 是整个过程中非常重要的辅助命令。

---

# 10. `git push`

现在本地已经有：

```text
commit
```

但它只存在于：

```text
你的电脑
```

如果 GitHub 上也要有这个版本，就需要：

```bash
git push
```

于是：

```text
本地仓库
   ↓ push
远程仓库
```

例如：

```text
GitHub
└── myproject
```

就会收到你的提交。

---

# 11. 为什么 `git commit` 后还要 `git push`？

这是 Git 新手非常容易混淆的。

```text
git commit
```

只是：

```text
本地
```

发生变化。

而：

```text
git push
```

才是：

```text
本地 → 远程
```

所以：

```text
git commit
≠
上传 GitHub
```

完整关系：

```text
代码修改
 ↓
git add
 ↓
暂存区
 ↓
git commit
 ↓
本地仓库
 ↓
git push
 ↓
GitHub 远程仓库
```

这四层一定要在脑子里形成。

---

# 12. `git clone`

如果别人已经在 GitHub 上有一个项目：

```text
https://github.com/xxx/project.git
```

你想把它拿到本地，可以：

```bash
git clone https://github.com/xxx/project.git
```

它会把远程仓库：

```text
GitHub
```

复制到：

```text
本地
```

并建立相应的 Git 仓库信息。

所以：

```text
clone
→ 第一次把远程项目完整拿到本地
```

这和：

```text
push
→ 把自己的本地提交推到远程
```

是相反方向的典型操作。

---

# 13. `pull`

如果项目已经存在本地，但远程发生了新的变化：

```text
GitHub
 ↓
别人提交了新代码
```

你可以通过：

```bash
git pull
```

获取远程更新并进行必要的整合。

可以先简单理解：

```text
push
→ 本地 → 远程

pull
→ 远程 → 本地
```

后面学习分支和冲突时，会进一步深入 `pull` 背后的过程。

---

# 14. 远程仓库到底是什么？

这里可以结合你板书里的结构图理解。

假设：

```text
你的电脑
├── 工作区
├── 暂存区
└── 本地仓库
```

GitHub：

```text
远程仓库
```

两边通过网络联系：

```text
                 网络
                  │
        ┌─────────┴─────────┐
        ↓                   ↓
     本地仓库             GitHub
                           远程仓库
```

最常见：

```text
git push
```

把本地提交推过去；

```text
git pull
```

把远程变化拿回来。

---

# 15. 为什么 Git 叫“分布式版本控制”？

这是 Git 和传统集中式版本控制理解上的一个重要区别。

集中式系统大致：

```text
             中央服务器
             /    |    \
           A      B      C
```

很多重要版本历史集中在中央服务器。

而 Git 更强调：

```text
        远程仓库
        ↙  ↓  ↘
      A    B    C
      ↓    ↓    ↓
   各自拥有自己的 Git 仓库
```

每个开发者的本地仓库都可以拥有完整的版本历史。

因此：

> **Git 的核心设计是分布式版本控制，而 GitHub 是常见的远程托管平台。**

这也是为什么：

```text
没有网络
```

的时候，你仍然可以：

```bash
git add
git commit
git log
git diff
```

进行大量 Git 操作。

只有需要和远程仓库交换数据时，才需要网络。

---

# 16. `git log`

既然 Git 保存了版本历史，那当然需要查看。

```bash
git log
```

可以查看提交历史。

例如：

```text
commit abc123...
Author: ...
Date: ...

    update main

commit def456...
Author: ...
Date: ...

    initial project
```

你看到的：

```text
commit
```

后面的那串内容，就是这个提交的重要标识之一：

> **Commit ID / Hash**

Git 使用哈希等机制标识对象和提交，因此每个提交都具有自己的唯一标识。

---

# 17. `git diff`

另一个非常实用的命令：

```bash
git diff
```

它可以查看当前修改与相应基线之间的差异。

例如你改了：

```cpp
int a = 10;
```

变成：

```cpp
int a = 20;
```

`git diff` 可以告诉你：

```text
10 → 20
```

到底改了什么。

所以：

```text
git status
→ 哪些东西变了？

git diff
→ 具体变了什么？
```

建议你现在就建立这个习惯。

# 7. 调试器 —— gdb / cgdb 使用

前面我们已经完成：

```text
Vim
 ↓
写代码
 ↓
gcc / g++
 ↓
编译
 ↓
make
 ↓
自动构建
```

现在还差一个非常关键的环节：

```text
程序运行出错
      ↓
为什么错？
      ↓
到底是哪一行？
      ↓
哪个变量的值不对？
      ↓
程序当时走到了哪里？
      ↓
gdb
```

所以这一章解决的是：

> **如何观察程序运行过程，并定位程序中的问题。**

结合你给的课堂板书，这一部分重点也是围绕：

```text
编译时加入调试信息
        ↓
进入 gdb
        ↓
设置断点
        ↓
运行
        ↓
单步执行
        ↓
观察变量
        ↓
定位问题
```

展开。

# 7-1 样例代码

先准备一份故意有问题的代码。

```c
#include <stdio.h>

int Add(int a, int b)
{
    return a + b;
}

int main()
{
    int a = 10;
    int b = 20;
    int ret = Add(a, b);

    printf("ret = %d\n", ret);

    return 0;
}
```

这个程序很简单。

正常结果：

```text
ret = 30
```

但是实际调试时，我们往往不是面对这么简单的情况，而是：

```text
几百行
几千行
甚至几十万行代码
```

程序可能只是：

```text
运行结果不对
```

或者：

```text
Segmentation fault
```

这时候你不能靠不停地 `printf()` 猜。

例如：

```c
printf("a=%d\n", a);
printf("b=%d\n", b);
printf("ret=%d\n", ret);
```

当然可以辅助排查，但是当程序复杂以后：

```text
大量 printf
 ↓
重新编译
 ↓
运行
 ↓
看输出
 ↓
继续修改 printf
 ↓
再编译
```

会越来越痛苦。

这就是调试器存在的意义。

# 7-2 预备

## 1. 为什么直接 `gdb ./test` 不够？

先回忆一下：

```bash
gcc test.c -o test
```

然后：

```bash
gdb ./test
```

可能也能启动 gdb。

但是如果你想：

```text
停在第 10 行
看看变量 a
看看当前代码
```

就需要程序里存在：

> **调试信息（debug information）**

这就是上一章已经提前讲过的：

```bash
-g
```

---

# 2. `-g` 的作用

重新编译：

```bash
gcc -g test.c -o test
```

这里：

```text
-g
```

会让编译器生成调试信息。

这些信息可以帮助调试器建立：

```text
机器代码
   ↕
源代码
   ↕
函数
   ↕
变量
   ↕
行号
```

也就是说，程序真正运行的是机器指令，但 gdb 可以借助调试信息告诉你：

```text
现在执行的是 test.c 第 12 行
变量 a = 10
变量 b = 20
```

这就是 `-g` 最重要的意义。

---

# 3. 为什么“源代码”和“机器代码”之间还需要对应关系？

上一章我们已经学过：

```text
test.c
 ↓
预处理
 ↓
编译
 ↓
汇编
 ↓
test.o
 ↓
链接
 ↓
test
```

最终 CPU 执行的是：

```text
机器指令
```

CPU 并不知道：

```text
main.c 第 17 行
int a = 10;
```

这些“人类概念”。

所以 gdb 想让你看到：

```text
第 17 行
a = 10
```

就必须知道：

```text
某段机器指令
        ↕
源代码第 17 行
```

以及：

```text
某个内存位置
        ↕
变量 a
```

`-g` 就是在生成这些调试信息。

---

# 4. 推荐调试时这样编译

初学阶段建议：

```bash
gcc -g -O0 test.c -o test
```

这里：

```text
-g
↓
调试信息

-O0
↓
关闭优化
```

为什么需要 `-O0`？

因为编译优化可能让程序的机器指令和你看到的源代码执行顺序、变量存储方式等出现差异。

例如你明明写：

```c
int a = 10;
int b = 20;
int c = a + b;
```

经过优化之后，编译器可能：

```text
重新安排指令
消除某些变量
把变量放进寄存器
```

于是调试体验可能变得复杂。

所以学习调试时：

```bash
gcc -g -O0 test.c -o test
```

是很好的习惯。

---

# 5. 进入 gdb

执行：

```bash
gdb ./test
```

进入后通常会看到类似：

```text
(gdb)
```

这个：

```text
(gdb)
```

就是：

> **gdb 命令输入提示符。**

注意现在已经不是 Linux shell：

```text
root@server:~#
```

而是：

```text
(gdb)
```

所以：

```bash
(gdb) run
```

是 gdb 命令。

而：

```bash
gcc -g test.c -o test
```

是 shell 命令。

一定要区分这两个环境。

# 7-3 常见使用

现在正式进入 gdb 最常用的命令。

---

# 1. `list` / `l`

进入 gdb 后：

```text
(gdb) list
```

也可以：

```text
(gdb) l
```

作用：

> **查看源代码。**

例如：

```text
1   #include <stdio.h>
2
3   int Add(int a, int b)
4   {
5       return a + b;
6   }
7
8   int main()
9   {
10      int a = 10;
11      int b = 20;
12      int ret = Add(a, b);
...
```

这就是板书中很重要的第一个操作：

```text
进入 gdb
 ↓
list
 ↓
看到源代码
```

---

# 2. 设置断点：`break`

假设：

```text
main
```

在：

```text
第 8 行
```

可以：

```text
(gdb) break 8
```

或者简写：

```text
(gdb) b 8
```

意思：

> **在第 8 行设置断点。**

也可以直接对函数下断点：

```text
(gdb) b main
```

表示：

> 在进入 `main` 时停下来。

例如：

```text
(gdb) b Add
```

表示：

> 在进入 `Add` 函数时停下来。

这是非常实用的方式。

---

# 3. 断点到底是什么？

假设：

```text
main()
{
    ...
    ret = Add(a, b);   ←
    ...
}
```

设置：

```text
b Add
```

那么程序运行到：

```text
Add()
```

时：

```text
程序
 ↓
遇到断点
 ↓
暂停
 ↓
把控制权交给 gdb
```

此时程序**不是结束了**。

而是：

> **暂停执行，等待你进一步发出调试命令。**

这就是断点。

---

# 4. `run`：运行程序

```text
(gdb) run
```

简写：

```text
(gdb) r
```

作用：

> **启动程序。**

如果之前设置：

```text
(gdb) b main
```

那么：

```text
(gdb) r
```

程序运行：

```text
程序开始
 ↓
进入 main
 ↓
遇到断点
 ↓
停下
```

gdb 会告诉你：

```text
Breakpoint 1, main () at test.c:...
```

并显示当前代码位置。

---

# 5. 断点停下来以后怎么办？

这时候不能：

> “程序怎么不动了？”

因为这正是我们需要的。

现在你可以问：

```text
现在是哪一行？
变量是多少？
下一行是什么？
进入函数了吗？
```

这时候就要用：

```text
next
step
print
continue
```

---

# 6. `next`：单步执行

```text
(gdb) next
```

简写：

```text
(gdb) n
```

含义：

> **执行下一步源代码语句，但通常不进入被调用函数内部。**

例如：

```c
int main()
{
    int a = 10;
    int b = 20;
    int ret = Add(a, b);
    printf("%d\n", ret);
    return 0;
}
```

如果停在：

```c
int ret = Add(a, b);
```

执行：

```text
n
```

会把这一整条语句执行完：

```text
Add(a, b)
```

函数内部不会展开成很多步。

---

# 7. `step`：进入函数

```text
(gdb) step
```

简写：

```text
(gdb) s
```

作用：

> **执行下一步，并且遇到函数调用时可以进入函数内部。**

例如：

```c
int ret = Add(a, b);
```

当前停在这里：

```text
s
```

可能进入：

```c
int Add(int a, int b)
{
    return a + b;
}
```

然后你就可以继续一步一步观察 `Add()`。

---

# 8. `next` 和 `step` 的区别

这是 gdb 最重要的一组命令。

| 命令           | 含义           |
| ------------ | ------------ |
| `n` / `next` | 单步执行，通常不进入函数 |
| `s` / `step` | 单步执行，可以进入函数  |

例如：

```text
main()
 ↓
Add()
```

使用：

```text
n
```

相当于：

```text
main
 ↓
整个 Add 执行完
 ↓
返回 main
```

而：

```text
s
```

相当于：

```text
main
 ↓
进入 Add
 ↓
Add 内部一行一行执行
```

所以：

> **想看函数内部 → `s`；不想进去 → `n`。**

---

# 9. `print`：查看变量

假设现在程序停在：

```c
int ret = Add(a, b);
```

我们想知道：

```text
a
b
ret
```

可以：

```text
(gdb) print a
```

简写：

```text
(gdb) p a
```

例如：

```text
$1 = 10
```

表示：

```text
a = 10
```

查看：

```text
b
```

：

```text
(gdb) p b
```

得到：

```text
$2 = 20
```

---

# 10. 为什么结果前面有 `$1`？

例如：

```text
(gdb) p a
$1 = 10
```

这个：

```text
$1
```

是 gdb 给这次打印结果分配的历史编号。

下一次：

```text
(gdb) p b
```

可能：

```text
$2 = 20
```

再：

```text
(gdb) p a + b
```

：

```text
$3 = 30
```

所以你甚至可以：

```text
(gdb) p $1
```

引用之前的结果。

不过初学阶段知道“这是 gdb 的历史结果编号”就够了。

---

# 11. 可以打印表达式

不只是：

```text
p a
```

还可以：

```text
p a + b
```

或者：

```text
p ret * 2
```

甚至查看结构体成员：

```text
p obj.member
```

因此：

> `print` 本质上不是“打印变量”，而是**让 gdb 求值并显示表达式的结果**。

---

# 12. `continue`：继续运行

假设：

```text
(gdb) b main
(gdb) r
```

停在断点。

我们不想每一行都看了，希望：

```text
继续运行
直到下一个断点
```

就使用：

```text
(gdb) continue
```

简写：

```text
(gdb) c
```

所以：

```text
r
→ 从头运行

n
→ 下一步

s
→ 下一步并进入函数

c
→ 继续运行到下一个断点 / 程序结束
```

---

# 13. 查看断点：`info break`

设置：

```text
(gdb) b main
(gdb) b Add
```

可以：

```text
(gdb) info break
```

简写：

```text
(gdb) i b
```

查看断点信息。

通常会看到类似：

```text
Num   Type       Disp   Enb   Address   What
1     breakpoint keep   y     ...       main
2     breakpoint keep   y     ...       Add
```

这就是：

> **当前有哪些断点。**

---

# 14. 删除断点：`delete`

例如：

```text
(gdb) delete 1
```

删除编号为 `1` 的断点。

也可以：

```text
(gdb) d 1
```

查看编号：

```text
info break
```

然后：

```text
delete 编号
```

形成：

```text
b 10
 ↓
创建断点

info b
 ↓
查看断点

d 1
 ↓
删除 1 号断点
```

---

# 15. `bt`：查看函数调用栈

这是调试时非常重要的一个命令。

```text
(gdb) bt
```

也就是：

> **backtrace**

例如程序调用：

```text
main
 ↓
foo
 ↓
bar
 ↓
test
```

当前在：

```text
test
```

执行：

```text
bt
```

可能得到类似：

```text
#0  test()
#1  bar()
#2  foo()
#3  main()
```

这就告诉你：

> **当前函数是怎么一路被调用到这里的。**

这个概念叫：

> **调用栈（Call Stack）**

以后你遇到段错误：

```text
Segmentation fault
```

`bt` 往往是第一批应该想到的工具之一。

---

# 16. `display`：每一步自动查看变量

如果你不断执行：

```text
n
n
n
n
```

每次都：

```text
p i
```

很麻烦。

可以：

```text
(gdb) display i
```

之后每次程序停下来，gdb 都会自动显示：

```text
i = ...
```

例如：

```text
(gdb) display i
1: i = 10
```

下一次：

```text
n
```

自动：

```text
1: i = 9
```

再：

```text
n
```

：

```text
1: i = 8
```

这对于观察：

```text
循环变量
指针
状态变量
```

特别方便。

取消：

```text
(gdb) undisplay 1
```

这里的 `1` 是 display 表达式的编号。

# 17. `quit`

退出 gdb：

```text
(gdb) quit
```

简写：

```text
(gdb) q
```

返回 Linux shell。

# 18. 一个完整调试过程

进入：

```bash

```

```text

```

查看：



然后：


### gdb 调试

源代码不需要插入大量调试输出：

```text
停下
```

课程标题写的是：


可以理解为：

> **一个以 gdb 为核心、提供更友好终端界面的调试前端。**

```text

真正负责调试
```

所以你现在先把：


学扎实。

# 21. 一个非常重要的概念：断点不是“修改代码”

例如：

```text
(gdb) b 10
```

你可能会误以为：

> “是不是在第 10 行插入了一条调试代码？”

不是。

断点是：

> **调试器建立的一种暂停条件。**

你的源代码：

```c
int a = 10;
```

仍然是：

```c
int a = 10;
```

并没有变成：

```c
debug...
int a = 10;
```

所以退出 gdb 后：

```text
源代码完全没有因为断点而发生修改。
```

不要一遇到 bug 就：

```text

```

应该逐渐形成：

```text

 ↓
在哪里出问题？
 ↓
断点
 ↓
程序执行到了哪里？
 ↓
变量当前是什么？
 ↓
调用路径是什么？
 ↓
哪一步开始偏离预期？
```

这就是调试的核心思路。

# 7-4 常见技巧

课程这里还有三个很重要的加餐：

```text
7-4-1 watch
7-4-2 set var
7-4-3 条件断点
```

这几个我不想只给你打一张命令表，因为它们真正有价值的地方是：

> **从“程序停下来让我看”进阶到“程序满足某个条件时自动停下来”。**

---

# 7-4-1 `watch`

假设：

```c
int i = 0;

while (i < 10)
{
    ++i;
}
```

我们现在想知道：

> `i` 是什么时候发生变化的？

可以：

```text
(gdb) watch i
```

意思：

> **监视变量 `i` 的变化。**

当：

```text
i = 0
```

变成：

```text
i = 1
```

gdb 可以自动暂停：

```text
Old value = 0
New value = 1
```

然后继续：

```text
(gdb) c
```

下一次变化：

```text
Old value = 1
New value = 2
```

又停下来。

---

# 1. `watch` 和普通断点的区别

普通：

```text
b 10
```

表示：

> 到第 10 行就停。

而：

```text
watch i
```

表示：

> `i` 的值发生变化就停。

所以：

```text
断点
→ 关注“程序执行到了哪里”

watch
→ 关注“某个变量什么时候变化”
```

这是非常重要的区别。

---

# 7-4-2 `set var` 确定问题原因

这是非常有意思的调试方法。

例如程序：

```c
int a = 10;
int b = 20;

int ret = a + b;

printf("%d\n", ret);
```

现在程序运行到这里：

```text
ret = 30
```

但你怀疑：

> “是不是 `a` 的值不对？”

可以直接：

```text
(gdb) set var a = 100
```

然后：

```text
(gdb) p a
```

得到：

```text
$1 = 100
```

再继续：

```text
(gdb) n
```

观察程序之后的行为。

---

# 1. `set var` 的本质

它不是：

> “修改源代码。”

而是：

> **在调试过程中直接修改程序当前内存/变量状态。**

例如：

```text
正常程序状态
a = 10
```

你临时修改：

```text
set var a = 100
```

变成：

```text
调试中的程序状态
a = 100
```

源代码：

```c
int a = 10;
```

仍然没变。

---

# 2. 为什么这个功能有用？

比如你怀疑：

```text
if (a > 100)
```

某个分支导致错误。

但是程序真实运行中：

```text
a = 50
```

永远进不去这个分支。

你可以在 gdb 中：

```text
set var a = 200
```

然后继续执行。

如果程序立刻暴露出某个问题：

```text
原本怀疑的分支
        ↓
人为制造进入条件
        ↓
程序行为发生变化
```

就能帮助你进一步确认：

> **这个变量是否与问题有关。**

注意：

> 这是调试实验，不是在真正修改程序源代码。

---

# 7-4-3 条件断点

最后一个非常实用的能力：

> **满足条件才停。**

假设：

```c
for (int i = 0; i < 100000; ++i)
{
    ...
}
```

如果你：

```text
b 某一行
```

程序可能停：

```text
第一次
第二次
第三次
...
十万次
```

这显然很烦。

但是如果我们真正关心：

```text
i == 99999
```

怎么办？

---

# 7-4-3-1 添加条件断点

可以直接：

```text
(gdb) break 10 if i == 99999
```

意思：

```text
第 10 行
+
i == 99999
```

两个条件同时满足：

```text
程序执行到第 10 行
        &&
i == 99999
        ↓
停下来
```

否则：

```text
继续运行
```

---

# 7-4-3-2 给已经存在的断点新增条件

例如已经有：

```text
(gdb) b 10
```

得到：

```text
Breakpoint 1
```

现在增加条件：

```text
(gdb) condition 1 i == 99999
```

意思：

> 给 1 号断点增加条件。

于是：

```text
Breakpoint 1
+
i == 99999
```

才会真正停下来。

所以有两种方式：

### 创建时直接加条件

```text
b 10 if i == 99999
```

### 已经存在，再添加条件

```text
condition 1 i == 99999
```

```text
 ↓
Vault
```

CentOS 官方明确说明，CentOS Linux 7 的软件包在结束生命周期后会被归档到 `vault.centos.org`。([CentOS 博客][3])

因此你现在在 CentOS 7 上看到：

```bash
yum install xxx
```

然后出现仓库地址失效、找不到有效 `baseurl` 等问题，并不奇怪。

---

# 3. 下载新的 Yum 源配置文件

你课件里写了：

```text
使用阿里云源
使用清华源
```

这里我要补充一个**当前环境下的重要认识**：

> 这些国内镜像源是否仍然保留 CentOS 7 的对应仓库，需要看镜像站当前实际情况；不能把课程当年的镜像地址永久当成现在有效地址。

对于已经 EOL 的 CentOS 7，**官方 Vault 是最容易解释清楚、也最稳定的历史归档来源**。([CentOS 博客][3])

例如可以将仓库指向类似：

```text
https://vault.centos.org/7.9.2009/
```

下面给你一个更适合理解的 `.repo` 结构：

```ini
[base]
name=CentOS-7.9.2009 - Base
baseurl=https://vault.centos.org/7.9.2009/os/$basearch/
enabled=1
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7

[updates]
name=CentOS-7.9.2009 - Updates
baseurl=https://vault.centos.org/7.9.2009/updates/$basearch/
enabled=1
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7

[extras]
name=CentOS-7.9.2009 - Extras
baseurl=https://vault.centos.org/7.9.2009/extras/$basearch/
enabled=1
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7
```

你现在不必急着背配置文件，关键是看懂：

```text
baseurl
   ↓
告诉 yum 去哪里找软件包
```

和之前学的：

```text
/etc/yum.repos.d/*.repo
```

正好对应起来。

---

# 4. 清理并生成缓存

修改源之后，不能直接认为 yum 已经完全切换。

先清理：

```bash
yum clean all
```

然后重新建立缓存：

```bash
yum makecache
```

整个逻辑：

```text
旧源缓存
   ↓
yum clean all
   ↓
清掉旧缓存
   ↓
yum makecache
   ↓
根据新源重新生成缓存
```

这里可以理解为：

> **修改了“仓库地址”以后，让 yum 丢掉旧的仓库缓存，再重新认识新的仓库。**

---

# 5. 更新系统

课程中给出：

```bash
yum update
```

或者：

```bash
yum update -y
```

但这里要特别注意：

**CentOS 7 已经 EOL，所以你现在使用 Vault 时拿到的是历史归档内容，并不会因为配置了 Vault 就重新获得持续的安全更新。** ([CentOS 博客][3])

所以：

```text
Vault
≠
CentOS 7 又恢复正常生命周期
```

Vault 的意义主要是：

```text
提供历史版本软件包
 ↓
让老系统的软件管理还能工作
```

而不是：

```text
继续获得新的 CentOS 7 官方安全更新
```

这个区别非常重要。

---

# 6. 恢复原有 Yum 源

如果你之前备份了：

```bash
cp -a /etc/yum.repos.d /etc/yum.repos.d.bak
```

那么恢复可以：

```bash
rm -rf /etc/yum.repos.d
cp -a /etc/yum.repos.d.bak /etc/yum.repos.d
```

然后：

```bash
yum clean all
yum makecache
```

于是：

```text
修改后的源
    ↓
不要了
    ↓
恢复备份
```

这就是为什么：

> **改系统配置之前先备份，是非常重要的 Linux 操作习惯。**

---

# 7. 验证 Yum 源

最基本：

```bash
yum repolist
```

你会看到仓库列表，例如：

```text
repo id
repo name
status
```

还可以：

```bash
yum makecache
```

确认缓存能否正常建立。

再测试：

```bash
yum search tree
```

或者：

```bash
yum info tree
```

如果能够正常查询，就说明：

```text
yum
 ↓
仓库
 ↓
软件包
```

这一链路基本恢复了。

# 8. CentOS 7 源故障的排查思路

不要看到：

```text
yum install xxx
```

失败，就马上换源。

应该按照层次排查：

```text
① 网络是否正常
        ↓
② DNS 是否正常
        ↓
③ repo 配置是否正确
        ↓
④ 仓库地址是否有效
        ↓
⑤ 软件包是否存在
        ↓
⑥ yum 缓存是否需要清理
```

这和你前面学习的 Linux 排错思想是一致的：

> **先找问题在哪一层，再修改对应的东西。**

# 二、Ubuntu 更新 apt 源

下面换 Ubuntu。

刚才是：

```text
CentOS
 ↓
yum
 ↓
.repo
```

Ubuntu 则是：

```text
Ubuntu
 ↓
apt
 ↓
APT 源配置
```

---

# 1. 备份现有 APT 源

Ubuntu 最经典的主配置文件：

```bash
/etc/apt/sources.list
```

先备份：

```bash
cp /etc/apt/sources.list /etc/apt/sources.list.bak
```

此外还要知道：

```text
/etc/apt/sources.list.d/
```

里面也可能有其他软件源配置。

所以完整理解应该是：

```text
/etc/apt/sources.list
        +
/etc/apt/sources.list.d/
        ↓
APT 软件源配置
```

---

# 2. 20.04 为什么现在需要注意？

Ubuntu 20.04：

```text
代号：
Focal Fossa
```

当前已经超过：

```text
2025-05-31
```

这个日期，也就是标准支持结束日期。([Ubuntu][2])

所以：

```text
Ubuntu 20.04
 ↓
普通标准仓库不再按照以前的生命周期提供标准支持
```

如果机器必须继续保留 20.04，Canonical 提供 Ubuntu Pro / ESM 方案；如果只是学习课程中的旧环境，也可能需要使用旧版本归档源。([Ubuntu 邮件列表][4])

---

# 3. Ubuntu 的 old-releases

Ubuntu 官方的旧版本下载/归档体系中仍然提供旧版本，例如 `20.04.6`。([Ubuntu Releases][5])

因此对于一个普通的、已经进入旧版本归档阶段的 Ubuntu 20.04 学习环境，经常会见到：

```text
old-releases.ubuntu.com
```

它的作用和刚才 CentOS 的：

```text
vault.centos.org
```

比较像：

```text
CentOS 7
 ↓
Vault

Ubuntu 旧版本
 ↓
old-releases
```

它们都体现的是：

> **“历史版本的仓库归档”。**

---

# 4. APT 源配置长什么样？

例如：

```text
deb http://archive.ubuntu.com/ubuntu focal main restricted universe multiverse
```

可以拆成：

```text
deb
 ↓
二进制软件包源

http://...
 ↓
仓库地址

focal
 ↓
Ubuntu 版本代号

main restricted universe multiverse
 ↓
仓库组件
```

Ubuntu 20.04 的代号是：

```text
focal
```

这是为什么你的课件里强调：

> **确保配置文件适配 Ubuntu 20.04**

因为如果你拿 Ubuntu 22.04 的：

```text
jammy
```

仓库配置直接放到 20.04：

```text
focal
```

系统版本和仓库版本就对不上。

所以：

```text
20.04 → focal
22.04 → jammy
24.04 → noble
26.04 → resolute
```

这也是为什么修改源时**不能只看“Ubuntu”三个字，还必须确认具体版本**。当前 Ubuntu 官方版本表也明确列出了这些版本及其生命周期。([Ubuntu][6])

---

# 5. 如果使用 Ubuntu 20.04 的归档源

核心思想是：

```text
原来的：

archive.ubuntu.com
security.ubuntu.com

        ↓

旧版本归档：

old-releases.ubuntu.com
```

并且：

```text
focal
```

仍然要保持为：

```text
focal
```

例如：

```text
deb http://old-releases.ubuntu.com/ubuntu/ focal main restricted universe multiverse
deb http://old-releases.ubuntu.com/ubuntu/ focal-updates main restricted universe multiverse
deb http://old-releases.ubuntu.com/ubuntu/ focal-security main restricted universe multiverse
deb http://old-releases.ubuntu.com/ubuntu/ focal-backports main restricted universe multiverse
```

这里的重点不是把这些行死背下来，而是理解：

```text
Ubuntu版本
+
仓库地址
+
组件
```

共同构成 APT 源。

---

# 6. 更新 APT 缓存

修改之后：

```bash
apt update
```

注意：

```text
apt update
```

不是：

> “升级系统”。

它主要是：

> **更新本地的软件包索引。**

可以理解成：

```text
远程仓库
 ↓
下载最新的软件包索引
 ↓
更新本地 APT 数据库
```

这和：

```bash
apt upgrade
```

是两回事。

---

# 7. `apt update` vs `apt upgrade`

一定要区分：

| 命令            | 作用              |
| ------------- | --------------- |
| `apt update`  | 更新软件包索引         |
| `apt upgrade` | 根据当前索引升级已安装的软件包 |

所以一般是：

```bash
apt update
```

然后才根据需要：

```bash
apt upgrade
```

也就是说：

```text
update
→ 更新“我有哪些软件、有什么版本”

upgrade
→ 真正升级已经安装的软件
```

这和前面：

```text
yum update
```

的概念不要完全机械对应。

---

# 8. 升级系统（可选）

课程里：

```bash
apt upgrade
```

属于可选步骤。

例如：

```bash
apt upgrade
```

或者自动确认：

```bash
apt upgrade -y
```

但要注意：

> 对于旧版本 Ubuntu，`apt upgrade` 并不会把系统自动变成新版本 Ubuntu。

例如：

```text
20.04
```

执行：

```bash
apt upgrade
```

并不会自动变成：

```text
24.04
```

它只是升级**当前发行版范围内的软件包**。

真正的发行版升级是另一套流程。

这个区别很重要。

观察有没有：

```text
Err:
```

再使用：


查看当前配置的软件源。

还可以：

验证仓库是否能提供软件包。

测试完整的软件包安装链路。

# 10. 恢复原有 APT 源

如果之前备份：

```bash
cp /etc/apt/sources.list /etc/apt/sources.list.bak
```

恢复：

```bash
cp /etc/apt/sources.list.bak /etc/apt/sources.list
```

然后：

```bash

```

如果你还修改了：

```text

```

则对应的 `.list` / `.sources` 文件也需要恢复。

所以：

> **备份整个软件源配置比只记一个文件名更加可靠。**

# 三、yum 和 apt 对照理解

现在把附录和第一章合起来。

| 项目      | CentOS 7                  | Ubuntu 20.04                              |
| ------- | ------------------------- | ----------------------------------------- |
| 软件包体系   | RPM                       | DEB                                       |
| 包管理器    | `yum`                     | `apt`                                     |
| 主要源配置   | `/etc/yum.repos.d/*.repo` | `/etc/apt/sources.list`、`sources.list.d/` |
| 更新索引/缓存 | `yum makecache`           | `apt update`                              |
| 安装      | `yum install xxx`         | `apt install xxx`                         |
| 卸载      | `yum remove xxx`          | `apt remove xxx`                          |
| 源配置核心   | `.repo`                   | `deb ...` / `.sources` 等                  |
| 老版本归档场景 | CentOS Vault              | Ubuntu old-releases                       |

---

# 四、为什么“更新软件源”不是简单换个网址？

现在你应该可以理解更深一层：

```text
软件源
```

实际上包含一整个体系：

```text
服务器地址
+
发行版版本
+
仓库组件
+
软件包索引
+
签名校验
```

所以：

```text
把 URL 随便换掉
```

并不意味着：

```text
软件源就一定正确
```

必须保证：

```text
你的系统版本
        ↓
对应的仓库版本
        ↓
正确的仓库地址
        ↓
正确的架构
        ↓
正确的软件包元数据
```

否则就可能出现：

```text
404
依赖冲突
找不到软件包
GPG 校验错误
仓库不可用
```

# 五、把整个“软件包管理”章节闭环

现在回头看第一章：

```text
                    Linux软件管理

                     软件包
                       ↓
                软件包仓库
                       ↓
            ┌──────────┴──────────┐
            ↓                     ↓
          yum                    apt
            ↓                     ↓
      RPM生态                 DEB生态
            ↓                     ↓
    CentOS / RHEL          Ubuntu / Debian
```

而软件源就是：

```text
yum / apt
    ↓
“去哪里找到软件？”
    ↓
软件源
```

如果源失效：

```text
yum / apt
    ↓
无法找到正确仓库
    ↓
安装软件失败
```

因此：

```text
软件包管理器
+
软件源
+
仓库
+
依赖
```

才构成完整的软件管理体系。
