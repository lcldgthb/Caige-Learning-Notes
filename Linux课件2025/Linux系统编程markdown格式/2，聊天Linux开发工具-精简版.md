# 2. 基础开发工具 —— 软件包管理器与编辑器 Vim

## 一、软件包管理器

软件包管理器是 Linux 开发环境的"入口知识"：后面安装 `vim`、`gcc/g++`、`git` 以及各种库，本质上都会不断接触它。先建立一条完整的认识链：

```text
Linux 软件
   ↓
软件包（Package）
   ↓
软件包仓库（Repository）
   ↓
软件包管理器（Package Manager）
   ↓
安装 / 升级 / 卸载 / 查询软件
```

### 1.1 什么是软件包

在 Windows 上安装软件，接触的通常是 `.exe`、`.msi`、`.zip` 这类安装包，双击后一路"下一步"即可。Linux 也需要安装软件，但它通常不让你手动找安装程序，而是把软件整理成一种**标准的软件包格式**，交给系统的软件包管理体系处理。

所谓**软件包（Package）**，简单理解就是：

> **把一个软件运行所需要的文件、信息以及安装规则，按照统一格式打包起来。**

一个软件包可能包含：可执行文件、配置文件、动态库、帮助文档、版权信息、版本信息、依赖关系、安装/卸载相关信息。所以软件包并不只是"一个可执行文件"。

### 1.2 为什么会有依赖关系

这是理解软件包管理器最重要的地方之一。假设安装程序 A，但 A 运行时需要 B、C、D，而 B 又依赖 E：

```text
        A
      / | \
     B  C  D
     |
     E
```

如果没有软件包管理器，你就得自己手动走完"下载 A → 发现缺 B → 下载 B → 发现 B 需要 E → 下载 E → 再处理 C → 再处理 D"的链条，不仅麻烦，还很容易出现**版本不匹配、依赖缺失**等问题。

所以软件包管理器最重要的能力之一就是：

> **自动处理软件之间的依赖关系。**

这也解释了为什么执行 `yum install xxx` 时，它有时会顺便安装一大堆其他软件。

### 1.3 Linux 软件生态：三个核心概念

理解 Linux 软件生态，先认识三个东西——它们不是一个东西：

| 概念     | 作用           |
| -------- | ------------ |
| 软件包    | 软件的标准化安装载体 |
| 软件包管理器 | 管理软件包的软件   |
| 软件包仓库  | 存放大量软件包的地方 |

可以类比手机：APK ≈ 软件包，应用商店 ≈ 软件包仓库，应用商店客户端 ≈ 软件包管理器。Linux 的机制比手机应用商店更开放，但这个类比非常适合理解三者关系。

### 1.4 为什么 Linux 有这么多软件生态

因为 Linux 并不是一个单独的"操作系统发行版"，而是：

```text
Linux Kernel + 系统工具 + 软件包系统 + 安装配置工具 + 桌面环境等
    ↓
Linux 发行版
```

常见发行版有 CentOS、Rocky Linux、AlmaLinux、RHEL、Ubuntu、Debian、Fedora、Arch Linux 等。不同发行版往往采用不同的软件包格式和管理工具：

| 发行版生态         | 常见软件包        | 常见管理工具        |
| ------------------ | -------------- | --------------- |
| CentOS / RHEL 系   | `.rpm`         | `yum` / `dnf`   |
| Ubuntu / Debian 系 | `.deb`         | `apt`           |
| Arch 系            | Arch Package   | `pacman`        |

所以：

> **`yum` 不是 Linux 通用命令，而是特定 Linux 发行版生态中的软件包管理工具。**

在 Ubuntu 上输入 `yum install gcc` 通常不是正确做法，Ubuntu 使用的是 `apt install gcc`。

### 1.5 yum 的基本认识与查询操作

本节以 **CentOS/RHEL 系**为主。`yum` 是一个软件包管理工具，可以帮助我们从软件仓库中查询、安装、升级、卸载软件，并处理依赖关系，工作过程可以理解为：

```text
你 → yum → 软件仓库 → 下载软件包 → 处理依赖 → 安装到系统
```

学习 `yum`，先学"查"：

**① 查看软件包**

```bash
yum list              # 列出软件包信息（包名、版本、仓库）
yum list gcc          # 查询名为 gcc 的软件包
yum list installed    # 专门查看已经安装的软件包
```

注意 `yum list` 偏向于查看软件包列表，`yum list installed` 专门查看已安装的软件包，两者容易混淆。

**② 搜索软件包**

只知道软件大概和什么有关、不知道具体包名时：

```bash
yum search network    # 按关键词搜索相关软件包
```

实际使用路径：不知道包名 → `yum search 关键词` → 找到可能的包名 → `yum install 包名`。

**③ 查看详细信息**

```bash
yum info gcc          # 查看 Name、Version、Release、Architecture、Size、Repository、Summary、Description 等信息
```

汇总成表：

| 命令                   | 作用        |
| -------------------- | --------- |
| `yum list`           | 查看软件包     |
| `yum list installed` | 查看已安装软件包  |
| `yum search xxx`     | 搜索软件包     |
| `yum info xxx`       | 查看软件包详细信息 |

### 1.6 安装与卸载

**安装**

```bash
yum install tree      # 安装 tree 软件包
```

执行 `yum install tree` 并不是简单地"下载 tree → 复制到某个目录"，它实际上会做很多事情：

```text
yum install tree
        ↓
查询仓库 → 找到 tree 软件包
        ↓
检查并计算 tree 的依赖关系
        ↓
下载 tree 以及必要依赖
        ↓
安装 → 更新软件包数据库
```

所以：

> **软件包管理器不仅仅负责"下载"，更重要的是负责"管理"。**

如果执行 `yum install A` 时看到同时安装了 B、C、D，不要觉得奇怪——很可能是因为 A 依赖 B、C，而 B 又依赖 D，yum 自动把依赖补齐了。这正是软件包管理器的重要价值。

**`-y` 选项**

安装过程中 yum 会让你确认（`Is this ok [y/d/N]:`），输入 `y` 继续。如果明确知道自己要装什么，可以用：

```bash
yum install -y tree   # 自动对所有需要确认的问题回答 yes
```

`-y` 在脚本、自动化环境中非常常见。但初学阶段建议多看看 yum 的输出内容，不要无脑加 `-y`——它会告诉你安装什么、升级什么、删除什么、需要下载多少、占用多少空间，这些信息本身很重要。

**卸载**

```bash
yum remove tree       # 卸载软件包
yum erase tree        # 某些环境中也可使用，效果类似
```

记住 `yum remove 软件包名` 就够用了。

### 1.7 完整流程串联

假设想在 Linux 上使用 `tree`，但不知道有没有安装，可以按下面的思路走：

```bash
# 第一步：看看有没有（| 是管道，把前一个命令的输出交给后一个命令筛选）
yum list installed | grep tree

# 第二步：没有安装，就按关键词搜索
yum search tree

# 第三步：查看详细信息
yum info tree

# 第四步：安装
yum install -y tree

# 第五步：使用
tree

# 第六步：不需要了就卸载
yum remove tree
```

其中 `yum list installed | grep tree` 把之前学过的**管道**和现在的**软件包管理**联系了起来：查看已安装软件包，再从中筛选出包含 `tree` 的行。以后安装 `vim`、`git`、开发库，本质上都是"查询 → 搜索 → 查看信息 → 安装 → 使用 → 卸载"这一套逻辑。

### 1.8 软件包名 ≠ 命令名

这里特别容易产生误解。`yum install gcc` 安装的是一个名叫 `gcc` 的**软件包**；安装之后使用的 `gcc test.c`，这里的 `gcc` 是**可执行程序/命令**。两者经常同名，但概念上并不完全相同。`yum install git` 与 `git --version` 同理。

所以不要建立"yum 后面写的东西就是命令"这样的死板认识：

```text
yum install xxx
        ↑
     软件包名

xxx
↑
可能是安装后提供的命令
```

至于一个软件包到底提供哪些命令和文件，后面深入 Linux 软件管理时还会继续接触。

### 1.9 yum 和 rpm 的关系

CentOS/RHEL 体系里经常同时看到 RPM 和 yum，它们不是同一个东西，可以先粗略理解：

```text
RPM → 更底层的软件包管理工具
YUM → 更上层的软件包管理工具
      ↓
   能够从仓库获取软件、解决依赖关系
```

直接拿到一个 `xxx.rpm` 文件时用 `rpm` 操作；而 `yum install xxx` 更偏向于**从软件仓库找到软件包，并自动处理依赖**。因此日常安装软件，`yum` 通常更方便。后面讲到动态库、静态库以及软件安装时还会再次遇到 RPM，现在先建立这个层次感就够了。

### 1.10 与 Ubuntu 的 apt 对照

以后会同时接触 CentOS 和 Ubuntu，这张表建议记住：

| 功能     | CentOS/RHEL 系     | Ubuntu/Debian 系   |
| ------ | ----------------- | ----------------- |
| 软件包格式  | RPM               | DEB               |
| 常用管理工具 | yum / dnf         | apt               |
| 安装     | `yum install xxx` | `apt install xxx` |
| 卸载     | `yum remove xxx`  | `apt remove xxx`  |
| 搜索     | `yum search xxx`  | `apt search xxx`  |
| 查看信息   | `yum info xxx`    | `apt show xxx`    |

核心不是背命令，而是理解：不同 Linux 发行版可能采用不同的软件包体系，对应不同的软件包管理器。以后看到 `apt install gcc`，不要觉得"怎么突然不是 yum 了"——这是**发行版不同**导致的。

### 1.11 使用注意事项

**① 不要随便卸载系统软件**

`yum remove xxx` 看起来只是删除一个软件，但如果存在"A 依赖 B，C 也依赖 B"的关系，删除 B 会导致 A、C 都可能无法运行。使用 `yum remove` 时（尤其是服务器环境），不要只看是否删除了目标软件，还要看 yum 给出的操作计划中 `Dependencies removed:` 部分删除了哪些依赖。软件包之间存在依赖关系，这正是软件包管理器核心价值的另一面。

**② `yum update` 不要随便执行**

`yum update` 的作用是**根据当前软件仓库，把系统中可以更新的软件包进行升级**，与 `yum install xxx`（安装指定软件）是两个不同概念。服务器上不要形成"看到 update 就直接执行"的习惯，因为系统更新可能涉及库版本、系统组件、网络组件、服务程序、内核相关组件。开发学习环境问题相对小一些，但生产服务器上的更新应该经过明确评估。

**③ 注意软件包名称**

"命令叫 git"不代表所有发行版、所有相关功能都对应一个叫 `git` 的包——实际存在的软件包可能有 `git`、`git-core`、`git-all`、`git-svn` 等等。所以 `yum search git` 很有价值。

**④ yum 不是万能的**

执行 `yum install abc` 报 `No package abc available.` 时，这不一定代表 Linux 上不存在 abc 软件，更准确的含义是：**当前 yum 配置的软件仓库中没有找到名为 abc 的可用软件包**。可能的原因包括：软件包真的不存在、包名写错、仓库没有配置、仓库中没有这个版本、仓库已经失效、网络无法访问仓库。

> **"yum 找不到" ≠ "Linux 没有这个软件"。**

### 1.12 安装源（软件仓库配置）

**什么是安装源**

yum 能工作，是因为它"去某个地方寻找软件包"，这个地方就是**软件源 / 软件仓库（Repository）**。所谓安装源，本质上就是告诉软件包管理器"你去哪里寻找软件包"。

一个 Linux 可以配置多个源，因为软件包不一定只有一个服务器提供：官方源、镜像源、校园镜像等服务器可以提供相同或相近的软件仓库内容，这样做最大的好处是**降低访问距离、提高下载速度，同时增加可用性**。

**什么是镜像源**

官方软件仓库可能距离很远，而国内镜像服务器（如阿里云镜像、清华大学镜像、中科大镜像）的网络路径通常更合适，下载体验更好。需要注意：

> **镜像源 ≠ 一个"不同的软件"。**

它通常只是对软件仓库内容进行镜像。

**yum 的仓库配置在哪里**

yum 的仓库配置位于 `/etc/yum.repos.d/` 目录，这个目录非常重要：

```bash
ls /etc/yum.repos.d/
```

通常可以看到若干 `.repo` 文件（如 `/etc/yum.repos.d/CentOS-Base.repo`），它们就是 yum 的仓库配置文件，作用是告诉 yum"软件仓库在哪里"。

**`.repo` 文件的核心字段**

打开一个 `.repo` 文件，经常会看到类似内容：

```ini
[base]
name=Base
baseurl=http://example.com/...
enabled=1
gpgcheck=1
gpgkey=...
```

| 字段         | 含义                                       |
| ---------- | ---------------------------------------- |
| `[base]`   | 仓库的标识名称                                   |
| `name`     | 仓库的人类可读名称                                 |
| `baseurl`  | 软件仓库真正访问的位置（yum 通过它找到仓库）                  |
| `enabled`  | `1` 启用，`0` 不启用                            |
| `gpgcheck` | 软件包签名校验，用于确认软件包的来源和完整性，是安全验证机制的一部分        |

**yum 突然不能用了怎么排查**

执行 `yum install tree` 报 `Cannot find a valid baseurl` 或 `Could not resolve host` 时，不要第一反应就是"yum 坏了"。应该沿着知识体系排查：

```text
yum → 仓库 → 仓库地址 → 网络 → DNS
```

可能是网络问题、DNS 问题、仓库地址问题、仓库失效，或者源配置过期。

**特别提醒：CentOS 7 已停止维护**

CentOS Linux 7 已于 2024 年 6 月 30 日结束生命周期（EOL），其软件包被归档到 `vault.centos.org`。Vault 中是历史快照，不再提供新的安全更新。所以现在使用 CentOS 7 时，如果 `yum install xxx` 突然失败，**很可能和仓库迁移、源失效有关**。这也解释了为什么课程最后专门有"CentOS 7 更新 yum 源"的附录——换源的完整流程（备份原源 → 替换源 → 清理缓存 → 重新生成缓存 → 验证）到附录再展开。

### 1.13 软件包管理器知识地图

到这里，你应该形成这样的整体认识：

```text
Linux 发行版
│
├── CentOS / RHEL   → RPM 软件包体系 → yum / dnf
├── Ubuntu / Debian → DEB 软件包体系 → apt
└── 其他发行版
```

以 CentOS/RHEL 为例，软件的流转过程是：

```text
软件 → 打包成 RPM 软件包 → 放入软件仓库
     → yum 从仓库寻找 → 解析依赖 → 下载安装 → 软件进入系统
```

其中 `/etc/yum.repos.d/*.repo` 负责告诉 yum"软件仓库在哪里"。而使用者最常做的操作就是：

```bash
yum search xxx
yum info xxx
yum install xxx
yum remove xxx
```

本节最重要的不是记住几个 `yum` 命令，而是理解 **Linux 软件是如何被组织和管理的**：

1. **软件包（Package）**：把软件运行所需的文件和相关元信息按照标准格式组织起来。
2. **软件包管理器**：负责软件包的查询、安装、卸载、升级以及依赖处理。
3. **软件包仓库（Repository）**：集中存放大量软件包，`yum` 从仓库中找到并获取软件。
4. **不同发行版的软件生态不同**：CentOS/RHEL 常见 RPM + `yum/dnf`，Ubuntu/Debian 常见 DEB + `apt`。
5. **核心思想**：yum 不只是"下载软件"，而是"管理软件及其依赖关系"。

## 二、编辑器 Vim

接下来进入第二个开发基础工具——**Vim**。对于 C/C++、Linux 后台开发来说，Vim 值得掌握。学习 Vim 最大的障碍并不是命令太多，而是：

> **Vim 和 Windows 编辑器最大的区别，是"模式"。**

如果这个概念没理解，后面的命令会全部变成死记硬背。

### 2.1 三种核心模式

普通编辑器一般是"打开文件 → 直接输入 → Ctrl+S 保存"，而 Vim 不是。Vim 默认进入的是**普通模式（Normal Mode）**——这个模式下按 `j` 可能不是输入字符 `j`，而是**让光标向下移动**。这就是第一次接触 Vim 最容易懵的地方。

Vim 最核心的三个模式及其切换关系：

```text
             ┌──────────────┐
             │   Normal     │
             │   普通模式    │
             └──────┬───────┘
                i / a ↓  ↑ Esc
             ┌──────────────┐
             │    Insert    │
             │    插入模式   │
             └──────────────┘

      普通模式下输入 : 进入
             ┌──────────────┐
             │ Command-line │
             │   末行模式    │
             └──────────────┘
```

先理解**普通模式、插入模式、末行模式**这三个就够。

### 2.2 基本操作闭环

**① 进入 Vim**

```bash
vim test.c
```

打开文件并默认处于普通模式。如果文件不存在，Vim 会创建一个新的编辑缓冲区；保存时文件才真正落到磁盘上。

**② 进入插入模式并编辑**

普通模式下按 `i` 进入插入模式，此时可以正常输入代码：

```cpp
#include <iostream>

int main()
{
    std::cout << "hello linux" << std::endl;
    return 0;
}
```

**③ 返回普通模式**

编辑完成后按 `Esc` 回到普通模式。`i → 进入插入模式`、`Esc → 返回普通模式`，这是 Vim 最基本的操作闭环。

**④ 保存与退出**

Vim 的保存不是 `Ctrl + S`，而是先按 `Esc` 回到普通模式，输入 `:` 进入末行模式，再执行命令：

```text
:w    → 保存（w = write）
:wq   → 保存并退出（w = write，q = quit）
:q!   → 不保存，强制退出（q = quit，! = 强制），即放弃当前修改
```

### 2.3 完整操作流程

以 `vim test.c` 为例，一次完整的编辑流程是：

```text
① 默认进入普通模式 → ② 按 i → ③ 进入插入模式 → ④ 输入代码
→ ⑤ 按 Esc → ⑥ 回到普通模式 → ⑦ 输入 :wq → ⑧ Enter → ⑨ 保存并退出
```

即：普通模式 →(i)→ 插入模式 →(Esc)→ 普通模式 →(:)→ 末行模式 →(Enter)→ 执行命令。

**为什么 Vim 一直强调"先按 Esc"**：因为 Vim 中最重要的一个习惯是——

> **不知道自己现在在哪个模式，就先按 `Esc`。**

例如正在输入 `int main()` 时不确定自己在什么模式，先按 `Esc` 回到普通模式，再执行 `:wq` 即可。这是初学者非常实用的习惯。

### 2.4 Vim 与普通编辑器的本质区别

| 对比     | 普通编辑器      | Vim         |
| ------ | ---------- | ----------- |
| 默认输入文字 | 通常可以直接输入   | 默认是普通模式     |
| 移动光标   | 鼠标/方向键     | 命令也可以完成     |
| 保存     | `Ctrl+S` 等 | `:w`        |
| 退出     | `Alt+F4` 等 | `:q`        |
| 保存并退出  | 常见快捷键      | `:wq`       |
| 核心设计   | 直接编辑       | **模式 + 命令** |

因此：

> **Vim 的核心不是"命令特别多"，而是"不同模式下，同一个按键具有不同意义"。**

后面学习普通模式命令集之后，会发现 `h`、`j`、`k`、`l`、`w`、`b`、`dd`、`yy`、`p`、`u` 这些看起来杂乱的命令，其实都建立在**普通模式**这个核心概念之上。

### 2.5 最小练习

在 Linux 中执行：

```bash
vim test.c
```

依次操作：按 `i` 进入插入模式，输入以下代码：

```cpp
#include <stdio.h>

int main()
{
    printf("hello linux\n");
    return 0;
}
```

然后按 `Esc`，输入 `:wq` 回车保存退出，再用 `cat test.c` 查看，应该能看到刚才写入的代码。

这个练习把前面学过的内容连接了起来：

```text
Linux 文件 → vim 编辑 → 保存到磁盘 → cat 查看
    ↓
gcc 编译 → 生成可执行程序 → 运行
```
