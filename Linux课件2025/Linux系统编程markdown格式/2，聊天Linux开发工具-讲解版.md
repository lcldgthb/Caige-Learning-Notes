# 一、软件包管理器

## 1.1 什么是软件包

在 Windows 上装软件，我们习惯去官网下载 `.exe` 安装包，一路"下一步"。Linux 的思路不同：

- **软件包（Package）**：把程序的二进制文件、配置文件、依赖信息打成一个包。RPM 系（CentOS/RHEL）是 `.rpm`，DEB 系（Ubuntu/Debian）是 `.deb`。
- **软件源 / 仓库（Repository）**：一个集中存放海量软件包的服务器，相当于*应用商店的仓库*。
- **包管理器**：客户端工具，负责"去仓库找包 → 下载 → 解决依赖 → 安装"，CentOS 用 **yum**，Ubuntu 用 **apt**。

> 类比：包管理器就是 Linux 的"应用商店 App"，软件源就是商店背后的仓库。你说"我要装 vim"，它自动去仓库拿货，还顺带把 vim 依赖的其他东西一起装好——依赖处理是它最大的价值。

比如软件 A 依赖 B、C、D，B 又依赖 E……手工装会让你崩溃，包管理器会递归地把整棵依赖树装好。

## 1.2 Linux 软件生态

软件包不是谁都能随便上架的：发行版官方会对包进行审核、编译、签名，保证安全和兼容。除了官方源，还有社区维护的扩展源，最著名的是 **EPEL**（Extra Packages for Enterprise Linux），可以理解为"官方商店的扩展货架"。

**重要现实情况**：老系统会"过期"。

- **CentOS 7 已于 2024-06-30 停止维护（EOL）**，官方源下线，旧包被转移到存档站 **Vault**（vault.centos.org）。
- **Ubuntu 20.04 标准支持到 2025-05-31**，之后软件源迁移到 **old-releases.ubuntu.com**，想用官方支持需付费订阅 ESM。

所以老机器上 yum/apt 报错"找不到源"，多半不是网坏了，而是源地址失效，需要换源（见附录）。

## 1.3 yum 具体操作

| 操作 | 命令 | 说明 |
|---|---|---|
| 列出软件 | `yum list` / `yum list \| grep xxx` | 包名格式：`名.架构 版本- release 来源仓库` |
| 搜索 | `yum search xxx` | 按关键字模糊找 |
| 安装 | `sudo yum install -y xxx` | `-y` 免确认；装软件是全局写操作，要 root |
| 卸载 | `sudo yum remove -y xxx` | 依赖它的包不会被自动带走 |

apt 的对应命令几乎对称：`apt list / apt search / sudo apt install -y / sudo apt remove -y`。

两个 apt 特有的高频命令容易混淆：

- `sudo apt update`：只**刷新软件包索引**（"商店的货架清单"），不升级任何软件。
- `sudo apt upgrade`：按新索引**真正升级软件**。
正确姿势是先 `update` 再 `upgrade`。

**注意事项**：装/删软件需要 root 权限（或 sudo）；同一时刻只能有一个 yum/apt 进程干活，否则报锁冲突；装完想验证，直接跑一下命令或 `which xxx` 看路径。

## 1.4 安装源（原理）

yum 的源配置文件在 **`/etc/yum.repos.d/`** 下，每个 `.repo` 文件描述一个仓库，核心字段：

```ini
[base]
name=CentOS-$releasever - Base
baseurl=http://mirror.aliyun.com/centos/...   # 仓库地址
enabled=1                                     # 1 启用 / 0 停用
gpgcheck=1                                    # 校验软件包签名，防篡改
gpgkey=file:///etc/pki/rpm-gpg/...
```

- **baseurl** 就是"仓库货架的网址"，把它从官方地址换成阿里云/清华镜像地址，下载速度立刻起飞——这就是"换源"的本质。
- **gpgcheck** 用发行版官方公钥验证包没有被掉包，生产环境不要关。

Ubuntu 侧对应的文件是 `/etc/apt/sources.list`，格式不同但思想一样：一行一个仓库地址。

# 二、Vim 编辑器

## 2.1 为什么是"多模式"

vim 和记事本最大的区别：**它是多模式编辑器**。刚接触会困惑"为什么我敲键盘不出字"，理解设计动机后就顺了：

> 类比：普通模式下，键盘不是打字机，而是*遥控器*——每个键都是一条命令（删一行、跳词、撤销）。要打字时按 `i` 切换到"打字机模式"，打完按 `Esc` 回到遥控器模式。换来的是：编辑代码时手不离开主键盘区，效率极高。

三大模式：

| 模式 | 作用 | 进入方式 | 退出方式 |
|---|---|---|---|
| **普通模式** Normal | 移动、删除、复制、粘贴——命令中心 | 默认启动即在此 | — |
| **插入模式** Insert | 真正输入文字 | 普通模式按 `i` 等 | `Esc` |
| **底行/末行模式** Last-line | 保存、退出、查找替换、设置 | 普通模式按 `:` | 执行完或 `Esc` |

## 2.2 模式切换

普通 → 插入的常用键（区别在光标落点）：

- `i`：在光标**前**插入（insert）
- `a`：在光标**后**插入（append）
- `o`：在**下一行**新开一行插入（open）
- `I` / `A` / `O`：行首插入 / 行尾插入 / 上一行新开

任何模式回普通模式：`Esc`。普通 → 底行：`:`。插入模式不能直达底行，必须先 `Esc`。

> 新手保命口诀：**不知道自己在哪个模式，就狂按 `Esc` 回普通模式**。

## 2.3 普通模式命令集

**光标移动**：

| 命令 | 作用 |
|---|---|
| `h j k l` | 左 / 下 / 上 / 右（古早键盘方向键） |
| `w` / `b` | 下一个词首 / 上一个词首 |
| `0` / `^` / `$` | 行首 / 第一个非空字符 / 行尾 |
| `gg` / `G` | 文件首行 / 文件尾行 |
| `nG` 或 `ngg` | 跳到第 n 行 |
| `{` / `}` | 上一空行 / 下一空行（按"段落"跳） |

**编辑动作**：

| 命令 | 作用 |
|---|---|
| `x` / `nx` | 删除光标处 / 后 n 个字符 |
| `dd` / `ndd` | 删除（剪切）当前行 / n 行 |
| `dw` | 删除一个词 |
| `yy` / `nyy` | 复制当前行 / n 行 |
| `p` / `P` | 粘贴到光标后 / 前 |
| `u` | 撤销 |
| `Ctrl + r` | 反撤销（重做） |
| `r` + 字符 | 替换光标处单个字符 |
| `cw` | 删除当前词并进入插入模式（change word） |
| `~` | 大小写切换 |

**核心思想：动作 + 范围可组合**。`d` 是"删除"动作，`w` 是"一个词"、`$` 是"到行尾"，于是 `dw` 删词、`d$` 删到行尾、`d3w` 删 3 个词。复制同理（`yw`、`y$`）。学会组合，命令量是乘法增长的。

## 2.4 底行模式命令集

| 命令 | 作用 |
|---|---|
| `:w` / `:q` / `:wq` | 保存 / 退出 / 保存并退出 |
| `:q!` | 强制退出不保存 |
| `:w!` | 强制保存（只读文件配合权限时用） |
| `/xxx` | 向下查找 xxx，`n` 下一个、`N` 上一个 |
| `?xxx` | 向上查找 |
| `:s/old/new/` | 替换当前行第一个 old |
| `:s/old/new/g` | 替换当前行所有 old |
| `:%s/old/new/g` | 全文替换（最常用） |
| `:set nu` / `:set nonu` | 显示 / 取消行号 |
| `:n`（数字） | 跳到第 n 行 |
| `:!命令` | 不退出 vim 执行 shell 命令，如 `:!ls` |

## 2.5 vim 配置（.vimrc）

`:set nu` 只对本次会话生效。想永久生效，写进家目录的配置文件 **`~/.vimrc`**，一行一条配置：

```vim
set nu          " 显示行号
set tabstop=4   " Tab 宽度 4
set autoindent  " 自动缩进
syntax on       " 语法高亮
```

vim 启动时自动读取该文件——每个用户各有一份，互不影响。

# 三、gcc / g++ 编译器

## 3.1 背景：翻译官的角色

计算机只认机器码。我们写的 C/C++ 是高级语言，需要"翻译官"把它变成 CPU 能执行的二进制——这个翻译过程就是**编译**，gcc 编译 C，g++ 编译 C++（g++ 是 gcc 家族里针对 C++ 的封装）。

> 直接看可执行文件是一堆乱码，因为那是给机器看的，不是给人看的。

## 3.2 编译四阶段（重点）

`gcc hello.c -o hello` 一条命令背后其实走了四步：

```
hello.c ──预处理──> hello.i ──编译──> hello.s ──汇编──> hello.o ──链接──> hello
           (-E)               (-S)              (-c)              (无选项)
```

| 阶段 | 选项 | 产物 | 干了什么 |
|---|---|---|---|
| **预处理** | `-E` | `.i` | 展开 `#include`（把头文件内容拷进来）、替换宏、去注释 |
| **编译** | `-S` | `.s` | 把 C 代码翻译成**汇编语言** |
| **汇编** | `-c` | `.o` | 把汇编翻译成**机器码**（可重定位目标文件） |
| **链接** | （默认） | 可执行文件 | 把多个 `.o` 和库文件"缝合"，确定函数最终地址 |

分步演示：

```bash
gcc -E hello.c -o hello.i    # 只预处理，停
gcc -S hello.i -o hello.s    # 到汇编，停
gcc -c hello.s -o hello.o    # 到目标文件，停
gcc hello.o -o hello         # 链接出可执行
```

平时都是一步到位 `gcc hello.c -o hello`，但理解四阶段对排查问题至关重要：**找不到头文件报在预处理/编译期，找不到函数实现报在链接期**——报错阶段不同，修法完全不同。

## 3.3 动态链接 vs 静态链接

`#include <stdio.h>` 只给了你 printf 的**声明**，它的**实现**在库里。链接就是去库里把实现接过来，有两种接法：

| | 动态链接 | 静态链接 |
|---|---|---|
| 库文件 | `.so`（shared object） | `.a`（archive） |
| 方式 | 程序里只记"地址"，**运行时**去共享库找 | 编译时把库代码**拷进**可执行文件 |
| 体积 | 小 | 大 |
| 依赖 | 运行机器必须装有对应 `.so` | 拷过去就能跑，零依赖 |
| 升级 | 库升级，所有程序一起受益 | 要重新编译 |

> 类比：动态链接像*点外卖*——你不需要厨房（库里不拷代码），但外卖平台（`.so`）倒了你就没饭吃；静态链接像*自备干粮*——走到哪吃到哪，但行李重。

gcc **默认动态链接**。加 `-static` 强制静态链接（系统需安装静态库）。

- `ldd ./hello`：查看可执行文件依赖哪些动态库、能不能找到——程序在别人机器上跑不起来，先 `ldd` 看一眼。
- 动态库找不到时的解决办法之一：设置环境变量 **`LD_LIBRARY_PATH`** 告诉加载器去哪个目录搜库。

## 3.4 静态库与动态库的制作（了解）

**静态库**：

```bash
gcc -c add.c -o add.o          # 先编出 .o
ar -rc libmymath.a add.o sub.o # ar 打包：r 插入/替换，c 创建
gcc main.c -L. -lmymath -o main  # 链接使用
```

**动态库**：

```bash
gcc -fPIC -c add.c -o add.o          # -fPIC 生成位置无关码
gcc -shared add.o -o libmymath.so    # -shared 生成动态库
gcc main.c -L. -lmymath -o main
export LD_LIBRARY_PATH=.             # 运行前让系统找得到
```

**三个关键链接选项**：

- `-I 目录`：告诉编译器去**哪找头文件**（编译期）
- `-L 目录`：告诉链接器去**哪找库文件**（链接期）
- `-l 名字`：链接哪个库。库文件叫 `libxxx.a/.so`，写 `-lxxx`（掐头去尾）

## 3.5 其他常用选项

| 选项 | 作用 |
|---|---|
| `-o 文件名` | 指定输出文件名 |
| `-g` | 加入调试信息（gdb 调试的前提） |
| `-Wall` | 打开常用警告（好习惯，建议常开） |
| `-std=c99` 等 | 指定语言标准 |
| `-O0 ~ -O3` | 优化等级，`-O0` 不优化（调试用），`-O2` 常用发布级别 |

> 调试时务必 `-g` 且配 `-O0`：优化会重排/删除代码，导致 gdb 里"行号乱跳、变量看不到"。

# 四、make / Makefile

## 4.1 背景：为什么需要 make

一个文件用 gcc 敲一条命令很爽，但真实项目几十上百个 `.c` 文件，还互相依赖，难道每次手写一长串 gcc？

> **gcc 回答"怎么编译"，make 回答"什么时候编译、编译哪些、按什么顺序编译"。** make 是"项目经理"，gcc 是"干活的工人"。

make 读一份叫 **Makefile** 的说明书，自动完成构建。

## 4.2 Makefile 的基本结构

```makefile
hello: hello.o          # 目标: 依赖
	gcc hello.o -o hello  # 命令（必须以 Tab 开头！）

hello.o: hello.s
	gcc -c hello.s -o hello.o

hello.s: hello.i
	gcc -S hello.i -o hello.s

hello.i: hello.c
	gcc -E hello.c -o hello.i

.PHONY: clean
clean:
	rm -f hello.i hello.s hello.o hello
```

三要素：

1. **目标（target）**：要生成的东西（也可以是动作，如 `clean`）
2. **依赖（dependency）**：生成它需要先有什么
3. **命令**：怎么生成，**行首必须是 Tab，不能是空格**——这是 Makefile 最著名的坑

## 4.3 make 的工作原理（重点）

**① 默认目标**：直接敲 `make`，只构建文件中**第一个**目标；`make clean` 才指定构建 clean。

**② 依赖递归推导**：make 发现 `hello` 依赖 `hello.o`，而 `hello.o` 不存在，就去文件里找"怎么造 `hello.o`"的规则，一路向下推，直到推到有现成文件（`hello.c`）为止，然后自底向上逐层执行——像递归/栈。

**③ 时间戳增量编译**：make 比较**目标与依赖的修改时间**——依赖比目标新，说明源文件被改过，目标需要重编；否则跳过。所以：

- 只改了 `hello.c` → 只会从受影响的环节开始重编，没动过的模块不重复编译，大项目省时明显。
- 连续敲两次 `make`，第二次提示 `is up to date` 什么都不做——因为没人变旧。
- 想强制重编？先 `make clean`。

**④ 伪目标 `.PHONY`**：`clean` 不生成文件，只是个动作名。如果目录里恰好有个叫 `clean` 的文件，make 会认为"目标已存在且够新"而拒绝执行。声明 `.PHONY: clean` 告诉 make："这是个假目标，永远要执行，别去比对时间戳"。

## 4.4 扩展语法：变量与自动变量

```makefile
CC = gcc
CFLAGS = -Wall -std=c99

hello: hello.c
	$(CC) $(CFLAGS) hello.c -o hello
```

- **变量**：`CC = gcc` 定义，`$(CC)` 引用。换编译器只改一行。
- **自动变量**：
  - `$@`：目标名（冒号左边）
  - `$^`：所有依赖（冒号右边全部）
  - `$<`：第一个依赖

```makefile
hello: hello.c
	$(CC) $^ -o $@     # 等价于 gcc hello.c -o hello
```

多文件项目的典型写法：每个 `.c` 编一个 `.o`，最后统一链接；头文件也要写进依赖里（头文件变了，包含它的 `.c` 就该重编）。

# 五、进度条小程序（练手 + 两个原理）

## 5.1 回车与换行（`\r` vs `\n`）

老打字机时代有两个动作：**回车**（Carriage Return，`\r`，0x0D）——把打印头*弹回本行行首*；**换行**（Line Feed，`\n`，0x0A）——纸张*滚到下一行*。合起来才是我们理解的"换行"。

- C 语言里 `\n` 一个字符就同时干了回车+换行两件事。
- **`\r` 只回到行首不换行**——后续输出会覆盖本行已有内容。这正是进度条"原地刷新"的秘密。

## 5.2 行缓冲区

`printf` 的内容不是立刻上屏的，而是先躺在 **stdout 缓冲区**里。显示器默认**行缓冲**：遇到 `\n` 或缓冲区满才一次性刷出。

所以这段代码会先"卡 3 秒"再显示 hello：

```c
printf("hello");   // 没有 \n，进缓冲区，不上屏
sleep(3);          // 睡了 3 秒，屏幕上什么都没有
```

解决：`fflush(stdout);` 强制立刻刷新缓冲区。进度条每秒刷新 100 次，每次都不能带 `\n`，全靠 `fflush`。

## 5.3 倒计时（原理应用）

```c
#include <stdio.h>
#include <unistd.h>

int main()
{
    int i = 10;
    while (i >= 0)
    {
        printf("%2d\r", i);   // %2d 两位宽度右对齐，避免 10→9 时残留 "0"
        fflush(stdout);       // 立刻上屏
        sleep(1);
        i--;
    }
    printf("\n");             // 结束换行，别把 shell 提示符盖了
    return 0;
}
```

## 5.4 进度条核心逻辑

思路：数组当"进度条画布"，循环 100 次——每轮多填一个 `#`，`\r` 回行首覆盖重打，`usleep` 控制速度，`fflush` 立即显示：

```c
char bar[101] = {0};
for (int i = 0; i <= 100; i++)
{
    printf("[%-100s][%3d%%]\r", bar, i);  // %-100s 左对齐固定宽度
    fflush(stdout);
    bar[i] = '#';
    usleep(50000);            // usleep 单位是微秒：50000us = 50ms
}
printf("\n");
```

格式符要点：`%-100s` 左对齐占 100 宽；`%3d` 保证 0~100 始终 3 位对齐；`%%` 输出字面百分号。

# 六、Git 版本管理

## 6.1 为什么需要版本控制

写代码常见灾难：改坏了想回退、想看看上周长什么样、多人改同一个文件打架。手动"复制文件夹改名 v1、v2、最终版、最终版2"是噩梦。**版本控制系统（VCS）**自动记录每次改动，随时穿越回任意历史版本。

**Git ≠ GitHub**：Git 是本地的版本控制*工具*；GitHub/Gitee 是托管 Git 仓库的*网站*。没有网、没有 GitHub，Git 在本机照样工作。

## 6.2 四区模型（核心概念）

```
工作区          暂存区           本地仓库          远程仓库
(Working Dir)  (Staging/Index)  (Local Repo)     (Remote Repo)
   │               │                │                 │
   │  git add ────>│                │                 │
   │               │ git commit ───>│                 │
   │               │                │  git push ─────>│
   │               │                │<───── git pull/clone
```

> 类比：**commit 就是游戏存档**。暂存区像"准备打包进行李箱"——你可以分多次 add，把想存进这个存档点的改动凑齐，再一次 commit 封箱。这样每个存档点都是一个语义完整的快照，而不是流水账。

- **`.git` 目录**：`git init` 后在项目根目录生成，所有版本历史都在里面——删了它，仓库历史就没了。
- **Commit ID**：每次提交的哈希指纹，全球唯一，是穿越版本的"坐标"。
- **分布式**：每人本地都有完整仓库和历史。集中式（SVN）断网=不能提交；Git 断网照常 commit，联网后再 push 同步。

## 6.3 常用命令

```bash
git init                 # 初始化本地仓库（生成 .git）
git clone <url>          # 从远程克隆整个仓库到本地

git status               # 查看状态：哪些改了、哪些已暂存（最高频命令）
git add 文件/目录         # 工作区 → 暂存区（git add . 暂存全部）
git commit -m "说明"      # 暂存区 → 本地仓库，-m 写存档说明
git log                  # 查看提交历史（--oneline 更简洁）
git diff                 # 查看工作区 vs 暂存区的具体改动

git push origin 分支名    # 本地仓库 → 远程仓库
git pull                 # 远程 → 本地（拉取并合并）
```

典型工作流就一句口诀：**改代码 → `add` → `commit` → `push`**。`status` 贯穿全程，随时用。

# 七、gdb / cgdb 调试器

## 7.1 背景与前提

程序出 bug 不靠猜、不靠满地 printf——用调试器**单步执行、看变量、设断点**。cgdb 是 gdb 的增强外壳，上面常驻显示源码，体验更好，命令完全兼容。

**前提**：编译必须带 `-g`（注入调试信息），且建议 `-O0`（关掉优化，否则代码被重排，行号对不上）：

```bash
gcc -g -O0 hello.c -o hello
gdb ./hello
```

发布版（release）不带 `-g`，无法有效调试。

## 7.2 常用命令（按使用顺序记）

| 命令 | 全称/含义 | 作用 |
|---|---|---|
| `l` | list | 查看源码（`l 行号` 看指定位置） |
| `b 行号` | break | 打断点；`b 函数名` 打在函数入口 |
| `info break` | — | 查看所有断点 |
| `r` | run | 运行（跑到断点停） |
| `n` | next | 单步：**逐过程**，函数调用一步跨过 |
| `s` | step | 单步：**逐语句**，遇到函数**进入**内部 |
| `c` | continue | 继续跑到下一个断点 |
| `p 变量` | print | 打印变量当前值 |
| `display 变量` | — | 每步自动显示该变量 |
| `undisplay 编号` | — | 取消自动显示 |
| `bt` | backtrace | 查看调用栈：当前函数是被谁调进来的 |
| `delete 编号` | — | 删除断点 |
| `q` | quit | 退出 gdb |

> 命令直接回车 = 重复上一条命令（单步时连按回车特别顺手）。

**next vs step 是高频考点**：遇到 `printf("...")` 或自定义函数调用，`n` 一步执行完整个函数；`s` 会钻进函数体内部逐行走。想排查函数内部用 `s`，信任函数只想看主流程用 `n`。

**几个进阶但实用的**：

- **条件断点**：`b 10 if i == 99999`——循环 10 万次，直接停在第 99999 次，不用按 99999 次 `c`。已存在的断点也能补条件：`condition 1 i == 99999`。
- **`watch 变量`**：监视变量，值一变就停——排查"变量不知在哪被改坏"的神器。
- **`set var i = 100`**：调试中直接改变量值，跳过漫长铺垫直达问题现场。
- **`p` 的输出带编号**：`$1 = 10`，之后可用 `$1` 引用历史结果。

**断点不修改源代码**——它只是调试器在运行时打的"停车标记"，删断点或退出 gdb 后程序原样。

**程序崩溃排查套路**：`r` 跑到崩溃 → `bt` 看调用栈定位崩在哪个函数哪一行 → 断点设在崩溃点之前 → `n/s` 逼近现场 + `p` 看变量找元凶。

# 附录：换软件源

默认源在国外的服务器，慢甚至已下线（CentOS 7、Ubuntu 20.04 都已过支持期），换国内镜像（阿里云、清华 TUNA、中科大 USTC）是常规操作。

**通用套路三步**：

1. **备份原配置**
   ```bash
   # CentOS
   sudo cp /etc/yum.repos.d/CentOS-Base.repo /etc/yum.repos.d/CentOS-Base.repo.bak
   # Ubuntu
   sudo cp /etc/apt/sources.list /etc/apt/sources.list.bak
   ```
2. **写入新源**：从镜像站帮助页复制对应系统版本的源内容，覆盖原文件。CentOS 7 已过 EOL，地址要指向 vault 存档或镜像站的 centos-vault 目录；Ubuntu 20.04 换镜像源照常（镜像站保留历史版本）。
3. **刷新缓存**
   ```bash
   # CentOS
   sudo yum clean all && sudo yum makecache
   # Ubuntu
   sudo apt update
   ```

换完源 `yum/apt` 速度立竿见影，报错"找不到仓库"也基本痊愈。
