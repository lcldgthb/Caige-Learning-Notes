# 2. 基础开发工具

> 这份文档根据《2,,基础开发工具.md》的正式标题重新组织，采用“先提出问题，再用一个完整例子验证”的方式讲解。
>
> 本章的主线不是背命令，而是完成一条真实的 Linux 开发链路：
>
> ```text
> 软件包管理器 → Vim 编辑代码 → gcc/g++ 编译 → Makefile 自动构建
>        ↓                                      ↓
>   Git 管理版本                         gdb/cgdb 定位问题
>        ↓
>      进度条：把前面学到的工具组合成第一个 Linux 程序
> ```
>
> 文中的终端输出采用脱敏后的示例。不同发行版、用户名、软件版本和终端主题会造成输出差异，但判断方法是一样的。

## 本节目标

学完本章后，应该能够完成下面这件事：在一个 Linux 开发目录中创建一个小型 C/C++ 程序，用 Vim 编辑，用 gcc/g++ 编译，用 Makefile 重复构建，用 Git 保存版本，并在程序出错时使用 gdb 定位问题。

具体目标如下：

- 知道什么是软件包、软件源和依赖，能用 yum/dnf 或 apt 查找、安装、验证和卸载软件。
- 能用 Vim 完成“打开文件、输入内容、保存退出、重新查看”的闭环，不再被 Vim 的模式切换卡住。
- 理解预处理、编译、汇编、链接四个阶段，并能看到每个阶段产生的文件。
- 能写出包含目标、依赖、配方和 `clean` 伪目标的基础 Makefile，理解为什么第二次 `make` 可能不再编译。
- 理解 `\r`、`\n`、标准输出缓冲和 `fflush`，完成一个可复用的进度条。
- 理解 Git 的工作区、暂存区、本地仓库和远端仓库，掌握 `status/add/commit/push` 的关系。
- 能使用 `-g` 编译调试版本，用断点、单步、打印变量、观察变量和条件断点定位问题。

## 1. 软件包管理器

先思考一个问题：如果想在 Linux 上使用 `vim`、`gcc` 或 `git`，是不是只能去网上下载源代码，然后自己编译？

当然不是。Linux 通常通过软件包管理器，从软件源下载已经构建好的软件包，并自动处理依赖。

```text
软件包：已经编译好的可安装文件
软件源：存放软件包和索引信息的服务器
包管理器：查询、下载、安装、升级、卸载软件的工具
依赖：目标软件运行或安装时需要的其他软件/库
```

一次安装大致经过：

```text
输入安装命令
    ↓
读取软件源索引
    ↓
查找目标包和依赖包
    ↓
下载软件包
    ↓
校验并写入系统目录
    ↓
更新软件数据库
    ↓
用版本命令验证
```

### 1-1 什么是软件包

在 Linux 中，一个软件通常不只是一个可执行文件，还可能包含：

- 可执行文件，例如 `/usr/bin/git`。
- 动态库，例如 `/usr/lib64/libxxx.so`。
- 配置文件，例如 `/etc/xxx.conf`。
- 手册页，例如 `/usr/share/man/` 下的文件。
- 依赖信息、版本信息和卸载清单。

把这些内容按照统一格式打包，就得到软件包。以 RPM 系为例，软件包通常以 `.rpm` 结尾；Debian 系通常以 `.deb` 结尾。

可以类比 Windows：

```text
Windows 安装程序       Linux 软件包
       ↓                      ↓
      .exe                  .rpm/.deb
       ↓                      ↓
    安装向导             yum/dnf/apt 处理
```

但 Linux 的包管理器不仅仅是“点下一步”。它还会根据软件包的元数据寻找依赖。例如安装一个开发工具时，可能同时需要安装库文件、头文件或其他运行库。

**从源代码编译和安装软件包有什么区别？**

```text
源代码安装：下载源码 → 配置 → 编译 → 安装 → 自己处理依赖
软件包安装：查询仓库 → 下载预编译包 → 自动处理依赖 → 安装
```

源代码安装更灵活，可以选择版本和编译选项；软件包安装更快、更容易升级和卸载。初学阶段优先使用包管理器，真正需要定制版本或编译选项时再研究源码安装。

### 1-2 Linux 软件生态

不同发行版的包管理器不同，但背后的逻辑相同：

| 系统家族 | 常见工具 | 软件包格式 | 常见查询工具 |
|---|---|---|---|
| CentOS/RHEL/Fedora | `yum`、`dnf` | RPM | `rpm` |
| Ubuntu/Debian | `apt`、`apt-get` | DEB | `dpkg` |

例如，在 CentOS/RHEL 系中：

```bash
yum search git
yum info git
sudo yum install -y git
rpm -q git
```

在 Ubuntu/Debian 系中：

```bash
apt search git
apt show git
sudo apt install -y git
dpkg -s git
```

这里的 `sudo` 表示“以被授权的更高权限执行这一条命令”，不是把当前 Shell 永久切换成 root。安装软件通常需要向 `/usr/bin`、`/etc` 等系统目录写入内容，所以普通用户需要 `sudo` 或管理员授权。

**为什么有很多镜像源？**

软件源本质上是软件包索引和文件的发布位置。国内镜像站通常通过同步上游仓库来缩短网络距离，提高下载速度和稳定性。镜像不是“另一个版本的 Linux”，也不是软件本身；它只是提供软件包的一个下载入口。

```text
上游仓库
    ↓ 同步
国内镜像站
    ↓ 提供索引与软件包
本机包管理器
    ↓
安装到本机
```

软件生态的价值在于：软件可以被打包、验证、分发和升级。一个操作系统是否好用，不只取决于内核，还取决于编译器、调试器、库、数据库、网络工具和社区文档是否丰富。

### 1-3 yum 具体操作

这一节用 `lrzsz` 作为示例包。它只是演示包管理流程，实际操作时也可以换成 `tree`、`vim-enhanced` 或其他确认过的软件包。

完整流程如下：

```text
确认系统 → 检查网络 → 搜索软件包 → 查看详情
    → 安装 → 查询验证 → 使用 → 卸载 → 再次验证
```

#### 1-3-1 查看软件包

先不要急着安装，先确认仓库里有没有这个包。

在 CentOS 7/RHEL 系环境中，可以这样查询：

```bash
[root@localhost ~]# cat /etc/redhat-release
CentOS Linux release 7.x.x (Core)

[root@localhost ~]# yum list | grep '^lrzsz\.'
lrzsz.x86_64                    0.12.20-36.el7                    epel
```

这一行可以拆成：

```text
lrzsz        x86_64       0.12.20-36.el7       epel
│            │            │                    │
│            │            │                    └── 软件源名称
│            │            └────────────────────── 版本与发行版标记
│            └────────────────────────────────── CPU 架构
└────────────────────────────────────────────── 软件包名称
```

- `lrzsz` 是包名。
- `x86_64` 表示面向 64 位 x86 架构。
- `0.12.20-36.el7` 中的 `el7` 通常表示 Enterprise Linux 7 生态。
- `epel` 表示这个包来自扩展软件源，不一定来自系统基础源。

Ubuntu 中对应的查询过程可能是：

```bash
student@ubuntu:~$ apt search lrzsz
Sorting... Done
Full Text Search... Done
lrzsz/jammy 0.12.21-10 amd64
  Tools for zmodem/xmodem/ymodem file transfer

student@ubuntu:~$ apt show lrzsz
Package: lrzsz
Version: 0.12.21-10
Architecture: amd64
Section: universe/comm
```

`apt search` 的输出通常用于“找包”，`apt show` 用于查看包的版本、架构、描述和依赖信息。不同 Ubuntu 版本的版本号可能不同，不能把课件中的版本号当成固定答案。

如果只想看已安装的软件包，可以使用：

```bash
rpm -qa | grep lrzsz       # RPM 系
apt list --installed 2>/dev/null | grep lrzsz  # Debian 系
```

**观察结果**：搜索成功只说明“仓库索引中能找到它”，还不等于它已经安装。判断安装状态要看 `rpm -q`、`dpkg -s` 或执行软件本身的版本命令。

#### 1-3-2 安装软件

确认软件包后再安装：

```bash
[root@localhost ~]# sudo yum install -y lrzsz
……省略依赖解析和下载进度……
Installed:
  lrzsz.x86_64 0:0.12.20-36.el7

Complete!
```

Ubuntu 的写法是：

```bash
student@ubuntu:~$ sudo apt install -y lrzsz
……省略下载进度……
Setting up lrzsz (...)
```

这里的 `-y` 表示对安装过程中的确认问题自动回答 yes。学习阶段可以使用，但在生产环境安装关键软件前，建议先不加 `-y`，查看将要安装、升级或删除哪些包。

安装完成后不要只看 `Complete!`，还要验证：

```bash
[root@localhost ~]# rpm -q lrzsz
lrzsz-0.12.20-36.el7.x86_64

[root@localhost ~]# command -v rz
/usr/bin/rz

[root@localhost ~]# command -v sz
/usr/bin/sz
```

Ubuntu 中可以使用：

```bash
student@ubuntu:~$ dpkg -s lrzsz | grep -E '^(Status|Version|Architecture):'
Status: install ok installed
Version: 0.12.21-10
Architecture: amd64
```

**安装过程中发生了什么？**

```text
sudo
  ↓ 获得写系统目录的授权
包管理器读取仓库索引
  ↓
解析 lrzsz 的依赖
  ↓
下载对应架构的软件包
  ↓
写入程序、手册和数据库记录
  ↓
命令出现在 PATH 中
```

如果输出中出现依赖包，说明包管理器正在为目标包准备运行环境。若出现“无法获取锁”，通常说明另一个包管理进程正在工作，不要同时强行启动多个安装操作。

#### 1-3-3 卸载软件

卸载前先确认包名，不要把相似包名看错：

```bash
[root@localhost ~]# rpm -q lrzsz
lrzsz-0.12.20-36.el7.x86_64

[root@localhost ~]# sudo yum remove lrzsz
……显示将要删除的内容……
Is this ok [y/N]: y
……省略过程……
Complete!
```

Ubuntu 中：

```bash
student@ubuntu:~$ sudo apt remove lrzsz
```

卸载后再次验证：

```bash
[root@localhost ~]# rpm -q lrzsz
package lrzsz is not installed

[root@localhost ~]# command -v rz || echo 'rz 已不存在'
rz 已不存在
```

`remove` 一般会删除软件及其注册信息，但配置文件、用户自己创建的数据或被其他软件共享的依赖可能有不同处理方式。执行卸载前应阅读包管理器列出的变更列表。

#### 1-3-4 注意事项

**第一，网络要先通。**

```bash
[root@localhost ~]# ping -c 3 example.com
64 bytes from ...: icmp_seq=1 ttl=... time=...
64 bytes from ...: icmp_seq=2 ttl=... time=...
--- example.com ping statistics ---
3 packets transmitted, 3 received, 0% packet loss
```

能解析域名并收到回复，说明当前网络检查基本通过；如果域名解析失败，可以分别检查网络地址、DNS 和防火墙。`ping` 失败不一定等于 HTTP 软件源一定不可用，因为有些主机禁止 ICMP。

**第二，区分包管理器和软件本身。**

```text
yum/apt：管理软件包
lrzsz：被管理的软件
软件源：提供软件包的位置和索引
```

**第三，不能并发操作同一个包数据库。**

如果另一个 `yum`/`dnf`/`apt` 正在更新索引或安装软件，当前命令可能出现锁错误。先确认是否真有另一个包管理进程在运行，不要直接删除锁文件。

**第四，输出会变化。** 软件版本、镜像源、发行版和 CPU 架构不同，下载大小、依赖数量和提示文字都会变。学习时抓住“包名、版本、架构、成功/失败原因”这些稳定信息。

### 1-4 安装源

软件源配置文件记录了包管理器去哪里查找软件包。常见目录如下：

```text
/etc/
├── yum.repos.d/
│   ├── CentOS-Base.repo       # 基础源配置
│   └── epel.repo              # 扩展源配置
└── apt/
    ├── sources.list           # 主配置
    └── sources.list.d/        # 分片配置目录
```

CentOS/RHEL 系中可以查看：

```bash
[root@localhost ~]# ls -l /etc/yum.repos.d/
total 8
-rw-r--r-- 1 root root  680 Sep 20 12:00 CentOS-Base.repo
-rw-r--r-- 1 root root  230 Sep 20 12:01 epel.repo

[root@localhost ~]# yum repolist
repo id             repo name                 status
base/7/x86_64       CentOS-7 - Base           ...
epel/x86_64         Extra Packages for EL 7   ...
```

Ubuntu 中可以查看：

```bash
student@ubuntu:~$ cat /etc/apt/sources.list
student@ubuntu:~$ ls -l /etc/apt/sources.list.d/
```

`/etc/yum.repos.d/` 和 `/etc/apt/sources.list.d/` 中的文件只是配置，不是已经安装的软件。修改源之前应先备份，并确认系统版本、发行版代号和镜像站说明完全匹配。CentOS 7 已结束标准维护，直接照抄旧教程更换源可能导致仓库失效；优先参考当前发行版和镜像站的官方说明。

## 2. 编辑器 Vim

### 2-1 Linux 编辑器-vim 使用

Vim 是运行在终端中的文本编辑器，适合在远程 Linux 主机上修改源代码和配置文件。vi 是传统编辑器，Vim 是兼容 vi 并增加了语法高亮、搜索、撤销、多窗口等功能的改进版本。

不要把 Vim 理解成“打开后直接输入文字的记事本”。Vim 启动后默认处于普通模式，键盘上的字母首先被解释为编辑命令。

先完成一个最小闭环：

```text
vim test.c
   ↓
按 i 进入插入模式
   ↓
输入 C 程序
   ↓
按 Esc 回到普通模式
   ↓
输入 :wq 保存并退出
   ↓
cat/编译/运行验证
```

创建示例目录：

```bash
mkdir -p ~/tool_demo/vim-demo
cd ~/tool_demo/vim-demo
vim test.c
```

在 Vim 中输入下面的程序：

```c
#include <stdio.h>

int main(void)
{
    printf("hello vim!\n");
    return 0;
}
```

退出后验证文件确实被保存：

```bash
$ cat test.c
#include <stdio.h>

int main(void)
{
    printf("hello vim!\n");
    return 0;
}

$ gcc test.c -o test
$ ./test
hello vim!
```

这里的 `cat` 是对 Vim 操作结果的外部验证：不要只相信“我按了保存”，要重新读取文件并编译运行。

### 2-2 vim 的基本概念

本章先掌握三种模式：

```text
                    ┌──────────────┐
                    │  普通模式     │
                    │ 移动/删除/复制 │
                    └──────┬───────┘
                         i/a/o│  │:
                ┌────────────▼  ▼────────────┐
                │ 插入模式       底行模式      │
                │ 输入文本       :wq/:q!/搜索  │
                └──────┬──────────────┬──────┘
                       Esc            Enter
                        └────回到普通模式────┘
```

**普通模式（Normal mode）**：启动 Vim 默认所在的模式。这里的 `h/j/k/l` 用于移动，`dd` 删除一行，`yy` 复制一行，`p` 粘贴，`u` 撤销。

**插入模式（Insert mode）**：只有进入插入模式，输入的字母才会作为正文写入文件。按 `Esc` 返回普通模式。

**底行模式（Command-line mode）**：在普通模式按 `:` 进入，用于保存、退出、搜索、替换、设置显示行号等。

可以把模式理解为“同一个键盘在不同状态下有不同含义”：

| 当前模式 | 按 `w` 的典型含义 |
|---|---|
| 普通模式 | 跳到下一个单词开头 |
| 插入模式 | 输入一个字符 `w` |
| 底行模式 | 作为命令文本的一部分 |

Vim 还有更多模式，例如可视模式、替换模式等，但初学阶段先用三种模式完成编辑闭环。

### 2-3 vim 的基本操作

**打开文件后发生什么？**

```bash
$ vim test.c
```

屏幕底部可能看到文件名、行数或 `[New File]`，光标位于普通模式。此时直接输入 `hello` 不会把 `hello` 写进文件，而是依次触发普通模式下的命令。

正确的输入过程是：

```text
1. vim test.c       启动，进入普通模式
2. i                进入插入模式
3. 输入文本         文件内容发生变化
4. Esc              回到普通模式
5. :w               保存但不退出
6. :q               退出
```

也可以一步完成保存退出：

```text
Esc → :wq → Enter
```

如果不想保存修改：

```text
Esc → :q! → Enter
```

`q!` 中的感叹号表示强制退出并放弃当前未保存内容。可以做一个对比实验：先打开文件，加入一行文字，然后分别使用 `:wq` 和 `:q!`，退出后用 `cat` 查看差异。

### 2-4 vim 正常模式命令集

这一节不要把命令当成孤立的按键，而要把它们放进“移动 → 选中/定位 → 修改 → 撤销”的操作链。

**插入位置的对比**：假设当前行是：

```text
hello world
     ^
     光标位于 o
```

- `i`：在光标前进入插入模式。
- `a`：在光标后进入插入模式。
- `o`：在当前行下方新建一行并进入插入模式。
- `O`：在当前行上方新建一行并进入插入模式。

**移动命令**：

- `h`、`j`、`k`、`l`：左、下、上、右。
- `0` 或 `^`：移动到行首。
- `$`：移动到行尾。
- `w`：下一个单词开头。
- `e`：下一个单词结尾。
- `b`：上一个单词开头。
- `gg`：文件开头。
- `G`：文件末尾。
- `15G`：跳到第 15 行。
- `Ctrl+B`/`Ctrl+F`：向上/向下翻页。

**删除命令**：

```text
x      删除光标所在字符
X      删除光标前一个字符
dd     删除当前行
3dd    从当前行开始删除 3 行
dw     删除到下一个单词开头
```

**复制和粘贴**：

```text
yy     复制当前行
3yy    复制当前行及下面共 3 行
p      在光标后/下一行粘贴
P      在光标前/上一行粘贴
```

**修改和撤销**：

```text
r      替换当前字符
R      连续替换，按 Esc 结束
u      撤销
Ctrl+r 重做
cw     修改当前单词
```

完整操作示例：

```text
普通模式：gg       → 回到文件开头
普通模式：/printf  → 搜索 printf，按 Enter
普通模式：n        → 找下一个匹配
普通模式：dd       → 删除当前行
普通模式：u        → 撤销删除
普通模式：yy       → 复制当前行
普通模式：p        → 粘贴
```

每完成一组操作，都可以用 `:w` 保存，再用 `cat -n test.c` 检查行号和内容。

### 2-5 vim 末行模式命令集

进入末行模式前，先按 `Esc` 确保处于普通模式，再按 `:`。输入命令后按 Enter 执行。

| 命令 | 作用 | 结果 |
|---|---|---|
| `:w` | 保存 | 留在 Vim 中 |
| `:w 文件名` | 另存为 | 写出一个新文件 |
| `:q` | 退出 | 文件未修改或已保存时有效 |
| `:wq` | 保存并退出 | 最常用的正常退出方式 |
| `:q!` | 放弃修改并退出 | 不保存当前修改 |
| `:set nu` | 显示行号 | 左侧出现行号 |
| `:set nonu` | 取消行号 | 隐藏行号 |
| `:15` | 跳到第 15 行 | 光标移动 |
| `:/main` | 向下搜索 main | 跳到匹配位置 |
| `:?main` | 向上搜索 main | 反向查找 |
| `:%s/old/new/g` | 全文替换 | 替换所有匹配项 |

搜索示例：

```text
Esc → /printf → Enter
```

屏幕会跳到第一个匹配位置，按 `n` 查找下一个，按 `N` 查找上一个。`/` 和 `?` 的区别是搜索方向不同。

保存退出失败时，先看错误提示：如果文件没有写权限，`:wq` 不会 magically 解决权限问题。可以退出后检查 `ls -l`，确认文件所有者和目录权限，不要为了保存一个普通文件而直接以 root 覆盖系统文件。

### 2-6 vim 操作总结

Vim 的最小生存流程可以压缩成：

```text
启动 Vim
  ↓
普通模式：i/a/o
  ↓
插入模式：输入文字
  ↓
Esc 回普通模式
  ↓
:wq 保存退出
  ↓
cat/编译验证
```

遇到“我怎么输入不了文字”：按 `i`。

遇到“我退不出去”：按 `Esc`，再输入 `:q!` 并按 Enter。

遇到“我误删了内容”：按 `u`。

遇到“我不知道当前在哪种模式”：按 `Esc` 通常可以安全回到普通模式，然后再决定下一步。

### 2-7 简单 vim 配置 [了解]

Vim 配置分为系统级和用户级：

```text
/etc/vimrc       系统级配置，可能影响所有用户
~/.vimrc         当前用户配置，只影响当前用户
```

建议先使用用户级配置，不要直接修改系统文件。一个最小配置如下：

```vim
syntax on
set number
set shiftwidth=4
set tabstop=4
set expandtab
```

保存为 `~/.vimrc` 后重新打开 Vim 即可观察效果：

```text
vim-demo/
├── test.c
└── ~/.vimrc
```

插件可以提供代码浏览、文件树和补全等功能，但插件安装会引入版本、路径和兼容性问题。初学阶段先掌握原生 Vim 和 `vimtutor`：

```bash
vimtutor
```

`vimtutor` 会打开一份交互式教程，建议在独立终端中按照提示练习，不要把教程中的按键误操作到重要源文件。

## 3. 编译器 gcc/g++

### 3-1 背景知识

编译器的任务不是“把文本直接变成程序”这么简单。以 C 程序为例，通常经历四个阶段：

```text
hello.c
  ↓ 预处理：展开头文件、宏替换、条件编译、去注释
hello.i
  ↓ 编译：检查语法和语义，生成汇编
hello.s
  ↓ 汇编：把汇编指令编码成目标文件
hello.o
  ↓ 链接：合并目标文件，解析外部符号，加入库
hello
```

可以先创建最小源文件：

```c
#include <stdio.h>

#define MESSAGE "hello gcc"

int main(void)
{
    printf("%s\\n", MESSAGE);
    return 0;
}
```

目录变化如下：

```text
gcc-demo/
└── hello.c

执行预处理后：
gcc-demo/
├── hello.c
└── hello.i

完成四阶段后：
gcc-demo/
├── hello.c
├── hello.i
├── hello.s
├── hello.o
└── hello
```

### 3-2 gcc 编译选项

基本格式：

```bash
gcc [选项] 源文件 [选项] 输出文件
```

最容易理解的学习方法是：每次只让 gcc 走到一个阶段，并检查目录中新增了什么。

#### 3-2-1 预处理（进行宏替换）

预处理主要完成：

- 展开 `#include` 文件。
- 替换 `#define` 宏。
- 根据 `#if`、`#ifdef` 进行条件编译。
- 删除注释。
- 处理部分编译控制指令。

命令使用 ASCII 短横线：

```bash
$ gcc -E hello.c -o hello.i
$ ls
hello.c  hello.i
$ wc -l hello.c hello.i
   9 hello.c
  ... hello.i
```

`-E` 表示预处理完成后停止，`-o hello.i` 指定输出文件。打开前几十行，通常可以看到大量头文件展开内容：

```bash
$ head -n 12 hello.i
# 0 "hello.c"
# 1 "/usr/include/..."
typedef ...
...
```

不同系统的头文件内容和行数差异很大，但你应该观察到：`hello.i` 通常比 `hello.c` 长很多，宏 `MESSAGE` 已经不再以原样出现，注释也被处理掉了。

**注意**：若只执行 `gcc -E hello.c`，结果默认输出到终端；使用 `-o hello.i` 才会把结果写入文件。源课件中“`-E` 不生成文件”和“`-o hello.i`”并不矛盾，准确说法是：`-E` 不自动生成默认的最终可执行文件，但可以配合 `-o` 保存预处理结果。

#### 3-2-2 编译（生成汇编）

编译阶段会检查语法、类型和语义，并把预处理后的 C 代码翻译成汇编代码。使用 `-S` 后在生成汇编文件时停止：

```bash
$ gcc -S hello.i -o hello.s
$ ls
hello.c  hello.i  hello.s
$ head -n 20 hello.s
        .file   "hello.c"
        .text
        .globl  main
main:
        ...
```

`hello.s` 是人类还能大致阅读的汇编文本，但它不是最终可执行文件。不同 CPU 架构的汇编格式不同，x86-64、ARM64 的内容不会一样。

也可以直接从源文件生成汇编：

```bash
gcc -S hello.c -o hello.s
```

gcc 会自动完成前面的预处理，但学习阶段分步执行更容易观察产物。

#### 3-2-3 汇编（生成机器可识别代码）

汇编阶段把 `hello.s` 翻译成目标文件：

```bash
$ gcc -c hello.s -o hello.o
$ ls -l hello.o
-rw-r--r-- 1 user user  ... Sep 20 12:10 hello.o
$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1, not stripped
```

`.o` 是 ELF 格式的可重定位目标文件。它包含机器指令、符号表和重定位信息，但通常还不能直接运行，因为 `printf` 等外部符号尚未和实际库实现连接起来。

也可以让 gcc 从 C 源文件直接停止在目标文件：

```bash
gcc -c hello.c -o hello.o
```

#### 3-2-4 连接（生成可执行文件或库文件）

链接阶段把一个或多个 `.o` 文件合并起来，并解析外部符号：

```bash
$ gcc hello.o -o hello
$ file hello
hello: ELF 64-bit LSB pie executable, x86-64, dynamically linked, ...
$ ./hello
hello gcc
```

链接器需要解决的问题包括：

- `main` 等入口和程序内部符号在哪里。
- `printf` 的实现位于哪个库。
- 多个目标文件之间的函数调用如何关联。
- 程序运行时需要加载哪些动态库。

最终产物通常有执行权限：

```bash
$ ls -l hello
-rwxr-xr-x 1 user user ... hello
```

如果看到 `undefined reference`，通常说明某个函数的实现没有被正确链接；如果看到 `No such file or directory`，可能是输入源文件、目标文件或动态加载器路径问题。

### 3-3 动态链接和静态链接

假设有两个程序都调用 `printf`：

```text
程序 A ─┐
        ├── printf 的实现
程序 B ─┘
```

静态链接会把需要的库代码复制进每个可执行文件：

```text
程序 A + libc 部分代码
程序 B + libc 部分代码
```

动态链接则让多个程序在运行时共享同一份动态库：

```text
程序 A ─┐
程序 B ─┼── /lib/.../libc.so.6
程序 C ─┘
```

动态链接可以减小可执行文件体积、共享内存并方便库升级，但运行时必须找到兼容的动态库。使用 `ldd` 查看动态依赖：

```bash
$ ldd hello
        linux-vdso.so.1 =>  (0x...)
        libc.so.6 => /lib64/libc.so.6 (0x...)
        /lib64/ld-linux-x86-64.so.2 (0x...)
```

地址会随系统和运行环境变化，重点看库的名称和路径。`libc.so.6` 中通常包含 C 运行库实现，`ld-linux...` 是动态加载器。

**为什么源文件里没有 `printf` 的函数体，程序仍然能运行？**

```text
hello.o 中留下 printf 的未解析符号
        ↓ 链接器查找 C 运行库
libc.so.6 提供 printf 的实现
        ↓
生成可执行文件
        ↓ 运行时加载动态库
```

可以用 `nm`（若已安装）观察符号，但不需要把符号表全部背下来：

```bash
nm -D /lib64/libc.so.6 | grep ' printf@@' | head
```

### 3-4 静态库和动态库

Linux 中常见后缀：

| 类型 | 常见后缀 | 代码进入程序的时间 | 典型特点 |
|---|---|---|---|
| 静态库 | `.a` | 链接时 | 可执行文件较大，运行时对该库依赖较少 |
| 动态库 | `.so` | 运行时加载 | 可共享、文件较小，但运行环境必须有兼容库 |

可以用 `file` 和 `ldd` 做观察：

```bash
$ gcc hello.c -o hello-dynamic
$ file hello-dynamic
hello-dynamic: ... dynamically linked ...
$ ldd hello-dynamic
        libc.so.6 => ...

$ gcc hello.c -static -o hello-static
$ file hello-static
hello-static: ... statically linked ...
```

静态链接不一定在每台机器上都能成功，因为系统可能没有安装对应的静态库包；即使成功，最终文件也通常更大。不要把 `-static` 当成“肯定更好”，它可能增加体积、限制动态安全更新，并遇到 glibc 等库的兼容性问题。

自定义库的基本关系可以记成：

```text
源文件 → .o
多个 .o → 静态库 .a 或动态库 .so
程序 + 库 → 链接 → 可执行文件
```

RHEL/CentOS 系环境可能需要安装静态库开发包，例如：

```bash
sudo yum install glibc-static libstdc++-static
```

安装前先确认发行版和软件源，不要在不了解依赖的情况下对服务器执行升级操作。

### 3-5 gcc 其他常用选项 - 了解即可

| 选项 | 作用 | 示例 |
|---|---|---|
| `-E` | 预处理后停止 | `gcc -E a.c -o a.i` |
| `-S` | 生成汇编后停止 | `gcc -S a.c -o a.s` |
| `-c` | 生成目标文件后停止 | `gcc -c a.c -o a.o` |
| `-o` | 指定输出文件 | `gcc a.c -o app` |
| `-g` | 生成调试信息 | `gcc -g a.c -o app-debug` |
| `-Wall` | 开启一组常见警告 | `gcc -Wall a.c -o app` |
| `-Wextra` | 开启更多警告 | `gcc -Wall -Wextra a.c` |
| `-O0` | 基本不优化，便于调试 | `gcc -O0 -g a.c` |
| `-O2` | 常用优化级别 | `gcc -O2 a.c -o app` |
| `-static` | 尝试静态链接 | `gcc -static a.c` |
| `-shared` | 构建动态库时使用 | `gcc -shared -fPIC ...` |
| `-w` | 关闭警告，不建议常用 | `gcc -w a.c` |

`-Wall` 不是“开启所有可能的警告”，而是一组常见且有价值的警告集合。开发时推荐：

```bash
gcc -Wall -Wextra -g -O0 hello.c -o hello-debug
```

没有 `-g` 仍然可以正常编译和运行，只是 gdb 不能很好地关联源代码行和变量。`-g` 不会自动修复程序逻辑错误。

## 4. 自动化构建-make/Makefile

### 4-1 背景

项目小的时候，手工执行两条命令似乎没有问题：

```bash
gcc -c main.c -o main.o
gcc main.o -o app
```

但项目一旦有几十个源文件，手工编译会遇到三个问题：

1. 命令太多，容易漏写或写错。
2. 只修改一个源文件，却可能重复编译全部文件。
3. 清理中间产物、执行测试和打包发布都需要另外记命令。

Makefile 用声明式规则记录这些关系，`make` 根据目标和依赖的时间戳决定要执行哪些命令。

```text
Makefile：描述目标、依赖和生成命令
make：读取 Makefile 并按依赖关系执行
```

### 4-2 理解

先用生活中的例子理解“目标—依赖”：月底要提交报销单，报销单依赖发票，发票依赖消费记录；如果消费记录没变，没必要重新整理全部内容。

程序构建也一样：

```text
app
├── main.o
│   └── main.c
└── util.o
    └── util.c
```

如果只修改 `util.c`，合理的构建工具应该只重新生成 `util.o`，然后重新链接 `app`，而不是重新编译没有变化的 `main.c`。

### 4-3 基本使用

先准备源文件 `myproc.c`：

```c
#include <stdio.h>

int main(void)
{
    printf("hello Makefile!\n");
    return 0;
}
```

手工编译：

```bash
$ gcc -c myproc.c -o myproc.o
$ gcc myproc.o -o myproc
$ ./myproc
hello Makefile!
```

目录如下：

```text
make-demo/
├── myproc.c
├── myproc.o
└── myproc
```

接下来创建 `Makefile`。下面的配方行必须使用真实的 Tab 缩进，而不是普通空格：

```makefile
myproc: myproc.o
	gcc myproc.o -o myproc

myproc.o: myproc.c
	gcc -c myproc.c -o myproc.o

.PHONY: clean
clean:
	rm -f myproc.o myproc
```

执行第一次构建：

```bash
$ rm -f myproc.o myproc
$ make
 gcc -c myproc.c -o myproc.o
 gcc myproc.o -o myproc
$ ls
Makefile  myproc  myproc.c  myproc.o
```

有些 make 会显示命令前没有多余空格，有些版本会显示 `gcc ...`；重点是两个目标都被重新生成。

第二次构建：

```bash
$ make
make: 'myproc' is up to date.
```

如果当前 make 输出为空，也可能表示目标已经是最新。此时没有重复执行 gcc，是 Makefile 的价值之一。

修改源文件后：

```bash
$ printf '\n/* changed */\n' >> myproc.c
$ make
gcc -c myproc.c -o myproc.o
gcc myproc.o -o myproc
```

因为 `myproc.c` 的修改时间比 `myproc.o` 新，所以先重新生成目标文件，再重新链接。

清理：

```bash
$ make clean
rm -f myproc.o myproc
$ ls
Makefile  myproc.c
```

`clean` 通常不是实际要生成的文件，而是一个操作目标，所以要用 `.PHONY: clean` 声明，保证当前目录即使出现名为 `clean` 的文件，也会执行清理命令。

### 4-4 推导过程

make 运行时可以理解为以下步骤：

```text
执行 make
   ↓
寻找 Makefile 或 makefile
   ↓
选择第一个目标作为默认目标
   ↓
检查目标 myproc 是否存在
   ↓
检查依赖 myproc.o 是否存在且是否更新
   ├── 不需要更新 → 不执行配方
   └── 需要更新 → 先构建 myproc.o
                         ↓
                    再链接 myproc
```

更详细的依赖关系：

```text
myproc
  └── myproc.o
        └── myproc.c
```

实验时间戳：

```bash
$ stat -c '%y %n' myproc.c myproc.o myproc
2026-09-20 10:00:00 myproc.c
2026-09-20 10:01:00 myproc.o
2026-09-20 10:01:00 myproc

$ touch myproc.c
$ make
gcc -c myproc.c -o myproc.o
gcc myproc.o -o myproc
```

`touch` 没有改变源代码内容，但更新了修改时间，make 仍然会认为源文件更新了，因此重新构建。make 关注的是文件依赖和时间戳，不会自动理解“文件内容是否真的变化”。

如果依赖文件不存在，make 会继续寻找生成它的规则；如果找不到规则，就会报错：

```text
make: *** No rule to make target 'missing.h', needed by 'main.o'.  Stop.
```

### 4-5 适度扩展语法

当源文件多起来时，可以使用变量、通配符和模式规则：

```makefile
CC := gcc
CFLAGS := -Wall -Wextra -g
TARGET := myproc
SRC := $(wildcard *.c)
OBJ := $(SRC:.c=.o)

$(TARGET): $(OBJ)
	$(CC) $(CFLAGS) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

.PHONY: clean test
clean:
	rm -f $(OBJ) $(TARGET)

test: $(TARGET)
	./$(TARGET)
```

自动变量：

- `$@`：当前规则的目标名。
- `$^`：当前目标的全部依赖。
- `$<`：当前目标的第一个依赖。

假设目录中有 `main.c` 和 `util.c`：

```text
make-demo/
├── Makefile
├── main.c
└── util.c
```

第一次 `make` 后：

```text
make-demo/
├── Makefile
├── main.c
├── main.o
├── util.c
├── util.o
└── myproc
```

`$(wildcard *.c)` 找到所有 `.c` 文件，`$(SRC:.c=.o)` 把每个源文件名转换成对应目标文件名。修改 `util.c` 后，make 只重编译 `util.o`，但仍需要重新链接最终程序。

`@` 放在配方命令前时，可以隐藏该命令本身，只显示命令产生的输出。初学阶段建议先不隐藏命令，方便观察 make 到底执行了什么。

## 5. Linux 第一个系统程序 - 进度条

### 5-1 补充 - 回车与换行

`\n` 和 `\r` 是两个不同的控制字符：

```text
\n：换行，移动到下一行
\r：回车，只回到当前行的开头
```

可以把它想象成老式打字机：回车把打印头移回左侧，换行把纸张向上推进一行。现代终端仍然保留这两个控制字符的语义。

```text
printf("10\\n");  → 输出 10 并换到下一行
printf("10\\r");  → 光标回到本行开头
```

进度条利用 `\r` 覆盖同一行：

```text
[##        ] 20%\r
[####      ] 40%\r
[######    ] 60%\r
```

在终端中，后两行可能覆盖前一行，看起来像一条不断变化的进度条；如果重定向到文件，`\r` 仍然是回车字符，文件中可能看到不同的控制字符效果。

### 5-2 行缓冲区

先看带换行的程序：

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hello bite!\n");
    sleep(3);
    return 0;
}
```

运行时通常立即看到 `hello bite!`，然后等待三秒退出，因为换行通常会触发行缓冲刷新。

去掉换行：

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hello bite!");
    sleep(3);
    return 0;
}
```

直接在终端运行时，可能仍会因为程序退出而看到输出；但在等待的三秒中不一定立即看到文字。原因是 `printf` 先把数据放进 `stdout` 缓冲区，输出设备和运行环境会影响何时刷新。

主动刷新：

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hello bite!");
    fflush(stdout);
    sleep(3);
    return 0;
}
```

`fflush(stdout)` 明确要求把 C 标准输出流中的数据交给底层输出设备，所以进度条每次刷新时通常都要调用它。

```text
printf 写入 stdout 缓冲区
        ↓
fflush(stdout)
        ↓
终端/文件描述符
```

需要注意：终端、管道和普通文件可能采用不同的缓冲策略。程序在终端运行能及时显示，不代表重定向到文件或管道时行为完全一样。

### 5-3 练手 - 倒计时程序

使用 `\r` 和 `fflush` 实现同一行倒计时：

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    for (int i = 10; i >= 0; --i)
    {
        printf("%-2d\\r", i);
        fflush(stdout);
        sleep(1);
    }
    printf("\n");
    return 0;
}
```

`%-2d` 为数字预留固定宽度，避免从两位数变成一位数后，前一次输出残留字符。例如：

```text
没有固定宽度：10 → 9，可能留下 90 的残影
固定宽度：     10 → 9 ，旧字符被空格覆盖
```

编译和运行：

```bash
$ gcc countdown.c -o countdown
$ ./countdown
0
```

屏幕中间过程是同一行覆盖，最终代码中的 `\n` 负责把光标移到下一行，让 Shell 提示符不会紧贴在 `0` 后面。

### 5-4 进度条代码

先看目录结构：

```text
process-demo/
├── process.h       # 对外声明
├── process.c       # 进度条实现
├── main.c          # 模拟下载并调用进度条
└── Makefile        # 自动编译
```

`process.h`：

```c
#pragma once

void process_v1(void);
void FlushProcess(double total, double current);
```

`process.c`：

```c
#include "process.h"
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define BAR_WIDTH 50
#define STYLE '#'

void process_v1(void)
{
    char buffer[BAR_WIDTH + 1] = {0};
    const char *label = "|/-\\";
    int label_len = (int)strlen(label);

    for (int current = 0; current <= BAR_WIDTH; ++current)
    {
        memset(buffer, ' ', BAR_WIDTH);
        buffer[BAR_WIDTH] = '\0';
        for (int i = 0; i < current; ++i)
        {
            buffer[i] = STYLE;
        }
        printf("[%-50s][%3d%%][%c]\\r",
               buffer, current * 100 / BAR_WIDTH,
               label[current % label_len]);
        fflush(stdout);
        usleep(50000);
    }
    printf("\n");
}

void FlushProcess(double total, double current)
{
    static int animation = 0;
    char buffer[BAR_WIDTH + 1] = {0};
    const char *label = "|/-\\";
    int filled = (int)(current * BAR_WIDTH / total);

    if (filled > BAR_WIDTH)
    {
        filled = BAR_WIDTH;
    }
    for (int i = 0; i < filled; ++i)
    {
        buffer[i] = STYLE;
    }
    for (int i = filled; i < BAR_WIDTH; ++i)
    {
        buffer[i] = ' ';
    }

    printf("[%-50s][%5.1f%%][%c]\\r",
           buffer, current * 100.0 / total,
           label[animation % 4]);
    fflush(stdout);
    ++animation;
}
```

这里有几个关键点：

```text
current / total       当前完成比例
filled                进度条中应该填充多少个字符
static animation      多次调用之间保留动画下标
fflush(stdout)        让每一帧及时显示
\r                    回到当前行开头覆盖上一帧
```

`buffer` 需要预留结尾的 `\0`，因为它要作为 C 字符串传给 `printf`。进度达到 100% 时要避免下标越过数组边界。

`main.c`：

```c
#include "process.h"
#include <stdio.h>
#include <unistd.h>

static void Download(void)
{
    const double total = 100.0;
    double current = 0.0;

    while (current <= total)
    {
        FlushProcess(total, current);
        usleep(30000);  // 模拟下载数据到达
        current += 1.0;
    }
    printf("\ndownload %.1fMB Done\n", total);
}

int main(void)
{
    Download();
    return 0;
}
```

Makefile：

```makefile
CC := gcc
CFLAGS := -Wall -Wextra -g
SRC := $(wildcard *.c)
OBJ := $(SRC:.c=.o)
BIN := processbar

$(BIN): $(OBJ)
	$(CC) $(CFLAGS) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

.PHONY: clean
clean:
	rm -f $(OBJ) $(BIN)
```

注意 `.PHONY: clean` 后面必须有 `clean`，而且命令行前面必须是 Tab。构建和运行：

```bash
$ make
 gcc -Wall -Wextra -g -c main.c -o main.o
 gcc -Wall -Wextra -g -c process.c -o process.o
 gcc -Wall -Wextra -g main.o process.o -o processbar

$ ./processbar
[##                                                ][  4.0%][|]
……中间刷新覆盖同一行……
[##################################################][100.0%][-]
download 100.0MB Done
```

真实终端不会把每一帧都换成新行，因为输出使用了 `\r`。这里用多行展示“开始、中间、完成”三个关键状态，便于阅读。

## 6. 版本控制器 Git

### 6-1 版本控制器

如果没有版本控制，项目目录可能变成：

```text
report-v1
report-v2
report-final
report-final-new
report-final-really-new
```

问题不只是文件多，而是你很难知道每份文件改了什么、哪一份是可靠版本、谁在什么时候修改了哪一部分。

Git 把项目变化记录成提交：

```text
工作区：正在编辑的文件
   ↓ git add
暂存区：准备进入下一次提交的内容
   ↓ git commit
本地仓库：本机保存的历史提交
   ↓ git push
远端仓库：团队或服务器共享的提交
```

Git 是分布式版本控制系统。很多历史操作在本地就能完成，不必每次查看差异都连接网络。

### 6-2 git 简史

Git 诞生于 Linux 内核项目对大型、分布式协作的需求。2005 年前后，Linux 社区需要一个速度快、支持大量分支、能够离线工作、适合管理超大项目的版本控制工具。

Git 的重要思想包括：

- 提交历史保存在本地，不依赖远端才能查看。
- 每次提交记录一组确定的项目状态和父提交。
- 分支是指向提交的可移动引用，不是复制一份完整项目。
- 合并用于把不同开发线的历史组合起来。

因此，Git 不只是“上传文件工具”。`commit` 是本地历史记录，`push` 才是向远端同步。

### 6-3 安装 git

CentOS/RHEL 系可以使用：

```bash
$ sudo yum install git
```

较新的发行版可能使用：

```bash
$ sudo dnf install git
```

Ubuntu 使用：

```bash
$ sudo apt update
$ sudo apt install git
```

安装后验证：

```bash
$ git --version
git version 2.x.y
$ command -v git
/usr/bin/git
```

版本号因发行版和安装时间而变化，不要把课件中的 `1.8.3.1` 当成固定输出。初次使用还应配置提交身份：

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global --list
```

提交身份写入提交元数据，不等于远端登录密码。不要把真实令牌写进仓库或公开截图。

### 6-4 在 Github 创建项目

远端仓库的基本流程是：

```text
注册/登录代码托管平台
        ↓
创建一个空仓库或按平台提示初始化
        ↓
复制 HTTPS 或 SSH 仓库地址
        ↓
git clone 到本地
        ↓
在本地编辑、提交、推送
```

本地克隆示例：

```bash
$ mkdir -p ~/projects
$ cd ~/projects
$ git clone <repository-url>
Cloning into 'demo-project'...
remote: Enumerating objects: ...
Receiving objects: 100% (...), done.
$ cd demo-project
$ ls -la
.  ..  .git  README.md
```

`.git` 是 Git 的内部数据库，保存对象、引用和配置，不要手动删除或随意修改其中的文件。

如果使用已有本地项目关联远端：

```bash
git init
git remote add origin <repository-url>
git remote -v
```

现代代码托管平台通常不允许直接使用账户密码进行 Git HTTPS 推送，可能需要个人访问令牌或 SSH 密钥。认证失败时，检查远端地址、令牌权限、SSH 公钥和当前分支，不要把令牌粘贴到聊天记录或提交历史中。

### 6-5 三板斧

准备一个本地项目：

```text
git-demo/
├── .git/
├── .gitignore
├── README.md
└── hello.c
```

第一步：查看状态。

```bash
$ git status
On branch main
No commits yet
Untracked files:
  hello.c
  README.md
```

此时文件在工作区，Git 已经知道目录存在，但还没有把它们放入下一次提交。

第二步：加入暂存区。

```bash
$ git add hello.c README.md
$ git status
Changes to be committed:
  new file:   README.md
  new file:   hello.c
```

`git add` 的含义不是“永久提交”，而是选择下一次 commit 要包含的内容。修改文件后，如果再次查看状态，可能同时出现“已暂存的旧版本”和“工作区还有未暂存的新修改”。

第三步：提交到本地仓库。

```bash
$ git commit -m "add hello program"
[main (root-commit) abc1234] add hello program
 2 files changed, ... insertions(+)
 create mode 100644 README.md
 create mode 100644 hello.c

$ git log --oneline
abc1234 (HEAD -> main) add hello program
```

这里的 `abc1234` 只是示例提交标识。`HEAD` 表示当前检出的提交位置。

修改 `hello.c` 后：

```bash
$ git diff
@@ -1,5 +1,5 @@
-int main(void) {
+int main(void)

$ git status
Changes not staged for commit:
  modified:   hello.c
```

确认修改后再次执行：

```bash
git add hello.c
git commit -m "format hello program"
git log --oneline --decorate -2
```

推送到远端：

```bash
git remote add origin <repository-url>
git push -u origin main
```

第一次推送可能需要认证和设置上游分支。没有可用远端时，可以先完整练习本地的 `status/add/commit/log/diff`，不要为了演示 push 随意使用未知仓库。

### 4. 其他

常用辅助命令：

```bash
git status              # 查看当前状态
git log --oneline       # 简洁查看历史
git diff                # 查看未暂存修改
git diff --staged       # 查看已暂存修改
git pull                # 拉取并整合远端更新
git branch              # 查看分支
git switch -c feature   # 创建并切换分支
```

`.gitignore` 用于告诉 Git 哪些未跟踪文件不应进入暂存区：

```gitignore
*.o
build/
*.log
.vscode/
```

注意：`.gitignore` 只对尚未被跟踪的文件有效。如果某个文件已经提交过，后来才写入 `.gitignore`，它不会自动从历史中消失。

出现冲突时，不要直接覆盖别人的修改。先查看冲突标记：

```text
<<<<<<< HEAD
当前分支内容
=======
另一条分支内容
>>>>>>> feature
```

手工编辑为最终版本后，再 `git add` 和 `git commit`。高风险操作如 `reset --hard`、强制推送会丢失本地或远端历史，使用前必须确认备份和影响范围。

## 7. 调试器 - gdb/cgdb 使用

### 7-1 样例代码

准备一个能计算 `1 + 2 + ... + 100` 的程序：

```c
// mycmd.c
#include <stdio.h>

static int Sum(int start, int end)
{
    int result = 0;
    for (int i = start; i <= end; ++i)
    {
        result += i;
    }
    return result;
}

int main(void)
{
    int start = 1;
    int end = 100;
    int result = Sum(start, end);
    printf("sum(%d, %d) = %d\n", start, end, result);
    return 0;
}
```

正常运行：

```bash
$ gcc mycmd.c -o mycmd-release
$ ./mycmd-release
sum(1, 100) = 5050
```

项目目录：

```text
gdb-demo/
├── mycmd.c
└── mycmd-release
```

### 7-2 预备

Linux gcc 默认可以编译出可执行程序，但默认不一定包含足够的源代码级调试信息。没有 `-g` 不是“无法编译”，而是 gdb 可能只能看到汇编、地址或无法显示变量。

对比编译：

```bash
$ gcc mycmd.c -O2 -o mycmd-release
$ gcc mycmd.c -O0 -g -o mycmd-debug

$ file mycmd-release
mycmd-release: ELF 64-bit ... dynamically linked ... not stripped

$ file mycmd-debug
mycmd-debug: ELF 64-bit ... with debug_info ... not stripped
```

具体 `file` 输出会因 gcc、链接器和系统不同而变化；重点观察调试版包含 `debug_info` 等调试信息。

```text
gdb-demo/
├── mycmd.c
├── mycmd-release    # 更接近发布构建
└── mycmd-debug      # 带源代码级调试信息
```

启动调试器：

```bash
gdb ./mycmd-debug
```

退出可以输入：

```text
(gdb) quit
```

程序正在运行时，`Ctrl+D` 并不是所有场景下都适合退出；初学阶段使用 `quit` 更明确。

### 7-3 常见使用

先用一个最小调试会话理解流程：

```text
(gdb) list main
(gdb) break main
(gdb) run
(gdb) next
(gdb) print start
(gdb) info locals
(gdb) finish
(gdb) quit
```

命令作用：

| 命令 | 作用 | 示例 |
|---|---|---|
| `list`/`l` | 查看源代码 | `list main` |
| `run`/`r` | 从头运行 | `run` |
| `break`/`b` | 设置断点 | `break main`、`break 15` |
| `next`/`n` | 单步但不进入函数 | `next` |
| `step`/`s` | 单步并进入函数 | `step` |
| `continue`/`c` | 继续到下一个断点 | `continue` |
| `print`/`p` | 打印表达式 | `p result` |
| `info locals` | 查看局部变量 | `info locals` |
| `backtrace`/`bt` | 查看调用栈 | `bt` |
| `finish` | 运行到当前函数返回 | `finish` |
| `delete` | 删除断点 | `delete 1` |
| `quit` | 退出 gdb | `quit` |

可复现的示例会话：

```text
$ gdb ./mycmd-debug
(gdb) list main
8       }
9
10      int main(void)
11      {
12          int start = 1;
13          int end = 100;
14          int result = Sum(start, end);
15          printf("sum(%d, %d) = %d\\n", start, end, result);
16          return 0;
17      }
(gdb) break 14
Breakpoint 1 at ...: file mycmd.c, line 14.
(gdb) run
Breakpoint 1, main () at mycmd.c:14
14          int result = Sum(start, end);
(gdb) next
15          printf("sum(%d, %d) = %d\\n", start, end, result);
(gdb) print result
$1 = 5050
(gdb) info locals
start = 1
end = 100
result = 5050
(gdb) continue
sum(1, 100) = 5050
[Inferior ... exited normally]
(gdb) quit
```

`next` 执行当前源代码行，但遇到函数调用时通常不进入函数内部；如果想观察 `Sum` 内部，应在调用行使用 `step`：

```text
(gdb) break 14
(gdb) run
(gdb) step
Sum (start=1, end=100) at mycmd.c:5
```

### 7-4 常见技巧 - 加餐

当普通断点只能告诉你“程序停在这里”，但不能解释“变量什么时候变错”时，可以使用 watch、临时修改变量和条件断点。

#### 7-4-1 watch

把程序改成容易观察的形式：

```c
static int Sum(int start, int end)
{
    int result = 0;
    for (int i = start; i <= end; ++i)
    {
        result += i;
    }
    return result;
}
```

进入函数后观察 `result`：

```text
(gdb) break Sum
(gdb) run
Breakpoint 1, Sum (start=1, end=100) at mycmd.c:5
(gdb) watch result
Hardware watchpoint 2: result
(gdb) continue
Hardware watchpoint 2: result
Old value = 0
New value = 1
(gdb) continue
Hardware watchpoint 2: result
Old value = 1
New value = 3
(gdb) continue
Hardware watchpoint 2: result
Old value = 3
New value = 6
```

`watch result` 会在表达式的值发生变化时暂停。循环次数很多时，可以在看到规律后删除观察点：

```text
(gdb) delete 2
```

不同机器可能显示 software watchpoint 或 hardware watchpoint，停下的具体时机也可能略有差异，但核心含义相同：变量发生了变化。

#### 7-4-2 set var 确定问题原因

故意增加一个错误标志：

```c
static int flag = 0;  // 故意制造错误

static int Sum(int start, int end)
{
    int result = 0;
    for (int i = start; i <= end; ++i)
    {
        result += i;
    }
    return result * flag;
}
```

重新编译调试版，程序输出：

```bash
$ ./mycmd-debug
sum(1, 100) = 0
```

进入 gdb 检查：

```text
(gdb) break Sum
(gdb) run
(gdb) until 9
(gdb) print result
$1 = 5050
(gdb) print flag
$2 = 0
(gdb) set var flag = 1
(gdb) print flag
$3 = 1
(gdb) next
(gdb) finish
Value returned is $4 = 5050
```

此时在内存中的当前调试进程里把 `flag` 临时改成了 1，验证了问题与 `flag` 有关。`set var` 不会修改磁盘上的 `mycmd.c`，退出 gdb 后重新运行仍会回到源码中的 `flag = 0`。要永久修复，必须修改源代码、重新编译并验证。

#### 7-4-3 条件断点

普通断点可能在循环中停 100 次；条件断点只在满足条件时停下。

##### 7-4-3-1 添加条件断点

假设 `result += i` 位于第 8 行，可以直接添加条件：

```text
(gdb) break mycmd.c:8 if i == 30
Breakpoint 2 at ...: file mycmd.c, line 8.
(gdb) continue
Breakpoint 2, Sum (start=1, end=100) at mycmd.c:8
(gdb) print i
$1 = 30
(gdb) print result
$2 = 435
```

这里的语法是：

```text
break 行号 if 条件
```

断点只有在执行到该行且 `i == 30` 时才会真正暂停。

##### 7-4-3-2 给已经存在的断点新增条件

如果断点编号是 2，可以在已有断点上追加条件：

```text
(gdb) break mycmd.c:8
Breakpoint 2 at ...
(gdb) condition 2 i == 30
(gdb) info breakpoints
Num  Type        Disp Enb  Address  What
2    breakpoint  keep y             stop only if i == 30
```

两种写法不要混淆：

```text
新增条件断点：break 8 if i == 30
修改已有断点：condition 2 i == 30
```

`cgdb` 是 gdb 的一个界面增强工具，通常在上方显示源代码、下方保留 gdb 命令窗口。它改变的是交互界面，不改变断点、单步、观察变量等调试机制。先掌握 gdb，再使用 cgdb 会更稳妥。

## 附录

附录中的换源命令可能直接修改系统软件源，属于高风险操作。必须先确认发行版、版本代号、备份位置和网络环境，不要把 CentOS 7 的旧地址直接套到新系统。

### Centos7 更新 yum 源

CentOS 7 已经比较老，官方源生命周期和镜像站策略可能发生变化。更换前先查看当前系统：

```bash
cat /etc/centos-release
uname -m
ls -l /etc/yum.repos.d/
```

推荐流程：

```text
确认系统版本
    ↓
备份 repo 文件
    ↓
准备与版本匹配的新配置
    ↓
清理缓存
    ↓
生成缓存并检查 repolist
    ↓
只安装一个小软件包验证
```

备份示例：

```bash
sudo mkdir -p /etc/yum.repos.d/backup
sudo cp -a /etc/yum.repos.d/*.repo /etc/yum.repos.d/backup/
```

备份后再查看：

```bash
ls -l /etc/yum.repos.d/backup/
```

不要未经核对就使用网络上的 `curl -o /etc/yum.repos.d/...` 命令覆盖配置。确认新源文件的发行版版本、架构和镜像站官方说明后，再放入配置目录。

更新缓存并验证：

```bash
sudo yum clean all
sudo yum makecache
sudo yum repolist
```

输出中重点观察仓库是否启用、是否有错误、仓库总数是否正常。不要把 `yum update` 作为“验证换源”的第一步；更新整个系统可能带来大量包变更。

如果确认需要恢复，先检查备份内容，再恢复：

```bash
sudo cp -a /etc/yum.repos.d/backup/*.repo /etc/yum.repos.d/
sudo yum clean all
sudo yum repolist
```

### Ubuntu 更新 apt 源

先确认 Ubuntu 版本和代号：

```bash
cat /etc/os-release
. /etc/os-release && printf '%s\n' "$VERSION_CODENAME"
```

不同版本可能使用 `focal`、`jammy`、`noble` 等代号，不能把课件中的 `focal` 原样复制到其他版本。

先备份：

```bash
sudo cp -a /etc/apt/sources.list /etc/apt/sources.list.bak
sudo cp -a /etc/apt/sources.list.d /etc/apt/sources.list.d.bak
```

查看当前配置：

```bash
cat /etc/apt/sources.list
grep -RIn '^[[:space:]]*deb ' /etc/apt/sources.list.d/ 2>/dev/null
```

修改源时应以当前镜像站的官方文档为准，确保每行中的发行版代号和组件匹配。不要下载来源不明的整份配置文件直接覆盖系统文件。

更新索引：

```bash
sudo apt update
```

验证时重点看是否出现 `Err:`、签名错误、发行版代号不匹配或仓库不存在。安装一个已知的小包进行验证：

```bash
apt policy git
sudo apt install --no-install-recommends git
 git --version
```

`apt update` 只是更新软件包索引，不等于升级系统；`apt upgrade` 和 `apt full-upgrade` 可能改变大量软件包，执行前应阅读变更列表并做好备份。

恢复备份：

```bash
sudo cp -a /etc/apt/sources.list.bak /etc/apt/sources.list
sudo rm -rf /etc/apt/sources.list.d
sudo cp -a /etc/apt/sources.list.d.bak /etc/apt/sources.list.d
sudo apt update
```

上面的恢复命令具有破坏性，只有在确认备份目录内容、当前路径和恢复目标后才能执行。学习时可以只阅读流程，不必在真实服务器上更换源。
